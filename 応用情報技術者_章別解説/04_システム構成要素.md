# 第4章 システム構成要素

## この章の地図

システム構成要素は、コンピュータやサーバをどう組み合わせて、速く、止まりにくく、拡張しやすいシステムを作るかを学ぶ章です。

1 台のコンピュータで小さな処理をするだけなら、あまり構成を考えなくても動きます。しかし、全校生徒が同時にアクセスする学習システム、全国から注文が来る EC サイト、止まると業務が止まる銀行システムでは、1 台の機械だけで全部を抱えるのは危険です。処理をどこに置くか、故障したら誰が引き継ぐか、データをどこに保存するか、混雑したらどこが詰まるかを設計する必要があります。

この章では、集中処理と分散処理、クライアントサーバ、冗長化、クラスタ、ロードバランサ、RAID、NAS/SAN、仮想化、性能評価、待ち行列、稼働率をつなげて見ます。名前の違いより大切なのは、「その構成は、どんな困りごとを解決し、代わりにどんな複雑さを増やすのか」です。

## なぜこの章を学ぶのか

利用者から見ると、システムは「動くか、動かないか」「速いか、遅いか」に見えます。しかし中では、Web サーバ、アプリケーションサーバ、データベース、ストレージ、ネットワーク、認証、監視、バックアップが協力しています。どれか 1 つが遅い、壊れる、容量不足になるだけで、利用者には「サイトが使えない」と見えます。

たとえば EC サイトで商品ページが開けないとします。原因は Web サーバの CPU かもしれません。商品画像の配信が詰まっているのかもしれません。DB の検索が遅いのかもしれません。ロードバランサが故障しているのかもしれません。ストレージの I/O が遅いのかもしれません。システム構成を理解すると、「どこが詰まっているのか」「どこを二重化すべきか」「どこに予算を使うべきか」を考えられるようになります。

この章の目標は、構成名を選ぶことではありません。利用者に必要な速度、止められる時間、失ってよいデータ量、運用できるコストを考えて、システム全体を設計する目を持つことです。

## 4.1 処理をどこに置くか

学校の成績管理システムを考えます。すべての成績データを 1 台の中央サーバに集めると、管理はしやすくなります。データが 1 か所にあるので、同じ生徒の成績が場所によって違う、という問題も起きにくくなります。権限管理やバックアップも中央でまとめて行えます。

このように、処理やデータを 1 か所に集める構成を集中処理といいます。集中処理は、管理しやすく、データの一貫性を保ちやすい構成です。一貫性とは、データのつじつまが合っていることです。たとえば、成績表と進級判定で同じ点数を見ている状態が一貫している状態です。

一方で、中央サーバが止まると全員が使えなくなります。全校生徒が一斉にアクセスすると、負荷が 1 か所に集中します。遠くの利用者から見ると通信が遅くなることもあります。

そこで、複数のコンピュータに処理を分ける構成が出てきます。これを分散処理といいます。たとえば、Web 画面を返すサーバを複数台にし、画像配信は CDN に任せ、検索は検索専用サーバに任せ、注文処理はキューで順番に処理する、といった分け方です。

分散処理の良さは、負荷を分けやすく、段階的に台数を増やせることです。1 台が壊れても、他のサーバで一部の処理を続けられる場合があります。反対に難しさは、全体の状態をそろえることです。複数の場所に同じデータを持つと、「どれが最新か」を決める必要があります。ネットワーク障害で一部だけ孤立することもあります。

集中処理と分散処理は、どちらかが絶対に上ではありません。重要なのは、守りたいものです。成績や会計のように強い一貫性が必要なデータは中央管理が向くことがあります。動画配信や画像配信のように、多くの利用者へ同じデータを速く届けたい場合は分散が向くことがあります。

## 4.2 クライアントサーバと3層構造

スマホアプリでログインボタンを押すと、スマホの中だけで処理が完結しているわけではありません。スマホは、入力された ID とパスワードをサーバへ送り、サーバが本人確認をし、結果を返します。このとき、スマホのように依頼する側をクライアント、機能を提供する側をサーバといいます。

クライアントは、利用者に近い場所で画面表示や入力を担当します。サーバは、共通のデータ管理、認証、業務処理を担当します。こう分けると、利用者の端末が変わっても、中央の業務ルールを共通化できます。スマホ、PC、タブレットが同じ成績データを見られるのは、裏側のサーバが共通だからです。

Web システムでは、よく 3 層構造で考えます。

```text
プレゼンテーション層 -> アプリケーション層 -> データ層
```

プレゼンテーション層は、画面や利用者とのやり取りを担当します。Web ブラウザやスマホアプリの画面がここに当たります。アプリケーション層は、業務ロジックを担当します。業務ロジックとは、その業務で守るべきルールです。たとえば「在庫が 0 の商品は注文できない」「成績は 0 から 100 の間」「承認者だけが申請を承認できる」といったルールです。データ層は、データベースやファイルを管理します。

3 層に分ける理由は、変更の影響を小さくするためです。画面のデザインを変えても、データベースの表をすべて作り直す必要はありません。データベースを高速化しても、利用者の画面の操作方法は変えずに済みます。

MVC も、責任を分ける考え方です。Model はデータと業務ルール、View は表示、Controller は入力を受けて Model と View をつなぐ役割です。たとえば欠席連絡アプリなら、欠席連絡の内容や登録ルールが Model、保護者に見える入力画面が View、送信ボタンを押したときに登録処理へつなぐ部分が Controller です。

ここで大事なのは、層や役割の名前そのものではありません。画面、業務ルール、データ保存を混ぜすぎると、変更が難しくなります。画面を少し変えるだけで成績計算の処理が壊れるような作りは、責任分担ができていません。

## 4.3 壊れることを前提にする信頼性設計

システムは必ず壊れます。ディスクは故障します。ネットワークは切れます。電源は落ちます。ソフトウェア更新で不具合が入ることもあります。人が設定を間違えることもあります。

信頼性設計で大事なのは、「壊れないはず」と願うことではありません。「壊れたときに、利用者への影響をどこまで小さくできるか」を考えることです。

高い信頼性が必要な場面では、同じ処理を 2 系統で同時に行い、結果を照合する構成があります。これをデュアルシステムといいます。たとえば、重要な制御システムで 2 つの処理結果が一致するか確認すれば、片方の異常に気づきやすくなります。ただし、同じものを 2 系統動かすため高価です。

一方、通常は主系が動き、故障時に待機系へ切り替える構成をデュプレックスシステムといいます。主系とは普段使っている側、待機系とは引き継ぐために用意している側です。

待機系にも準備の度合いがあります。ホットスタンバイは、待機系もすぐ動ける状態で動作しているため、切替が速い方式です。ウォームスタンバイは、ある程度準備してあるが、切替には少し作業が必要な方式です。コールドスタンバイは、普段は停止していて、故障時に起動や設定を行う方式です。速く復旧できるほど便利ですが、その分コストや運用負荷が増えます。

災害対策では、RTO と RPO が重要です。RTO は Recovery Time Objective の略で、どれくらいの時間で復旧するかという目標です。たとえば RTO が 2 時間なら、障害発生から 2 時間以内にサービスを使える状態へ戻すことを目指します。

RPO は Recovery Point Objective の略で、どの時点のデータまで戻せるかという目標です。RPO が 15 分なら、最悪でも 15 分前のデータまでは戻せるようにする、という意味です。

RTO と RPO は似ていますが、守るものが違います。RTO は止まっている時間、RPO は失う可能性があるデータの時間幅です。たとえば、システムは 10 分で起動できても、バックアップが 1 日前なら、復旧は速いがデータは 1 日分失われる可能性があります。

## 4.4 複数台でさばくクラスタとロードバランサ

利用者が増えると、1 台のサーバでは処理しきれなくなります。そこで複数のサーバをまとめて、1 つのシステムのように使います。これをクラスタリングといいます。

クラスタには、大きく 2 つの目的があります。1 つは可用性を高めることです。可用性とは、使いたいときに使える性質です。1 台が故障しても別のサーバが引き継げば、利用者への影響を小さくできます。もう 1 つは負荷分散です。複数台でリクエストを分担すれば、全体として多くの利用者に対応できます。

Web サーバを複数台にしたとき、利用者から来たリクエストをどのサーバへ送るか決める装置や仕組みがロードバランサです。ロードバランサは、順番に振り分けたり、接続数が少ないサーバへ送ったり、性能の高いサーバへ多めに送ったりします。

ただし、ロードバランサを置くだけで全部解決するわけではありません。ログイン状態やカートの中身のようなセッション情報をどこに置くかが問題になります。セッション情報とは、利用者が一連の操作をしている間、その利用者を識別するための情報です。

もしセッション情報を各 Web サーバの中だけに置くと、最初のリクエストはサーバ A、次のリクエストはサーバ B に送られたとき、サーバ B は利用者のログイン状態を知りません。これを防ぐには、同じ利用者を同じサーバへ送る、セッション情報を共有ストアに置く、サーバ間でセッションを複製する、などの設計が必要です。

クラスタリングは「台数を増やせば速くなる」という単純な話ではありません。複数台にした後も、共有データベース、ファイル保存、セッション、ネットワーク、外部 API が詰まることがあります。どこが全体のボトルネックかを見る必要があります。ボトルネックとは、全体の性能を制限している一番細い部分です。

グリッドコンピューティングは、ネットワーク上の多数のコンピュータを束ね、大きな計算を分担する考え方です。クラスタが比較的まとまった管理下の複数台を 1 つのシステムとして使うのに対し、グリッドは地理的にも組織的にも離れた計算資源を組み合わせる発想が強くなります。科学技術計算や大量データ処理で、空いている計算資源を活用する考え方につながります。

Hadoop は、大量データを複数台のサーバに分散して保存し、分散処理するための基盤として広く知られた技術です。中心になる考え方は、巨大な 1 台を買うのではなく、複数台にデータを分け、処理もデータの近くで分担することです。HDFS は Hadoop Distributed File System の略で、大きなファイルをブロックに分け、複数ノードに複製して保存します。ノードとは、ネットワーク上で処理や保存を担うコンピュータのことです。

MapReduce は、処理を `Map` と `Reduce` に分ける考え方です。`Map` は各データ片から中間結果を作り、`Reduce` は同じキーの中間結果を集約します。たとえば大量のアクセスログから URL ごとのアクセス回数を数えるなら、各ノードが自分の持つログを読んで「この URL が 1 回」という中間結果を出し、最後に URL ごとに合計します。Hadoop を学ぶ意味は、製品名を知ることではありません。大量データでは「保存場所」「処理場所」「故障しても続ける仕組み」を一体で設計する必要がある、と理解することです。

## 4.5 ストレージは容量だけで選ばない

ストレージは、データを保存する装置や仕組みです。アプリケーションは再インストールできても、注文履歴、成績、顧客情報、研究データを失うと取り返しがつかないことがあります。だからストレージ設計では、容量だけでなく、速度、故障への強さ、復旧時間、共有しやすさ、バックアップを考えます。

RAID は、複数のディスクを組み合わせて、性能や信頼性を高める技術です。RAID 0 はストライピングです。データを複数ディスクに分けて書くため速くできますが、どれか 1 台が壊れると全体のデータが壊れます。重要データには単独では向きません。

RAID 1 はミラーリングです。同じデータを 2 台以上に書きます。1 台が壊れても別の 1 台から読めます。容量効率は悪くなりますが、考え方は単純で復旧しやすい方式です。

RAID 5 は、データとパリティを複数ディスクに分散して持ちます。パリティとは、故障したディスクの内容を復元するための情報です。1 台故障まで耐えられます。RAID 6 はパリティを二重に持つため、2 台故障まで耐えられます。その分、書込み性能や利用可能容量は不利になります。

RAID 10 は、ミラーリングとストライピングを組み合わせます。性能と信頼性のバランスが良い一方、必要なディスク本数が多くなります。

容量計算も、式が出てきた場面で意味を確認します。1TB のディスクを 4 台使う場合を考えます。

RAID 5 は、4 台のうち 1 台分相当をパリティに使います。したがってデータとして使えるのは、全体の 4 台分からパリティ 1 台分を引いた 3 台分です。

```text
RAID 5 の利用可能容量 = (4 - 1) × 1TB
                     = 3 × 1TB
                     = 3TB
```

なぜ `4 - 1` なのかというと、4 台のうち 1 台分を復旧用情報に使うからです。

RAID 6 は、2 台分相当を二重パリティに使います。

```text
RAID 6 の利用可能容量 = (4 - 2) × 1TB
                     = 2 × 1TB
                     = 2TB
```

RAID 1 は同じデータを複数台へコピーするため、同じ 1TB ディスクを 2 台使っても、見かけ上使える容量は 1TB です。増えるのは容量ではなく、故障への強さです。

ストレージの接続方法にも違いがあります。DAS は Direct Attached Storage の略で、サーバに直接つながったストレージです。単純で分かりやすい一方、複数サーバから共有しにくいことがあります。

NAS は Network Attached Storage の略で、ネットワーク越しにファイル単位で共有します。学校の共有フォルダのように、ファイル名やフォルダ構造で扱います。SAN は Storage Area Network の略で、ブロック単位で高速にストレージを扱う構成です。大規模なデータベースや仮想化基盤で使われます。

ここでいうファイル単位とブロック単位の違いも重要です。ファイル単位では「成績.xlsx を開く」のように、ファイルとして扱います。ブロック単位では、OS からはディスクの一部のように見え、より低いレベルで読み書きします。

ストレージ仮想化は、複数の物理ディスクやストレージ装置をまとめ、利用者やサーバからは 1 つの大きなストレージのように見せる技術です。仮想化という言葉は「実物がない」という意味ではありません。実物はあります。ただし、実物の細かい場所や構成を隠し、使いやすい形に見せます。サーバから見ると 10TB の領域に見えていても、裏側では複数の装置に分散していたり、後から容量を足せる構成になっていたりします。

シンプロビジョニングは、見かけ上は大きな容量を割り当て、実際に書き込まれた分だけ物理容量を使う方式です。たとえば 100 人に 100GB ずつ割り当てると、見かけ上は `100 × 100GB = 10000GB`、つまり 10TB が必要に見えます。ここで `100 × 100GB` は「人数 × 1 人あたり容量」です。10000GB を TB に直すと、おおよそ 10TB です。しかし全員が最初から 100GB 使うとは限らないので、実際の物理容量は 3TB から始め、利用状況を見ながら増やす設計ができます。便利ですが、全員が一斉に容量を使うと足りなくなる危険があります。見かけの割当量と実容量の差を監視しないと、ある日突然書き込めなくなります。

スナップショットは、ある時点の状態を切り出して残す仕組みです。ファイルや仮想マシンを更新する前にスナップショットを取れば、更新失敗時にその時点へ戻しやすくなります。ただし、スナップショットはバックアップそのものではありません。同じ装置の中に差分として持っているだけなら、その装置全体が壊れたときに一緒に失われます。バックアップは、別の場所、別の装置、別の権限で保管することまで考えます。

レプリケーションは、データを別の場所へ複製することです。同期レプリケーションでは、両方に書けたことを確認してから完了にします。データを失いにくい一方、遠くの拠点との通信が遅いと書込み全体も遅くなります。非同期レプリケーションでは、まず近くへ書いて完了にし、後から遠くへ送ります。速くしやすい一方、障害直前の更新がまだ送られていない可能性があります。これは RPO とつながります。RPO が 0 に近いほど失ってよいデータ時間は短く、同期や頻繁な複製が必要になります。

そして、RAID はバックアップではありません。RAID はディスク故障には備えられますが、誤削除、ランサムウェア、アプリのバグによるデータ破壊、災害には弱い場合があります。バックアップは、別の場所や別の時点にデータを戻せるようにする仕組みです。

## 4.6 仮想化は物理資源を使いやすい形に見せる

仮想化は、物理的な CPU、メモリ、ディスク、ネットワークを、ソフトウェアで柔軟に分けて使う技術です。1 台の物理サーバの上に複数の仮想マシンを作れば、それぞれが別のサーバのように振る舞います。

仮想マシンは、OS ごと分離された仮想的なコンピュータです。開発用、検証用、本番用を分けたり、古い OS を動かしたり、サーバを別の物理機へ移したりしやすくなります。

仮想化には、ホスト型とハイパーバイザ型があります。ホスト型は、普段使う OS の上に仮想化ソフトを入れて、その上で仮想マシンを動かします。個人の PC で検証環境を作る場面に向きます。ハイパーバイザ型は、ハードウェア上で直接仮想化層を動かします。サーバ用途ではこちらが使われることが多く、性能や管理に優れます。

コンテナは、仮想マシンとは少し違います。コンテナは OS カーネルを共有しながら、アプリケーションの実行環境を分離します。仮想マシンより軽く、起動も速いことが多いです。ただし、OS まるごとを分ける仮想マシンとは分離の粒度が違います。

コンテナを 1 個だけ動かすなら、「軽い実行箱」として理解しても何とか扱えます。しかし本番システムでは、同じアプリケーションを複数個動かし、障害時に自動で立て直し、古い版から新しい版へ止めずに入れ替え、どのコンテナへ通信を流すかを決める必要があります。ここで使われる考え方がコンテナオーケストレーションです。オーケストレーションは、楽団の指揮のように、多数の部品を全体として動かすという意味です。

Kubernetes のようなオーケストレーション基盤では、「このアプリを 3 個動かしたい」「この条件を満たすサーバに置きたい」「異常なコンテナは作り直したい」という望ましい状態を宣言します。宣言とは、細かい手順を 1 つずつ命令するのではなく、最終的にどうなっていてほしいかを書くことです。たとえば `replicas = 3` と指定した場合、3 は動かしたいコンテナ数です。実際に 1 個が落ちて 2 個になれば、基盤は「望ましい状態との差が 1 個ある」と判断し、もう 1 個を起動して 3 個に戻そうとします。このとき、`3 - 2 = 1` という引き算は、不足数を求めるための計算です。左の 3 が目標、右の 2 が現在、差の 1 が追加すべき数を表します。

ただし、コンテナオーケストレーションは万能ではありません。アプリケーションが状態を自分のコンテナ内だけに持っていると、コンテナを作り直したときにデータが消えることがあります。ログをどこへ集めるか、秘密情報をどう渡すか、ネットワークをどう分離するか、データベースのような永続データをどう守るかも設計しなければなりません。コンテナは「配備しやすくする技術」であって、「正しい設計を自動で作る技術」ではありません。

サーバレスも、仮想化やクラウドと一緒に理解すると見通しがよくなります。サーバレスは「サーバが存在しない」という意味ではなく、利用者がサーバ台数、OS、実行環境の細かい管理を直接行わず、関数やイベント単位で処理を動かす方式です。たとえば、画像がアップロードされたら縮小画像を作る、問い合わせフォームが送信されたら通知する、といった処理に向きます。アクセスがない時間はほとんど動かず、必要なときだけ起動するため、使い方によっては費用や運用負担を下げられます。

一方で、サーバレスにはコールドスタートがあります。コールドスタートは、しばらく使われていなかった処理を起動するときに、実行環境の準備で遅れが出ることです。長時間動き続ける処理、細かい性能調整が必要な処理、状態を長く保持する処理では、普通のサーバやコンテナの方が扱いやすい場合があります。高度な構成判断では、「新しい技術だから使う」のではなく、起動頻度、処理時間、状態の持ち方、監視のしやすさ、障害時の追跡しやすさを比べます。

VDI は Virtual Desktop Infrastructure の略で、利用者のデスクトップ環境をサーバ側で動かし、端末から画面だけを操作する構成です。学校や企業では、端末を紛失してもデータを端末内に残しにくい、同じ環境を集中管理しやすい、古い端末でも一定の環境を使える、といった利点があります。一方で、ネットワークが遅いと操作感が悪くなり、サーバ側に負荷が集中します。VDI は端末管理とセキュリティに効きますが、ネットワークとサーバ基盤の設計が重要です。

仮想化の利点は、資源利用率を高められることです。物理サーバを 1 業務に 1 台ずつ用意すると、CPU やメモリが余ることがあります。仮想化すれば、複数の業務を 1 台に集約し、必要に応じて移動や複製ができます。

一方で、仮想化は見えない依存関係を増やします。1 台の物理サーバの上に多くの仮想マシンを載せると、その物理サーバが故障したときに多くのシステムへ影響します。ストレージやネットワークが共有されるため、どこが詰まっているか分かりにくくなることもあります。

## 4.7 「遅い」を分解する性能指標

利用者が「遅い」と言うとき、その意味は 1 つではありません。ボタンを押してから最初の反応が遅いのか、処理が最後まで終わるのが遅いのか、同時に処理できる件数が少ないのか、混雑時だけ遅いのかで、見るべき指標が違います。

レスポンスタイムは、要求してから最初の応答が返るまでの時間です。Web ページでボタンを押して、画面が反応し始めるまでの時間に近い感覚です。

ターンアラウンドタイムは、要求してから処理が完全に終わるまでの時間です。成績集計を依頼して、集計ファイルが完成するまでの時間のように、全体の完了時間を見ます。

スループットは、単位時間あたりに処理できる量です。1 秒に何件の注文を処理できるか、1 分に何枚の画像を変換できるか、といった指標です。

利用率は、CPU やディスクなどの資源がどれくらい使われているかです。利用率が低すぎると資源が余っています。しかし高ければ高いほど良いわけでもありません。利用率が高すぎると、少しの揺らぎで待ち時間が急増します。

性能評価では、ベンチマーク、モニタリング、キャパシティプランニングを使います。ベンチマークは、標準的な負荷をかけて性能を比較することです。モニタリングは、CPU、メモリ、I/O、ネットワーク、エラー数などを継続して見ることです。キャパシティプランニングは、将来の利用者数やデータ量を見積もり、必要な資源を計画することです。

近年の運用では、可観測性という考え方も重要です。可観測性は、外から見える情報を使って、システム内部で何が起きているかを理解できる性質です。代表的な材料は、メトリクス、ログ、トレースです。メトリクスは CPU 使用率、応答時間、エラー率のような数値です。ログは、いつ何が起きたかの記録です。トレースは、1 つのリクエストが Web サーバ、API、DB、外部サービスをどう通ったかを追う情報です。

たとえば「朝だけ遅い」という問い合わせが来たとします。CPU 使用率だけを見ると普通でも、トレースを見ると外部通知サービスで 800ms 待っているかもしれません。ログを見ると、特定クラスのデータだけエラーが多いかもしれません。メトリクス、ログ、トレースは別々の資料ではなく、障害の全体像を立体的に見るための材料です。

アラート設計も大切です。すべての小さな異常で通知すると、担当者は疲れて本当に重要な異常を見落とします。逆に通知が少なすぎると、利用者から言われるまで気づけません。良いアラートは、利用者影響に近く、対応行動につながります。CPU 使用率が高いだけでなく、「欠席登録の 5 分間エラー率が 5% を超えた」のように、サービスの失敗として見ると判断しやすくなります。

性能改善で大切なのは、測る前に決めつけないことです。CPU が遅いと思っていたら、実は DB のインデックス不足かもしれません。ネットワークが遅いと思っていたら、アプリケーションが同じデータを何度も読んでいるのかもしれません。測定値を見て、ボトルネックを特定します。

## 4.8 待ち行列理論は余裕の重要さを教える

レジ、病院、サーバ、ネットワーク、CPU など、依頼が来て処理する場所には待ち行列ができます。待ち行列理論は、混雑すると待ち時間がどう増えるかを考えるための道具です。

まず、記号を読みます。

`λ` は平均到着率です。ラムダと読みます。単位時間あたりに何件の依頼が来るかを表します。たとえば 1 秒に 8 件のリクエストが来るなら、`λ = 8 件/秒` です。

`μ` は平均サービス率です。ミューと読みます。単位時間あたりに何件処理できるかを表します。1 秒に 10 件処理できるサーバなら、`μ = 10 件/秒` です。

`ρ` は利用率です。ローと読みます。処理装置がどれくらい忙しいかを表します。

1 台の窓口なら、利用率は次の式で表せます。

```text
ρ = λ / μ
```

なぜ到着率をサービス率で割るのでしょうか。利用率は「処理能力のうち、どれだけ使っているか」だからです。1 秒に 10 件処理できるサーバへ 1 秒に 8 件来るなら、10 件分の能力のうち 8 件分を使っています。

```text
利用率 = 使っている量 / 処理できる量
       = 8 / 10
       = 0.8
       = 80%
```

これを記号にすると、使っている量が `λ`、処理できる量が `μ` なので、

```text
ρ = λ / μ
```

となります。

`ρ` が 1 に近づくと、待ち時間は急に大きくなります。`ρ >= 1` では、平均的に処理が追いつかず、待ち行列が増え続けます。

M/M/1 の代表的な式として、平均応答時間があります。

```text
平均応答時間 = 1 / (μ - λ)
```

この式で一番大事なのは、分母の `μ - λ` です。`μ` は処理できる量、`λ` は入ってくる量なので、`μ - λ` は余っている処理能力です。

```text
余っている処理能力 = μ - λ
```

たとえば、処理能力が 10 件/秒で、到着が 5 件/秒なら、

```text
μ = 10
λ = 5
μ - λ = 10 - 5 = 5
平均応答時間 = 1 / 5 = 0.2 秒
```

到着が 9 件/秒に増えると、

```text
μ = 10
λ = 9
μ - λ = 10 - 9 = 1
平均応答時間 = 1 / 1 = 1 秒
```

処理能力は同じ 10 件/秒なのに、余裕が 5 から 1 に減っただけで、平均応答時間は 0.2 秒から 1 秒に悪化します。

さらに `λ = 9.8` なら、

```text
μ - λ = 10 - 9.8 = 0.2
平均応答時間 = 1 / 0.2 = 5 秒
```

ここで高校数学としての割り算の意味を確認します。`1 / 0.2` は、0.2 を何倍すれば 1 になるかを求めています。0.2 は 1/5 なので、その逆数は 5 です。だから `1 / 0.2 = 5` です。

この式は、「利用率が高いほど効率が良い」と単純に考える危険を教えてくれます。余裕が分母にあるため、余裕が小さくなると待ち時間は急激に増えます。サーバ運用で CPU 100% を目指してはいけないのは、このためです。

待ち行列モデルは、ケンドール記号で表すことがあります。たとえば `M/M/1` は、到着間隔がランダム、サービス時間もランダム、窓口が 1 つというモデルです。最初の `M` は到着のばらつき、2 つ目の `M` は処理時間のばらつき、最後の `1` は窓口数を表します。ここでいうランダムは、毎回ぴったり同じ間隔で来るのではなく、確率的にばらつくという意味です。

`M/M/s` は、窓口が `s` 個あるモデルです。サーバが 1 台ではなく複数台ある状況に近いです。このとき利用率の考え方は、1 台の処理能力だけでなく、全体の処理能力で見ます。1 台が `μ` 件/秒処理できるサーバを `s` 台置くなら、全体の処理能力はおおよそ `sμ` 件/秒です。したがって利用率は次のように考えます。

```text
ρ = λ / (sμ)
```

たとえば、到着率 `λ = 18 件/秒`、1 台あたりのサービス率 `μ = 10 件/秒`、サーバ数 `s = 2` なら、

```text
sμ = 2 × 10 = 20
ρ = 18 / 20
  = 0.9
```

全体としては 90% の利用率です。1 台だけなら `18 / 10 = 1.8` で処理が追いつきませんが、2 台なら平均的には処理できます。ただし、利用率 90% は余裕が小さい状態です。到着のばらつきがあると、短時間にリクエストが集中し、待ち時間が大きくなることがあります。複数台に増やす設計でも、「平均では処理できる」だけでなく、ピーク時のばらつき、待ち時間、障害時に 1 台減った場合まで考えます。

M/M/s モデルで平均待ち時間をより詳しく見たいときは、「待たされる確率」と「待つことになったときの余裕」を分けて考えます。記号を先に短く整理します。`λ` は到着率、`μ` は 1 台あたりのサービス率、`s` はサーバ台数です。`a = λ / μ` は、処理負荷を 1 台分の能力で割った値で、トラフィック強度と呼ばれます。`ρ = a / s = λ / (sμ)` は、全体の利用率です。

待たされる確率を `P(wait)` とすると、M/M/s では次の形で計算できます。

```text
P(wait) =
  { a^s / (s! × (1 - ρ)) }
  /
  { Σ(n=0 から s-1 まで) a^n / n! + a^s / (s! × (1 - ρ)) }
```

見た目は重いですが、意味は「待ち行列ができる状態の重み」を「全状態の重み」で割っています。`!` は階乗です。たとえば `3! = 3 × 2 × 1 = 6` です。`Σ` は合計記号で、`n = 0` から `s - 1` まで順番に足すという意味です。

先ほどと同じく、`λ = 18`、`μ = 10`、`s = 2` で計算します。まず `a` を求めます。

```text
a = λ / μ
  = 18 / 10
  = 1.8
```

次に `ρ` を求めます。

```text
ρ = a / s
  = 1.8 / 2
  = 0.9
```

`s = 2` なので、合計部分は `n = 0` から `1` までです。

```text
Σ a^n / n! = a^0 / 0! + a^1 / 1!
```

ここで `a^0 = 1` です。どんな 0 でない数も 0 乗は 1 と決めます。また `0! = 1` です。これは組合せ計算で自然に成り立つように決められています。

```text
a^0 / 0! + a^1 / 1!
= 1 / 1 + 1.8 / 1
= 1 + 1.8
= 2.8
```

次に、待ち行列ができる側の重みを計算します。

```text
a^s / (s! × (1 - ρ))
= 1.8^2 / (2! × (1 - 0.9))
```

まず `1.8^2` は `1.8 × 1.8 = 3.24` です。`2!` は `2 × 1 = 2` です。`1 - 0.9 = 0.1` です。

```text
1.8^2 / (2! × (1 - 0.9))
= 3.24 / (2 × 0.1)
= 3.24 / 0.2
= 16.2
```

これを分子、そして `2.8 + 16.2` を分母に入れます。

```text
P(wait) = 16.2 / (2.8 + 16.2)
        = 16.2 / 19
        ≒ 0.853
```

約 85.3% の確率で待つ、という意味です。利用率 90% なので、ほとんど待たないように見えるかもしれませんが、ランダムな到着では待ちがかなり起きます。

平均待ち時間 `Wq` は、待たされる確率を、全体の余裕 `sμ - λ` で割ります。

```text
Wq = P(wait) / (sμ - λ)
```

この例では、

```text
sμ - λ = 2 × 10 - 18
       = 20 - 18
       = 2
```

なので、

```text
Wq = 0.853 / 2
   ≒ 0.426 秒
```

サービス時間そのものの平均は `1 / μ` です。`μ = 10 件/秒` なら、1 件あたりの平均処理時間は、

```text
1 / 10 = 0.1 秒
```

です。平均応答時間は、待ち時間と処理時間を足します。

```text
平均応答時間 = Wq + 1 / μ
            ≒ 0.426 + 0.1
            ≒ 0.526 秒
```

この計算から、サーバを 2 台にしても利用率が高いと待ち時間は無視できない、と分かります。性能設計では、平均到着率だけでなく、待たされる確率とピーク時の余裕まで見る必要があります。

キャパシティプランニングでは、現在の平均利用率だけで判断しません。利用者数の増加、季節変動、キャンペーン、データ量の増加、バックアップや集計処理の時間帯を見ます。さらに、垂直拡張と水平拡張を区別します。垂直拡張は 1 台の CPU やメモリを強くする方法です。水平拡張は台数を増やす方法です。水平拡張は柔軟ですが、ロードバランサ、セッション、DB、整合性の設計が必要になります。

動的な拡張性とは、負荷に応じて資源を増減しやすい性質です。クラウドでは、アクセスが増えた時間だけサーバ台数を増やし、落ち着いたら減らす設計ができます。これをオートスケーリングと呼ぶことがあります。ただし、アプリケーションが水平拡張に向いていなければ、台数を増やしても効果は出ません。セッションを各サーバ内にだけ持つ、DB が 1 台で詰まる、起動に時間がかかる、初期化処理が重い、といった問題があると、動的拡張はうまく働きません。拡張性はインフラだけでなく、アプリケーション設計とデータ設計の性質でもあります。

分散システムでは、整合性、可用性、分断耐性を同時に考えます。整合性は、どのノードに問い合わせても矛盾しない結果を得られる性質です。可用性は、障害や混雑があっても要求に応答できる性質です。分断耐性は、ネットワークが一部切れてもシステム全体として動き続ける性質です。ネットワーク分断とは、サーバ同士の通信が途中で切れ、互いの状態を確認できなくなることです。

CAP の考え方では、ネットワーク分断が起きている間、強い整合性と高い可用性を同時に完全には満たせないと考えます。たとえば、東日本のサーバと西日本のサーバが通信できなくなったとします。両方で注文を受け付け続ければ可用性は高いですが、同じ在庫を二重に売る危険があります。逆に、片方が相手を確認できるまで注文を止めれば整合性は守りやすいですが、利用者にはサービス停止として見えます。

結果整合性は、すぐには全ノードの値がそろわなくても、更新が伝わりきれば最終的に同じ状態へ近づくという考え方です。SNS の「いいね」数、検索インデックス、アクセス解析の集計のように、少し遅れても大きな問題になりにくい情報では有効です。一方、銀行残高、在庫引当、座席予約のように二重処理が許されない情報では、より強い整合性や排他制御が必要になります。分散システムの設計では、すべてを強くそろえるのではなく、どのデータにどの水準の整合性が必要かを分けます。

障害に強い通信設計では、リトライも注意が必要です。リトライは、失敗した要求をもう一度送ることです。ネットワークでは、相手が処理していないのか、処理したが返事だけ届かなかったのか分からないことがあります。このとき同じ注文登録を再送して二重登録されると困ります。そこで、同じ要求 ID は 1 回分として扱う冪等性を設計します。冪等とは、同じ操作を何度実行しても結果が変わらない性質です。

また、障害中の相手に何度も要求を送り続けると、相手の復旧をかえって遅らせることがあります。サーキットブレーカは、失敗が続いた相手への呼び出しを一時的に止め、時間をおいて少しずつ再開する考え方です。電気回路の遮断器と同じ発想で、壊れかけた依存先へ全要求を流し続けないようにします。タイムアウト、リトライ、バックオフ、冪等性、サーキットブレーカは、分散システムで「たまに失敗する通信」を前提にした設計部品です。

## 4.9 稼働率は壊れにくさと直しやすさで決まる

「かなり安定している」という表現だけでは、サービス水準や投資判断はできません。止まりにくさを数字で見るために、MTBF、MTTR、稼働率を使います。

MTBF は Mean Time Between Failures の略で、平均故障間隔です。平均してどれくらい動いてから故障するかを表します。長いほど壊れにくいといえます。

MTTR は Mean Time To Repair の略で、平均修理時間です。故障してから復旧するまでに平均どれくらいかかるかを表します。短いほど直しやすいといえます。

稼働率は、全体時間のうち正常に動いている時間の割合です。

```text
稼働率 = MTBF / (MTBF + MTTR)
```

この式は、「全体のうち、動いている部分の割合」を表します。割合を求める基本は、

```text
割合 = 部分 / 全体
```

です。ここでは、部分が正常に動いている時間、つまり MTBF です。全体は、正常に動いている時間と修理している時間を合わせたものなので、`MTBF + MTTR` です。

```text
部分 = MTBF
全体 = MTBF + MTTR
稼働率 = MTBF / (MTBF + MTTR)
```

たとえば、平均 1000 時間動いて、壊れたら平均 10 時間で直るなら、

```text
稼働率 = 1000 / (1000 + 10)
```

まず括弧の中を計算します。

```text
1000 + 10 = 1010
```

したがって、

```text
稼働率 = 1000 / 1010
       ≒ 0.9901
```

パーセントにするには 100 を掛けます。

```text
0.9901 × 100 ≒ 99.01%
```

この式から分かることは、可用性を上げる方法が 2 つあるということです。MTBF を長くして壊れにくくする方法と、MTTR を短くして早く直せるようにする方法です。高価な部品を使って壊れにくくするだけでなく、監視、自動復旧、手順書、訓練によって修理時間を短くすることも重要です。

直列システムでは、どれか 1 つが止まると全体が止まります。Web サーバと DB サーバがどちらも必要な構成なら、Web も DB も動いているときだけサービスが動きます。

```text
直列の全体稼働率 = A × B
```

なぜ掛け算するのでしょうか。全体が動くには、A が動くことと B が動くことが両方必要だからです。独立した 2 つの条件が両方成り立つ確率は掛け算で求めます。

```text
A の稼働率 = 0.9
B の稼働率 = 0.8
全体稼働率 = 0.9 × 0.8
           = 0.72
           = 72%
```

並列システムでは、どちらか 1 つが動いていれば全体が動く構成を考えます。この場合は、直接「動く場合」を数えるより、「両方止まる場合」を考える方が簡単です。

```text
並列の全体稼働率 = 1 - (1 - A)(1 - B)
```

`1 - A` は A が止まる確率です。`1 - B` は B が止まる確率です。両方止まる確率は `(1 - A)(1 - B)` です。全体が動く確率は、全体 1 から「両方止まる確率」を引けば求められます。

例として、A の稼働率が 0.9、B の稼働率が 0.8 なら、

```text
A が止まる確率 = 1 - 0.9 = 0.1
B が止まる確率 = 1 - 0.8 = 0.2
両方止まる確率 = 0.1 × 0.2 = 0.02
全体稼働率 = 1 - 0.02
           = 0.98
           = 98%
```

直列では 72% だったものが、並列では 98% になります。冗長化が可用性を大きく上げる理由です。ただし、実際には切替失敗、設定ミス、共通部品の故障、運用ミスがあるため、計算どおりにいくとは限りません。

FIT は、10 億時間あたりの故障回数を表します。部品レベルの信頼性評価で使われます。値が大きいほど、故障が多い部品と考えます。

## 4.10 可用性を年間停止時間で見る

稼働率 99.9% と聞くと、とても高く感じます。しかし、年間停止時間に直すと見え方が変わります。

年間停止時間は、1 年の時間に停止している割合を掛けて求めます。

```text
年間停止時間 = 365日 × 24時間 × (1 - 稼働率)
```

なぜ `1 - 稼働率` を使うのでしょうか。稼働率は「使える割合」です。停止している割合は、全体 `1` から使える割合を引いたものです。

稼働率 99.9% は、小数に直すと `0.999` です。パーセントは 100 分のいくつかを表すので、

```text
99.9% = 99.9 / 100 = 0.999
```

停止している割合は、

```text
1 - 0.999 = 0.001
```

1 年の時間は、

```text
365日 × 24時間 = 8760時間
```

したがって、

```text
年間停止時間 = 8760時間 × 0.001
             = 8.76時間
```

99.9% でも、年間では約 8.76 時間止まる計算です。99.99% なら停止割合は `1 - 0.9999 = 0.0001` なので、

```text
年間停止時間 = 8760時間 × 0.0001
             = 0.876時間
```

0.876 時間を分に直すには 60 を掛けます。

```text
0.876 × 60 = 52.56分
```

稼働率の 9 が 1 つ増えるだけで、必要な設計と運用はかなり難しくなります。冗長化、監視、自動切替、データ複製、復旧訓練、障害対応手順が必要です。

## 実務で使える理解

システム構成を考えるときは、まず利用者にとって何が困るかを考えます。画面が少し遅いことが問題なのか、注文データを失うことが問題なのか、1 時間止まることが問題なのか、1 分でも止まることが問題なのかで、選ぶ構成は変わります。

デュアルとデュプレックスは、どちらも 2 系統を使いますが目的と動きが違います。デュアルは同じ処理を同時に行って結果を照合します。デュプレックスは主系と待機系を用意して、故障時に切り替えます。

RAID は、性能、容量、耐障害性を一緒に見ます。RAID 0 は速いが壊れやすい、RAID 1 は単純で復旧しやすいが容量効率が悪い、RAID 5/6 は容量効率と冗長性のバランスを取る、RAID 10 は性能と信頼性を重視する構成です。

NAS はファイル共有、SAN はブロックレベルの高速な共有ストレージとして見ると違いが分かります。仮想化は、物理資源を抽象化して柔軟に使う技術です。ただし、共有部分に負荷や障害が集中することもあります。

性能では、レスポンスタイム、ターンアラウンドタイム、スループット、利用率を混同しないことが大切です。待ち行列では、利用率が 1 に近いほど危険です。複数台構成では、`ρ = λ / (sμ)` のように全体の処理能力で余裕を見る必要があります。稼働率計算では、直列か並列かをまず図にします。

## 自分の言葉で説明できるか

- 集中処理と分散処理を、学校システムや EC サイトの例で比較できる。
- 3 層 Web システムで、画面、業務ルール、データ保存が分かれる理由を説明できる。
- ホット、ウォーム、コールドスタンバイの違いを、復旧時間とコストで説明できる。
- RTO と RPO の違いを、停止時間と失うデータ量で説明できる。
- ロードバランサを置いたとき、セッション情報をどこに置くべきか説明できる。
- RAID 0/1/5/6/10 を、速度、容量、故障への強さで比較できる。
- RAID がバックアップではない理由を説明できる。
- DAS、NAS、SAN の違いを、ファイル単位とブロック単位の違いから説明できる。
- レスポンスタイム、ターンアラウンドタイム、スループットを具体例で区別できる。
- `ρ = λ / μ` の意味を、到着量と処理能力の比として説明できる。
- `M/M/s` で、サーバ台数 `s` を増やしても利用率や待ち確率が高ければ遅延が残る理由を説明できる。
- 直列・並列システムの稼働率を、なぜ掛け算や `1 - ...` で求めるのか説明できる。

## ありがちな誤解

- 冗長化すれば必ず止まらないわけではありません。切替失敗、設定ミス、共通部品障害があります。
- クラウドに置けば自動的に高可用になるわけではありません。可用性設計は利用者側にも責任があります。
- RAID はバックアップではありません。誤削除や論理破壊には別の備えが必要です。
- スケールアウトは万能ではありません。共有 DB、セッション、外部 API がボトルネックになることがあります。
- 利用率が高いほど良いとは限りません。余裕がなくなると待ち時間が急増します。
- 稼働率の数字だけで安心してはいけません。利用者に影響する停止時間、復旧手順、データ損失の可能性まで見ます。
