# 第8章 セキュリティ

## この章の地図

セキュリティは、情報を守るための技術と管理の章です。ここでいう「守る」は、単に秘密にすることだけではありません。許可されていない人に読ませないこと、勝手に書き換えられないこと、必要なときに使えることまで含みます。

暗号、認証、PKI、攻撃手法、リスクマネジメント、セキュリティ評価は、ばらばらの用語ではありません。中心にある問いは、「何を、誰から、どこで、どの程度守るのか」です。暗号は盗み見に備え、認証は相手が誰かを確かめ、署名は改ざんと本人性を確認し、ファイアウォールや WAF は通信や Web 入力の境界を守り、ISMS は組織として守り続ける仕組みを作ります。

攻撃手法も、名前から入るより「システムが何を信じすぎたのか」で見ると理解しやすくなります。SQL インジェクションは入力を SQL 命令として混ぜてしまう問題、XSS は入力をブラウザで実行されるコードとして出してしまう問題、CSRF はブラウザから来たリクエストを本人の意思だと扱ってしまう問題です。この章では、攻撃名と対策を対応表として眺めるのではなく、信頼境界がどこで破られているかを追います。

## なぜこの章を学ぶのか

セキュリティは、専門部署だけの仕事ではありません。アプリを作る人、サーバを運用する人、データを扱う人、メールを開く人、全員に関係します。なぜなら、攻撃者は技術の弱点だけでなく、人の油断、運用のすき間、設定ミスも狙うからです。

たとえば、パスワードを強くしても、偽サイトに入力してしまえば盗まれます。通信を暗号化しても、サーバ側に SQL インジェクションの弱点があればデータは漏れます。バックアップがなければ、ランサムウェアで暗号化された後に復旧できません。

この章を学ぶと、「何を守るのか」「何から守るのか」「どこが弱点か」「どの対策がどのリスクを下げるのか」を筋道立てて考えられるようになります。

## 8.1 暗号化

この節を学ぶ理由は、データは通信中にも保存中にも盗み見される可能性があるからです。暗号化を使うと、たとえデータを見られても、鍵がなければ内容を読めないようにできます。

暗号化を理解すると、HTTPS、VPN、ファイル暗号化、パスワード保護の意味が分かります。同時に、鍵をどう渡すか、どう管理するかが重要だと分かります。

暗号化は、読めるデータを、鍵がないと読めない形へ変換することです。復号は、暗号化されたデータを元に戻すことです。ここでいう鍵は、家の鍵のような物理的なものではなく、暗号処理に使う数値やデータです。

共通鍵暗号では、暗号化と復号に同じ鍵を使います。友達同士で同じ秘密の合言葉を決め、その合言葉を知っている人だけが文章を読める、というイメージです。共通鍵暗号は高速なので、大量の通信データを暗号化するのに向いています。AES が代表例です。

ただし、共通鍵暗号には大きな問題があります。相手に同じ鍵をどうやって安全に渡すかです。鍵をメールで送ったら、そのメールを盗み見た人にも鍵が知られてしまいます。これを鍵配送問題といいます。

公開鍵暗号では、公開鍵と秘密鍵のペアを使います。公開鍵は他人に配ってよい鍵、秘密鍵は自分だけが守る鍵です。公開鍵で暗号化したデータは、対応する秘密鍵で復号できます。つまり、相手の公開鍵で暗号化すれば、秘密鍵を持つ相手だけが読めます。RSA や楕円曲線暗号が代表例です。

公開鍵暗号は鍵配送に強い一方、共通鍵暗号より処理が重くなりがちです。そこで実際の HTTPS などでは、両方を組み合わせます。最初に公開鍵暗号を使って安全に共通鍵を共有し、その後の大量データ通信は高速な共通鍵暗号で行います。これをハイブリッド方式といいます。

ここで大切なのは、「共通鍵と公開鍵のどちらが優れているか」ではありません。共通鍵暗号は速いが鍵を渡すのが難しい。公開鍵暗号は鍵を渡しやすいが重い。この性質の違いを組み合わせて、実用的な通信を作っています。

ここからさらに大事になるのが鍵管理です。強い暗号アルゴリズムを使っていても、鍵が漏れれば暗号は意味を失います。家のドアが頑丈でも、合鍵を玄関の前に置いていたら守れないのと同じです。鍵管理では、鍵を安全に作る、必要な相手へ安全に渡す、盗まれにくい場所に保存する、使える人やプログラムを絞る、定期的に入れ替える、不要になった鍵を無効化して廃棄する、という一連の流れを考えます。この流れを鍵のライフサイクルと呼びます。

鍵を作るときには乱数の質が重要です。乱数とは、予測しにくい値です。もし鍵が「現在時刻」や「連番」のように予測しやすい値から作られていたら、攻撃者は候補を絞れてしまいます。強い鍵とは、長いだけでなく、攻撃者が予測できない方法で作られた鍵です。

鍵を保存するとき、ソースコードや設定ファイルに秘密鍵や API キーをそのまま書くのは危険です。コード管理システムに上がったり、バックアップに残ったり、ログに出たりすると、後から消したつもりでも完全には消えません。そこで、秘密情報を専用の保管場所で管理するシークレット管理を使います。さらに重要な鍵では、HSM や KMS を使うことがあります。HSM は Hardware Security Module の略で、鍵を装置の外へ出しにくい形で暗号処理を行う専用機器です。KMS は Key Management Service の略で、クラウドなどで鍵の作成、保管、権限管理、ローテーションをまとめて扱うサービスです。

ローテーションは、鍵を定期的または必要時に入れ替えることです。なぜ入れ替えるのかというと、漏えいした鍵が使われ続ける期間を短くするためです。たとえば同じ鍵を 3 年間使う設計では、1 年目に盗まれても 3 年目まで悪用される可能性があります。90 日ごとに入れ替える設計なら、盗まれた鍵が有効な期間を短くできます。ただし、ローテーションは「新しい鍵を作る」だけでは足りません。古い鍵で暗号化されたデータを読めるようにするか、新しい鍵で再暗号化するか、古い鍵をいつ無効化するかを決める必要があります。

大量データでは、データそのものを暗号化する鍵と、その鍵を暗号化して守る上位の鍵を分けることがあります。これをエンベロープ暗号化と呼びます。封筒をさらに金庫に入れるような考え方です。データごとの鍵で本文を暗号化し、そのデータ鍵をマスター鍵で暗号化して保存します。マスター鍵を入れ替えるとき、すべての大きなデータを暗号化し直す代わりに、データ鍵を包み直すだけで済む場合があります。ここでも、暗号の強さは数式だけでなく、運用の設計で決まります。

## ハッシュと MAC

ハッシュ関数は、任意の長さのデータから、固定長の値を作る関数です。任意の長さとは、短い文章でも長いファイルでも入力できるという意味です。固定長とは、入力がどれだけ長くても、出力の長さは決まっているという意味です。

ハッシュは、データの指紋のようなものです。同じ入力なら同じハッシュ値になります。入力が少しでも変わると、ハッシュ値は大きく変わります。さらに、ハッシュ値から元の入力を戻すのは非常に困難です。

たとえば、配布されているソフトウェアのファイルにハッシュ値が書かれていることがあります。ダウンロードしたファイルのハッシュ値を計算し、公開されている値と一致すれば、途中で壊れたり改ざんされたりしていない可能性が高いと判断できます。

パスワード保存でもハッシュが使われます。サービス側が元のパスワードをそのまま保存していると、漏えいしたときに利用者のパスワードが直接盗まれます。そこで、元のパスワードではなくハッシュ値を保存します。ログイン時には、入力されたパスワードのハッシュ値を計算し、保存済みのハッシュ値と比べます。

ただし、単純なハッシュだけでは弱い場合があります。よくあるパスワードを大量に試す攻撃に備えるため、ソルトやストレッチングを使います。ソルトは、パスワードに加えるランダムな値です。ストレッチングは、ハッシュ計算を何度も繰り返して、総当たり攻撃のコストを上げる方法です。

MAC は Message Authentication Code、メッセージ認証コードです。秘密鍵とメッセージから値を作り、改ざんと送信者の正当性を確認します。ハッシュだけなら誰でも計算できますが、MAC は秘密鍵を知っている相手だけが正しい値を作れます。そのため、「内容が変わっていないこと」と「秘密鍵を共有している相手から来たこと」を確認できます。

## 8.2 無線 LAN の暗号

この節を学ぶ理由は、無線 LAN の通信は空間に電波として広がるからです。有線のようにケーブルへ物理的につながなくても、近くにいれば通信を観測できる可能性があります。

無線 LAN の暗号を学ぶと、なぜ WEP が危険なのか、なぜ WPA2/WPA3 を使うべきなのか、パスフレーズ管理がなぜ重要なのかが分かります。

無線 LAN は電波を使うため、通信が空間に広がります。教室で話した声が周りにも聞こえるように、電波も近くにいる機器から観測される可能性があります。そのため、無線 LAN は「盗聴されるかもしれない」ことを前提に守ります。

WEP は古い暗号方式で、現在では安全ではありません。鍵の使い方に弱点があり、短時間で破られる可能性があります。WPA は WEP の改善として登場しました。WPA2 は AES/CCMP を使い、長く標準的に利用されてきました。WPA3 は、より強い認証と暗号化を提供します。

暗号方式だけでなく、パスフレーズも重要です。パスフレーズとは、無線 LAN 接続に使う長めの合言葉のようなものです。短く単純なパスフレーズだと、総当たりや辞書攻撃で破られやすくなります。

WPS は、ボタン操作などで簡単に接続するための仕組みです。便利ですが、設定や方式によっては攻撃面を増やします。不要なら無効化を検討します。企業や学校のように利用者が多い環境では、共有パスフレーズだけでなく、利用者ごとの認証を組み合わせることも重要です。

家庭の Wi-Fi では、全員が同じパスフレーズを使う方式がよくあります。この方式は設定が簡単ですが、誰か 1 人にパスフレーズを教えると、その人が辞めた後も同じ合言葉で接続できるかもしれません。全員で同じ鍵を共有する設計では、「誰が接続したのか」を個別に追いにくくなります。

学校や企業では、802.1X 認証を使って、利用者ごと、端末ごとに認証する構成があります。802.1X は、ネットワークへ入る前に認証を行う仕組みです。EAP は Extensible Authentication Protocol の略で、認証方式を運ぶ枠組みです。RADIUS サーバは、アクセスポイントやスイッチからの問い合わせを受け、利用者が接続してよいかを判断します。

この構成では、アクセスポイントは単に電波を出す装置ではなく、「認証されるまで内部ネットワークへ通さない門番」になります。利用者 A のアカウントを停止すれば、共有パスフレーズを全員に配り直さなくても A だけを止められます。ログにも、どの利用者や端末がいつ接続したかを残しやすくなります。暗号方式、利用者認証、端末管理、ログは別々の部品に見えますが、無線 LAN の安全性はこれらを組み合わせて決まります。

## 8.3 認証

この節を学ぶ理由は、システムが「誰が使っているのか」を確認しなければならないからです。本人確認が弱いと、他人になりすましてデータを見たり操作したりできてしまいます。

認証を学ぶと、パスワード、多要素認証、生体認証、RADIUS、リモートアクセスの意味がつながります。さらに、認証と認可は別物だと理解できます。

認証は、利用者が本人であることを確認することです。認可は、認証された人に何を許すかを決めることです。

認証と認可の違いは、学校への入館で考えると分かりやすいです。校門で学生証を見せて本人確認するのが認証です。その生徒が職員室に入ってよいか、成績データを見てよいかを決めるのが認可です。本人であることが確認できても、すべての操作が許されるわけではありません。

認証要素には、知識、所持、生体があります。知識はパスワードや PIN のように本人が知っているものです。所持は IC カード、スマートフォン、トークンのように本人が持っているものです。生体は指紋、顔、静脈のように本人の身体的特徴です。

多要素認証は、異なる種類の要素を組み合わせます。パスワードと秘密の質問は、どちらも「知識」なので、多要素とは言いにくいです。パスワードに加えてスマートフォンの認証アプリを使うなら、知識と所持の組合せになります。

リモートアクセスでは、外部のネットワークから組織内のシステムへ入るため、特に慎重な確認が必要です。VPN で暗号化された通信路を作り、端末認証、利用者認証、アクセス制御を組み合わせます。端末認証は、その PC やスマホが許可された端末かを確認することです。利用者認証は、使っている人が本人かを確認することです。

RADIUS は、ネットワーク機器から認証サーバへ認証、認可、課金情報を問い合わせるプロトコルです。課金という言葉は料金だけでなく、利用記録の管理という意味でも使われます。無線 LAN やリモートアクセスで、利用者ごとの認証を集中管理するために使われます。

### ログインは「パスワードを当てる」だけでは終わらない

ログイン処理を深く見ると、認証、セッション管理、認可、監査がつながっていることが分かります。

利用者がパスワードを入力すると、サーバはそのパスワードが正しいか確認します。このとき、サーバが平文のパスワードをそのまま保存してはいけません。平文とは、暗号化やハッシュ化されていない読める形のことです。もしデータベースが漏えいしたら、利用者のパスワードがそのまま盗まれ、他サービスにも使い回される危険があります。

そこで、パスワードは通常、ソルトを加えてハッシュ化して保存します。ソルトは利用者ごとに異なるランダムな値です。同じパスワードでもソルトが違えば保存されるハッシュ値が変わるため、攻撃者が事前に作った対応表を使いにくくなります。さらに、ストレッチングによってハッシュ計算をわざと重くすると、総当たり攻撃の速度を下げられます。

ログインに成功した後も、毎回パスワードを送るわけではありません。サーバはセッション ID を発行し、ブラウザはそれを Cookie などで保持します。セッション ID は「この利用者はログイン済みである」とサーバに示す一時的な鍵です。だからセッション ID が盗まれると、攻撃者はパスワードを知らなくてもログイン済み利用者になりすませます。

このため、Cookie には Secure、HttpOnly、SameSite などの属性を付けます。Secure は HTTPS 通信でだけ Cookie を送る指定です。HttpOnly は JavaScript から Cookie を読みにくくする指定で、XSS によるセッション ID 窃取の被害を減らします。SameSite は、別サイトからのリクエストに Cookie を送る条件を制限し、CSRF の被害を減らします。

認証が終わったら、次は認可です。ログイン済みだからといって、全員が管理者画面を使えるわけではありません。生徒、保護者、教員、管理者では、見られるデータも実行できる操作も違います。認証は「あなたは誰か」、認可は「あなたは何をしてよいか」です。この違いを設計で分けないと、本人確認はできているのに権限が広すぎる、という危険な状態になります。

認可の設計では、RBAC や ABAC という考え方があります。RBAC は Role-Based Access Control、ロールに基づくアクセス制御です。ロールは役割です。生徒、担任、学年主任、管理者のような役割ごとに、見られる画面や操作を決めます。ABAC は Attribute-Based Access Control、属性に基づくアクセス制御です。属性とは、その人や対象データが持つ性質です。たとえば「担任である」「2年A組を担当している」「本人の子どもである」「平日 8 時から 18 時の操作である」といった条件を使って判断します。

RBAC は分かりやすく管理しやすい一方、役割が増えすぎると複雑になります。ABAC は細かい条件を表せますが、なぜ許可されたのか、どの条件が効いたのかを説明できる設計が必要です。高度な認可では、単に管理者フラグを 1 つ持つのではなく、「誰が、どの対象に、どの操作を、どんな条件でできるのか」を明確にします。

シングルサインオンでは、1 回の認証結果を複数サービスで使います。学校のアカウントで学習アプリ、メール、オンライン教材に入れるような形です。SAML は、組織の認証基盤とクラウドサービスをつなぐ認証連携でよく使われます。OAuth 2.0 は、あるサービスにパスワードを渡さず、別サービスへの限定的なアクセス権を与える仕組みです。OpenID Connect は OAuth 2.0 の上に本人確認の情報を載せる仕組みです。ここで混同しやすいのは、OAuth は主に「アクセス権を委任する」話で、OpenID Connect は「誰としてログインしたか」を扱う話だという点です。

OAuth 2.0 では、アクセストークンが重要です。アクセストークンは、ある操作を許可されたことを示す短い通行証のような値です。たとえば学習アプリがカレンダーサービスに「予定を読む」権限だけをもらうなら、カレンダーのパスワードそのものではなく、限定されたアクセストークンを使います。スコープは、そのトークンで許される範囲です。読み取りだけ、書き込みも可、特定 API だけ、といった範囲を絞ります。

トークンは便利ですが、漏れれば悪用されます。Bearer トークンは「持っている人を許可する」性質があるため、盗まれると本人確認なしで使われる危険があります。だから HTTPS で送る、ブラウザやアプリ内の保存場所を慎重に選ぶ、有効期限を短くする、必要なスコープだけにする、といった対策が必要です。リフレッシュトークンは、新しいアクセストークンを得るための長めの権限を持つ値なので、さらに厳重に扱います。

OpenID Connect では ID トークンが出てきます。ID トークンは「誰として認証されたか」を伝えるための情報です。アクセス権を表すアクセストークンと、本人確認の結果を表す ID トークンを混同すると設計を誤ります。現代の Web やスマホアプリでは、認可コードフローや PKCE のように、トークンを安全に受け渡すための手順が使われます。PKCE は、認可コードを途中で盗まれても悪用されにくくするための追加確認です。

## 8.4 ディジタル署名と PKI

この節を学ぶ理由は、インターネット上では相手が本物か、データが改ざんされていないかを確認する必要があるからです。顔を見て書類に印鑑を押す代わりに、公開鍵、秘密鍵、証明書を使います。

ディジタル署名と PKI を理解すると、HTTPS の証明書、電子契約、ソフトウェア配布、メール署名がどのように信頼を作っているかが分かります。

ディジタル署名は、本人性、完全性、否認防止を実現する技術です。本人性は、本当にその人が作ったものだと確認できることです。完全性は、途中で改ざんされていないことです。否認防止は、あとから「自分は送っていない」と否定しにくくすることです。

ディジタル署名では、次の流れで「本人が署名したこと」と「改ざんされていないこと」を確認します。

1. メッセージのハッシュ値を作る。
2. 送信者の秘密鍵でハッシュ値を暗号化する。
3. 受信者は送信者の公開鍵で検証する。

これにより、送信者の秘密鍵を持つ人が署名したこと、メッセージが改ざんされていないことを確認できます。

PKI は公開鍵基盤です。公開鍵が本当に本人のものかを証明する仕組みです。

PKI では、公開鍵を信頼するために複数の役割が協力します。

CA は認証局で、公開鍵と所有者情報を結びつけた証明書を発行します。ブラウザが HTTPS サイトを信頼できるのは、サーバが示した証明書を、信頼済みの CA からたどって確認できるからです。RA は登録局で、証明書を発行する前の本人確認や組織確認を担当します。CA が最終的に証明書を出すとしても、その前に「この人や組織は本当に名乗っている相手か」を確認する役割が必要です。

ディジタル証明書は、公開鍵、所有者情報、有効期限、発行者、署名などを含むデータです。証明書があることで、「この公開鍵はこのサーバや組織のものだ」と確認できます。ただし、証明書は途中で失効することがあります。秘密鍵が漏えいした、組織情報が変わった、誤って発行された、といった場合です。CRL や OCSP は、その証明書が今も有効か、失効していないかを確認する仕組みです。

SSL/TLS は、サーバ認証、暗号化、改ざん検知を行う通信プロトコルです。HTTPS は HTTP を TLS で保護したものです。

ここで大事なのは、「公開鍵は公開してよい」と言っても、その公開鍵が本当に相手のものかは別問題だということです。攻撃者が偽物の公開鍵を渡してきたら、利用者は攻撃者に向けて安全だと思って暗号化してしまいます。そこで、CA が公開鍵と所有者情報を結びつけたディジタル証明書を発行します。

証明書が失効することもあります。秘密鍵が漏えいした、所有者情報が変わった、証明書を誤って発行した、などの場合です。CRL や OCSP は、証明書がまだ有効かを確認するために使います。

### TLS は暗号化だけでなく相手確認もしている

HTTPS の鍵マークを見ると、「暗号化されているから安全」と考えがちです。しかし TLS が守っていることを分解すると、もう少し正確に理解できます。

まず、ブラウザはサーバから証明書を受け取ります。証明書には、サーバ名、公開鍵、有効期限、発行した CA などが含まれます。ブラウザは、証明書のサーバ名がアクセス先のドメイン名と合っているか、有効期限が切れていないか、信頼できる CA からつながる証明書かを確認します。ここで失敗すると、ブラウザは警告を出します。

次に、ブラウザとサーバは暗号通信に使う鍵を安全に共有します。現代の TLS では、毎回の通信ごとに一時的な鍵を作る方式が使われます。これにより、あとから長期秘密鍵が漏えいしても、過去の通信内容を復号されにくくできます。この性質を前方秘匿性といいます。

その後の大量データ通信では、共通鍵暗号を使います。公開鍵暗号は便利ですが重いため、最初の相手確認や鍵共有に使い、実際のデータ本体は高速な共通鍵暗号で守ります。これは第8章の最初で見たハイブリッド方式そのものです。

ただし、TLS は「通信路」を守る技術です。通信先のサーバが本物で、途中で盗聴や改ざんされにくいことは確認できます。しかし、そのサイトの運営者が誠実か、入力した商品が本当に届くか、Web アプリに脆弱性がないかまでは保証しません。HTTPS は「安全な人間が運営している」という意味ではなく、「通信が TLS で保護されている」という意味です。

HSTS は HTTP Strict Transport Security の略で、ブラウザに「このサイトへは HTTPS でだけ接続する」と記憶させる仕組みです。利用者が誤って `http://` でアクセスしたり、攻撃者が暗号化なしの HTTP へ誘導したりすると、通信内容が盗み見や改ざんの危険にさらされます。HSTS が有効なら、ブラウザは次回以降そのサイトへ HTTPS で接続しようとします。つまり TLS は 1 回の通信を守る仕組み、HSTS は「暗号化された入口を使い続ける」ためのブラウザ側の約束だと考えられます。

ただし、HSTS も設定すれば終わりではありません。証明書更新を失敗したまま HSTS を強く設定していると、利用者は回避してアクセスしにくくなります。これは安全性としては望ましい面もありますが、運用を誤るとサービス停止につながります。セキュリティ対策は、技術、設定、証明書更新、監視、障害対応がつながって初めて働きます。

## 8.5 情報セキュリティ対策

この節を学ぶ理由は、攻撃や事故への対策は 1 つでは足りないからです。マルウェア対策、ファイアウォール、IDS/IPS、WAF、DMZ、VPN などを組み合わせて守ります。

セキュリティ対策を学ぶと、どの対策がどの層・どの弱点に効くのかを整理できます。製品名から入るのではなく、守る場所と目的で理解することが重要です。

マルウェアは、悪意あるソフトウェアの総称です。ウイルスは他のファイルに感染して広がります。ワームは自力でネットワークを広がります。トロイの木馬は有用なソフトに見せかけて不正動作します。ランサムウェアはデータを暗号化し、復旧と引き換えに身代金を要求します。スパイウェアは情報を盗みます。

ネットワーク対策では、守る境界を考えます。ファイアウォールは、通信をルールで許可または遮断します。たとえば、外部から社内 DB へ直接接続できないようにします。IDS は Intrusion Detection System、侵入検知システムです。怪しい通信を検知します。IPS は Intrusion Prevention System、侵入防止システムです。検知した通信を遮断するところまで行います。

WAF は Web Application Firewall です。通常のファイアウォールが IP アドレスやポート番号などを見るのに対し、WAF は Web アプリへの入力内容や HTTP の文脈を見て、SQL インジェクションや XSS のような攻撃を防ぎます。

DMZ は DeMilitarized Zone、非武装地帯という意味から来た言葉です。外部公開サーバを内部 LAN から分離する領域です。Web サーバのようにインターネットへ公開するサーバを、社内の重要システムと同じ場所に置くと危険です。DMZ に置くことで、公開サーバが攻撃されても内部 LAN へ直接広がりにくくします。

VPN は Virtual Private Network です。インターネットのような共有ネットワーク上に、暗号化された仮想的な専用通信路を作ります。外出先から社内システムへ接続するときなどに使います。

TLS アクセラレータは、TLS の暗号処理を専用装置などで肩代わりし、Web サーバの負荷を下げます。暗号化は安全性のために必要ですが、処理負荷もあります。大量アクセスを扱うシステムでは、どこで TLS を終端するかも設計上の論点になります。

TLS 終端とは、暗号化された通信をどこで復号するかという設計です。たとえば、インターネットから来た HTTPS 通信をロードバランサやリバースプロキシで復号し、その後ろの Web サーバへ HTTP で渡す構成があります。リバースプロキシとは、利用者から見るとサーバの入口に立ち、裏側の複数サーバへ要求を振り分けたり、防御処理をしたりする仕組みです。

TLS を入口で終端すると、証明書管理や暗号処理を集中させやすく、WAF が HTTP の中身を見て攻撃を検出しやすくなります。しかし、終端後の内部通信が平文なら、内部ネットワークで盗聴されたときに内容が見える可能性があります。だから、内部通信も再暗号化する、ネットワークを分離する、アクセス権を絞る、ログを監視する、といった設計が必要になります。

WAF も万能ではありません。WAF は既知の攻撃パターンや異常な入力を止める助けになりますが、アプリケーション本体の入力検証、認可チェック、セッション管理が不要になるわけではありません。たとえば、「本人の成績だけ見られる」という認可ルールをアプリが間違えていれば、WAF だけでは業務ルール違反を完全には防げません。セキュリティ対策は、入口の装置とアプリ内部の設計を重ねて考えます。

## 8.6 脅威と攻撃手法

この節を学ぶ理由は、攻撃の考え方を知らないと防御を設計できないからです。攻撃者は、入力、認証、セッション、ブラウザ、通信、サーバ設定、人間の心理など、さまざまな弱点を狙います。

攻撃手法を学ぶと、「なぜ入力チェックが必要か」「なぜ出力エスケープが必要か」「なぜ CSRF トークンが必要か」を、理由から理解できます。

セキュリティの基本は CIA です。

Confidentiality は機密性で、許可された人だけが情報を読めることです。成績データや個人情報が、関係ない人に見えないようにする性質です。Integrity は完全性で、情報が正しく、勝手に改ざんされていないことです。点数や振込先口座がこっそり変えられたら、情報は存在していても信頼できません。Availability は可用性で、必要なときに使えることです。データが安全に保管されていても、サービス停止で必要なときに使えなければ価値を出せません。

CIA を実際の設計に使うには、「どの資産を、誰から、どこで守るのか」まで具体化します。資産とは、守る価値があるものです。個人情報、成績データ、決済情報、ソースコード、秘密鍵、ログ、サービスそのものの稼働などが資産になります。

攻撃者も一種類ではありません。外部の攻撃者、内部の不正利用者、誤操作する正規利用者、マルウェアに感染した端末、委託先の設定ミスなど、さまざまです。攻撃者が変わると、守る場所も変わります。外部攻撃者には公開サーバの入口を守る必要があります。内部不正には権限分離や監査ログが効きます。誤操作には確認画面、入力チェック、ロールバック手順が効きます。

信頼境界という考え方も重要です。信頼境界とは、「ここから先のデータは信用してよい」と見なす境目です。インターネットから来た入力、ブラウザから送られた Cookie、社内ネットワークから来た通信、別システムから受け取った CSV ファイルなどは、どれも無条件に信用してはいけません。境界を越えるデータは、検証し、必要なら変換し、権限を確認してから使います。

最小権限は、必要な権限だけを与える考え方です。Web アプリがデータベースに接続するとき、検索だけでよい処理に削除権限まで与えると、SQL インジェクションなどが起きたとき被害が広がります。最初から権限を絞っておけば、攻撃が成功してもできることを減らせます。

多層防御は、1 つの対策が破られても次の対策で止める考え方です。入力検証、認証、認可、ログ監視、バックアップ、ネットワーク分離、WAF、脆弱性管理は、それぞれ違う場所で効きます。どれか 1 つを入れれば終わりではなく、攻撃の進み方を想像して複数の壁を置きます。

脅威モデリングは、作った後に弱点を探すだけでなく、設計段階で「何が攻撃されるか」を考える活動です。まず守る資産を決めます。次に、システムの入口、データの流れ、信頼境界、外部サービス、管理者操作を見ます。そして、なりすまし、改ざん、否認、情報漏えい、サービス不能、権限昇格のような観点で、どんな攻撃があり得るかを考えます。

たとえば欠席連絡アプリなら、保護者になりすまして登録する、他の家庭の欠席情報を見る、登録履歴を後から否認する、通知サービスへ個人情報を送りすぎる、大量アクセスで朝の受付を止める、一般利用者が管理者機能を使う、といった脅威を考えます。こうして脅威を先に出すと、認証、認可、監査ログ、入力制限、レート制限、通知データの最小化を要件として設計に入れられます。

ゼロトラストは、「社内ネットワークの中だから安全」と決めつけない考え方です。昔は、境界防御として外と内を分け、内側を比較的信用する設計が多くありました。しかしクラウド利用、リモートワーク、委託先連携、端末持ち出しが増えると、内側にいることだけでは信用できません。ゼロトラストでは、利用者、端末、場所、通信先、操作内容を継続的に確認し、必要最小限のアクセスだけを許します。これは製品名ではなく、信頼の置き方を変える設計思想です。

攻撃手法は、攻撃される場所で見るとつながりが見えます。

SQL インジェクションは、Web フォームなどの入力値に SQL を混ぜ、データベースを不正操作する攻撃です。問題の本質は、利用者が入力した文字列を「データ」ではなく「命令の一部」として扱ってしまうことです。対策では、プレースホルダを使って、SQL の命令部分と値を明確に分けます。

クロスサイトスクリプティング、つまり XSS は、Web ページに悪意あるスクリプトを埋め込む攻撃です。掲示板に投稿された文字列を、そのまま HTML として出力すると、ブラウザが文字列ではなく JavaScript として実行してしまうことがあります。対策では、出力する場所の文脈に合わせてエスケープします。エスケープとは、特別な意味を持つ文字を、ただの文字として扱われる形に変換することです。

CSRF は、ログイン済み利用者のブラウザに、本人が意図しない操作を送らせる攻撃です。問題の本質は、「ログイン済みブラウザから来たリクエストだから本人の意思だ」と信じてしまうことです。対策では、攻撃者が推測できない CSRF トークンをフォームに含め、本当にその画面から送られた操作かを確認します。

認可不備は、本人確認はできているのに、操作対象を正しく制限できていない問題です。たとえば、保護者 A がログインしている状態で、URL や API の `studentId` を別の生徒の ID に変えると、保護者 B の子どもの欠席情報が見えてしまうような場合です。このように、直接指定された ID を変えるだけで他人のデータへアクセスできる問題は IDOR、Insecure Direct Object Reference と呼ばれます。

認可不備の本質は、「ログイン済みだから、この対象データを見てもよい」と信じてしまうことです。正しくは、リクエストごとに「誰が、どの対象に、どの操作をしてよいか」をサーバ側で確認します。画面にボタンを出さないだけでは足りません。攻撃者は画面を使わず、API へ直接リクエストできます。欠席連絡アプリなら、`studentId` が存在するかだけでなく、その生徒がログイン利用者の子どもか、担任の担当クラスか、保健室が見るべき範囲かまで確認します。

セッションハイジャックは、セッション ID を盗んでなりすます攻撃です。セッション ID は、ログイン後の利用者を識別する鍵のような値です。これが盗まれると、パスワードを知らなくてもログイン済み利用者として扱われる危険があります。

CORS は Cross-Origin Resource Sharing の略で、ブラウザが別のオリジンへアクセスする条件を制御する仕組みです。オリジンとは、URL のスキーム、ホスト名、ポート番号の組合せです。`https://example.com` と `https://api.example.com` はホスト名が違うため別オリジンです。ブラウザは、あるサイトの JavaScript が別サイトの情報を勝手に読めないように、同一オリジンポリシーという制限を持っています。

CORS は、この制限に例外を作るための仕組みです。たとえば学習アプリの画面が `https://app.example.jp` にあり、API が `https://api.example.jp` にある場合、API 側が「この画面からの読み取りは許可する」と応答ヘッダで示します。ここで大事なのは、CORS はブラウザによる読み取り制御であって、サーバ側の認可の代わりではないことです。CORS で許可したからといって、誰の成績でも返してよいわけではありません。API は必ず利用者の認証と認可を確認します。

CORS の設定を広げすぎると危険です。たとえば資格情報つきのリクエストを広い範囲のオリジンに許可すると、意図しないサイトから利用者の情報を読まれる可能性があります。開発中に便利だからといって、広い許可を本番に残してはいけません。セキュリティ設定では、「どこから呼ばれる必要があるか」を具体的に列挙し、不要な許可を増やさないことが重要です。

SSRF は Server-Side Request Forgery の略で、サーバに攻撃者が選んだ宛先へアクセスさせる攻撃です。利用者が入力した URL をサーバが取得して画像や文書を読み込む機能があるとします。このとき、サーバが入力された URL を無条件に信じると、攻撃者は外部サイトだけでなく、本来インターネットから見えない内部管理画面、クラウドのメタデータサービス、社内 API へサーバからアクセスさせる可能性があります。

SSRF の本質は、「サーバからの通信は安全だ」と内部側が信じている点を突くことです。外部の攻撃者は直接内部ネットワークへ入れなくても、公開サーバを踏み台にして内部向け通信を発生させます。対策では、取得してよい URL の形式やドメインを許可リストで制限し、内部アドレスや管理用アドレスへ出ていく通信を止め、サーバに不要な外向き通信権限を与えないようにします。ここでも、入力検証とネットワーク分離と最小権限を組み合わせます。

クリックジャッキングは、利用者に見えている画面と実際にクリックされる画面をずらし、意図しない操作をさせる攻撃です。たとえば透明に近い別サイトのボタンを上に重ね、利用者が普通のボタンを押したつもりで重要操作を実行してしまう場合があります。対策には、他サイトのフレーム内に自分のページを埋め込ませない設定があります。`X-Frame-Options` や CSP の `frame-ancestors` を使うと、どのサイトが自分のページをフレーム表示できるかを制限できます。

DoS や DDoS は、大量の通信や重い処理を発生させ、サービスを使えなくする攻撃です。機密性や完全性だけでなく、可用性を狙う攻撃です。DDoS の D は Distributed、分散型という意味で、多数の端末から一斉に攻撃します。

中間者攻撃は、通信の途中に入り、盗聴や改ざんを行う攻撃です。TLS では、暗号化だけでなく証明書によるサーバ認証を行うことで、接続先が本物かを確認します。

フィッシングは、偽サイトやメールで認証情報を盗む攻撃です。技術的な弱点だけでなく、人間の判断を狙います。ブルートフォース攻撃は可能なパスワードを総当たりで試す攻撃、辞書攻撃はよく使われる単語や漏えい済みパスワードを試す攻撃です。

メールのなりすまし対策には SPF、DKIM、DMARC があります。メールはもともと、差出人欄を比較的自由に書ける仕組みから発展してきたため、「表示された差出人名が本物に見える」だけでは信用できません。SPF は、あるドメインのメールを送ってよいサーバを DNS に登録しておき、受信側が送信元サーバを確認する仕組みです。DNS はドメイン名と情報を対応づける仕組みなので、「このドメインの正しい送信サーバはどれか」を公開する場所として使われます。

DKIM は、送信側がメールに電子署名を付け、受信側が DNS に公開された公開鍵で検証する仕組みです。本文や重要なヘッダが途中で改ざんされていないか、確かにそのドメインの秘密鍵を持つ送信側から出たかを確認できます。DMARC は、SPF や DKIM の結果を使って、認証に失敗したメールをどう扱うかをドメイン所有者が宣言する仕組みです。受信拒否、隔離、報告などの方針を決められます。

この 3 つは役割が違います。SPF は「送信してよいサーバか」、DKIM は「メールに署名があり改ざんされていないか」、DMARC は「失敗したとき受信側にどう扱ってほしいか」を扱います。フィッシング対策では、利用者教育だけでなく、ドメイン、DNS、署名、受信側ポリシーを組み合わせて、偽メールが届きにくく、届いても判定しやすい状態を作ります。

バッファオーバフローは、用意されたメモリ領域を超えて書き込み、不正な実行や異常終了を狙う攻撃です。プログラムが入力の長さを正しく確認していないと起きます。

パストラバーサルは、ファイル名やパスの入力を悪用し、本来読ませるつもりのないファイルへ到達する攻撃です。たとえば、利用者にレポートファイルをダウンロードさせる機能で、サーバが入力されたファイル名をそのまま保存ディレクトリと結合すると、攻撃者が上位ディレクトリへ移動する指定を混ぜて、設定ファイルや秘密情報を読もうとする場合があります。対策では、利用者が指定できるファイルを ID で管理し、実際の保存パスをサーバ側で引き、許可されたディレクトリの外へ出ていないかを確認します。

OS コマンドインジェクションは、アプリケーションが OS コマンドを組み立てるとき、利用者入力が命令の一部として解釈されてしまう問題です。画像変換やファイル圧縮のように外部コマンドを呼ぶ機能で、入力値を文字列連結してコマンドに混ぜると、攻撃者が意図しない追加操作を実行させる危険があります。対策では、そもそもシェルを通さない API を使う、引数を配列として渡して命令と値を分ける、許可された形式だけを受け付ける、実行権限を最小にする、という設計を取ります。

攻撃への対策は、「攻撃が成立した理由」を打ち消すように選びます。SQL インジェクションでは、入力値が SQL 命令に混ざることが問題なので、プレースホルダで命令と値を分け、DB の権限も最小限にします。XSS では、文字列がブラウザ上でコードとして実行されることが問題なので、出力エスケープや CSP を使います。CSP は Content Security Policy の略で、ブラウザに「どこから読み込んだスクリプトなら実行してよいか」を伝える仕組みです。CSRF では、ログイン済みブラウザから来たというだけで本人の意思だと信じることが問題なので、CSRF トークンや SameSite Cookie で、正しい画面から送られた操作かを確認します。認可不備では、ログイン済みかどうかだけでなく、対象データごとに操作権限を確認します。SSRF では、サーバからアクセスしてよい宛先を制限し、内部ネットワークへの踏み台化を防ぎます。セッションハイジャックではセッション ID の盗難が問題なので、HTTPS、Cookie の Secure/HttpOnly 属性、ログイン後のセッション再生成を使います。DoS では可用性が狙われるため、レート制限、CDN、冗長化で負荷を分散し、被害を小さくします。

## 8.7 情報セキュリティ管理

この節を学ぶ理由は、セキュリティは技術だけでなく組織的に続ける活動だからです。どの資産を優先して守るか、どのリスクを受け入れるか、誰が責任を持つかを決める必要があります。

情報セキュリティ管理を学ぶと、リスク対応、ISMS、評価基準、監査、教育が、技術対策と同じくらい重要だと分かります。

リスクは、脅威が脆弱性を突き、損失が起きる可能性です。

```text
リスク = 資産価値 × 脅威 × 脆弱性
```

この式は、厳密な物理法則ではなく、リスクを比べるための考え方です。「大切なものほど」「攻撃や事故が起きやすいほど」「弱点が大きいほど」リスクが大きくなる、という関係を表しています。

なぜ掛け算なのでしょうか。どれか 1 つが 0 に近いと、リスクも小さくなるからです。

資産価値がほぼ 0 なら、たとえ攻撃されても失う価値が小さいため、優先度は下がります。脅威がほぼ 0 なら、害を与える原因や機会がほとんどないため、リスクは小さくなります。脆弱性がほぼ 0 なら、攻撃や事故が起きても弱点を突かれにくいため、損失につながりにくくなります。このように、リスクは 1 つの要素だけで決まるのではなく、守る価値、起こりやすさ、弱さが重なったところで大きくなります。

たとえば 0 から 5 の点数で仮に評価すると、どの対策を優先すべきかを説明しやすくなります。

```text
資産価値 = 5
脅威 = 4
脆弱性 = 3
リスク = 5 × 4 × 3
       = 60
```

対策によって脆弱性を 3 から 1 に下げられたなら、

```text
リスク = 5 × 4 × 1
       = 20
```

資産価値や脅威をすぐには変えられない場合でも、脆弱性を下げることでリスクを下げられる、という読み方をします。

リスクへの対応は、必ずしも「全部なくす」ことではありません。回避は、リスクのある活動そのものをやめることです。たとえば、危険が大きすぎる外部公開機能を提供しない判断です。低減は、対策によって発生可能性や影響を下げることです。パッチ適用、アクセス制御、バックアップがこれに当たります。移転は、保険や外部委託などで損失や責任の一部を移すことです。受容は、対策コストや発生確率を考えたうえで、残るリスクを組織として受け入れることです。受容は「放置」ではなく、理由を説明できる判断です。

ISMS は、情報セキュリティを継続的に管理する仕組みです。PDCA サイクルで改善します。

基準や組織名も、何をそろえるためのものかで見るとつながります。ISO/IEC 27001 は、ISMS を組織として運用するための規格です。ISO/IEC 15408 は、製品やシステムのセキュリティ機能を評価するための基準で、Common Criteria とも呼ばれます。CVSS は、脆弱性の深刻度を数値で表すための枠組みです。JPCERT/CC や IPA は、セキュリティ情報の提供、注意喚起、インシデント対応支援などを行う組織です。

ISO/IEC 15408 や Common Criteria を読むときに重要なのは、「安全な製品」という大きな言い方をそのまま信じないことです。評価は、決められた対象、決められた設定、決められた脅威モデルに対して行われます。評価対象を TOE、Target of Evaluation と呼びます。TOE は「この評価で見る製品やシステムの範囲」です。たとえばファイアウォール製品を評価する場合でも、管理サーバ、ログ保存先、外部認証サーバ、運用手順まで全部が TOE に入るとは限りません。

評価では、Security Target という文書が重要になります。これは、その TOE が何を守るのか、どの機能を持つのか、どんな前提条件で使われるのかを示す文書です。高校生向けに言えば、「この製品は、どんな条件なら、何を約束するのか」を書いた仕様書です。ここに「管理者は安全な手順で初期設定する」「物理的に安全な場所に設置する」といった前提があるなら、その前提が破られた使い方まで評価結果が保証しているわけではありません。

Protection Profile は、同じ種類の製品に共通する要求をまとめたものです。たとえば、ある種類の暗号モジュールやファイアウォールに対して「この種類の製品なら、最低限このような脅威を考え、このような機能を持つべきだ」という基準を表します。Security Target が個別製品の約束だとすれば、Protection Profile は製品カテゴリごとの共通要求に近いものです。

EAL は Evaluation Assurance Level、評価保証レベルです。ここでいう保証は、「絶対に破られない」という意味ではありません。設計文書、実装、テスト、開発手順、脆弱性分析などを、どの深さまで確認したかを表します。EAL が高いほど、評価の深さや厳密さは増します。しかし、EAL が高ければすべての環境で安全という意味ではありません。古いバージョン、評価外の設定、別の部品との組合せ、運用ミス、新しい攻撃手法には別の判断が必要です。

したがって、セキュリティ評価結果を見るときは、少なくとも 4 つを確認します。第 1 に、TOE はどこまでか。第 2 に、どの Security Target に対して評価されたか。第 3 に、どのバージョン、設定、運用前提で評価されたか。第 4 に、自分たちの使い方がその範囲に入っているかです。評価済み製品を使うことは有力な判断材料ですが、評価範囲を読まずに「認証済みだから安全」と扱うのは危険です。

CVSS は、脆弱性の危険度を共通の物差しで話すために使います。単に「危険そう」では、どれを先に直すべきか説明できません。たとえば、外部からネットワーク越しに攻撃でき、認証不要で、成功すると機密情報を大量に読める脆弱性は優先度が高くなります。一方、管理者権限でログインした後に、特殊な操作をした場合だけ起きる問題は、影響はあっても緊急度が違うかもしれません。

ただし、CVSS の点数だけで対応順を決めるのも危険です。実際にその機能がインターネットへ公開されているか、攻撃コードが出回っているか、社内の重要データに届くか、代替策があるかで優先度は変わります。高度なセキュリティ判断では、CVSS のような共通指標に、自分たちの資産価値、露出状況、業務影響を重ねて考えます。

脆弱性管理は、自分たちが書いたコードだけを見る活動ではありません。現代のソフトウェアは、OS、ミドルウェア、ライブラリ、コンテナイメージ、クラウドサービス、開発ツールに支えられています。直接書いていない部品に脆弱性が見つかれば、自分のサービスにも影響します。これをソフトウェアサプライチェーンのリスクとして考えます。

SBOM は Software Bill of Materials の略で、ソフトウェア部品表です。どのライブラリを、どのバージョンで、どの製品に含めているかを一覧できるようにします。食品の原材料表示に近い考え方ですが、目的は表示そのものではなく、問題が見つかったときに影響範囲をすばやく調べることです。あるライブラリに重大な脆弱性が見つかったとき、SBOM があれば「どのサービスが影響を受けるか」「どのバージョンを更新すべきか」を追いやすくなります。

サプライチェーン対策では、依存ライブラリの更新、署名付きパッケージの検証、不要な依存の削減、ビルド環境の保護、秘密情報の混入検査も重要です。たとえばソースコードに API キーや秘密鍵を入れてしまうと、リポジトリが漏れたときに外部サービスを悪用される可能性があります。セキュリティは本番サーバだけでなく、開発、ビルド、配布の流れ全体で考えます。

セキュリティインシデント対応では、発見、初動、封じ込め、根絶、復旧、再発防止を分けて考えます。発見は、ログ、監視、利用者からの連絡、外部機関からの通知などで異常に気づく段階です。初動では、影響範囲を広げないために、関係者へ連絡し、証拠を消さないようにします。封じ込めは、攻撃者の動きを止める段階です。感染端末をネットワークから切り離す、漏えいした鍵を無効化する、攻撃元通信を遮断する、といった対応があります。

根絶は、原因を取り除く段階です。マルウェアを削除する、脆弱な設定を直す、パッチを当てる、盗まれた認証情報を変更するなどです。復旧では、バックアップから戻す、サービスを再開する、監視を強めるなどを行います。最後に再発防止として、なぜ検知が遅れたのか、なぜ侵入を許したのか、なぜ被害が広がったのかを振り返ります。インシデント対応は、慌てて元に戻すだけでは終わりません。

インシデント対応で特に大切なのは、証拠を壊さないことです。攻撃を受けたサーバをすぐ初期化すれば、一見きれいに戻ったように見えるかもしれません。しかし、どのアカウントが使われたのか、どのファイルが読まれたのか、いつ侵入されたのか、外部へデータが送られたのかが分からなくなります。影響範囲が分からなければ、利用者への説明、法的対応、再発防止が弱くなります。

フォレンジックは、事故や攻撃の証拠を保全し、分析する活動です。ディスクの内容、メモリ、ログ、ネットワーク通信、認証履歴、クラウドの操作履歴などを、後から説明できる形で扱います。ここでいう保全とは、ただコピーすることではありません。いつ、誰が、どの機器から、どの方法で取得したかを記録し、取得後に改ざんされていないことを確認できるようにします。証拠は、技術調査だけでなく、組織として責任ある説明をするためにも必要です。

ログは、残していれば十分ではありません。ログの時刻がずれていると、出来事の順序を追えません。サーバ A では 10:00 にログイン、サーバ B では 09:58 に大量ダウンロードと記録されていても、時計がずれていれば本当の順序が分からなくなります。そのため、NTP などで時刻をそろえます。さらに、攻撃者が侵入後にログを消す可能性もあるため、重要なログは別の場所へ転送し、書き換えにくい形で保存します。

EDR は Endpoint Detection and Response の略で、PC やサーバなどの端末で起きている不審な動きを検知し、調査や封じ込めを支援する仕組みです。従来のウイルス対策が既知の不正ファイル検出に寄りがちだったのに対し、EDR はプロセスの起動、ファイル操作、通信先、認証の様子などをつなげて見ます。たとえば、普段使われない管理ツールが深夜に起動し、短時間で多くのファイルへアクセスし、外部へ通信しているなら、単独の出来事より危険度が高く見えます。

ランサムウェアへの備えでは、バックアップの考え方が重要です。バックアップが同じネットワーク上に常時接続され、同じ管理者権限で書き換えられるなら、攻撃者にまとめて暗号化される可能性があります。だから、バックアップは世代を分け、通常の利用者や感染端末から直接書き換えられない場所に保管し、復元できるかを定期的に確認します。バックアップは「取っている」だけでは不十分で、「必要な時間内に、必要な時点へ、実際に戻せる」ことが重要です。

復旧では、きれいなバックアップを選ぶ判断も必要です。侵入に気づいた日が今日でも、攻撃者は数週間前から内部にいたかもしれません。その場合、昨日のバックアップにはすでに不正な設定やマルウェアが含まれている可能性があります。復旧とは、単に最新のデータを戻す作業ではなく、どの時点が安全だったのかを調べ、再侵入されないよう原因を取り除いたうえでサービスを戻す活動です。

脆弱性管理でも、見つかったものを順番に直せばよいわけではありません。公開サーバにあり、攻撃方法が広く知られ、重要データへ届く脆弱性は優先度が高くなります。一方、外部から届かない検証環境にあり、追加の認証が必要で、影響が限定的な脆弱性は、同じ CVSS 点数でも対応順が変わることがあります。対応順は、深刻度、露出、攻撃可能性、資産価値、代替策、停止できる時間を合わせて決めます。

パッチ適用にも設計があります。急いで直すべき脆弱性では早さが重要ですが、本番システムに変更を入れる以上、新しい障害を生む可能性もあります。そのため、影響範囲を確認し、検証環境で試し、戻し方を用意し、適用後に監視します。緊急時には通常より速く進める必要がありますが、記録や承認や結果確認を完全に省くと、あとから何が起きたか分からなくなります。セキュリティ対応は、急ぐことと雑にすることを分けて考えます。

SOC は Security Operation Center、セキュリティ監視を行う組織や機能です。CSIRT は Computer Security Incident Response Team、インシデント対応を担うチームです。SIEM は Security Information and Event Management で、サーバ、ネットワーク機器、認証基盤、アプリケーションなどのログを集め、相関分析します。相関分析とは、単独では小さく見える出来事を組み合わせて意味を読むことです。たとえば、深夜のログイン失敗、直後の海外 IP からの成功ログイン、大量ダウンロードが別々に起きているように見えても、つなげるとアカウント侵害の兆候かもしれません。

## 8.8 セキュリティを設計に埋め込む

セキュリティは、最後に診断ツールをかけて終わるものではありません。要求、設計、実装、テスト、運用のそれぞれで考える必要があります。後から対策を付け足すと、画面、API、DB、ログ、権限、運用手順の全部に手戻りが出ることがあります。

まず、守る資産を具体化します。資産とは、価値があり、失われると困るものです。個人情報、成績、支払情報、ソースコード、秘密鍵、ログ、業務ノウハウ、サービスの稼働そのものも資産です。資産が分からないままでは、何を守っているのか分からず、対策が形だけになります。

次に、データの分類を行います。誰でも見てよい公開情報、校内だけで扱う内部情報、本人や担当者だけが見られる個人情報、漏れると重大な被害が出る秘密情報では、必要な保護が違います。すべてを最高機密のように扱うと運用が重くなり、逆にすべてを軽く扱うと事故が起きます。分類は、保護の強さを決めるための前提です。

セキュリティ要件は、具体的に書きます。「安全にする」では設計できません。「保護者は自分の子どもの欠席連絡だけ閲覧できる」「管理者操作は操作日時、操作者、対象、結果を監査ログに残す」「パスワード再設定リンクは 30 分で無効になる」「重要操作では再認証を求める」のように、確認できる文にします。

デフォルト拒否も重要です。デフォルト拒否とは、許可されたものだけを通し、それ以外は拒否する考え方です。逆に、特に禁止したものだけ止める方式では、想定していない操作が通る可能性があります。権限設計では、「誰ができないか」を後から足すより、「誰が何をできるか」を明示し、それ以外は拒否する方が安全です。

フェイルセキュアは、失敗したとき安全側に倒れる設計です。たとえば認可サーバへ問い合わせできないときに、確認できないから全員を通すのは危険です。確認できないなら一時的に拒否し、利用者には適切なエラーを出す方が安全です。ただし、医療や防災のように止めること自体が危険な場合もあるため、何を安全側とするかは業務の性質で決めます。

入力検証は、サーバ側で行います。画面側で入力チェックをしていても、攻撃者はブラウザを通さず直接 API へリクエストを送れます。画面の JavaScript で 200 文字以内に制限しているから大丈夫、とは言えません。サーバ側でも型、長さ、範囲、形式、権限、状態を確認します。

出力エスケープは、出す場所の文脈で変わります。HTML の本文に出すのか、HTML 属性に出すのか、JavaScript 文字列に入れるのか、URL に入れるのかで、危険な文字の意味が違います。XSS 対策では、「入力時に消毒すれば終わり」ではなく、出力する場所で特別な意味を持たない形に変換する考え方が大切です。

認可チェックは、画面を隠すだけでは足りません。管理者ボタンを一般利用者の画面に表示しないことは大切ですが、API 側で権限を確認しなければ、URL やリクエストを直接送られて操作される可能性があります。見た目の制御と、サーバ側の認可は別の層で考えます。

ログ設計では、調査に必要な情報と、残してはいけない情報の両方を考えます。誰が、いつ、どこから、何を、どの結果で行ったかは重要です。一方で、パスワード、秘密鍵、認証トークン、過度に詳しい個人情報をログに出すと、ログ漏えい時の被害が大きくなります。ログは証拠にもなりますが、守るべきデータにもなります。

エラーメッセージも設計対象です。「このメールアドレスは登録されています」と出すと、攻撃者が登録済みアドレスを調べられる場合があります。一方で、利用者に何も分からないエラーだけを返すと、正当な利用者が困ります。外部に出すメッセージは安全で分かりやすく、内部ログには調査に必要な詳細を残す、という分け方が有効です。

クラウド利用では、責任分担を理解します。クラウド事業者がデータセンターや物理サーバを守っていても、利用者側の設定ミスでストレージを公開してしまえば情報漏えいが起きます。ID 管理、アクセス権限、ネットワーク設定、暗号鍵、ログ、バックアップ、利用者データの扱いは、サービス形態によって利用者側の責任が残ります。

最後に、セキュリティは利用者体験とも関係します。厳しすぎるルールで利用者が別の危険な回避策を使うようになると、かえって危険です。たとえば、パスワード変更を頻繁に強制しすぎて、利用者がメモに書いて貼るようになれば意味が薄れます。安全性、使いやすさ、運用負荷を同時に見て、現実に守り続けられる設計にします。

人的対策も、単なる注意喚起ではなく設計として考えます。人は疲れていると確認を省き、急いでいると警告を読まず、信頼している相手からの連絡だと思うとリンクを開きやすくなります。だから「気をつけましょう」だけでは弱く、危険な操作をしにくい画面、二重確認、権限分離、承認手順、通報しやすい窓口を用意します。

フィッシング対策では、利用者教育と技術対策を組み合わせます。メールの文面だけで本物か判断するのは難しいため、送信ドメイン認証、迷惑メールフィルタ、ブラウザの警告、多要素認証、パスワードマネージャを重ねます。パスワードマネージャは、正しいドメインでだけ保存済みパスワードを入力するため、偽サイトに気づく助けにもなります。

多要素認証にも運用上の注意があります。攻撃者がパスワードを盗んだ後、何度も承認通知を送り、利用者が誤って承認することがあります。承認するだけの方式ではなく、番号照合、操作内容の表示、普段と違う場所からのログイン検知、重要操作での再確認を組み合わせると、誤承認の危険を減らせます。

アカウントのライフサイクル管理も重要です。利用者が入ったときにアカウントを作り、役割が変わったときに権限を変え、離れたときに停止する流れです。入学、進級、担任変更、卒業、転勤、委託契約終了のような出来事に合わせて、権限も変わらなければなりません。

特に危険なのは、辞めた人や役割が変わった人の権限が残ることです。昔は担当者だったから管理者権限を持っていたが、今は関係ないのに残っている、という状態は攻撃や誤操作の入口になります。定期的なアクセス権レビューでは、各利用者が今もその権限を必要としているかを確認します。

特権アカウントは、通常アカウントより強く管理します。特権アカウントとは、管理者権限を持ち、設定変更、利用者管理、ログ閲覧、データ削除などができるアカウントです。便利だから全員を管理者にする、共有管理者アカウントを使い回す、という運用は危険です。誰がどの操作をしたか追えず、被害も広がります。

特権管理では、普段は低い権限で作業し、必要なときだけ承認を得て一時的に高い権限を使う方法があります。操作は記録し、重要な作業では二人承認や作業後レビューを行います。強い権限は、持ち続けるものではなく、必要な時間だけ借りるものとして設計すると安全性が上がります。

教育では、専門用語を並べるだけでは効果が出ません。利用者が実際に遭遇する場面で考えます。偽のログイン画面、添付ファイル、緊急を装う依頼、上司や先生を名乗る連絡、QR コード、クラウド共有リンクなど、日常に近い例で「どこを確認するか」「迷ったらどこへ聞くか」を決めます。

報告しやすさも防御の一部です。利用者が「怪しいリンクを開いたかもしれない」と思ったとき、怒られるのが怖くて黙っていると被害が広がります。早く報告すれば、パスワード変更、セッション無効化、端末隔離、ログ確認で被害を小さくできます。セキュリティ文化とは、失敗を隠させない仕組みでもあります。

## 8.9 セキュリティテストと診断

セキュリティは、設計したつもりで終わりではありません。実際に攻撃されにくいか、設定が意図どおりか、ログで追跡できるかを確認する必要があります。普通の機能テストが「期待どおり使えるか」を見るのに対し、セキュリティテストは「期待していない使われ方をされても守れるか」を見ます。

脆弱性診断は、既知の弱点や危険な設定がないかを調べる活動です。Web アプリなら、SQL インジェクション、XSS、CSRF、認可不備、セッション管理、危険な HTTP ヘッダ、エラーメッセージの情報漏えいなどを見ます。ネットワークなら、不要なポート、古いプロトコル、弱い暗号設定、管理画面の露出などを確認します。

ペネトレーションテストは、攻撃者の視点でどこまで侵入や権限拡大が可能かを検証する活動です。脆弱性を個別に見つけるだけでなく、複数の弱点を組み合わせたときの被害を見ます。たとえば、弱いパスワードで一般利用者としてログインし、認可不備で他人の情報を見て、さらに管理機能へ到達できるかを確認します。個別の弱点は小さく見えても、つながると重大な被害になります。

セキュリティテストでは、正常系だけではなく悪用の流れを考えます。入力欄へ長すぎる文字列を入れる、HTML や SQL の特殊文字を入れる、他人の ID を URL に入れる、ログイン前に API を呼ぶ、権限の低い利用者で管理 API を呼ぶ、同じ要求を連続で送る、期限切れトークンを使う。こうした操作は、普通の利用者があまりしないからこそ、設計の穴が見つかります。

ただし、診断ツールの結果をそのまま結論にしてはいけません。ツールは広く調べるのに役立ちますが、業務ルールの認可不備や、データの意味に関わる問題は見落とすことがあります。たとえば「担任は自分のクラスだけ見られる」というルールは、ツールだけでは判断しにくいです。セキュリティ診断では、ツールによる確認と、人間による設計理解の両方が必要です。

診断結果には優先順位を付けます。外部から攻撃できる、認証なしで悪用できる、重要データに届く、攻撃方法が簡単、被害が大きいものは早く対応します。一方で、到達条件が厳しいものや代替策で一時的に抑えられるものは、変更リスクと合わせて計画します。ここでも、危険度、露出、業務影響、修正の難しさを合わせて判断します。

修正後には再確認が必要です。脆弱性を直したつもりでも、別の入力経路が残っている、似た画面に同じ問題がある、修正で別の機能を壊した、ということがあります。セキュリティ対応は、発見、修正、再確認、記録、再発防止までを一つの流れとして扱います。

## 8.10 データ保護とプライバシー

セキュリティでは、攻撃者を止めることだけでなく、万一漏れたときの被害を小さくすることも重要です。ここでは法律や経営判断としてのプライバシーではなく、システム設計として「どのデータを、どこで、どの範囲まで見せるか」を扱います。

最初に考えるのは、そもそもそのデータが必要かです。欠席連絡に必要なのは、日付、種別、理由、対象生徒、連絡者、確認者などです。目的に関係ない家庭事情や詳細な健康情報まで自由入力で集めると、漏えい時の被害が大きくなります。暗号化や権限管理の前に、不要なデータを持たないこと自体が防御になります。

保存期間もセキュリティ設計です。データは画面から消しても、ログ、CSV 出力、バックアップ、外部連携先に残ることがあります。どこに複製されるかを洗い出し、不要になったら削除、無効化、匿名化のどれを行うかを決めます。削除を設計せずに保存だけ増やすと、攻撃者に渡す材料も増えます。

マスキングは、必要な部分だけ見せ、不要な部分を隠す方法です。電話番号の一部を `***` にする、問い合わせ担当には詳細な成績を見せない、といった設計です。画面だけを隠しても、CSV 出力や通知メールに全情報が出れば意味がありません。保護対象は、画面、API、ログ、帳票、外部送信まで同じデータの流れとして追います。

仮名化は、氏名などを別の ID に置き換え、直接は個人を分かりにくくする方法です。対応表が残っていれば元に戻せるため、対応表そのものを強く守る必要があります。匿名化は、個人へ戻せないように加工する考え方ですが、名前を消すだけでは足りません。少人数のクラス、珍しい属性、日付の組合せから個人が推測できる場合があるからです。

外部サービスへデータを渡すときは、渡す項目を最小にします。通知サービスへ送るなら、宛先と通知本文だけで足りるかもしれません。学生番号、詳細理由、内部メモまで送る必要があるのかを確認します。外部へ出したデータは、自分たちのシステム内だけの権限管理では守れません。

## 8.11 設定管理とハードニング

セキュリティ事故は、高度な攻撃だけで起きるわけではありません。初期パスワードのまま使う、不要な管理画面を公開する、古い暗号方式を許す、誰でも読める場所に秘密情報を置く、といった設定ミスでも起きます。

ハードニングは、システムを安全な設定へ固めることです。不要なサービスを止める、不要なポートを閉じる、管理画面への接続元を絞る、初期アカウントを無効化する、弱い暗号方式を使わない、ログを有効にする、バックアップを確認する、といった作業が含まれます。機能を増やすのではなく、攻撃される入口を減らす考え方です。

初期設定は便利さを優先していることがあります。導入直後にすぐ試せるよう、広い権限、簡単なパスワード、公開されたサンプル機能が残っている場合があります。検証環境では便利でも、本番にそのまま持ち込むと危険です。本番環境では、必要な機能だけを有効にし、管理者権限や公開範囲を明確にします。

設定管理では、どの設定が正しい状態なのかを記録します。人が手作業でサーバごとに設定すると、少しずつ差が出ます。あるサーバだけ古い TLS 設定が残る、ある環境だけデバッグモードが有効になっている、あるストレージだけ公開設定になっている、という差分は事故につながります。設定をコードやテンプレートで管理すると、差分をレビューし、同じ設定を再現しやすくなります。

秘密情報の扱いも設定管理の一部です。API キー、DB パスワード、秘密鍵、トークンは、ソースコード、チャット、表計算ファイル、ログに直接置くべきではありません。専用のシークレット管理に置き、誰が読めるか、いつ使われたか、いつ入れ替えるかを管理します。

セキュリティベースラインは、最低限満たすべき安全な設定の基準です。新しいサーバやクラウド環境を作るたびに、ログ、権限、暗号設定、ネットワーク公開範囲、バックアップ、監視が基準を満たすか確認します。ベースラインがあると、担当者ごとの判断差を減らせます。

設定は一度固めれば終わりではありません。運用中に一時対応で開けたポート、調査のために上げた権限、検証のために入れた例外が、そのまま残ることがあります。定期的に設定を棚卸しし、不要な許可や例外を戻します。セキュリティは追加する対策だけでなく、増えた例外を減らす作業でもあります。

## 実務で使える理解

- 暗号化、ハッシュ、署名、認証を混同しない。
- 共通鍵は速いが鍵配送が課題。公開鍵は鍵配送に強いが遅い。
- ディジタル署名は、送信者の秘密鍵で署名し、公開鍵で検証する。
- 証明書は、公開鍵と所有者を CA が結びつける。
- 攻撃は「どの信頼境界を破ったか」で読む。SQL、ブラウザ、セッション、通信、可用性のどこが狙われたかを見る。
- 認可不備は、ログイン済みかどうかではなく、対象データへの操作権限で考える。
- SSRF、パストラバーサル、OS コマンドインジェクションは、入力がサーバ側の通信先、ファイルパス、OS 命令に混ざる問題として読む。
- リスク対応は、回避、低減、移転、受容。
- Common Criteria や EAL は、評価対象、設定、前提条件、評価の深さを読んで判断する。
- セキュリティ要件は、資産、脅威、権限、ログ、復旧、データ保護まで含めて具体化する。
- 診断やテストは、設計どおり守れているかと、想定外の使われ方に耐えられるかを見る。
- ハードニングでは、不要な入口を閉じ、安全な設定を維持する。

## 自分の言葉で説明する

- 共通鍵暗号と公開鍵暗号を比較できる。
- ハッシュ関数の用途を説明できる。
- MAC とディジタル署名の違いを説明できる。
- PKI、CA、証明書、CRL/OCSP を説明できる。
- TLS が何を守るか説明できる。
- ファイアウォール、IDS、IPS、WAF の違いを説明できる。
- SQL インジェクション、XSS、CSRF がそれぞれ何を信じすぎた攻撃か説明できる。
- IDOR がなぜ認証ではなく認可の問題なのか説明できる。
- SSRF、パストラバーサル、OS コマンドインジェクションを、サーバ側で信頼してはいけない入力の例として説明できる。
- CIA を説明できる。
- リスク対応の回避、低減、移転、受容を、具体的な判断例で説明できる。
- ISMS と PDCA の関係を説明できる。
- TOE、Security Target、Protection Profile、EAL を、評価範囲と保証の深さという観点で説明できる。
- 脆弱性診断とペネトレーションテストの違いを説明できる。
- データ最小化、マスキング、仮名化、匿名化の違いを説明できる。
- 特権アカウントと通常アカウントを分ける理由を説明できる。
- ハードニングと設定管理がなぜ事故防止に効くか説明できる。

## 深く身につけるための補講

セキュリティは「強い暗号を使えば終わり」ではありません。守る対象、攻撃者、弱点、運用、法律、教育まで含めて考える必要があります。

たとえば、家を守ることを考えます。

鍵を強くすることは、暗号や認証に近い対策です。本人でない人が入れないようにします。誰がどの部屋に入れるかを決めることは、認可に近い対策です。家族でも金庫までは開けられない、来客は玄関まで、といった範囲を決めます。

監視カメラを置くことは、ログ監視に近い対策です。何かが起きたとき、いつ、誰が、どこで行動したかを後から追えるようにします。侵入された後に気づく仕組みは IDS に近く、侵入をその場で止める仕組みは IPS や WAF に近いです。火事や地震に備えることは、可用性やバックアップに近い対策です。攻撃だけでなく事故や災害でも、必要なサービスを続けられるようにします。

情報セキュリティも同じで、1 つの対策だけでは守りきれません。多層防御が必要です。

## 暗号・ハッシュ・署名を混同しない

3 つは似て見えますが、目的が違います。暗号化は、第三者に読めないようにするための技術です。正しい鍵を持っていれば復号して元の内容を読めます。ハッシュは、データから指紋のような短い値を作る技術です。普通は元に戻すためではなく、同じデータか、改ざんされていないかを確認するために使います。ディジタル署名は、本人性と改ざんなしを示すための技術です。送信者の秘密鍵で署名し、受信者は公開鍵で検証します。

パスワード保存で暗号化ではなくハッシュを使うのは、管理者にも元のパスワードを戻せないようにするためです。ただし単純なハッシュだけでは総当たりに弱いので、ソルトやストレッチングも使います。

## 攻撃は「信頼した入力」から起きる

多くの攻撃は、システムが外部からの入力を信じすぎることで起きます。

SQL インジェクションでは、入力を SQL の一部として信じてしまうことが問題です。本来は検索条件の値として扱うべき文字列が、データベースへの命令に混ざってしまいます。XSS では、入力された文字列を HTML や JavaScript として信じてしまうことが問題です。本来は画面に表示する文字列なのに、ブラウザがコードとして実行してしまいます。

CSRF では、利用者のブラウザから来たリクエストを本人の意思だと信じてしまうことが問題です。ログイン済みであることと、その操作を本人が画面上で選んだことは別です。セッションハイジャックでは、セッション ID を持っている人を本人だと信じてしまうことが問題です。だから、セッション ID を盗まれにくくし、漏れた場合の被害も小さくする必要があります。

IDOR では、指定された ID のデータを見てもよいと信じてしまうことが問題です。SSRF では、入力された URL へサーバがアクセスしてよいと信じてしまうことが問題です。パストラバーサルや OS コマンドインジェクションでは、入力された文字列をファイルパスや命令の一部として信じてしまうことが問題です。

対策の基本は、入力を検証し、出力時に文脈に合わせてエスケープし、権限を最小にし、重要操作では追加確認することです。

## ありがちな誤解

- パスワードを複雑にすれば十分ではない。漏えい、使い回し、フィッシングへの対策も必要。
- 暗号化していれば改ざんされないとは限らない。完全性の確認が必要。
- 社内ネットワークなら安全とは限らない。内部不正や侵害済み端末がある。
- セキュリティ製品を入れれば終わりではない。設定、監視、更新、教育が必要。
- 可用性もセキュリティの一部。止められる攻撃も守るべき対象。
- 診断ツールだけでは業務ルールの認可不備まで十分に見つけられない。
- データは暗号化すれば何でも集めてよいわけではない。必要性と保存期間も設計する。
- 初期設定のまま動いていることは、動作確認としては便利でも本番の安全性とは別です。
- ログインできていることと、そのデータを見てよいことは別。
- 入力チェックは画面側だけでは足りない。サーバ側で対象、権限、形式、範囲を確認する。
- セキュリティ評価済みの製品でも、評価された範囲、バージョン、設定、運用前提から外れれば、同じ安全性が保証されるとは限らない。

## 手を動かす課題

1. SNS アカウントを守るための対策を、認証、認可、監視、復旧に分けて説明してください。
2. SQL インジェクションが起きる理由を、「入力を命令として扱ってしまう」という言葉で説明してください。
3. 暗号化、ハッシュ、ディジタル署名の違いを、手紙のたとえで説明してください。
4. リスク対応の回避、低減、移転、受容を、文化祭の出店準備を例に説明してください。
5. 欠席連絡アプリで外部通知サービスへ渡してよいデータと、渡すべきでないデータを分けて説明してください。
6. セキュリティ診断で見つかった問題を、危険度、露出、業務影響から優先順位付けしてください。
7. 新しく公開する Web サーバで、不要な入口を減らすために確認すべき設定を説明してください。
8. 欠席連絡アプリで `studentId` を別の値に変えると他人の情報が見える問題を、IDOR と認可の観点で説明してください。
9. 利用者が入力した URL やファイル名をサーバが扱う機能で、SSRF やパストラバーサルを防ぐ設計を説明してください。
10. 「Common Criteria 認証済みの製品だから安全」と言われたとき、TOE、Security Target、EAL、評価された設定の観点で、追加確認すべきことを説明してください。
