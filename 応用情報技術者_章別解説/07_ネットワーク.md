# 第7章 ネットワーク

## この章の地図

ネットワークは、コンピュータ同士が通信するための約束ごとです。階層モデル、IP アドレス、TCP/UDP、アプリケーションプロトコル、無線 LAN、伝送制御を理解すると、「なぜ通信できるのか」「なぜ遅いのか」「なぜ届かないのか」を説明できるようになります。

この章では、まず「1 つの通信がどれだけ多くの役割に分かれているか」を見ます。ブラウザでページを開くとき、画面には一瞬で表示されるように見えますが、裏側では、名前解決、経路選択、到達確認、暗号化、要求と応答の形式、電波やケーブルでの送受信が分担されています。

高度な理解とは、OSI や TCP/IP の層名を順番に並べることではありません。「この通信障害は DNS の問題か、IP の問題か、TCP の問題か、HTTP の問題か」「この装置は MAC アドレスを見ているのか、IP アドレスを見ているのか、ポート番号を見ているのか」を切り分けられることです。

## なぜこの章を学ぶのか

ネットワークは、現代の IT の血管のようなものです。スマホで動画を見る、学校のクラウド教材を開く、オンラインゲームをする、銀行アプリで残高を見る、これらはすべてネットワーク通信の上で動いています。

通信がうまくいかないとき、初心者は「インターネットが壊れた」と一言で考えがちです。しかし実際には、Wi-Fi、IP アドレス、DNS、ルーティング、TCP、TLS、HTTP など、別々の仕組みが段階的に関わっています。どの段階で失敗しているかを切り分けられると、原因を論理的に探せます。

この章を学ぶと、「名前を住所に変える」「相手まで道を選ぶ」「届いたか確認する」「Web の形式で要求する」という通信の分業が見えるようになります。

## 7.1 通信プロトコルの標準化

この節を学ぶ理由は、通信には共通の約束が必要だからです。人間同士でも、言語や住所の書き方が違うと手紙が届きません。コンピュータ同士も同じで、データの形、送る順番、エラー時の対応を決める必要があります。

階層モデルを学ぶと、通信を一気に丸ごと飲み込もうとせず、「電気信号」「同じ LAN 内」「ネットワーク間」「アプリのやり取り」のように分けて理解できます。

プロトコルは、通信の約束です。送る順番、形式、エラー時の処理を決めます。

### なぜ通信を階層に分けるのか

もし Web ブラウザが、Wi-Fi の電波の出し方、LAN ケーブルの信号、ルータの経路選択、データの再送、暗号化、HTML の要求形式をすべて直接知っていなければならないとしたら、ブラウザは複雑すぎて作れません。Wi-Fi が新しくなるたびに、ブラウザも作り直しになります。

そこで通信では、役割を層に分けます。上の層は下の層に「このデータを相手へ運んで」と頼みます。下の層は、上の層の中身を深く知らなくても、自分の担当だけを果たします。

身近な例で考えると、荷物を送るときに、送り主は中身を用意し、配送会社は宛先まで運び、道路や鉄道や飛行機は物理的に移動を支えます。送り主はトラックのエンジン構造まで知らなくても荷物を送れます。配送会社も、箱の中身が教科書か服かまで知らなくても運べます。この「役割を分ける」考え方が階層化です。

### TCP/IP モデルとは何か

TCP/IP モデルは、インターネットで実際に使われる通信の責任分担です。名前に TCP と IP が入っていますが、TCP と IP だけを指すのではありません。HTTP、DNS、TCP、UDP、IP、ICMP、Ethernet、Wi-Fi など、インターネットを動かすプロトコル群を、役割ごとに整理した見方です。

たとえば、ブラウザで `https://example.com/` を開くとします。ブラウザが送りたい本体は、Web サーバへの要求です。

```text
GET / HTTP/1.1
Host: example.com
```

しかし、この文字列だけでは相手に届きません。次のように、各層が自分の担当情報を付け足していきます。

```text
アプリケーション層
  HTTP の要求を作る

トランスポート層
  TCP で、相手アプリのポート番号、順序、再送を管理する

インターネット層
  IP で、相手コンピュータの IP アドレスまで届ける

ネットワークインタフェース層
  Ethernet や Wi-Fi で、次の機器までフレームとして送る
```

ここで大事なのは、各層が解く問題が違うことです。

- HTTP は、Web の要求と応答の形式を決めます。
- TCP は、データを順番どおり確実に届ける努力をします。
- IP は、宛先 IP アドレスへ向かう経路をたどります。
- Ethernet や Wi-Fi は、同じ LAN の中で次の機器へ届けます。

つまり TCP/IP モデルは、「通信を小さな責任に分ける設計図」です。層名を並べるための表ではありません。短く並べると次のようになりますが、読むときは必ず「その層が何の責任を引き受けているか」に戻ります。

```text
アプリケーション層: HTTP, SMTP, DNS など
トランスポート層: TCP, UDP
インターネット層: IP, ICMP
ネットワークインタフェース層: Ethernet, Wi-Fi
```

### カプセル化を箱で理解する

カプセル化とは、上の層のデータを下の層が包むことです。HTTP のデータを TCP が包み、それを IP が包み、それを Ethernet や Wi-Fi が包みます。

```text
[Ethernet ヘッダ [IP ヘッダ [TCP ヘッダ [HTTP データ]]]]
```

ヘッダとは、配送に必要な宛名や管理情報です。荷物でいえば、箱の外に貼る送り状のようなものです。

受信側では逆に、外側から順に外していきます。

```text
Ethernet が外側を確認する
IP が宛先 IP を確認する
TCP が順序やポート番号を確認する
HTTP が要求内容を読む
```

この仕組みのおかげで、HTTP は Wi-Fi の細部を知らなくてよく、Wi-Fi は HTTP の中身を知らなくてよくなります。

### ブラウザでページを開く通信を一続きで追う

TCP/IP モデルを本当に理解するには、層名を上から読むだけでは足りません。ブラウザで `https://example.com/news` を開いた瞬間、コンピュータの中で何が順番に起きるかを追うと、各層の役割が立体的に見えます。

最初に、ブラウザは URL を分解します。`https` は通信を TLS で保護するという方式、`example.com` は相手の名前、`/news` は相手サーバ内でほしい資源の位置です。ここで注意したいのは、`example.com` は人間に読みやすい名前であって、IP がそのまま運べる住所ではないことです。

次に DNS で、`example.com` に対応する IP アドレスを調べます。これは「学校名から住所を調べる」作業に近いです。DNS が失敗すると、ネットワーク回線が生きていても、ブラウザは相手の住所を知らないため接続できません。このとき利用者には「サイトが見つかりません」のように見えますが、実際には HTTP 以前の名前解決で止まっています。

IP アドレスが分かると、端末はその宛先が自分と同じネットワーク内か、外のネットワークかを判断します。外のネットワークなら、まずデフォルトゲートウェイへ渡します。デフォルトゲートウェイとは、自分の LAN から外へ出るときの出口になるルータです。ここで最終目的地の IP アドレスは `example.com` のサーバですが、次に直接渡す相手はルータです。だから、IP アドレスだけでなく、次に渡す相手の MAC アドレスも必要になります。

その後、TCP が通信の入口を作ります。Web サーバの HTTPS は通常 443 番ポートで待ち受けています。ポート番号は、1 台のサーバの中でどのアプリケーションに届けるかを示す番号です。IP アドレスが建物の住所なら、ポート番号は部屋番号です。TCP は 3 ウェイハンドシェイクで、こちらから送れること、相手が受け取れること、相手の返事をこちらが受け取れることを確認します。

HTTPS では、このあと TLS が暗号化された通信路を作ります。TLS は単にデータを読めなくするだけではありません。証明書によって「本当にそのサーバへつながっているか」も確認します。ここが弱いと、通信が暗号化されていても、攻撃者のサーバに向けて暗号化してしまう危険があります。

最後に、HTTP の要求が送られます。HTTP は「どの資源がほしいか」「どんな形式を受け取れるか」「Cookie を持っているか」など、Web アプリケーションとしての会話を決めます。ここまで来て初めて、Web サーバは `GET /news` のような要求を読み、HTML や JSON や画像などを返します。

この一連の流れを、層ごとの担当として言い換えるとこうなります。DNS は名前を住所へ変換します。IP はネットワークをまたいで宛先へ近づけます。Ethernet や Wi-Fi は次の機器へ実際に渡します。TCP は順序、再送、ポート番号を管理します。TLS は通信相手と暗号化を確認します。HTTP は Web の意味を持つ要求と応答を扱います。これが、TCP/IP モデルを「通信の責任分担」として読むということです。

### ヘッダは各担当者が貼る作業メモ

カプセル化で付け足されるヘッダは、ただの飾りではありません。各層が自分の仕事をするための作業メモです。

TCP ヘッダには、送信元ポート、宛先ポート、順序番号、確認応答番号などが入ります。順序番号は、分割されたデータを受信側で正しい順番に戻すために使います。確認応答番号は、「ここまで受け取った」と相手に知らせるために使います。これがあるから、途中で抜けたデータを再送できます。

IP ヘッダには、送信元 IP アドレス、宛先 IP アドレス、生存時間 TTL などが入ります。TTL は Time To Live の略で、パケットがネットワーク内を無限に回り続けないようにする値です。ルータを 1 つ通るたびに減り、0 になると破棄されます。もし経路設定のミスでぐるぐる回るパケットがあっても、TTL によって永遠には残りません。

Ethernet ヘッダには、送信元 MAC アドレスと宛先 MAC アドレスが入ります。これは最終目的地ではなく、同じ LAN 内で次に直接渡す相手を示します。遠くの Web サーバへ行く通信でも、あなたの PC が最初に見る宛先 MAC は、多くの場合、家庭や学校のルータです。

つまり、ヘッダは「誰が何を見て、どこまで責任を持つか」を分けるための情報です。TCP/IP モデルを理解するとは、このヘッダの責任範囲を読めるようになることでもあります。

### OSI 基本参照モデルは何のためにあるのか

OSI 基本参照モデルは、通信機能を 7 層に分けた標準的な説明モデルです。実際のインターネットは TCP/IP モデルで動いていますが、OSI は「どの機能がどのあたりの責任か」を説明する共通語として使われます。

たとえば、ネットワーク機器の説明で「L2 スイッチ」「L3 ルータ」「L7 ロードバランサ」と言うことがあります。この L2、L3、L7 は OSI の層番号を指します。つまり OSI は、現場で会話するための地図として役立ちます。7 層は次の順に、利用者に近い役割から物理的な信号に近い役割へ下りていきます。

```text
7 アプリケーション層
6 プレゼンテーション層
5 セション層
4 トランスポート層
3 ネットワーク層
2 データリンク層
1 物理層
```

下の層ほど線や電気信号に近く、上の層ほど利用者が使うアプリケーションに近いです。

TCP/IP モデルと OSI モデルは、完全に 1 対 1 で対応するわけではありません。TCP/IP は実装のための実用的な分類、OSI は説明や整理のための細かい分類、と考えると分かりやすいです。

### 層で考えると何がうれしいのか

層で考えると、トラブルの切り分けができます。

たとえば、Web ページが開かないとします。

- Wi-Fi に接続できないなら、ネットワークインタフェース層や物理的な問題かもしれません。
- IP アドレスが取れていないなら、IP 設定や DHCP の問題かもしれません。
- `ping` は通るのに Web だけ開かないなら、TCP のポート、TLS、HTTP、プロキシ設定が怪しくなります。
- IP アドレスでは開けるのにドメイン名では開けないなら、DNS が怪しくなります。

このように、階層モデルは通信障害を論理的に分解する道具です。

## 7.2 ネットワーク接続装置

この節を学ぶ理由は、通信機器がそれぞれ違う情報を見て中継しているからです。スイッチは MAC アドレスを見て LAN 内で届け、ルータは IP アドレスを見て別ネットワークへ届けます。

接続装置を理解すると、「なぜこの通信は同じ教室内では届くのに、外部には出られないのか」「どこで通信を分ければ安全か」を考えられます。

接続装置は、「パケットやフレームのどの情報を見て判断するか」で分類できます。

同じ `example.com` へアクセスする通信でも、機器によって見ている場所が違います。

```text
リピータ
  電気信号や光信号を見る

スイッチ
  宛先 MAC アドレスを見る

ルータ
  宛先 IP アドレスを見る

L4 ロードバランサ
  IP アドレスとポート番号を見る

L7 ロードバランサ
  HTTP の URL、ヘッダ、Cookie などを見る
```

これは、郵便で考えると分かりやすいです。建物の中で部屋番号を見て配る係、町から町へ住所を見て運ぶ係、荷物の種類を見て冷蔵便や通常便に分ける係は、見ている情報が違います。ネットワーク装置も同じです。

リピータは物理層の装置で、弱くなった電気信号や光信号を再生します。宛先の意味までは見ません。ブリッジやスイッチはデータリンク層の情報、つまり MAC アドレスを見て、同じ LAN の中でどのポートへフレームを流すかを決めます。スイッチは、多数のポートを持つ高速なブリッジと考えると分かりやすいです。

ルータはネットワーク層の装置で、IP アドレスを見て別のネットワークへパケットを運びます。同じ校内 LAN の中で配るのではなく、「次はどのネットワークへ渡すか」を決める役割です。ゲートウェイは、より上位の層まで見て、異なるプロトコルや異なるシステム同士をつなぐ場合に使われます。L4 ロードバランサはポート番号などを見て振り分け、L7 ロードバランサは HTTP の URL、ヘッダ、Cookie などアプリケーション層の情報まで見て、どのサーバへ渡すかを決めます。

VLAN は、物理的な配線とは別に、論理的な LAN を分ける技術です。同じスイッチに接続していても、部署ごとにブロードキャスト範囲を分けられます。

たとえば同じ校舎の同じスイッチにつながっていても、教員用端末と生徒用端末を同じ LAN に入れると、不要な通信が見えたり、管理が難しくなったりします。VLAN を使うと、物理的には同じ機器を使いながら、論理的には別のネットワークとして分けられます。

VLAN を複数のスイッチへまたがって使うときは、トランクポートが必要になります。トランクポートは、複数の VLAN のフレームを 1 本の物理リンクに通すためのポートです。各フレームには VLAN ID が付けられ、「これは教員用 VLAN」「これは生徒用 VLAN」のように区別されます。アクセスポートは、通常 1 つの VLAN に所属する端末向けのポートです。教室の PC をつなぐポートはアクセス、スイッチ同士をつなぐポートはトランク、と考えると整理しやすいです。

VLAN は分ける技術ですが、VLAN を分けただけで通信が絶対に安全になるわけではありません。VLAN 間で通信させるにはルータや L3 スイッチが必要になり、そこでアクセス制御を設計します。教員 VLAN から成績サーバへは許可し、生徒 VLAN からは許可しない、といったルールを作ります。物理配線、VLAN、IP サブネット、ファイアウォール規則が食い違うと、意図しない通信や通信不能が起きます。

スイッチを冗長化するときは、ループにも注意します。ループとは、フレームが輪のような経路をぐるぐる回れる状態です。Ethernet のフレームには IP の TTL のような寿命がないため、ループするとブロードキャストが増え続け、ネットワーク全体が重くなることがあります。これをブロードキャストストームと呼びます。STP は Spanning Tree Protocol の略で、ループを避けるために一部の経路をあえて待機状態にします。冗長な線を引くことは高信頼化に見えますが、制御しない冗長性は事故の原因にもなります。

SDN は、ネットワーク制御をソフトウェアで集中管理する考え方です。NFV は、ルータやファイアウォールなどのネットワーク機能を汎用サーバ上のソフトウェアとして実現します。

## 7.3 データリンク層の制御

この節を学ぶ理由は、同じ LAN の中でデータを届ける仕組みを理解するためです。IP アドレスが最終的な住所だとしても、同じネットワーク内で実際に機器へ届けるには MAC アドレスやフレームの仕組みが必要です。

データリンク層を学ぶと、スイッチ、Ethernet、Wi-Fi、MAC アドレス、誤り検出がつながります。

データリンク層は、同じネットワーク内でフレームを届けます。ここで使われる MAC アドレスは、NIC に割り当てられた識別子です。NIC は Network Interface Card の略で、PC やサーバがネットワークへ接続するための部品や機能です。Ethernet では、この MAC アドレスを使って同じ LAN 内の次の相手へフレームを届けます。

IP アドレスが「最終目的地の住所」だとすると、MAC アドレスは「次に直接渡す相手の識別子」です。インターネットの遠くのサーバへ通信するときでも、あなたの PC が最初に直接渡す相手は、たいてい家庭や学校のルータです。そのため、同じ LAN の中では MAC アドレスが必要になります。

```text
最終目的地: example.com の IP アドレス
次に直接渡す相手: ルータの MAC アドレス
```

この違いを押さえると、「IP アドレスだけでよいのでは？」という疑問がほどけます。IP はネットワークをまたぐための住所、MAC は同じ LAN の中で次の一歩を踏み出すための宛先です。

IP アドレス、MAC アドレス、ポート番号は、どれも「宛先」のように見えるので混乱しやすいです。しかし、見ている範囲が違います。MAC アドレスは同じ LAN 内の次の機器を見ます。IP アドレスはネットワークをまたいだ最終的なコンピュータを見ます。ポート番号は、そのコンピュータの中のアプリケーションを見ます。

たとえば家から Web サーバへ接続するとき、あなたの PC は最終目的地の IP アドレスを知っています。しかし、最初に電波やケーブルで直接渡せる相手は家庭のルータです。だから Ethernet や Wi-Fi の宛先 MAC はルータになります。ルータは受け取った IP パケットを見て、次のルータや回線へ渡します。これが何度も繰り返され、最後に Web サーバがいるネットワークへ届きます。最後の LAN では、宛先 MAC が Web サーバの NIC になります。

ここでポート番号がなければ、Web サーバのどのアプリに渡すかが分かりません。同じサーバで HTTPS、SSH、メール、監視エージェントが同時に動いていることがあります。IP アドレスでサーバまでは届いても、ポート番号でアプリケーションを選ばなければ、正しいプログラムに渡せません。

同じ通信媒体を複数の機器で共有するときは、誰がいつ送信するかを調整する必要があります。これをメディアアクセス制御といいます。CSMA/CD は、有線 Ethernet で衝突を検出する考え方です。ただし現在はスイッチの普及により、昔の共有型 Ethernet のような衝突は少なくなっています。CSMA/CA は、無線 LAN で衝突を避ける考え方です。無線では送信しながら衝突を正確に検出しにくいため、先に待つ、確認を取るなどの工夫で衝突を避けます。

Ethernet フレームには、宛先 MAC、送信元 MAC、タイプ、データ、FCS などが含まれます。FCS は誤り検出に使われます。

FCS は、フレームが途中で壊れていないかを確認するための値です。受信側は、届いたデータから同じ計算をして、FCS と合うかを見ます。合わなければ、途中でビットが化けた可能性があるため、そのフレームは捨てます。

## 7.4 ネットワーク層のプロトコル

この節を学ぶ理由は、異なるネットワークへデータを届けるためです。家庭内や学校内だけでなく、世界中のサーバへ通信するには、ネットワークをまたいで経路を選ぶ仕組みが必要です。

IP アドレスとサブネットを理解すると、ネットワークの住所設計、クラウドのネットワーク分割、通信できない原因の切り分けができるようになります。

IP は、異なるネットワーク間でパケットを届けるためのプロトコルです。ベストエフォート型で、到達保証や順序保証はしません。保証は TCP など上位層が担当します。

ベストエフォートとは、「できるだけ届けるが、必ず届くとは約束しない」という意味です。これは無責任に見えるかもしれませんが、インターネット全体を単純で拡張しやすくするための重要な設計です。IP は経路選択に集中し、再送や順序制御は TCP などに任せます。役割を分けることで、ネットワークの中心部分を複雑にしすぎないようにしています。

ルータは、受け取った IP パケットをどこへ渡すかをルーティングテーブルで決めます。ルーティングテーブルは、宛先ネットワークと次に渡す相手の対応表です。自分の PC が「外へ出るときはデフォルトゲートウェイへ渡す」と設定されているのも、経路選択の一種です。

経路選択で重要なのが最長一致です。たとえば、宛先 `10.1.2.34` に対して、`10.1.0.0/16` へ行く経路と `10.1.2.0/24` へ行く経路が両方あるとします。`/16` は先頭 16 ビットが一致する範囲、`/24` は先頭 24 ビットが一致する範囲です。24 ビット一致する方が、16 ビット一致する方より細かい範囲を指します。差を見ると `24 - 16 = 8` で、`/24` の方が 8 ビット分だけ詳しい条件です。ルータはより具体的な `10.1.2.0/24` の経路を選びます。これが最長一致です。

経路は手で設定する静的ルーティングもありますが、大きなネットワークでは動的ルーティングを使います。動的ルーティングでは、ルータ同士が経路情報を交換し、障害や経路変更に追従します。OSPF は組織内ネットワークで使われる代表的な動的ルーティングプロトコルです。BGP はインターネットのように、組織や通信事業者のネットワーク同士をつなぐ経路制御で重要です。AS は Autonomous System、自律システムです。1 つの組織や事業者が一貫した方針で管理するネットワークのまとまりと考えると分かりやすいです。

ここで大切なのは、経路は「最短距離」だけで決まるとは限らないことです。帯域、遅延、費用、障害、契約、組織の方針によって、どの経路を選ぶかが変わります。インターネットは技術だけでなく、事業者同士の接続と運用方針の集まりでもあります。

IPv4 アドレスは 32 ビットです。たとえば次のように、8 ビットずつ 4 つに区切って十進数で表します。

```text
192.168.1.10
```

サブネットマスクは、ネットワーク部とホスト部を分けます。`192.168.1.10/24` という表記では、`/24` が「先頭 24 ビットがネットワーク部」という意味です。

```text
192.168.1.10/24
ネットワーク部: 24 ビット
ホスト部: 8 ビット
ホスト数: 2^8 - 2 = 254
```

なぜ `2^8` なのでしょうか。1 ビットは 0 または 1 の 2 通りです。ホスト部が 8 ビットなら、

```text
2 × 2 × 2 × 2 × 2 × 2 × 2 × 2 = 2^8 = 256
```

通りの組合せがあります。

なぜ `-2` するのでしょうか。IPv4 では、ホスト部が全部 0 のアドレスはネットワークそのものを表し、ホスト部が全部 1 のアドレスはブロードキャストを表すため、普通の機器には割り当てられないからです。

したがって、

```text
利用可能ホスト数 = 256 - 2
                = 254
```

サブネット計算では、まずプレフィックス長からホスト部のビット数を求めます。次に `2^(ホスト部ビット数)` で 1 サブネットあたりのアドレス数を出します。IPv4 では通常、そこからネットワークアドレスとブロードキャストアドレスを除いて利用可能ホスト数を求めます。最後に、ネットワークアドレス、ブロードキャストアドレス、利用可能範囲を確認します。

IPv6 は 128 ビットのアドレスを使います。IPv4 の 32 ビットよりはるかに大きいので、アドレス空間が非常に広くなります。表記が長くなるため省略表記があり、自動設定や IPsec との関係も重要です。IPv6 を学ぶときは、「IPv4 の単なる桁数増加」ではなく、アドレス設計や運用を大きく変える仕組みとして見ます。

IPv6 では、アドレスが長くなるだけでなく、周辺の仕組みも変わります。IPv4 では、同じ LAN 内で IP アドレスから MAC アドレスを調べるために ARP を使いました。IPv6 では ARP の代わりに NDP、Neighbor Discovery Protocol を使います。Neighbor は隣接する機器という意味で、同じリンク上にいるルータや端末を見つけたり、相手のリンク層アドレスを調べたりします。

IPv6 の自動設定には SLAAC があります。SLAAC は Stateless Address Autoconfiguration の略です。Stateless は、サーバが各端末の状態を細かく保持しないという意味です。端末はルータから Router Advertisement、つまり RA と呼ばれる通知を受け取り、ネットワークのプレフィックスを知ります。そこへ自分のインタフェース識別子を組み合わせて、自分の IPv6 アドレスを作ります。ここでプレフィックスとは、同じネットワークに属することを表す前半部分です。

DHCPv6 も IPv6 の設定に使われます。DHCPv6 は、IPv6 版の DHCP です。SLAAC だけでアドレスを作る場合もあれば、DHCPv6 で DNS サーバなどの追加情報を受け取る場合もあります。組織のネットワークでは、端末管理、ログ、アドレス払い出し方針のために SLAAC と DHCPv6 をどう組み合わせるかを設計します。

ICMPv6 も重要です。IPv4 では ICMP を単なる `ping` のための補助的なものと見てしまいがちですが、IPv6 では NDP や経路上のエラー通知にも深く関わります。むやみに ICMPv6 を止めると、アドレス解決や経路 MTU 探索が壊れ、通信が不安定になります。セキュリティのために制限することはありますが、「全部止めれば安全」とは考えません。

IPv6 移行では、IPv4 と IPv6 を同時に使うデュアルスタック、片方の通信をもう片方のネットワーク上に包んで運ぶトンネリング、アドレスやプロトコルを変換する方式があります。現実のネットワークでは、一度に全端末と全サービスを IPv6 だけにするのは難しいため、移行期間の設計が必要です。DNS、ファイアウォール、監視、ログ、アクセス制御が IPv6 に対応していないと、アドレスだけ用意しても安全に運用できません。

NAT は、プライベートアドレスとグローバルアドレスを変換します。NAPT はポート番号も使い、複数端末で 1 つのグローバルアドレスを共有できます。

家庭の Wi-Fi につながるスマホや PC は、多くの場合 `192.168.x.x` のようなプライベート IP アドレスを持ちます。この住所は家庭内では使えますが、そのままインターネット全体では通用しません。そこでルータが、家庭内の住所を外向けのグローバル IP アドレスへ変換します。これが NAT です。

複数端末が同じグローバル IP を共有できるのは、NAPT がポート番号も使って区別するからです。

```text
PC A: 192.168.1.10:50001
PC B: 192.168.1.11:50002
        ↓ NAPT
外向き: 203.0.113.5:別々のポート
```

ルータは対応表を持ち、返ってきた通信をどの端末へ戻すか判断します。

ICMP は、IP 通信の制御やエラー通知に使われます。`ping` は ICMP Echo を利用します。

ネットワーク管理では、いくつかの基本コマンドで「どこまで届いているか」を切り分けます。`ping` は、相手から応答が返るかを確認します。ただし、相手や途中の機器が ICMP を止めている場合、サービス自体は動いていても `ping` が失敗することがあります。だから `ping` の失敗だけで相手サーバ全体が停止しているとは断定できません。

`traceroute` や `tracert` は、宛先までの途中経路を確認するために使います。どのルータまでは届き、どこから先で止まっているかを見る手がかりになります。`ipconfig` や `ifconfig`、`ip addr` は、自分の端末に設定された IP アドレス、サブネットマスク、デフォルトゲートウェイなどを確認します。`nslookup` や `dig` は、DNS が名前を正しく IP アドレスへ変換できているかを確認します。

障害調査では、コマンドを順番に使います。まず自分の IP 設定を見ます。次にデフォルトゲートウェイへ届くか確認します。外部 IP へ届くかを見ます。最後に DNS 名で引けるか、HTTP やアプリケーションの応答があるかを確認します。こうすると、物理層、ネットワーク層、名前解決、アプリケーション層のどこで失敗しているかを分けられます。

## 7.5 トランスポート層

この節を学ぶ理由は、アプリ同士の通信品質を決めるためです。IP は「相手のコンピュータへ届ける」役割ですが、どのアプリに届けるか、順番どおり届いたか、届かなかったら再送するかは別の仕組みが必要です。

TCP と UDP を理解すると、Web、動画通話、ゲーム、DNS で通信方式が違う理由を説明できます。

IP は、宛先 IP アドレスへ向かってパケットを運びます。しかし IP だけでは、次のことを保証しません。

- 相手に必ず届くこと。
- 送った順番どおりに届くこと。
- 同じデータが重複しないこと。
- 相手アプリが受け取れる量に合わせること。

そこで、必要に応じてトランスポート層が通信品質を補います。

TCP は、通信相手との接続を作ってからデータを送るコネクション型のプロトコルです。信頼性を重視し、順序制御、再送制御、フロー制御、輻輳制御を行います。Web、メール、ファイル転送のように、少し遅れても欠けずに届くことが重要な用途で使われます。たとえばファイル転送で 1 ビットでも欠けると、ファイルは壊れます。Web ページでも、HTML の途中が抜けると正しく表示できません。TCP は番号を付けて送り、届かなければ再送し、順番が入れ替われば並べ直します。

ただし、信頼性のために確認や再送の処理が必要です。そのため、少し遅れても完全性が大事な通信に向きます。

UDP は、接続を作らずに送るコネクションレス型のプロトコルです。軽量ですが、到達保証や順序保証は基本的にありません。DNS、音声、動画、リアルタイム通信などで使われます。動画通話で 1 秒前の音声が完璧に届いても、今さら聞こえては困ります。少し欠けても、今の音声や映像が届く方が大事です。DNS のような短い問い合わせでも、UDP の軽さが役に立ちます。

つまり、TCP と UDP の違いは「高級な方と低級な方」ではありません。通信の目的が違います。TCP が通信を始めるときは、3 ウェイハンドシェイクで入口をそろえます。

```text
SYN -> SYN/ACK -> ACK
```

3 ウェイハンドシェイクは、通信を始める前に「こちらから送れる」「相手も受け取れる」「こちらも相手の返事を受け取れる」ことを確認する手順です。

```text
1. クライアント: SYN
   接続したいです。

2. サーバ: SYN/ACK
   いいですよ。こちらからも確認します。

3. クライアント: ACK
   返事を受け取りました。始めましょう。
```

この手順により、TCP はいきなりデータを送りつけるのではなく、通信の入口をそろえてから送信を始めます。

ポート番号は、同じ IP アドレス内でアプリケーションを識別します。

IP アドレスだけでは、1 台のコンピュータのどのアプリに届ければよいか分かりません。1 台のサーバでは、Web サーバ、メールサーバ、SSH などが同時に動くことがあります。ポート番号は、建物の住所に対する部屋番号のようなものです。

代表的なポート番号には、HTTP の 80、HTTPS の 443、SMTP の 25、POP3 の 110、IMAP の 143、DNS の 53、SSH の 22 があります。番号だけを見るのではなく、「その番号の先で、どのアプリケーションプロトコルが待ち受けているか」を考えます。

## 7.6 アプリケーション層のプロトコル

この節を学ぶ理由は、利用者が実際に使うサービスの通信形式を理解するためです。Web、メール、名前解決、時刻同期、ファイル転送は、それぞれ目的に合わせたプロトコルで動きます。

アプリケーション層を学ぶと、ブラウザでページが開く流れ、メールが送受信される流れ、ドメイン名が IP アドレスになる流れが見えてきます。

メールでは、送る役割と読む役割が分かれます。SMTP はメール送信やメールサーバ間転送に使われます。POP3 はメールを端末へ取り出す方式で、IMAP はサーバ上のメールを管理しながら読む方式です。Web では、HTTP が Web の要求と応答を扱い、HTTPS は HTTP を TLS で暗号化します。Cookie は、サーバがブラウザに保存させる小さな情報で、セッション管理などに使われます。

HTTP は基本的にステートレスです。ステートレスとは、サーバが前のリクエストを当然には保持していない、という意味です。たとえば、1 回目のリクエストでログイン画面を表示し、2 回目のリクエストで成績画面を開くとしても、HTTP のリクエスト単体だけを見ると「同じ利用者の続きの操作か」は分かりません。そこで Cookie を使い、ブラウザが次回以降のリクエストに識別用の値を付けて送ります。

典型的には、Cookie に利用者名やパスワードそのものを入れるのではなく、セッション ID を入れます。セッション ID は、サーバ側に保存されたログイン状態を引くための番号のようなものです。流れを単純化するとこうなります。

```text
1. 利用者がログインする
2. サーバがセッション ID を発行する
3. ブラウザが Cookie としてセッション ID を保存する
4. 次のリクエストで Cookie を送る
5. サーバがセッション ID からログイン中の利用者を判断する
```

ここで重要なのは、Cookie が「本人そのもの」ではなく、「本人として扱うための鍵」になり得ることです。セッション ID が盗まれると、攻撃者がその利用者として扱われる危険があります。だから Cookie には属性を付けて守ります。`Secure` は HTTPS 通信のときだけ送る指定、`HttpOnly` は JavaScript から読み取れないようにする指定、`SameSite` は別サイトからのリクエストに Cookie をどの程度付けるかを制御する指定です。これらは魔法の防御ではありませんが、盗難や CSRF の被害を減らすための重要な部品です。

Cookie は便利ですが、状態を持ち込むことで設計が難しくなります。共有端末でログアウトし忘れると、次の利用者にログイン状態が残るかもしれません。共有キャッシュが利用者ごとの応答を保存してしまうと、別の人の情報を返す事故につながります。Web アプリでは、Cookie、キャッシュ、認証、認可を別々の仕組みとして理解し、それぞれがどこを守っているかを設計します。

HTTP は、メソッドとステータスコードで会話します。メソッドは「何をしたいか」です。GET は資源を取得したい、POST はデータを送って処理してほしい、PUT は指定した資源を置き換えたい、DELETE は削除したい、という意味で使われます。ステータスコードは、サーバから見た結果です。`200` は成功、`301` や `302` は別の場所への転送、`400` は要求の形が悪い、`401` は認証が必要、`403` は権限がない、`404` は見つからない、`500` はサーバ側のエラーです。数字は単なる番号ではなく、先頭の桁で大まかな種類を表します。`4xx` は利用者側の要求に問題があることが多く、`5xx` はサーバ側で処理できなかったことを示します。

API 設計では、この意味をそろえることが重要です。存在しないデータに対して `500` を返すと、利用者側は「サーバが壊れた」と誤解します。本当は見つからないなら `404`、ログインしていないなら `401`、ログイン済みだが権限がないなら `403` のように、状態を正しく返すことで、クライアント側も適切に処理できます。ネットワークの知識は、通信できるかどうかだけでなく、失敗をどう表現するかにも関わります。

HTTP キャッシュも、Web の性能を大きく左右します。キャッシュとは、一度取得したデータを近くに保存し、次回すぐ使えるようにすることです。ブラウザ、プロキシ、CDN は、画像、CSS、JavaScript、API 応答などをキャッシュできます。CDN は Content Delivery Network の略で、利用者に近い場所からコンテンツを配る仕組みです。遠いサーバまで毎回取りに行かないため、表示が速くなり、元のサーバの負荷も下がります。

ただし、キャッシュは古い情報を見せる危険も持ちます。そこで HTTP では、`Cache-Control`、`ETag`、`Last-Modified` のようなヘッダで、どれくらい保存してよいか、再確認が必要かを伝えます。ヘッダとは、本文とは別に付く制御情報です。たとえば `Cache-Control: max-age=60` なら、60 秒間は新しく取りに行かず保存済みの応答を使ってよい、という意味になります。

`ETag` は、応答内容につける識別子のようなものです。ブラウザは次回アクセスするとき、「自分が持っている ETag はこれです。変わっていますか」とサーバに聞けます。変わっていなければ、サーバは本文を送り直さず `304 Not Modified` を返します。`304` は「変更されていない」という意味です。本文を送らないため通信量を減らせます。

キャッシュ設計では、何を長く保存してよいかを分けます。ロゴ画像やバージョン付きの JavaScript は長く保存しやすいです。一方、成績、残高、在庫のように利用者ごとに違い、最新性が重要な情報は慎重に扱います。キャッシュは速くする道具ですが、認可や個人情報と組み合わさると危険にもなります。別の利用者の情報をキャッシュから返す事故を防ぐため、共有キャッシュに保存してよい応答か、利用者ごとの応答かを明確にします。

TLS は、HTTP の中身を暗号化するだけの箱ではありません。通信相手の確認、暗号化に使う鍵の合意、改ざん検出をまとめて行います。HTTPS で Web サイトへ接続するとき、ブラウザはまずサーバから証明書を受け取ります。証明書には、対象のドメイン名、公開鍵、有効期限、発行者などが含まれます。

公開鍵は、相手に公開してよい鍵です。秘密鍵は、サーバ側だけが持つ鍵です。公開鍵で確認できる情報があっても、対応する秘密鍵を本当に持っている相手でなければ、正しい手順を完了できません。これにより、ブラウザは「このサーバは証明書に対応する秘密鍵を持っている」と確認できます。

ただし、証明書を誰でも勝手に作れるなら意味がありません。そこで CA、Certificate Authority、認証局が出てきます。CA は、証明書の発行者です。ブラウザや OS は、信頼する CA の情報をあらかじめ持っています。サーバ証明書が信頼された CA から発行され、途中の中間証明書も正しくつながり、ドメイン名と有効期限が合っていれば、ブラウザはその証明書を信頼できます。このつながりを証明書チェーンといいます。

TLS では、最終的に大量のデータを共通鍵暗号でやり取りします。共通鍵暗号は、暗号化と復号に同じ鍵を使う方式です。公開鍵暗号だけで全データを送ればよいと思うかもしれませんが、公開鍵暗号は計算が重いため、大量データには向きません。そこで、接続の最初に公開鍵暗号や鍵交換の仕組みで安全に共通鍵を共有し、その後の HTTP データは共通鍵で高速に暗号化します。

流れを単純化すると、次のようになります。

```text
1. ブラウザが TLS で接続したいと伝える
2. サーバが証明書を送る
3. ブラウザが証明書のドメイン名、有効期限、CA の署名を確認する
4. ブラウザとサーバが通信に使う共通鍵を合意する
5. その共通鍵で HTTP の要求と応答を暗号化する
```

ここで大事なのは、HTTPS が「Web サイト全体が信頼できる」と保証するわけではないことです。TLS が主に保証するのは、接続先の確認、通信経路上の盗聴対策、改ざん検出です。サイト運営者が悪意を持っている場合や、ログイン後のアプリケーションに脆弱性がある場合は、TLS だけでは防げません。だから、HTTPS は必要条件ですが、十分条件ではありません。

名前や設定を扱うプロトコルも重要です。DNS はドメイン名を IP アドレスに対応させます。DHCP は IP アドレスなどを端末へ自動配布します。

DNS は、名前を IP アドレスへ変換する仕組みです。人間は `example.com` のような名前を扱いますが、IP が届けるために必要なのは IP アドレスです。ブラウザで URL を入力したとき、最初から HTTP 通信が始まるわけではありません。まず DNS で相手の住所を調べます。

```text
人間が扱う名前: example.com
通信で必要な住所: 93.184.216.34 のような IP アドレス
```

DNS には、再帰問い合わせと権威サーバの考え方があります。利用者の端末は、多くの場合、まずキャッシュ DNS サーバへ「この名前の IP アドレスを教えて」と聞きます。キャッシュ DNS サーバは、必要ならルート、TLD、権威 DNS サーバへ順にたどって調べます。権威 DNS サーバは、そのドメインについて正しい情報を持つサーバです。たとえば学校の公式ドメインなら、そのドメインのレコードを管理しているサーバが権威を持ちます。

TTL は Time To Live で、DNS の答えをどれくらいキャッシュしてよいかを表します。TTL が 3600 秒なら、1 時間は同じ答えを再利用できます。ここで `3600 秒 = 60 分` です。なぜなら 1 分は 60 秒なので、`3600 ÷ 60 = 60` と割れば分に直せるからです。TTL が長いと問い合わせが減って速くなりますが、IP アドレスを変更したときに古い答えが残りやすくなります。TTL が短いと変更は反映されやすい一方、DNS 問い合わせが増えます。DNS 運用では、速さと変更のしやすさのバランスを取ります。

DHCP は、端末に IP アドレスなどを自動で配る仕組みです。家庭や学校で Wi-Fi につなぐだけで通信できるのは、端末が DHCP から IP アドレス、デフォルトゲートウェイ、DNS サーバなどを受け取っているからです。

そのほか、FTP や SFTP はファイル転送、NTP は時刻同期、SNMP はネットワーク管理、LDAP はディレクトリサービス参照に使われます。ディレクトリサービスとは、利用者や端末などの情報をまとめて検索・管理する仕組みです。

NTP は Network Time Protocol の略で、コンピュータの時刻をそろえるために使います。時刻同期は地味ですが、運用では非常に重要です。複数サーバのログを調べるとき、サーバ A の時計が 5 分進み、サーバ B の時計が 3 分遅れていると、どの出来事が先に起きたのか分からなくなります。認証トークンや証明書にも有効期限があるため、時計が大きくずれると、正しい利用者なのに拒否されたり、期限切れを見逃したりします。

分散システムでは、「時刻が完全に一致している」と仮定しすぎるのも危険です。ネットワーク遅延があり、各機器の時計も少しずつずれます。だからログには UTC など基準の時刻を使い、タイムゾーンを明確にし、トレース ID やリクエスト ID で一連の処理を結びつけます。UTC は世界共通の基準時刻として使われる時刻です。日本時間は通常 UTC より 9 時間進んでいるので、`2026-07-04 12:00 JST` は `2026-07-04 03:00 UTC` に対応します。`12 - 9 = 3` と 9 時間を引くのは、日本時間から UTC へ戻すためです。

VoIP は、音声を IP ネットワークで送る技術です。SIP は呼制御、RTP は音声データ転送に使われます。

呼制御とは、電話でいう「相手を呼び出す」「応答する」「通話を終了する」といった操作を管理することです。SIP は、誰と誰が通話するか、相手が応答したか、どの通信条件を使うかを調整します。一方、RTP は実際の音声データを小さな単位で連続して運びます。つまり、SIP は通話の段取り、RTP は通話中の音声の流れ、と分けて考えると分かりやすいです。

音声通信では、完全性よりリアルタイム性が強く求められます。古い音声パケットが後から完全に届いても、会話では役に立ちません。そのため、VoIP では遅延、ジッタ、パケット損失が品質に直結します。ジッタが大きいと、音声が途切れたり不自然に伸び縮みしたりします。受信側ではジッタバッファを使い、少しだけためてから再生することで揺らぎを吸収します。ただし、ためすぎると今度は遅延が増え、会話のテンポが悪くなります。

VoIP は NAT やファイアウォールとも相性問題を起こしやすいです。SIP で「このアドレスとポートへ音声を送って」と伝えても、その情報がプライベートアドレスのままだと、外部から戻ってくる RTP が正しい端末へ届かないことがあります。そこで、SBC、Session Border Controller のような装置で通信を仲介したり、NAT 越えの仕組みを使ったりします。音声が片方向だけ聞こえない、呼び出しはできるが通話が始まらない、といった障害は、SIP の制御通信と RTP の音声通信を分けて調べる必要があります。

## 7.7 伝送技術

この節を学ぶ理由は、通信中のデータは壊れたり、欠けたり、順番が乱れたりすることがあるからです。特に無線や長距離通信では、ノイズや混雑の影響を受けます。

誤り制御や再送制御を学ぶと、なぜチェック用の値を付けるのか、なぜ届かなかったデータを送り直すのか、通信品質をどう保つのかが分かります。

誤り制御は、届いたデータが壊れていないかを確かめるための仕組みです。パリティチェックは 1 ビットの誤り検出に使われます。CRC は多項式を使った強力な誤り検出です。ハミング符号は、誤りを検出するだけでなく訂正もできる符号です。

再送制御は、壊れたデータや届かなかったデータを送り直すための仕組みです。Stop-and-Wait は 1 つ送って確認を待つ方式で、単純ですが遅くなります。Go-Back-N は複数送れますが、誤りがあった位置以降をまとめて再送します。Selective Repeat は、誤ったものだけを選んで再送します。

フロー制御は、受信側が処理できる量に合わせて送信量を調整します。輻輳制御は、ネットワーク全体の混雑を避けるために送信量を調整します。

TCP のフロー制御では、ウィンドウという考え方を使います。受信側は、「いま自分が受け取れる量」を送信側に知らせます。送信側は、その範囲を超えて送りすぎないようにします。もし受信側のアプリが処理に時間をかけていてバッファが空かないなら、受信可能な量は小さくなります。送信側がそれを無視して大量に送ると、受信側であふれてしまいます。

ウィンドウサイズが 64KB、往復時間 RTT が 100ms だとします。RTT は Round Trip Time、送ってから確認応答が返るまでの往復時間です。単純化すると、1 RTT の間に 64KB まで送れるので、最大スループットの目安は次のように考えられます。

```text
スループット ≒ ウィンドウサイズ / RTT
```

RTT の 100ms は 0.1 秒です。したがって、

```text
スループット ≒ 64KB / 0.1秒
             = 640KB/秒
```

`/ 0.1` は 10 倍することと同じです。0.1 秒ごとに 64KB 送れるなら、1 秒ではその 10 回分を送れるからです。このように、回線速度が速くても、ウィンドウサイズや遅延が小さくなければ十分に使い切れないことがあります。

輻輳制御は、ネットワーク全体を詰まらせないための制御です。受信側が受け取れるかだけでなく、途中のルータや回線が混雑していないかを考えます。TCP では、最初から全速力で送るのではなく、スロースタートのように少しずつ送信量を増やし、損失や遅延の兆候があれば送信量を下げます。これは遠慮しているのではなく、全員が一斉に送りすぎてネットワーク全体が崩れるのを防ぐ仕組みです。

QoS は Quality of Service の略で、通信品質を用途に合わせて制御する考え方です。通信品質というと回線速度だけを考えがちですが、実際には帯域、遅延、ジッタ、パケット損失を分けて見ます。帯域は一定時間にどれだけ多くのデータを送れるかです。遅延は相手へ届くまでの時間です。ジッタは遅延の揺らぎです。パケット損失は途中でデータが失われることです。

用途によって重視するものは違います。動画ファイルのダウンロードでは、多少遅延があっても最終的に全部届くことが重要です。一方、音声通話では、少し前の音声があとから完全に届いても意味が薄く、遅延とジッタが小さいことが重要です。オンラインゲームや遠隔操作でも、遅延の大きさが体感品質に直結します。

QoS では、重要な通信を分類し、優先制御や帯域制御を行うことがあります。たとえば学校のネットワークで、オンライン授業の音声・映像を、巨大ファイルのダウンロードより優先する設計です。ただし、優先制御は魔法ではありません。回線容量そのものが足りなければ、優先されない通信は遅くなります。QoS は不足する資源を増やす技術ではなく、混雑時にどの通信を先に通すかを決める設計です。

QoS を設計するときは、「どの通信が重要か」を技術だけで決められません。授業、医療、決済、監視、バックアップでは優先順位が違います。ネットワーク設計では、アプリケーションの重要度、利用時間帯、許容遅延、許容損失を明確にしてから制御します。

同期制御は、送信側と受信側で「どこからどこまでが 1 つのデータか」「どのタイミングで読めばよいか」をそろえる考え方です。通信では、送る側がビット列を流しても、受け取る側が区切りを誤ると意味が壊れます。たとえば `01100001` を文字 `a` と読むには、8 ビットのまとまりを正しく見つける必要があります。1 ビットずれて読むと、まったく別の値になります。

非同期式の通信では、文字やデータ単位ごとにスタートビットやストップビットを付けて、受信側が区切りを取り直せるようにします。単純で扱いやすい一方、制御用のビットが増えるため効率は下がります。同期式の通信では、送信側と受信側がクロックやフレームのタイミングを合わせ、連続したデータを効率よく送ります。高速通信では効率が重要なので、フレーム同期やクロック回復の仕組みが必要になります。

ここでいう同期は、「同時に処理する」という日常語より少し正確です。通信の文脈では、送信側と受信側のタイミング、区切り、順序の認識を合わせることです。これが崩れると、エラー訂正や再送以前に、何を受け取ったのか分からなくなります。

## 7.8 交換方式

この節を学ぶ理由は、通信路をどう共有するかで効率や遅延が変わるからです。電話のように回線を占有する方式と、インターネットのようにパケットを分けて共有する方式では、向いている用途が違います。

交換方式を学ぶと、通信の混雑、遅延、帯域共有、古い WAN 技術の考え方を理解できます。

回線交換では、通信中は専用回線を確保します。電話のように、話している間は通信路を占有するイメージです。遅延は安定しやすい一方、実際にデータを送っていない時間も回線を占有します。

パケット交換では、データを小さなパケットに分けて送ります。複数の通信が同じ回線を効率的に共有できますが、混雑で遅延したり、順序が入れ替わったりすることがあります。インターネットは、このパケット交換の考え方を土台にしています。

ATM は固定長セルを使う交換方式です。フレームリレーは、誤り制御を簡略化した高速な WAN 技術として使われました。

MTU は、1 回で送れる最大転送単位です。MTU より大きい IP パケットは分割が必要になることがあります。

MTU を理解すると、「小さな通信は通るのに、大きなファイル転送だけ失敗する」ような現象を説明できます。たとえば Ethernet の一般的な MTU は 1500 バイトです。ここに VPN やトンネリングを重ねると、元のパケットに追加のヘッダが付きます。ヘッダとは、宛先や制御情報を書いた荷札のような部分です。荷札が増えると、同じ 1500 バイトの枠に入る実データは小さくなります。

経路の途中に、より小さい MTU の区間がある場合、送信側はその大きさに合わせる必要があります。この発見に使う考え方が Path MTU Discovery です。送信側は大きすぎるパケットを送ったとき、途中の機器から「この大きさでは通せない」という通知を受け取り、サイズを下げます。IPv4 では途中のルータが分割する場合がありますが、IPv6 では途中のルータは分割せず、送信元が適切な大きさに調整します。そのため、ICMPv6 の通知が届かないと、接続はできているように見えるのに、大きなデータだけ詰まることがあります。

性能設計では、MTU を大きくすれば常によいわけではありません。大きいパケットはヘッダの割合を減らせますが、機器や経路が対応していないと破棄や再送が増えます。小さすぎると、同じデータ量を運ぶためにパケット数が増え、処理負荷が高くなります。MTU は、回線、機器、VPN、クラウド接続、監視のすべてを含めて合わせる値です。

## 7.9 無線 LAN

この節を学ぶ理由は、無線通信が有線とは違う制約を持つからです。電波は目に見えず、壁や距離や他の機器の影響を受けます。同じ空間を複数端末で共有するため、衝突を避ける工夫も必要です。

無線 LAN を学ぶと、Wi-Fi が遅い、つながらない、場所によって不安定になる理由を、電波・チャネル・暗号・アクセス制御から考えられるようになります。

無線 LAN は IEEE 802.11 系の規格です。

無線 LAN では、有線 LAN よりも次の制約を強く意識します。

- 電波を共有するため、有線より衝突や干渉を考える必要がある。
- 距離、障害物、チャネル設計が性能に影響する。
- セキュリティ設定が重要。

IEEE 802.11 系には、802.11a/b/g/n/ac/ax などの規格があります。周波数帯は 2.4GHz、5GHz、6GHz などです。2.4GHz 帯は届きやすいですが干渉しやすいです。5GHz 帯は比較的高速で干渉が少ないですが、障害物に弱めです。

無線 LAN のアクセス制御では CSMA/CA を使います。また、RTS/CTS によって隠れ端末問題を緩和できます。隠れ端末問題とは、アクセスポイントからは両方見えるが端末同士は互いの電波を聞き取れず、同時送信して衝突してしまう問題です。

チャネル割り当ても重要です。チャネルは、無線で使う周波数の通り道のようなものです。近くのアクセスポイントが同じ、または重なったチャネルを使うと、互いに干渉して速度が落ちます。2.4GHz 帯では重ならないチャネルが少ないため、設計が難しくなります。5GHz 帯や 6GHz 帯は使えるチャネルが多く、高速化しやすい一方、障害物や距離の影響を受けやすい場合があります。

無線 LAN の性能問題では、「規格上の最大速度」だけを見てはいけません。実際の速度は、電波強度、端末数、チャネル干渉、壁や床、暗号処理、アクセスポイントの配置、バックボーン回線の速度で変わります。教室で全員が同時に動画教材を見るなら、アクセスポイント 1 台の規格値より、同時接続数とチャネル設計を見る必要があります。

## 実務で使える理解

- 接続装置は、見るアドレスで層を判断する。MAC なら 2 層、IP なら 3 層、ポートなら 4 層。
- IP は到達保証しない。保証は TCP。
- サブネットは、ホスト部ビット数から利用可能数を出す。
- TCP は信頼性、UDP は軽量性。
- プロトコルは名前だけでなく、「どの層で、何を解決する約束か」で理解する。
- Cookie は HTTP に状態を持ち込む仕組みであり、セッション管理、属性、キャッシュ、認可と分けて考える。
- TLS は、証明書による相手確認、共通鍵の合意、通信の暗号化と改ざん検出を分けて理解する。
- QoS は、帯域、遅延、ジッタ、損失のうち何を優先するかを用途から決める。
- VoIP は、SIP の呼制御と RTP の音声転送を分け、遅延、ジッタ、NAT 越えを含めて設計する。
- 無線 LAN は、有線の衝突検出ではなく衝突回避。

## 自分の言葉で説明する

- OSI 7 階層が、通信機能をどのように分けて考えるモデルか説明できる。
- TCP/IP モデルが、インターネットの通信をどの責任に分けているか説明できる。
- リピータ、スイッチ、ルータ、ゲートウェイの違いを説明できる。
- VLAN の目的を説明できる。
- IPv4 のホスト数を計算できる。
- NAT と NAPT の違いを説明できる。
- TCP と UDP の違いを説明できる。
- ポート番号が、同じ IP アドレス内のアプリケーション識別に必要な理由を説明できる。
- DNS、DHCP、SMTP、POP3、IMAP、HTTP、HTTPS の役割を説明できる。
- HTTP がステートレスであることと、Cookie によるセッション管理の関係を説明できる。
- `Secure`、`HttpOnly`、`SameSite` が Cookie のどの危険を減らすか説明できる。
- TLS の証明書チェーン、CA、共通鍵暗号の役割を説明できる。
- 帯域、遅延、ジッタ、パケット損失の違いを用途例で説明できる。
- VoIP で SIP と RTP の役割が違うことを説明できる。
- CSMA/CD と CSMA/CA を区別できる。

## 深く身につけるための補講

ネットワークを理解するコツは、「データが旅をする」と考えることです。あなたがブラウザで Web ページを開くと、画面の裏側では多くの役割分担が動いています。

例として、`https://example.com` を開く流れを見ます。

1. ブラウザは `example.com` の IP アドレスを知りたい。
2. DNS に問い合わせ、IP アドレスを得る。
3. その IP アドレスへ TCP 接続を作る。
4. HTTPS なので TLS で暗号化された通信路を作る。
5. HTTP リクエストを送る。
6. Web サーバが HTML などを返す。
7. ブラウザが画面に表示する。

ここで重要なのは、DNS、TCP、TLS、HTTP がそれぞれ違う問題を解決していることです。

DNS は、`example.com` のような人間に読みやすい名前を、通信に使う IP アドレスへ変換します。名前と住所を対応づける仕組みです。TCP は、データが途中で分割されても、順番どおり、欠けにくく届くように管理します。TLS は、その TCP の上で、盗聴や改ざんを防ぐために暗号化と相手確認を行います。HTTP は、Web ブラウザと Web サーバが「何をください」「これを返します」とやり取りするための要求と応答の形式です。

## 層で考えるとトラブルシュートできる

「Web ページが開かない」と言っても、原因は 1 つではありません。

物理層では、ケーブルが抜けていないか、Wi-Fi の電波が届いているか、リンクランプが点いているかを見ます。ここが壊れていれば、上位の設定をいくら直しても通信できません。データリンク層では、同じ LAN の中で相手に届くか、VLAN の分離や MAC アドレス学習がおかしくないかを見ます。

ネットワーク層では、IP アドレス、サブネットマスク、デフォルトゲートウェイ、ルーティングを確認します。同じ LAN の外へ出るには、次に渡すルータが必要です。トランスポート層では、TCP 接続できるか、ポートが開いているか、ファイアウォールで止められていないかを見ます。アプリケーション層では、DNS が名前解決できるか、HTTP の応答が返るか、認証やアプリ設定で失敗していないかを見ます。

層に分けると、「どこまでは届いていて、どこから失敗しているか」を切り分けられます。

## TCP と UDP を用途で理解する

TCP は、確実に届くことを重視します。届かなければ再送し、順番が入れ替われば並べ直します。その代わり、処理は重くなります。

UDP は、軽さと速さを重視します。届かなかったデータを基本的には追いかけません。その代わり、リアルタイム性が必要な通信に向きます。

用途で見ると、ファイル転送は 1 ビットでも欠けると困るので TCP が向きます。動画通話は、少し欠けても遅れて届くより今の映像が大事なので UDP が向きます。DNS は短い問い合わせを素早く送るため、UDP がよく使われます。

## ありがちな誤解

- IP アドレスだけでは、同じ PC 内のどのアプリに届けるか分からない。ポート番号が必要。
- IP は配送先を決めるが、確実な到着までは保証しない。
- DNS はインターネットそのものではなく、名前解決の仕組み。
- HTTPS は「安全なサイト」という意味ではなく、「通信が TLS で保護されている」という意味。
- TLS があっても、悪意あるサイト運営者やアプリケーションの脆弱性まで消えるわけではない。
- Cookie はログイン状態を扱えるが、認可の代わりではない。サーバ側で対象データへの権限確認が必要。
- VoIP は UDP で送れば終わりではない。遅延、ジッタ、NAT、ファイアウォール、QoS が品質に影響する。
- QoS は回線容量を増やす技術ではなく、混雑時の優先順位を設計する考え方。
- Wi-Fi がつながっていても、インターネットへ出られるとは限らない。

## 手を動かす課題

1. 自宅や学校のネットワークを、端末、Wi-Fi ルータ、インターネット、DNS の関係で説明してください。
2. `192.168.10.0/26` のホスト部ビット数と利用可能ホスト数を途中式つきで計算してください。
3. 「DNS は通るが HTTP が通らない」とき、どの層を疑うか説明してください。
4. TCP が向く通信と UDP が向く通信を、それぞれ 3 つ挙げて理由を説明してください。
5. HTTPS 接続で、DNS、TCP、TLS、HTTP がそれぞれ何を担当するか順に説明してください。
6. オンライン授業、バックアップ、ゲーム、動画配信で、帯域、遅延、ジッタ、損失のどれを重視するか比較してください。
7. Cookie にセッション ID を入れる設計で、`Secure`、`HttpOnly`、`SameSite` がないとどんな危険が増えるか説明してください。
8. VoIP で「呼び出しは鳴るが相手の声が聞こえない」とき、SIP と RTP を分けて原因候補を説明してください。
