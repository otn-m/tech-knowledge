# 第9章 システム開発技術

## この章の地図

システム開発技術は、システムをどう作るかを扱う章です。単にプログラムを書く話ではありません。利用者の困りごとを理解し、開発できる要件へ落とし、構造を設計し、実装し、テストし、レビューし、長く変更できる形にする活動です。

この章の中心にある問いは、「正しいものを、正しく作るにはどうすればよいか」です。正しいものを作るには、利用者や業務に本当に必要なものを見極める必要があります。正しく作るには、バグが少なく、保守しやすく、安全に動くように作る必要があります。

ウォータフォール、アジャイル、プロトタイピングは、開発の進め方の違いです。DFD や UML は、頭の中の理解を図として共有する道具です。結合度や凝集度は、変更に強い部品分割かどうかを見る物差しです。テストとレビューは、品質を最後に祈るのではなく、途中から証拠を積み上げる活動です。

## なぜこの章を学ぶのか

初心者は「コードを書ければシステムは作れる」と思いがちです。しかし、要求が曖昧なまま作ると、完成しても使われないものになります。設計が悪いと、少し変更するだけで壊れます。テストが弱いと、本番で利用者がバグを見つけることになります。

たとえば学校の欠席連絡アプリを作るとします。「スマホから欠席連絡できるようにしたい」という希望だけでは、開発できません。保護者が入力するのか、生徒本人が入力するのか。担任、保健室、教務部の誰に通知するのか。締切時刻はあるのか。兄弟のいる家庭はどうするのか。誤送信を取り消せるのか。個人情報を誰が見られるのか。こうしたことを決めて初めて設計と実装に進めます。

この章を学ぶと、システムを「作る前」「作っている途中」「作った後」に分けて、品質を作り込む考え方が身につきます。

## 9.1 開発プロセスは状況に合わせて選ぶ

開発プロセスは、チームでどう進むかの設計です。文化祭の準備でも、最初に全部決めてから作るのか、試作品を見せながら直すのかで進め方が変わります。システム開発でも、要求が安定しているか、失敗したときの影響が大きいか、利用者と頻繁に相談できるかによって、適した進め方が変わります。

ウォータフォールモデルは、要件定義、設計、実装、テストを順番に進める考え方です。要求が比較的安定していて、契約や文書化が重要な大規模開発に向きます。たとえば、法律や業務規則が明確で、途中変更のコストが大きいシステムでは、最初に合意を固める意味があります。一方で、後から要求が大きく変わると手戻りのコストが高くなります。

プロトタイピングモデルは、試作品を作り、利用者に確認してもらいながら要求を明確にする方法です。利用者自身も何がほしいか言葉にしきれていない場合に役立ちます。ただし、試作品をそのまま本番に使うと、性能、セキュリティ、保守性が足りないことがあります。試作品は「学ぶためのもの」なのか「育てて本番にするもの」なのかを区別します。

スパイラルモデルは、開発を繰り返し、各サイクルでリスク分析を行う方法です。技術的に難しい、失敗時の影響が大きい、未知の要素が多い開発に向きます。大きな失敗を最後に発見するのではなく、リスクの高い部分から確かめます。

アジャイル開発は、短い反復で動くソフトウェアを作り、利用者や顧客からの反応を見ながら改善していく考え方です。要求が変わりやすいサービスや、早く価値を届けたい開発に向きます。ただし、計画しない開発ではありません。短い周期で計画、実装、確認、改善を繰り返します。

スクラムはアジャイル開発の代表的な枠組みです。プロダクトバックログには、作るべき機能や改善項目を優先順位つきで置きます。スプリントは、短い開発期間です。スプリントレビューではできたものを確認し、レトロスペクティブでは進め方を振り返ります。プロダクトオーナは価値と優先順位に責任を持ち、スクラムマスタはチームがうまく進められるよう支援し、開発者は実際に成果物を作ります。

## 要件定義は利用者の言葉を検証可能な約束に変える

システム開発で最初に難しいのは、利用者が言ったことをそのまま作ることではありません。利用者の困りごとを、開発者が設計・実装・テストできる形へ変換することです。

利用者の言葉は、多くの場合あいまいです。「使いやすくしてほしい」「早く表示してほしい」「安全にしてほしい」「管理しやすくしてほしい」と言われても、そのままでは完成条件が分かりません。高校の欠席連絡アプリで「早く連絡できるようにしたい」と言われたら、何秒以内に画面が開けばよいのか、朝の混雑時に何人が同時に使うのか、保護者が途中で入力を間違えたら修正できるのか、担任にはどのタイミングで通知するのかを確認する必要があります。

要求と要件は似ていますが、分けて考えると理解しやすくなります。要求は、利用者や関係者が望んでいることです。要件は、それをシステムが満たすべき条件として整理したものです。要求が「朝の電話を減らしたい」なら、要件は「保護者は当日 8:30 までに欠席理由を登録できる」「担任は自分のクラスの当日欠席一覧を確認できる」「登録後に担任へ通知する」のように、確認できる形へ落とします。

機能要件は、システムが何をするかです。ログインする、欠席連絡を登録する、一覧を表示する、通知を送る、CSV を出力する、などが該当します。非機能要件は、システムがどの品質で動くかです。応答時間、同時利用者数、稼働率、セキュリティ、操作性、バックアップ、監査ログ、保守性、法令対応などが入ります。

非機能要件は、初心者ほど見落としがちです。しかし実務では非常に重要です。機能としては欠席登録できても、朝 8 時台にアクセスが集中して画面が開かないなら使えません。個人情報を扱うのにアクセスログが残らなければ、問題が起きたとき調査できません。スマホで使う前提なのに PC 画面だけで設計すると、保護者は入力しづらくなります。

良い要件には、受入条件があります。受入条件とは、「これを満たしていれば完成と判断する」という確認基準です。たとえば「保護者は欠席連絡を登録できる」だけでは弱いです。「ログイン済み保護者は、当日または翌日の欠席・遅刻・早退を選び、理由を 200 文字以内で入力し、登録後に確認画面で内容を見られる」のように書くと、設計とテストにつながります。

要件は、あとから追跡できる必要があります。これをトレーサビリティといいます。あるテストケースがどの要件を確認しているのか、ある設計項目がどの要求から来たのかをたどれる状態です。トレーサビリティがないと、仕様変更が来たときに、どの画面、DB、API、テストを直すべきか分からなくなります。

要件定義は、変更を禁止するための作業ではありません。変更が起きたときに、影響範囲、費用、納期、リスクを判断できるようにする作業です。アジャイル開発でも要件は不要になりません。むしろ短い周期で要件を見直すため、何が決まっていて、何が仮説で、何を検証するのかを明確にする力が必要です。

品質特性も、要件として扱います。品質特性とは、システムが「どのような良さ」を持つべきかを表す観点です。機能として正しいだけでは足りません。朝の欠席連絡アプリなら、8 時台の混雑でも遅くならない性能、個人情報を守るセキュリティ、保護者がスマホで迷わず使える使用性、障害時にも連絡手段を失わない信頼性、後から通知方法を変えられる保守性が必要になります。

品質特性は、しばしばトレードオフになります。トレードオフとは、一方を強めると別の何かが難しくなる関係です。セキュリティを高めるために毎回多要素認証を求めると、安全性は上がりますが、朝の忙しい時間の使いやすさは下がるかもしれません。性能を上げるためにキャッシュを使うと速くなりますが、古い情報を見せないための整合性管理が必要になります。つまり非機能要件は「できれば速く、安全で、使いやすく」ではなく、どの状況で、どの水準を、どの理由で求めるのかを決める設計判断です。

品質特性は、測れる文にすると設計とテストにつながります。「速いこと」ではなく「平日 7:30 から 8:30 に同時 500 人が利用しても、欠席登録画面の 95% が 2 秒以内に応答する」と書けば、性能テストを設計できます。「安全であること」ではなく「保護者は自分の子どもの欠席連絡だけ閲覧でき、別家庭の情報へアクセスした場合は拒否され、監査ログに残る」と書けば、権限テストを作れます。よい要件は、開発者だけでなく、利用者、運用担当者、監査担当者が同じ意味で確認できる文です。

## 9.2 組込みソフトウェアは現実世界とつながる

ソフトウェアは画面の中だけで動くものではありません。自動車、家電、医療機器、工場設備の中にもプログラムがあります。スマホアプリの表示が少し遅いのと、車のブレーキ制御が遅いのでは、意味がまったく違います。

組込みソフトウェアでは、メモリや CPU が限られることがあります。センサやアクチュエータと連携します。アクチュエータとは、モーターやバルブのように、信号を物理的な動きへ変える装置です。決められた時間内に応答しなければ危険につながることもあります。これをリアルタイム性といいます。

リアルタイム性は、単に速いことではありません。期限を守ることです。平均して速くても、たまに大きく遅れるなら、ブレーキ制御や医療機器では問題になります。

共通フレームや CMMI、ISO/IEC 15504 のようなプロセス評価は、開発を個人の勘や頑張りだけに依存させないために使います。発注者と受注者が同じ言葉で作業範囲を話せなければ、「そこまで含まれると思っていた」「それは契約外だと思っていた」という食い違いが起きます。成熟した組織では、開発プロセスが定義され、測定され、改善されます。

共通フレームは、システムやソフトウェアを企画し、開発し、運用し、保守する活動を、関係者が同じ言葉で整理するための枠組みです。ここで大切なのは、細かい文書名をそろえることだけではありません。誰が要求を出し、誰が要件として確認し、誰が設計し、誰が受け入れ、運用後の変更をどう扱うのかを、作業と責任として見えるようにすることです。

たとえば、欠席連絡アプリを外部会社に依頼するとします。学校側は「保護者が連絡できるアプリがほしい」と言い、開発会社は「入力画面と一覧画面を作ればよい」と考えるかもしれません。しかし実際には、利用者登録、本人確認、権限、通知、障害時の連絡、データ移行、操作説明、保守窓口、契約終了時のデータ返却まで関係します。共通フレームのような考え方を使うと、こうした活動を漏れなく確認しやすくなります。

プロセス評価は、「この組織は安定して良い開発ができるか」を見るための考え方です。たまたま優秀な人がいて成功したのか、誰が担当しても一定の品質で進められる仕組みがあるのかは違います。CMMI は能力成熟度モデル統合と呼ばれ、組織の開発や管理の成熟度を段階的に見る考え方です。ISO/IEC 15504 は SPICE とも呼ばれ、プロセスがどの程度実行され、管理され、改善されているかを評価する枠組みです。

成熟度という言葉は、「偉いかどうか」ではありません。作業が毎回場当たり的なのか、手順が定義されているのか、実績を測って改善しているのか、組織として学習できているのかを見る物差しです。たとえば、毎回リリース直前に大量のバグが出るなら、単に開発者を増やすより、要件レビュー、設計レビュー、自動テスト、リスク管理、リリース判定のプロセスを改善する方が効果的かもしれません。

ただし、プロセスを整えることは、書類を増やすことと同じではありません。目的のない承認や形式だけのレビューは、開発を遅くするだけです。よいプロセスは、重要な判断を早くし、手戻りを減らし、品質の根拠を残すためにあります。高校のグループ制作でも、役割分担、締切、確認方法があると楽になるように、ソフトウェア開発でも「どう進めるか」を設計することが成果物の品質につながります。

ソフトウェア再利用は、過去に作った部品や知識を使い回し、品質と生産性を上げる考え方です。ただし、コピーして貼り付けることだけが再利用ではありません。ライブラリ、フレームワーク、コンポーネント、テンプレート、設計パターン、API、共通基盤など、再利用にはいろいろな形があります。

ライブラリは、必要な機能を呼び出して使う部品です。たとえば日付計算、暗号化、グラフ描画、HTTP 通信などを自分で全部作らず、信頼できるライブラリを使います。フレームワークは、アプリ全体の骨組みを提供し、開発者がその決められた流れに沿って処理を書きます。ライブラリは「こちらから呼ぶ道具」、フレームワークは「全体の流れを握り、必要なところでこちらのコードを呼ぶ土台」と考えると違いが分かります。

再利用で大切なのは、責任の境界です。便利な部品を使うと開発は速くなりますが、その部品にバグや脆弱性があれば自分のシステムにも影響します。バージョン、ライセンス、保守状況、セキュリティ修正、互換性を確認する必要があります。また、自分たちの業務に合わない共通部品を無理に使うと、かえって複雑になります。高度な再利用は、「同じものを使えばよい」ではなく、「変わりにくい部分を共通化し、変わりやすい部分を差し替えられるようにする」設計です。

API も、再利用される部品の一種です。API はプログラム同士の約束なので、画面よりも一度公開した後の変更が難しいことがあります。たとえば欠席連絡登録 API が `reason` という項目を必須にしているなら、スマホアプリ、管理画面、外部通知システムがその約束に合わせて作られます。後から急に項目名を `absenceReason` に変えると、呼び出している側が壊れます。

そのため、API 仕様では、入力項目、型、必須か任意か、エラー時の形式、認証方式、レート制限、冪等性、バージョンを決めます。冪等性は、同じ要求を何度送っても結果が 1 回送ったときと同じになる性質です。通信では、送信後に返事だけ失われることがあります。利用者が再送したとき、同じ注文や同じ欠席連絡が二重登録されると困ります。要求 ID を付けて同じ ID は 1 回分として扱うと、再送に強くなります。

API のバージョン管理は、変更の影響を小さくするために使います。古い利用者がまだ `v1` を使っている間に、新しい仕様を `v2` として公開すれば、すべての利用者を同時に変更しなくて済みます。ただし、古い版を永遠に残すと保守が重くなります。いつまで使えるか、移行方法は何か、互換性を壊す変更かどうかを明確にする必要があります。API 設計は、プログラムの入口を作る作業であると同時に、将来の変更をどう受け止めるかの設計です。

## 9.3 分析と設計は現実を作れる形に変える

分析は、現実の業務で何が起きているかを分解して見る活動です。設計は、それをどう作ればよいか組み立てる活動です。「便利にしたい」「ミスを減らしたい」という言葉を、そのままプログラムにはできません。データの流れ、処理、状態、ルールへ落とす必要があります。

DFD は Data Flow Diagram、データの流れを表す図です。欠席連絡アプリなら、保護者が欠席理由を入力し、システムが担任へ通知し、欠席履歴を保存します。このとき、誰からデータが来て、どの処理を通り、どこに保存され、誰へ渡るかを見える化します。

DFD では、プロセス、データフロー、データストア、外部実体を使います。プロセスはデータを変換する処理です。データフローはデータの流れです。データストアは保存場所です。外部実体はシステムの外にいる利用者や別システムです。保護者、担任、メール配信サービスなどが該当します。

データディクショナリは、データ項目の定義集です。「欠席日」は日付型である、「理由」は最大何文字である、「学生番号」はどの形式である、といった意味をそろえます。ミニ仕様書は、DFD のプロセスの詳細を書きます。図だけでは分からない条件分岐や計算規則を文章で補います。

データ中心設計では、処理よりもデータ構造を重視します。業務データは長く残るため、安定したデータモデルを作ることが重要です。事象応答分析では、外部や時間から発生する事象に対して、システムがどう応答するかを分析します。

データ中心設計を深く理解するには、「画面は変わるが、事実は残る」と考えると分かりやすくなります。欠席連絡アプリでは、画面デザインや通知方法は変わるかもしれません。しかし、学生、保護者、クラス、欠席日、理由、登録時刻、確認者という事実は長く残ります。データモデルが弱いと、画面を少し変えるだけで過去データの意味が分からなくなったり、同じ情報を複数の場所で矛盾して持ったりします。

データ中心設計では、エンティティ、属性、関係を丁寧に見ます。エンティティは、管理したい対象です。学生、保護者、欠席連絡、教員などが該当します。属性は、その対象が持つ情報です。学生なら学生番号、氏名、所属クラスなどです。関係は、対象同士のつながりです。保護者は学生に紐づき、欠席連絡は学生と登録者に紐づきます。ここを曖昧にすると、「兄弟がいる家庭では保護者をどう表すのか」「担任が変わった後の過去確認者は誰として残すのか」といった問題が後から出ます。

事象応答分析では、システムの外から起きる出来事を起点に考えます。保護者が欠席連絡を登録した、担任が確認した、締切時刻を過ぎた、通知サービスが失敗した、年度が変わった、という出来事に対して、システムが何をするべきかを整理します。画面や機能名から始めると見落とす例外も、事象から考えると見つかりやすくなります。

たとえば「締切時刻を過ぎた」という事象を考えると、登録を禁止するのか、警告して受け付けるのか、電話連絡へ誘導するのか、担任へ別通知するのかを決める必要があります。「通知サービスが失敗した」という事象では、欠席連絡の保存まで取り消すのか、保存は成功として後で通知を再送するのか、利用者にどう表示するのかを考えます。分析とは、きれいな正常系だけを描く作業ではなく、現実に起こる出来事へシステムがどう責任を持つかを決める作業です。

## 9.4 オブジェクト指向は責任を持つ単位で考える

オブジェクト指向を学ぶ理由は、大きなシステムを、現実のものごとに近いまとまりで考えられるようにするためです。商品、注文、利用者、支払い、通知のような単位にデータと操作をまとめると、何がどの責任を持つのかが見えやすくなります。

クラスは、オブジェクトの設計図です。たとえば `学生` クラスなら、氏名、学生番号、学年といった属性と、欠席連絡を確認する、成績を表示する、といった操作を持つかもしれません。インスタンスは、クラスから作られた具体的な実体です。`学生` クラスが設計図なら、「学生番号 S001 の佐藤さん」はインスタンスです。

属性は、オブジェクトが持つ状態です。氏名、点数、注文状態などです。メソッドは、オブジェクトが外部に提供する操作です。点数を登録する、注文を確定する、通知を送る、などです。

カプセル化は、内部のデータを外部から直接触らせず、決められた操作を通じて扱わせる考え方です。点数を外から自由に書き換えられると、-10 点や 200 点が入るかもしれません。`点数を登録する` メソッドの中で 0 から 100 の範囲を確認すれば、不正な状態を防ぎやすくなります。

継承は、既存クラスの性質を引き継いで新しいクラスを作る仕組みです。`利用者` クラスから `学生` と `教員` を派生させると、氏名やログイン情報など共通部分をまとめられます。ただし、継承を使いすぎると階層が複雑になり、変更に弱くなることがあります。

多態性は、同じ操作名でも対象に応じて動作が変わる性質です。`通知する` という操作でも、メール通知、アプリ通知、SMS 通知では内部の処理が違います。呼び出す側は `通知する` と頼めばよく、具体的な送り方は対象のクラスに任せられます。

クラス間の関係も、責任のつながりとして読みます。関連は、つながりがある関係です。集約は全体と部分の関係ですが、部分は独立して存在できます。コンポジションは強い全体部分関係で、全体が消えると部分も消えます。汎化は継承関係です。依存は一時的に利用する関係です。

## 9.5 UMLは何を見える化するかで選ぶ

UML は、設計を図で表す標準記法です。文章だけで複雑な関係や処理順序を説明すると、読み手ごとに解釈がずれることがあります。図にすると、構造、時間の流れ、状態変化、配置のどれを話しているのかがはっきりします。

ユースケース図は、利用者と機能の関係を見える化します。欠席連絡アプリなら、保護者が欠席連絡を登録し、担任が一覧を確認し、管理者が利用者を管理する、といった関係を表します。

クラス図は、クラス、属性、操作、関係を表します。シーケンス図は、時間順のメッセージを表します。ログイン処理で、画面、認証サーバ、データベースがどの順にやり取りするかを見るのに向きます。

アクティビティ図は、処理の流れを表します。状態遷移図は、状態とイベントを表します。申請が「下書き」「提出済み」「承認済み」「差戻し」のように変化する場合に役立ちます。コンポーネント図は部品構成、配置図は物理配置を表します。

UML は、絵を描くことが目的ではありません。関係者の理解をそろえるための言語です。図を描くなら、「この図で何を確認したいのか」を先に決めます。

## 9.6 モジュール設計は変更に強くするためにある

モジュールは、プログラムを分割した部品です。良いモジュール設計では、役割がはっきりし、変更の影響が小さくなります。

結合度は、モジュール間の依存の強さです。低いほど、片方を変えたときに相手へ影響しにくくなります。必要なデータだけを渡すデータ結合は比較的良い形です。データ構造ごと渡すスタンプ結合、相手の処理を制御するフラグを渡す制御結合、外部仕様に依存する外部結合、グローバルデータを共有する共通結合、他モジュール内部を直接参照する内容結合へ進むほど、変更の影響が強くなります。

凝集度は、モジュール内部のまとまりです。高いほど、そのモジュールが何を担当しているかが明確になります。1 つの明確な機能を担当する機能的凝集は良い形です。時間的に同時に行うだけ、種類が似ているだけ、何となく集めただけのモジュールは、変更に弱くなります。

たとえば、認証モジュールはログイン、ログアウト、本人確認を担当します。注文モジュールは注文作成や注文状態更新を担当します。決済モジュールは決済要求や決済結果確認を担当します。通知モジュールはメールやメッセージ送信を担当します。役割が分かれていると、決済方法を追加しても認証処理に影響しにくくなります。

結合度と凝集度は、名前だけではなく、変更が起きたときの痛みとして理解します。たとえば、欠席連絡アプリで通知方法をメールからアプリ通知へ増やすとします。通知処理があちこちの画面や登録処理に直接書かれていると、変更箇所が広がります。これは結合度が高い状態です。一方、通知モジュールに「通知する」という操作を集めておけば、登録処理は通知の内部方式を知らずに済みます。

凝集度が低いモジュールは、「便利そうだから何でも入れた道具箱」のようになります。たとえば `共通処理` という名前のモジュールに、日付変換、メール送信、権限確認、CSV 出力、画面表示補助が混ざっていると、何を変更したときに何が影響を受けるか読みにくくなります。良いモジュールは、名前を見れば責任が分かります。`欠席連絡登録サービス`、`通知サービス`、`権限判定`、`監査ログ記録` のように責任が分かれると、変更理由も分かれます。

インタフェースも重要です。ここでのインタフェースは画面の見た目だけではなく、部品同士の約束です。あるモジュールが別のモジュールへ何を渡し、何を受け取り、どんなエラーを返すかを決めます。約束が曖昧だと、単体では動いていた部品が結合時に壊れます。日付を `2026-07-03` の文字列で渡すのか、日付型で渡すのか、タイムゾーンを含むのか、といった小さな違いが本番障害につながることがあります。

変更に強い設計では、依存の向きも見ます。画面、業務ロジック、データベース、外部通知サービスが互いに直接知りすぎると、1 つの変更が連鎖します。たとえば通知サービスの API が変わっただけで、登録画面、担任画面、管理画面を全部直すなら、依存が広がりすぎています。間に通知モジュールのインタフェースを置き、画面側は「通知する」という約束だけを知るようにすると、外部サービス変更の影響を閉じ込められます。これは情報隠蔽とも呼ばれ、内部の実現方法を外から隠し、約束された操作だけを公開する考え方です。

コード設計は、モジュール設計を実際のソースコードへ落とす段階です。ここでいうコードは、学生番号や商品番号のような識別コードではなく、プログラムのソースコードです。クラス名、関数名、変数名、エラー処理、ログ、コメント、入力チェック、戻り値の形をそろえることで、チームで読めるプログラムにします。

良い命名は、未来の読み手への説明です。`data` や `temp` のような名前だけでは、何のデータか分かりません。`absenceRequest`、`studentId`、`submittedAt` のように役割が分かる名前にすると、処理の意味を追いやすくなります。ただし、名前が長ければ良いわけでもありません。大切なのは、そのプログラムの責任を正確に表すことです。

コメントは、コードを日本語でなぞるために書くものではありません。`i = i + 1` に「i を 1 増やす」と書いても、新しい情報はありません。コメントが役立つのは、「なぜこの制限があるのか」「なぜここで外部 API の再試行を 3 回にしているのか」「なぜ 8:30 ちょうどを許すのか」のように、コードだけでは読み取りにくい判断理由を書く場合です。

例外処理もコード設計です。エラーが起きたときに、利用者へ何を返すのか、ログには何を残すのか、再試行できるのか、処理を取り消すのかを決めます。たとえば通知サービスが失敗したとき、欠席連絡の登録まで取り消すのか、登録は成功として通知だけ再試行するのかで、業務上の意味が変わります。コード設計は見た目の整え方ではなく、障害時の振る舞いまで含む設計です。

## 9.7 テストは不安を減らす技術

テストは、バグがないことを完全に証明するものではありません。重要なリスクについて、期待どおり動く証拠を増やす活動です。

ブラックボックステストは、内部構造を見ず、入力と出力で確認します。仕様から見るテストです。同値分割では、同じように扱われる入力をグループに分け、代表値を試します。境界値分析では、条件の境目を確認します。たとえば 0 以上 100 以下なら、-1、0、1、99、100、101 を確認します。境目には `>` と `>=` のような間違いが出やすいからです。

デシジョンテーブルは、条件の組合せと結果を表で整理します。状態遷移テストは、状態とイベントによる変化を確認します。申請が「下書き」から「提出済み」へ進み、差戻しで「下書き」に戻るような場合に使います。

デシジョンテーブルが役立つのは、条件が複数あり、組合せで結果が変わるときです。たとえば欠席連絡で、「締切前か」「保護者本人か」「対象日が許可範囲内か」という 3 条件があるとします。条件が 3 つで、それぞれ true/false の 2 通りなら、組合せは次の数になります。

```text
組合せ数 = 2^3
        = 8
```

なぜ `2^3` かというと、1 つ目の条件が 2 通り、2 つ目も 2 通り、3 つ目も 2 通りなので、

```text
2 × 2 × 2 = 8
```

になるからです。人間は「だいたい大丈夫」と思っても、8 通りのうち 1 通りだけ抜けることがあります。デシジョンテーブルは、条件の組合せを明示し、許可、拒否、警告、管理者確認などの結果を漏れなく考えるための道具です。

ホワイトボックステストは、内部構造を見て確認します。命令網羅は命令を通ったか、分岐網羅は分岐の真偽を通ったか、条件網羅は条件の真偽を通ったかを見ます。経路網羅は可能な経路を確認しますが、経路数が爆発することがあります。

網羅率は、確認すべき対象のうち、どれだけ確認できたかを割合で表します。

```text
網羅率 = 実際に確認した数 / 確認すべき総数 × 100
```

なぜ割り算するのでしょうか。割合を求める基本は、

```text
部分 / 全体
```

だからです。分岐が 20 個あり、そのうち 18 個をテストで通ったなら、

```text
網羅率 = 18 / 20 × 100
```

まず割り算します。

```text
18 / 20 = 0.9
```

割合をパーセントにするために 100 を掛けます。

```text
0.9 × 100 = 90
```

したがって、

```text
網羅率 = 90%
```

ただし、網羅率 100% ならバグがない、という意味ではありません。確認した観点では通った、という意味です。

テスト設計では、まず何を不安に思っているのかを言葉にします。入力値の境界が不安なのか、状態遷移が不安なのか、権限が不安なのか、外部サービスとの接続が不安なのかで、選ぶテスト技法が変わります。

同値分割は、すべての入力を試せないときに使います。たとえば欠席理由が 1 文字以上 200 文字以内なら、1 文字、100 文字、200 文字は有効な代表です。0 文字や 201 文字は無効な代表です。すべての文字数を試さなくても、同じ扱いになる範囲から代表を選びます。

境界値分析は、条件の境目を重点的に見ます。プログラムでは `8:30 まで` を `8:30 を含む` とするのか、`8:30 より前` とするのかで結果が変わります。`<=` と `<` の 1 文字の違いが、利用者にとっては「登録できるはずなのにできない」という障害になります。だから境界の直前、境界そのもの、直後を見るのです。

状態遷移テストは、画面やデータが状態を持つときに重要です。欠席連絡が「未登録」「登録済み」「担任確認済み」「取消済み」のように変化するなら、どの状態からどの操作が許されるかを確認します。登録済みの連絡を取り消せるのか、担任確認後も修正できるのか、取消済みを再登録できるのか。状態を考えないテストでは、こうした抜けが残ります。

権限テストも忘れてはいけません。保護者は自分の子どもの情報だけ見られるべきです。担任は自分のクラスの情報を見られますが、他クラスの詳細までは見られないかもしれません。管理者は利用者管理ができます。正しい人が使えることだけでなく、使ってはいけない人が使えないことを確認するのが権限テストです。

テスト戦略では、単体テスト、結合テスト、システムテスト、受入テストの役割を分けます。単体テストは小さな関数やクラスを確認します。結合テストは部品のつなぎ目を確認します。システムテストはシステム全体として要件を満たすかを確認します。受入テストは、利用者や発注者の視点で使えるかを確認します。どれか 1 種類だけでは足りません。小さな部品が正しくても全体の流れが壊れることがあり、全体テストだけでは原因特定が遅くなります。

### 性能・負荷・信頼性をテストする

機能が正しくても、混雑時に遅すぎればシステムは使えません。欠席連絡アプリなら、朝 7:30 から 8:30 にアクセスが集中します。平常時に 1 人で操作して速いことと、500 人が同時に使っても許容範囲に収まることは別です。だから性能や負荷も、要件からテストへ落とします。

負荷テストは、想定される利用量をかけて、応答時間、エラー率、CPU、メモリ、DB、ネットワーク、キューの長さを確認します。たとえば「同時 500 人で欠席登録の 95% が 2 秒以内」と要件に書いたなら、500 人相当の操作を発生させ、95% の応答が 2 秒以内かを測ります。

ここで平均だけを見ると危険です。100 回のうち 95 回が 1 秒、5 回が 20 秒だったとします。合計時間は、速い 95 回ぶんが `95 × 1秒 = 95秒`、遅い 5 回ぶんが `5 × 20秒 = 100秒` なので、合わせて `95秒 + 100秒 = 195秒` です。平均は合計を回数で割るため、`195秒 / 100回 = 1.95秒` になります。平均だけなら良さそうに見えますが、20 秒待たされた利用者にとっては失敗に近い体験です。だから 95 パーセンタイルや 99 パーセンタイルを見ることがあります。95 パーセンタイルは、全体の 95% がその値以下に収まる境目です。多くの利用者が十分速いか、少数だけ極端に遅くないかを分けて判断できます。

ストレステストは、想定以上の負荷をかけ、どこで限界に達するかを調べるテストです。目的は、無限に耐えることを確認することではありません。限界を超えたとき、エラーが増えるのか、応答が遅くなるのか、DB 接続が枯渇するのか、キューが伸び続けるのかを知ることです。限界の近くでどう壊れるかを知っていれば、監視しやすく、緊急時の判断もしやすくなります。

スパイクテストは、急に負荷が跳ね上がったときの挙動を見ます。朝の締切直前、メール通知直後、災害連絡直後など、アクセスはなだらかに増えるとは限りません。オートスケーリングがあっても、起動に時間がかかるなら、急増の最初の数分は遅くなるかもしれません。スパイクテストでは、増え方そのものを試します。

長時間試験は、時間がたつと出る問題を見るために行います。短時間なら問題なくても、数時間から数日動かすと、メモリリーク、ログ肥大化、一時ファイルの残り、DB 接続の解放漏れ、キャッシュの偏りが見えることがあります。長く動くサーバでは、「起動直後は速い」だけでは足りません。

性能テストでは、環境とデータも重要です。開発者の PC で少量データを使って速くても、本番相当のデータ量、ネットワーク、外部サービス、認証、ログ出力では違う結果になります。もちろん本番と完全に同じ環境を毎回用意するのは難しいですが、少なくとも何が違うかを記録し、結果を過大評価しないようにします。

性能問題を見つけたら、原因を測って分けます。CPU が高いのか、DB クエリが遅いのか、インデックスが効いていないのか、外部 API を待っているのか、ロック待ちなのか、ログ出力が詰まっているのか。負荷テストは合否判定だけでなく、どこがボトルネックになるかを見つけ、設計を直すための実験でもあります。

外部 API とつながるシステムでは、契約テストも役立ちます。ここでいう契約は法律文書ではなく、API の約束です。どの URL に、どんな JSON を送り、どんなステータスコードと項目が返るかを確認します。通知サービス側が `studentId` を `student_id` に変えただけでも、呼び出す側は壊れるかもしれません。契約テストは、相手サービスの内部を全部知らなくても、入り口と出口の約束が保たれているかを確かめる方法です。

回帰テストは、以前動いていた機能が変更後も壊れていないかを見るテストです。回帰とは、良くなったはずのものが前の悪い状態へ戻ることです。欠席理由の文字数制限を直したら、なぜか通知メールが送られなくなった、というような事故を防ぐために行います。変更が増えるほど、人間の手作業だけで回帰テストを続けるのは難しくなるので、自動テストとCIが効いてきます。

CI は Continuous Integration、継続的インテグレーションです。開発者が変更をこまめに統合し、自動でビルド、テスト、静的解析を走らせます。ビルドは、ソースコードを実行可能な形や配布できる形に変換することです。静的解析は、プログラムを実行せずにコードを調べ、危険な書き方、型の不整合、セキュリティ上の問題を見つける方法です。CI の価値は、問題を後でまとめて見つけるのではなく、小さな変更の直後に見つけることです。

CD は Continuous Delivery または Continuous Deployment として使われます。Continuous Delivery は、いつでも本番へ出せる状態を保つ考え方です。Continuous Deployment は、自動テストを通った変更を自動で本番へ出すところまで進める考え方です。どちらも、リリース作業を職人技にせず、手順、検証、戻し方をパイプラインとして管理します。パイプラインとは、変更が本番へ近づくまでの一連の流れです。

本番リリースでは、変更を一度に全利用者へ出すとは限りません。ブルーグリーンデプロイでは、現在動いている環境とは別に新しい環境を用意し、切替によって新旧を入れ替えます。問題があれば元の環境へ戻しやすくなります。カナリアリリースでは、一部の利用者や一部のサーバにだけ新バージョンを出し、エラー率や応答時間を見ながら広げます。ここで大切なのは、「出す」だけでなく、観測し、止め、戻せることです。

機能フラグも変更を安全にする技術です。機能フラグは、コードは本番に入っていても、設定で機能を有効化または無効化できる仕組みです。全員に公開する前に社内利用者だけ有効にする、障害が出た機能だけ止める、といった運用ができます。ただし、古いフラグを残し続けると条件分岐が増え、コードが複雑になります。安全なリリースは、出し方だけでなく、後片付けまで含みます。

データベース変更は特に慎重に扱います。アプリの新しい版だけでなく、古い版も一時的に動くことがあるため、列の削除や意味変更を急に行うと壊れます。安全な移行では、まず新しい列を追加し、アプリが新旧両方を扱えるようにし、データを移し、十分確認してから古い列を消す、という段階を踏むことがあります。これは、停止時間を減らし、戻しやすくするための設計です。

データ移行では、プログラムの切替以上に「意味が同じまま移せたか」が重要です。古いシステムの生徒番号、氏名、クラス、保護者連絡先を新システムへ移すとき、列名が同じでも意味が違うことがあります。旧システムの「住所」が自宅住所なのか、通知先住所なのか、保護者住所なのかを確認しないまま移すと、データは入っているのに業務では使えない状態になります。

移行では、抽出、変換、投入、検証を分けます。抽出は旧システムからデータを取り出すことです。変換は、形式やコード体系を新システムに合わせることです。投入は新システムへ入れることです。検証は、件数、合計、代表データ、例外データを突き合わせることです。たとえば旧システムの生徒数が 1200 人なら、新システムでも対象条件に合う生徒が 1200 人いるかを確認します。件数だけでなく、退学済み、休学中、同姓同名、外字を含む氏名など、問題になりやすいデータも見ます。

本番移行前にはリハーサルを行います。リハーサルは、実際に近いデータ量と手順で予行演習することです。移行に何時間かかるか、途中で失敗したらどこまで戻せるか、切替後に旧システムへ戻す判断基準は何かを確認します。データ移行は一度きりの作業に見えますが、設計、テスト、監査、利用者告知、戻し手順まで含む開発作業です。

## 9.8 結合テストは部品のつなぎ目を見る

部品が単体で正しくても、組み合わせた瞬間に問題が出ることがあります。友達同士がそれぞれ担当部分を作っても、最後につないだらサイズが合わない、受け渡す情報が違う、順番が合わない、ということがあります。システムでも同じで、インタフェースのずれを確認する必要があります。

トップダウンテストは、上位モジュールから下位モジュールへ結合していく方法です。未完成の下位モジュールはスタブで代用します。スタブは呼ばれる側の代用品です。

ボトムアップテストは、下位モジュールから上位モジュールへ結合していく方法です。未完成の上位モジュールはドライバで代用します。ドライバは呼ぶ側の代用品です。

ビッグバンテストは、一気に結合する方法です。単純に見えますが、問題が起きたとき原因特定が難しくなります。サンドイッチテストは、上位と下位の両側から進める方法です。

## 9.9 テスト管理とレビュー

バグを「見つけたら直す」だけでは品質を管理できません。どんな欠陥がどれだけあり、どれが重大で、どれが未解決で、なぜ起きたのかを記録しなければ、同じ失敗を繰り返します。

バグ管理では、発見日、重要度、優先度、原因、修正状況、再現手順を管理します。累積発見件数、累積修正件数、未解決件数を見ると、テストの進み方や修正状況が分かります。ただし、発見件数が急に減ったから品質が良いとは限りません。テストが不足している可能性もあります。

バグ管理図は、バグの発見と修正の状況を時間の流れで見る図です。よく使うのは、横軸に日付やテスト期間、縦軸に件数を置き、累積発見件数、累積修正件数、未修正件数を追う形です。累積とは、そこまでの合計です。1 日目に 5 件、2 日目に 8 件、3 日目に 4 件見つかったなら、3 日目までの累積発見件数は次のようになります。

```text
累積発見件数 = 5 + 8 + 4
             = 17
```

ここで足し算をする理由は、3 日目までに見つかった総数を知りたいからです。日ごとの件数だけを見ると、その日に何件見つかったかは分かりますが、プロジェクト全体としてどれだけ欠陥を処理してきたかは分かりません。累積で見ると、発見の勢いが増えているのか、落ち着いてきたのか、修正が追いついているのかを読みやすくなります。

未修正件数は、見つかったがまだ直っていない件数です。累積発見件数が 17 件、累積修正件数が 12 件なら、

```text
未修正件数 = 累積発見件数 - 累積修正件数
           = 17 - 12
           = 5
```

未修正件数が増え続けているなら、テストで見つける速度に修正が追いついていません。リリース前なのに未修正の重大バグが残っているなら、日程より品質リスクを優先して判断する必要があります。一方、発見件数が減っていて未修正件数も減っているなら、品質が安定してきた可能性があります。ただし、テスト範囲が狭いだけで発見件数が少ない場合もあるため、管理図だけで判断しません。

バグ数の推測では、見つかったバグ数だけでなく、まだ残っている可能性を考えます。たとえばテスト開始直後は、重要な機能を広く触るためバグが多く見つかります。テストが進むにつれて、修正も進み、同じ観点のバグは減っていくはずです。発見件数の曲線がなだらかになり、未解決件数も減っていれば、品質が安定してきた可能性があります。

ただし、発見件数が少ない理由は 2 つあります。品質が良くなったから少ない場合と、テストが弱くて見つけられていない場合です。そこで、テスト項目の消化率、重要機能の網羅、レビュー指摘、障害の重大度、修正後の再発、未テスト領域を合わせて見ます。欠陥密度という考え方もあります。これは、プログラム規模や機能規模に対して欠陥がどれくらい見つかったかを見る指標です。数字は比較の手がかりになりますが、単独で品質を証明するものではありません。

バグ数を推測する代表的な考え方に、埋込バグ法があります。これは、あらかじめ分かっている人工的なバグをいくつか入れておき、テストでそのうち何件見つかったかから、本物のバグの見つかり具合を推定する方法です。もちろん実際の開発では、使い方や対象を慎重に考える必要がありますが、考え方は「見つけられた割合」から残りを推定することです。

たとえば、人工的なバグを 20 件入れたとします。テストでそのうち 16 件が見つかりました。このとき、人工バグの発見率は次のように計算できます。

```text
人工バグの発見率 = 見つかった人工バグ数 / 埋め込んだ人工バグ数
                = 16 / 20
                = 0.8
```

`16 / 20` は、20 件中 16 件を見つけたという割合です。`0.8` は 80% を意味します。割合をパーセントで言いたい場合は、`0.8 × 100 = 80` なので 80% です。

同じ発見率で本物のバグも見つかっていると仮定します。もし本物のバグが 40 件見つかっているなら、「本物のバグ全体の 80% が 40 件に相当する」と考えます。

```text
見つかった本物のバグ数 = 推定される本物の総バグ数 × 発見率
40 = 推定される本物の総バグ数 × 0.8
```

ここから、推定される本物の総バグ数を求めます。両辺を `0.8` で割るのは、右辺の `× 0.8` を取り除き、総バグ数だけを左に出したいからです。

```text
推定される本物の総バグ数 = 40 / 0.8
                         = 50
```

すでに 40 件見つかっているので、まだ残っている本物のバグは、

```text
推定残存バグ数 = 推定される本物の総バグ数 - 見つかった本物のバグ数
               = 50 - 40
               = 10
```

と推定できます。ただし、この推定は「人工バグと本物のバグが同じくらい見つけやすい」という仮定に依存します。人工バグが簡単すぎれば発見率は高く見え、残存バグを少なく見積もってしまいます。逆に人工バグが不自然に難しければ、残存バグを多く見積もるかもしれません。推定は判断材料であり、品質を自動的に保証するものではありません。

信頼度成長モデルは、テストと修正が進むにつれてソフトウェアの信頼性が高まる様子をモデル化する考え方です。難しく聞こえますが、本質は「テストで欠陥を見つけ、直し、同じ種類の欠陥が減っていくなら、障害発生の確率も下がるはずだ」と考えることです。高度な品質管理では、感覚で「そろそろ大丈夫」と言うのではなく、発見傾向、残存リスク、テスト範囲を根拠に判断します。

レビューは、プログラムを実行する前にも欠陥を見つけられる活動です。仕様の曖昧さ、設計の無理、読みづらいコード、テスト観点の不足を早く共有し、チーム全体の理解をそろえます。

ウォークスルーは、作成者が成果物を説明し、参加者が確認する方法です。インスペクションは、役割と手順を決めた厳格なレビューです。ラウンドロビンレビューは参加者が順番に確認します。ピアレビューは同僚による確認です。

形式手法は、数学的な仕様記述や検証により、曖昧さや矛盾を減らす方法です。高い信頼性が必要な分野で使われます。普通の文章で「申請は承認後に取り消せる」と書くと、誰が、いつ、どの状態で取り消せるのかが曖昧になることがあります。形式手法では、状態、操作、事前条件、事後条件、不変条件を厳密に表します。

不変条件とは、処理の前後で常に成り立つべき条件です。たとえば銀行口座なら、「残高は原則として 0 未満にならない」「振込では、送金元から減った金額と送金先に増えた金額が対応する」といった条件です。状態遷移モデルやモデル検査では、システムが取り得る状態を機械的に調べ、危険な状態へ到達しないかを確認します。すべてのシステムで重い形式手法を使うわけではありませんが、曖昧な日本語を、確認可能な条件へ落とす姿勢はどの開発でも役立ちます。

レビューで大切なのは、相手を責めることではありません。成果物を早く良くすることです。良いレビューでは、「この要件は誰の操作を想定しているのか」「この例外時は何を表示するのか」「この名前は別の意味にも読めないか」「このテストで本当に要件を確認できるか」のように、成果物に対して質問します。

レビュー対象はコードだけではありません。要件定義書、画面設計、DB 設計、API 仕様、テスト仕様、運用手順書もレビュー対象です。上流の誤りほど、後で見つかると修正コストが大きくなります。だから、コードを書いた後だけでなく、要求や設計の段階で欠陥を見つけることが重要です。

品質は最後に検査で付け足すものではありません。要求を具体化し、設計で責任を分け、実装で約束を守り、テストで証拠を集め、レビューで思い込みを減らすことで、最初から作り込むものです。

## 9.10 保守と構成管理は変え続けるための技術

ソフトウェアは、完成した瞬間に終わるものではありません。利用者が増える、法律が変わる、端末が変わる、外部サービスの仕様が変わる、攻撃手法が変わる。動いているシステムほど、使われ続けるために変更が必要になります。

保守には種類があります。是正保守は、見つかった欠陥を直すことです。適応保守は、OS、ブラウザ、法制度、外部 API など環境の変化に合わせることです。完全化保守は、使いやすさや性能を高めることです。予防保守は、将来の障害や変更困難を防ぐために、構造を改善することです。

この分類が大切なのは、同じ「改修」でも目的が違うからです。障害を直す改修と、性能を上げる改修と、将来のために構造を整える改修では、優先度、テスト範囲、利用者への説明、リリース時期が変わります。保守は残務処理ではなく、システムの価値を保つ活動です。

技術的負債は、短期的に速く進めるために選んだ設計や実装上の妥協が、後から変更コストとして返ってくる状態です。負債という言葉が使われるのは、借金のように利子がつくからです。小さな重複や分かりにくい名前を放置すると、次の変更で理解に時間がかかり、さらに場当たり的な修正が積み重なります。

ただし、技術的負債は単に「悪いコード」という意味ではありません。納期やリスクを考えて、あえて暫定策を選ぶ場合もあります。重要なのは、負債を見えないままにしないことです。なぜ暫定策にしたのか、どんなリスクがあり、いつ返すのかを記録します。返すとは、設計を整理し、テストを追加し、不要な分岐を消し、理解しやすい構造へ戻すことです。

リファクタリングは、外から見える振る舞いを変えずに、内部構造を改善することです。関数を分ける、名前を分かりやすくする、重複を減らす、責任の場所を移す、といった作業です。外から見える動きが変わらないため、回帰テストが重要になります。テストが弱いと、内部を整理したつもりで利用者から見える動きを壊しても気づけません。

構成管理は、ソフトウェアを構成する部品と変更を管理する活動です。ソースコード、設定ファイル、ライブラリのバージョン、DB スキーマ、環境変数、ビルド手順、リリース手順がばらばらに管理されていると、「どの版が本番に入っているのか」「同じものをもう一度作れるのか」が分からなくなります。

バージョン管理は、変更履歴を追うための基本です。誰が、いつ、なぜ変更したかを残すと、不具合が出たときに原因を探しやすくなります。タグやリリース番号を使うと、本番に出した版を特定できます。依存ライブラリのバージョンも固定しないと、同じソースコードから違う動作の成果物ができることがあります。

ビルドの再現性も重要です。再現性とは、同じ入力から同じ成果物を作れることです。開発者の PC では動くが本番では動かない、昨日は作れたが今日は依存ライブラリが変わって作れない、という状態では安心してリリースできません。ビルド手順を自動化し、依存関係を管理し、環境差を小さくすることは、開発速度だけでなく品質にも関わります。

リリース管理では、どの変更をいつ、どの手順で、どの環境へ出すかを管理します。変更一覧、影響範囲、テスト結果、戻し手順、承認、監視項目をそろえます。リリースはボタンを押す瞬間だけではありません。出す前の確認、出した直後の監視、問題が出たときの切戻し、利用者への連絡まで含む一連の活動です。

保守しやすいシステムは、将来の自分たちを助けます。要件が変わることを前提に、責任を分け、テストを残し、構成を管理し、変更の理由を記録する。これが、長く使われるソフトウェアを作るための開発技術です。

受入は、開発側が「作りました」と言うだけでは終わりません。利用者や発注者の視点で、業務に使える状態かを確認します。受入テストでは、機能が動くかだけでなく、実際の業務手順、権限、データ、帳票、通知、例外時の対応まで見ます。

たとえば欠席連絡アプリなら、保護者が登録できることだけでなく、担任が朝の短い時間で一覧を確認できるか、保健室へ必要な情報が届くか、登録を間違えたとき訂正できるか、通信障害時に代替手順があるかを確認します。システム単体として正しくても、業務の流れに入らなければ使えるとは言えません。

受入条件は、要件定義の段階から考えておくべきです。最後になってから「これで完成か」を話し合うと、開発側と利用者側の期待がずれていることがあります。「一覧表示できる」ではなく、「担任は自分のクラスの当日分を、登録時刻順に、スマホと PC の両方で確認できる」のように、判定できる条件にします。

移行判定では、機能、データ、運用、教育、サポートの準備をそろえて見ます。プログラムが動いても、利用者アカウントが用意されていない、旧システムからデータが移っていない、問い合わせ先が決まっていない、先生向け説明がない、という状態では本番利用に耐えません。リリース判定は、コードだけでなく業務開始の準備を確認する場です。

運用引き継ぎでは、運用担当者が日々何を見るのかを具体化します。監視項目、アラートの意味、障害時の一次対応、再起動してよい条件、データ修正の手順、利用者問い合わせへの回答、ベンダへの連絡条件を決めます。開発者だけが知っている暗黙の手順を残すと、障害時に対応が遅れます。

マニュアルも、操作説明だけでは足りないことがあります。管理者向けには、利用者追加、権限変更、ログ確認、バックアップ確認、障害時の連絡先が必要です。利用者向けには、日常操作、入力ミス時の対応、困ったときの問い合わせ先が必要です。同じシステムでも、読む人によって必要な情報は違います。

初期稼働期間は、通常より注意深く見ます。リリース直後は、想定していなかった使い方、データの偏り、問い合わせの集中、性能問題が出やすいからです。ログ、エラー率、応答時間、問い合わせ内容、利用者のつまずき方を観察し、必要なら素早く改善します。

このように、開発技術はコードを書く技術だけではありません。要求を決め、設計し、作り、確かめ、移し、運用へ渡し、変え続ける技術です。最初からこの流れ全体を考えると、システムは「完成したけれど使えない」状態になりにくくなります。

## 9.11 運用で見えるように作る

システムは、本番で動き始めてからも問題が起きます。通信が遅い、特定の利用者だけ登録できない、外部サービスが失敗する、朝だけ負荷が高い、ある操作の後だけエラーが増える。こうした問題を調べるには、運用で何が起きているかを見えるように設計しておく必要があります。

可観測性は、外から見える情報を使って、システム内部の状態を推測できる性質です。代表的な情報に、ログ、メトリクス、トレースがあります。ログは、いつ何が起きたかの記録です。メトリクスは、応答時間、エラー率、CPU 使用率、キューの長さのような数値です。トレースは、1 つの要求が複数サービスを通る流れを追う情報です。

ログ設計では、調査に必要な情報を残します。エラーが起きた時刻、利用者の種類、対象データ、処理名、結果、原因に近い情報が必要です。ただし、パスワード、秘密鍵、過度に詳しい個人情報をログへ出してはいけません。ログは障害調査の助けになりますが、漏れれば被害を広げるデータにもなります。

相関 ID も有効です。相関 ID は、1 つの要求に付ける追跡用の識別子です。画面、API、認証、通知、データベース処理が別々にログを出しても、同じ相関 ID があれば、1 つの操作の流れとしてつなげられます。利用者が「登録できなかった」と問い合わせたとき、時刻と相関 ID があれば、どの処理で失敗したかを追いやすくなります。

メトリクスでは、平均だけを見ると危険です。平均応答時間が 1 秒でも、一部の利用者だけ 10 秒かかっているかもしれません。そこで、95 パーセンタイルや 99 パーセンタイルを見ることがあります。95 パーセンタイルは、全体の 95% がその値以下に収まる境目です。多くの利用者にとって十分速いか、少数の利用者が極端に遅くないかを見るために使います。

アラートは、鳴ればよいものではありません。多すぎるアラートは担当者を疲れさせ、本当に重要な異常を見落とす原因になります。アラートは、利用者影響がある、すぐ判断が必要、対応手順がある、という条件を満たすものに絞ります。単なる情報はダッシュボードで見ればよく、夜中に人を起こす必要があるものとは分けます。

運用を見据えた設計では、失敗を前提にします。外部通知サービスが失敗したとき、登録処理全体を失敗にするのか、登録は成功として通知を後で再送するのか。データベース接続が一時的に切れたとき、すぐエラーにするのか、短く再試行するのか。再試行するなら、二重登録を防ぐために冪等性が必要です。障害時の振る舞いは、コードを書いた後に自然に決まるものではなく、業務上の意味から設計します。

利用者へのエラー表示も、運用の一部です。内部エラーをそのまま見せると、意味が分からないだけでなく、内部情報を漏らす可能性があります。一方で、「失敗しました」だけでは、利用者も問い合わせ担当も次に何をすればよいか分かりません。利用者には安全で行動可能な説明を出し、内部ログには調査に必要な詳細を残します。

開発段階から運用を考えると、テストの観点も変わります。機能が成功するかだけでなく、失敗時にログが残るか、監視で検知できるか、再試行で二重処理にならないか、エラーメッセージが適切か、運用手順で復旧できるかを確認します。運用しやすいシステムは、障害が起きないシステムではなく、問題を早く見つけ、影響を抑え、根拠を持って直せるシステムです。

## 9.12 利用者視点の品質を設計する

システムは、仕様どおり動いても、利用者が迷うなら目的を達成できません。使用性は、利用者が目的の操作を、無理なく、間違いにくく、効率よく行えるかを見る品質です。高校の欠席連絡アプリなら、保護者が朝の短い時間にスマートフォンで入力できること、担任が授業前に一覧をすぐ確認できることが重要です。

使用性は、見た目をきれいにするだけではありません。入力項目が多すぎないか、選択肢の言葉が分かるか、エラー時に直し方が分かるか、前の画面へ戻っても入力が消えないか、確認画面で何を確認すべきかが分かるか、といった具体的な設計です。

アクセシビリティは、利用者の身体的条件、利用環境、端末の違いがあっても使えるようにする考え方です。文字が小さすぎないか、色だけでエラーを示していないか、キーボードだけで操作できるか、読み上げソフトで意味が伝わるか、通信が遅い環境でも必要な操作ができるかを考えます。

使用性やアクセシビリティも、要件として書けます。「分かりやすい画面」では弱いです。「必須入力の不足がある場合、該当項目の近くに理由と修正方法を表示する」「エラーは色だけで示さず、文字でも示す」「主要操作はスマートフォン幅でも横スクロールなしで行える」のように書くと、設計とテストにつながります。

利用者テストでは、作った人ではなく実際に近い利用者に操作してもらいます。開発者は画面の意図を知っているため、迷わず使えてしまいます。初めて使う人がどこで止まるか、どの言葉を誤解するか、どの操作を見落とすかを見ることで、仕様書だけでは見えない問題が分かります。

ここでも、利用者の声をそのまま機能追加に変えるだけでは不十分です。「ボタンを増やしてほしい」という声の奥には、「次に何をすればよいか分からない」という問題があるかもしれません。要求の言葉から原因を探り、画面構成、説明文、入力順序、初期値、エラー表示を設計します。利用者視点の品質は、感覚ではなく、観察と要件化と検証で作ります。

## 実務で使える理解

開発モデルは、要求変更への強さ、文書化、リスク対応で比較します。DFD はデータの流れ、UML クラス図は構造、シーケンス図は時間順を見ます。オブジェクト指向は、責任を持つ単位にデータと操作をまとめる考え方です。

モジュール設計では、結合度を低く、凝集度を高くします。ブラックボックステストは仕様から、ホワイトボックステストは内部構造から見ます。スタブは呼ばれる側の代用品、ドライバは呼ぶ側の代用品です。性能・負荷・信頼性テストは、混雑時や長時間運用で要件を満たせるかを確認します。レビューは、テスト実行前にも欠陥を見つけられます。

バグ管理図では、累積発見件数、累積修正件数、未修正件数の動きから、テストの進み方と修正の追いつき具合を読みます。埋込バグ法のような推定は、発見率から残存バグ数を見積もる考え方ですが、仮定を理解して使います。

保守、構成管理、リリース管理、可観測性は、作った後も変え続けるための開発技術です。ログ、メトリクス、トレース、相関 ID は、本番で起きた問題を根拠を持って調べるために設計します。

使用性とアクセシビリティは、見た目の好みではなく品質要件です。利用者が迷わず、間違いにくく、必要な環境で使えるかを、要件、設計、テストに落とします。

## 自分の言葉で説明できるか

- ウォータフォール、プロトタイピング、スパイラル、アジャイルを、要求の変わりやすさとリスクで比較できる。
- DFD の 4 要素を、欠席連絡アプリなどの具体例に当てはめて説明できる。
- UML の代表図を、何を見える化する図かで説明できる。
- クラス、インスタンス、カプセル化、継承、多態性を具体例で説明できる。
- 結合度と凝集度を、変更しやすさと影響範囲の観点から説明できる。
- 同値分割と境界値分析を、入力条件の例で使える。
- 命令網羅、分岐網羅、条件網羅を区別できる。
- 負荷テスト、ストレステスト、スパイクテスト、長時間試験の違いを説明できる。
- 平均応答時間だけでなく、95 パーセンタイルを見る理由を説明できる。
- スタブとドライバの違いを、呼ぶ側と呼ばれる側で説明できる。
- バグ管理図で、累積発見件数、累積修正件数、未修正件数を読み取れる。
- 埋込バグ法で、発見率と推定残存バグ数を計算できる。
- ウォークスルーとインスペクションの違いを説明できる。
- 是正保守、適応保守、完全化保守、予防保守を区別できる。
- ログ、メトリクス、トレース、相関 ID の役割を説明できる。
- 使用性とアクセシビリティを、測れる要件として書ける。

## 深く身につけるための補講

システム開発で最も危険なのは、「作り始めるのが早いこと」そのものではありません。何を確かめるために作っているのか分からないまま進むことです。画面を先に作るのが有効な場合もあります。しかし、それが利用者の要求を確認するための試作品なのか、本番品質の土台なのかを区別しないと、あとで苦しくなります。

欠席連絡アプリを例に、要求からレビューまでを一度つなげて見ます。

最初の要求は、たとえば次のような利用者の言葉です。

```text
朝の電話が多くて大変なので、スマホから欠席連絡できるようにしたい。
```

これは大事な出発点ですが、このままでは開発できません。誰が、いつ、何を、どの条件でできる必要があるかに分解します。

```text
保護者は、当日の 8:30 まで欠席・遅刻・早退を登録できる。
登録内容には、生徒、日付、種別、理由、連絡者、連絡時刻を含める。
担任は、自分のクラスの当日連絡一覧を確認できる。
保健室は、全校の欠席・感染症疑いの一覧を確認できる。
登録後、保護者と担任に通知する。
登録内容の閲覧は、権限を持つ利用者だけに制限する。
```

このように、利用者の言葉を開発できる条件へ落としたものが要件です。要件が具体化すると、テストも作れるようになります。「8:30 まで登録できる」なら、8:29、8:30、8:31 の境界値を確認できます。「担任は自分のクラスだけ見られる」なら、別クラスのデータが見えないことを確認できます。

## DFDで欠席連絡アプリを見る

DFD では、データがどこから来て、どの処理を通り、どこへ保存され、誰へ渡るかを見ます。

欠席連絡アプリでは、外部実体として保護者、担任、保健室、通知サービスが考えられます。保護者は欠席連絡を入力します。担任は連絡一覧を確認します。保健室は必要な情報を確認します。通知サービスはメールやアプリ通知を送ります。

プロセスとしては、欠席連絡を受け付ける処理、入力内容を検証する処理、連絡を保存する処理、通知を作成する処理、一覧を表示する処理があります。

データフローは、欠席日、種別、理由、生徒番号、連絡者、通知内容などです。データストアは、利用者情報、クラス情報、欠席連絡履歴、通知履歴などです。

DFD を描く意味は、処理名を並べることではありません。たとえば「保護者が入力した理由は、担任だけでなく保健室にも流れるのか」「通知サービスには個人情報をどこまで渡すのか」「履歴はどこに保存されるのか」を確認できます。セキュリティや個人情報保護の観点も、データの流れを見ることで見つけやすくなります。

## UMLで同じアプリを見る

同じ欠席連絡アプリでも、UML の図によって見るものが変わります。

ユースケース図では、保護者が欠席連絡を登録する、担任が一覧を見る、管理者が利用者を登録する、といった利用者と機能の関係を見ます。これは、機能範囲を関係者と確認するのに役立ちます。

クラス図では、`学生`、`保護者`、`教員`、`クラス`、`欠席連絡`、`通知` のようなクラスと関係を考えます。たとえば、1 人の学生に複数の保護者が紐づくかもしれません。1 つの欠席連絡は、1 人の学生、1 日付、1 つの種別を持ちます。こうした関係を先に整理すると、DB 設計やプログラム構造が安定します。

シーケンス図では、時間順のやり取りを見ます。

```text
保護者画面 -> API: 欠席連絡を送信
API -> 認証処理: 利用者を確認
API -> 入力検証: 内容を確認
API -> DB: 欠席連絡を保存
API -> 通知サービス: 担任へ通知
API -> 保護者画面: 登録完了を返す
```

このように並べると、どこで認証するのか、保存前に検証するのか、通知失敗時に登録をどう扱うのか、といった設計上の問いが見えてきます。

状態遷移図では、欠席連絡の状態を見ます。

```text
下書き -> 提出済み -> 確認済み
提出済み -> 取消申請中 -> 取消済み
```

状態を整理すると、「確認済みの連絡を保護者が消せるのか」「取消は誰が承認するのか」「通知後に修正したら再通知するのか」を検討できます。

## テスト設計を要求に戻して考える

テストは、実装後に何となく触ることではありません。要件やリスクから確認観点を作ります。

欠席連絡アプリで「8:30 まで登録できる」という要件があるなら、境界値は重要です。

```text
8:29 -> 登録できるはず
8:30 -> 仕様で許すなら登録できるはず
8:31 -> 登録できないはず
```

ここで「8:30 ちょうど」を許すのか許さないのかが曖昧だと、実装者と利用者で解釈がずれます。テストを考えることで、要件の曖昧さが見つかることがあります。

「担任は自分のクラスだけ見られる」という要件なら、正常系だけでは足りません。自分のクラスの欠席連絡が見えること、別クラスの欠席連絡が見えないこと、担任でない利用者が一覧にアクセスできないこと、管理者は必要な範囲を見られることを確認します。

「通知する」という要件も、単純ではありません。通知サービスが成功した場合、失敗した場合、遅延した場合、同じ通知が二重に送られた場合を考えます。欠席連絡の保存と通知は、どちらが失敗したときにどう扱うのかを設計しておく必要があります。

## レビューで見るべきもの

レビューは、コードの細かい書き方だけを見る場ではありません。要求、設計、テスト観点、運用、セキュリティを早い段階で確認する場です。

欠席連絡アプリの要件レビューでは、利用者が本当に困っていることに合っているかを見ます。朝の電話を減らしたいのに、アプリ入力後に結局電話確認が必要なら、目的に合っていません。

設計レビューでは、責任の分け方を見ます。通知処理が登録処理に強く結びつきすぎていると、通知サービスの障害で登録まで失敗するかもしれません。個人情報を含むデータがログに出すぎていないかも確認します。

テストレビューでは、正常系だけでなく、境界値、権限違反、通信失敗、二重送信、取消、遅延、入力ミスを見ているかを確認します。

コードレビューでは、読みやすさ、例外処理、入力チェック、権限確認、ログ、テストしやすさを見ます。レビューの目的は作成者を責めることではなく、成果物の欠陥を早く見つけ、チーム全体の理解をそろえることです。

## ありがちな誤解

- アジャイルは計画しない開発ではありません。短い周期で計画、実装、確認、改善を繰り返します。
- テスト工程で初めて品質を作るのではありません。品質は要求、設計、実装の段階から作り込みます。
- UML は絵を描くことが目的ではありません。関係者の理解をそろえるための言語です。
- レビューは人を責める場ではありません。成果物の欠陥を早く見つける場です。
- 網羅率が高くても、重要な観点が抜けていれば品質は保証できません。
- バグ発見件数が少ないことは、品質が高い証拠とは限りません。テストが弱い可能性もあります。
- 平均応答時間が良くても、一部の利用者だけ極端に遅いなら、体験としては失敗に近い場合があります。
- ログを出していれば運用しやすいとは限りません。調査に必要な情報と出してはいけない情報を分ける必要があります。
- 利用者の要望をそのまま機能追加にするだけでは、根本原因を外すことがあります。
