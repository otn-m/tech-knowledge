# 第2章 アルゴリズムとプログラミング

## この章の地図

アルゴリズムは「手順の設計」です。プログラミング言語の書き方そのものではなく、データをどう持ち、どう処理すれば速く正しく答えが出るかを学ぶ章です。

この章では、リスト、スタック、キュー、木、ハッシュのようなデータ構造を、単なる名前ではなく「どんな操作に強い形か」として見ます。探索は目的のデータを見つける技術、整列はデータを順番に並べて扱いやすくする技術、再帰は同じ形の小さい問題に分ける考え方です。計算量は、入力が増えたときに時間やメモリがどう増えるかを読むための物差しです。

## なぜこの章を学ぶのか

プログラムは、ただ命令を上から書けばよいわけではありません。同じ目的でも、データの持ち方や処理手順が悪いと、少しデータが増えただけで動かなくなります。

たとえば、学校全体 1000 人の名簿から 1 人を探すだけなら、上から順に見ても間に合います。しかし、全国の利用者 1000 万人から毎秒何千回も検索するなら、探し方を工夫しなければサービスになりません。SNS のタイムライン、動画サイトの検索、ゲームの経路探索、銀行の取引処理、スマホの連絡先表示など、ほとんどの IT はデータ構造とアルゴリズムの上で動いています。

この章を学ぶと、「とりあえず動く」から一段上がって、「データが増えても速く、壊れにくく、変更しやすい」プログラムを考えられるようになります。

## 2.1 リスト

いきなり「リストはデータ構造です」と言われても、初学者には何の話か分かりにくいはずです。まず、身近な画面を思い出してください。

- 音楽アプリの再生リスト。
- YouTube や SNS の通知一覧。
- ブラウザの閲覧履歴。
- ToDo アプリのタスク一覧。
- チャットアプリのメッセージ一覧。
- EC サイトのカート内商品。

これらはすべて、「複数のデータが順番に並んでいて、追加されたり、削除されたり、並び替えられたりする」ものです。このようなデータをコンピュータの中でどう持つか、という話がリストです。

リストを学ぶと、次のような判断ができるようになります。

- 新しい通知を先頭に追加したい。
- 3 番目の曲をすぐ再生したい。
- 途中のタスクを削除したい。
- 順番を入れ替えたい。
- 大量の履歴を効率よく扱いたい。

つまりリストは、ただの「並び」ではありません。「順番のあるデータを、どんな操作に強い形で保存するか」を考えるための入口です。

リストを実現する代表的な方法が、配列と連結リストです。どちらも「順番に並んだデータ」を表せますが、得意なことが違います。配列は、添字で直接アクセスできる構造です。`i` 番目を読むのは速い一方、真ん中への挿入や削除では後ろの要素をずらす必要があるため遅くなります。

配列は、映画館の座席のようなものです。座席番号が分かれば、その席にすぐ行けます。同じように、配列では `3 番目` や `100 番目` のように番号で直接アクセスできます。

しかし、真ん中に新しい人を入れたい場合はどうでしょう。座席が詰まっていれば、後ろの人をずらす必要があります。配列でも同じで、真ん中にデータを挿入すると、後ろのデータをずらす処理が必要になります。

配列は、番号で素早く取り出したいとき、データ数が大きく変わらないとき、先頭から順番に高速に処理したいときに向きます。画像のピクセルや表のように、位置そのものに意味があるデータでも配列は強力です。

連結リストは、各要素が「次の要素への参照」を持つ構造です。途中への挿入や削除は、参照を付け替えるだけなので速くできます。その代わり、`i` 番目へ直接飛ぶことはできず、先頭からたどる必要があります。

連結リストは、宝探しのメモのようなものです。最初のメモに「次は図書館へ」と書いてあり、図書館のメモに「次は体育館へ」と書いてある、という形で次々にたどります。

各データは、値そのものに加えて「次のデータはどこにあるか」を持ちます。この「どこにあるか」を参照、またはポインタと呼びます。

```text
[データA | 次はB] -> [データB | 次はC] -> [データC | 次はなし]
```

途中に新しいデータを入れたいときは、全員をずらす必要はありません。矢印のつなぎ先を変えればよいのです。

```text
A -> B -> C

A -> B -> X -> C
```

このため、連結リストは途中への挿入や削除に強いです。一方で、100 番目のデータを直接取りに行くことはできません。先頭から 1 つずつ矢印をたどる必要があります。

連結リストは、途中への追加や削除が多いとき、データ数が頻繁に変わるとき、先頭から順に処理できればよいときに向きます。メモリ上で連続した場所を確保しにくい場合にも、参照でつなげられることが利点になります。

単方向リストは次だけ、双方向リストは前後両方を指します。循環リストは最後が先頭を指します。

```text
A -> B -> C
```

前には戻れません。軽く作れますが、逆方向の移動は苦手です。

```text
A <-> B <-> C
```

前後に移動できます。ブラウザの「戻る」「進む」のような操作に向きます。ただし、前後の参照を持つぶん管理は少し複雑になります。

```text
A -> B -> C -> A
```

最後が最初につながります。順番に何度も回す処理、たとえばラウンドロビン方式のように順番に処理を回す場面で考え方が使われます。

配列と連結リストの違いを、操作ごとに見るとこうなります。

| 操作 | 配列 | 連結リスト |
|---|---|---|
| `i` 番目を読む | 得意。番号で直接行ける | 苦手。先頭からたどる |
| 末尾に追加 | 比較的得意 | 得意。ただし末尾への参照を保持している場合 |
| 真ん中に挿入 | 苦手。後ろをずらす | 得意。参照を付け替える |
| 真ん中を削除 | 苦手。後ろをずらす | 得意。参照を付け替える |
| メモリ効率 | 参照が不要で効率的 | 次への参照ぶん余分に使う |

ここで大切なのは、「どちらが優れているか」ではありません。何をしたいかによって、向いている構造が変わるということです。

## リストによる木の表現

木構造は、各ノードに子への参照を持たせれば表現できます。2 分木なら、左の子と右の子への参照を持つだけです。

```text
node = {
  value,
  left,
  right
}
```

ポインタや添字を使って木を表すと、メモリ上のデータ構造として扱えます。`left` と `right` の番号を追えば、親子関係を復元できます。

完全 2 分木のように、上から順にすき間なくノードが並ぶ木は、配列でも表しやすくなります。完全 2 分木とは、最後の段を除いてすべて埋まっていて、最後の段も左から順に詰まっている 2 分木です。ヒープはこの形をよく使います。ヒープは、親が子より小さい、または親が子より大きいという性質を保つ木で、優先度付きキューの実装に使われます。

配列の添字を 1 から始めると、親子の位置を式で求められます。あるノードの添字を `i` とすると、

```text
左の子 = 2i
右の子 = 2i + 1
親 = floor(i / 2)
```

`floor` は小数点以下を切り捨てる関数です。なぜこの式になるかを、上から順に番号を振って考えます。根を 1 番にします。根の左の子は 2 番、右の子は 3 番です。2 番の左の子は 4 番、右の子は 5 番です。3 番の左の子は 6 番、右の子は 7 番です。

```text
        1
      /   \
     2     3
    / \   / \
   4   5 6   7
```

2 番の子を見ると、左は `2 × 2 = 4`、右は `2 × 2 + 1 = 5` です。3 番の子を見ると、左は `2 × 3 = 6`、右は `2 × 3 + 1 = 7` です。だから、一般に `i` 番の左の子は `2i`、右の子は `2i + 1` になります。

親を求める式も同じ番号から分かります。4 番と 5 番の親は 2 番です。`4 / 2 = 2`、`5 / 2 = 2.5` なので、小数点以下を切り捨てると 2 になります。6 番と 7 番の親は 3 番です。`6 / 2 = 3`、`7 / 2 = 3.5` で、切り捨てると 3 です。

この配列表現では、ポインタを持たなくても親子関係を計算できます。そのためメモリ効率が良く、ヒープのように「根の最小値または最大値を素早く取り出し、形を保ちながら並べ替える」構造に向きます。一方で、完全 2 分木の形から大きく外れる木や、途中にすき間が多い木では、配列の空きが増えたり、表現が不自然になったりします。木をポインタで持つか配列で持つかは、木の形と操作の性質で決めます。

## 2.2 スタックとキュー

スタックとキューは、「どの順番で処理するか」を決めるための考え方です。データをただ保存するだけでなく、「次に取り出すべきものはどれか」をルール化します。

たとえば、ブラウザの戻るボタンでは、直前に見たページへ戻りたいので、後から入った履歴を先に取り出します。これはスタックです。一方、プリンタの印刷待ちでは、先に依頼した人から印刷されるのが自然です。これはキューです。

この 2 つを学ぶと、順番待ち、履歴、Undo、タスク処理、探索アルゴリズムの動きが理解しやすくなります。

スタックは、後に入れたものを先に出します。LIFO は Last In, First Out の略で、「最後に入ったものが最初に出る」という意味です。スタックにデータを入れる操作を push、取り出す操作を pop と呼びます。机の上にプリントを積むと、最後に置いたプリントが一番上に来て、最初に取りやすくなります。これがスタックの感覚です。

スタックは、関数呼出し、括弧の対応、深さ優先探索、逆ポーランド記法で使われます。関数呼出しでは、後から呼ばれた関数が先に終わり、呼び出し元へ戻ります。括弧の対応では、開き括弧を積み、閉じ括弧が来たら直前の開き括弧と対応させます。「直前に始まったものを先に閉じる」のでスタックが合います。

逆ポーランド記法は、演算子を後ろに置く式の書き方です。普通の式 `3 + 4` は、逆ポーランド記法では `3 4 +` と書きます。`3 + 4 × 5` は、掛け算を先に行うので `3 4 5 × +` になります。

スタックで `3 4 5 × +` を計算してみます。数が来たらスタックに積みます。演算子が来たら、必要な個数だけ取り出して計算し、結果をまた積みます。

```text
3 を積む        -> [3]
4 を積む        -> [3, 4]
5 を積む        -> [3, 4, 5]
× が来る        -> 4 と 5 を取り出し、4 × 5 = 20 を積む -> [3, 20]
+ が来る        -> 3 と 20 を取り出し、3 + 20 = 23 を積む -> [23]
```

最後に残った 23 が答えです。逆ポーランド記法では括弧や演算子の優先順位をあいまいにせず、左から順に処理できます。コンパイラや電卓の内部処理を理解する入口にもなります。

キューは、先に入れたものを先に出します。FIFO は First In, First Out の略で、「最初に入ったものが最初に出る」という意味です。キューにデータを入れる操作を enqueue、取り出す操作を dequeue と呼びます。店の行列で、先に並んだ人から案内されるのがキューの感覚です。

キューは、プリンタの印刷待ち、タスク処理、幅優先探索で使われます。幅優先探索では、先に見つけた頂点から順に調べる必要があるため、キューに入れた順番がそのまま探索の順番になります。

優先度付きキューは、入った順番ではなく優先度で取り出します。ヒープで実装されることが多いです。

## グラフ探索

グラフ探索は、「つながりの中をどう進むか」を決める技術です。地図アプリの経路探索、SNS の友達関係、ゲームの迷路、Web ページのリンク巡回など、点と線で表せるものはたくさんあります。

ここで DFS と BFS を学ぶ理由は、同じ「探す」でも目的によって進み方が変わるからです。深く一気に進むのか、近いところから広げるのか。この違いは、探索結果と効率に直結します。

深さ優先探索 DFS は、行けるところまで進み、行き止まりになったら戻る探索です。最後に見つけた候補を先に調べるため、スタックと相性があります。迷路探索、トポロジカルソート、連結成分探索に使われます。幅優先探索 BFS は、近い頂点から順に調べる探索です。先に見つけた候補から順に調べるため、キューと相性があります。重みなしグラフの最短距離を求めるときに使われます。

DFS と BFS の違いは、「次に調べる候補をどの順番で保留するか」にあります。

DFS では、最後に見つけた分岐を先に調べます。後から入れたものを先に取り出すので、スタックと相性がよくなります。行けるところまで深く進み、行き止まりになったら直前の分岐へ戻ります。

BFS では、先に見つけた候補から順に調べます。先に入れたものを先に取り出すので、キューと相性がよくなります。出発点から距離 1 の場所、距離 2 の場所、距離 3 の場所というように、同心円状に広げていくイメージです。

ただし、BFS がそのまま最短距離を求められるのは、すべての辺を「1 歩」と見なせるときです。実際の道路では、A から B までは 2 分、B から C までは 30 分、A から C までは 10 分というように、辺ごとの重みが違います。このようなグラフを重み付きグラフと呼びます。重みは、距離、時間、料金、通信遅延、危険度など、「小さいほどよい」と考える量なら何でも表せます。

重み付きグラフで最短経路を求める代表的な方法がダイクストラ法です。ダイクストラ法は、出発点から各頂点までの「現時点で分かっている最短距離」を少しずつ改善し、もうこれ以上短くならない頂点を確定していきます。ここでいう確定とは、「この頂点までの最短距離はこれで決まり」と言える状態です。

たとえば、出発点 S から A まで 4、S から B まで 1、B から A まで 2 という道があるとします。最初に S から直接見える距離だけを見ると、A は 4、B は 1 です。しかし B まで 1 で行き、そこから A へ 2 で進むと、S から A までの合計は `1 + 2 = 3` になります。直接 A に行く 4 より小さいので、A までの暫定距離を 4 から 3 に更新します。

この更新を、緩和と呼びます。緩和という言葉は少し固いですが、意味は単純です。「いま知っている行き方より、もっと短い行き方を見つけたら、そちらに直す」という操作です。式で書くと、ある頂点 `u` までの最短距離候補を `dist[u]`、`u` から隣の頂点 `v` へ進む辺の重みを `weight(u, v)` としたとき、`v` までの新しい候補は次のようになります。

```text
新しい候補 = dist[u] + weight(u, v)
```

なぜ足し算なのかを丁寧に見ます。`dist[u]` は「出発点から u まで来るのに必要な合計」です。そこからさらに `u` から `v` へ移動するので、その分の `weight(u, v)` を追加します。だから、出発点から `u` を通って `v` に行く合計は `dist[u] + weight(u, v)` です。この値が、これまで知っていた `dist[v]` より小さければ、`dist[v]` を更新します。

```text
もし dist[u] + weight(u, v) < dist[v] なら、
dist[v] = dist[u] + weight(u, v) に更新する
```

この不等式は、「新しい行き方の合計が、古い候補より短いなら採用する」と読めます。左辺は `u` を経由して `v` に行く距離、右辺はこれまで知っていた `v` への最短距離候補です。左辺のほうが小さいと分かった瞬間に、右辺の値を左辺へ置き換えます。

ダイクストラ法では、まだ確定していない頂点のうち、暫定距離が最も小さいものを次に確定します。ここで優先度付きキューが役に立ちます。優先度付きキューに「距離が小さい頂点ほど先に出す」という規則を持たせると、次に確定すべき頂点を効率よく取り出せます。単純に全頂点を毎回探すと遅くなりますが、ヒープを使った優先度付きキューなら、候補の取り出しと更新を効率よく行えます。

ダイクストラ法が正しく働く重要な条件は、辺の重みが負でないことです。負の重みがあると、「あとから通ると合計が急に小さくなる道」が存在してしまいます。ダイクストラ法は、最も小さい暫定距離の頂点を「もう短くならない」と判断して確定するため、あとから負の辺でさらに小さくなる可能性があると、この判断が崩れます。負の重みを含む可能性がある場合は、ベルマンフォード法のように、辺の緩和を何度も繰り返して安全に調べる別の方法を使います。

ここまでをまとめると、BFS は「すべての道のコストが同じ」場合の近い順探索です。ダイクストラ法は、「道ごとにコストが違うが、コストは負ではない」場合に、距離の小さい候補から確定していく探索です。どちらも最短経路を扱いますが、前提が違います。前提を見抜けると、アルゴリズムをただ名前で選ぶのではなく、データの性質に合わせて選べるようになります。

## 2.3 木

木は、「階層」を扱うためのデータ構造です。高校生にとって身近な例なら、学校のフォルダ、家系図、部活動の組織図、Web ページの HTML 構造があります。

階層構造をリストだけで表そうとすると、「誰の下に誰がいるのか」「どのフォルダの中にどのファイルがあるのか」が分かりにくくなります。木を学ぶと、親子関係、入れ子、分類、探索を自然に扱えるようになります。

木は、階層構造を表すデータ構造です。一番上のノードを根と呼びます。子を持たないノードは葉です。ノード同士の上下関係は親・子、同じ親を持つノード同士は兄弟として表します。深さは根からの距離、高さは最も深い葉までの距離です。

2 分木は、各ノードの子が最大 2 つの木です。

完全 2 分木は、上から左詰めで埋まった 2 分木です。前に見たように、完全 2 分木は配列で親子関係を計算しやすいため、ヒープでよく使われます。ここでは、完全 2 分木そのものを「形の制約」として理解します。すき間なく左から詰まっているから、どの位置の親子関係も番号で追えるのです。

## 2 分探索木

2 分探索木では、左部分木は自分より小さく、右部分木は自分より大きい値を持ちます。探索するときは、まず根を見ます。探す値が現在のノードより小さければ左へ、大きければ右へ進みます。見つかるか、葉を越えて「もう候補がない」と分かったら終了です。

木がバランスしていれば探索は `O(log n)` です。ただし、値が昇順に入ると一直線になり、`O(n)` まで悪化します。そこで AVL 木や赤黒木のような平衡木が使われます。

バランスしている木とは、左右の高さが大きく偏っていない木です。2 分探索木は、値の大小で左右に進むので、1 回進むたびに候補が大きく減るほど速くなります。理想的には、候補がだいたい半分ずつ減るため `O(log n)` になります。しかし `1, 2, 3, 4, 5` のように昇順で挿入すると、右の子ばかりにつながり、連結リストのような形になります。この場合、探すたびにほぼ全部をたどることになり、`O(n)` に悪化します。

平衡木は、この偏りを直すために回転という操作を使います。回転は、木の探索順序を壊さずに、親子関係を組み替えて高さをならす操作です。たとえば右に偏りすぎた木では、中央に近いノードを上へ持ち上げ、左右の高さを近づけます。ここで重要なのは、値の大小関係は保ったまま形だけを整えることです。だから、探索木としての性質を維持しながら、探索、挿入、削除を `O(log n)` に近づけられます。

AVL 木は高さの差を厳しく管理するため、探索は安定しやすい一方、更新時の回転が増えることがあります。赤黒木は、色のルールでおおまかにバランスを保つため、実装や更新性能のバランスがよく、多くの標準ライブラリやOS内部のデータ構造で使われます。高度な理解では、「平衡木は速い木の名前」ではなく、「入力順によって探索木が劣化する問題を、構造の自動調整で防ぐ仕組み」と捉えます。

## 2.4 探索アルゴリズム

探索は、「欲しいものをどう見つけるか」です。名簿から生徒を探す、商品コードから価格を探す、ゲームで目的地への道を探す、ログからエラーを探す。IT の多くは探索をしています。

探索を学ぶ理由は、探し方によって速さが大きく変わるからです。100 件なら順番に見ても困りません。しかし 1 億件から毎秒探すなら、線形探索では間に合わないことがあります。

線形探索は、先頭から順に見る方法です。整列されていなくても使えますが、最悪の場合は最後まで見るので計算量は `O(n)` です。2 分探索は、整列済みのデータで使う方法です。中央と比較し、候補を半分ずつ減らすため、計算量は `O(log n)` になります。

2 分探索の注意点は、データが整列済みであることです。整列されていない配列に 2 分探索は使えません。

なぜ 2 分探索が `O(log n)` になるのかを、式を省かずに見ます。候補が `n` 個あるとして、1 回比較すると候補は半分になります。2 回比較すると、さらに半分なので `n / 2 / 2 = n / 4` 個です。これは `n / 2^2` と書けます。3 回なら `n / 2^3` です。

`k` 回比較した後の候補数は、次のように表せます。

```text
候補数 = n / 2^k
```

探索が終わるには、候補が 1 個以下になればよいので、

```text
n / 2^k <= 1
```

この不等式を変形します。両辺に `2^k` を掛けます。`2^k` は正の数なので、不等号の向きは変わりません。

```text
n <= 2^k
```

これは「2 を k 回掛けた数が n 以上になればよい」という意味です。そこで、`k` は `log2 n` 以上になります。`log2 n` は、「2 を何乗したら n になるか」を表す数です。

```text
k >= log2 n
```

たとえば `n = 1024` なら、`1024 = 2^10` です。つまり 2 を 10 回掛けると 1024 になります。

```text
log2 1024 = 10
```

だから 1024 個の整列済みデータでも、2 分探索なら最大でだいたい 10 回の比較で候補を 1 個まで絞れます。これが、線形探索の `O(n)` と 2 分探索の `O(log n)` の決定的な差です。

## ハッシュ法

ハッシュ法は、キーをハッシュ関数で配列の位置に変換します。平均的には `O(1)` で検索できます。

衝突とは、違うキーが同じ位置になることです。衝突が起きたとき、チェイン法では同じ位置にリストをぶら下げます。オープンアドレス法では、決まった規則で別の空き位置を探します。

ハッシュ法は速いですが、順序を保つのは苦手です。範囲検索や整列順の走査が必要なら、木構造の方が向きます。

ハッシュ表の性能では、負荷率も大切です。負荷率は、表の大きさに対して、どれくらい要素が入っているかを表します。

```text
負荷率 = 登録されている要素数 / ハッシュ表のサイズ
```

ハッシュ表のサイズが 1000、登録されている要素数が 700 なら、次のように計算します。

```text
負荷率 = 700 / 1000
       = 0.7
```

`0.7` は 70% という意味です。割合を百分率に直すには 100 を掛けます。

```text
0.7 × 100 = 70
```

負荷率が高くなると、空き場所が減り、衝突が増えやすくなります。チェイン法では 1 つの場所にぶら下がるリストが長くなり、オープンアドレス法では次の空き場所を探す回数が増えます。平均 `O(1)` は「いつでも必ず 1 回で見つかる」という意味ではありません。よいハッシュ関数、適切な表サイズ、負荷率の管理がそろって初めて近づける性能です。

## オーダ記法

オーダ記法は、アルゴリズムの「伸び方」を見るための道具です。何秒かかるかは CPU や環境によって変わりますが、データが 10 倍になったとき処理が 10 倍で済むのか、100 倍になるのか、もっと爆発するのかは設計段階で知っておきたい情報です。

この考え方を知らないと、小さいテストデータでは動いたプログラムが、本番データで急に使いものにならない、ということが起きます。

オーダは、入力数 `n` が増えたときの増え方を表します。

`O(n)` の `O` はオーダと読みます。大まかな増え方を見る記号です。`n` はデータの個数で、名簿なら人数、配列なら要素数です。`O(n)` は、データが 2 倍なら処理量もだいたい 2 倍になる、という意味です。

`O(log n)` は、データが増えても処理量がゆっくりしか増えないことを表します。2 分探索のように、毎回候補を半分に減らせる処理で出てきます。

`O(n^2)` は、データが 2 倍になると処理量が約 4 倍になる、という意味です。2 重ループで全組合せを比べる処理でよく出ます。

```text
O(1) < O(log n) < O(n) < O(n log n) < O(n^2) < O(2^n)
```

代表的な増え方を小さい順に並べると、このようになります。`n` が小さいと差が見えにくくても、`n` が大きくなると差が爆発します。実装では、ループの入れ子、データ構造、I/O 回数を見て、処理が将来のデータ量に耐えるか判断します。

たとえば次のような 2 重ループを考えます。

```text
for i in 1..n
  for j in 1..n
    処理
```

これは `n × n` 回なので `O(n^2)` です。

Big-O では、細かい定数や低次の項を捨てて、入力が大きくなったときに支配的になる部分を見ます。たとえば処理回数が次の式で表せるとします。

```text
3n^2 + 10n + 50
```

`n` が小さいときは `10n` や `50` も見えます。しかし `n` が大きくなると、`n^2` の増え方が一番強くなります。実際に `n = 1000` を入れてみます。

```text
3n^2 = 3 × 1000^2
```

`1000^2` は `1000 × 1000` なので、

```text
1000^2 = 1,000,000
3n^2 = 3 × 1,000,000
     = 3,000,000
```

残りも計算します。

```text
10n = 10 × 1000
    = 10,000
```

定数項は 50 です。全部を足すと、

```text
3,000,000 + 10,000 + 50 = 3,010,050
```

全体のほとんどは `3n^2` です。さらに Big-O では、定数倍の `3` も捨てます。なぜなら、入力が増えたときの伸び方を比べたいからです。`3n^2` も `100n^2` も、入力を 2 倍にするとおおよそ 4 倍になります。したがって、この処理は `O(n^2)` と見ます。

## 2.5 整列アルゴリズム

整列は、データを決まった順番に並べることです。成績順、日付順、価格順、名前順、人気順など、一覧を見やすくしたり、後で探しやすくしたりするために使います。

整列を学ぶ理由は、並べ替えが単独で便利なだけでなく、検索や集計の前処理にもなるからです。たとえば、データが整列済みなら 2 分探索が使えます。重複データも、並んでいれば見つけやすくなります。

基本的な整列では、バブルソート、選択ソート、挿入ソートを理解します。バブルソートは隣同士を比較して交換する単純な方法ですが、データが多いと遅くなります。選択ソートは最小値を探して先頭へ置きます。挿入ソートは、整列済み部分に 1 個ずつ挿入します。ほぼ整列済みなら速く動きます。

整列法を比べるときは、平均計算量だけでなく、最悪計算量、安定性、追加メモリ、元データがほぼ整列済みかどうかを見ます。バブルソートや選択ソートは理解しやすいですが、基本的には `O(n^2)` です。挿入ソートも最悪は `O(n^2)` ですが、ほぼ整列済みのデータでは動かす量が少なく、実際には速いことがあります。

安定性は、同じキーを持つデータの元の順序を保つ性質です。たとえば、先に学年で並べ、その後クラスで安定ソートすると、同じクラスの中では学年順が残ります。追加メモリも重要です。マージソートは安定で性能も読みやすい一方、併合用の作業領域が必要です。ヒープソートは追加メモリを抑えやすいですが、安定ではありません。クイックソートは平均的に速いですが、基準値の選び方で最悪性能が悪くなります。現実のライブラリでは、こうした特徴を組み合わせたハイブリッドなソートが使われることもあります。

より大きなデータでは、クイックソート、マージソート、ヒープソートの考え方が重要です。クイックソートは基準値で分割して再帰的に整列します。平均は `O(n log n)` ですが、基準値の選び方が悪いと最悪 `O(n^2)` になります。マージソートは半分に分けて整列し、最後に併合します。常に `O(n log n)` ですが、追加メモリが必要です。ヒープソートはヒープを使って整列し、`O(n log n)` で追加メモリが少ない方法です。

安定ソートとは、同じキーのデータの元の順序が保たれるソートです。名簿を「学年で並べた後、クラスで安定ソート」すると、クラス内で学年順が残る、という使い方ができます。

マージソートがなぜ `O(n log n)` になるのかを、分割と併合で考えます。データを半分に分け続けると、1 個ずつになるまでに何段必要かは、2 分探索と同じく `log2 n` 段です。各段では、全体として `n` 個の要素を併合します。たとえば 8 個なら、下の段では 1 個同士を合わせ、次の段では 2 個同士を合わせ、最後に 4 個同士を合わせます。各段で見れば、要素は合計 8 個ぶん処理されます。

```text
1段あたりの処理量 = n
段数 = log2 n
全体の処理量 = n × log2 n
```

だから `O(n log n)` です。式の `log2 n` は「半分に分け続けたとき、1 個になるまでの段数」です。`n` は「各段で合計何個の要素を見るか」です。この 2 つを掛けるので、`n log n` になります。

クイックソートも、基準値でほぼ半分に分け続けられるなら平均的に `O(n log n)` になります。しかし基準値が毎回最小値や最大値に近いと、片方にほとんど全部が残ります。すると分割が半分ではなく、`n - 1` 個と 0 個のように偏ります。この場合、比較回数はおおよそ次の合計になります。

```text
(n - 1) + (n - 2) + ... + 1
```

この和は、1 から `n - 1` までの合計と同じです。1 から `m` までの合計は `m(m + 1) / 2` なので、ここでは `m = n - 1` と置けます。

```text
1 + 2 + ... + (n - 1) = (n - 1)n / 2
```

展開すると、

```text
(n - 1)n / 2 = (n^2 - n) / 2
             = 1/2 n^2 - 1/2 n
```

Big-O では支配的な `n^2` を見るため、最悪の場合は `O(n^2)` になります。クイックソートの基準値選びが重要なのは、このためです。

## 2.6 再帰法

再帰は、「同じ形の小さな問題に分ける」考え方です。最初は不思議に見えますが、フォルダの中にフォルダがある、木の枝の先にまた枝がある、数式の中に同じ形の式がある、という入れ子構造ではとても自然です。

再帰を学ぶと、木構造、ファイル探索、構文解析、分割統治アルゴリズムを理解しやすくなります。

再帰は、自分自身を呼び出す方法です。重要なのは、必ず終了条件を持つことです。階乗を求める関数なら、`n! = n × (n - 1)!` という形で、同じ形の小さい問題に分けられます。

```text
fact(n)
  if n == 0
    return 1
  return n * fact(n - 1)
```

再帰を読むときは、基底条件が何かを最初に確認します。基底条件とは、それ以上自分を呼ばずに答えを返す条件です。次に、呼び出すたびに問題が小さくなっているかを見ます。最後に、小さな問題の答えをどう合成して全体の答えに戻しているかを追います。

再帰は木やグラフ、分割統治と相性がよいです。ただし呼出しごとにスタックを使うため、深すぎるとスタックオーバーフローが起きます。

階乗 `fact(3)` を、呼び出しの積み重なりとして追ってみます。

```text
fact(3)
= 3 × fact(2)
= 3 × (2 × fact(1))
= 3 × (2 × (1 × fact(0)))
```

ここで `fact(0)` は基底条件なので `1` を返します。

```text
= 3 × (2 × (1 × 1))
```

内側から計算します。

```text
1 × 1 = 1
2 × 1 = 2
3 × 2 = 6
```

したがって、

```text
fact(3) = 6
```

再帰を読むときに大切なのは、「呼び出しが先に深く進み、基底条件に到達してから戻りながら答えを合成する」という時間の流れです。スタックは、この途中の計算を保持するために使われます。`fact(3)` は `3 × fact(2)` の `3 ×` の部分を保持したまま `fact(2)` を待ちます。同じように `fact(2)` は `2 ×` を保持したまま `fact(1)` を待ちます。深すぎる再帰でスタックオーバーフローが起きるのは、この「待っている途中計算」が積み上がりすぎるからです。

## 分割統治、貪欲法、動的計画法

少し発展すると、アルゴリズムは「問題をどう分け、どう決めるか」という設計パターンで見られます。分割統治は、問題を独立した小問題に分け、それぞれを解いてから結合します。マージソートや 2 分探索はこの考え方です。

貪欲法は、その時点で最もよさそうな選択を積み重ねる方法です。たとえば「毎回いちばん早く終わる予定を選ぶ」といったスケジューリングではうまくいく場合があります。ただし、目先の最善が全体の最善になるとは限りません。貪欲法を使うには、「局所的な最善を選び続けても全体最適になる」性質を確認する必要があります。

動的計画法は、同じ小問題を何度も解かないように、答えを保存して再利用する方法です。フィボナッチ数を例にします。

```text
F(n) = F(n - 1) + F(n - 2)
F(0) = 0
F(1) = 1
```

普通に再帰で `F(5)` を計算すると、`F(3)` や `F(2)` が何度も出てきます。

```text
F(5) = F(4) + F(3)
F(4) = F(3) + F(2)
F(3) = F(2) + F(1)
```

ここで `F(3)` が重複しています。さらに `F(2)` も何度も出ます。動的計画法では、一度求めた `F(2)` や `F(3)` を表に保存します。次に必要になったら再計算せず、表から取り出します。

小さい方から計算すると、流れはこうなります。

```text
F(0) = 0
F(1) = 1
F(2) = F(1) + F(0) = 1 + 0 = 1
F(3) = F(2) + F(1) = 1 + 1 = 2
F(4) = F(3) + F(2) = 2 + 1 = 3
F(5) = F(4) + F(3) = 3 + 2 = 5
```

動的計画法の本質は、難しい公式を使うことではありません。「同じ小問題が何度も出るなら、その答えを保存して再利用する」という考え方です。経路の最短距離、文字列の類似度、ナップサック問題など、多くの高度なアルゴリズムで使われます。

貪欲法と動的計画法の違いは、コインの枚数を最小にする問題で見ると分かりやすくなります。使えるコインが `1円, 3円, 4円` で、合計 6 円を作りたいとします。

貪欲法なら、その時点で一番大きく使えるコインを選びます。

```text
6円を作る
まず 4円を選ぶ。残りは 6 - 4 = 2円
残り 2円では 3円も4円も使えないので、1円を選ぶ。残りは 2 - 1 = 1円
もう一度 1円を選ぶ。残りは 1 - 1 = 0円
```

結果は `4円 + 1円 + 1円` で 3 枚です。しかし最適解は `3円 + 3円` の 2 枚です。つまり、「今いちばん大きいコインを選ぶ」という局所的な最善は、このコイン体系では全体最適になりません。

動的計画法では、6 円だけをいきなり考えず、0 円、1 円、2 円、3 円と小さい金額から最小枚数を表にします。ここでは `dp[x]` を「x 円を作るための最小枚数」とします。`dp` は dynamic programming の略としてよく使われる名前です。

0 円を作るにはコインがいらないので、

```text
dp[0] = 0
```

です。1 円を作るには 1 円コインを 1 枚足します。

```text
dp[1] = dp[1 - 1] + 1
      = dp[0] + 1
      = 0 + 1
      = 1
```

2 円は、1 円を作る最小枚数に 1 円コインを足します。

```text
dp[2] = dp[2 - 1] + 1
      = dp[1] + 1
      = 1 + 1
      = 2
```

3 円では、1 円コインを使う方法と 3 円コインを使う方法を比べます。`min` は最小値を選ぶ関数です。

```text
1円を最後に使う場合: dp[3 - 1] + 1 = dp[2] + 1 = 2 + 1 = 3
3円を最後に使う場合: dp[3 - 3] + 1 = dp[0] + 1 = 0 + 1 = 1
dp[3] = min(3, 1) = 1
```

4 円では、1 円、3 円、4 円のどれを最後に使うかを比べます。

```text
1円を最後に使う場合: dp[4 - 1] + 1 = dp[3] + 1 = 1 + 1 = 2
3円を最後に使う場合: dp[4 - 3] + 1 = dp[1] + 1 = 1 + 1 = 2
4円を最後に使う場合: dp[4 - 4] + 1 = dp[0] + 1 = 0 + 1 = 1
dp[4] = min(2, 2, 1) = 1
```

5 円では、

```text
1円を最後に使う場合: dp[5 - 1] + 1 = dp[4] + 1 = 1 + 1 = 2
3円を最後に使う場合: dp[5 - 3] + 1 = dp[2] + 1 = 2 + 1 = 3
4円を最後に使う場合: dp[5 - 4] + 1 = dp[1] + 1 = 1 + 1 = 2
dp[5] = min(2, 3, 2) = 2
```

6 円では、

```text
1円を最後に使う場合: dp[6 - 1] + 1 = dp[5] + 1 = 2 + 1 = 3
3円を最後に使う場合: dp[6 - 3] + 1 = dp[3] + 1 = 1 + 1 = 2
4円を最後に使う場合: dp[6 - 4] + 1 = dp[2] + 1 = 2 + 1 = 3
dp[6] = min(3, 2, 3) = 2
```

したがって、6 円を作る最小枚数は 2 枚です。貪欲法では 3 枚になりましたが、動的計画法では `dp[3]` などの小さい問題の答えを使い、正しく 2 枚にたどり着きました。

この式の読み方は、「最後にどのコインを使ったか」で場合分けしている、と考えると分かります。たとえば最後に 3 円コインを使って 6 円を作るなら、その直前には 3 円を作れていればよいです。だから `dp[6 - 3] + 1` になります。`+ 1` は、最後に足した 3 円コイン 1 枚ぶんです。

一般化すると、使えるコインを `coin` として、

```text
dp[x] = min(dp[x - coin] + 1)
```

と書けます。ただし、`x - coin` が 0 以上になるコインだけを考えます。高校生がここでつまずきやすいのは、なぜ `dp[x - coin]` を見るのかです。理由は、合計 `x` 円の最後の 1 枚を `coin` 円だと決めたら、その前に作るべき金額は `x - coin` 円だからです。最後の 1 枚を外すと、残りの問題が小さい同じ形の問題になるのです。

動的計画法が使いやすい問題には、2 つの特徴があります。1 つ目は、最適解が小さい問題の最適解から作れることです。これを最適部分構造といいます。2 つ目は、同じ小問題が何度も出てくることです。これを重複部分問題といいます。この 2 つがあるなら、再帰で何度も解くより、表に保存して再利用する価値があります。

ここからさらに一段進むと、「そもそも効率よく解ける問題なのか」という視点が必要になります。現実の IT では、正しい答えを出すだけでなく、限られた時間で答えを出す必要があります。入力が少ないときだけ動く方法では、大規模サービスや物流、暗号、AI の探索には使えません。

多項式時間で解ける問題は、入力サイズを `n` としたとき、計算量が `n`、`n^2`、`n^3` のような形で上から押さえられる問題です。たとえば `n^2` は、`n` を 10 倍にすると計算量が約 100 倍になります。増え方は大きいですが、指数的な増え方よりはずっと扱いやすいです。

一方、`2^n` のような指数時間は急激に増えます。なぜなら、`n` が 1 増えるたびに候補数が 2 倍になるからです。`2^10 = 1024` ならまだ扱えそうですが、`2^30` は `1073741824`、つまり約 10 億です。ここでの式変形は、2 を 30 個掛けるという意味です。

```text
2^30 = 2 × 2 × ... × 2
```

10 個分なら、

```text
2^10 = 1024
```

です。30 個分は `2^10` が 3 回分なので、

```text
2^30 = 2^10 × 2^10 × 2^10
     = 1024 × 1024 × 1024
     = 1073741824
```

となります。入力が少し増えただけで、候補を全部試す方法が現実的でなくなる理由が見えます。

P は、多項式時間で解ける問題の集まりです。NP は、答えの候補を渡されたときに、それが正しいかを多項式時間で確認できる問題の集まりです。ここで大事なのは、「答えを見つけること」と「答えが正しいと確認すること」は違うという点です。たとえば、複雑な時間割を作るのは大変でも、完成した時間割を見て「同じ先生が同時に 2 クラスを担当していないか」「教室が重なっていないか」を確認するのは比較的しやすい場合があります。

NP 完全問題は、NP の中でも特に中心的な難しさを持つ問題です。巡回セールスマン問題、充足可能性問題、ナップサック問題の一部などが関係します。高度な実務では、NP 完全という名前を知ることより、「全探索で完全な最適解を出そうとすると現実的でないかもしれない」と判断できることが大切です。その場合、近似アルゴリズム、貪欲法、動的計画法、枝刈り、制約プログラミング、ヒューリスティックを使い、どれくらい良い解をどれくらいの時間で得たいのかを設計します。

## 2.7 プログラム言語

プログラム言語は、人間の考えをコンピュータへ伝えるための言葉です。ただし、どの言語も同じ考え方で作られているわけではありません。手順を重視する言語、もの同士の関係を重視する言語、関数の組合せを重視する言語があります。

言語の分類を学ぶ理由は、目的に合った考え方を選ぶためです。業務アプリ、AI、組込み、Web、データ分析では、向いている書き方や言語の性質が違います。

プログラム言語は、抽象化の仕方で分類できます。手続き型は、手順を順番に書く考え方で、C などが代表例です。オブジェクト指向は、データと操作をオブジェクトにまとめます。Java などでよく使われます。関数型は、関数の合成や値の変換を重視します。論理型は、事実と規則から推論します。

どの言語でも、基本的な制御構造は重要です。順次は上から順に実行すること、選択は `if` や `case` で条件により分岐すること、反復は `for` や `while` で繰り返すことです。例外処理は、通常でない事態を別経路で扱う仕組みです。

言語の特性を見るときは、単に「C は手続き型」「Java はオブジェクト指向」のように分類するだけでは足りません。型、メモリ管理、副作用、並行処理、実行方式が、バグの出方や保守性に影響します。

型は、値の種類です。整数、文字列、真偽値、日付、利用者オブジェクトなどを区別します。静的型付けの言語では、実行前に型の不整合を多く見つけられます。たとえば数値に文字列を足そうとしたり、存在しないメソッドを呼ぼうとしたりすると、コンパイル時に検出できる場合があります。動的型付けの言語では、実行時の柔軟性が高い一方、型の間違いが実行して初めて表面化することがあります。どちらが常に上という話ではなく、開発速度、規模、テスト、チームの経験で向き不向きが変わります。

副作用とは、関数や処理が、戻り値を返す以外に外の状態を変えることです。変数を書き換える、ファイルへ保存する、画面に表示する、ネットワークへ送る、データベースを更新する、といった動きです。副作用が多い処理は、実行順序や呼び出し回数に依存しやすく、テストも難しくなります。関数型の考え方が重視されるのは、副作用を減らし、同じ入力なら同じ出力になる部分を増やすと、並行処理やテストがしやすくなるからです。

実行方式も言語の特性です。コンパイル方式では、人間が書いたソースコードを、実行前に機械語や中間コードへ変換します。実行前に多くの検査をしやすく、実行時の効率も高くしやすい一方、ビルドという変換作業が必要です。インタプリタ方式では、ソースコードや中間表現を実行しながら解釈します。試しながら開発しやすい一方、実行時に解釈の負担が出ることがあります。現代の言語処理系では、最初は中間コードへ変換し、よく使う部分を JIT コンパイルするように、複数の方式を組み合わせることもあります。JIT は Just-In-Time の略で、実行時に必要になった部分を機械語へ変換する方式です。

メモリ管理も、プログラムの安全性と性能に関わります。C のように開発者が明示的にメモリを確保・解放する言語では、不要になった領域を解放し忘れるメモリリークや、解放済みの領域を使ってしまう危険があります。ガベージコレクションを持つ言語では、使われなくなったオブジェクトを実行環境が回収します。これにより多くのメモリ管理ミスを減らせますが、回収のタイミングによって一時的に処理が止まったり、メモリ使用量が増えたりすることがあります。安全性と性能は、言語の機能だけでなく、実行環境の設計にも左右されます。

値渡しと参照渡しも、バグの原因になりやすい考え方です。値渡しは、関数へ値のコピーを渡す考え方です。関数の中で変更しても、元の値には影響しません。参照渡しは、データそのものへの参照を渡す考え方です。関数の中で変更すると、呼び出し元から見えるデータも変わることがあります。たとえば、名簿リストを関数に渡して並べ替えたとき、元の名簿まで順序が変わるなら、参照を通じて同じデータを触っている可能性があります。大きなデータを毎回コピーすると遅くなる一方、参照で共有すると意図しない変更が起きることがあります。

例外処理は、エラーを「どこで検出し、どこで回復し、どこで利用者へ伝えるか」を設計する仕組みです。例外を全部握りつぶしてしまうと、処理が失敗したのに成功したように見えます。逆に、下位の細かいエラーをそのまま利用者へ出すと、意味が分からなかったり、内部情報を漏らしたりします。良い設計では、低い層で技術的な原因を記録し、上位の層で利用者に分かるメッセージへ変換します。

並行処理と並列処理も区別します。並行処理は、複数の仕事を同じ期間に扱うことです。1 つの CPU で短く切り替えながら処理しても並行です。並列処理は、複数の CPU コアなどで本当に同時に実行することです。Web サーバが多くの利用者のリクエストを扱うときは並行性が重要です。画像処理や機械学習の行列計算では並列性が重要です。言語やライブラリが、スレッド、非同期処理、イベントループ、プロセス、GPU 実行をどう扱うかは、性能と安全性に直接関わります。

## 実務で使える理解

- データ構造の問題は、操作が「検索」「挿入」「削除」「順序保持」のどれを重視しているかで選ぶ。
- DFS/BFS は、探索候補を「後入れ先出し」で持つか「先入れ先出し」で持つかから動きを説明する。
- 2 分探索は「整列済み」が条件。
- ハッシュは平均 `O(1)` だが、衝突と順序の問題がある。
- ソートは、平均計算量、最悪計算量、安定性、追加メモリを見比べる。
- 再帰は、終了条件と問題サイズの減少を確認する。
- 貪欲法は局所最適が全体最適になる条件を確認し、動的計画法は小問題の答えを表に保存して再利用する。
- プログラム言語は、分類名だけでなく、型、実行方式、メモリ管理、副作用、値渡しと参照渡しが設計に与える影響で見る。

## 自分の言葉で説明する

- 配列と連結リストの長所短所を説明できる。
- スタックとキューの違いを、具体例で説明できる。
- DFS と BFS の使いどころを、探索順序と目的の違いから説明できる。
- 2 分探索木が偏るとなぜ遅くなるか説明できる。
- ハッシュ衝突の解決方法を 2 つ説明できる。
- `O(n log n)` と `O(n^2)` の差を説明できる。
- 主要ソートの特徴を比較できる。
- 再帰関数の基底条件を見つけられる。
- 貪欲法が失敗する例を説明できる。
- 動的計画法の `dp[x] = min(dp[x - coin] + 1)` を、最後に使うコインという考え方で説明できる。
- 最適部分構造と重複部分問題を、具体例で説明できる。
- コンパイル方式、インタプリタ方式、JIT コンパイルの違いを説明できる。
- ガベージコレクションの利点と、性能上の注意点を説明できる。
- 値渡しと参照渡しの違いを、意図しない変更の観点で説明できる。

## 深く身につけるための補講

アルゴリズムの本質は、速いプログラムを書くことだけではありません。「データが増えても破綻しない考え方」を身につけることです。

同じ機能でも、データ量が 100 件なら何でも動きます。100 万件、1 億件になると、選んだデータ構造と計算量がそのままシステムの限界になります。

## データ構造は、未来の操作を予測して選ぶ

データ構造を選ぶときは、保存する形だけでなく、あとで何をしたいかを考えます。

| やりたいこと | 向く構造 | 理由 |
|---|---|---|
| 添字で高速に読む | 配列 | 位置が分かれば直接アクセスできる |
| 途中に頻繁に挿入する | 連結リスト | 参照の付け替えで済む |
| 最近入れたものから戻す | スタック | LIFO が自然 |
| 到着順に処理する | キュー | FIFO が自然 |
| 最小値・最大値をすぐ取り出す | ヒープ | 優先度付きキューを効率よく実装できる |
| キーで高速検索する | ハッシュ表 | 平均 `O(1)` で探せる |
| 範囲検索や順序走査をする | 平衡木 | 順序を保ちながら `O(log n)` で操作できる |

高度な理解では、「この構造は何が速く、何を犠牲にしているか」を説明できる必要があります。

## 計算量を身体感覚にする

`O(n^2)` は、入力が 10 倍になると処理量が約 100 倍になります。`O(n log n)` はずっと穏やかです。

例として、1 回の基本処理が 1 マイクロ秒だとします。

| n | O(n) | O(n log2 n) | O(n^2) |
|---:|---:|---:|---:|
| 1,000 | 0.001 秒 | 約 0.010 秒 | 1 秒 |
| 100,000 | 0.1 秒 | 約 1.7 秒 | 約 2.8 時間 |
| 10,000,000 | 10 秒 | 約 232 秒 | 約 3 年 |

この表を見ると、計算量は机上の理論ではなく、運用できるかどうかを決める現実的な制約だと分かります。

## 例で理解する: BFS と DFS の違い

駅の乗換を考えます。

ある駅から目的駅まで「乗換回数が最小」の経路を探したいなら BFS が自然です。近い駅から順に広げるので、最初に目的駅へ到達した経路が最短になります。

一方、迷路で「とにかく出口まで行ける経路を 1 つ見つけたい」なら DFS が自然です。行けるところまで深く進み、だめなら戻ります。

同じグラフ探索でも、目的が違えば選ぶアルゴリズムが違います。

## 再帰を理解するコツ

再帰は、慣れないと「自分を呼ぶ不思議な処理」に見えます。しかし本質は、問題を同じ形の小さい問題に分けることです。

たとえば、ディレクトリ内の全ファイルを数える処理は再帰で自然に書けます。

```text
count(dir)
  total = 0
  for item in dir
    if item is file
      total += 1
    if item is directory
      total += count(item)
  return total
```

ディレクトリの中にディレクトリがあり、その中にもディレクトリがあります。構造が入れ子なので、再帰が自然です。

再帰では、終了条件があるか、呼び出すたびに問題が小さくなっているか、戻り値をどう合成するか、深さが大きすぎてスタックを使い切らないかを必ず確認します。

## ありがちな誤解

- ハッシュ表は常に最強ではない。順序や範囲検索には弱い。
- 配列は古い構造ではない。CPU キャッシュに乗りやすく、実際には非常に速いことが多い。
- 再帰は必ず遅いわけではない。ただし呼出しコストとスタック深さを考える。
- クイックソートは平均では速いが、基準値の選び方が悪いと最悪 `O(n^2)`。
- Big-O は定数を無視する。小さいデータでは理論上遅い方法が実際には速いこともある。
- 貪欲法は「毎回よさそうに選ぶ」だけでは正しさを保証できない。
- 動的計画法は表を作る作業ではなく、同じ小問題を再利用する設計。
- ガベージコレクションがある言語でも、メモリやリソースを気にしなくてよいわけではない。
- 参照を渡すと常に悪いわけではない。コピーのコストと、意図しない変更の危険を両方見る。
