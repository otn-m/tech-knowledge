# 第5章 ソフトウェア

## この章の地図

ソフトウェアの章は、OS と開発環境が中心です。OS は、アプリケーションとハードウェアの間に立って、CPU、メモリ、ファイル、入出力を公平かつ安全に管理します。

この章で扱う内容は、一見すると名前が多く見えます。しかし中心にある問いは 1 つです。限られたコンピュータ資源を、複数のプログラムが同時に、安全に、効率よく使うにはどうすればよいか。プロセス、スレッド、スケジューリング、排他制御、仮想記憶、ファイル権限は、すべてこの問いへの答えです。

さらに、プログラムが CPU に実行されるまでには、コンパイラ、リンカ、ローダなどの変換と配置の仕組みが関わります。OSS では、ソースコードを利用できることと、どんな条件で配布・改変できるかを区別する必要があります。ソフトウェアを「動くもの」としてだけでなく、「資源を使い、他者と共存し、権利条件を持つもの」として見ていきます。

## なぜこの章を学ぶのか

アプリは、CPU やメモリやファイルを直接好き勝手に使っているわけではありません。OS が間に入り、複数のアプリが安全に同時実行できるように管理しています。

たとえば、音楽を流しながらブラウザを開き、チャット通知を受け取れるのは、OS が CPU の時間を細かく分け、メモリを守り、入出力を管理しているからです。アプリが固まっても他のアプリまで壊れにくいのは、プロセスの分離やメモリ保護があるからです。

この章を学ぶと、アプリの裏側で OS が何をしているか、なぜ排他制御が必要か、なぜメモリ不足で遅くなるか、なぜ OSS ライセンスを確認しなければならないかが分かります。

## 5.1 OS の構成と機能

この節を学ぶ理由は、OS がなければアプリが安全に動けないからです。アプリが直接ハードウェアを好き勝手に操作すると、他のアプリのデータを壊したり、システム全体を止めたりする危険があります。

OS の役割を理解すると、なぜ権限が必要か、なぜシステムコールを通すのか、なぜアプリが固まってもOS全体は動き続けられるのかが分かります。

OS は基本ソフトウェアです。基本というのは「簡単」という意味ではありません。他のアプリケーションが動く土台という意味です。アプリケーションがハードウェアを直接扱うと、危険で複雑になります。たとえば、ブラウザがディスクを自由に読み書きでき、ゲームが OS のメモリを書き換えられ、チャットアプリが別アプリの通信を盗み見られるなら、コンピュータは安心して使えません。

そこで OS は、資源管理と抽象化を行います。資源管理とは、CPU、メモリ、ファイル、入出力装置、ネットワークを、誰にどれだけ使わせるか調整することです。抽象化とは、複雑なハードウェアの違いを隠し、アプリからは共通の操作に見せることです。アプリはディスクの細かい制御を知らなくても、「ファイルを開く」「読み込む」「書き込む」といった操作でデータを扱えます。

プロセス管理では、実行中のプログラムに CPU の時間を割り当てます。メモリ管理では、各プロセスの領域を分け、他のプロセスや OS の領域を壊さないようにします。ファイル管理では、データを名前付きのまとまりとして保存し、権限や階層構造を管理します。入出力管理では、キーボード、画面、ディスク、ネットワークカードなどの装置の違いを吸収します。ユーザ管理とセキュリティ管理では、誰が何を実行でき、どのファイルを読めるかを制御します。

カーネルは OS の中心部分です。ハードウェアに近い機能を担当します。CPU には、危険な操作を許すカーネルモードと、アプリケーションを制限付きで動かすユーザモードがあります。カーネルモードでは、OS が特権命令を実行できます。特権命令とは、メモリ管理や入出力装置の制御のように、間違えるとシステム全体を壊し得る命令です。ユーザモードでは、アプリケーションは直接そのような命令を実行できません。

アプリケーションがファイルを読むときは、システムコールを通じて OS に依頼します。これにより、勝手に他人のメモリやデバイスを壊さないようにできます。

システムコールは、アプリが OS に「安全にやってほしいこと」を頼む入口です。たとえばアプリが `report.txt` を読みたいとします。アプリは自分で SSD の制御信号を出すのではなく、「このファイルを開きたい」「この範囲を読みたい」と OS に依頼します。このとき CPU はユーザモードからカーネルモードへ切り替わります。モードが切り替わるのは、ファイルやデバイスの操作が他のプロセスやシステム全体に影響し得るからです。

OS はまず、利用者やプロセスにそのファイルを読む権限があるか確認します。次に、ファイル名から実際の保存場所を調べます。ファイルの中身がすでにメモリ上のキャッシュにあれば、ディスクへ行かずに返せます。なければ、デバイスドライバに依頼してストレージから読み込みます。読み込みが終わると割込みで OS に知らされ、OS は待っていたプロセスを再び実行可能状態に戻します。

この一連の流れを見ると、システムコールは単なる関数呼び出しではないことが分かります。普通の関数呼び出しは同じプログラムの中で処理が移るだけですが、システムコールでは CPU の特権レベルが変わり、OS の検査、ファイルシステム、キャッシュ、デバイスドライバ、割込みが関わります。安全性を保つための門であり、ハードウェアの複雑さを隠すための窓でもあります。

## マイクロカーネルとモノリシックカーネル

モノリシックカーネルは、多くの OS 機能をカーネル内に持つ方式です。ファイルシステム、デバイスドライバ、ネットワーク機能などがカーネル空間で動くため、機能同士のやり取りは速くできます。一方で、カーネル内の不具合はシステム全体に影響しやすくなります。

マイクロカーネルは、カーネルをできるだけ小さくし、最小限のプロセス間通信、スケジューリング、低レベルのメモリ管理などに絞る考え方です。ファイルシステムやドライバの一部をユーザ空間のサーバとして動かすことで、保守性や信頼性を高めやすくなります。ただし、機能同士がメッセージをやり取りする回数が増えるため、通信オーバヘッドが問題になることがあります。

ここでのオーバヘッドとは、本来やりたい処理そのものではなく、それを実現するために余分に必要になる処理時間や手間のことです。たとえば、友達に直接話せば 1 秒で済む内容を、先生を通して伝えると時間がかかるようなものです。安全性や整理された構造を得る代わりに、少し手間が増える場合があります。

## 5.2 タスク管理

この節を学ぶ理由は、コンピュータが複数の作業を同時に進めているように見える仕組みを理解するためです。音楽再生、ブラウザ、通知、ダウンロードが同時に動く裏側では、OS が CPU の時間を細かく分けています。

タスク管理を学ぶと、プロセス、スレッド、スケジューリング、排他制御、デッドロックがつながります。並行処理のバグを理解するためにも重要です。

タスクまたはプロセスは、実行中のプログラムです。プロセスの状態は、「CPU さえもらえれば進めるのか」「いま CPU を使っているのか」「CPU ではなく別の出来事を待っているのか」で分かれます。実行可能状態のプロセスは、CPU が割り当てられれば実行できます。実行中状態のプロセスは、実際に CPU を使っています。待ち状態のプロセスは、入出力完了やロック解放などを待っていて、CPU をもらってもまだ進めません。

状態の移り変わりは、次のように読みます。

```text
実行可能 -> 実行中 -> 待ち
```

実行可能は、CPU が空けばすぐ動ける状態です。教室の前で順番待ちしている生徒に似ています。実行中は、実際に CPU を使っている状態です。待ちは、入出力完了やロック解放など、何かを待っていて CPU をもらっても進めない状態です。

状態遷移を読むときは、「CPU が欲しいのか」「何かを待っているのか」で判断します。

大切なのは、「待ち」と「実行可能」は違うことです。実行可能なプロセスは CPU を待っています。待ち状態のプロセスは、CPU ではなく別の出来事を待っています。

## スケジューリング

CPU は同時に多くのプロセスを実行しているように見えますが、実際には短い時間で切り替えています。どのプロセスに CPU を渡すかを決めるのがスケジューリングです。

FCFS は First Come First Served の略で、先に来たものから実行する方式です。行列に並んだ順番に処理するので単純ですが、最初にとても長い処理が来ると、後ろの短い処理が長く待たされます。

SJF は Shortest Job First の略で、実行時間が短いと予想されるものを先に実行する方式です。平均待ち時間を短くしやすい一方、実行時間を事前に正確に知るのが難しく、長い処理が後回しにされ続ける可能性があります。

ラウンドロビンは、時間片ごとに順番に CPU を渡す方式です。時間片とは、1 回に CPU を使わせる短い時間の区切りです。対話型のシステムでは、各アプリが少しずつ動くことで、利用者には同時に動いているように見えます。

優先度方式では、優先度の高いプロセスから実行します。緊急性の高い処理を先に進められますが、優先度の低い処理がいつまでも実行されない飢餓状態に注意が必要です。

ラウンドロビンでは、時間片が長すぎると FCFS に近づき、短すぎると切替オーバヘッドが増えます。

CPU を別のプロセスへ渡すとき、OS はコンテキストスイッチを行います。コンテキストとは、そのプロセスが再開するために必要な状態です。具体的には、プログラムカウンタ、レジスタの値、スタックポインタ、メモリ管理に関する情報などです。いま走っているプロセスの状態を保存し、次に走らせるプロセスの状態を復元することで、各プロセスは「自分が続きから動いている」と見えます。

プリエンプションは、実行中のプロセスから OS が CPU を取り上げられる仕組みです。タイマ割込みが一定時間ごとに発生し、OS は「このプロセスは時間片を使い終わったので、次のプロセスへ渡す」と判断できます。プリエンプションがないと、長い処理や無限ループに入った処理が CPU を握り続け、他のアプリが反応できなくなります。

ただし、切り替えは無料ではありません。コンテキストスイッチ中は、利用者の計算そのものは進みません。時間片を短くしすぎると反応はよく見えますが、保存と復元の回数が増えます。長くしすぎると切替回数は減りますが、対話型アプリの反応が悪くなります。スケジューリングは、公平性、応答性、スループット、オーバヘッドのバランスを取る設計です。

## 同期制御と排他制御

複数プロセスが同じデータを同時に更新すると、結果が壊れることがあります。これを競合状態といいます。たとえば銀行口座の残高を、2 つの処理が同時に更新する場面を考えます。

```text
残高 1000 円
A が 100 円引く
B が 200 円引く
```

2 つの処理が同時に古い残高を読んでしまうと、本来 700 円になるべきものが 800 円や 900 円になることがあります。

排他制御では、同時に入ってはいけない部分をクリティカルセクションとして、1 つのプロセスだけが入れるようにします。ロック、セマフォ、ミューテックス、モニタは、そのための代表的な仕組みです。

ロックは、ある処理が共有データを使っている間、他の処理を入れない札のようなものです。ミューテックスは mutual exclusion、つまり相互排除のためのロックで、基本的には 1 つの処理だけが所有します。セマフォは整数値で資源数を管理します。P 操作で確保し、V 操作で解放します。たとえば同時に 3 人まで使える会議室なら、セマフォの値を 3 から始め、使う人が P 操作で 1 減らし、使い終わった人が V 操作で 1 増やすと考えられます。モニタは、共有データとそれを操作する手続きをまとめ、外から同時に壊されにくくする仕組みです。

排他制御は、正しく使えばデータを守ります。しかし、使い方を誤ると、優先度の設計まで乱します。代表例が優先度逆転です。優先度逆転とは、本来はすぐ実行したい高優先度の処理が、低優先度の処理を待つせいで進めなくなる現象です。

たとえば、低優先度の処理 L が共有データのロックを持っているとします。そこへ高優先度の処理 H が来て、同じロックを必要としました。H は L がロックを返すまで待ちます。ここまでは自然です。ところが、その途中で中優先度の処理 M が CPU を使い続けると、L はロックを返すための実行時間をもらえません。結果として、H は M より優先度が高いのに、M のせいで間接的に待たされます。これが「優先度が逆転している」と呼ばれる理由です。

対策の 1 つに優先度継承があります。優先度継承では、高優先度の処理が待っているロックを低優先度の処理が持っている間だけ、その低優先度の処理を一時的に高優先度として扱います。そうすると L が早く実行され、ロックを返し、H が進めるようになります。ここで大切なのは、ロックは単なる「同時に入らせない道具」ではなく、スケジューリング、応答時間、リアルタイム性にまで影響する設計要素だということです。自動車制御、医療機器、ロボット、取引システムのように時間制約が厳しい場面では、排他制御の正しさだけでなく、待たされ方まで設計します。

## デッドロック

デッドロックは、複数プロセスが互いに資源を待ち続け、永久に進まない状態です。

デッドロックが起こる背景には、4 つの条件があります。これは名前だけを並べるより、「なぜ止まるのか」を資源の流れで見ると理解しやすくなります。

相互排除は、ある資源を同時に複数のプロセスが使えないことです。プリンタや更新中のファイルのように、同時に使うと壊れる資源では必要になります。

占有と待ちは、プロセスがすでに資源を持ったまま、さらに別の資源を待つことです。資源 X を持ったまま資源 Y を待つプロセスがいると、資源 X も他のプロセスには使えません。

横取り不可は、他のプロセスが持っている資源を強制的に奪えないことです。途中で無理に取り上げるとデータが壊れる資源では、この性質が必要になります。

循環待ちは、待ち関係が輪になることです。プロセス A が B の持つ資源を待ち、B が C の持つ資源を待ち、C が A の持つ資源を待つと、誰も先に進めません。

この 4 条件が同時に成立すると、デッドロックが起こり得ます。予防するには、どれか 1 つを崩します。たとえば、資源を必ず同じ順序で獲得すれば循環待ちを防げます。プリンタ、ファイル、データベース行を使うなら、すべての処理で「ファイルを取ってからプリンタを取る」のように順序をそろえます。

デッドロックと似た言葉に、飢餓状態とライブロックがあります。飢餓状態は、ある処理だけがいつまでも実行機会や資源を得られない状態です。全体としてシステムは動いているのに、優先度の低い処理や運の悪い処理だけが取り残されます。デッドロックでは関係する処理が互いに待って止まりますが、飢餓状態では他の処理は普通に進む点が違います。

ライブロックは、処理が止まってはいないのに、目的に近づかない状態です。たとえば 2 つの処理が衝突を避けようとして、どちらも相手に合わせて状態を変え続けるものの、結局どちらも資源を取れない場合です。見かけ上は CPU を使い、状態も変わるので、完全停止しているデッドロックより発見しにくいことがあります。並行処理の設計では、「動いているか」だけでなく、「完了へ進んでいるか」を見る必要があります。

## プロセスとスレッド

プロセスは、メモリ空間や資源を持つ実行単位です。スレッドは、プロセス内の実行の流れです。プロセスを「アプリが持つ作業部屋」だとすると、スレッドはその部屋の中で実際に作業する人に近いものです。同じプロセス内のスレッドはメモリを共有するため、データを渡しやすく、作成や切替もプロセスより軽くできます。その代わり、同じ変数やデータ構造を同時に触ると競合が起きます。

Web サーバでは、複数リクエストをスレッドで並行処理することがあります。

プロセスのメモリ空間は、いくつかの領域に分けて考えられます。プログラムの機械語命令を置く領域、グローバル変数を置く領域、動的に確保するヒープ、関数呼び出しや局所変数に使うスタックがあります。ヒープは、実行中に必要になったデータ構造を置く場所です。スタックは、関数が呼ばれるたびに積まれ、戻るときに取り除かれる作業メモのような領域です。

別々のプロセスは、基本的には別々のメモリ空間を持ちます。そのため、片方が不正な番地へ書き込んでも、OS の保護が働けば他方のメモリまでは壊しません。一方、同じプロセス内のスレッドは、ヒープやグローバル変数を共有します。共有できるから高速に協力できますが、同時に更新すると競合状態が起きます。スレッドは軽い実行単位ですが、設計は軽くありません。共有する範囲を理解し、必要な場所だけ排他制御することが重要です。

## 5.3 記憶管理

この節を学ぶ理由は、メモリが有限であり、しかも安全に分けて使う必要があるからです。複数のアプリが同じメモリを勝手に使うと、データ破壊やセキュリティ問題が起きます。

記憶管理を学ぶと、メモリ不足、スワップ、ページフォールト、仮想記憶、メモリ保護が理解できます。アプリが急に遅くなる原因を考えるときにも役立ちます。

実記憶管理は、主記憶をどう割り当てるかを扱います。固定区画方式では、メモリをあらかじめ固定サイズの区画に分けます。管理は単純ですが、小さいプログラムに大きな区画を割り当てると、区画の中に使われない部分が残ります。これが内部断片化です。「部屋を借りたけれど、部屋の中に空きスペースが余っている」状態です。

可変区画方式では、必要な大きさに合わせてメモリを割り当てます。無駄が少なく見えますが、割当てと解放を繰り返すと、小さな空き領域があちこちに散らばります。合計すれば十分な空きがあっても、連続した大きな領域がないため割り当てられないことがあります。これが外部断片化です。「空席はあるが、友達 5 人が並んで座れる席はない」状態に似ています。

メモリプール管理は、よく使う大きさのメモリ領域をあらかじめまとめて用意しておき、必要になったらそこから取り出して使う方法です。毎回 OS に細かくメモリを要求すると、管理の手間が増えたり、断片化が起きたりします。メモリプールを使うと、同じ大きさの領域を高速に確保・解放しやすくなります。ゲーム、組込み、サーバのように、短時間に多くの小さなオブジェクトを作って捨てる処理で役立ちます。ただし、プールの大きさを見誤ると、使われない領域が余ったり、必要なときに足りなくなったりします。

## 仮想記憶管理

仮想記憶は、実際の主記憶より大きなメモリ空間があるように見せる仕組みです。使っていないページを補助記憶へ退避します。ここでページとは、仮想アドレス空間を固定サイズに区切った単位です。実記憶側も同じようなサイズのページ枠に分け、ページ表で「仮想アドレス上のこのページは、実記憶のどのページ枠にあるか」を対応づけます。

必要なページが主記憶にないときは、補助記憶から読み込みます。この出来事をページフォールトといいます。フォールトは「故障」という意味で使われることもありますが、ここでは必ずしも異常終了ではなく、「必要なページがまだ主記憶にないので OS が取りに行く」という合図です。ページフォールトが多すぎると、CPU が計算する時間よりページの入替えを待つ時間が長くなり、スラッシングが起きます。

ページを入れる場所が足りないときは、どのページを追い出すかを決めます。FIFO は First In First Out の略で、先に入ったページを追い出します。LRU は Least Recently Used の略で、最も長く使われていないページを追い出します。LFU は Least Frequently Used の略で、使用頻度が低いページを追い出します。名前だけを追うより、「時間の古さで見るのか、最近使ったかで見るのか、頻度で見るのか」を区別するのが大切です。

仮想アドレスが実際の主記憶の番地へ変換される流れも押さえます。仮想アドレスは、ページ番号とページ内オフセットに分けられます。ページ番号は「何番目のページか」、ページ内オフセットは「そのページの先頭から何バイト進んだ位置か」です。

ページサイズが 4096 バイトで、仮想アドレスが 12345 だとします。まず 12345 が何番目のページに入るかを求めます。ページごとに 4096 バイトずつ区切るので、4096 で割った商がページ番号、余りがページ内オフセットです。

```text
ページ番号 = 12345 ÷ 4096 の商
```

`4096 × 3 = 12288` で、`4096 × 4 = 16384` は 12345 を超えます。したがって商は 3 です。余りは、元の番地から 3 ページ分を引いて求めます。

```text
ページ内オフセット = 12345 - 4096 × 3
                  = 12345 - 12288
                  = 57
```

つまり、仮想アドレス 12345 は「仮想ページ 3 の先頭から 57 バイト進んだ場所」です。ページ表を調べて、仮想ページ 3 が実記憶のページ枠 8 にあると分かったなら、物理アドレスは次のように求めます。

```text
物理アドレス = ページ枠番号 × ページサイズ + ページ内オフセット
```

値を入れます。

```text
物理アドレス = 8 × 4096 + 57
```

先に掛け算をします。

```text
8 × 4096 = 32768
```

そこへページ内オフセットを足します。

```text
物理アドレス = 32768 + 57
              = 32825
```

このように、ページ番号は変換されますが、ページ内のずれであるオフセットはそのまま使われます。ページの中で 57 バイト進んだ位置という事実は、仮想ページでも物理ページ枠でも変わらないからです。

毎回ページ表を主記憶まで見に行くと遅いので、CPU には TLB という小さな高速キャッシュがあります。TLB は、最近使った仮想ページ番号と物理ページ枠番号の対応を保持します。TLB に対応があれば速く変換でき、なければページ表を調べます。必要なページが主記憶になければページフォールトになり、OS が補助記憶から読み込みます。

ページフォールトが起きたとき、OS は現在の命令をいったん止め、必要なページを読み込む場所を確保し、必要なら古いページを追い出し、補助記憶から読み込み、ページ表を更新して、止めた命令を再実行できるようにします。プログラムから見ると、単にメモリを読んだだけに見えますが、裏側では大きな処理が走っています。

スラッシングは、プロセスが本当に使っているページの集合を主記憶に置ききれないときに起こりやすくなります。この「近い時間に実際によく使うページの集まり」をワーキングセットと呼びます。ワーキングセットがメモリに収まっていれば、ページフォールトは少なくて済みます。収まらないと、ページを入れては追い出し、すぐまた必要になって読み戻す状態になり、CPU は計算より入替え待ちに時間を使います。

プログラムの中で使うメモリには、OS が管理する大きな仕組みと、言語実行環境が管理する細かい仕組みがあります。OS はプロセスに仮想アドレス空間を与えます。その中で、プログラムはスタックやヒープを使います。スタックは関数呼び出しに合わせて増減しやすい領域で、ヒープは実行中に必要になったデータを柔軟に置く領域です。

手動メモリ管理では、プログラムが必要なメモリを確保し、不要になったら解放します。C 言語のように手動管理が中心の環境では、無駄が少なく細かく制御できる一方、解放忘れや二重解放が問題になります。解放忘れは、使わなくなったメモリを返さず、長く動くほど使用メモリが増える問題です。二重解放は、すでに返した領域をもう一度返してしまい、管理情報を壊す問題です。

メモリリークは、使わなくなったメモリが解放されず残り続ける現象です。短時間で終わるプログラムなら目立たないこともありますが、サーバのように何日も動き続けるプログラムでは深刻です。少しずつメモリが増え、最終的にスワップが増えたり、プロセスが停止したりします。

ガベージコレクションは、不要になったオブジェクトを実行環境が自動的に回収する仕組みです。ガベージは「もう使われないデータ」という意味です。プログラムから到達できないオブジェクトは、今後使えないと判断できるため、回収対象になります。到達できるとは、変数や配列やオブジェクトの参照をたどって、そのデータへ行けるという意味です。

ガベージコレクションがあると、解放忘れや二重解放を減らせます。しかし、メモリ管理を考えなくてよいわけではありません。不要なデータへの参照を持ち続けていると、実行環境は「まだ使うかもしれない」と判断し、回収できません。また、回収処理が走るタイミングで一時的に処理が止まることもあります。リアルタイム性が重要なシステムでは、この停止時間も設計対象になります。

メモリ安全性も重要です。配列の範囲外へ書き込む、解放済みのメモリを読む、初期化していない値を使う、といった問題は、異常終了だけでなくセキュリティ問題にもつながります。言語や実行環境によって、こうした危険をコンパイル時に防ぐ、実行時に検査する、開発者の責任にする、といった違いがあります。ソフトウェアを安全に作るには、OS の保護と、言語のメモリ管理の両方を理解する必要があります。

## 5.4 言語プロセッサ

この節を学ぶ理由は、人間が書いたプログラムがそのまま CPU に読まれるわけではないからです。高級言語のコードは、コンパイラやインタプリタ、リンカ、ローダを通って実行できる形になります。

言語プロセッサを学ぶと、ビルド、リンクエラー、ライブラリ、実行ファイル、最適化の意味が分かります。開発環境で起きるエラーを理解する土台になります。

言語プロセッサは、プログラムをコンピュータが実行できる形に変換するソフトウェアです。アセンブラはアセンブリ言語を機械語へ変換します。コンパイラは高級言語を機械語や中間コードへ変換します。インタプリタは、プログラムを少しずつ解釈しながら実行します。リンカは複数のオブジェクトファイルやライブラリを結合し、ローダは実行プログラムをメモリに配置します。

コンパイルは、だいたい次の流れで進みます。

1. 字句解析。
2. 構文解析。
3. 意味解析。
4. 最適化。
5. コード生成。

静的リンクは実行ファイルにライブラリを含めます。動的リンクは実行時に共有ライブラリを読み込みます。

ソースコードから実行までを、もう少し現実の流れで見ます。C 言語のようなコンパイル型言語では、まずソースコードが字句解析で単語に分けられます。`int count = 0;` なら、`int`、`count`、`=`、`0`、`;` のような意味のある単位に分けます。次に構文解析で、それらの並びが文法に合っているかを木構造として調べます。意味解析では、型が合っているか、宣言されていない変数を使っていないかなどを確認します。

最適化では、同じ結果を保ったまま速くしたり小さくしたりします。たとえば、計算結果が変わらない式を先にまとめたり、使われない処理を消したりします。その後、コード生成で機械語に近い命令列を作ります。ここでできるファイルは、多くの場合まだ単独では実行できないオブジェクトファイルです。なぜなら、他のファイルにある関数や、ライブラリにある関数の実体とまだ結び付いていないからです。

リンカは、複数のオブジェクトファイルとライブラリを結合し、関数名や変数名の参照を実際の場所へ対応づけます。この名前と実体の対応を解決する作業をシンボル解決といいます。リンクエラーは、文法エラーとは違います。ソースコード 1 つずつの文法は正しくても、「呼び出している関数の実体が見つからない」「同じ名前が複数定義されている」といった結合段階の問題で起きます。

ローダは、実行ファイルをメモリへ配置し、必要な共有ライブラリを読み込み、プログラムを開始できる状態にします。動的リンクを使う場合、実行時に共有ライブラリが見つからなければ起動に失敗します。つまり「コンパイルできた」「リンクできた」「ロードできた」「実行中に正しく動いた」は別々の段階です。エラーがどの段階で起きたかを分けると、原因をかなり絞れます。

インタプリタは、ソースコードや中間表現を読みながら実行します。コンパイラのように事前に機械語へ変換する方式に比べ、実行開始までが速かったり、対話的に試しやすかったりします。一方で、同じ処理を何度も実行する場合、毎回解釈する分のコストが問題になることがあります。

JIT は Just-In-Time コンパイルの略で、実行時に必要な部分を機械語へ変換する方式です。最初から全部を変換するのではなく、実際によく使われる部分を見つけて最適化します。たとえば、ある関数が何度も呼ばれると分かったら、その関数を機械語に変換して高速化します。これにより、インタプリタの柔軟さと、コンパイル済みコードの速さを組み合わせられます。

ただし、JIT も常に有利とは限りません。実行開始直後は、どの部分がよく使われるかを観測し、変換する時間が必要です。短時間で終わるプログラムでは、その準備コストが目立つことがあります。逆に、長く動くサーバやブラウザ上のプログラムでは、よく使う部分を実行中に最適化できるため効果が出やすくなります。

中間コードを使う処理系もあります。人間が書いたソースコードを、特定 CPU 専用の機械語ではなく、仮想機械が実行する中間表現へ変換します。仮想機械は、その中間コードを実行するための実行環境です。これにより、同じ中間コードを複数の OS や CPU 上で動かしやすくなります。ただし、実行環境のバージョン、ライブラリ、設定が違えば動作が変わることもあるため、やはり環境管理は必要です。

## 5.5 開発ツール

この節を学ぶ理由は、現代の開発は人間の記憶と手作業だけでは支えられないからです。コード量が増え、複数人で開発し、頻繁に変更するには、履歴管理、自動テスト、静的解析、デバッグの支援が必要です。

開発ツールを学ぶと、なぜ Git を使うのか、なぜ CI で自動テストするのか、なぜ静的解析で早くミスを見つけるのかが分かります。

開発ツールは、「人間が間違えやすい場所をどこで助けるか」で見ると整理できます。IDE は編集、ビルド、デバッグをまとめて扱える環境です。デバッガは、ブレークポイントでプログラムを止め、ステップ実行で 1 行ずつ進め、変数の値を確認するために使います。バージョン管理は変更履歴を残し、複数人の変更を合わせるための仕組みで、Git が代表例です。静的解析はプログラムを実行せずにコードの問題を検出し、動的解析は実行時の動作を調べます。CI は Continuous Integration の略で、変更のたびに自動ビルドや自動テストを行い、壊れた変更を早く見つけます。

CI と並んで CD という言葉も出てきます。CD には Continuous Delivery と Continuous Deployment の 2 つの意味で使われることがあります。Continuous Delivery は、いつでもリリースできる状態まで成果物を作り、検査し、準備しておくことです。Continuous Deployment は、検査を通った変更を本番環境へ自動で反映するところまで進めます。どちらも「手作業でしか出せないリリース」を減らす考え方ですが、本番反映まで自動化するかどうかは、システムの重要度、監査要求、障害時の影響によって決めます。

ビルドの再現性も重要です。ビルドは、ソースコードから実行できる形のプログラムや配布物を作ることです。同じソースコードを使っているのに、今日作ると動き、明日作ると壊れるなら、原因調査がとても難しくなります。そこで依存関係を管理します。依存関係とは、自分のプログラムが利用している外部ライブラリやツールの関係です。パッケージマネージャは依存ライブラリを取得してくれますが、毎回「その時点で新しい版」を取ると結果が変わることがあります。ロックファイルは、実際に使ったライブラリ名と正確なバージョンを固定する記録です。料理でいえば、「小麦粉を使う」だけではなく、「どの銘柄の何グラムを使ったか」まで残すようなものです。

SBOM は Software Bill of Materials、ソフトウェア部品表です。材料表という名前の通り、アプリケーションがどのライブラリ、どのバージョン、どのライセンスに依存しているかを一覧できるようにします。あるライブラリに深刻な脆弱性が見つかったとき、SBOM がなければ「自分たちのどのシステムが影響を受けるのか」を探すだけで時間を失います。ロックファイルがビルドの再現性に効くのに対して、SBOM はセキュリティ、ライセンス、サプライチェーン管理に効きます。サプライチェーンとは、製品やサービスが作られるまでに関わる部品や提供者のつながりです。ソフトウェアでも、外部ライブラリやビルドツールが攻撃されると、自分のコードが正しくても被害を受ける可能性があります。

性能問題ではプロファイラを使います。プロファイラは、プログラムのどの関数に時間がかかっているか、どこでメモリを多く使っているかを測る道具です。画面が遅いとき、人間の直感だけで「たぶんデータベースが遅い」と決めると外れることがあります。実際には、同じ計算を何度もしていたり、不要なファイル読込みをしていたり、通信待ちが原因だったりします。プロファイラで測ると、改善すべき場所を数字で絞れます。高度な開発では、勘で速くするのではなく、測定してから直します。

DevSecOps は、開発、運用、セキュリティを後から別々に足すのではなく、変更の流れの中に組み込む考え方です。静的解析で危険な書き方を早く見つけ、依存ライブラリの脆弱性を検査し、秘密情報がコードに混ざっていないか確認し、テスト環境から本番環境まで同じ手順で配備します。セキュリティを最後の検査だけにすると、問題が見つかったときに設計から戻る必要があります。だから、開発ツールは効率化だけでなく、安全性を早い段階で作り込むためにも使われます。

各ツールは、開発工程のどこで人間のミスを減らし、再現性を高め、品質を見える化するかで理解します。

## 設定ファイルと環境変数

アプリケーションの動きは、ソースコードだけで決まるわけではありません。接続先 URL、DB 名、タイムアウト秒数、ログレベル、機能の有効無効、外部サービスのキーなどは、設定として外に出すことがあります。

設定を外に出す理由は、同じプログラムを開発環境、検証環境、本番環境で使い回すためです。コードに本番 DB の接続先を直接書くと、検証環境へ切り替えるたびにコードを直す必要があります。設定として分ければ、プログラム本体は同じまま、環境に応じて接続先や動作を変えられます。

環境変数は、OS や実行環境からプロセスへ渡される設定値です。コンテナやクラウド環境では、環境変数で設定を渡すことがよくあります。ただし、環境変数に秘密情報を入れる場合は注意が必要です。プロセス一覧、ログ、診断情報、誤ったエラー出力から見えることがあります。秘密情報は、必要なプロセスだけが読めるようにし、ログへ出さない設計にします。

設定ミスは、コードのバグと同じくらい重大です。デバッグモードが本番で有効になっている、検証用の認証回避が残っている、ログレベルが高すぎて個人情報を出している、外部公開してはいけない管理画面が開いている。これらは、プログラムの文法が正しくても起きます。

そのため、設定もレビューと管理の対象にします。どの設定が本番で許されるか、初期値は安全か、変更履歴が残るか、変更後に戻せるかを確認します。ソフトウェアを理解するには、コード、依存ライブラリ、実行環境、設定を一体として見る必要があります。

## 5.6 UNIX 系 OS

この節を学ぶ理由は、サーバや開発環境の多くが UNIX 系の考え方で動いているからです。Linux、macOS、クラウドサーバ、コンテナ環境を扱うとき、ファイル、プロセス、権限、標準入出力の理解が必要になります。

UNIX 系 OS を学ぶと、コマンド操作、権限設定、ログ確認、自動化、サーバ運用の基礎が身につきます。

UNIX 系 OS は、ファイル、プロセス、ユーザ権限を統一的に扱います。

UNIX 系 OS の考え方を読むときは、次の概念が土台になります。

- ルートディレクトリ `/` から始まる階層構造。
- デバイスもファイルのように扱う。
- 標準入力、標準出力、標準エラー。
- パイプでコマンドをつなぐ。
- パーミッションで権限を制御する。

```text
r = 読み取り
w = 書き込み
x = 実行
```

UNIX のパーミッションでは、`r`、`w`、`x` の 3 種類の権限を読みます。`r` は読み取り、`w` は書き込み、`x` は実行です。対象は、所有者、グループ、その他です。たとえば `rw-r--r--` は、所有者だけ書込み可、他は読取りのみです。

パーミッションは数字でも表します。`r` は 4、`w` は 2、`x` は 1 として足し合わせます。なぜ足し算で表せるかというと、読み取り、書き込み、実行という 3 つの権限を、それぞれ別のビットに対応させているからです。`rwx` なら `4 + 2 + 1 = 7` です。`rw-` なら実行権限がないので `4 + 2 + 0 = 6`、`r--` なら `4 + 0 + 0 = 4` です。したがって `rw-r--r--` は、所有者が 6、グループが 4、その他が 4 なので `644` と表せます。

ここで大事なのは、数字を合言葉のように扱わないことです。`chmod 777` は全員に読み取り、書き込み、実行を許す設定です。便利そうに見えますが、他人や別プロセスが勝手に書き換えられる危険があります。Web サーバの設定ファイルや秘密鍵に広すぎる権限を付けると、OS の保護を自分で壊すことになります。

ディレクトリの `x` は、ファイルの実行とは少し意味が違います。ディレクトリに対する実行権限は、その中へ入ったり、中のファイル名をたどったりする権限です。ディレクトリに `r` があれば一覧を読めますが、`x` がなければ中のファイルへ進めません。ファイルとディレクトリでは同じ `rwx` でも意味が変わるので、権限は対象の種類と一緒に読む必要があります。

UNIX の強い考え方の 1 つは、入出力を小さな部品としてつなぐことです。標準入力はプログラムへ入ってくる通常の入力、標準出力は通常の結果、標準エラーはエラーメッセージ用の出力です。画面に出ているように見える文字も、実際には標準出力という流れへ書かれていると考えられます。

パイプは、あるコマンドの標準出力を、次のコマンドの標準入力へ渡します。

```sh
ls | grep ".md"
```

この例では、`ls` がファイル一覧を標準出力へ出し、その流れが `grep ".md"` の標準入力になります。`grep` は受け取った行の中から `.md` を含むものだけを出します。1 つの大きな万能プログラムを作るのではなく、小さな道具を標準入出力でつないで目的を達成するのが UNIX 的な発想です。

この標準入力や標準出力を支える考え方が、ファイルディスクリプタです。ファイルディスクリプタは、プロセスが開いている入出力対象を番号で表したものです。普通のファイルだけでなく、端末、パイプ、ネットワークソケットなども、読み書きできる対象として扱えます。

多くの UNIX 系 OS では、プロセスが始まった時点で次の番号が用意されています。

```text
0 = 標準入力
1 = 標準出力
2 = 標準エラー
```

プログラムが `read(0, ...)` のように 0 番から読むと、標準入力からデータを読みます。標準入力がキーボードならキーボードから読み、ファイルにリダイレクトされていればファイルから読み、パイプでつながれていれば前のコマンドの出力から読みます。プログラム本体は「相手がキーボードかファイルかパイプか」を毎回特別扱いしなくても、同じ読み取り操作で扱えます。

リダイレクトができるのは、プロセスを起動する前に、OS やシェルがこの番号の向き先を差し替えられるからです。たとえば `grep "ERROR" app.log > errors.txt` では、`grep` の 1 番、つまり標準出力が画面ではなく `errors.txt` に向けられます。`grep` から見ると、いつも通り標準出力へ書いているだけです。外側で向き先が変えられているので、同じプログラムを画面出力にもファイル保存にも使えます。

ファイルディスクリプタは便利ですが、資源でもあります。開いたファイルやソケットを閉じ忘れると、プロセス内に使い終わった番号が残り続けます。長く動くサーバでこれが続くと、新しい接続やファイルを開けなくなることがあります。メモリリークと同じように、ファイルディスクリプタのリークも運用障害になります。OS を理解すると、アプリの障害を「CPU」「メモリ」「ディスク」だけでなく、「開いているファイルや接続の数」からも調べられるようになります。

ファイルという考え方も広く使われます。通常のファイルだけでなく、端末やデバイスもファイルのようなインタフェースで扱える場合があります。これは「すべてが本当に同じ物体」という意味ではなく、読み書きの操作を共通化して、プログラムから扱いやすくする抽象化です。

UNIX 系のファイルシステムでは、ファイル名そのものと、ファイルの実体を分けて考えると理解が深まります。多くの UNIX 系ファイルシステムでは、ファイルの実体に関する情報を inode のような管理情報で持ちます。inode には、ファイル種別、所有者、権限、サイズ、データの置き場所などが記録されます。ファイル名は、その inode を指す入口だと考えられます。

この考え方を知ると、ハードリンクとシンボリックリンクの違いが見えます。ハードリンクは、同じファイル実体に別の名前を付けるようなものです。入口が複数あるだけなので、片方の名前を消しても、別の名前が残っていれば実体は残ります。シンボリックリンクは、別のパスを指す特別なファイルです。参照先が消えると、リンクは残っていてもたどれなくなります。

ファイルシステムでは、障害時に壊れにくくする仕組みも重要です。ファイルを保存するとき、OS はデータ本体だけでなく、ファイル名、サイズ、更新時刻、データの置き場所などの管理情報も更新します。もし更新の途中で電源が落ちると、データ本体と管理情報が食い違う可能性があります。

ジャーナリングは、変更内容を本格的に反映する前に、これから行う操作の記録を残す仕組みです。ジャーナルは日誌や記録という意味です。たとえば「このファイルのサイズを変える」「このブロックを使う」という操作を先に記録しておけば、障害後にファイルシステムは途中だった操作をやり直すか、取り消すかを判断しやすくなります。これにより、ディスク全体を最初から長時間検査しなくても、整合性を回復しやすくなります。

ただし、ジャーナリングはバックアップの代わりではありません。ジャーナリングが守る主な対象は、ファイルシステムの構造が壊れないことです。利用者が誤ってファイルを消した場合や、アプリケーションが間違った内容を上書きした場合、その内容まで元に戻せるとは限りません。ファイルシステムの整合性、データの内容、バックアップ、世代管理は別々に考えます。

権限管理でも、基本の `rwx` だけでは足りない場面があります。ACL、Access Control List は、より細かく「誰にどの権限を与えるか」を指定する仕組みです。所有者、グループ、その他という 3 分類だけでは、特定の先生だけに読取りを許す、特定の運用担当だけに書込みを許す、といった設定が難しい場合があります。ACL は柔軟ですが、設定が複雑になるほど、意図しない許可や消し忘れも起きやすくなります。権限は広げることより、あとから説明できることが大切です。

パスも重要です。絶対パスはルートディレクトリ `/` から目的地まで全部書く方法です。相対パスは、現在いるディレクトリを基準に書く方法です。たとえば同じ `logs/app.log` でも、どのディレクトリから実行しているかで指す場所が変わります。プログラムやシェルスクリプトで相対パスを使うときは、「実行時のカレントディレクトリ」がどこかを意識しないと、開発環境では動くのに本番で失敗することがあります。

リダイレクトは、標準入力や標準出力の向き先を変える仕組みです。画面に出す代わりにファイルへ保存したり、ファイルの内容をコマンドへ入力したりできます。パイプとリダイレクトを組み合わせると、小さな道具をつなげて強力な処理を作れます。

```sh
grep "ERROR" app.log > errors.txt
```

この例では、`grep "ERROR" app.log` の結果を画面ではなく `errors.txt` に書き込みます。`>` は出力先をファイルへ変える記号です。既存ファイルを上書きするため、運用作業では注意が必要です。追記したい場合は `>>` を使います。こうした仕組みは便利ですが、間違えると重要なログを上書きすることもあります。UNIX の道具は強力なので、権限、パス、入出力の向きを理解して使う必要があります。

## コンピュータグラフィックスの基本技術

コンピュータグラフィックスをソフトウェア側から見ると、画像をどう表すかだけでなく、描画処理をどの層が担当するかが重要になります。アプリケーションは「この四角形を描く」「この 3D モデルを表示する」といった命令を出しますが、実際には OS、グラフィックスライブラリ、デバイスドライバ、GPU が協力しています。デバイスドライバは、OS とハードウェアの間で、具体的な装置の操作を引き受けるソフトウェアです。

画像の表し方には、大きくラスタ形式とベクタ形式があります。ラスタ画像は、ピクセルと呼ばれる小さな点を並べて画像を表します。写真やスクリーンショットはラスタ画像として扱われることが多いです。ベクタ画像は、線、曲線、円、塗りつぶしなどを数式や図形命令として表します。ロゴやアイコンのように、拡大してもなめらかにしたい画像に向きます。

ラスタ画像では、解像度と色深度がデータ量に直結します。解像度は、横と縦に何個のピクセルがあるかです。たとえば `1920 × 1080` の画像なら、ピクセル数は次のように求めます。

```text
ピクセル数 = 1920 × 1080
           = 2,073,600
```

なぜ掛け算するかというと、横 1920 個の点が縦方向に 1080 行並ぶからです。1 行に 1920 個あり、それが 1080 行あるので、全体は `1920 × 1080` 個になります。

色深度は、1 ピクセルの色を何ビットで表すかです。RGB で赤、緑、青をそれぞれ 8 ビットで表すなら、1 ピクセルは `8 + 8 + 8 = 24` ビットです。8 ビットでは `2^8 = 256` 段階を表せます。赤が 256 通り、緑が 256 通り、青が 256 通りあるので、色の組合せは、

```text
256 × 256 × 256 = 16,777,216
```

通りです。これは「フルカラー」と呼ばれることがあります。

先ほどの `1920 × 1080` 画像を 24 ビットカラーでそのまま持つと、必要なビット数は、

```text
2,073,600 ピクセル × 24 ビット
= 49,766,400 ビット
```

です。1 バイトは 8 ビットなので、バイト数に直すには 8 で割ります。

```text
49,766,400 / 8 = 6,220,800 バイト
```

約 6.2 MB です。ここでは圧縮を考えていません。PNG や JPEG のような画像形式では、同じ色が続く、細部を少し省く、人間が気づきにくい情報を減らす、といった方法で容量を小さくします。つまり、画面に見える画像の大きさと、保存ファイルの大きさは同じではありません。

透過を扱うときは、アルファ値を使います。アルファ値は、前面の色をどれくらい見せるかを表す値です。単純化すると、前面色と背景色を次のように混ぜます。

```text
表示色 = 前面色 × α + 背景色 × (1 - α)
```

`α` が 1 なら前面だけ、`α` が 0 なら背景だけです。`α = 0.25` なら前面を 25%、背景を 75% 混ぜます。`1 - α` とするのは、前面と背景の割合を足して 1、つまり 100% にするためです。

画面表示では、フレームバッファという考え方があります。フレームは 1 枚の画面、バッファは一時的に置く場所です。つまりフレームバッファは、画面に出す画像データを置くメモリ領域です。アニメーションやゲームでは、描いている途中の画面をそのまま表示するとちらつきます。そこで、裏側のバッファに次の画面を描き終えてから表側へ切り替えるダブルバッファリングを使います。これは、利用者に見せる画面と、次に見せる画面の準備場所を分ける設計です。

3D グラフィックスでは、立体の形をいきなり画面の点として持つのではなく、段階的に変換します。まずモデル座標で物体自身の形を表します。次にワールド座標で、物体を空間のどこに置くかを決めます。さらにカメラから見た座標へ変換し、最後に 3D の位置を 2D の画面へ投影します。この流れを描画パイプラインと呼びます。パイプラインとは、処理を段階に分け、前の段階の結果を次の段階へ流していく仕組みです。

画面へ投影した後は、三角形などの図形をピクセルへ変換します。これをラスタライズといいます。3D モデルは多くの場合、三角形の集まりとして扱われます。GPU は多数のピクセルや頂点に似た計算を同時に行うのが得意です。だから画像処理、ゲーム、3D 表示、機械学習の一部で GPU が使われます。ただし、GPU を使えば必ず速くなるわけではありません。データを CPU と GPU の間で移す時間、メモリ容量、並列化しやすい計算かどうかが効きます。

奥行きの判定には Z バッファを使います。Z は奥行きを表す値です。同じ画面位置に複数の物体が重なるとき、手前のものを表示し、奥のものを隠す必要があります。Z バッファには、各ピクセルで現在いちばん手前にある奥行きを記録します。新しく描こうとする点がそれより手前なら更新し、奥なら描かない、という判断をします。

アンチエイリアスは、斜め線や曲線のギザギザを目立ちにくくする技術です。画面はピクセルの格子なので、斜め線を完全になめらかには置けません。そこで境界付近の色を少し混ぜ、急な段差を和らげます。これは「ぼかせばよい」という単純な話ではなく、解像度、視認性、処理負荷のバランスです。

AI 開発で使われる OSS も、ソフトウェアの章で考える対象です。機械学習ライブラリや数値計算ライブラリは、モデルを作るための関数を提供しますが、内部では CPU、GPU、メモリ、ファイル、ネットワークを使います。つまり AI ライブラリは魔法の箱ではなく、OS の資源管理、ハードウェアの並列処理、OSS ライセンス、データ管理の上で動くソフトウェアです。便利なライブラリを使うほど、依存関係、バージョン、ライセンス、再現性を管理する必要があります。

## ソフトウェア更新と互換性

ソフトウェアは、作って終わりではありません。脆弱性修正、性能改善、OS やブラウザの変更、外部サービスの仕様変更に合わせて更新されます。更新は必要ですが、同時に新しい障害を生む可能性もあります。

互換性とは、古い利用者や周辺システムが、新しい版でも壊れずに使える性質です。API の項目名を変える、設定ファイルの形式を変える、ライブラリの関数の意味を変える、といった変更は、呼び出す側を壊すことがあります。自分のプログラムだけを見て「新しい版では動く」と判断しても、利用している別システムが古い前提で作られていれば障害になります。

後方互換性は、新しい版が古い使い方を受け入れる性質です。たとえば、新しい API でも古い項目名を一定期間受け付ける、古い設定ファイルを読み込めるようにする、といった対応です。互換性を保つと移行は楽になりますが、古い仕様を長く残しすぎると内部が複雑になります。そこで、廃止予定を知らせ、移行期間を設け、いつ削除するかを明確にします。

パッチは、既存ソフトウェアの一部を修正する更新です。セキュリティパッチは脆弱性を直すため特に重要です。ただし、急いで適用すれば常に安全とは限りません。依存しているライブラリの版が上がると、別の機能が動かなくなることがあります。重要なシステムでは、検証環境で確認し、戻し方を用意し、適用後に監視します。

バージョン番号も、変更の大きさを伝える手がかりになります。一般に、互換性を壊す大きな変更、機能追加、バグ修正を番号で分ける考え方があります。番号そのものに絶対の法律があるわけではありませんが、利用者に「この更新は安全に上げられるのか」「修正が必要なのか」を伝える約束として機能します。

ソフトウェア更新の高度な理解では、最新版にすることだけを目的にしません。何を直す更新か、どの互換性が変わるか、どの依存関係に影響するか、問題が出たとき戻せるかを確認します。更新は、リスクを減らす作業であると同時に、新しいリスクを持ち込む変更でもあります。

## OSS

OSS は、ソースコードが公開され、利用、改変、再配布が許されるソフトウェアです。ただしライセンス条件に従う必要があります。GPL は、派生物にも GPL を求めるコピーレフトが強いライセンスです。コピーレフトとは、自由に使える状態を派生物にも引き継がせる考え方です。LGPL はライブラリとして利用する場合に配慮したライセンスです。MIT、BSD、Apache は比較的緩やかなライセンスですが、著作権表示やライセンス文の同梱など、守るべき条件はあります。

OSS は無料という意味ではありません。重要なのは、ソースコード利用の権利と条件です。

## 実務で使える理解

- OS の役割は「資源管理」と「抽象化」で考える。
- プロセス状態は、CPU 待ちか入出力待ちかで整理する。
- スケジューリングは、公平性、応答性、平均待ち時間のどれを重視するかを見る。
- 排他制御は、共有資源とクリティカルセクションを見つける。
- デッドロックは、どの資源を誰が持ち、誰が何を待っているかを線で追う。
- 仮想記憶は、ページフォールトとスラッシングに注意する。
- コンパイラ、リンカ、ローダの順序を間違えない。
- メモリリーク、ガベージコレクション、JIT は、実行環境が性能と安全性にどう関わるかで理解する。
- 更新では、脆弱性修正、互換性、依存関係、戻し方を合わせて見る。
- 設定ファイルと環境変数は、コードとは別にアプリの動作を変える重要な要素として扱う。
- UNIX の標準入出力は、ファイルディスクリプタの向き先を変える仕組みとして理解する。
- コンピュータグラフィックスは、ピクセル、色深度、フレームバッファ、GPU、描画パイプラインを分けて理解する。
- OSS はライセンス条件まで見る。

## 自分の言葉で説明する

- カーネルモードとユーザモードの違いを説明できる。
- プロセス状態遷移を図なしで説明できる。
- ラウンドロビンの時間片が長すぎる/短すぎる場合を説明できる。
- セマフォ、ロック、ミューテックスの目的を説明できる。
- デッドロックの 4 条件を、資源の取り合いの例で説明できる。
- 内部断片化と外部断片化を区別できる。
- ページング、ページフォールト、スラッシングを説明できる。
- コンパイラ、リンカ、ローダの役割を区別できる。
- 手動メモリ管理とガベージコレクションの長所と注意点を説明できる。
- JIT と事前コンパイルとインタプリタの違いを、実行開始の速さと長時間実行時の性能から説明できる。
- 後方互換性と廃止予定の意味を、API 更新の例で説明できる。
- 設定ミスがコードのバグと同じくらい重大になる理由を説明できる。
- ファイルディスクリプタ 0、1、2 が標準入力、標準出力、標準エラーに対応することを説明できる。
- UNIX のパーミッションを読める。
- ラスタ画像とベクタ画像の違いを、拡大時の見え方とデータ表現から説明できる。
- 解像度と色深度から、非圧縮画像のおおよそのデータ量を計算できる。
- フレームバッファ、ダブルバッファリング、Z バッファ、アンチエイリアスの役割を説明できる。
- OSS ライセンスの違いを大まかに説明できる。

## 深く身につけるための補講

OS は、コンピュータの資源を安全に共有するための管理者です。CPU、メモリ、ファイル、ネットワーク、デバイスは限られています。複数のプログラムが同時に使うためには、誰がいつ何を使えるかを調整する必要があります。

OS を理解すると、次のような現象の理由が分かります。

- アプリが固まっても OS 全体は動き続ける。
- メモリ不足で突然遅くなる。
- ファイル権限がないと読み書きできない。
- 2 つの処理が同じデータを更新すると壊れる。
- 再起動すると直る障害がある。

## プロセスは「実行中の世界」

プログラムはファイルです。プロセスは、そのプログラムが実行され、メモリ、開いているファイル、環境変数、権限、スレッドなどを持った状態です。

同じアプリを 2 回起動すると、プログラムファイルは 1 つでもプロセスは 2 つできます。それぞれ別のメモリ空間を持ちます。

この分離があるから、あるアプリが勝手に別アプリのメモリを読んだり壊したりできません。

## 並行処理で起きる現実のバグ

在庫が 1 個の商品を、2 人が同時に購入する例を考えます。

```text
A: 在庫を読む -> 1
B: 在庫を読む -> 1
A: 在庫を 1 減らす -> 0
B: 在庫を 1 減らす -> 0
```

結果は在庫 0 ですが、2 人に売れてしまいました。本当は片方だけ成功すべきです。

これは、読み取りと更新が分かれており、その間に別処理が割り込むことで起きます。排他制御やトランザクションが必要です。

排他制御は「同時に動かすな」という単純な話ではありません。どこを同時実行してよく、どこを守るべきかを正しく決める設計です。守りすぎると遅くなり、守らなすぎると壊れます。

## デッドロックを物語で理解する

2 人がそれぞれ片方の箸を持っていて、もう片方の箸を相手が離すのを待っていると食事が進みません。これがデッドロックです。

システムでも同じです。

```text
プロセス A: 資源 X を持ち、資源 Y を待つ
プロセス B: 資源 Y を持ち、資源 X を待つ
```

解決するときは、デッドロックの 4 条件のどれかを崩します。資源を必ず同じ順序で取れば、循環待ちを防げます。必要な資源を最初にまとめて取れば、占有と待ちを減らせます。タイムアウトしたらいったん解放してやり直す方法もあります。発生を完全には防がず、デッドロックを検出して片方の処理を中止する設計もあります。

## 仮想記憶は「大きく見せる」だけではない

仮想記憶の価値は、主記憶より大きなメモリを見せることだけではありません。

- プロセスごとに独立したアドレス空間を与える。
- 他プロセスのメモリを直接読めないようにする。
- 必要なページだけ読み込んで効率化する。
- メモリ保護により OS の安定性を高める。

つまり仮想記憶は、性能、保護、抽象化を同時に実現する仕組みです。

## OSS ライセンスを実務として理解する

OSS は「無料で自由に使えるもの」ではありません。ライセンスに従うことで利用できます。

実務では次を確認します。

- 商用利用できるか。
- 改変できるか。
- 再配布できるか。
- ソースコード公開義務があるか。
- 著作権表示やライセンス文の同梱が必要か。
- 特許条項があるか。

ライセンスを理解しないまま製品に組み込むと、後から公開義務や契約違反が問題になります。

## ありがちな誤解

- スレッドは軽いが、安全とは限らない。共有メモリの競合が起きる。
- ロックを増やせば安全になるとは限らない。デッドロックや性能低下が起きる。
- メモリが足りないと、単に失敗するだけでなくスワップで極端に遅くなる。
- ガベージコレクションがあってもメモリ管理を考えなくてよいわけではない。
- インタプリタは常に遅いわけではない。JIT や実行環境の最適化がある。
- 最新版への更新は常に無条件で安全とは限らない。検証と戻し方が必要。
- コードが同じでも設定が違えば、本番だけで障害が起きることがあります。
- GPU は万能な高速化装置ではありません。CPU と GPU の間のデータ転送や、並列化しやすい処理かどうかが効きます。
- JPEG や PNG のファイルサイズだけを見ても、メモリ上の画像サイズは分かりません。圧縮後の容量と展開後のピクセルデータ量は別です。
- OSS はライセンスを守ることで初めて安心して使える。

## 手を動かす課題

1. 在庫 1 個を 2 人が同時購入する例で、どこをクリティカルセクションにすべきか説明してください。
2. デッドロックの 4 条件を、身近な道具の取り合いで例示してください。
3. 仮想記憶がセキュリティにも役立つ理由を説明してください。
4. 好きな OSS を 1 つ選び、ライセンス名と利用条件を調べる前提で、確認すべき項目を列挙してください。
5. サーバプログラムでメモリリークが起きると、時間とともに何が悪化するか説明してください。
6. JIT が短時間で終わる処理より長時間動く処理で効果を出しやすい理由を説明してください。
7. ライブラリを新しい版へ更新するとき、互換性、依存関係、戻し方として何を確認するか説明してください。
8. 本番環境でデバッグモードが有効なままだと、どんな問題が起きるか説明してください。
9. `grep "ERROR" app.log > errors.txt` を、ファイルディスクリプタ 0、1、2 のうちどれがどう変わるかで説明してください。
10. `1280 × 720` の 24 ビットカラー画像を非圧縮で持つとき、必要なバイト数を途中式つきで計算してください。
11. 3D ゲームで「モデルはあるのに手前と奥の表示がおかしい」場合、Z バッファの観点から原因を説明してください。
