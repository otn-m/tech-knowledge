# 第2章・第2話　データ型と式――同じ0と1でも、整数・文字・日付では意味が違う

コンピュータの内部では、あらゆる値が最終的にビット列として保存されます。
ただし、プログラムが実行する操作の意味は、その値を何として解釈するかによって違ってくるわけです。

```text
20 + 5        → 数の加算なら25
"20" + "5"  → 文字列の連結なら"205"
```

同じ`+`という記号であっても、数値なら加算、文字列なら連結という処理になります。
記号の字面だけでは式の意味が決まりません。
値の種類、表現範囲、許される操作を体系的にまとめた規則を**データ型**、短く型と呼びます。

## 型が定める表現と操作

### 1 型が必要な理由

冒頭に挙げた数値と文字列の違いが示すとおり、型は保存方法だけでなく、操作と意味の双方を規定する仕組みです。
主な役割は次の三つです。

1. **保存方法を決める**
   - 何ビット使うか。
   - 符号や小数をどう表すか。
2. **許される操作を決める**
   - 数なら加算、文字列なら連結など。
3. **意味の取り違えを見つける**
   - 日付に人数を足すなど、不自然な操作をエラーにする。

型が表す情報は、記憶域の大きさだけにとどまりません。
「これは金額の円」「これは利用者ID」といった業務上の意図も表現できます。

### 2 整数型

個数のように、小数部分を持たない数には整数型を用います。

```text
-3, 0, 42, 1000000
```

表現できる数値の範囲は、ビット数と符号の有無によって決まる仕組みです。

8ビットの場合、範囲は次のとおりです。

- 符号なし――0から255。
- 二の補数の符号付き――-128から127。

許容範囲を越えるとオーバフローが発生します。
範囲を越えた際の扱いは、言語仕様によって対応が分かれるところです。

- エラーにする。
- 下位ビットだけ残して回り込む。
- 自動的に大きな整数に広げる。

#### 8ビット整数の範囲を導く

8ビット列は各桁2通りなので、組合せは全部で`2⁸=256`通りになります。
符号なしの場合は`00000000₂=0`から`11111111₂=255`までの範囲です。
二の補数の符号付き整数では、先頭0側が0〜127、先頭1側が−128〜−1を表すため、全体の範囲は−128〜127となります。
最小列`10000000₂=-128`、最大列`01111111₂=127`に対応するわけです。

### 3 実数型――コンピュータでは多くが浮動小数点

小数を含む値の表現には実数型を用います。

```text
3.14
-0.25
1.0e6
```

多くの言語で提供される実数型は、IEEE 754の単精度・倍精度などの二進浮動小数点形式です。

```text
単精度  主に32ビット
倍精度  主に64ビット
```

倍精度は単精度より広い表現範囲と多い有効桁を持ちますが、どちらも有限のリソースにすぎません。

0.1のように二進数では正確に表せない値があり、丸め誤差や桁落ち、オーバフローやアンダフローに注意が必要です。

### 4 十進型と固定小数点型

金額計算のように十進の桁を正確に扱いたい場面では、十進型や固定小数点型を選択します。

```text
12.34円を、小数点以下2桁の固定小数として持つ
内部では1234という整数に近い形で持つ
```

十進型や固定小数点型を導入する場合でも、次の項目は業務仕様としてあらかじめ決めておくことが重要です。

- 端数をいつ丸めるか。
- 切上げ、切捨て、四捨五入のどれを採用するか。
- 消費税を商品ごとに掛けるか、合計後に計算するか。

## 真偽、文字、値のない状態を区別する

### 5 論理型

数値を計算するだけでなく、条件判定を伴う式には、真と偽の2値を扱う論理型を用います。

```text
true
false
```

たとえば、比較式を評価した結果として得られる値が真偽値です。

```text
age >= 18  → trueまたはfalse
```

数値の0を偽、0以外を真として自動変換する言語もありますが、数値と論理を混用するとコードの意図が曖昧になります。

データベースではNULLを含む3値論理を扱うケースがあり、通常の真偽判定とは前提が異なる点に留意が必要です。

### 6 文字型と文字列型

#### 文字型

文字型は、単一の文字や符号単位を格納するデータ型として機能します。

```text
'A'
'あ'
```

ただし、処理系の文字型がUnicodeコードポイント1個、人間が認識する1文字、あるいはUTF-16符号単位1個のどれを指すかは確認が必要です。

#### 文字列型

文字列型は、一連の文字の並びを表現します。

```text
"こんにちは"
"A12"
""
```

`""`は文字の長さが0である空文字列のことです。
値そのものが存在しない状態を表すNULLとは明確に異なります。

### 7 NULL――値がない、または分からない

0円という金額と金額不明、空の文字列と未登録の氏名を同一視すると、後から両者を区別できません。
値が存在している状態と、値そのものが欠落している状態を明確に切り分けて扱います。

NULLは、値そのものが存在しないことを表す特別な状態として定義される値です。

```text
空文字列 ""   文字列は存在し、文字数0
数値0          数値は存在し、値が0
NULL           値がない、未設定、不明など
```

NULLが具体的に何を意味するのかは、システム設計の中で決める方針です。

- まだ入力されていない。
- 該当する対象が存在しない。
- 外部から情報が得られず不明である。
- 意図的に削除された履歴である。

複数の理由を1つのNULLに集約してしまうと、後の処理で原因を切り分けられません。

また、NULLに対して一般的な演算を適用した際にNULLが伝播する言語や、実行時例外を送出する言語が存在します。

## 値の集合と、値をまとめる構造

### 8 列挙型

値の欠落だけでなく、注文の進捗状況のように、取り得る状態の集合を限定して管理したい場面もあります。
許容された候補値を識別名付きで列挙して定義するのが**列挙型**です。

```text
OrderStatus = {受付, 支払済, 発送済, 取消}
```

単なる整数値の0、1、2、3を割り振る手法に比べ、コードの意味が明瞭になり、不正な状態値の混入を防ぎやすくなります。

ただし、新しい状態値を追加した局面では、すべての分岐ロジックが追従できているか点検が必要です。

### 9 配列型と構造型

複数のデータを束ねる際は、同一型の値をインデックス番号で順序付けするか、異なる役割の属性をフィールド名で集約するかを切り分けます。

#### 配列型

同一型の複数の値を、連続した添字番号によって管理するデータ構造です。

```text
scores = [70, 85, 90]
```


#### 構造型

異なる意味や型を持つ複数の項目を、1つのまとまりとして統合します。
言語によってレコード、構造体などと呼ばれます。

```text
Student
  id: 整数
  name: 文字列
  score: 整数
```

「配列は同一の型を番号で整理する」「構造型は多様な役割を名前で集約する」という整理が基本原則です。

### 10 抽象データ型

内部の保存形式に依存せず、利用者から見える値と提供される操作の仕様によって型を定義します。

たとえばスタックというデータ構造では、次のような基本操作を規定する設計です。

- 空のスタックを作る。
- pushで上に積む。
- popで上から取り出す。
- topで一番上を見る。
- 空か調べる。

内部の実装に配列を採用するか連結リストを採用するかという詳細は、利用者側から隠蔽できます。
このような「何ができるか」という仕様と「どう作るか」という実装の分離こそが抽象化の考え方です。

## 型を検査し、変換を明示する

### 11 静的型付けと動的型付け

プログラム内で発生した型の不整合をどの段階で検出するかは、言語処理系の型検査の仕組みによって決まります。

#### 静的型付け

静的型付けでは、変数や式が持つデータ型の整合性をコード実行前に静的に検証します。

```text
整数 total
total = "abc"  → 実行前に型誤り
```

実行前に潜在的なバグを早期発見でき、コンパイラによる最適化を施しやすい点が大きな利点です。

#### 動的型付け

実行時の値そのものが型情報を保持しており、操作が実行される瞬間に型の適合性を検証します。

```text
x = 10
x = "abc"
```

コードを柔軟に記述できる反面、特定の実行経路を通過した段階で初めて型エラーが顕在化するリスクを抱えています。

静的型付けか動的型付けかという分類だけで、システムの安全性や開発効率の優劣が確定するわけではありません。
型システム、テストスイート、設計手法、開発ツールを組み合わせて品質を担保します。

### 12 型推論

プログラマが明示的に型名を記述しなくても、初期値や周囲の文脈からコンパイラが型を自動決定する機能を型推論と呼びます。

たとえば、次の代入文における初期値から、処理系は`x`を整数型として推論するわけです。

```text
x = 3
```

型名を省略して書けることと、型チェックが存在しないことの間には明確な違いがあります。

### 13 暗黙の型変換

異なるデータ型の値を同一の式で評価する際、言語処理系が背後で自動的に型を変換する機能が存在します。
これが**暗黙の型変換**です。

```text
整数3 + 実数0.5
→ 整数3を実数3.0へ変換
→ 3.5
```

簡潔な記述を可能にする一方で、どの型へ昇格したかがコード上から見えにくく、意図しない解釈を生む原因にもなります。
丸め誤差や桁落ち、符号の解釈齟齬といった不具合は、この見えない変換によって生じるものです。

たとえば次の式を評価した結果が`"102"`になるか、数値の12になるか、あるいは型不一致で拒否されるかは言語仕様に左右されます。

```text
"10" + 2
```

暗黙の型変換に頼る設計を避け、重要な境界部分では型変換を明示的に記述する姿勢が大切です。

### 14 明示的な型変換

プログラマが意図を込めて型の変換手順を指定する操作をキャスト、あるいは明示的型変換と呼びます。

```text
整数へ変換("123") → 123
文字列へ変換(123) → "123"
```

入力文字列`"12x"`を整数にパースできないケースのように、変換失敗時の異常系への考慮も欠かせません。

変換処理の実装にあたっては、次の観点を確認することが肝要です。

```text
変換できたか
範囲内か
余分な文字はないか
単位は正しいか
```


### 15 狭い型へ変えると情報を失う

実数から整数へ型を変換する処理では、次のように小数部分を切り捨てる挙動が発生します。

```text
実数3.9 → 整数3
```

この挙動は一般的な四捨五入の規則とは一致しません。

次の変換例では、元の数値が変換先データ型の表現上限を超過してしまいます。

```text
大きな整数1000 → 八ビット整数
```

また、次の変換のように有効桁の一部が失われてしまうケースもあります。

```text
倍精度 → 単精度
```

したがって、型変換を実施する前には値が許容範囲に収まっているかを検証し、丸め規則を明記する設計が不可欠です。

## 型と評価方法から式の結果を読む

### 16 整数除算

整数同士の除算演算において、計算結果の小数部を切り捨てて整数値を返すプログラミング言語が多く存在します。

```text
5 / 2 → 2
```

実数同士の計算として除算を実行した場合には、次の計算結果が得られます。

```text
5.0 / 2.0 → 2.5
```

平均値を算出する処理で合計値とデータ件数の双方が整数型であると、端数データが暗黙のうちに欠落してしまうわけです。

平均値の小数部を保持したい場合は、次のように除算の前に意図して一方を実数型へ変換します。

```text
average = real(total) / count
```

負の整数に対する除算で、小数部を0方向に切り捨てるか、負の無限大方向へ丸めるかは言語仕様によって規定が分かれる論点です。

### 17 演算のオーバロード

同一の演算子記号や関数名が、渡されたオペランドのデータ型に応じて異なる処理を実行する言語機能があります。

```text
2 + 3          → 整数加算
2.0 + 3.0      → 浮動小数点加算
"a" + "b"    → 文字列連結
```

この仕組みを多重定義、またはオーバーロードと呼ぶわけです。

同名の関数名に対して引数の数や型が異なる複数のシグネチャを定義し、呼び出し側から適切に振り分ける機能もオーバーロードに含まれます。

なお、オブジェクト指向で登場するオーバーライドは、子クラスが親クラスのメソッド実装を上書きする操作であり、両者はまったく異なる概念です。

ここで**クラス**とは、同一種のオブジェクトが備える属性データと振る舞いを定義した設計図を指します。
親クラス`Animal`が備える操作`speak()`を子クラス`Dog`が継承し、犬独自の実装に差し替える動作がオーバーライドに相当するわけです。

```text
Animal
  └─ Dog: speak()を「ワン」と実装
```


### 18 評価順序と短絡評価

式の型が正しく決定されたとしても、式を構成するすべての部分式が実行されるとは限りません。
論理演算式では、左辺の評価結果だけで式全体の真偽が確定した場合、右辺の評価をスキップする仕様が存在します。

AND演算では左辺が偽であれば、右辺を評価するまでもなく式全体の結果は偽です。
OR演算では左辺が真であれば、右辺を評価するまでもなく式全体の結果は真です。

このように不要な評価を省略する動作を短絡評価と呼びます。

```text
x != 0 AND 10/x > 2
```

`x=0`の条件下では、左辺が偽と評価されるため、右辺で発生し得る0除算エラーを未然に回避できるわけです。

ただし、右辺に関数呼出しなどの副作用が伴う場合、期待していた処理が呼び出されない不具合へ発展する恐れがあります。
判定条件式の中に不要な副作用を紛れ込ませてはなりません。

## 内容の一致と、参照先の一致

### 19 参照型と値型という見方

データそのものを変数領域に直接格納する値型と、ヒープ領域などに存在する実体への参照を変数に保持する参照型を区別する言語仕様があります。

```text
a = [1,2]
b = a
bへ3を追加
```

もし`a`と`b`が同一の配列実体を参照している場合、`a`を経由して参照した配列の内容も`[1,2,3]`へ更新されます。

変数を独立して複製したと誤認したまま同一の実体を共有していると、意図しない副作用が広範囲へ波及してしまうわけです。

変数への代入やオブジェクトの複製を扱う局面では、次の観点を明確に区別して整理します。

```text
同じ対象を共有する代入か
中身を複製するコピーか
入れ子の中まで複製するか
```


### 20 等価性――同じ対象か、同じ内容か

データの内容が合致している2つの配列を「同一」と表現すること自体は直感に沿っています。
しかし、一方の要素を更新した際にもう一方へ影響が及ぶかを厳密に判定するには、内容の一致と参照先の一致を分離して評価しなければなりません。

オブジェクトの比較には2つの異なる水準が存在します。

- 同一性――メモリ上で同一の単一インスタンスを指し示しているか。
- 値の等価性――保持している内部データの内容が一致しているか。

独立してメモリ上に生成された2つの`[1,2]`は、保持する値が等価であっても、参照先としては別のオブジェクトです。

各言語の比較演算子`==`がどちらの基準で判定を下すかは、対象の型や言語仕様によって細かく規定されています。

### 21 型を設計するときの問い

1. 取り得る最小値と最大値は何か。
2. 小数は必要か。
   十進で正確に扱う必要があるか。
3. 値がない状態は必要か。
   何種類の理由があるか。
4. 単位や通貨を区別すべきか。
5. 変更可能か、不変にするか。
6. 外部入力をどう検証するか。
7. 保存・通信時の形式は何か。
8. 将来、新しい状態を追加するか。

単に「最も大きなメモリ幅を持つ型」を選定すれば安全というわけではありません。
業務上の意味付け、処理性能、ストレージの保存形式、そして外部システムとの相互運用性を総合的に判断して決定します。

冒頭で提示した`20+5`と`"20"+"5"`は、同一の演算記号を含みながらも異なる型の値を評価する式でした。
値のデータ型、暗黙の型変換、式の評価順序、参照共有の機構を立体的に把握することで、式がもたらす評価結果とシステムの状態変化を正確に読み解けるようになります。
