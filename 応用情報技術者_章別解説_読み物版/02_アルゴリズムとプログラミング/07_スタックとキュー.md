# 第2章・第7話　スタックとキュー――取り出す順序を、データ構造の規則にする

学食やカフェテリアの返却口では、最後に一番上に積まれたトレイや皿から順に手に取ります。
対照的に銀行や病院の窓口受付では、発券機で順番を待つ先頭の来客から順番に案内されるのが原則です。
同一のデータ群を保管している場合であっても、要素を取り出す順序規則が異なれば、システムが直後に処理すべき対象データは全く別物になります。

最後に追加された要素から優先して取り出す順序構造をスタック、最初に追加された要素から先着順で取り出す構造をキューと呼びます。
計算機科学では、スタックの動作原則を後入れ先出し（LIFO: Last In, First Out）、キューの動作原則を先入れ先出し（FIFO: First In, First Out）と総称するわけです。
これらは単なるメモリ上の格納形式にとどまらず、どの端からデータを投入しどの端から払い出すかというアクセス規約を定めた代表的な抽象データ型（ADT）です。

## スタックの順序を実装する

### 1 スタック――上だけを使う積み重ね

```text
上 top → [C] 最後に入れた
         [B]
         [A] 最初に入れた
```

スタックが外部に提供する基本的な操作インターフェースは、次の体系で定義されます。
データを天頂部に積む`push`、天頂部からデータを取り出して削除する`pop`、削除せずに天頂部のデータを参照する`top`（または`peek`）、そして内部が空であるかを判定する`isEmpty`などです。

LIFOとはLast In, First Outの略称であり、最後に投入されたデータが最初に取り出される順序規律を指しています。

### 2 pushとpopを追う

空のスタック状態を起点として、要素の出し入れの流れを追跡してみましょう。

```text
push(A)  [A]
push(B)  [A,B]  ←右を上とする
push(C)  [A,B,C]
pop()    Cを返し [A,B]
pop()    Bを返し [A]
```

スタックにおける`push`と`pop`の操作は、常にデータの天頂部（top）と呼ばれる同一の端点に対してのみ実行されます。

### 3 アンダーフローとオーバフロー

`pop`はスタック天頂部の値を返却して削除する操作ですが、スタックが空のときには取り出すべき値が存在しません。
また固定長配列でスタックを構築した場合、容量上限に達した状態で実行される`push`にも同様に境界条件の破綻が現れます。

#### アンダーフロー

要素が1つも存在しない空スタックに対して`pop`を実行しようとするエラー状態です。
返却すべきデータ実体が存在しないため、例外の送出、特定のエラーコード、あるいは成否を表す真偽値などを用いて呼び出し元へ異常を通知します。
通常データとして出現し得る数値を安易にエラー値に割り当てると、正常値と異常値の判別がつかなくなる点に注意が必要です。

#### オーバフロー

メモリ容量が固定されたスタックが満杯であるにもかかわらず、さらに`push`を試みる過剰書き込み状態です。
用途に応じて動的配列のように自動拡張する、書き込みを即座に拒否する、あるいは古いデータを破棄して上書きするなどの運用方針を選択します。
隣接するメモリ領域へ無断で書き込みを侵入させてはなりません。

### 4 配列でスタックを作る

スタックの内部構造は、固定長の配列と現在の要素数を管理するポインタ変数`top`を組み合わせることで簡潔に実装可能です。
ここでは`top`変数を「次に新しい要素を格納すべき空きインデックス位置」として定義します。

```text
data = 容量5の配列
top = 0
```

`push`操作を呼び出す際は、まず配列に空き領域が残っているかを確認した上で値を代入し、その直後に`top`を1つ前進させます。

```text
関数 push(x)
    もし top == capacity ならエラー
    data[top] = x
    top = top + 1
```

対する`pop`操作では、スタックが空でないことを検証した後に`top`を1つデクリメントし、指し示された位置の値を返却する手順です。

```text
関数 pop()
    もし top == 0 ならエラー
    top = top - 1
    data[top]を返す
```

あらかじめ`top`を1減算することで、直前まで有効であった天頂部要素のインデックス番地に復帰できるわけです。

なお、実装方式によっては`top`を「現に最上部にある要素自身の添字」と定義する流派も存在します。
設計時はどちらの定義を採用しているかを明確に統一しなければなりません。

### 5 連結リストでスタックを作る

単方向連結リストの先頭ノードをスタックの天頂部（top）と見立てて構築する手法も広く用いられます。

```text
top → C → B → A
```

先頭への要素挿入を`push`とし、先頭ノードの切り離しを`pop`として実装します。
どちらの操作も先頭ノードに対する局所的なポインタ操作のみで完結するため、計算量は常に極めて高速な`O(1)`です。
システムの利用可能メモリが許す限り容量の上限なく要素を蓄積できますが、各ノードにポインタ保持用のメモリ幅が必要となります。

## 最後の操作から戻る処理

### 6 関数呼出しにスタックを使う

プログラムの実行中に関数Aが関数Bを呼び出し、さらにBが関数Cを呼び出す呼び出し連鎖を考えてみましょう。

```text
push Aの呼出し枠
push Bの呼出し枠
push Cの呼出し枠
```

このとき呼び出された関数Cが最初に終了し、次いで関数B、最後に最初の関数Aへと順番に処理が回帰します。
最後に呼び出された関数から逆順に復帰していく動作モデルは、まさにLIFO（スタック）の性質そのものです。
メモリ上のスタック領域に確保される呼出し枠（スタックフレーム）には、復帰先番地、引数、ローカル変数などが格納されます。

### 7 元に戻す操作

テキストエディタのUndo（元に戻す）機能も、スタック構造を活用して実現されます。

```text
文字Aを追加
文字Bを追加
段落を削除 ← 一番上
```

「元に戻す」を実行した際は、履歴スタックから直前の操作を`pop`して取り出し、その逆の打ち消し操作を実行する仕組みです。
取り消した操作を「やり直す（Redo）」機能を提供したい場合は、Undoで取り出された操作を別のRedoスタックへと積み直します。
なおユーザーが新しい編集操作を実行した局面では、過去のRedo履歴をすべて破棄してクリアするのが一般的なUI設計です。

### 8 括弧の正しさを検査する

数式やプログラムの構文解析において、開き括弧と閉じ括弧の対応関係を検証する処理にもスタックが威力を発揮します。

```text
([]{})
```

文字列を先頭から1文字ずつ走査し、開き括弧に遭遇した場合は即座にスタックへ`push`します。
閉じ括弧に遭遇した際は、スタックが空でないことを確認した上で直前の開き括弧を`pop`し、括弧の種類が正しくペアを成しているかを照合する手順です。
走査が完了した最終時点でスタックが完全に空であれば、数式内の括弧は完全に整合していたと判定できます。

次の文字列例では、`)`を読み出した時点でスタックの天頂部が`[`となっており、括弧の入れ子関係が破綻していることを検知可能です。

```text
([)]
```

単に開き括弧と閉じ括弧の総数をカウントするだけの手法では、このような順序と種類の不整合を検出できません。

### 9 逆ポーランド記法を計算する

演算子を被演算子の後ろに配置する逆ポーランド記法（後置記法）の数式評価は、スタックを用いることで括弧なしに一意に計算できます。

```text
3 4 5 × +
```

数式を左から順に走査し、数値であればスタックへ`push`し、演算子に遭遇した際はスタックから数値を2つ`pop`して演算を実行します。
計算された結果の値を再びスタックへ`push`することで、複雑な優先順位を持つ式も一本道で処理できるわけです。

```text
3     [3]
4     [3,4]
5     [3,4,5]
×     4×5=20 → [3,20]
+     3+20=23 → [23]
```

減算や除算のような非可換な演算を行う際は、後から`pop`された値が式の左辺（被演算子）となる順序関係に留意が必要です。

```text
8 2 -
最初に2をpop、次に8をpop
8-2=6
```


### 10 深さ優先探索とバックトラック

迷路探索やゲームの盤面探索において、1つの進路を行き止まりに達するまで突き進み、壁に突き当たったら直前の分岐点まで巻き戻す探索手順を考えます。
このような処理では、未探索の分岐点候補や進行経路の履歴をスタック上に積み上げて管理します。
これが深さ優先探索（DFS: Depth First Search）およびバックトラッキングの基本アルゴリズムです。
再帰呼出しを用いて記述された深さ優先探索も、言語処理系が管理する呼出しスタックを暗黙のうちに活用しています。

## キューの順序を実装する

### 11 キュー――入口と出口が別の列

```text
取出し front → [A][B][C] ← rear 追加
```

キューは、データを取り出す出口（front）と新しくデータを投入する入口（rear）が対極に分離された待ち行列構造です。
末尾へ要素を追加する`enqueue`、先頭から要素を取り出して削除する`dequeue`、先頭要素を参照する`front`（または`peek`）、そして空判定を行う`isEmpty`などの基本操作を提供します。
FIFOとはFirst In, First Outの略称であり、最初に並んだデータから優先して処理される公平な順序規約を意味するわけです。

### 12 キューの操作を追う

```text
enqueue(A) [A]
enqueue(B) [A,B]
enqueue(C) [A,B,C]
dequeue()  Aを返し [B,C]
enqueue(D) [B,C,D]
```

窓口の先着受付、プリンタの印刷ジョブ管理、ネットワーク通信のパケットバッファなど、到着順序を厳密に保ちたい処理で不可欠となります。

### 13 単純な配列キューの問題

固定長配列を用いて素朴にキューを実装すると、要素を`dequeue`して取り出した前方領域に未使用の空き領域が取り残されてしまいます。
追加位置`rear`を右方向へ進めるだけの単純な設計では、`rear`が配列末尾に到達した時点で、前方に空き枠が存在するにもかかわらず新規追加不能に陥るわけです。

`dequeue`のたびに後続の全要素を1マスずつ左側へシフトさせると、1回の取り出しに`O(n)`の移動コストを強いられてしまいます。
シフトを行わずに`front`ポインタだけを右へ進めると、配列の左半分が空洞化したまま`rear`が右端で溢れてしまいます。

```text
[空][空][C][D][E]
        front     rearは端
```

この無駄な空き領域の断片化を解消するために考案されたのが、配列の末尾と先頭を環状に連結する循環キューの仕組みです。

### 14 循環キュー

配列の終端インデックスの直後が、再び先頭のインデックス0へと環状に接続されているかのようにインデックス計算を行う設計です。

```text
次の位置 = (現在位置 + 1) % capacity
```

容量が5枠の配列であれば、位置4の次の格納位置は剰余演算によりインデックス0へと安全に還流します。

```text
(4+1)%5=0
```

物理的には平坦な直線状のメモリ空間でありながら、モジュロ演算の導入によって論理的なリングバッファとして再定義できるわけです。

## 循環する配列の境界を定める

### 15 frontとrearの定義

循環キューの境界状態を厳密に管理するため、ポインタの役割を次のように明確に定義します。
`front`を取り出し対象が存在する現在位置、`rear`を次に新しい要素を書き込むべき空き位置と定義してみましょう。

```text
空条件：front == rear
```

しかしこの単純な取り決めだけでは、要素が1周して全枠が満杯になった際にも`front == rear`が成立してしまい、空状態と満杯状態の区別がつきません。

### 16 空と満杯を区別する方法

空状態と満杯状態の判定衝突を回避するには、配列の利用枠に1つの制約を設けるか、補助的な変数を併用します。

1つの有力な設計パターンは「配列の1枠を常にダミーの空き枠として予約しておく」手法です。
容量が5の配列であっても最大4要素までしか格納を許可せず、` (rear + 1) % capacity == front `となった状態を満杯と定義します。
あるいは現在の有効要素数を記録するカウンタ変数`count`を独立して保持し、`count == 0`を空、`count == capacity`を満杯と判定する設計も明快です。
どちらの境界判定方式を採用しているかを設計書に明記し、判定計算式を混同しないよう注意します。

### 17 循環キューのenqueueとdequeue

要素数カウンタ`count`を併用する方式における循環キューの実装ロジックを確認してみましょう。

```text
関数 enqueue(x)
    もし count == capacity ならエラー
    data[rear] = x
    rear = (rear + 1) % capacity
    count = count + 1
```

```text
関数 dequeue()
    もし count == 0 ならエラー
    x = data[front]
    front = (front + 1) % capacity
    count = count - 1
    xを返す
```

要素の追加も取り出しもポインタと変数の更新のみで完結するため、どちらの操作も定数時間の`O(1)`で高速に完了します。

### 18 連結リストでキューを作る

単方向連結リストの先頭ノードを`front`、末尾ノードを`rear`として割り当てると、要素数無制限の動的キューを容易に構築可能です。

```text
front → A → B → C ← rear
```

`enqueue`は`tail`ポインタの直後へ新規ノードを追加して`tail`を進め、`dequeue`は`head`ポインタの先頭ノードを1つ進めて返却します。
要素の追加と削除はいずれも`O(1)`の定数時間で動作する優れた構造です。
最後の1要素を`dequeue`してキューが完全に空になった局面では、`front`だけでなく`rear`ポインタもNULLへとリセットするケアを忘れてはなりません。

## 仕事を取り出す順序を選ぶ

### 19 幅優先探索

探索開始地点から近い順（辺の経由数が少ない順）にグラフの頂点を網羅的に探索する幅優先探索（BFS: Breadth First Search）ではキューを用います。

```text
Aの隣B,Cをenqueue
Bをdequeueし、その未訪問隣接Dをenqueue
Cをdequeueし、Eをenqueue
```

このアルゴリズムに従うと、頂点を探索する順序はA、B、C、D、Eの順序となるわけです。
すべての辺の重みが均一なグラフ構造においては、最初にある頂点に到達した経路こそが最短経路となる特性を備えています。

### 20 メッセージキュー

処理を依頼する送信側システムと、依頼を実際に実行する受信側システムの間をキューで疎結合に中継する非同期アーキテクチャがメッセージキューです。

```text
送信者 → [メッセージの列] → 受信者
```

生産者と消費者の処理速度の乖離をキューが一時的に吸収し、一時的な高負荷やシステム障害時にもリクエストの損失を防止できます。
ただしネットワーク再送に伴って同一メッセージが重複して届くリスクや、並行ワーカーによる処理順序の逆転などが発生し得ます。
したがって、メッセージの重複排除（冪等性の確保）、順序保証の要否、満杯時の溢れ制御、デッドレターキューによる異常メッセージの隔離などを総合的に設計しなければなりません。

### 21 優先度付きキュー

通常のFIFOキューは到着時刻が早いものを優先して払い出します。
これに対し、タスクの締切や障害の緊急度など、データ自身が持つ優先度スコアに基づいて最重要の要素から順に取り出したい場面では「優先度付きキュー」を用います。

```text
緊急障害 優先度10
通常処理 優先度1
```

ここで**ヒープ**とは、親ノードと子ノードの間に常に一定の大小関係が成立し、根ノードから最小値または最大値を効率よく取り出せる完全二分木構造です。
優先度付きキューを二分ヒープを用いて実装すると、要素の追加および最高優先度要素の取り出しの双方を`O(log n)`の計算量で実現できます。
なお、優先度の低いタスクが永遠に処理されずに放置される飢餓状態（スタベーション）を未然に防止するため、キュー内の滞留時間に応じて優先度を徐々に底上げするエージング処理の導入が有効です。

### 22 両端キュー

列の先頭端と末尾端の両側から要素の追加と削除を自由に行える柔軟なキュー構造を両端キュー（deque: double-ended queue）と呼びます。

```text
左端 ← [A][B][C] → 右端
```

両端キューはスタックとキューの双方の振る舞いを併せ持ち、特定アルゴリズムの高速化に広く貢献します。
**スライディングウィンドウ**とは、配列上の連続する一定区間を1要素ずつ横にずらしながら、区間から外れる要素を捨て、新たに入る要素を迎え入れることで、区間内の統計量を効率的に再計算する手法です。
両端キューはこのスライディングウィンドウにおける最大値・最小値の追跡や、並行処理における作業分配（ワークスティーリング）の実装基盤として重宝されます。

## 用途と操作の契約を合わせる

### 23 スタックかキューかを選ぶ

直前の操作を打ち消して履歴を逆順に巻き戻したい場合や、関数の呼び出し関係のようにネストした構造を局所的に解決したい場合はスタックが最適です。
一方、業務の到着順に従って公平に処理を進めたい場合や、出発点から距離が近い順に空間を探索したいシナリオではキューを選定します。

皿を上から順に取り出すように直前の文脈へと回帰するならスタックを採用するわけです。
受付窓口の列のように先着順でリクエストを捌いていくならキューの採用が妥当となります。

### 24 操作の契約

抽象データ型としてのスタックやキューを運用する際は、境界時のインターフェース仕様を明確に取り決めます。

空の状態で取り出し操作を試みた際の例外処理、内部バッファが満杯の際の受け入れ拒否方針、NULL要素の許容性、マルチスレッド環境における並行アクセスの排他制御、そして各操作の最悪計算量などがその典型です。
内部の具象実装を配列から連結リストへと差し替えたとしても、これらの外部契約が堅牢に維持されていれば、利用側のビジネスロジックを一切壊すことなく安全に保守できます。
