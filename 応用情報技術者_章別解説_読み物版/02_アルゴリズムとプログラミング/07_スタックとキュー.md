# 第2章・第7話　スタックとキュー――取り出す順序を、データ構造の規則にする

食堂の皿を上に積むと、最後に置いた皿を最初に取ります。
受付の列では、最初に並んだ人を最初に案内します。

この2つの順序を、データ構造として定めます。

- スタック：後入れ先出し、LIFO。
- キュー：先入れ先出し、FIFO。

保存した値が同じなら、入れ物の違いは実装上の都合に見えるかもしれません。
取り出す順序が違えば、同じ値を入れても次に処理される値が変わります。

どちらも「値の置き場所」だけでなく、「どこから追加し、どこから取り出せるか」という操作規則を含む抽象データ型です。

---

## 1 スタック――上だけを使う積み重ね

```text
上 top → [C] 最後に入れた
         [B]
         [A] 最初に入れた
```

基本操作は、

- push：上に積む。
- pop：上から取り出し、削除する。
- top、peek：上の値を見るが、削除しない。
- isEmpty：空か調べる。

です。

LIFOはLast In, First Out、最後に入れたものが最初に出るという意味です。

## 2 pushとpopを追う

空から始めます。

```text
push(A)  [A]
push(B)  [A,B]  ←右を上とする
push(C)  [A,B,C]
pop()    Cを返し [A,B]
pop()    Bを返し [A]
```

pushとpopは、どちらも一端だけを操作します。

## 3 アンダーフローとオーバフロー

`pop`は上の値を返す操作ですが、空のときには「上の値」が存在しません。
固定長の配列なら、空きがないときの`push`にも同じ種類の境界が現れます。

### アンダーフロー

空のスタックからpopしようとします。
返す値がありません。

例外、エラー値、失敗結果などで通知します。
エラー値に通常データと同じ値を使うと区別できません。

### オーバフロー

固定容量のスタックが満杯なのにpushします。

動的に拡張する、追加を拒否する、古い値を捨てるなど、用途に応じます。
黙って隣の記憶域に書いてはいけません。

## 4 配列でスタックを作る

配列と、現在の要素数`top`を使います。
ここでは`top`を「次に入れる位置」とします。

```text
data = 容量5の配列
top = 0
```

pushします。

```text
関数 push(x)
    もし top == capacity ならエラー
    data[top] = x
    top = top + 1
```

popします。

```text
関数 pop()
    もし top == 0 ならエラー
    top = top - 1
    data[top]を返す
```

popでは、先にtopを1減らして、最後の有効要素位置に戻ります。

`top`を最上要素の添字と定義する実装もあります。
定義を混ぜないでください。

## 5 連結リストでスタックを作る

リストの先頭をスタックの上にします。

```text
top → C → B → A
```

- push：先頭挿入。
- pop：先頭削除。

どちらも`O(1)`です。
容量は利用可能メモリまで増やせますが、ノードごとに参照欄が必要です。

## 6 関数呼出しにスタックを使う

関数AがBを呼び、BがCを呼びます。

```text
push Aの呼出し枠
push Bの呼出し枠
push Cの呼出し枠
```

Cが先に終わり、次にB、最後にAに戻ります。
最後に呼んだ関数から戻るのでLIFOです。

呼出し枠には、戻り先、引数、ローカル変数などが入ります。

## 7 元に戻す操作

文書編集で操作をスタックに積みます。

```text
文字Aを追加
文字Bを追加
段落を削除 ← 一番上
```

「元に戻す」は最後の操作をpopし、その逆操作を行います。

「やり直す」には、取り消した操作を別のredoスタックに積みます。
新しい操作を行ったら、redo履歴を捨てるのが一般的です。

## 8 括弧の正しさを検査する

```text
([]{})
```

左から読みます。

1. 開き括弧ならpush。
2. 閉じ括弧なら、空でないことを確認しpop。
3. popした開き括弧と種類が対応するか確認。
4. 最後にスタックが空なら正しい。

```text
([)]
```

では`)`を読んだとき、一番上は`[`なので種類が合いません。

括弧の個数だけ数えても、順序と種類の不一致を見つけられません。

## 9 逆ポーランド記法を計算する

```text
3 4 5 × +
```

1. 数ならpush。
2. 演算子なら2つpop。
3. 計算結果をpush。

```text
3     [3]
4     [3,4]
5     [3,4,5]
×     4×5=20 → [3,20]
+     3+20=23 → [23]
```

引き算・割り算では、後にpopした方が左の値です。

```text
8 2 -
最初に2をpop、次に8をpop
8-2=6
```

## 10 深さ優先探索とバックトラック

迷路で1つの道を奥に進み、行止まりなら直前の分岐に戻るには、未処理の分岐や経路をスタックに積みます。

これが深さ優先探索、DFSとバックトラッキングの基本です。

再帰で書いた深さ優先探索も、呼出しスタックを暗黙に使っています。

## 11 キュー――入口と出口が別の列

```text
取出し front → [A][B][C] ← rear 追加
```

基本操作は、

- enqueue：末尾に追加。
- dequeue：先頭から取り出し、削除。
- front、peek：先頭を見る。
- isEmpty：空か調べる。

です。

FIFOはFirst In, First Out、最初に入れたものが最初に出るという意味です。

## 12 キューの操作を追う

```text
enqueue(A) [A]
enqueue(B) [A,B]
enqueue(C) [A,B,C]
dequeue()  Aを返し [B,C]
enqueue(D) [B,C,D]
```

先着順の受付、印刷待ち、通信要求などに使います。

## 13 単純な配列キューの問題

取り出した先頭側には空きが残ります。
ところが、追加位置を右へ進めるだけの実装では、末尾に着いた時点でその空きを再利用できません。

先頭を0、末尾を要素数として、dequeueのたび全要素を左にずらすと、1回`O(n)`です。

ずらさずfrontだけ右に進めると、配列の左側に空きがあるのに、rearが右端に到達します。

```text
[空][空][C][D][E]
        front     rearは端
```

そこで配列を輪として使います。

## 14 循環キュー

末尾の次を配列先頭に戻します。

```text
次の位置 = (現在位置 + 1) % capacity
```

容量5で位置4の次は、

```text
(4+1)%5=0
```

です。

物理的には1列の配列ですが、論理的に輪として扱います。

## 15 frontとrearの定義

一例として、

- `front`：次に取り出す要素の位置。
- `rear`：次に追加する空き位置。

とします。

```text
空条件：front == rear
```

しかし、このままでは満杯で1周した場合も`front==rear`になり、空と区別できません。

## 16 空と満杯を区別する方法

`front`と`rear`が同じなら空、と決めるだけでは足りません。
循環して最後の枠まで埋めたときにも、両者が同じ位置へ戻り得るからです。

### 一枠を常に空ける

次のrearがfrontなら満杯とします。
容量5でも最大4要素です。

```text
(rear+1)%capacity == front → 満杯
```

### 要素数countを別に持つ

```text
count==0 → 空
count==capacity → 満杯
```

### フラグを持つ

最後の操作が追加か削除かなどを記録します。

どの定義を使うか明記し、式を混ぜません。

## 17 循環キューのenqueueとdequeue

countを持つ方式です。

```text
関数 enqueue(x)
    もし count == capacity ならエラー
    data[rear] = x
    rear = (rear + 1) % capacity
    count = count + 1
```

```text
関数 dequeue()
    もし count == 0 ならエラー
    x = data[front]
    front = (front + 1) % capacity
    count = count - 1
    xを返す
```

どちらも`O(1)`です。

## 18 連結リストでキューを作る

headをfront、tailをrearにします。

```text
front → A → B → C ← rear
```

- enqueue：tail後に追加し、tailを更新。
- dequeue：headを次に進める。

どちらも`O(1)`です。

最後の1要素をdequeueして空になったとき、frontだけでなくrearもNULLにします。

## 19 幅優先探索

入口から辺の本数が少ない順に頂点を調べる幅優先探索、BFSではキューを使います。

```text
Aの隣B,Cをenqueue
Bをdequeueし、その未訪問隣接Dをenqueue
Cをdequeueし、Eをenqueue
```

調べる順はA,B,C,D,Eです。

重みなしグラフでは、最初に到達したときの辺数が最短です。

## 20 メッセージキュー

送信側と受信側を切り離せば、障害も互いに影響しないように見えます。
実際には、再試行で同じメッセージが複数回届くことや、複数の受信側で処理順が変わることまで決める必要があります。

送信側が仕事をキューに入れ、受信側が後で取り出す構成があります。

```text
送信者 → [メッセージの列] → 受信者
```

処理速度の違いを吸収し、一時障害から再試行できます。

ただし、

- 順序保証。
- 同じメッセージが複数回届く可能性。
- 満杯時の動作。
- 処理失敗と再試行。
- 永久に失敗するメッセージの隔離。

を設計します。

## 21 優先度付きキュー

待ち時間を公平にするならFIFOで足ります。
締切や緊急度を優先すると、後から来た要素が先に出るため、低優先度の要素が長く残る可能性が生まれます。

単純なFIFOではなく、優先度が高い要素を先に取り出します。

```text
緊急障害 優先度10
通常処理 優先度1
```

ここで**ヒープ**は、親子間の大小関係を保ち、最小値または最大値を根から速く取り出せる完全二分木です。
優先度付きキューをヒープで実装すると、追加・最優先取出しを`O(log n)`で行えます。
構造と計算量は次話の[木とヒープ](08_木とヒープ.md)で導きます。

低優先度が永遠に処理されない飢餓を防ぐため、待ち時間で優先度を上げるエージングなどを使います。

## 22 両端キュー

両端から追加・削除できるキューをdeque、デックと呼びます。

```text
左端 ← [A][B][C] → 右端
```

スタックとキューの両方に似た操作を提供します。
**スライディングウィンドウ**は、列の連続区間を1要素ずつずらし、出る要素を除き入る要素を加えるなどして、区間内の和・最大値を毎回全計算せず更新する方法です。
両端キューは区間の端から不要要素を除く実装や作業分配に使われます。

## 23 スタックかキューかを選ぶ

### スタック

- 最新の操作から戻す。
- 入れ子構造。
- 1つの道を深く探索。
- 関数呼出し。

### キュー

- 到着順に処理。
- 近い場所から探索。
- 生産者と消費者の速度差を吸収。
- 待ち仕事を保存。

「最後を先にするか」「最初を先にするか」をまず問います。

## 24 操作の契約

抽象データ型として、次を明確にします。

- 空でpop/dequeueしたらどうなるか。
- 満杯で追加したらどうなるか。
- NULLを要素として入れられるか。
- 順序は保証されるか。
- 複数処理から同時に使えるか。
- 操作の最悪時間は何か。

実装が配列かリストかを変えても、この契約を守ります。
