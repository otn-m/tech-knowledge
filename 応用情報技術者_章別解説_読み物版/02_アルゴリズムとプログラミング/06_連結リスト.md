# 第2章・第6話　連結リスト――離れた要素を「次の場所」でつなぐ

配列の途中に要素を挿入する場合、後続のすべての要素を物理的にシフトさせる必要があります。
対して連結リストでは、要素同士を結びつける参照ポインタを付け替えるだけで順序関係を再構成可能です。
ただし、ポインタを付け替える対象位置がすでに判明している状況と、その位置を先頭から探索する状況とでは、所要時間のオーダーが大きく異なります。

連結リストの動作を追跡する際は、格納されたデータ値そのものに加えて、どの要素からどの要素へとポインタが到達可能であるかを厳密に辿ります。
挿入や削除の実行途中で参照関係を誤って見失ってしまうと、後続のノード群がメモリ上に実在しているにもかかわらず永久に到達できなくなるためです。

## リンクをたどって要素に到達する

### 1 ノードとリンク

連結リストを構成する個々の要素単位をノード（節点）と呼びます。
単方向リストにおける各ノードは、格納すべきデータ本体と、次のノードのメモリ位置を示す参照ポインタをペアとして保持する構造です。
この参照関係はポインタ、あるいは単にリンクとも呼ばれます。

```text
Node
  data
  next
```

リストの終端に位置する末尾ノードの`next`フィールドには、後続ノードが存在しないことを示すNULL（空ポインタ）を格納します。

### 2 先頭参照

リスト全体のデータ構造を管理・走査するためには、先頭ノードの存在場所を指し示すポインタが不可欠です。

```text
head → [A|・] → [B|・] → [C|NULL]
```

もし`head`ポインタの値を誤って上書きして失ってしまうと、他に参照経路が存在しない限りすべてのノードへ到達できなくなってしまいます。

要素が1つも存在しない空のリストにおいては、`head=NULL`として表現するのが通例です。

### 3 順番は住所ではなくリンクで決まる

ノードA、B、Cが配置されたメモリアドレスが物理的に遠く離れていたとしても、ポインタがA→B→Cと連結されていれば論理的にはこの順番で要素を走査できます。

```text
A 100番地
B 700番地
C 240番地
```

主記憶上の物理的な番地順序と、リンクポインタが規定する論理的な並び順は完全に直交した概念です。

### 4 リストを走査する

```text
current = head
while current != NULL
    current.dataを処理
    current = current.next
```

変数`current`は、現在処理対象として着目しているノードへのポインタを表しています。

走査処理は各ノードをちょうど1回ずつ通過するため、n個の要素を持つリストの全件走査にかかる計算量は`O(n)`です。

ループ処理の末尾で`current=current.next`というポインタの更新を失念すると、同一ノードを永久に処理し続ける無限ループへ陥ります。

### 5 i番目へ直接飛べない

先頭ノードを1番目として10番目のノードの値を取得したい場合であっても、先頭からポインタを順に9回たどらなければなりません。
0始まりの添字体系を採用する場合、添字10の要素へ到達するには先頭から10本のリンクを経由する必要があります。

```text
0番 → 1番 → 2番 → ... → 10番
```

目的の位置が先頭から離れるほど経由すべきリンクの本数が線形に増大するため、任意位置の参照操作の計算量は`O(n)`に達します。
メモリアドレスの直接計算によって瞬時に要素を特定できる配列構造の`O(1)`とは、ここが決定的な相違点です。

## 参照を保持して順序を変える

### 6 先頭へ挿入する

次のように要素が連結された初期リストを想定してみましょう。

```text
head → A → B → C
```

ここに新しいノードXを先頭要素として挿入する手順は次のとおりです。

1. `X.next=head`を設定し、Xから従来の先頭ノードAへのリンクを確立する。
2. `head=X`を設定し、リスト全体の先頭ポインタをXへ更新する。

```text
head → X → A → B → C
```

ここで最も重要なのはポインタ更新の順序関係です。
もし先に`head=X`を実行してしまうと、従来の先頭ノードAを指す参照が消失し、後続リスト全体を見失ってしまいます。

ポインタの付け替え操作自体は定数ステップで完結するため、計算量は極めて高速な`O(1)`です。

### 7 途中へ挿入する

リストの途中に新しいノードを割り込ませる際は、挿入位置の直前に位置するノードへのポインタを参照します。
直前ノードのポインタがあらかじめ特定されていれば、必要な作業は2本のリンクの更新のみで済みます。

ノードAとBの間に新しいノードXを挿入してみましょう。

```text
A → B
```

1. `X.next=A.next`を実行し、XからノードBへの接続を確立する。
2. `A.next=X`を実行し、AからノードXへのリンクを確立する。

```text
A → X → B
```

先に`A.next=X`を書き換えてしまうとノードBへの到達経路が断たれるため、一時退避ポインタがない限り後続ノードを喪失する危険を伴います。

挿入位置の直前ノードAの参照がすでに手元にある前提であれば、リンク付け替えの計算量は`O(1)`です。
しかしノードAの位置を先頭から探す必要があるケースでは、探索処理に`O(n)`の時間を要します。

挿入アルゴリズムの計算量を評価する際は、位置探索にかかる費用も含めて総合的に判断しなければなりません。

### 8 削除する

単方向リストから特定ノードBを安全に削除するには、ノードBへ向かっている先行リンクをバイパスさせる必要があります。
ノードAの`next`をノードCへ付け替える必要があるため、削除対象Bだけでなく、その直前に位置するノードAのポインタが不可欠です。

連結A→B→Cから中間ノードBを切り離してみましょう。

```text
A.next = B.next
```

このポインタ付け替えを実行した結果、リストの論理構造はA→Cへと更新されます。

削除対象の直前ノードAがすでに判明していれば、ポインタのバイパス処理は`O(1)`で完了します。
しかし対象ノードBのポインタしか保持していない場合、単方向リストでは手前のノードへ逆行できない点に注意が必要です。

ノードの切り離しを終えた後、C言語のように手動メモリ管理を行う環境では不要となったノードBの領域を確実に解放します。
ガベージコレクションを備えた言語処理系であれば、誰からも参照されなくなった時点でメモリが自動的に回収される仕組みです。

### 9 末尾参照

リストの末尾へのデータ追加が高い頻度で発生するユースケースでは、末尾ノードを直接指し示す専用ポインタ`tail`を併せて保持します。

```text
head → A → B → C ← tail
```

新しいノードXを末尾に追加するには、現在の末尾ノードからXへリンクを結び、その直後に`tail`ポインタをXへと進めます。
この2ステップの更新はいずれも定数時間であり、`O(1)`で即座に完了可能です。

```text
tail.next = X
tail = X
```

要素数0の空リストに最初のノードXを挿入する際は、`head`と`tail`の双方にノードXのポインタを設定します。
逆にリストの最後の1要素を削除した局面では、両方のポインタをNULLへとリセットする後処理が必要です。

### 10 番兵ノード

有効なデータ値を格納しないダミーの先頭ノードを「番兵ノード（sentinel node）」として常駐させる設計パターンが存在します。

```text
sentinel → A → B → C
```

空リストの状態であっても番兵ノード自体はメモリ上に常に存在するため、先頭への要素挿入や先頭要素の削除を、中間位置の操作とまったく同一のロジックで統一的に扱えます。
なお番兵ノードは管理用の補助ノードにすぎないため、リストの要素数をカウントする際には計算対象から除外するルールです。

## 前後と循環のリンクを持たせる

### 11 双方向リスト

各ノードに対して後続ノードへのリンク（next）だけでなく、先行ノードへのリンク（prev）も併せて保持させるデータ構造を双方向リストと呼びます。

```text
NULL ← A ⇄ B ⇄ C → NULL
```

```text
Node
  data
  prev
  next
```

双方向リストを採用すると、ポインタを前後の両方向へ自由に行き来でき、自身のノード情報さえ分かっていれば直前ノードを即座に特定して削除できる構造です。
その反面、ノードごとにポインタ領域のメモリ消費が増大し、挿入や削除の際に保守すべきリンクの本数も倍増するトレードオフを抱えています。

### 12 双方向リストへ挿入する

双方向リストに新しいノードを挿入する際は、新ノードから前後へ向かう2本のポインタと、両隣のノードから新ノードへ向かう2本のポインタの計4本を更新します。

ノードAとBの間に新ノードXを割り込ませる例を考えてみましょう。

```text
X.prev = A
X.next = B
A.next = X
B.prev = X
```

この4つのポインタ更新のうち1本でも設定を誤ると、「前方へは進めるが後方へは戻れない」といったリンク不整合のバグを引き起こします。

更新処理を実装した後は、リスト全体で次の不変条件が満たされているかを必ず検証することが不可欠です。

- 任意のノードにおいて、`node.next.prev == node`が成立すること。
- 任意のノードにおいて、`node.prev.next == node`が成立すること。
- 先頭ノードの`prev`がNULLを指していること。
- 末尾ノードの`next`がNULLを指していること。

### 13 環状リスト

末尾ノードの`next`ポインタをNULLで終わらせず、リストの先頭ノードへと循環させてループを形成する構造を環状リスト（循環リスト）と呼びます。

```text
A → B → C
↑       ↓
└───────┘
```

タスクを順番に巡回して割り当てるラウンドロビン方式のスケジューリングなどで重宝される設計です。

ポインタをたどっても決してNULL終端に達しないため、探索の開始ノードに戻ってきたことや既定回数の処理を終えたことを終了条件として設計します。
終了判定の設計を誤ってしまうと、脱出不能な無限ループに陥る点に注意が必要です。

## 抽象的な操作と記憶配置を分ける

### 14 線形リストという抽象概念

データ要素が一列の直線的な順序関係を持って並んでいるデータ構造全般を、情報科学では線形リストと総称します。
線形リストという抽象的な仕様は、連続メモリを用いる配列（順次リスト）としても、ポインタを用いる連結リストとしても実装可能です。

「リストに対してどのような操作が提供されるか」という抽象データ型としてのインターフェースと、「それをメモリ上でどう配置するか」という具象実装は切り離して捉えます。

### 15 メモリ配置と局所性

配列構造では各要素がメモリ上に隙間なく連続して配置されているため、空間的局所性に優れ、CPUキャッシュの恩恵を最大限に享受できる構造です。

一方で連結リストの各ノードは、ヒープ領域上の散らばったアドレスに分散して確保される傾向があります。
次のノードのアドレスを読み出してからでなければ次の要素へアクセスできず、キャッシュミスが多発しやすい性質を抱えているわけです。
加えてデータ本体のメモリ幅に加えてポインタ格納用のオーバーヘッドが要求される点にも注意が必要です。
計算量理論上は同じ`O(n)`の走査であっても、物理的なメモリ局所性の差異によって実測の処理速度には大きな開きが生じます。

### 16 メモリ管理の危険

手動で動的メモリの確保と破棄を制御する低水準言語では、ポインタ操作の不備が深刻な不具合を招きます。

メモリリークは確保したノードの解放を怠ったままポインタを喪失する事象であり、ダングリングポインタはすでに破棄されたメモリ領域を指す無効ポインタを誤って読み書きする危険なバグです。
さらに同一のメモリ領域を重複して解放する二重解放や、無効なNULL番地をノード実体と誤認して参照するNULLポインタ参照などにも厳重な警戒が求められるところです。

ガベージコレクションを備えた環境であっても、不要となったノードへの参照をリスト内に放置し続ければメモリ回収が行われず、実質的なメモリリークへと発展します。

### 17 循環参照

ノードAがノードBを参照し、同時にノードBがノードAを参照し合っているような閉じた循環関係を循環参照と呼ぶわけです。

```text
A → B
↑   ↓
└───┘
```

参照カウント方式を採用した素朴なメモリ管理機構では、外部からのアクセス経路が完全に途絶えた後も互いの参照カウンタが0にならず、メモリ領域が回収不能に陥るケースがあります。
プログラムのルート（大域変数やコールスタック）から到達可能かどうかを有向グラフとして探索するトレーシングGCであれば、孤立した循環構造も漏れなく安全に回収可能です。

## 逆順への変更を不変条件で確かめる

### 18 リストを逆順にする

単方向リストA→B→Cのポインタの向きをその場で反転させ、C→B→Aへと逆転させる典型的なアルゴリズムを追跡してみましょう。

この操作を一時配列を使わずに実現するには、3つのポインタ変数を協調して運用します。

```text
prev = NULL
current = head

while current != NULL
    nextNode = current.next
    current.next = prev
    prev = current
    current = nextNode

head = prev
```

反復ループの各周回においては、後続のポインタを見失わないよう次の3ステップを厳密な順序で実行するわけです。

1. 後続ノードへの到達経路を失わないよう、`current.next`を`nextNode`に退避する。
2. 着目中のノードのリンクを反転させ、直前のノード`prev`へ向ける。
3. `prev`と`current`のポインタ変数をそれぞれ1ステップずつ前方へ前進させる。

後続ポインタの退避を行う前にリンクを書き換えてしまうと、未処理のリスト領域へ二度とアクセスできなくなってしまいます。

### 19 ループ不変条件で逆順を説明する

上記の反転アルゴリズムにおいて、各ループ周回の先頭時点では常に次の不変条件が成立しています。

- ポインタ`prev`を起点として、処理済みのノード群が完全に逆順で連結されていること。
- ポインタ`current`を起点として、未処理のノード群が元の順序関係を維持したまま連結されていること。

1つのノードを未処理側から処理済み側へ移送してもこの論理的関係性が崩れないため、最終的に`current=NULL`に達した時点でリスト全体の反転が数学的に完了するわけです。

## 操作の条件を含めて計算量を比べる

### 20 リストでよく使う操作の計算量

単方向リストにおける各種基本操作の計算量を整理すると、目的位置のノードポインタが事前に得られているか否かによって性能特性が大きく分岐する点に注目が必要です。

| 操作 | 代表的な計算量 |
|---|---:|
| 先頭参照 | O(1) |
| i番目参照 | O(n) |
| 値の探索 | O(n) |
| 先頭挿入 | O(1) |
| 既知ノード後に挿入 | O(1) |
| 挿入位置を探して挿入 | O(n) |
| 既知の前ノードがある削除 | O(1) |
| tailありの末尾追加 | O(1) |


### 21 配列とリストを比べる

配列と連結リストでは、要素の参照、途中への挿入、そしてメモリ領域の拡張にかかる計算コストが大きく異なります。

| 観点 | 配列 | 連結リスト |
|---|---|---|
| i番目参照 | O(1) | O(n) |
| 途中挿入 | 要素移動O(n) | 場所が既知ならリンク変更O(1) |
| メモリ | 連続領域 | ノードごとに分散可能 |
| 追加情報 | 少ない | ポインタが必要 |
| キャッシュ局所性 | 良い傾向 | 悪い傾向 |
| 容量拡張 | 再確保・コピー | ノードごとに追加 |

ノードAとBの間に新しいノードXを挿入するシナリオにおいて、直前のノードAをすでに手元に保持していれば、連結リストのポインタ付け替えは瞬時の`O(1)`で完了する仕組みです。
しかしノードAの位置を先頭から探索しなければならない状況であれば、その探索時間`O(n)`が支配的となります。
システムのアクセス頻度、取り扱うデータ件数、そしてキャッシュ効率を総合的に勘案した上で、要件に最適なデータ構造を選択する姿勢が大切です。
