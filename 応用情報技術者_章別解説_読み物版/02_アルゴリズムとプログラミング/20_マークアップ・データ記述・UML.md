# 第2章・第20話　マークアップ・データ記述・UML――構造を文字と図で伝える

文書の見出しを示すタグ、商品の値を送るデータ、注文処理を表す図は、いずれも構造を相手に伝達するための表記体系です。
共通の構文形式に従って記述すれば、受取側も同一のデータ構造として機械的に解析できます。
ただし、価格の通貨単位、値の業務制約、部品間の協調関係までは、構文規則だけで一意に定まるわけではありません。

マークアップ言語、データ記述言語、UMLについて、何を表せるか、どの規則を機械検査できるか、意味の合意がどこに必要となるかを順に整理していきます。

## 第1部　マークアップ言語

### タグで文書の構造を表す

#### 1 マークアップとは何か

文章に「ここは見出し」「ここは段落」「ここは重要語」という論理的な印を付ける行為を、マークアップと呼びます。

```html
<h1>今日の献立</h1>
<p>カレーを作ります。</p>
```

`<h1>`や`<p>`がその印に該当するわけです。
マークアップの体系的な記述規則を定めた言語が、**マークアップ言語**です。

実行処理の手順を命令する言語形態と異なり、文書やデータの論理構造や意味属性を明示的に記述する役割を担います。

#### 2 タグ、要素、内容

HTMLやXMLでは、山括弧で囲んだ印をタグと呼びます。

```html
<p>こんにちは</p>
```

- `<p>`は開始タグ。
- `</p>`は終了タグ。
- `こんにちは`は内容。
- 開始タグから終了タグまで全体が要素。

終了タグに含まれるスラッシュ記号`/`は、「この要素がここで終了する」ことを示す印です。

#### 3 属性

要素に追加のメタデータを付与する仕組みを、属性と呼びます。

```html
<a href="https://example.com">案内</a>
```

`href`が属性名、指定されたURLが属性値です。
アンカーを示す`a`要素は、外部リソースへのリンク関係を表現します。

属性値は引用符で囲む記法が構文上安全とされます。
各属性の意味や許容される値の範囲は、言語仕様によって厳密に規定されるわけです。

#### 4 入れ子

要素の内部にさらに別の要素を包含させる入れ子（ネスト）構造も可能です。

```html
<p>これは<strong>重要</strong>です。</p>
```

タグを開いた順序の逆順で正しく閉じる必要があります。

```html
正しい: <p><strong>文字</strong></p>
誤り:   <p><strong>文字</p></strong>
```

Webブラウザは一部の構文誤りを寛容に推測修復しますが、レンダリング結果が設計意図どおりになるとは限りません。
一方、XMLではこの種の構文破綻を一切許容しない厳格な設計をとるわけです。

#### 5 特別な文字のエスケープ

本文中に文字として`<`を直接記述すると、タグの開始記号として構文解析されてしまいます。
そのため実体参照と呼ばれる特別な表記へと置き換えます。

```html
&lt;   → <
&gt;   → >
&amp;  → &
&quot; → "
```

文脈上の特殊文字を文字データとして無害化する変換が、エスケープです。
Webセキュリティの観点からも極めて重要な基礎技術に位置づけられます。

### HTMLの要素と文書型を使う

#### 6 HTML

**HTML**（HyperText Markup Language）は、Web文書の構造と意味を表すマークアップ言語です。

その最小限の文書骨格を次の例に示します。

```html
<!doctype html>
<html lang="ja">
  <head>
    <meta charset="utf-8">
    <title>料理の紹介</title>
  </head>
  <body>
    <h1>カレー</h1>
    <p>野菜を煮込む料理です。</p>
  </body>
</html>
```

- `doctype`は文書をHTMLとして標準的に解釈させる宣言。
- `html`は文書全体。
- `head`は題名や設定など文書情報。
- `body`は画面上の主内容。
- `meta charset`は文字符号化を示す。
- `title`はブラウザのタブなどに出る題名。

#### 7 代表的なHTML要素

- `h1`〜`h6`――見出しの階層。
- `p`――段落。
- `a`――リンク。
- `img`――画像。
- `ul`、`ol`、`li`――箇条書き。
- `table`、`tr`、`th`、`td`――表。
- `form`、`label`、`input`、`button`――入力フォーム。
- `header`、`nav`、`main`、`article`、`section`、`footer`――文書上の役割。

文字を大きく見せる装飾目的を排し、文書全体の最上位見出しという論理的階層に基づいて`h1`を選択します。
視覚的な見た目の調整は、後述するスタイルシートに委ねるわけです。

#### 8 ハイパーテキスト

文書から別文書や特定位置へ相互に参照を結び、非直線的に移動できる文書体系を、ハイパーテキストと呼びます。
HTML（HyperText Markup Language）の名称もこの概念に由来します。

```html
<a href="chapter2.html">第2章へ</a>
```

参照先は相対URLまたは絶対URLで指定可能です。
相対URLは現在の配置場所を基準とするため、文書一式を別サーバや別階層に移送しやすい利点があります。

#### 9 SGML

SGML、Standard Generalized Markup Languageは、文書の構造を記述するマークアップ言語を定義するための大きな枠組み、メタ言語です。

HTMLは歴史的にSGMLの応用仕様として策定されました。
XMLもまた、SGMLの設計思想を基礎としつつ、Web上で軽量に扱えるよう仕様を大幅に簡素化した言語です。

単一のタグセットというより、SGMLが多様な文書型を定義するための共通基盤であったと捉える形をとるわけです。

#### 10 DTD

文書で使える要素、順序、属性などを定義するものをDTD、Document Type Definition、文書型定義と呼びます。

概念的な例です。

```text
book要素はtitleの後にchapterを1個以上持つ
chapter要素はheadingとparagraphを持つ
```

```dtd
<!ELEMENT book (title, chapter+)>
<!ELEMENT title (#PCDATA)>
<!ELEMENT chapter (heading, paragraph+)>
```

定義されたDTDに基づき、対象文書が構文規約を満たしているかを機械的に検査できます。
現代のHTML標準では、かつての複雑なDTD宣言に代えて極めて簡潔な`<!doctype html>`を採用しているわけです。

### XMLの文法と用途の規則を分ける

#### 11 XML

**XML**（Extensible Markup Language）は、用途に応じて独自のタグ名を定義し、構造化データを文字列表現できるマークアップ言語を指します。

```xml
<?xml version="1.0" encoding="UTF-8"?>
<product id="42">
  <name>鉛筆</name>
  <price currency="JPY">120</price>
</product>
```

`product`や`name`、`price`は、この業務用途に合わせて独自に定義したタグ名です。
XML仕様自体が「price」の業務的意味を定義しているわけではありません。
送受信者間でタグの構造と意味規則をあらかじめ合意しておく必要があります。

#### 12 XMLの整形式

XMLの基本文法を守った文書を、**整形式**（well-formed）と呼ぶわけです。

主な規則です。

- 文書全体を囲む根要素が1つある。
- 開始タグには対応する終了タグがある。
- 入れ子を正しく閉じる。
- 要素名の大文字・小文字を区別する。
- 属性値を引用符で囲む。
- 特別文字をエスケープする。

内容のない要素は、次のように空要素タグで閉じられます。

```xml
<br />
```


#### 13 妥当なXML

整形式であることに加え、DTDやXML Schemaで定めた文書型に従うものを妥当、validと呼びます。

次の文書は基本文法上の整形式ですが、仕様が`product`内に`name`と`price`だけを許すなら、妥当ではありません。

```xml
<product><banana /></product>
```

整形式はXML自身の基本文法への合致、妥当性はその特定用途で定めた構造スキーマへの適合を意味するわけです。

#### 14 名前空間

異なる用途のXMLを混ぜると、同じ要素名が衝突します。
名前をURIと結び付けて区別する仕組みがXML名前空間です。

```xml
<root xmlns:h="http://example.com/html"
      xmlns:f="http://example.com/furniture">
  <h:table>...</h:table>
  <f:table>...</f:table>
</root>
```

`h`や`f`は名前空間の接頭辞です。
ここで用いられるURIは一意な識別子として機能するものであり、該当URLへのネットワーク通信を強制する意味ではありません。

### XMLを読み用途へ変換する

XMLの構造をプログラムで処理するには、メモリ上にどのように展開するかを検討します。
全体を保持するDOMと、先頭から逐次イベントとして処理するSAXとでは、消費メモリ量と操作の柔軟性に大きな差異があるわけです。

#### 15 DOMでXMLを読む

**DOM**は、XMLやHTML文書全体をメモリ上に木構造として展開し、ノードの探索や改変を自在に行うプログラミングモデルです。

```text
product
├─属性 id="42"
├─name
│ └─「鉛筆」
└─price
  ├─属性 currency="JPY"
  └─「120」
```

長所として、ツリー内を双方向に走査し、部分構造を書き換えやすい柔軟性が挙げられます。
その反面、巨大な文書ではメモリ消費量が急激に肥大化する短所を抱えるわけです。

#### 16 SAXでXMLを読む

**SAX**、Simple API for XMLは、文書を先頭から読み、開始タグ、文字、終了タグなどのイベントが起きるたび利用者の処理を呼びます。

```text
startElement("product")
startElement("name")
characters("鉛筆")
endElement("name")
...
```

文書全体をメモリに保持しないため、ギガバイト級の巨大なXMLであっても僅かなメモリ消費で走査できます。
ただし一度通り過ぎた箇所へ戻ったり、任意の要素を書き換えたりすることは困難であり、必要なコンテキストは自前の変数で保持しなければなりません。

| 観点 | DOM | SAX |
|---|---|---|
| 読み方 | 全体を木にする | 先頭からイベントで流す |
| 記憶量 | 大きくなりやすい | 小さくしやすい |
| 自由な移動・変更 | 得意 | 苦手 |
| 巨大文書の1回処理 | 不向きな場合 | 向く |


#### 17 XML Schema

XML文書の構造と値のデータ型をXML形式自身で定義する仕様が、**XML Schema**です。
W3C XML SchemaをXSDと呼ぶこともあります。

DTDと比較して、文字列、整数、日付、値の範囲、出現回数、名前空間などを厳密に制約できる設計です。

```text
priceは0以上の整数
productにはnameが1回、priceが1回
```

スキーマ構文を満たしていても、「販売終了商品の価格を変更してはならない」といった動的な業務規則まですべて定義できるわけではありません。
アプリケーションロジック側での追加検証が不可欠となるわけです。

#### 18 SOAP

SOAPは、XMLでメッセージを包み、Webサービス間で安全に交換するための通信規約を指します。

```xml
<soap:Envelope ...>
  <soap:Header>...</soap:Header>
  <soap:Body>
    <getPrice>...</getPrice>
  </soap:Body>
</soap:Envelope>
```

- Envelopeは封筒全体。
- Headerは認証、経路などの付加情報。
- Bodyは実際の要求・応答。
- Faultはエラー情報。

SOAPメッセージの転送にはHTTPプロトコルが多用されますが、SOAPの本質は独立したXMLエンベロープ規約です。
厳格な型契約や署名・暗号化拡張が求められる企業間システム連携などで採用されてきました。

#### 19 SVG

SVG（Scalable Vector Graphics）は、二次元ベクターグラフィックスをXMLで記述する画像形式です。

```xml
<svg xmlns="http://www.w3.org/2000/svg" width="200" height="100">
  <circle cx="50" cy="50" r="30" fill="red" />
</svg>
```

画素ごとに色情報を配列するビットマップ形式と異なり、幾何学的な図形要素を座標と数式によって保持します。
画面をいくら拡大しても輪郭が劣化せず、CSSやスクリプトからスタイルを動的に操作できる利点があるわけです。
なお、写真のように連続階調が極めて複雑な画像には、ラスター画像形式の方が適しています。

### 文書の機能集合と表示を定める

#### 20 XHTML

XHTMLは、HTMLをXMLの文法で再定義したマークアップ言語です。

XMLなので、次を厳密に守ります。

- 要素名を規定の小文字で書く。
- すべての要素を閉じる。
- 入れ子を正しくする。
- 属性値を引用符で囲む。

```html
<br />
<img src="photo.png" alt="写真" />
```

ブラウザによる曖昧な構文修復に頼ることなく、汎用的なXMLパーサによって機械的に処理できる利点があります。

#### 21 XHTML Basic

携帯端末や情報家電など計算資源が限られた機器向けに、XHTMLの基本的なサブセットを定義した仕様がXHTML Basicです。

機能を中核要素に絞り込むことで、異種デバイス間での確実な互換性を確保する設計思想に基づきます。

#### 22 XHTML Modularization

XHTMLの要素・属性群を、テキスト、表、フォームなどのモジュールに分け、用途に必要な組合せで文書型を定義できる仕組みがXHTML Modularizationです。

ここでいうモジュールも「役割ごとの部品」です。
端末や用途に応じて機能集合を構成できます。

---

#### 23 CSS

**CSS**、Cascading Style Sheetsは、HTMLやXMLの要素をどう表示するか指定するスタイルシート言語です。

```css
p {
  color: navy;
  font-size: 16px;
}
```

- `p`は対象を選ぶセレクタ。
- `{ … }`は宣言のまとまり。
- `color`はプロパティ。
- `navy`は値。

HTML文書に装飾指定を混入させることなく、文書構造と視覚スタイルの明確な分離を実現できます。

#### 24 セレクタ

```css
p             /* p要素 */
.warning      /* class="warning" */
#main         /* id="main" */
article p     /* article内のp */
button:hover  /* ポインタが重なったbutton */
```

class属性は複数要素のグループ化に用い、id属性は文書内での一意識別の用途に供するわけです。

#### 25 カスケード

単一の要素に対して複数のスタイル規則が競合した場合、宣言元、重要度、詳細度、記述順序に基づいて最終的な適用値が算出されます。
規則が滝のように連鎖・統合されることから、カスケードと呼ばれるわけです。

また、親要素の指定が子要素へと伝播する継承の仕組みも備わっています。
ただし、すべてのプロパティが無条件に継承されるわけではありません。

`!important`を過度に乱用するとスタイルの上書き関係が著しく不透明になるリスクを伴います。
コンポーネント指向の命名規則と適切な詳細度の設計によって整合性を維持する姿勢が求められるわけです。

#### 26 レイアウトとレスポンシブ設計

CSSにはFlexboxやGridといった強力なレイアウト機構が備わっています。
さらに、表示領域の幅や端末特性に応じて適用スタイルを分岐させるメディアクエリも利用可能です。

```css
@media (max-width: 600px) {
  .columns { display: block; }
}
```

単一のHTMLソースをスマートフォンの狭小画面からデスクトップの大画面まで最適化させる設計を、レスポンシブWebデザインと呼びます。

#### 27 XSL

XSL（Extensible Stylesheet Language）は、XML文書の表示や構造変換を司る一連の言語仕様群です。

- XSLT――XMLを別のXML、HTML、文字などに変換する。
- XPath――XML木の中の場所を指定する。
- XSL-FO――印刷用ページ配置などを記述する。

##### 27.1 XSLTの考え

入力XMLの特定要素に合うテンプレートを適用し、出力を作ります。

```text
商品XML
  ↓ XSLT変換
商品一覧HTML
```

CSSが対象文書の視覚表現を指定するのに対し、XSLTは文書構造そのものを別のツリーへと変換する機能を持つわけです。

## 第2部　データ記述言語

### 交換するデータの型を合意する

#### 28 JSON

**JSON**、JavaScript Object Notationは、構造化データを文字で表す軽量形式です。

```json
{
  "name": "青木",
  "age": 30,
  "member": true,
  "address": null,
  "skills": ["設計", "試験"]
}
```

JSONでは、次の種類の値を組み合わせて構造を表します。

- オブジェクト――`{}`内の名前と値の組。
- 配列――`[]`内の順序付きの値。
- 文字列――二重引用符で囲む。
- 数値。
- 真偽値`true`、`false`。
- 値なしを表す`null`。

#### 29 JSONの厳密な規則

- 名前と文字列は二重引用符を使う。
- 最後の要素の後に余分なカンマを置かない。
- 標準JSONにはコメントがない。
- `NaN`や`Infinity`は標準の数値ではない。
- オブジェクト名の重複は、受取側で扱いが異なり危険なので避ける。

次の例は、最後に余分なカンマがあるため、標準JSONとして不正です。

```json
{ "price": 100, }
```

JavaScriptのオブジェクト記法とJSONは似ていますが同一ではありません。

#### 30 JSONで失われやすい型

JSONには標準の日付型、バイト列型、整数と小数の厳密な区別などがありません。

```json
{ "createdAt": "2026-07-14T10:00:00+09:00" }
```

日付を文字列として書き、形式を別途約束します。

倍精度浮動小数点数を標準とする環境では、64ビット整数などの巨大な値を正確に復元できない場合があります。
したがってID値などは文字列として伝達するなど、送受信間で精度と許容範囲を合意しておく設計が肝要です。
バイナリデータや独自オブジェクトを文字列化する際にも、相互運用可能な表現形式を統一する形をとるわけです。

#### 31 JSON Schema

JSONデータの構造、型、必須項目、範囲などをスキーマとして形式定義する仕様に、JSON Schemaがあります。

```text
nameは必須の文字列
ageは0以上の整数
```

XML Schemaと同様に構造検証を機械的に自動化できますが、権限確認や複雑な業務規則はアプリケーション側でも検証する設計が欠かせません。

### 設定とシステムの仕様を記述する

#### 32 YAML

**YAML**は、字下げを使って構造を表し、人が読み書きしやすいことを目指すデータ記述形式です。

```yaml
name: 青木
age: 30
member: true
skills:
  - 設計
  - 試験
address: null
```

主に設定ファイルやデータ交換、インフラの構成管理手順の記述などに広く用いられます。

#### 33 YAMLの字下げ

YAMLでは、同一の階層深さを一定数の半角スペースでそろえる構文規約をもつ形です。
タブ文字による字下げを禁止している点が代表的な特徴といえます。

```yaml
server:
  host: example.com
  port: 443
```

`host`と`port`は`server`直下のプロパティとして認識されます。
インデントの乱れはデータ階層の不整合やパースエラーに直結するため、厳格な空白管理が欠かせません。

#### 34 YAMLの注意点

YAMLは便利ですが、機能が多く、解析器や版で暗黙の型解釈が異なることがあります。

```yaml
value: yes
date: 2026-07-14
code: 00123
```

文字列として意図した`yes`や日付形式の表記が、パーサによって自動的に真偽値やタイムスタンプへと型変換されてしまうケースも散見されます。
重要な識別子や文字列値は二重引用符で明示的にクォートし、適用スキーマを明文化しておく配慮が必要です。

さらに、アンカー・エイリアスや独自オブジェクトのインスタンス化を伴う高度機能は、安全でないデシリアライズ攻撃の標的となり得ます。
信頼できない入力をパースする際は、セーフロード機能を用い、階層の深さや許可する型を厳密に制限する防壁が不可欠です。

#### 35 JSONとYAMLの選択

| 観点 | JSON | YAML |
|---|---|---|
| 構造記号 | `{}`、`[]`が明示的 | 主に字下げ |
| コメント | 標準にはない | 書ける |
| 機能 | 比較的少なく単純 | 表現力が高い |
| よくある用途 | Web API、機械間交換 | 人が編集する設定 |

YAMLはJSONのデータモデルを表せる広い形式ですが、両者の解析規則は同じではありません。
用途、ツール、安全性、相互運用性で選びます。

#### 36 DDL

DDL、Data Definition Languageは、データベースの表、列、制約などの構造を定義する言語です。

SQLの例です。

```sql
CREATE TABLE Product (
  product_id INTEGER PRIMARY KEY,
  name       VARCHAR(100) NOT NULL,
  price      INTEGER NOT NULL
);
```

`CREATE`、`ALTER`、`DROP`といったスキーマ定義命令が、典型的なDDLに分類されます。
データレコードの操作を担うDMLや、権限を管理するDCLと明確に区別して運用されるわけです。
リレーショナルデータベースにおける構造設計の詳細は、後続のデータベース章で体系的に扱います。

#### 37 SDL

SDL、Specification and Description Languageは、通信システムなど、出来事を受けて状態が変わるシステムの仕様と動作を記述する形式言語です。

状態、入力信号、出力信号、遷移、処理などを図や文章で表します。

```text
待機状態
  ├─「開始」を受信 → 動作中状態
  └─「取消」を受信 → 待機状態
```

曖昧な自然文だけでなく、状態遷移を厳密に検討し、検証やコード生成につなげられます。

#### 38 ADL

ADL、Architecture Description Languageは、ソフトウェアやシステムの構成要素、接続、インターフェース、制約を記述する言語の総称です。

```text
注文サービス ─→ 在庫サービス
      │
      └────→ 決済サービス
```

単なるブロック図にとどまらず、コンポーネントが提供・要求するインターフェース、通信プロトコル、配置制約などを形式的に記述できるADLが存在します。
単一のプログラミング言語を指すというより、共通の記述目的を共有する言語群の総称として用いられる場合があるわけです。

## 第3部　UML

### 図にする目的と視点を選ぶ

#### 39 UMLとは何か

**UML**、Unified Modeling Languageは、ソフトウェアを中心とするシステムの構造や振る舞いを図で表すための標準的な表記法です。

UMLはプログラミング言語ではありません。
図を描けば自動的によい設計になるわけでもありません。

役割は、関係者の考えを見える形にし、要求、構造、動作、配置の認識をそろえることです。

#### 40 モデルは現実の一部を選ぶ

地図は現実の町をすべて再現せず、道路地図なら道路、鉄道路線図なら駅と接続を強調します。
同様にUML図においても、表現目的に応じて不可欠な情報のみを選択的に抽象化するわけです。
目的に直接関与しない細部まで描き込むと、意思決定に必要な中核関係が埋没し、図の保守性も低下してしまいます。

したがって、関心事に応じた視点ごとに最適なダイアグラムを選択する設計をとるわけです。

- 利用者に何を提供するかを見る。
- クラスの構造を見る。
- 1操作の時間順を見る。
- 状態変化を見る。
- 実行機器への配置を見る。

UML図は、システムの静的構造を捉える「構造図」と、動的な振る舞いを捉える「振る舞い図」の2大体系に大別されます。

##### 構造を表す図

- クラス図
- オブジェクト図
- コンポーネント図
- パッケージ図
- 配置図
- コンポジット構造図

##### 振る舞いを表す図

- ユースケース図
- アクティビティ図
- ステートマシン図
- シーケンス図
- コミュニケーション図
- 相互作用概要図
- タイミング図

シーケンス図などは、振る舞い図の中でも時系列のやり取りを重視する相互作用図に位置づけられるわけです。

### クラスと関係を定義する

静的構造を共有する際には、型が保持する属性と操作、ならびに型同士の対応関係を明示します。
ドメイン概念をクラスとして配置したうえで、関連の多重度や所有の強弱を厳密に定義する形をとるわけです。

#### 42 クラス図

クラス自身の内部構成と、クラス間の静的な結合関係を網羅して表現します。

```text
┌─────────────────┐
│ Product          │  ← クラス名
├─────────────────┤
│ -name: String    │  ← 属性
│ -price: Integer  │
├─────────────────┤
│ +changePrice(p)  │  ← 操作
└─────────────────┘
```


##### 42.1 属性

オブジェクトが持つデータを属性と呼びます。
`name`、`price`などです。

##### 42.2 操作

オブジェクトに依頼できる処理を操作と呼びます。
実装された処理本体をメソッドと呼ぶことがあります。

`+`は公開、`-`は非公開、`#`は保護された可視性を示す記法です。

#### 43 関連と多重度

クラス間のつながりを関連で表します。

```text
Customer 1 ───── 0..* Order
```

1人の`Customer`には0個以上の`Order`が紐づき、各`Order`には必ず1人の`Customer`が対応します。
実線で関連の存在を示し、両端の多重度によってインスタンス数の制約を厳密に定めているわけです。

代表的な多重度です。

- `1`――ちょうど1つ。
- `0..1`――ないか1つ。
- `*`または`0..*`――0個以上。
- `1..*`――1個以上。
- `2..5`――2個以上5個以下。

#### 44 ロール名

関連の端で、相手が自分にとってどの役割かを示す名前をロール名と呼びます。

```text
Employee ───── Department
 employee      employer
```

自己関連の構造を表現する場面において、ロール名は特に絶大な効果を発揮します。

```text
Employee  manager 0..1 ───── 0..* subordinates Employee
```

同一のEmployeeクラスであっても、上司と部下という異なる文脈上の役割を明瞭に区別できるわけです。

#### 45 集約とコンポジション

全体と部分の関係を表します。

- **集約**――白いひし形。
  部分が全体と別に存在し得る弱い所有。
- **コンポジション**、合成――黒いひし形。
  部分の寿命が全体に強く属する。

```text
Team ◇── Player       集約の例
Order ◆── OrderLine   合成の例
```

現実の意味に基づいて使います。
単に「配列を持つ」から合成、と機械的に決めません。

#### 46 汎化と実現

一般的な基底型と特殊な派生型の関係を**汎化**と呼び、白抜きの三角矢印を一般側に向けます。

```text
Dog ─────▷ Animal
Cat ─────▷ Animal
```

インターフェースが定義した契約を具象クラスが実装する関係が、実現です。

#### 47 依存

あるクラスが別のクラスをメソッド引数や局所変数として一時的に参照するなど、変更の影響が波及する関係を依存と呼びます。
UMLではこれを開いた矢尻の破線矢印で表記する規則です。

長期的な参照を伴う関連に比べて弱い結合度を示しますが、モデルの目的を鑑みて重要な依存関係のみを選択的に描画します。

---

### 具体的な対象と構成を表す

#### 48 オブジェクト図

特定の実行時点における具体的なオブジェクトのインスタンス状態と、実体間のリンクを写し取る図が、オブジェクト図です。
クラス図が型の静的な設計図であるのに対し、オブジェクト図はある一瞬のスナップショットに相当します。

```text
product42:Product
name = "鉛筆"
price = 120
```

多重度や関連が実際の事例でどう機能するかを検証し、複雑なデータ構造を直感的に共有するのに有効な手法です。

#### 49 パッケージ図

モデル要素をまとめたパッケージと、その依存関係を表します。

```text
┌────────┐      ┌────────┐
│ 注文   │ ───→ │ 在庫   │
└────────┘      └────────┘
```

大規模システムにおける名前空間、アーキテクチャ層、サブシステム群の境界を整理する図です。
パッケージ間の依存関係が循環していないか、上位層が下位層に健全に依存しているかを検証する用途に適しています。

#### 50 コンポーネント図

独立して配布・交換可能なソフトウェアの実行単位と、それが提供・要求するインターフェースを可視化する図が、コンポーネント図です。

```text
[注文Web] ──要求── (在庫API) ── [在庫サービス]
```

クラスより粒度の大きなサービスやライブラリの物理的な依存関係を把握する目的で多用されます。

#### 51 配置図

サーバ、端末、実行環境などの物理・仮想ノードに対し、各ソフトウェア配置構成をマッピングする図が、配置図です。

```text
<<device>> 利用者PC
  └─ブラウザ
       │ HTTPS
<<server>> Webサーバ
  └─注文アプリ
       │ DB接続
<<server>> DBサーバ
  └─注文DB
```

通信プロトコル、冗長化構成、セキュリティ境界、インフラの配置トポロジーを検討する際に威力を発揮します。

#### 52 コンポジット構造図

単一のクラスやコンポーネントの内部構造を、内部部品（part）や相互作用点（port）の結線として詳細化する図が、コンポジット構造図です。

- part――内部を構成する部品。
- port――外部との相互作用点。
- connector――部品・ポート間の接続。

```text
┌──────── OrderProcessor ────────┐
│ [validator]──[calculator]──[repo] │
└──── port: orderAPI ─────────────┘
```

クラス図が型同士の関係を示すのに対し、コンポジット構造図は1要素の内部協調を見せます。

---

### 利用者の目的と対象の状態を表す

#### 53 ユースケース図

システムの外部に位置する利用者や外部システムが、どのような目的を達成できるかを鳥瞰する図が、ユースケース図です。

- アクター――役割としての利用者・外部システム。
- **ユースケース**――外部から見た目的。
- システム境界――対象範囲。

```text
顧客 ─── (商品を検索する)
顧客 ─── (注文する)
管理者 ─ (商品を登録する)
```

画面のUI部品や内部関数の羅列を排し、外部アクターに対して完結した価値を提供する目的そのものを記述します。

#### 54 includeとextend

複数ユースケースが必ず共通処理を包含する関係を、`<<include>>`の依存関係として定義するわけです。

```text
(注文する) ──include──> (本人を確認する)
```

一方、特定条件下でのみ追加実行される拡張シナリオは、`<<extend>>`の関係で表現します。

```text
(クーポンを適用する) ──extend──> (注文する)
```

矢印の向きが混同されやすいため、includeは基本側から共通側へ、extendは拡張側から基本側へと向ける規則です。

#### 55 アクティビティ図

処理や業務の流れ、分岐、並行を表します。
フローチャートに似ていますが、活動間の流れや並行処理を表すUML図です。

```text
● 開始
↓
[注文を受ける]
↓
◇ 在庫あり?
├─はい→[決済する]→◎ 終了
└─いいえ→[欠品を通知]→◎
```

太いバーを用いて処理の流れを並行に枝分かれさせるforkや、同期結合させるjoinを表現します。
実行主体ごとに区画を分けるスイムレーンを導入すれば、業務の責任分界点を明快に図示できるわけです。

#### 56 ステートマシン図

単一のオブジェクトが、外部イベントの発生に応じてどのような状態へと遷移していくのかをモデル化します。

```text
[未払い] --支払成功--> [支払済み]
[支払済み] --発送--> [発送済み]
[未払い] --期限切れ--> [取消]
```

状態間の遷移線には、イベント、ガード条件、アクションをラベルとして併記する記法をとるわけです。

```text
イベント [ガード条件] / アクション
```

具体例としては`支払要求 [残高あり] / 領収記録を作る`といった形式で記述します。

- イベントは遷移のきっかけ。
- ガードは遷移してよい条件。
- アクションは遷移時の処理。

状態の数が一見少なく見えても、直交する状態軸を無秩序に合成すると状態爆発を招く点に留意が必要です。
複雑な振る舞いを整理するには、複合状態や並行領域を活用して階層的に構造化するアプローチをとります。

---

### 参加者のやり取りを時間順に表す

複数オブジェクトが協調動作する過程を可視化するには、送受信されるメッセージと時系列の関係を捉える構成が有効です。
同期呼出しの成否や分岐条件、時間制約の有無に応じて、適切な図的表現を選択します。

#### 57 シーケンス図

複数の参加者が送るメッセージを、上から下の時間順で表します。

```text
顧客     画面       注文サービス       在庫
 |        |              |              |
 |注文--->|              |              |
 |        | create() --->|              |
 |        |              | check() ---->|
 |        |              |<---- available|
 |        |<----- success|              |
 |<--完了-|              |              |
```

縦の破線は**ライフライン**、細長い長方形は実行中の区間、横矢印はメッセージです。

#### 58 同期メッセージと非同期メッセージ

呼出し結果が返るまで待つものを同期メッセージ、送った後に別処理を続けるものを非同期メッセージとして描き分けます。

呼出し元への戻りメッセージは、通常、開いた矢尻の破線矢印で表現します。
単純な図記号の羅列にとどめず、処理完了の待機要件や送達順序の保証、例外時の回復手順を注記として補足しておくことが重要です。

#### 59 複合フラグメント

シーケンス図の一部を枠で囲み、条件分岐や反復実行を表現する構文要素が、複合フラグメントです。

- `alt`――条件によるどれか1つ。
  if/else。
- `opt`――条件付きで行う。
- `loop`――繰返し。
- `par`――並行。
- `break`――条件時に残りを中断。

正常系のフローだけでなく、タイムアウトやリトライなどの例外経路を網羅することで、潜在的な設計漏れを洗い出せます。

#### 60 コミュニケーション図

オブジェクト同士のリンクを空間的に配置し、メッセージに番号を付与して呼び出し順序を示す図が、コミュニケーション図です。

```text
customerUI ──1:createOrder()── orderService
orderService ──1.1:check()── inventory
```

シーケンス図が時系列の直感的な把握に優れるのに対し、コミュニケーション図は参加者間の結合関係の把握に強みを持ちます。
すなわち同一の協調動作を、時間軸と空間軸という異なる視座から捉え直す関係にあるわけです。

#### 61 相互作用概要図

複数の相互作用シナリオを、アクティビティ図のような制御フローで上位統合する図が、相互作用概要図です。

```text
●
↓
[ログインの相互作用]
↓
◇ 成功?
├→ [注文の相互作用]
└→ [エラー案内の相互作用]
```

複雑な業務フローの全体像と、個々の詳細シーケンスとを階層的に接続して俯瞰できます。

#### 62 タイミング図

横方向の時間軸に沿って、複数の対象の状態や信号値がいつ遷移するかを厳密に可視化する図です。

```text
時間 →
信号A  LOW ────┐ HIGH ─────┐ LOW
                └───────────┘
状態B  待機 ───── 動作中 ─── 完了
```

組込み制御機器、通信プロトコル、リアルタイムシステムにおいて、応答期限、遅延時間、並行状態の整合性を検証する用途に適しています。

### 同じシステムを各図で説明する

#### 63 図同士の整合性

複数の図で同じシステムを表す場合は、操作の名前、登場する部品、許される状態変更をそろえます。
視点を変えてもモデル間の整合が破綻しないよう、各図の対応関係を慎重に突き合わせる形をとるわけです。

- ユースケース「注文する」を実現するシーケンスがあるか。
- シーケンスで呼ぶ操作がクラス図にあるか。
- ステートマシン上で禁止された状態変更を、活動が行っていないか。
- コンポーネントが要求するインターフェースを提供者が持つか。
- 配置先で必要な通信が可能か。

UMLツールで一部を検査できても、意味上の整合は人のレビューが必要です。

#### 64 図を描きすぎない

コードの修正に伴ってすべての図を同期更新し続けることは困難であり、陳腐化したモデルは誤解を招く原因となります。

したがって正式に保守すべき中核図面と、一時的な検討用スケッチとを明確に区別して運用する方針が肝要です。

- 誰のどの判断に使う図か。
- どの抽象度か。
- 正式に保守する図か、一時的な検討図か。
- ソースや設定から自動生成できるか。

システムの全容を網羅しようとせず、設計上特に重要で誤解が生じやすい中核の関係を最小限の図で明示します。

HTMLやXMLは文書の論理構造を、JSONやYAMLは交換データの構造を、UMLはシステムの静的関係や動的振る舞いを可視化する道具です。
構文規則を正しく満たすことに加え、通貨単位、値の許容範囲、クラス間の多重度、非同期通信の順序性を、受け手側と明確に合意しておく必要があります。
表記法そのものが保証する構造的整合性と、各システム固有のドメイン意味論とを明確に峻別して設計を進める視点が肝要となるわけです。
