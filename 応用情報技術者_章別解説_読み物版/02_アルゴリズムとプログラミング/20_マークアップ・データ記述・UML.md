# 第2章・第20話　マークアップ・データ記述・UML――構造を文字と図で伝える

構造を形式に従って書けば、受け手は同じ構造として解析できます。
タグや構文が正しくても、単位、制約、関係の意味まで自動で一致するわけではありません。

形式が保証する範囲を見分ける必要があります。


## 第1部　マークアップ言語

## 1 マークアップとは何か

文章に「ここは見出し」「ここは段落」「ここは重要語」という印を付けることを**マークアップ**と呼びます。

```html
<h1>今日の献立</h1>
<p>カレーを作ります。</p>
```

`<h1>`や`<p>`が印です。
マークアップの書き方を定めた言語が**マークアップ言語**です。

通常のプログラミング言語のように処理手順を書くことが中心ではなく、文書やデータの構造・意味を記述します。

## 2 タグ、要素、内容

HTMLやXMLでは、山括弧で囲んだ印を**タグ**と呼びます。

```html
<p>こんにちは</p>
```

- `<p>`は開始タグ。
- `</p>`は終了タグ。
- `こんにちは`は内容。
- 開始タグから終了タグまで全体が要素。

終了タグの斜線`/`は「ここで終わる」という印です。

## 3 属性

要素に追加情報を付けるものを**属性**と呼びます。

```html
<a href="https://example.com">案内</a>
```

`href`が属性名、URLが属性値です。
`a`要素はリンクを表します。

属性値は引用符で囲むのが分かりやすく安全です。
属性の意味と使える値は言語仕様で決まります。

## 4 入れ子

要素の中に別要素を置けます。

```html
<p>これは<strong>重要</strong>です。</p>
```

開いた順の逆に閉じます。

```html
正しい: <p><strong>文字</strong></p>
誤り:   <p><strong>文字</p></strong>
```

HTMLブラウザは一部の誤りを推測修正しますが、その結果が意図どおりとは限りません。
XMLではこの種の誤りを許しません。

## 5 特別な文字のエスケープ

本文中に`<`を書きたいとき、そのままではタグ開始と解釈されます。
特別な書き方に変えます。

```html
&lt;   → <
&gt;   → >
&amp;  → &
&quot; → "
```

文脈に応じて特別な意味をなくす変換を**エスケープ**と呼びます。
Web安全性でも重要です。

## 6 HTML

**HTML**、HyperText Markup Languageは、Web文書の構造と意味を表すマークアップ言語です。

最小限の文書例です。

```html
<!doctype html>
<html lang="ja">
  <head>
    <meta charset="utf-8">
    <title>料理の紹介</title>
  </head>
  <body>
    <h1>カレー</h1>
    <p>野菜を煮込む料理です。</p>
  </body>
</html>
```

- `doctype`は文書をHTMLとして標準的に解釈させる宣言。
- `html`は文書全体。
- `head`は題名や設定など文書情報。
- `body`は画面上の主内容。
- `meta charset`は文字符号化を示す。
- `title`はブラウザのタブなどに出る題名。

## 7 代表的なHTML要素

- `h1`〜`h6`――見出しの階層。
- `p`――段落。
- `a`――リンク。
- `img`――画像。
- `ul`、`ol`、`li`――箇条書き。
- `table`、`tr`、`th`、`td`――表。
- `form`、`label`、`input`、`button`――入力フォーム。
- `header`、`nav`、`main`、`article`、`section`、`footer`――文書上の役割。

見た目を大きくしたいだけで`h1`を選ぶのではなく、最上位見出しだから選びます。
見た目はCSSで整えます。

## 8 ハイパーテキスト

文書から別文書や別位置に参照を張り、非直線的に移動できるものを**ハイパーテキスト**と呼びます。
HTML名のHyperTextはこれを指します。

```html
<a href="chapter2.html">第2章へ</a>
```

リンク先は相対URLまたは絶対URLで書けます。
相対URLは現在位置を基準にするため、文書一式を別場所に移しやすい利点があります。

## 9 SGML

**SGML**、Standard Generalized Markup Languageは、文書の構造を記述するマークアップ言語を定義するための大きな枠組み、メタ言語です。

HTMLは歴史的にSGMLの応用として定義されました。
XMLも、SGMLの考えを基に、Webで扱いやすいよう簡素化した言語です。

「SGMLタグがHTMLにそのままある」というより、SGMLが文書型を定義する土台だったと捉えます。

## 10 DTD

文書で使える要素、順序、属性などを定義するものを**DTD**、Document Type Definition、文書型定義と呼びます。

概念的な例です。

```text
book要素はtitleの後にchapterを1個以上持つ
chapter要素はheadingとparagraphを持つ
```

```dtd
<!ELEMENT book (title, chapter+)>
<!ELEMENT title (#PCDATA)>
<!ELEMENT chapter (heading, paragraph+)>
```

DTDに従っているか検査できます。
現在のHTMLのdoctypeは、過去の長いDTD参照より簡潔な`<!doctype html>`を使います。

## 11 XML

**XML**、Extensible Markup Languageは、用途に応じて独自の要素名を定義し、構造化データを文字で表せるマークアップ言語です。

```xml
<?xml version="1.0" encoding="UTF-8"?>
<product id="42">
  <name>鉛筆</name>
  <price currency="JPY">120</price>
</product>
```

`product`、`name`、`price`は、この用途で決めた名前です。
XMLそのものが「priceの意味」を決めるわけではありません。
作成者間で文書構造と意味を合意します。

## 12 XMLの整形式

XMLの基本文法を守った文書を**整形式**、well-formedと呼びます。

主な規則です。

- 文書全体を囲む根要素が1つある。
- 開始タグには対応する終了タグがある。
- 入れ子を正しく閉じる。
- 要素名の大文字・小文字を区別する。
- 属性値を引用符で囲む。
- 特別文字をエスケープする。

```xml
<br />
```

のように、内容のない要素を空要素タグで閉じられます。

## 13 妥当なXML

開始タグと終了タグが対応していれば、正しいXMLに見えます。
それで保証されるのは整形式であることまでで、必要な要素や属性がそろうかはDTDやXML Schemaとの照合で決まります。

整形式であることに加え、DTDやXML Schemaで定めた文書型に従うものを**妥当**、validと呼びます。

```xml
<product><banana /></product>
```

は基本文法上は整形式でも、仕様がproduct内にはnameとpriceだけを許すなら妥当ではありません。

整形式はXML自身の文法、妥当性はその用途の構造規則への適合です。

## 14 名前空間

異なる用途のXMLを混ぜると、同じ要素名が衝突します。
名前をURIと結び付けて区別する仕組みが**XML名前空間**です。

```xml
<root xmlns:h="http://example.com/html"
      xmlns:f="http://example.com/furniture">
  <h:table>...</h:table>
  <f:table>...</f:table>
</root>
```

`h`と`f`は接頭辞です。
URIは識別名として働き、必ずそのURLにアクセスするという意味ではありません。

## 15 DOMでXMLを読む

**DOM**は、XMLやHTML文書全体を木として主記憶に読み込み、ノードをたどったり変更したりする方法です。

```text
product
├─属性 id="42"
├─name
│ └─「鉛筆」
└─price
  ├─属性 currency="JPY"
  └─「120」
```

長所は、親子を自由に移動し、複数回調べ、変更しやすいことです。
短所は、巨大文書を丸ごと木にするため多くの記憶を使うことです。

## 16 SAXでXMLを読む

文書全体を木にすれば、どの要素へも後から移動できます。
巨大な文書でその自由を得るには全体をメモリへ置く必要があるため、SAXは先頭から読む代わりに保持量を抑えます。

**SAX**、Simple API for XMLは、文書を先頭から読み、開始タグ、文字、終了タグなどのイベントが起きるたび利用者の処理を呼びます。

```text
startElement("product")
startElement("name")
characters("鉛筆")
endElement("name")
...
```

文書全体を保持しないため大きなXMLを少ない記憶で処理できます。
後ろから前に戻ったり、任意部分を自由に修正したりするのは難しく、必要状態を自分で持ちます。

| 観点 | DOM | SAX |
|---|---|---|
| 読み方 | 全体を木にする | 先頭からイベントで流す |
| 記憶量 | 大きくなりやすい | 小さくしやすい |
| 自由な移動・変更 | 得意 | 苦手 |
| 巨大文書の1回処理 | 不向きな場合 | 向く |

## 17 XML Schema

XML文書の構造と値の型をXML形式で定義するものに**XML Schema**があります。
W3C XML SchemaをXSDと呼ぶこともあります。

DTDより、文字列、整数、日付、範囲、出現回数、名前空間などを詳しく定義できます。

```text
priceは0以上の整数
productにはnameが1回、priceが1回
```

文法を満たしても、「販売終了商品の価格を変更してはいけない」のような業務規則まですべて表せるわけではありません。
アプリケーション側の検証も必要です。

## 18 SOAP

**SOAP**は、XMLでメッセージを包み、Webサービス間で交換するための規約です。

```xml
<soap:Envelope ...>
  <soap:Header>...</soap:Header>
  <soap:Body>
    <getPrice>...</getPrice>
  </soap:Body>
</soap:Envelope>
```

- Envelopeは封筒全体。
- Headerは認証、経路などの付加情報。
- Bodyは実際の要求・応答。
- Faultはエラー情報。

HTTP上で使われることが多いですが、SOAPはXMLメッセージ処理の規約であり、HTTPそのものではありません。
厳密な契約、拡張仕様、企業間連携などで使われます。

## 19 SVG

**SVG**、Scalable Vector Graphicsは、図形をXMLで表す形式です。

```xml
<svg xmlns="http://www.w3.org/2000/svg" width="200" height="100">
  <circle cx="50" cy="50" r="30" fill="red" />
</svg>
```

画素の色を1個ずつ保存するラスター画像と違い、円、線、文字、経路などの形を数値で保存します。
拡大しても輪郭が荒れにくく、CSSやスクリプトで変更できます。

写真のような複雑な画像には、画素形式の方が適する場合があります。

---

## 20 XHTML

**XHTML**は、HTMLをXMLの文法で再定義したマークアップ言語です。

XMLなので、次を厳密に守ります。

- 要素名を規定の小文字で書く。
- すべての要素を閉じる。
- 入れ子を正しくする。
- 属性値を引用符で囲む。

```html
<br />
<img src="photo.png" alt="写真" />
```

誤った構文をブラウザが寛容に直すことに頼らず、XMLツールで処理できます。

## 21 XHTML Basic

携帯端末、テレビ、PDAなど、PCブラウザより機能や資源が限られた機器でも扱えるよう、XHTMLの基本的な機能集合を定めたものが**XHTML Basic**です。

必要機能を絞り、機器間の互換性を高める考えです。

## 22 XHTML Modularization

XHTMLの要素・属性群を、テキスト、表、フォームなどの**モジュール**に分け、用途に必要な組合せで文書型を定義できる仕組みが**XHTML Modularization**です。

ここでいうモジュールも「役割ごとの部品」です。
端末や用途に応じて機能集合を構成できます。

---

## 23 CSS

**CSS**、Cascading Style Sheetsは、HTMLやXMLの要素をどう表示するか指定するスタイルシート言語です。

```css
p {
  color: navy;
  font-size: 16px;
}
```

- `p`は対象を選ぶセレクタ。
- `{ … }`は宣言のまとまり。
- `color`はプロパティ。
- `navy`は値。

HTMLに見た目を直接大量に書かず、構造と表示を分離できます。

## 24 セレクタ

```css
p             /* p要素 */
.warning      /* class="warning" */
#main         /* id="main" */
article p     /* article内のp */
button:hover  /* ポインタが重なったbutton */
```

classは複数要素に同じ分類を付け、idは文書内の一意識別に使います。

## 25 カスケード

同じ要素に複数規則が当たるとき、由来、重要度、セレクタの具体性、記述順などで最終値を決めます。
規則が段階的に重なるため**カスケード**と呼びます。

子要素が親の文字色などを受け継ぐ**継承**もあります。
すべてのプロパティが継承されるわけではありません。

`!important`を多用すると上書き関係が追いにくくなります。
部品構造と命名、適切な具体性で管理します。

## 26 レイアウトとレスポンシブ設計

CSSにはFlexbox、Gridなどの配置機能があります。
画面幅や端末特性に応じて規則を変える**メディアクエリ**を使えます。

```css
@media (max-width: 600px) {
  .columns { display: block; }
}
```

1つの文書を小さな画面から大きな画面まで使いやすくする設計を**レスポンシブWebデザイン**と呼びます。

## 27 XSL

**XSL**、Extensible Stylesheet Languageは、XML文書の表示・変換に関する言語群です。

- XSLT――XMLを別のXML、HTML、文字などに変換する。
- XPath――XML木の中の場所を指定する。
- XSL-FO――印刷用ページ配置などを記述する。

### 27.1 XSLTの考え

入力XMLの特定要素に合うテンプレートを適用し、出力を作ります。

```text
商品XML
  ↓ XSLT変換
商品一覧HTML
```

CSSは主に同じ文書の見た目を指定し、XSLTは構造そのものを別文書に変換できます。

## 第2部　データ記述言語

## 28 JSON

**JSON**、JavaScript Object Notationは、構造化データを文字で表す軽量形式です。

```json
{
  "name": "青木",
  "age": 30,
  "member": true,
  "address": null,
  "skills": ["設計", "試験"]
}
```

主な値の種類です。

- オブジェクト――`{}`内の名前と値の組。
- 配列――`[]`内の順序付きの値。
- 文字列――二重引用符で囲む。
- 数値。
- 真偽値`true`、`false`。
- 値なしを表す`null`。

## 29 JSONの厳密な規則

- 名前と文字列は二重引用符を使う。
- 最後の要素の後に余分なカンマを置かない。
- 標準JSONにはコメントがない。
- `NaN`や`Infinity`は標準の数値ではない。
- オブジェクト名の重複は、受取側で扱いが異なり危険なので避ける。

```json
{ "price": 100, }
```

は最後のカンマがあるため標準JSONとして不正です。
JavaScriptのオブジェクト記法とJSONは似ていますが同一ではありません。

## 30 JSONで失われやすい型

JSONへ変換できても、元の型をすべて保存できたとは限りません。
日付、巨大整数、バイナリ、オブジェクト固有の型は、文字列や数値へ変えた瞬間に元の型情報を失うことがあります。

JSONには標準の日付型、バイト列型、整数と小数の厳密な区別などがありません。

```json
{ "createdAt": "2026-07-14T10:00:00+09:00" }
```

日付を文字列として書き、形式を別途約束します。

非常に大きな整数をJavaScriptなどで通常の数値に読むと正確に表せない場合があります。
IDは文字列で渡すなど、送受信側で型と範囲を合意します。

## 31 JSON Schema

JSONデータの構造、型、必須項目、範囲などを記述する仕様にJSON Schemaがあります。

```text
nameは必須の文字列
ageは0以上の整数
```

XML Schemaと同様、構造検証を自動化できますが、権限や複雑な業務規則はアプリケーションでも検証します。

## 32 YAML

**YAML**は、字下げを使って構造を表し、人が読み書きしやすいことを目指すデータ記述形式です。

```yaml
name: 青木
age: 30
member: true
skills:
  - 設計
  - 試験
address: null
```

設定ファイル、データ交換、操作手順の記述などに使われます。

## 33 YAMLの字下げ

同じ深さを同じ数の空白でそろえます。
タブを字下げに使わない規則があります。

```yaml
server:
  host: example.com
  port: 443
```

`host`と`port`は`server`の内側です。
字下げがずれると構造が変わるか、構文エラーになります。

## 34 YAMLの注意点

引用符や括弧が少ないYAMLは、人が短く書けます。
その省略によって、日付や真偽値に見える文字列、字下げ、処理系ごとの解釈差を意識する必要が生まれます。

YAMLは便利ですが、機能が多く、解析器や版で暗黙の型解釈が異なることがあります。

```yaml
value: yes
date: 2026-07-14
code: 00123
```

文字列のつもりが真偽、日付、数に解釈される処理系もあり得ます。
重要値は引用符で囲み、スキーマや使用版を決めます。

別名や外部オブジェクト生成などの高度機能を安全でない解析方法で信用できない入力に使うと、資源枯渇や任意処理につながる実装もあります。
安全読込み機能、サイズ・深さ制限、許可型の制限を使います。

## 35 JSONとYAMLの選択

| 観点 | JSON | YAML |
|---|---|---|
| 構造記号 | `{}`、`[]`が明示的 | 主に字下げ |
| コメント | 標準にはない | 書ける |
| 機能 | 比較的少なく単純 | 表現力が高い |
| よくある用途 | Web API、機械間交換 | 人が編集する設定 |

YAMLはJSONのデータモデルを表せる広い形式ですが、両者の解析規則は同じではありません。
用途、ツール、安全性、相互運用性で選びます。

## 36 DDL

**DDL**、Data Definition Languageは、データベースの表、列、制約などの構造を定義する言語です。

SQLの例です。

```sql
CREATE TABLE Product (
  product_id INTEGER PRIMARY KEY,
  name       VARCHAR(100) NOT NULL,
  price      INTEGER NOT NULL
);
```

`CREATE`、`ALTER`、`DROP`などがDDLに分類されます。
データ行を検索・更新するDML、権限を扱うDCLなどと区別します。
詳しくはデータベース章で扱います。

## 37 SDL

**SDL**、Specification and Description Languageは、通信システムなど、出来事を受けて状態が変わるシステムの仕様と動作を記述する形式言語です。

状態、入力信号、出力信号、遷移、処理などを図や文章で表します。

```text
待機状態
  ├─「開始」を受信 → 動作中状態
  └─「取消」を受信 → 待機状態
```

曖昧な自然文だけでなく、状態遷移を厳密に検討し、検証やコード生成につなげられます。

## 38 ADL

**ADL**、Architecture Description Languageは、ソフトウェアやシステムの構成要素、接続、インターフェース、制約を記述する言語の総称です。

```text
注文サービス ─→ 在庫サービス
      │
      └────→ 決済サービス
```

単なる箱と線だけでなく、部品が提供・要求する機能、通信方式、配置、性能制約などを記述できるADLがあります。
特定の一言語名ではなく、目的を共有する言語群を指す場合があります。

## 第3部　UML

## 39 UMLとは何か

**UML**、Unified Modeling Languageは、ソフトウェアを中心とするシステムの構造や振る舞いを図で表すための標準的な表記法です。

UMLはプログラミング言語ではありません。
図を描けば自動的によい設計になるわけでもありません。

役割は、関係者の考えを見える形にし、要求、構造、動作、配置の認識をそろえることです。

## 40 モデルは現実の一部を選ぶ

図を詳しく描けば、表現できる現実の範囲は広がります。
目的に関係しない情報まで入れると、判断に必要な関係が埋もれ、更新も追いつかなくなります。

地図は現実の町をすべて再現せず、道路地図なら道路、鉄道路線図なら駅と接続を強調します。

UML図も目的に必要な情報だけを選びます。
1枚にすべてを詰めると読めません。

- 利用者に何を提供するかを見る。
- クラスの構造を見る。
- 1操作の時間順を見る。
- 状態変化を見る。
- 実行機器への配置を見る。

目的ごとに図を選びます。

## 41 構造図と振る舞い図

UML図は大きく分けられます。

### 構造を表す図

- クラス図
- オブジェクト図
- コンポーネント図
- パッケージ図
- 配置図
- コンポジット構造図

### 振る舞いを表す図

- ユースケース図
- アクティビティ図
- ステートマシン図
- シーケンス図
- コミュニケーション図
- 相互作用概要図
- タイミング図

シーケンス図などは、振る舞い図の中でも相互作用図に分類されます。

## 42 クラス図

クラス、属性、操作、クラス同士の関係を表します。

```text
┌─────────────────┐
│ Product          │  ← クラス名
├─────────────────┤
│ -name: String    │  ← 属性
│ -price: Integer  │
├─────────────────┤
│ +changePrice(p)  │  ← 操作
└─────────────────┘
```

### 42.1 属性

オブジェクトが持つデータを**属性**と呼びます。
`name`、`price`などです。

### 42.2 操作

オブジェクトに依頼できる処理を**操作**と呼びます。
実装された処理本体をメソッドと呼ぶことがあります。

`+`は公開、`-`は非公開、`#`は保護された可視性を示す記法です。

## 43 関連と多重度

クラス間に線を引くだけでも、何らかの関係は示せます。
1人が複数件を持てるのか、必ず1件必要なのかは、多重度を書かなければ読み手ごとに解釈が分かれます。

クラス間のつながりを**関連**で表します。

```text
Customer 1 ───── 0..* Order
```

1人のCustomerに0個以上のOrderが対応し、一Orderは一Customerに対応する意味です。

代表的な多重度です。

- `1`――ちょうど1つ。
- `0..1`――ないか1つ。
- `*`または`0..*`――0個以上。
- `1..*`――1個以上。
- `2..5`――2個以上5個以下。

## 44 ロール名

関連の端で、相手が自分にとってどの役割かを示す名前を**ロール名**と呼びます。

```text
Employee ───── Department
 employee      employer
```

自己関連では特に役立ちます。

```text
Employee  manager 0..1 ───── 0..* subordinates Employee
```

同じEmployee型でも、上司と部下の役割を区別できます。

## 45 集約とコンポジション

全体と部分の関係を表します。

- **集約**――白いひし形。
  部分が全体と別に存在し得る弱い所有。
- **コンポジション**、合成――黒いひし形。
  部分の寿命が全体に強く属する。

```text
Team ◇── Player       集約の例
Order ◆── OrderLine   合成の例
```

現実の意味に基づいて使います。
単に「配列を持つ」から合成、と機械的に決めません。

## 46 汎化と実現

一般的な型と特殊な型の関係を**汎化**と呼び、白三角矢印を一般側に向けます。

```text
Dog ─────▷ Animal
Cat ─────▷ Animal
```

インターフェースの約束をクラスが実装する関係を**実現**と呼び、破線の白三角矢印で表します。

## 47 依存

1クラスが一時的に別クラスを引数や局所変数として使うなど、変更の影響を受ける関係を**依存**と呼び、破線矢印で表します。

関連より弱い一時的利用を示すことが多いですが、図の目的に応じ、必要な依存だけを描きます。

---

## 48 オブジェクト図

ある時点の具体的なオブジェクトと値、リンクを表します。
クラス図が型の設計図なら、オブジェクト図は一瞬の実例です。

```text
product42:Product
name = "鉛筆"
price = 120
```

多重度や関連が実際の事例でどう見えるか確認し、複雑なデータ構造を説明するのに役立ちます。

## 49 パッケージ図

モデル要素をまとめた**パッケージ**と、その依存関係を表します。

```text
┌────────┐      ┌────────┐
│ 注文   │ ───→ │ 在庫   │
└────────┘      └────────┘
```

大規模システムの名前空間、層、機能群を整理します。
依存が循環していないか、上位層が下位実装にどう依存するかを見ます。

## 50 コンポーネント図

交換・配布できるソフトウェア部品と、提供・要求するインターフェースを表します。

```text
[注文Web] ──要求── (在庫API) ── [在庫サービス]
```

クラスより大きな実装単位、サービス、ライブラリ、実行部品の依存を見るのに使います。

## 51 配置図

サーバ、端末、実行環境などの**ノード**に、どのソフトウェア部品を配置するか表します。

```text
<<device>> 利用者PC
  └─ブラウザ
       │ HTTPS
<<server>> Webサーバ
  └─注文アプリ
       │ DB接続
<<server>> DBサーバ
  └─注文DB
```

物理・仮想構成、通信路、冗長化、セキュリティ境界、性能上の配置を検討します。

## 52 コンポジット構造図

1クラスやコンポーネントの内部を、部品、接続、外部との窓口で表します。

- **part**――内部を構成する部品。
- **port**――外部との相互作用点。
- **connector**――部品・ポート間の接続。

```text
┌──────── OrderProcessor ────────┐
│ [validator]──[calculator]──[repo] │
└──── port: orderAPI ─────────────┘
```

クラス図が型同士の関係を示すのに対し、コンポジット構造図は1要素の内部協調を見せます。

---

## 53 ユースケース図

システムの外にいる利用者・外部システムが、システムからどの目的を達成できるかを表します。

- **アクター**――役割としての利用者・外部システム。
- **ユースケース**――外部から見た目的。
- **システム境界**――対象範囲。

```text
顧客 ─── (商品を検索する)
顧客 ─── (注文する)
管理者 ─ (商品を登録する)
```

画面のボタン一覧や内部関数一覧ではなく、アクターに価値を与える目的を書きます。

## 54 includeとextend

どちらもユースケース間を結ぶため、部品の再利用を表す同じ矢印に見えます。
`include`は必ず組み込む共通処理、`extend`は条件に応じて追加される振る舞いです。

複数ユースケースが必ず共通処理を含む関係を`<<include>>`で表します。

```text
(注文する) ──include──> (本人を確認する)
```

特定条件で追加される任意・条件付き振る舞いを`<<extend>>`で表します。

```text
(クーポンを適用する) ──extend──> (注文する)
```

矢印方向を混同しやすいので、includeは基本側から含まれる側、extendは追加側から拡張される基本側に向けます。

## 55 アクティビティ図

処理や業務の流れ、分岐、並行を表します。
フローチャートに似ていますが、活動間の流れや並行処理を表すUML図です。

```text
● 開始
↓
[注文を受ける]
↓
◇ 在庫あり?
├─はい→[決済する]→◎ 終了
└─いいえ→[欠品を通知]→◎
```

太い棒で流れを複数に分けるfork、複数を待ち合わせるjoinを表します。
担当ごとの**スイムレーン**に分ければ責任分担を見せられます。

## 56 ステートマシン図

1つの対象が、出来事に応じて状態を変える様子を表します。

```text
[未払い] --支払成功--> [支払済み]
[支払済み] --発送--> [発送済み]
[未払い] --期限切れ--> [取消]
```

遷移ラベルは次の形で書けます。

```text
イベント [ガード条件] / アクション
```

例は`支払要求 [残高あり] / 領収記録を作る`です。

- イベントは遷移のきっかけ。
- ガードは遷移してよい条件。
- アクションは遷移時の処理。

状態数が少なく見えても、独立した状態軸を無理に組み合わせると爆発します。
必要なら複合状態や並行領域を使います。

---

## 57 シーケンス図

複数の参加者が送るメッセージを、上から下の時間順で表します。

```text
顧客     画面       注文サービス       在庫
 |        |              |              |
 |注文--->|              |              |
 |        | create() --->|              |
 |        |              | check() ---->|
 |        |              |<---- available|
 |        |<----- success|              |
 |<--完了-|              |              |
```

縦の破線は**ライフライン**、細長い長方形は実行中の区間、横矢印はメッセージです。

## 58 同期メッセージと非同期メッセージ

呼出し結果が返るまで待つものを同期メッセージ、送った後に別処理を続けるものを非同期メッセージとして描き分けます。

戻りメッセージは破線矢印で表すことがあります。
図記号だけでなく、待つか、順序保証があるか、失敗時どうするかを注記します。

## 59 複合フラグメント

シーケンス図の一部を枠で囲み、条件や繰返しを表します。

- `alt`――条件によるどれか1つ。
  if/else。
- `opt`――条件付きで行う。
- `loop`――繰返し。
- `par`――並行。
- `break`――条件時に残りを中断。

正常経路だけでなく、在庫なし、タイムアウト、再試行などを描くと、隠れた要求を見つけられます。

## 60 コミュニケーション図

オブジェクト同士のリンクを空間的に配置し、メッセージに番号を付けて順序を表します。

```text
customerUI ──1:createOrder()── orderService
orderService ──1.1:check()── inventory
```

シーケンス図は時間順を読みやすく、コミュニケーション図は参加者間の結び付きに焦点を当てます。
同じ相互作用を別の見方で表します。

## 61 相互作用概要図

複数の相互作用、たとえばシーケンス図で詳しく表した場面を、アクティビティ図のような流れで結びます。

```text
●
↓
[ログインの相互作用]
↓
◇ 成功?
├→ [注文の相互作用]
└→ [エラー案内の相互作用]
```

大きな業務シナリオの流れと、各場面の詳細なやり取りを階層化できます。

## 62 タイミング図

横方向の時間に沿い、複数の対象の状態や値がいつ変わるか表します。

```text
時間 →
信号A  LOW ────┐ HIGH ─────┐ LOW
                └───────────┘
状態B  待機 ───── 動作中 ─── 完了
```

制御装置、通信プロトコル、リアルタイムシステムで、期限、遅延、同時関係を確認するのに向きます。

## 63 図同士の整合性

各図が単独で正しく見えても、同じ操作の名前や登場する部品が図ごとに違えば、システム全体の説明は食い違います。
複数の図を使う価値は視点を増やすことにあり、別々の仕様を作ることにはありません。

別の図が同じシステムを表すなら、内容が食い違ってはいけません。

- ユースケース「注文する」を実現するシーケンスがあるか。
- シーケンスで呼ぶ操作がクラス図にあるか。
- ステートマシン上で禁止された状態変更を、活動が行っていないか。
- コンポーネントが要求するインターフェースを提供者が持つか。
- 配置先で必要な通信が可能か。

UMLツールで一部を検査できても、意味上の整合は人のレビューが必要です。

## 64 図を描きすぎない

変更のたびに全図を直せず、古い図が残ると逆に誤解を生みます。

次を明確にします。

- 誰のどの判断に使う図か。
- どの抽象度か。
- 正式に保守する図か、一時的な検討図か。
- ソースや設定から自動生成できるか。

世界全体を描くのではなく、重要で説明しにくい関係を最小の図で示します。

## 解答

1. 文章・データに、見出しや段落など構造・意味を示す印を付けることです。
2. タグは山括弧の印、要素は開始から内容・終了までの構造、属性は要素への追加情報です。
3. 後から開いた内側を先に閉じます。
4. 特別文字を文法記号でなくデータとして安全に表すためです。
5. 同じ構造に異なる表示を適用し、意味、保守、アクセシビリティを保ちやすくするためです。
6. SGMLは文書型を定義する大きな枠組みで、HTMLは歴史的にその応用として定義されました。
7. 使える要素、順序、出現回数、属性などの文書型です。
8. `product`や`price`など、交換する用途の合意に合わせて要素名と構造を定義できることです。
9. 整形式はXML基本文法を守ること、妥当性はDTDやSchemaで定めた用途別構造にも従うことです。
10. 異なる用途で同じ要素名が持つ意味の衝突を防ぎます。
11. DOMは全体を木にして多くの記憶を使うが自由に移動・変更でき、SAXは先頭からイベントで流して少ない記憶で扱えます。
12. 整数・日付などの型、値範囲、出現回数、名前空間などです。
13. Envelopeは全体の封筒、Headerは付加情報、Bodyは要求・応答本体です。
14. 画素でなく円や線などの形と座標を保存し、拡大時に再描画できるからです。
15. 全要素を閉じ、正しい入れ子、引用符、小文字などXMLの整形式を求めます。
16. Basicは限られた端末向け基本機能集合、Modularizationは機能群を部品化して必要な文書型を組み立てる仕組みです。
17. セレクタは対象要素を選び、プロパティは変更する表示項目、値は設定内容です。
18. 複数の規則が当たるとき、由来、重要度、具体性、順序などで最終値を決める仕組みです。
19. CSSは主に文書の表示を指定し、XSLTはXML構造を別文書に変換します。
20. オブジェクト、配列、文字列、数値、真偽値、nullです。
21. 一重引用符の文字列、末尾カンマ、コメント、NaN、Infinityなどです。
22. JSON標準に専用日付型がなく、受取側の数値精度で大整数が丸められる場合があるからです。
23. 字下げ自体が親子構造を表すためです。
24. 安全読込み機能、許可型制限、サイズ・深さ・別名数の制限、スキーマ検証などです。
25. DDLはDB構造、SDLは状態と信号によるシステム動作仕様、ADLは構成要素と接続などのアーキテクチャです。
26. いいえ。
   システムをモデル化して伝える標準表記法です。
27. 属性は持つデータ、操作は外部から依頼できる処理です。
28. `0..1`はないか1つ、`1..*`は1つ以上です。
29. 関連先が自分にとってどの役割かを示し、特に自己関連や複数関連を区別します。
30. 集約は部分が別に存在し得る弱い全体・部分、合成は部分の寿命が全体に強く属する関係です。
31. クラス図は型と関係、オブジェクト図はある時点の具体例と値を表します。
32. コンポーネント図はソフトウェア部品とインターフェース、配置図は機器・実行環境に何を置くかに注目します。
33. 1クラス・コンポーネント内部の部品、ポート、接続を表します。
34. いいえ。
   顧客、管理者、外部決済システムなど、システムと関わる役割です。
35. includeは必ず含む共通動作、extendは特定条件で基本ユースケースに加える動作です。
36. アクティビティ図は仕事・制御の流れ、ステートマシン図は一対象の状態とイベントによる遷移に焦点を当てます。
37. 時間の進行です。
38. `alt`は条件分岐、`loop`は繰返し、`par`は並行です。
39. 参加オブジェクト同士のリンク・構造を強調します。
40. 相互作用概要図は複数の相互作用を大きな流れで結び、タイミング図は時間に沿う状態・値の変化を表します。
41. シーケンス図で呼ぶ操作がクラス図にもあるか、コンポーネントの要求APIを提供者が持つかなどです。
42. 保守できず古い図が誤解を生み、読み手の判断に不要な細部で重要関係が埋もれるからです。
