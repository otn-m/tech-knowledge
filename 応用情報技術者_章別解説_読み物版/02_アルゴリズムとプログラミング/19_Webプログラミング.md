# 第2章・第19話　Webプログラミング――ブラウザの向こうで何が動くのか

ブラウザに1つの画面が表示されるまでには、複数の通信と処理が進みます。
HTMLを受け取った後も、画像、スタイル、プログラムを取得し、文書の構造と表示を組み立てます。

利用者の操作に応じてサーバへ追加の要求を送る場合は、応答を待つ時間や、返ってくる順序も画面の動作に関係します。
URLからHTTPの交換、サーバとブラウザの分担、状態の保持へと、画面の背後にある処理を追います。

## URLから要求と応答へ進む

### 1 Webとは何か

**Web**、World Wide Webは、ネットワーク上の文書や機能を、リンクで結び、共通の方法で取得・利用する仕組みです。

インターネットは、世界中のネットワーク同士を結ぶ基盤です。
Webはその上で動く代表的なサービスの1つです。
電子メールもインターネットを使いますが、Webそのものではありません。

### 2 ブラウザ

Webページを取得し、画面に表示し、利用者の操作を受けるプログラムを**Webブラウザ**と呼びます。

ブラウザは、主に次の処理を行います。

- URLを解釈する。
- サーバに要求を送る。
- HTML、CSS、画像、プログラムなどを受け取る。
- 文書構造と見た目を組み立てる。
- JavaScriptを実行する。
- 画面を描き、クリックや文字入力を処理する。
- 保存情報や安全上の制限を管理する。

### 3 クライアントとサーバ

サービスを要求する側を**クライアント**、要求を受けて機能やデータを提供する側を**サーバ**と呼びます。

```text
利用者
  ↓操作
ブラウザ（クライアント）
  ↓ 要求
Webサーバ
  ↓ 応答
ブラウザ
  ↓表示
利用者
```

サーバは機械を指すことも、その機械で待ち受けるプログラムを指すこともあります。
文脈で判断します。

### 4 URL

Web上の場所を表す文字列を**URL**、Uniform Resource Locatorと呼びます。

```text
https://example.com:443/products/42?color=blue#reviews
```

このURLは、次の部分に分けて読めます。

```text
https     通信方法を表すスキーム
example.com サーバ名、ホスト名
443       ポート番号。省略されることが多い
/products/42 パス
color=blue クエリ文字列
reviews   ページ内の位置を表すフラグメント
```

フラグメントは通常、サーバへのHTTP要求には送られず、ブラウザ内で使われます。

### 5 HTTP

ブラウザとWebサーバが要求と応答を交換する代表的な約束が**HTTP**です。
暗号化などで保護した通信がHTTPSです。

ブラウザからの要求を**HTTPリクエスト**、サーバからの返事を**HTTPレスポンス**と呼びます。

```text
クライアント → リクエスト → サーバ
クライアント ← レスポンス ← サーバ
```

ネットワークの細かな仕組みは後章で扱います。
1回の要求には、方法、宛先、付加情報があり、場合によって本文も含まれます。
応答には、状態、付加情報、本文があります。

## HTTPの契約を読む

### 6 HTTPメソッド

要求の目的を表すものを**HTTPメソッド**と呼びます。

- GET――情報を取得する。
- POST――データを送り、新規処理などを依頼する。
- PUT――指定先の全体を作成・置換する。
- PATCH――一部を変更する。
- DELETE――削除する。

実際の意味はサービス設計で決まりますが、共通の意味に沿うと利用者、ブラウザ、キャッシュ、ツールが扱いやすくなります。

GETで注文確定など状態変更を行うと、リンクの先読み、再読込み、検索機械の巡回だけで処理が起きる危険があります。

### 7 状態コード

HTTPレスポンスには、結果を3桁の数で表す**状態コード**があります。

- 2xx――成功。
  200 OKなど。
- 3xx――別場所への転送など。
  301、302など。
- 4xx――要求側に関係する問題。
  400、401、403、404など。
- 5xx――サーバ側の失敗。
  500、503など。

`404 Not Found`は要求した資源が見つからないことです。
画面に200と表示されなくても、ブラウザ内部では状態コードを受け取っています。
HTTP上の応答が成功していても、本文に業務上のエラーを返すAPI設計はあり得ます。
利用する際は、状態コードと応答内容の契約を併せて確認します。

### 8 ヘッダと本文

要求・応答には、処理に必要な付加情報である**ヘッダ**と、実際の内容である**ボディ**、本文があります。

応答ヘッダの例です。

```text
Content-Type: text/html; charset=utf-8
Content-Length: 1234
```

`Content-Type`は本文がHTML、JSON、画像など何であるかを示します。
型を正しく示さないと、誤表示や安全上の問題につながる場合があります。

## サーバが応答内容を作る

### 9 静的なWebページ

保存済みのHTMLファイルをそのまま返すページを、ここでは**静的ページ**と呼びます。

```text
GET /about.html
     ↓
保存済みabout.htmlを返す
```

要求ごとに内容を計算しないため、単純で高速に配布しやすい特徴があります。
画像、CSS、JavaScriptファイルも静的資源として配信できます。

### 10 動的なWebページ

利用者、時刻、データベースなどに応じ、サーバ側プログラムが応答内容を作るページを**動的ページ**と呼びます。

```text
GET /products/42
     ↓
商品番号42をデータベースから読む
     ↓
商品名、価格、在庫をHTMLへ埋める
     ↓
応答する
```

同じURLでも、ログイン中の利用者や在庫状況で内容が変わります。

### 11 Webサーバ

HTTP要求を待ち受け、静的ファイルを返したり、アプリケーションに処理を渡したりするプログラムを**Webサーバ**と呼びます。

Apache HTTP Serverは代表例です。
ほかにも多くのWebサーバがあります。

```text
ブラウザ
  ↓ HTTP
Webサーバ
  ├─静的ファイルなら直接返す
  └─動的要求ならアプリケーションへ渡す
```

暗号通信、アクセス制御、圧縮、ログ、別サーバへの転送などを担う場合もあります。

### 12 サーバサイドプログラミング

サーバ上で要求を受け、業務処理を行い、応答を作ることを**サーバサイドプログラミング**と呼びます。

サーバ側では、次の役割を担います。

- 入力を検証する。
- 利用者を認証し、権限を確認する。
- データベースを読み書きする。
- 在庫、料金、予約などの業務規則を実行する。
- HTMLやJSONを作る。
- ログ、監査、エラー処理を行う。

Java、PHP、Python、Ruby、JavaScript、Goなど多様な言語・枠組みを使えます。

### 13 JSP

**JSP**、JavaServer Pagesは、HTMLにJava側の動的出力を組み合わせるサーバ側技術です。

概念的には次のようなテンプレートです。

```text
<h1>こんにちは、${userName}さん</h1>
```

サーバが`userName`を安全に埋め、完成したHTMLをブラウザに送ります。
ブラウザにJSPのソースやJavaの処理自体を送るのではありません。

複雑な業務処理を表示テンプレートに全部書くと保守しにくいため、表示、制御、業務ロジックを分けます。

### 14 CGI

Webサーバが外部プログラムを起動し、要求情報を渡して応答を受け取る共通の仕組みに**CGI**、Common Gateway Interfaceがあります。

初期の動的Webで広く使われました。
要求ごとにプロセスを起動する単純な方式は負荷が大きいため、常駐プロセス、アプリケーションサーバ、FastCGIなどの方式が使われます。

### 15 アプリケーションサーバ

Webサーバの後ろで、業務プログラムの実行環境、接続管理、トランザクション、認証などを提供するものを**アプリケーションサーバ**と呼びます。

製品や構成によりWebサーバとの境界は異なります。
1つのプログラムが両方の役割を持つ場合もあります。

## ブラウザが構造と動作を組み立てる

### 16 HTML、CSS、JavaScriptの分担

ブラウザ側では、3つの技術で構造、表示、動作を分担します。

- HTML――文書の構造と意味。
- CSS――見た目と配置。
- JavaScript――動作と操作への反応。

文書の見出しや段落をHTMLで表し、色や配置をCSSで指定し、クリック後の処理をJavaScriptで記述します。

### 17 クライアントサイドプログラミング

ブラウザ内で動くプログラムを書くことを**クライアントサイドプログラミング**と呼びます。

JavaScriptで次を行えます。

- クリックや入力を処理する。
- 入力の見た目上の誤りをすぐ案内する。
- ページの一部を変更する。
- サーバに追加要求を送り、結果を表示する。
- アニメーションや複雑な操作画面を作る。

利用者の機械で動くため、サーバ負荷を減らし、素早い反応を作れます。
しかし利用者はコードを読んだり変更したり、要求を直接作ったりできます。

したがって、権限確認、価格計算、重要な入力検証をクライアント側だけに任せてはいけません。
サーバ側で必ず再確認します。

### 18 DOM

ブラウザはHTMLを木構造として扱います。
これを**DOM**、Document Object Modelと呼びます。

```html
<body>
  <h1>商品</h1>
  <button>購入</button>
</body>
```

概念上、次の木になります。

```text
body
├─h1
│ └─「商品」
└─button
  └─「購入」
```

JavaScriptはDOMの要素を探し、文字、属性、子要素、見た目を変更できます。

### 19 イベント

クリック、キー入力、読込み完了、通信完了など、発生した出来事を**イベント**と呼びます。

イベントが起きたとき呼ぶ関数を**イベントハンドラ**と呼びます。

```text
購入ボタンのクリック時
    数量を読む
    サーバへ注文要求を送る
```

Web画面は、上から下に一度実行して終わるだけでなく、イベントを待ち、起きるたび処理する**イベント駆動**で動きます。

### 20 リッチクライアント

サーバに毎回画面全体を作らせるだけでなく、クライアント側に多くの表示・操作機能を持たせたものを**リッチクライアント**と呼びます。

Webブラウザで動くリッチなアプリケーションは、デスクトップアプリに近い操作感を提供します。

ただしクライアントが複雑になり、状態管理、端末性能、ブラウザ差、アクセシビリティ、安全性を考える必要があります。

## 非同期通信で画面の一部を更新する

### 21 Ajax

ページ全体を読み直さず、ブラウザ内のプログラムが裏でサーバと通信し、必要部分だけ更新する考えを**Ajax**と呼びます。

名前はAsynchronous JavaScript and XMLに由来します。
現在はXMLだけでなくJSONも広く使います。

```text
利用者が検索語を入力
  ↓
JavaScriptがサーバへ検索要求
  ↓ ページ全体は残る
サーバが候補データを返す
  ↓
JavaScriptが候補欄だけ更新
```


### 22 非同期とは何か

要求を送った後、返事が来るまで画面全体を止めず、別の操作や描画を続け、完了時に結果を処理することを**非同期処理**と呼びます。

通信の待ち時間と、画面操作を処理する時間を分けて扱います。

JavaScriptでは、コールバック、Promise、`async/await`などで完了後処理を書きます。

### 23 非同期処理の順序問題

複数の通信を並行に始めると、完了順が開始順と違うことがあります。
古い応答で新しい画面状態を上書きしないように、どの要求への応答かを区別します。

検索欄に「cat」と入力した直後に「car」に変えたとします。

```text
要求1: cat ─────────→ 遅く返る
要求2: car ───→ 早く返る
```

要求2の結果を表示した後、古い要求1が返って上書きすると、入力と違う候補になります。

要求番号を付けて最新だけ採用する、古い要求を取消す、現在の入力と応答条件を照合するなどの対策が必要です。

### 24 JSON

サーバとブラウザのデータ交換によく使う文字形式が**JSON**です。

```json
{
  "productId": 42,
  "name": "鉛筆",
  "price": 120,
  "inStock": true
}
```

人が比較的読みやすく、多くの言語で扱えます。
HTMLそのものではなく、データ構造を文字で表します。

JSONの文法は、次話のマークアップ・データ記述・UMLで扱います。

### 25 Web API

Webを通じ、プログラムから機能やデータを利用する窓口を**Web API**と呼びます。

```text
GET /api/products/42
→ 商品42のJSON
```

人間向け画面と違い、入力形式、出力形式、状態コード、認証方法、利用制限、版の約束が重要です。

### 26 RESTという設計の考え

Webの性質を活かし、商品、注文、利用者などを資源としてURLで表し、HTTPメソッドで操作する設計様式を**REST**と呼びます。

```text
GET    /orders/123  注文123を取得
POST   /orders      注文を作成
PATCH  /orders/123  一部変更
DELETE /orders/123  削除
```

「HTTPを使えばすべてREST」というわけではありません。
状態をサーバの会話履歴に依存させないなど複数の制約があります。
実務ではREST風APIという広い用法もあります。

## 画面の構成と実行場所を選ぶ

### 27 SPA

初回にアプリケーションの枠とJavaScriptを読み込み、その後はデータを取得しながらブラウザ内で画面を切り替える構成を**SPA**、Single Page Applicationと呼びます。

1つのHTMLしか見えないというより、ページ全体の再読込みを繰り返さず、1つのアプリとして複数画面を実現する考えです。

#### 27.1 利点

- 画面切替を素早く滑らかにできる。
- クライアント側で状態を保ち、複雑な操作を作れる。
- サーバをデータAPIとして分離しやすい。

#### 27.2 課題

- 初回に多くのコードを読む場合がある。
- クライアント側の状態管理が複雑になる。
- URL、戻るボタン、再読込みを正しく設計する必要がある。
- 検索機械や画面読上げへの配慮が必要。
- JavaScriptが動かない・失敗した場合の扱いが必要。

### 28 クライアント側ルーティング

SPAでも、利用者が特定画面をURLで保存・共有できる必要があります。
URLのパスと表示部品を対応付ける処理を**ルーティング**と呼びます。

```text
/products/42 → 商品詳細画面
/cart        → カート画面
```

ブラウザの履歴APIを使い、戻る・進む操作とも整合させます。
サーバも、そのURLを直接開いたときSPAの入口を返す設定が必要です。

### 29 フロントエンドフレームワーク

画面部品、状態、イベント、画面切替を組み立てる共通仕組みを提供するものを**フロントエンドフレームワーク**またはライブラリと呼びます。

画面を組み立てるために、次のような仕組みを提供します。

- UIを再利用可能なコンポーネントに分ける。
- 状態が変われば表示を更新する。
- データの流れを規則化する。
- ビルド、テスト、画面切替の道具を組み合わせる。

ツールを使うだけで複雑さが消えるわけではありません。
小さな静的ページに大規模枠組みを入れると、配布量と保守負担が増す場合があります。

### 30 コンポーネント

画面を独立した部品に分けます。

```text
商品ページ
├─商品画像
├─商品情報
├─数量入力
├─購入ボタン
└─レビュー一覧
```

各部品が受け取る値を**プロパティ**、内部で変わる値を**状態**と呼ぶ枠組みがあります。

部品を小さくしすぎると追跡が難しく、大きすぎると再利用・テストしにくくなります。
利用者に見える1つの役割を目安にします。

### 31 サーバサイドレンダリング

SPAのJavaScriptだけで最初の画面を作るのではなく、サーバで初期HTMLを作って返すことを**サーバサイドレンダリング**、SSRと呼びます。

初期表示、検索機械、低性能端末への利点があります。
その後ブラウザ側プログラムがイベント処理を引き継ぐことを**ハイドレーション**と呼ぶ枠組みがあります。

サーバとブラウザが同じ初期表示を作らないと不一致が起きるため、時刻や乱数などにも注意します。

### 32 WebAssembly

**WebAssembly**、略してWasmは、ブラウザなどで実行できる低水準のバイナリ命令形式です。

C、C++、Rustなどで書いた処理をWasmにコンパイルし、画像処理、ゲーム、数値計算などをWebで高速に動かす用途があります。

```text
別言語のソース
  ↓ コンパイル
WebAssemblyモジュール
  ↓ ブラウザの実行環境
実行
```

JavaScriptを完全に置き換えるものではありません。
DOM操作などWeb機能との連携にはJavaScriptや標準インターフェースを使うことが多くあります。

ブラウザの安全な隔離環境、**サンドボックス**内で動き、明示的に許された機能にだけアクセスします。
ただしWasmを使うだけでコードが安全になるわけではありません。

## 独立した要求に状態を持たせる

### 33 HTTPは基本的に状態を覚えない

HTTPの各要求は、基本的に独立しています。
サーバは何もしなければ、2回目の要求が1回目と同じ利用者か分かりません。
この性質を**ステートレス**と呼びます。

ログインや買物かごを続けるため、利用者を識別する仕組みが必要です。

### 34 Cookie

サーバからブラウザに保存を依頼し、後の要求で同じサイトに送る小さな値を**Cookie**と呼びます。

```text
サーバ → Set-Cookie: sessionId=abc...
ブラウザが保存
次の要求 → Cookie: sessionId=abc...
```

Cookieにパスワードや重要データそのものを置くのではなく、推測困難なセッション識別子を置き、実データをサーバ側に持つ設計があります。

`Secure`、`HttpOnly`、`SameSite`などの属性で送信条件とスクリプトアクセスを制限します。

### 35 セッション

複数の要求にまたがる1利用者の状態を**セッション**と呼びます。

```text
CookieのsessionId
       ↓
サーバ上のセッション表
       ↓
ログイン利用者、買物かごなど
```

識別子が盗まれると利用者になりすまされる可能性があります。
ログイン時の再発行、HTTPS、期限、ログアウト時の無効化などが必要です。

サーバを複数台に増やす場合、どのサーバでもセッションを読める共有保存場所を使うか、状態を署名付きトークンに持たせるなどの設計が必要です。

### 36 キャッシュ

一度取得した応答をブラウザや中継装置に一時保存し、再利用する仕組みを**キャッシュ**と呼びます。

応答を再利用すると、通信量と待ち時間、サーバ負荷を減らせます。
再検証までの期間を延ばすと、サーバの更新が利用者へ反映されるまでの時間も長くなります。
しかし古いデータや、別利用者向けの機密応答を誤って返さないよう、有効期限、再検証、公開範囲をヘッダで指定します。

更新したのに古いJavaScriptが残る問題を避けるため、ファイル名に内容のハッシュを含める方法があります。

## 入力と通信の境界を守る

### 37 Web入力は信用しない

ブラウザ画面で入力欄を制限しても、利用者はHTTP要求を直接作れます。

```text
画面では数量1〜10
攻撃者は数量-999を直接送る
```

サーバは、すべての外部入力を型、長さ、範囲、形式、権限、関係性で検証します。

### 38 XSS

利用者入力をHTMLにそのまま埋め込み、悪意あるスクリプトが別利用者のブラウザで動く問題を**クロスサイトスクリプティング**、XSSと呼びます。

入力を全部削るのではなく、出力する場所に合った**エスケープ**を行います。

- HTML本文に出す。
- HTML属性に出す。
- URLに入れる。
- JavaScript文字列に入れる。

場所ごとに安全な変換が違います。
信頼できないHTMLを許すなら、安全な要素だけ残すサニタイズも必要です。

### 39 SQLインジェクション

入力文字列をSQL命令に連結すると、入力が命令の一部として解釈される危険があります。

```text
危険な考え:
"SELECT ... WHERE name='" + userInput + "'"
```

値と命令を分離する**パラメータ化クエリ**、プレースホルダを使います。
単なる引用符の置換を自作せず、データベース用ライブラリに値として渡します。

### 40 CSRF

ログイン中の利用者のブラウザに、別サイトから意図しない状態変更要求を送らせる攻撃を**クロスサイトリクエストフォージェリ**、CSRFと呼びます。

同じサイトから発行したと確認できるCSRFトークン、CookieのSameSite属性、Origin確認、重要操作の再認証などを使います。

GETで状態変更しないことも基本です。

### 41 同一生成元ポリシーとCORS

悪意あるWebページが、利用者の別サイトのデータを勝手に読むのを防ぐブラウザの基本制限が**同一生成元ポリシー**です。

スキーム、ホスト、ポートの組を**オリジン**と呼びます。

別オリジンからの読取りをサーバが明示的に許可する仕組みが**CORS**です。
CORSが制御するのは、ブラウザが応答をスクリプトへ渡す範囲です。
利用者の認証や権限確認は別に行います。
誰でも読めるよう`*`を付けても、安全になるわけではありません。

## 失敗と利用環境を含めて設計する

### 42 非同期要求の失敗を扱う

通信は必ず成功するわけではありません。

- 接続できない。
- タイムアウトする。
- サーバが5xxを返す。
- 応答形式が壊れている。
- 利用者が途中で画面を閉じる。
- 同じ操作が二重送信される。

読み込み中表示、取消し、再試行、エラー案内を設計します。
注文や決済では、再試行しても1回だけ処理される**冪等性**の仕組み、たとえば一意な要求IDが必要です。

### 43 性能を見る場所

画面が遅い原因は1か所とは限りません。

```text
名前解決
接続・暗号通信
要求送信
サーバ待ち
応答受信
HTML解析
JavaScript実行
画像・フォント取得
配置と描画
```

計測せず「サーバが遅い」「JavaScriptが遅い」と決めません。
ブラウザの開発者ツール、サーバログ、分散追跡などで時間を分解します。

### 44 アクセシビリティ

視覚、聴覚、運動、認知などの違いがあっても利用できるよう設計することを**アクセシビリティ**と呼びます。

- 見出しやボタンを意味あるHTML要素で作る。
- キーボードだけでも操作できる。
- 画像に代替テキストを付ける。
- 色だけで状態を伝えない。
- 十分な色の差と拡大への対応をする。
- 入力エラーを理解できる言葉で示す。

クリック可能な見た目を`div`だけで作るより、標準の`button`を使う方が、キーボード操作や読上げの意味を得やすくなります。

### 45 段階的強化

基本的なHTMLだけでも主要内容と操作を使えるようにし、CSSやJavaScriptで体験を強化する考えを**段階的強化**と呼びます。

すべてのアプリで完全にJavaScriptなしに対応できるとは限りません。
それでも、通信失敗、低速端末、読上げ、検索機械など、多様な環境を考える原則になります。

商品ページを1つ表示するにも、資源の取得、HTMLの解析、プログラムの実行、画面の描画が必要です。
購入ボタンを押した後は、非同期要求の順序、サーバ側の検証、セッション、二重送信への対処まで関係します。
画面の動作を理解するには、どこで何を処理し、どの要求にどの応答が返るかを追います。
