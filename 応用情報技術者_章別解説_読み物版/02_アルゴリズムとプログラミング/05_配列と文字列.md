# 第2章・第5話　配列と文字列――同じ種類の値を、番号付きで並べる

同一データ型の値をメモリ上に一列に並べた配列構造では、添字さえ判明していれば目的の要素へ直接アクセスできます。
しかし、列の途中に新たな値を挿入する操作では、挿入位置より後方にあるすべての要素を1つずつ後ろへ移動させなければなりません。
同じ配列を扱う操作であっても、単一要素の参照、全体の走査、要素の追加や挿入では、計算量と必要な処理手順が根本的に異なります。

## 添字から位置を求め、全体を走査する

### 1 要素と添字

```text
scores = [70, 85, 90]
```

- 配列全体の名前――`scores`
- 格納された個々のデータ――要素。
- 要素の格納位置を示す識別番号――添字（インデックス）。

0から始まるインデックス体系を採用する言語では、各要素を次の添字によって指定する仕組みです。

```text
scores[0] = 70
scores[1] = 85
scores[2] = 90
```

要素数が3個である配列において、末尾要素の添字は2となります。

```text
要素数nなら、有効添字は0からn-1
```

各種試験の擬似言語仕様においては、配列の添字が1から開始される取り決めも珍しくありません。
問題を解く際は、添字の開始番号に関する定義を最初に確認する習慣が大切です。

### 2 なぜ0から始める言語が多いのか

日常生活において事物を順に数え上げる感覚からは、最初の番号を1とする方が直感に沿っています。
しかし計算機のメモリモデルにおいて、配列の添字を「先頭アドレスからのオフセット（相対距離）」と捉え直すと、先頭要素までの距離は0と定義するのが極めて自然です。

具体例として、配列の先頭番地を1000、各要素のデータサイズを4バイトと仮定してみましょう。

```text
0番目のアドレス = 1000 + 4×0 = 1000
1番目のアドレス = 1000 + 4×1 = 1004
i番目のアドレス = 1000 + 4×i
```

このように添字の数値を先頭からのずれ（offset）として直接乗算に利用できるわけです。

もちろん0始まりの設計だけが唯一絶対の正解というわけではありません。
歴史的な言語や特定の数式志向言語では1始まりを採用するものや、プログラマが任意の下限インデックスを定義できる環境も存在します。

### 3 ランダムアクセス

上記のメモリアドレス計算式を適用すれば、先頭アドレス、要素サイズ、そして添字の値から目的要素の物理番地を一意に特定可能です。
先頭から順に要素をたどることなく、任意の位置へ瞬時に到達できます。

この高速なアクセス特性をランダムアクセス（直接アクセス）と呼ぶわけです。

ここでのrandomという英単語は無作為やでたらめを指す言葉というよりも、任意の位置へ均一な時間で直接到達できる性質を意味しています。
したがって、配列における特定要素の参照操作の計算量は、通常`O(1)`です。

### 4 配列の走査

特定の1要素だけを直接読み出す処理とは対照的に、配列内の全要素を先頭から順次走査していく反復処理を**走査**と呼びます。

```text
for i = 0 から length(scores)-1 まで
    scores[i]を表示
```

要素の現在位置（添字）を意識せず要素値そのものだけを順次取り出せば十分な文脈では、次のような拡張for構文も活用されます。

```text
for each score in scores
    scoreを表示
```

添字情報がロジックに不可欠な処理なのか、要素値の読み出しだけで完結するのかに応じて最適な構文を使い分ける設計が基本です。

### 5 合計と平均

配列の全要素を1回ずつ走査すれば、要素全体の合計値と平均値を簡単に算出できます。

```text
total = 0
for each score in scores
    total = total + score

もし length(scores) > 0 なら
    average = real(total) / length(scores)
```

要素数が0の空配列が渡された場合に備え、0除算を未然に防止するガード処理が欠かせません。
また、整数型の除算によって小数部の端数が切り捨てられないよう、キャストの型変換にも配慮が必要です。

配列サイズをnとすると、全要素を1周走査するため計算量は`O(n)`となります。

### 6 最大値と最小値

配列内の最大値を探索するアルゴリズムでは、まず空配列の例外を検査した上で、先頭要素の値を暫定最大値として初期化します。

```text
もし配列が空なら
    データなし

maxValue = scores[0]
for i = 1 から length(scores)-1 まで
    もし scores[i] > maxValue なら
        maxValue = scores[i]
```

最初の要素`scores[0]`を初期値に採用したため、比較ループの走査開始位置は1番目の要素から始めれば十分です。

最大値そのものだけでなくその要素が存在したインデックス番号も保持したい場合は、値の更新と連動して`maxIndex`も記録します。

## 長さと容量、追加と移動の費用

### 7 固定長配列

配列のインスタンス生成時に要素数をあらかじめ固定し、後からのサイズ変更を許可しないデータ構造です。

```text
整数 scores[30]
```

必要なデータ総数が静的に確定している局面では極めてシンプルに扱え、メモリ上に連続した領域を無駄なく配置できます。
その反面、定義された最大容量を超過した要素の追加は一切行えず、使用されなかった空き領域はメモリ浪費につながる点に留意が必要です。

### 8 動的配列

実行時における要素の追加要求に応じて、自動的に領域を拡張できるように見せかける柔軟なデータ構造が動的配列です。
動的配列の内部実装では、現に格納されている有効データ数を表すサイズ（size）と、内部的に事前確保されたメモリ枠数を表す容量（capacity）の2つの属性を区別して管理します。

次の状態例では有効要素が3個、確保済み容量が4枠であるため、末尾に1枠の空き領域が存在しています。

```text
size=3, capacity=4
[A][B][C][空]
```

空き枠が尽きた満杯状態で新たな要素を追加しようとすると、処理系はより大きな新規メモリ領域を確保し、既存の全要素をそちらへ丸ごと移送するわけです。

```text
[A][B][C][D]  満杯
↓ 例えば容量8を新規確保してコピー
[A][B][C][D][空][空][空][空]
```


### 9 償却計算量

動的配列の末尾への要素追加は、内部配列に空き領域が残っている限り単なる代入操作にすぎず、計算量`O(1)`で完了します。
しかし容量不足が発生した際には、領域拡張のために全要素のメモリコピーが実行され、その1回に限り`O(n)`の多大なコストを要します。

容量が満杯になるたびに領域を1要素ずつしか増やさない愚直な設計をとると、追加のたびに毎回全コピーが発生して極めて非効率です。
そこで容量が枯渇した際には既存の2倍といった幾何級数的な倍率で一気に領域を拡張し、高コストな再配置処理の発生頻度を劇的に引き下げます。

多数回の追加操作全体をならして1回あたりの平均処理コストを算定した尺度を「償却計算量」と呼び、末尾追加のコストは償却`O(1)`と評価されるわけです。

ただしこの評価は「どの1回を切り取っても絶対にO(1)で終わる」という保証を意味するものではありません。
ミリ秒単位の応答遅延が致命傷となるリアルタイム制御システムでは、極大のメモリコピーが発生する最悪実行時間への配慮も不可欠です。

### 10 末尾への追加と途中への挿入

動的配列の容量拡張コストを償却したとしても、配列の途中位置へ要素を挿入する際に生じる物理的なデータ移動コストは依然として残ります。
末尾への追加であれば空き枠に即座に配置できますが、中間位置への割り込みではそうはいきません。

特定の位置に要素を割り込ませるには、その位置以降に並んでいるすべての要素を1マスずつ後方へ退避させる必要があります。

```text
[A][B][C][D]
位置1へXを挿入
[A][X][B][C][D]
       ↑ B,C,Dを移動
```

この要素シフト操作に伴い、任意位置への挿入の計算量は最悪ケースで`O(n)`に達します。
要素の削除操作においても、空いた隙間を詰めてインデックスの連続性を維持するために後続要素を前方へシフトさせる同等の移動コストが発生するわけです。

## 範囲と、行や列の配置を確かめる

### 11 範囲外アクセス

要素数が3個である配列に対して、誤って存在しない添字を指定して`array[3]`を読み出そうとする操作を範囲外アクセスと呼びます。

境界外への不当なアクセスが発生した際の振る舞いは、実行環境や言語処理系によって次のような違いが生じるわけです。

- 明示的な例外やエラーを送出して安全に処理を中断する。
- 処理系による保証のない未定義動作（undefined behavior）に陥る。
- 隣接する無関係なメモリアドレスを不正に読み書きしてしまう。

境界検査が省略された低水準な実行環境では、機密情報の漏洩やメモリデータの破壊、果ては不正侵入攻撃の脆弱性へと直結する危険に警戒が必要です。

### 12 多次元配列

一次元の列としてデータを並べるだけでなく、縦の行と横の列で構成される二次元テーブルを表現するには多次元配列を用います。

```text
matrix = [
  [1,2,3],
  [4,5,6]
]
```

```text
matrix[0][0]=1
matrix[1][2]=6
```

添字を指定する際は、第1添字が行番号、第2添字が列番号を表しているルールを厳格に守り、両者を取り違えないよう注意が必要です。

### 13 行優先と列優先

数学的な行列として表現された二次元配列も、コンピュータの物理メモリ上では連続した一本の平坦なアドレス空間へと直列化して格納されます。

#### 行優先

第1行の全要素を先頭から順にメモリへ配置し、その直後に第2行の要素群を続けて並べていく方式です。

```text
1,2,3,4,5,6
```


#### 列優先

第1列の全要素を縦方向に優先して並べ、その直後に第2列の要素群を配置していく方式です。

```text
1,4,2,5,3,6
```

プログラムの反復ループをメモリ上の物理配置と同じ順序で走査させると、CPUキャッシュのヒット率が向上して処理性能が大幅に高まる場合があります。

### 14 二次元配列のアドレス計算

行優先配置を採用し、行列の列数を`C`、1要素あたりのバイト数を`S`、先頭メモリアドレスを`B`と置きます。
このとき、0始まりの添字`[r][c]`が配置されているメモリアドレスは、次の計算式によって導出可能です。

```text
アドレス = B + (r×C+c)×S
```

現在位置の前方には完全に埋まった先行行が`r`行分存在し、各行に`C`個の要素が並んでいるため、行スキップ分として`r×C`個の要素が存在します。
さらに当該行の先頭から目的要素の直前までに`c`個の先行要素が存在するため、両者を合算してオフセットを計算する仕組みです。

### 15 不規則な二次元配列

各行が保持する要素数が不均一であり、行ごとに異なる長さを備えた構造をジャグ配列（不規則配列）と呼びます。

```text
[
 [1,2],
 [3,4,5,6],
 [7]
]
```

この構造は物理的な長方形の単一連続領域に限定されず、各行の実体を参照するポインタの配列として構成される場合が一般的です。
そのため、行インデックスごとに要素長が異なる前提に立ち、添字の境界検査を個別に行わなければなりません。

## コピーした範囲と、共有する対象

### 16 配列のコピー

配列変数の代入や複製操作を扱う際は、メモリ上で何を複製し何を共有しているのかを厳格に見極める必要があります。
配列の要素がオブジェクトへの参照である場合、外側の配列コンテナだけを新しく複製しても、内部の要素実体は新旧で共有されたままです。

代入文`b = a`を実行した際の挙動は、言語仕様によって二通りに分かれます。

```text
b = a
```

配列データ全体を新しいメモリ領域へ丸ごと複製する言語もあれば、同一の配列実体を指し示す参照ポインタのみを複製する言語も存在します。

#### 浅いコピー

最外層のコンテナ配列だけを新しく複製し、内部に含まれるオブジェクトの参照先は元のまま共有する方式です。

#### 深いコピー

配列の入れ子関係を再帰的に走査し、内部の実体オブジェクトに至るまですべて独立に新規複製する方式です。

オブジェクトグラフの中に循環参照が存在する場合や、意図して共有すべき状態を持つ設計、極めて巨大なデータ構造では、無計画な深いコピーはメモリ消費や処理性能の面で深刻な問題を引き起こしかねません。

### 17 スライス

既存の配列の一部分を切り出して部分配列として表現する機構がスライスです。

たとえば次の記法により、添字2、3、4の3要素を切り出し、末尾の境界値5を含まない半開区間として定義する言語処理系が多く見られます。

```text
a[2:5]
```

「開始位置を含み、終了位置を含まない」という半開区間の設計を採用すると、切り出される要素数が`終了 - 開始`という単純な引き算で求まるため、境界計算のバグを防ぎやすい点が大きな利点です。

```text
開始を含む、終了を含まない
要素数 = 終了 - 開始
```

切り出されたスライスが独立した新規メモリコピーなのか、それとも元配列の同一領域を覗き見る軽量なビュー（窓）なのかは、言語の仕様によって規定が異なります。

## 文字列の操作と、数える単位

### 18 文字列は文字の並び

文字列データは、内部的には文字コードの並びを格納した一種の配列構造として実現されているデータ形式です。

```text
text = "ABC"
```

文字列を扱うプログラムでは、長さの取得、特定位置の文字抽出、部分文字列の切り出し、パターン検索、連結、そしてトークン分割といった操作を日常的に実行します。

### 19 文字列の不変性

多くの現代的なプログラミング言語では、一度メモリ上に生成された文字列の内容を後から直接書き換えることができない「不変オブジェクト（イミュータブル）」としての設計が標準的です。

たとえば次の文字列結合のコード例では、既存の`"A"`という文字列領域が書き換えられるわけではありません。
新しく`"AB"`という独立した文字列インスタンスがメモリ上に新設され、変数`s`の参照先がそちらへ付け替えられます。

```text
s = "A"
s = s + "B"
```

ループ処理の中で単純な`+`演算子を用いて文字列を1文字ずつ反復連結していくと、周回のたびに毎回メモリ確保と文字列全コピーが繰り返され、全体の計算量が`O(n²)`に爆発する危険を伴います。
したがって大量の文字列結合を高速に処理する際は、文字列ビルダや配列バッファに一度要素を集約し、最後に一括結合する実装が定石です。

### 20 文字列の長さは何を数えるか

ディスプレイの画面上に文字が5つ表示されているからといって、プログラム上の文字列長が数値の5になるとは限りません。
文字列の長さを問い合わせた際、バイト数、符号単位数、コードポイント数、人間が見た文字数のどれを基準にして数えているかによって戻り値が劇的に変動します。

英数字の`"A"`であれば1文字1バイトで単純ですが、多言語の絵文字や結合文字列を扱う文脈ではその前提が通用しなくなるわけです。

処理系が返す「文字列長」が次のどの単位をカウントしているのかを常に意識しておくことが大切です。

- 物理的なメモリ使用量を示すバイト数。
- UTF-16における2バイト単位の符号単位数。
- Unicode体系における抽象的なコードポイント数。
- 人間が視覚的に1文字と認識する書記素クラスタ（grapheme cluster）数。

UIフォームの入力文字数制限を単純なバイト長で検証してしまうと、日本語や多言語を扱う利用者だけが不当に短い文字数で入力制限に引っかかる不利益を被りかねません。
ネットワーク通信の帯域計算にはバイト長を用い、画面上の入力制限には書記素クラスタ数を用いるなど、目的に応じて基準を使い分ける配慮が求められます。

### 21 終端文字を持つ文字列

伝統的なC言語などでは、文字列の終端を数値0の値を持つNUL文字（` `）によって明示するメモリ表現が使われます。

```text
'A' 'B' 'C' NUL
```

この方式において文字列の長さを測定するには、メモリの先頭からNUL文字が出現するまで1バイトずつ走査しなければなりません。
文字列の途中にNUL文字そのものを含めることができず、終端文字の配置を失念するとメモリ境界を越えて暴走する危険を孕んでいます。
対照的に近年の言語では、文字列の長さ情報をデータ本体とは別にヘッダ領域で保持する安全な方式が主流です。

### 22 文字列比較

文字列同士の比較処理においても、単なるコードポイントの大小比較、言語文化に即した辞書順ソート、英字の大文字小文字の同一視、正規化処理の有無など、適用される規則が多岐にわたります。

たとえば次の比較を数値比較と異なり文字列の辞書順として評価した場合、先頭文字`"1"`が文字`"2"`よりもコードポイント上で小さいため、式全体が真と判定されてしまいます。

```text
"10" < "2"
```

数値としての10と2を比較した結果であれば偽となるはずです。
数値を表現した文字列を比較したい場合は、入力フォーマットを検証した上で正しく数値型へキャストしてから比較演算を行わなければなりません。

### 23 文字列入力の検証

ユーザーや外部システムから受け取る文字列データには、設計者の想定を超える多様なノイズが含まれ得ます。

空白文字のみの入力、前後に混入した不要なスペース、想定外の改行コード、異なるUnicode正規化形式、極端に長大なテキスト、制御文字、あるいは見た目が酷似した同形異字（ホモグラフ）などがその代表例です。

これらの入力に対して安易に一律の削除や自動変換を施してしまうと、人名やパスワードが持つ固有の文字情報を誤って破壊してしまうリスクが生じます。
入力項目ごとに受け入れ規則を厳密に定義し、生の入力値と正規化後の値を適切に分離して保持する設計が肝要です。

### 24 配列を選ぶときの問い

冒頭で提示した点数の配列でも、添字を用いた任意アクセスの計算量は瞬時の`O(1)`でしたが、平均値を算出するには全件走査の`O(n)`が必要でした。
要素の挿入や配列の複製を伴う設計では、移動を強いられるデータ範囲と参照共有の範囲まで正確に予測した上でデータ構造を選定します。
