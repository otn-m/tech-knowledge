# 第3章 第5話 CPU性能とパイプライン

「3GHzのクロック周波数を持つCPUだから高速である」とは一概に言い切れません。
周波数が高い製品を単純に選べばよいように思えるかもしれません。
しかし、1命令の処理に何クロックを要するか、同一のタスクに何命令を消費するか、主記憶の応答待ちがどれほど発生するかによって、実際の処理性能の順位は容易に逆転します。

プロセッサの処理時間は、次の数式へと体系的に分解できる形です。

```text
CPU実行時間
= 命令数 × 1命令当たり平均クロック数 ÷ 1秒当たりクロック数
```

動作周波数は、性能決定式のわずか一要素にすぎないわけです。
計算式の各項の単位を厳密に追跡すれば、どのボトルネックを改善すべきか、そしてどの待ち時間がプロセッサ計算式の外部に存在するのかを明快に見分けられます。

## 周期と命令数から実行時間を求める

### 1 クロック

CPU内部に配置された無数の同期論理回路は、一定間隔で刻まれる電気信号の立ち上がりや立ち下がりに同期して状態を遷移させます。
この同期用の周期的なタイミング信号を**クロック**と呼ぶ形です。

```text
高 ┌─┐ ┌─┐ ┌─┐
   │ │ │ │ │ │
低 ┘ └─┘ └─┘ └─
    1   2   3   サイクル
```

信号が0から1へ立ち上がり、再び0を経て次の立ち上がりに至るまでの1往復の区間をクロックサイクルと定義します。

### 2 周波数

このクロック信号が1秒間に何回繰り返されるかを示す物理量が**周波数**であり、その単位にはHz（ヘルツ）を用いるわけです。
1Hzは1秒間に1回、1kHzは1,000回、1MHzは100万回、1GHzは10億回の振動を表します。
動作クロックが3GHzであれば、プロセッサは1秒間に30億回ものサイクルを規則正しく刻んでいる形です。

### 3 サイクルタイム

クロック周波数の逆数を計算すると、1クロックの刻みにかかる極小の所要時間が導き出されます。
この1サイクル当たりの所要時間を**サイクルタイム**（クロック周期）と呼ぶ形です。

```text
サイクルタイム = 1 ÷ クロック周波数
```

動作周波数が1GHzのプロセッサであれば、計算は次のようになります。

```text
1 ÷ 1,000,000,000秒
= 1ナノ秒
```

ナノ秒（ns）は10億分の1秒に相当する時間の単位に他なりません。
動作周波数が2GHzであればサイクルタイムは0.5ns、4GHzであれば0.25nsへと短縮されます。
周波数が2倍になれば、1サイクルの所要時間は正確に半分へと圧縮される理屈です。

### 4 CPI

1サイクルの所要時間が判明したとしても、それだけで直ちに1つの命令の実行時間が確定するわけではありません。
命令を1つ実行するために平均して何サイクルのクロックが必要となるかを示す指標が、**CPI**（Cycles Per Instruction）です。

```text
CPI = 総クロック数 ÷ 実行命令数
```

例えば100個の命令列を実行するのに250クロックを要したとすれば、その区間の平均CPIは2.5と算出されます。
多数の命令を平均化した統計値であるため、一般にCPIの値は小数を含む実数となる形です。
命令の種別、パイプラインの停止頻度、キャッシュミスの発生率などによって、実効CPIの値は大きく変動します。

### 5 CPU実行時間の式

1命令の実行に要する平均クロック数にプログラム全体の命令総数を乗じ、それを1秒間に進むクロック周波数で除算すれば、CPUの実行時間が算出できます。
プログラムの命令数を$I$、平均CPIを$C$、クロック周波数を$f$として定義してみましょう。

```text
必要クロック数 = I × C
一クロック時間 = 1/f

実行時間 = I × C × 1/f
         = I × C ÷ f
```

数式の単位についても確認しておく必要があります。

```text
命令 × クロック/命令 ÷ クロック/秒
= 秒
```

命令とクロックの単位が約分によって相殺され、最終的に所要時間である「秒」だけが美しく導き出される形です。

### 6 計算例

命令総数が6億命令、平均CPIが1.5、クロック周波数が3GHzであるプログラムの処理時間を計算してみます。

```text
総クロック数 = 6億 × 1.5 = 9億
実行時間 = 9億 ÷ 30億/秒 = 0.3秒
```

仮に同一のクロック周波数であっても、命令の構成が悪化してCPIが2.0に跳ね上がれば、所要時間は0.4秒へと悪化してしまう形です。
逆にコンパイラの最適化によって命令総数を4億命令に削減できれば、実行時間は0.2秒へと短縮されます。
この計算からも、プロセッサの処理速度が周波数の高低だけで決まるものではない事実が浮き彫りとなるわけです。
なお、この公式が算出するのは、一定のCPIと周波数を仮定した純粋なプロセッサ計算処理時間にとどまります。
ディスク入出力やネットワーク通信の待機時間を含むシステム経過時間とは明確に区別し、省電力機能で周波数が動的に変動する環境では区間ごとの積分計算を行う配慮が欠かせません。

## 実行する命令の内容を計算へ入れる

### 7 命令ミックス

実際のプログラムにおいて平均CPIを精度高く算出するためには、各命令が必要とする個別サイクル数に加え、各命令の出現頻度を考慮しなければなりません。
現実のワークロードにおいて各命令種別が実行全体に占める出現比率を、命令ミックスと呼びます。

| 命令種類 | 割合 | CPI |
|---|---:|---:|
| 整数演算 | 50% | 1 |
| 主記憶アクセス | 30% | 3 |
| 分岐 | 20% | 2 |

全体の平均CPIは、出現確率を重みとして掛け合わせる加重平均によって導き出される形です。

```text
0.5×1 + 0.3×3 + 0.2×2
= 0.5 + 0.9 + 0.4
= 1.8
```

出現比率を無視して単純に平均サイクル数を計算してしまうと、プログラムの実態とかけ離れた誤った性能評価を招いてしまいます。

## 性能指標が測る対象を区別する

### 8 MIPS

純粋な所要時間の測定とは別に、1秒間に実行可能な命令数をベースとしてプロセッサの処理能力を表す指標も存在します。
1秒間に何百万回の命令を実行できるかを表す指標が**MIPS**（Million Instructions Per Second）です。

```text
MIPS = 1秒当たり命令数 ÷ 1,000,000
```

クロック周波数が3GHz、平均CPIが1.5の環境であれば、計算は次のようになります。

```text
1秒当たり命令数 = 3,000,000,000 ÷ 1.5
                 = 2,000,000,000
MIPS = 2,000
```

### 9 MIPS比較の落とし穴

MIPSの数値は直感的で分かりやすい指標ですが、異なるアーキテクチャ間での安易な比較には落とし穴が潜んでいる点に注意しなければなりません。
プロセッサの命令セットが異なれば、1つの命令が内部で遂行する仕事量そのものが根本から異なるためです。
複雑な処理を1命令で完結させるアーキテクチャAと、単純な命令を3つ連ねて同一処理を実現するアーキテクチャBが存在する場合、BのほうがMIPS値で高く見えても実際の処理完了時間は遅いという逆転現象が起こり得ます。
そのため、同一のソースコード、同一のコンパイラ最適化、同一のISAという厳格な比較条件を揃えたうえで評価を下す姿勢が欠かせません。

### 10 FLOPS

整数命令を中心としたMIPSに対し、科学技術計算の分野では浮動小数点演算の処理速度を直接測定する指標が多用されます。
1秒間に実行可能な浮動小数点演算の回数を示す性能指標が**FLOPS**（Floating-point Operations Per Second）です。

- MFLOPSは、毎秒100万回の浮動小数点演算能力を示します。
- GFLOPSは、毎秒10億回の浮動小数点演算能力を示します。
- TFLOPSは、毎秒1兆回の浮動小数点演算能力を示します。

スーパーコンピュータのランキングやGPU、AIアクセラレータの演算性能を格付けする場面で主役となる指標に他なりません。
1つのベクトル命令が8要素の積和演算を一括実行する場合、乗算8回と加算8回の計16回の演算としてカウントする流儀が標準的です。
公称スペックとしての理論ピーク性能と、実際のアプリケーションを走行させて得られる実効性能との間には、メモリアクセス待ちや制御の分岐によって大きな乖離が生じます。

## 一件の時間と単位時間の処理量を分ける

### 11 レイテンシとスループット

処理性能を議論するうえでは、1件の処理を開始してから完了するまでの応答時間を表すレイテンシと、単位時間あたりに処理できる総件数を表すスループットを厳密に区別する視点が欠かせません。
レイテンシを短縮することと、スループットを拡大することは、工学的には全く別次元の最適化アプローチです。
例えば1回の洗濯に60分を要する洗濯機がある場合、1回の処理レイテンシは60分となります。
その洗濯機を10台並べて同時に稼働させれば、1着の服を洗い終える時間は60分のままであっても、1時間あたりに処理できる洗濯物の総スループットは10倍に跳ね上がる形です。
CPUの高速化技術を学ぶ際にも、この2つの評価軸を明確に意識して読み解く姿勢が求められます。

### 12 パイプライン

実行時間の計算式においてCPIを極限まで低減できれば、動作周波数や命令数を変えることなく処理速度を大幅に引き上げられる形です。
そこで、先行する命令が完全に終了するのを直列に待つ従来構造を脱却し、複数の命令における異なる処理ステージを並行して重ね合わせる技術が開発されました。
命令の処理工程を複数の独立したステージに分割し、ベルトコンベアのように異なる命令を並行して流し込む仕組みが**命令パイプライン**です。
標準的な5段パイプラインの構成を見てみましょう。

```text
IF  命令取出し
ID  命令解読
EX  演算・アドレス計算
MEM 主記憶アクセス
WB  結果書戻し
```

## 命令の異なる段階を重ねる

### 13 パイプラインなし

パイプライン機構を持たない逐次実行モデルでは、先行命令が5つのステージをすべて完了するまで後続命令は待機を強いられます。

```text
命令1: IF ID EX MEM WB
命令2:                IF ID EX MEM WB
命令3:                               IF ID EX MEM WB
```

3つの命令を処理するために、都合15ステージ分のクロックサイクルを直列に消費してしまう形です。

### 14 パイプラインあり

これに対し、各ステージを担うハードウェア回路が独立して動作できるパイプライン構成では、異なる命令の異なるステージを同時に駆動します。

```text
時刻     1  2  3   4   5   6   7
命令1   IF ID EX MEM  WB
命令2      IF ID  EX MEM  WB
命令3         IF  ID  EX MEM  WB
```

最初の命令こそ完了までに5サイクルを要しますが、ひとたびパイプラインが充填された後は、毎サイクルごとに1命令ずつが次々と完了していく形です。

### 15 理想パイプラインのサイクル数

パイプラインの段数を$k$、実行する命令の総数を$n$と置いた場合、理想的な条件下での所要クロックサイクル数は次の計算式で求まります。

```text
k + n - 1
```

最初の1命令が$k$段のパイプラインを満たすまでに$k$サイクルを要し、残る$n-1$個の命令が毎サイクル1つずつ完了していくためです。
5段パイプラインで100命令を処理する場合、所要サイクル数は`5 + 100 - 1 = 104`サイクルまで大幅に圧縮されます。
非パイプライン構成で500サイクルを要していた処理が、ほぼ1/5のサイクル数で完了する計算に他なりません。

### 16 パイプラインは一命令を5倍速くしない

ただし、パイプライン化によって1命令あたりのレイテンシ自体が5倍速くなるわけではない点には注意が必要です。
向上するのはあくまで単位時間あたりの処理完了数、すなわちスループットに集中します。
さらに現実のハードウェアでは、ステージ間のレジスタ伝搬遅延、後続処理への依存関係、分岐の発生、メモリアクセスの滞留などが重なり、理想的な理論値そのままのスループットを維持することは困難です。

## 重ねた処理が止まる原因を追う

### 17 パイプラインハザード

ステージを重ね合わせる理想論から一歩踏み込み、パイプラインの円滑な進行を阻害する物理的な要因をいかに解消するかが実効性能を左右します。
パイプラインの流れが乱れ、後続命令を予定のクロックで前進させられなくなる障害を**パイプラインハザード**と呼ぶ形です。
ハザードの発生要因は、主に次の3種類に大別されます。

1. 構造ハザード
2. データハザード
3. 制御ハザード

### 18 構造ハザード

同一のクロックサイクルにおいて、異なるステージが同一の物理回路やメモリポートを同時に利用しようとして競合を起こす現象が構造ハザードです。
例えば、命令取出しステージ（IF）とデータアクセスステージ（MEM）が、単一ポートの主記憶バスを取り合ってしまうケースが該当します。
命令用とデータ用でキャッシュメモリを物理的に分離するハーバード構造の導入や、ポートの多重化によって衝突を回避する設計が一般的です。
回避しきれない競合に対しては、後続ステージに何もしない空きサイクル（ストール／バブル）を意図的に挿入して待機させます。

### 19 データハザード

使用するハードウェア資源が独立していても、先行命令が書き出す計算結果を後続命令が入力データとして利用する場合、値の確定を待たなければなりません。
前の命令の演算結果がまだレジスタに書き戻されていないタイミングで後続命令がその値を参照しようとして発生する衝突が、データハザードです。

```text
命令1: R1 = R2 + R3
命令2: R4 = R1 + R5
```

命令2の実行にはR1の計算完了が不可欠となります。

#### 19.1 フォワーディング

このデータ依存を解決する最も強力なハードウェア手法がフォワーディング（バイパス）です。
先行命令の演算結果がALUから出力された瞬間に、レジスタへの書き戻しを待たず、内部配線を通じて後続命令のALU入力端子へ直接バイパス供給します。

#### 19.2 ストール

フォワーディングを用いても解消できないメモリアクセス待ちなどに対しては、インターロック回路によって後続命令を安全にストールさせる形です。

#### 19.3 命令スケジューリング

さらに、コンパイラやCPUが命令の実行順序を並べ替え、依存関係のない無関係な命令を間に挟んで待ち時間を埋める命令スケジューリングも多用されます。
先行の書込みを後続が読むRAW（Read After Write）依存の処理こそが、パイプライン設計における最大の焦点に他なりません。

### 20 制御ハザード

演算データの準備状況とは別に、条件分岐命令によって次にフェッチすべき命令のアドレス自体が確定しない事態も発生します。
条件分岐の判定結果が確定するまで、どの番地から命令をフェッチすべきかが定まらない障害が制御ハザードです。

```text
もしR1==0なら番地500へ
そうでなければ次へ
```

#### 20.1 分岐予測

分岐の成立・不成立を何の手立てもなく待っていてはパイプラインが停止してしまうため、過去の実行履歴に基づいてジャンプ先をあらかじめ予測して先読みフェッチを行う分岐予測が導入されています。
予測が的中していればパイプラインを一切淀ませることなく高速処理を維持できる形です。

#### 20.2 予測失敗

しかし予測が外れた場合には、誤った経路で途中まで実行を進めていた命令群をすべて破棄し、正しい分岐先から命令をフェッチし直すパイプラインフラッシュの代償を払わなければなりません。
パイプラインの段数が深くなればなるほど、予測失敗時に破棄される無駄な処理量とペナルティサイクル数は増大します。

#### 20.3 遅延分岐

一部のRISCプロセッサでは、分岐命令の直後にあるスロットの命令を分岐結果に関わらず必ず実行する遅延分岐のアーキテクチャも採用されました。

## 命令の重ね方と発行数を増やす

### 21 スーパーパイプライン

パイプラインの各ステージをさらに微細に分割し、1サイクルの時間を極限まで縮めて動作周波数を跳ね上げる手法をスーパーパイプラインと呼びます。
ステージ数を深く設計するほど周波数を引き上げやすい反面、段間ラッチ回路のオーバーヘッドや分岐予測失敗時の損失が跳ね上がるトレードオフを抱える形です。

### 22 スーパースカラ

これに対し、パイプラインの段数を深くするアプローチと並び、同一のクロックサイクル内に複数の命令を並行してフェッチ・実行する方式が**スーパースカラ**です。

```text
サイクル1: 命令A→整数演算器、命令B→ロードユニット
```

プロセッサ内部のデコード回路が命令間の依存関係を実行時に動的に解析し、同時に利用可能な演算ユニットへと並列に命令をディスパッチします。

### 23 VLIW

一方、実行時のハードウェアで依存関係を調べる代わりに、コンパイラが静的解析によって並列実行可能な演算群を1つの超長命令にパックする設計がVLIW（Very Long Instruction Word）です。
CPU側のスケジューリング論理を大幅に簡素化して消費電力を抑えられる反面、コンパイラの最適化能力への依存度が極めて高く、世代を超えたオブジェクトコードの互換性維持に難点を残します。

### 24 ハイパースカラ

学術書や製品資料によっては、極めて多数の命令を同時にデコード・発行する超並列スーパースカラ設計をハイパースカラと称する事例も存在します。
明確な業界標準の定義が存在する用語というより、スーパースカラの並列規模をさらに押し広げた概念として理解しておくのが適切です。

## 待ちを避け、同じ演算をまとめる

### 25 アウトオブオーダ実行

プログラムに記述された命令順序に従うと依存関係でストールしてしまう場合であっても、後続にある独立した命令を前倒しで追い越して実行する方式を**アウトオブオーダ実行**と呼びます。

```text
1. 主記憶からR1を読む  ← 待機
2. R2=R1+1           ← 1に依存して待機
3. R5=R3+R4          ← 独立しているため先行実行可能
```

メモリ待ちで足止めされている命令を尻目に、後方の独立した計算を先回りして終わらせることで、プロセッサ内部の演算ユニットの稼働率を限界まで高める仕組みです。
もちろん、最終的なレジスタへの書き戻しや例外の処理は、元のプログラム順序と完全に一致するようリオーダバッファ（ROB）を用いて厳密に調停され、プログラムの論理的な整合性は完全に保証されます。

### 26 ベクトル処理

単一の命令で独立した複数データを並行処理する手法としては、ベクトル処理（SIMD）も極めて強力です。

```text
A[0..7] + B[0..7] → C[0..7]
```

音声や画像、ディープラーニングの行列演算において、単一の命令コードで数十個から数百個のデータ要素を一括演算する圧倒的なスループットを発揮します。
ただし、条件分岐が要素ごとに不規則に発生する処理では並列実行の効率が低下する点に留意が必要です。

## 用途に合わせて性能を測る

### 27 性能測定の原則

ここまで検証してきた多彩な指標やマイクロアーキテクチャの高速化技術は、実際に走らせるプログラムの性質やデータパターンによってその実効効果が大きく揺らぎます。
真の性能を客観的に評価するためには、次に掲げる測定の原則を厳格に順守しなければなりません。

1. 実際の業務形態に限りなく近い実測ワークロードで測定する。
2. 入力データの規模や構造の条件を同一に揃える。
3. 初回実行時のコールドスタートと、キャッシュが充填された定常状態を区別する。
4. 単純なCPU処理時間だけでなく、I/O待ちを含めた経過時間や消費電力を総合評価する。
5. 平均的なスループットだけでなく、最悪ケースのレイテンシや性能のばらつきを把握する。
6. 使用したコンパイラの最適化オプション、OSのカーネル版数、実行環境の諸元を克明に記録する。

単一のクロック周波数や公称MIPSの数値だけに惑わされることなく、多角的な指標を突き合わせてアーキテクチャの実力を見抜く眼養いが何より重要です。
