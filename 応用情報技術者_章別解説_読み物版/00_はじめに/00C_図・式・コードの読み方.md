# 第0部C 図・式・コードの読み方――記号の集まりに見えなくする

ITの教科書や試験問題を開くと、至るところに四角い箱、矢印、数式、そしてプログラムのコードが現れます。
初めはそれらが無機質な記号の羅列に見えて、どこから目を向ければよいか途方に暮れがちです。
しかも紛らわしいことに、同じ「矢印」であっても、データの流れる向き、処理の順番、親子の上下関係など図ごとに異なる役割を担います。
数式の「`=`」は左右の釣り合いを示すのに対し、プログラムの「`=`」は右の計算結果を左の変数に放り込む操作を表す仕組みです。

記号の形が同じだからといって、意味まで共通しているとは限りません。
図の種類や文脈を確かめ、その記号が何の対象、どの向き、どんな変化を表しているかを正しく見極める姿勢が大切です。
視線の動かし方と読み解きのルールさえ身につければ、複雑に見える図や式やコードも頭の中で生き生きと動き出します。

## 図に描かれた情報を読み分ける

### 1 図は何かを省略した模型

図は、現実のすべてを写真のようにそのまま写し取った表現ではありません。
観光用の地図が必要な道路や駅を選び取って示すように、ITの図も特定の目的に必要な情報だけを抜き出す設計です。

たとえば、ブラウザとWebサーバの通信は次のように描かれます。

```text
利用者のブラウザ ──要求──→ Webサーバ
利用者のブラウザ ←─応答──── Webサーバ
```

この図から読み取るべき対象は、「要求と応答がどちらの向きに進むのか」というやり取りの順序と方向です。
コンピュータの物理的な大きさや形、ケーブルの長さ、通信にかかる秒数はあらかじめ省略されています。
また、ブラウザが左側に描かれているからといって、地理的な東西関係を表しているわけでもありません。

図を読むときは、まず次の2点を意識する方針が有効です。

1. 何を知るための図か（目的）
2. 現実の何をあえて省略しているか（前提）

この2つの視点を保つだけで、「描かれていない勝手な情報」を読み取って誤解する危険を劇的に減らせます。

### 2 箱、線、矢印

ITの図で最も頻繁に登場する基本パーツが、箱、線、矢印の3要素です。
どれも単純な図形ですが、その図の中で何を指しているのかは、添えられた名前や解説文によって決まります。

#### 箱

四角い箱は、ハードウェア、ソフトウェア、個々の処理ステップ、あるいはデータの集まりなどを表す記号です。

```text
┌──────────┐
│ 注文を受け付ける │  ← 処理を表す箱
└──────────┘
```

この箱であれば、中に書かれた名前から「注文を受け付けるという処理のステップ」を表していると分かります。
箱の形だけから「これは機械だろうか、プログラムだろうか」と決めつけず、必ず中に書かれた名前と前後の文脈を確かめる姿勢が肝要です。

#### 線

線は、2つのもののあいだにある何らかの関係性を表現します。
物理的なケーブルの接続、電波で通信できる関係、あるいは組織やデータの上下関係など、その線が意味する関係性は図の種類によって異なる規則です。

#### 矢印

矢印は、向きを持った線として描かれます。
データの移動、処理が進む順番、命令を呼び出す向き、時間の経過などを表現する道具です。

```text
注文画面 ──注文内容──→ 注文処理
```

この矢印は、「注文画面から注文処理へ向けて、注文内容というデータが渡される」と読めます。
単に矢印の先端の向きを見るだけでなく、「何が」「どこから」「どこへ」向かっているのかを主語と目的語を補いながら追うことが大切です。

### 3 上下や左右は、図ごとに意味が違う

矢印と同じように、上下や左右といった配置が持つ意味も、図の種類ごとに大きく異なる仕様です。
一般的な文章のように「上から下へ」「左から右へ」時間が進む図が多いのは確かですが、すべての図がその共通ルールに従っているわけではありません。

次のような木の形をした図（ツリー構造）では、上が親、下が子という所属や分類の階層関係を表す構成です。

```text
学校
├─ 1年
│  ├─ A組
│  └─ B組
└─ 2年
   ├─ A組
   └─ B組
```

この図の上下を「時間の経過」として読んでしまうと、「1年生が終わってから2年生になる」というような誤読につながってしまいます。
一方、処理の実行スケジュールを表す次の図（ガントチャート）では、まさに横方向に沿って時間が進んでいく設計です。

```text
時刻 →  0    1    2    3    4
処理A    [────────]
処理B         [────────]
```

図の隅に軸の名前や**凡例**（はんれい。記号や色の意味を説明した枠）がある場合は、本文よりも先にそこへ目を向けます。
図が採用している座標のルールを最初に把握することが、正しい読解への一番の近道です。

### 4 表は行と列の交点を読む

一覧表の形式もよく使われますが、数字だけを拾い読みすると意味を取り違えてしまいます。
表では、横方向の並びを**行**（ぎょう）、縦方向の並びを**列**（れつ）と呼び、行の見出しと列の見出しが交差する位置（セル）でひとつの事実を表す構造です。

```text
商品     単価     個数
りんご   120円      3
みかん    80円      5
```

表の中に単に「`120円`」と書かれていても、それだけでは何の数値か分かりません。
列の見出しを見上げて「単価」であることを確かめ、次に行を横にたどって「りんご」であることを確認して初めて、完全な情報として成立する段取りです。

#### 空欄と「0」はまったく違う

表を読むときに極めて重要な視点として、「値が書かれていない空欄」と「0という数値」の明確な区別があります。

```text
欠席回数 0回      「欠席がゼロである」という事実が確認できている
欠席回数 （空欄）  まだ出欠を確認していないか、記録を忘れている
```

欠席回数が「0回」であれば、その生徒は皆勤であり、欠席がない事実が確実に確定している状態です。
しかし「空欄」の場合、単に調査が終わっていないのか、記録を付け忘れたのか、本当のところは判明しません。
第6章のデータベースで学ぶ「NULL（ヌル）」という概念も、まさにこの未確定な空欄を表すための重要な仕組みです。

## 数式を意味のある文として読む

### 5 数式は左から機械的に読まない

数式も、図と同じように「意味を凝縮した文章」として読み解く姿勢が求められます。

```text
平均 = 合計 ÷ 個数
```

この式は、「平均という値は、全員の合計を個数で均等に割ったものと等しい」と述べる内容です。
記号を左から棒読みする姿勢を脱し、「どの量」に「どのような操作」をして釣り合わせているのかを読み解くことが大切です。
同じ関係を、アルファベットの文字を使って書き換えると次のようになります。

```text
m = s ÷ n
```

文字だけが並ぶと急に難しそうに見えますが、それぞれの文字の定義を横に並べてみれば、先ほどの日本語の式とまったく同じです。

```text
m: 平均（mean）
s: 合計（sum）
n: 個数（number）
```

#### 式を読む七つの手順

本編で新しい数式に出会ったときは、次の7つの問いを順に言葉で確かめてみてください。

1. 目的：何を求め、どの判断を下すための式なのか。
2. 記号の意味：それぞれの文字、添字、定数は、現実世界の何を指しているのか。
3. 単位：入力する数値の単位と、計算の結果として出てくる単位は何なのか。
4. 演算理由：なぜ足し、引き、掛け、割り、累乗しているのか。
5. 計算順：括弧、累乗、掛け算・割り算、足し算・引き算をどの順序で解くのか。
6. 結果の意味：求まった数値を現実の世界に戻すと、何を意味しているのか。
7. 適用条件：分母が0でない、前提が独立しているなど、どんな条件のもとで使える式なのか。

#### 七項目を埋める例――平均の計算

具体例として、3人の生徒のテストの点数`70点、80点、90点`から平均点を求める式`m = s ÷ n`を、この7つの手順に当てはめてみましょう。

1. 目的：3人のばらばらな点数を、集団を代表する1つの数値に要約する。
2. 記号の意味：`m`は平均点、`s`は3人の合計点、`n`は生徒の人数（3人）。
3. 単位：合計点`s`の単位は「点」、人数`n`の単位は「人」。`点 ÷ 人`で、結果の単位は「点/人（1人当たりの点数）」になる。
4. 演算理由：全員の点数をひとまとめに足し合わせ（`s`）、それを人数（`n`）で均等に山分けするため割り算を使う。
5. 計算順：まず足し算で合計`s = 70 + 80 + 90 = 240`を求め、その後に割り算`m = 240 ÷ 3 = 80`を行う。
6. 結果の意味：求まった「80点」は、全員の実力を均等にならしたときの基準点数。
7. 適用条件：人数`n`が1人以上であること（`n > 0`）。また、全員が同じ難易度の同じテストを受けていること。

このように7つの視点から分解すると、数式の背後にある論理がくっきりと見えてきます。

#### 添字と指数を見分ける

文字の周囲に小さく付く数字にも、決定的な役割の違いがあります。

```text
x₁  1番目のx（添字：名札）
x₂  2番目のx（添字：名札）
```

文字の右下に小さく書かれた数字は**添字**（そえじ、インデックス）と呼ばれ、仲間の中の順番や識別番号を表す「名札」です。
これは掛け算の指定ではありません。
一方、文字の右上に小さく書かれた数字は**指数**（累乗）を表す記法です。

```text
x² = x × x （指数：2回掛ける操作）
```

この2は名札とは異なり、「`x`を2個掛け合わせる」という計算の命令に当たります。
同じ小さな数字であっても、右下にあるのか右上にあるのかで意味が激変する構造です。

#### Σは「決められた範囲を全部足す」という合図

大量の数値を全部足し合わせる計算を短く表現するために、ギリシャ文字の大文字**Σ**（シグマ）を使います。
第1章以降の理論や統計の解説でも頻出の記号です。

```text
Σ xᵢ
```

これは、「指定された範囲の`xᵢ`をすべて順番に足し合わせてください」という命令を表す記法です。
たとえば、3つの測定値`x₁ = 3`、`x₂ = 5`、`x₃ = 7`がある場合、シグマの記号は足し算の式へとほどいて計算できます。

```text
Σ xᵢ = x₁ + x₂ + x₃
     = 3 + 5 + 7
     = 15
```

どこからどこまでの範囲を足すのかは、シグマの上下や前後の文脈に必ず明記される設計です。
記号の威圧感に惑わされず、「ただの足し算の省略形だ」と気楽に捉えてください。

## コードの実行と値の変化

### 6 コードは「機械に実行させる手順の表記」

数式が「量と量の釣り合い」を表すのに対し、プログラムのコードは「コンピュータに実行させる動作の手順」を時系列で表します。
人間が読み書きしやすいように一定の文法で手順を書き下した記述を、**コード**（またはソースコード）と呼ぶ約束です。

たとえば、「点数が60点以上なら合格、そうでなければ不合格」という判定の手順を見てみましょう。

```text
もし 点数 >= 60 なら
    「合格」と表示する
そうでなければ
    「不合格」と表示する
```

このような、特定のプログラミング言語の細かな文法に縛られず、処理の骨格を自然言語混じりで表した書き方が**擬似コード**です。
情報処理技術者試験の出題でも多用されるスタイルに当たります。

擬似コードを読むときは、頭の中で具体的な数値を代入し、1行ずつ指でたどりながら実行の道筋を追う操作が**トレース**です。
もし「点数 = 75」だった場合、処理は次のように進みます。

1. 「点数」という入れ物に75が入る。
2. 条件式`75 >= 60`を判定する。
3. 75は60以上なので、条件は「成立（真）」と判定される。
4. 「合格」と表示する行を実行する。
5. 「そうでなければ」のブロックは実行をスキップして終了する。

コードの上に2つの表示処理が書かれていても、両方が実行されるわけではない点に注意が必要です。
条件の判定結果によって、どちらか一方のルートだけが選ばれます。

#### 記号を一つずつ読む

プログラムのコードでは、日常会話や数学とは少し異なる意味で使われる記号が存在します。

| 記号 | よくある役割 | 注意点 |
|---|---|---|
| `=` | 代入（右の値を左へ入れる） | 数学の「等しい」とは意味が異なる言語が多い |
| `==` | 比較（左右が等しいか調べる） | 一致していれば「真」、異なれば「偽」になる |
| `!=` | 比較（左右が等しくないか調べる） | 不等号の一種（数学の≠と同じ） |
| `>` / `>=` | 大小比較（より大きい / 以上） | `>=`は境界値を含む |
| `()` | 計算順序の優先、関数の引数 | 先に計算する部分や、渡す材料を包む |
| `[]` | 配列の添字や要素の指定 | `データ[0]`のように番号で要素を取り出す |
| `"..."` | 文字列のリテラル | 囲まれた文字そのものを値として扱う |

特に、代入の「`=`」と比較の「`==`」の使い分けはプログラミングの基本です。

#### 変数の状態を表で追う

変数の値が書き換わっていく様子を、次のコードで確かめます。1から3までの整数を合計する処理です。

```text
合計 = 0
合計 = 合計 + 1
合計 = 合計 + 2
合計 = 合計 + 3
表示する(合計)
```

2行目の`合計 = 合計 + 1`という式を見てください。
もしこれが数学の等式なら、「両辺から合計を引くと 0 = 1 になってしまい、絶対に成り立たないおかしな式」に当たります。
しかし、プログラミングにおける「`=`」は等号にとどまらず**代入**です。
「右辺にある現在の合計値に1を足し算し、その計算結果を左辺の合計という入れ物に入れ直す」という更新操作を意味します。

1行進むごとに変数の値がどう変化するかを、表（トレース表）にして追ってみる段取りです。

| 実行した行 | 計算の内容 | 合計の新しい値 |
|---|---|---:|
| `合計 = 0` | 最初の初期値として0を入れる | 0 |
| `合計 = 合計 + 1` | いまの0に1を足す（0 + 1） | 1 |
| `合計 = 合計 + 2` | いまの1に2を足す（1 + 2） | 3 |
| `合計 = 合計 + 3` | いまの3に3を足す（3 + 3） | 6 |

最後に画面へ表示される値は「6」という結果です。
このように、1行実行されるたびに変数の中身が最新の値へと上書きされていく感覚を掴んでおくことが、アルゴリズムを読み解く大切な基礎になります。

### 7 SQLはデータベースへの依頼文

プログラムには、計算手順を上から下へと細かく指図する命令（手続き型）だけでなく、「欲しい結果の条件だけを伝えて、探し方は相手に任せる」という命令スタイル（宣言型）もあります。
第6章で詳しく学ぶ**SQL**（エスキューエル）は、データベースに問い合わせを行うための専用言語です。

```sql
SELECT name
FROM students
WHERE score >= 80;
```

この命令文は、英語の語順そのままに次のように読めます。

```text
SELECT name       name（氏名）という列を取り出してください
FROM students     students（学生名簿）という表から
WHERE score >= 80 score（点数）が80点以上の行だけに絞り込んで
```

全体としては、「学生名簿の表から、点数が80点以上の学生を探し出し、その氏名の一覧を返してください」というデータベースへの依頼文です。
SQLを読むときは、元の大きな表から「行がどう絞り込まれ」「どの列が抜き出されて」「どんな結果の一覧表になるか」をイメージしながら読み解きます。

## 同時処理と項目の関係を図で確かめる

### 8 時系列表は同時処理の問題を見つける

コンピュータの世界では、複数の処理が同時に並行して動く現象が日常茶飯事です。
しかし、文章の説明だけで「どちらが先にデータを読み、いつ書き換えたか」を把握しようとすると、頭の中が混乱してしまいます。
そこで役立つのが、縦軸に時間の経過を並べた**時系列表**（シーケンス表）です。

2人の利用者（処理Aと処理B）が、残り1個しかない同じ商品の在庫を同時に購入しようとした場面を例に取ります。

```text
時刻  処理A（利用者1）      処理B（利用者2）      データベースの在庫数
 1    在庫数（1個）を読む                           1
 2                          在庫数（1個）を読む     1
 3    在庫を0個に書き換える                         0 （購入完了！）
 4                          在庫を0個に書き換える   0 （購入完了！？）
```

最後の在庫数だけを見れば「0」になっているので、1個の商品が無事に売れて終わったように見えがちです。
しかし、時間を上から下へ順に追っていくと、深刻な不具合の発生がはっきりと判明します。
処理Aだけでなく処理Bもまた時刻2の時点で「まだ在庫が1個ある」と読み取ってしまい、2人とも購入手続きが完了してしまう二重販売事故につながるわけです。

時系列表を読むときは、次の4項目に沿って視線を動かします。

1. 時間がどの方向（通常は上から下）に進んでいるかを確認する。
2. 時刻を1行ずつ進めながら、それぞれの登場人物が何をしたかを追う。
3. 共有しているデータ（在庫数など）がどの瞬間に書き換わったかを見る。
4. すでに古くなってしまった過去のデータをもとに行動してしまった処理がないかを探す。

最終的な結果の数字だけでなく、「そこに至る手順の交錯」を追うことで、同時並行処理に潜む不具合を鮮やかにあぶり出せる構造です。

### 9 木構造とネットワーク図を混同しない

関係性を表す図を読むときは、線の形だけに惑わされず、「何と何が、どういうルールで結びついているのか」を確かめます。

たとえば、パソコンのフォルダ構造を表す図は**木構造**（ツリー構造）です。
すべての子フォルダは必ずたった1つの親フォルダにぶら下がっており、枝分かれは一方通行で、決して輪（ループ）を描いて元に戻ることはありません。

```text
親フォルダ
├─ 子フォルダA
└─ 子フォルダB
```

これに対して、道路網やインターネットの通信網を表す図は**ネットワーク構造**（グラフ構造）です。
1つの地点が複数の地点と網の目のようにつながっており、別ルートを通ってぐるりと一周して元の場所に戻ることもできます。

```text
A ── B
│ ╲  │
C ── D
```

どちらの図にも線と文字が並んでいますが、階層関係を表しているのか相互に行き来できる通信路を表しているのかによって、図の性質は根本から異なる設計です。
「親は1つだけか、複数あるか」「ループはあるか」という2つの基準を持っておけば、両者を簡単に見分けることができます。

## 記号の迷宮から抜け出すために

### 10 読めないときの戻り方

ブラウザとWebサーバの図では、矢印は要求と応答の向きでした。
数学のテストの式では「`=`」は左右の等しさを表し、プログラミングでは新しい値を入れ物へ上書きする代入を表していたはずです。
図、式、コードを読むときに最も大切なのは、記号の形を丸暗記するにとどまらず、「その場でその記号がどんな役割を任されているのか」を冷静に見定める姿勢にあります。

もし解説を読んでいて途中で意味が分からなくなったときは、次の7つのチェックリストに沿ってつまずきの原因を特定してみてください。

1. 未定義の言葉がないか：まだ意味を知らない専門用語をそのまま放置していないか。
2. 記号の定義があるか：矢印や文字の意味が、凡例や本文のどこかで説明されていないか。
3. 入力と出力は何か：その仕組みや式が「何を受け取って、何を吐き出すものなのか」が明確か。
4. 向きはどちらか：時間やデータが、上から下へ流れているのか、左から右へ流れているのか。
5. 1つ前の状態は何か：値が変わる直前、変数には何が入っていたのか。
6. 何が変わったのか：その1行の処理によって、どのデータがどう書き換わったのか。
7. 小さな具体例にできないか：文字や大きな数字を、手計算できる具体例に置き換えられないか。

図や式をどれほど長く眺めていても、記号の意味が自然に湧き出てくるわけではありません。
「矢印の意味が分からない」なら凡例や冒頭の説明へ戻るのが第一歩です。
「文字`n`の意味が分からない」なら変数の定義へと立ち戻ります。
「値がなぜ変わったか分からない」なら直前の行の変数表へ戻るのが定石です。
分からない最小のステップまで立ち戻り、足場を固め直す地道な作業を繰り返します。
その積み重ねこそが、無味乾燥に見える記号の集まりを確かな理解へと変える確実な道筋です。
