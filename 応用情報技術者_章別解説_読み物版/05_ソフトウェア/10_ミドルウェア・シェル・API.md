# 第5章・第10話　ミドルウェア・シェル・API――共通の仕事を一度だけ作る

通販アプリ、予約アプリ、会計アプリは目的が違っても、データ保存、通信、認証、ログ、取引管理など似た機能を必要とします。

すべてのアプリが一から作れば、時間が掛かり、異なる不具合を抱えます。OSとアプリの中間で、複数アプリへ共通機能を提供するソフトウェアが**ミドルウェア**です。

```text
業務アプリ
────────────
ミドルウェア
────────────
OS
────────────
ハードウェア
```

## 1 OSとの違い

OSはCPU、メモリ、装置、ファイルなど低い水準の資源を管理します。

ミドルウェアはOSの機能を使い、データベース、Web処理、メッセージ、取引など、アプリに近い共通機能を提供します。

境界は絶対ではなく、OSへ組み込まれる機能もあります。選択時は提供機能、性能、互換性、運用、費用、サポートを見ます。

## 2 DBMS

**DBMS**、Database Management Systemは、データベースを管理するミドルウェアです。

- データ構造を定義する。
- 検索・追加・更新・削除する。
- 複数処理の同時更新を制御する。
- 故障から回復する。
- 権限を管理する。
- 索引で検索を速める。

アプリは保存装置の物理番地を直接操作せず、SQLなどで「条件に合う注文を探す」と依頼します。詳しくは第6章で学びます。

## 3 Webサーバとアプリケーションサーバ

**Webサーバ**はHTTP要求を受け、静的ファイルを返し、動的処理へ要求を渡します。

**アプリケーションサーバ**は、業務アプリの実行環境、DB接続プール、セッション、トランザクション、認証などを提供します。

製品によって機能が重なり、同じプロセスで動く場合もあります。名称より、どの役割を持つかを確認します。

## 4 通信管理システム

通信接続、相手識別、プロトコル変換、再送、経路、セッションなどを管理し、アプリ間通信を支えるミドルウェアが**通信管理システム**です。

異なる機種・OS・データ形式のアプリをつなぐ**アプリケーションプログラム間連携ソフトウェア**もあります。

共通の通信基盤が止まると多数アプリへ影響するため、容量、冗長化、変更管理が重要です。

## 5 メッセージ指向ミドルウェア

送信側がメッセージをキューへ置き、受信側が後で取り出す仕組みです。

```text
注文受付 → [通知キュー] → メール送信
```

受信側が一時停止してもキューに保持し、送受信の速度差を吸収します。

ただし次を決めます。

- 一回だけか、少なくとも一回配送か。
- 重複時にどうするか。
- 順序を保証する範囲。
- 何回再試行するか。
- 永久失敗をどこへ隔離するか。
- キュー満杯時にどうするか。

## 6 TPモニター

多数の利用者から来る取引処理を管理するミドルウェアが**TPモニター**です。TPはTransaction Processingです。

- 要求受付と振分け。
- プロセス・スレッドの共有。
- DB接続の共有。
- トランザクションの開始・確定・取消。
- 負荷・障害監視。
- 複数資源の更新調整。

銀行、予約など大量オンライン取引で、アプリごとに資源を持つ無駄を減らし、一貫した制御を行います。

## 7 運用管理・開発支援ミドルウェア

監視、ジョブ、自動配備、ログ収集などを行う**運用管理ツール**も、共通基盤として使われます。

アプリ作成、試験、版管理などを助ける**ソフトウェア開発支援ツール**も広いミドルウェアの用語例へ含まれます。

## 8 シェル

利用者から文字の命令、**コマンド**を受け取り、解釈し、プログラム起動やOS機能呼出しを行うソフトウェアが**シェル**です。shellは殻で、カーネルという核を包む利用者との境界です。

```text
利用者 → シェル → OSカーネル
```

コマンドを解釈するため**コマンドインタプリタ**とも呼びます。

## 9 代表的なシェル

- **Bourne Shell**、B Shell――UNIX系の代表的な系統。公式用語表などでは、空白を入れずに **BShell** と書くこともあります。
- **C Shell**――C言語に似た構文を持つ系統。**CShell** と書くこともあります。
- **cmd.exe**――Windowsの代表的なコマンド処理系。

現代にはbash、zsh、PowerShellなどもあります。同じ名前のコマンドでも構文・機能が違う場合があります。

## 10 コマンドの基本構造

```text
command option argument
```

- commandはすること。
- optionは方法の変更。
- argumentは対象。

例えば「一覧を詳しく表示」「このファイルをコピー」のように読みます。空白、引用符、特殊文字の扱いはシェルごとに決まります。

## 11 標準入力・出力・エラー

多くのコマンドは三つの流れを持ちます。

- 標準入力――通常はキーボードなどから読む。
- 標準出力――通常の結果を画面などへ出す。
- 標準エラー出力――エラー・診断を別の流れへ出す。

出力をファイルへ向ける**リダイレクト**、一方の出力を次の入力へつなぐ**パイプ**で、小さなコマンドを組み合わせます。

```text
コマンドA | コマンドB
```

## 12 シェルスクリプト

複数コマンド、条件分岐、繰返しなどをファイルへ書き、自動実行するものが**シェルスクリプト**です。

バックアップ、ログ整理、配備などを自動化できます。入力の引用漏れ、途中失敗、二重実行、強い権限、秘密情報の表示へ注意します。

## 13 API

ソフトウェアから別ソフトウェアの機能を呼ぶための約束が**API**、Application Programming Interfaceです。

関数APIなら、名前、引数、戻り値、エラー、呼ぶ順序などを定めます。

```text
open(ファイル名, 読取モード) → 成功ならハンドル、失敗ならエラー
```

API仕様は、利用者向け画面ではなく、プログラム同士の契約書です。

## 14 Web API

ネットワーク越しにHTTPなどで呼び出すAPIが**Web API**です。

```text
GET /weather?city=Tokyo
→ 状態コード200とJSONの天気
```

URL、操作、入力形式、認証、応答形式、エラー、回数制限、版を仕様化します。遠隔通信なので、遅延、切断、重複、相手変更を扱います。

## 15 ライブラリ

再利用できるプログラム部品を整理して格納したものが**ライブラリ**です。

- **ソースライブラリ**――人が読めるソース部品。
- **オブジェクトライブラリ**――翻訳済み目的コード部品。
- **ロードライブラリ**――実行時に読み込める実行部品。
- **DLL**、Dynamic Link Library――動的に結合する共有ライブラリ。
- **クラスライブラリ**――オブジェクト指向のクラス群。

ライブラリは呼ばれた機能を提供し、通常はアプリ全体の流れを支配しません。

## 16 フレームワーク

アプリの標準構造、処理の流れ、拡張箇所を用意するクラス・ライブラリ群が**開発フレームワーク**です。

ライブラリではアプリが部品を呼ぶのに対し、フレームワークでは枠組みがアプリの書いた部品を呼ぶ、**制御の反転**がよくあります。

代表的な用語例はApache Struts、CakePHP、Spring Framework、Ruby on Railsです。製品名を暗記するだけでなく、標準構造と共通機能を再利用する目的を理解します。

## 17 コンポーネントウェア

明確なインタフェースを持つ交換・再利用可能なソフトウェア部品を**コンポーネント**と呼び、その部品を組み合わせて開発する考えが**コンポーネントウェア**です。

- Java Beans――Javaの部品規約。
- CORBA――異なる言語・機種の分散オブジェクトを呼ぶ仕組み。
- OSGi――Java部品の動的追加・版・依存関係を管理する仕組み。

部品化しても、インタフェース、版、依存、障害伝播、性能を管理します。

## 18 接続プール

DB接続の作成・認証には時間が掛かります。あらかじめ複数接続を作り、要求ごとに貸し借りするものが**接続プール**です。

作成費用を減らせますが、数が少なければ待ち、多すぎればDBを圧迫します。返却漏れ、切断済み接続の検査、最大待ちを管理します。

## 19 選択の観点

- 必要機能と標準対応。
- 性能と拡張性。
- 障害時の動作。
- 安全な更新とサポート期間。
- 既存アプリ・言語との互換性。
- 運用監視のしやすさ。
- ライセンスとTCO。
- 他製品へ移る難しさ。

高機能なミドルウェアは、設定・依存・障害点も増やします。必要な機能を明確にします。


## 応用情報技術者試験での扱われ方

- **典型設問:** 「OSとミドルウェアの役割を区別してください。」
- **条件語:** `ミドルウェア`を本文の定義と対応させます。
- **最初の着眼点:** 二つの語を、対象・目的・成立条件・失敗時の四列に置いて比べます。
- **途中の組立て・式:** 共通点を一つ、相違点を一つ示し、問題の条件へ合う側を選びます。 対象、目的、入力と出力、処理時点、成立条件、障害時を表にし、問題文で差が付く列を根拠にします。
- **典型誤答と理由:** 名称や長所だけで選ぶと、守る対象・処理時点・前提条件が違う方式を交換可能だと誤認します。

## 確認問題

1. OSとミドルウェアの役割を区別してください。
2. メッセージキューが送受信の速度差を吸収できる理由を答えてください。
3. TPモニターが共有・管理するものを三つ答えてください。
4. シェルを「殻」と呼ぶ位置関係を説明してください。
5. 標準出力と標準エラーを分ける利点を答えてください。
6. API仕様に含める項目を四つ答えてください。
7. ライブラリとフレームワークの制御の向きを比べてください。
8. 接続プールを大きくしすぎる問題を答えてください。
