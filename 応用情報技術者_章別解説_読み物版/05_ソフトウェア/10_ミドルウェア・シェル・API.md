# 第5章 第10話 ミドルウェア、シェル、API

通販アプリ、予約アプリ、会計アプリは目的が違っても、データ保存、通信、認証、ログ、取引管理など似た機能を必要とします。
すべてを一から作れば開発に時間がかかり、設計ごとに異なる不具合を抱え込みかねません。
OSとアプリの中間で、複数のアプリに共通機能を提供するソフトウェアが**ミドルウェア**です。
共通機能を任せれば自作するコード量は減るものの、アプリはその部品の障害や版、設定に依存する形となります。

```text
業務アプリ
────────────
ミドルウェア
────────────
OS
────────────
ハードウェア
```

## 共通の保存、通信、取引を任せる

### 1 OSとの違い

OSはCPUやメモリ、周辺入出力、ファイルといった低水準の計算資源を管理する役割を担います。
これに対してミドルウェアは、データベース、Web処理、メッセージ連携、取引処理など、業務アプリに近い共通機能を担うソフトウェアです。
両者の境界は固定されておらず、かつてミドルウェアと呼ばれた機能がOS標準へ組み込まれる例も珍しくありません。
採用にあたっては、提供機能だけでなく、処理性能、互換性、運用性、費用、保守サポート体制の比較検討が欠かせないわけです。

### 2 DBMS

通販アプリが注文を探す処理では、保存場所そのものの番地より、データの構造と検索方法の定義が欠かせません。
このデータベース管理を専門に受け持つミドルウェアが、**DBMS**（Database Management System）です。
データ構造の定義をはじめ、レコードの検索、追加、更新、削除を一括して実行します。
複数の処理が同時に走る際の排他制御や、障害発生時のデータ復旧、アクセス権限の管理もその守備範囲です。
索引用のインデックスによって検索速度を高める仕組みも備えています。
アプリ側はディスク上の物理番地を意識せず、SQL文などで「条件に合う注文を探す」と指示を出すだけで完結する設計です。
より詳細な構造と運用については、第6章で改めて体系的に取り上げます。

### 3 Webサーバとアプリケーションサーバ

**Webサーバ**はクライアントからのHTTP要求を受け付け、静的ファイルを返却しつつ、動的な処理要求を後段へ渡す役割を果たします。
一方のアプリケーションサーバは、業務ロジックの実行環境、DB接続プール、セッション管理、トランザクション制御、認証機能などを一手に引き受ける基盤です。
製品によっては両者の機能が一体化し、同一のプロセスで稼働する場合も少なくありません。
製品の名称だけに惑わされず、それぞれがどの役割を分担しているかを見極める姿勢が大切です。

### 4 通信管理システム

通信接続の確立、通信相手の識別、プロトコル変換、再送制御、伝送経路やセッションの管理を行い、アプリ間の通信を支えるミドルウェアを通信管理システムと呼びます。
異なる機種やOS、データ形式を採用したアプリ同士を結ぶアプリケーションプログラム間連携ソフトウェアも、この領域に含まれる仕組みです。
共通の通信基盤が停止すると接続する多数の業務に影響が及ぶため、回線容量の見積もり、冗長化の設計、変更管理の徹底が求められます。

### 5 メッセージ指向ミドルウェア

送信側が受信側の処理完了を待つ同期構成は単純ですが、受信側が停止した影響がそのまま送信側へ波及します。
これに対し、メッセージを一度キューへ預ければ送受信のタイミングを切り離せる反面、重複や順序、キューの滞留を自前で制御しなければなりません。
送信側がメッセージをキューへ格納し、受信側が都合のよい時点で取り出す非同期の仕組みをメッセージ指向ミドルウェアと総称します。

```text
注文受付 → [通知キュー] → メール送信
```

受信側が一時的に停止していてもデータはキューに保持され、処理速度の差を安全に吸収できる点が大きな特徴です。
キューを導入する際は、確実に1回だけ届けるのか、それとも少なくとも1回届ける配送保証にするのかを取り決めておく必要があります。
あわせて重複メッセージの排除手順、順序を保証する範囲、再試行の上限回数も明確に定めます。
処理に永久失敗したメッセージを隔離する退避場所や、キュー満杯時の受け入れ制御も事前に定めておくべき論点です。

### 6 TPモニター

多数の端末や利用者から届く取引処理を効率よく管理するミドルウェアを、TPモニターと呼びます。
名称のTPはTransaction Processingの略称です。
要求の受付と振り分けをはじめ、OSプロセスやスレッドの共有、データベース接続の共有などを集中制御します。
トランザクションの開始、確定、取り消しの管理はもちろん、処理負荷や障害の監視、複数資源をまたぐ更新調整もその職務です。
銀行の勘定系や座席予約といった大量のオンライン取引において、アプリごとに資源を抱え込む無駄を省き、システム全体で一貫した制御を実現します。

### 7 運用管理・開発支援ミドルウェア

システムの死活監視、定周期ジョブ、自動配備、ログ収集などを担う運用管理ツールも、システム全体を支える共通基盤として位置づけられます。
さらに、プログラムの作成、テスト、版管理を補助するソフトウェア開発支援ツールも、広義のミドルウェアの分類例に数えられる概念です。

## コマンドの入出力を組み合わせる

### 8 シェル

共通機能はサーバ側の常駐部品だけに存在するわけではありません。
利用者や運用スクリプトがOSの諸機能を組み合わせる窓口として、シェルが入出力の連携を仲介します。
利用者から文字列による命令、すなわちコマンドを受け取って解釈し、プログラムの起動やOS機能の呼び出しを行うソフトウェアが**シェル**です。
shellは殻を意味し、核となるOSカーネルを包み込んで外部の利用者と仲介する境界に例えられます。

```text
利用者 → シェル → OSカーネル
```

入力されたコマンドを順次解釈して実行する性質から、コマンドインタプリタとも呼ばれる存在です。

### 9 代表的なシェル

シェルの代表的な系統には、UNIX初期から受け継がれるBourne Shell（B Shell）と、C言語に似た構文を持つC Shellが存在します。
公式の用語表などでは空白を挟まず、BShellやCShellと表記される事例も少なくありません。
Windows環境における代表的な文字入力のコマンド処理系はcmd.exeです。
現代の開発や運用ではbashやzsh、PowerShellなども広く普及しています。
同じ名前のコマンドであっても、処理系によって利用できる構文や細かな動作仕様が異なる点には注意が必要です。

### 10 コマンドの基本構造

シェル上で入力するコマンド行では、実行する処理、動作の細かな指定、操作対象の3要素を分けて記述します。

```text
command option argument
```

commandが実行内容、optionが動作方法の指定、argumentが処理対象を指す構造です。
たとえば「一覧を詳細に表示する」「特定のファイルを指定場所へ複製する」といった関係として読み解けます。
空白文字の区切り方や引用符の使い方、ワイルドカードなどの特殊記号の解釈規則は、利用するシェル固有の文法規則に依存するわけです。

### 11 標準入力・出力・エラー

多くのコマンドは、入力、通常の結果出力、エラーや診断情報の出力という3系統のデータ経路を備えています。
標準入力は通常キーボードなどから読み込み、標準出力は正常な処理結果を画面などへ送出する経路です。
一方で標準エラー出力は、エラーメッセージや診断ログを通常結果と混ざらないよう独立して出力します。
出力をファイルへ書き換えるリダイレクトや、一方の出力を次のコマンドの入力へ直結するパイプを使えば、単機能の小さなコマンド同士を柔軟に連結できる仕組みです。

```text
コマンドA | コマンドB
```

### 12 シェルスクリプト

複数のコマンド群や条件分岐、繰り返し処理をあらかじめファイルへ記述し、一連の作業をまとめて自動実行する仕組みをシェルスクリプトと呼びます。
定期的なバックアップやログの整理、アプリケーションの配備作業などを再現性高く自動化できる点が大きな強みです。
作成時は引数の引用符による囲み漏れ、処理の途中失敗時の例外処理、同一スクリプトの多重実行、不要な管理者権限の行使、ログへの秘密情報の露出といった点に十分配慮しなければなりません。

## プログラムから共通機能を呼ぶ

### 13 API

コマンド同士を組み合わせる手法とは別に、プログラムコードの中から直接共通機能を呼び出すための境界面が求められます。
呼び出し規約を固定しておけば内部実装を後から交換しやすくなる反面、引数や戻り値、エラー発生時の取り決めを双方が厳密に守らなければなりません。
あるソフトウェアから別のソフトウェアが提供する機能を呼び出すための仕様や約束事を、**API**（Application Programming Interface）と呼びます。
関数呼び出しの形式であれば、関数名、引数の型と個数、戻り値の型、例外やエラーコード、関数を呼ぶ順序などが厳密に規定される規約です。

```text
open(ファイル名, 読取モード) → 成功ならハンドル、失敗ならエラー
```

APIの仕様書は、画面レイアウトとは異なり、プログラム同士が安全にやり取りするための契約書に他なりません。

### 14 Web API

ネットワークを経由し、HTTPなどのプロトコルを用いて遠隔から呼び出すAPIをWeb APIと呼びます。

```text
GET /weather?city=Tokyo
→ 状態コード200とJSONの天気
```

URLの構造、HTTPメソッドによる操作種別、リクエストパラメータの形式、認証認可の方式、レスポンスのデータ構造、HTTP状態コードとエラー形式、呼び出し頻度制限、APIのバージョン管理方針などを明確に仕様化しておく必要があります。
ネットワークを挟んだ通信である以上、通信遅延、接続遮断、要求の重複到達、相手先サーバの仕様変更といった分散環境特有の事象も考慮しなければなりません。

### 15 ライブラリ

APIを通じて呼び出される機能群は、再利用可能なソフトウェア部品として体系的に整理されます。
このように再利用可能なプログラム部品群を収集・管理したものが**ライブラリ**です。
開発者が閲覧・編集できるソースコードの形式でまとめたものをソースライブラリ、コンパイル済みの目的コードの形式で束ねたものをオブジェクトライブラリと呼び分けます。
実行時にメモリへ読み込んで即座に利用できる実行形式の部品集が、ロードライブラリです。
プログラムの実行時に動的結合される共有ライブラリはDLL（Dynamic Link Library）、オブジェクト指向言語のクラス群を束ねたものはクラスライブラリに分類されます。
一般にライブラリは呼び出された機能だけを実行して処理を返し、アプリケーション全体の制御の流れそのものを握ることはありません。

### 16 フレームワーク

アプリケーションの標準的な骨格、制御の流れ、拡張ポイントをあらかじめ用意したクラスやライブラリの集合体を、開発フレームワークと呼びます。
ライブラリではアプリ側が主体となって部品を呼び出すのに対し、フレームワークでは枠組み側がアプリの実装コードを呼び出す制御の反転が生じる点が特徴的です。
代表的な具体例としてApache Struts、CakePHP、Spring Framework、Ruby on Railsなどが挙げられます。
単に製品の固有名詞を暗記するだけでなく、標準的な構造と共通処理を枠組みごと再利用することで開発効率と統一感を高める狙いを理解しておく姿勢が欠かせません。

### 17 コンポーネントウェア

明確に定義されたインタフェースを持ち、独立して交換や再利用が可能なソフトウェア部品をコンポーネントと呼び、それらを組み合わせてシステムを組み立てる設計思想をコンポーネントウェアと呼びます。
Java BeansはJava言語における部品規約であり、CORBAは異なるプログラミング言語やハードウェアの間で分散オブジェクトを呼び出す規格です。
またOSGiは、Java実行環境において部品の動的追加や版管理、モジュール間の依存関係を管理する仕組みを提供します。
ソフトウェアを部品単位に分割できたとしても、境界面の仕様、版の互換性、依存の連鎖、障害の波及、通信性能への配慮が不要になるわけではありません。

## 接続資源と依存する製品を選ぶ

### 18 接続プール

データベースへの新規接続の確立や認証処理には、一定の負荷と時間がかかります。
そこで、起動時にあらかじめ複数の接続を確立しておき、要求に応じて接続を貸し出して再利用する仕組みが**接続プール**です。
接続を都度生成する負荷を大幅に削減できる反面、プールの接続数が少なすぎれば要求が待たされ、多すぎればデータベース側の計算資源を過剰に圧迫しかねません。
接続の返却漏れや、通信が切断された無効接続の定期検知、接続待ちのタイムアウト時間などを適切に設計・管理することが求められます。

### 19 選択の観点

ミドルウェアやライブラリを選定する際は、求める機能への適合性や標準規格への準拠状況、処理性能と拡張性、障害発生時の振る舞いを綿密に検証することが不可欠です。
セキュリティパッチの提供を含むサポート期間、既存の業務プログラムや利用言語との整合性、運用時の監視やトラブルシューティングの容易さも判断材料となります。
導入費用やライセンス体系、将来的に別の製品へ移行する際の切り替えコストも併せて見積もらなければなりません。
多機能な製品を安易に選べば、設定の複雑さや依存ライブラリの増大、新たな障害発生箇所の増加という副作用も招きます。
自らのシステムに必要な機能要件を明確に絞り込む姿勢が大切です。

通販、予約、会計などの業務が同一のデータ永続化や通信制御を必要とするなら、検証済みの共通部品に任せる構成が合理的といえます。
自作を避けた機能の複雑さが消滅するわけではありません。
障害時の挙動、版の互換性、ライセンス管理といった外部依存の管理へと形を変えて残ります。
再利用の恩恵は、どの境界面を誰が責任を持って保守するのかを見極め、引き受けて初めて得られる成果といえるでしょう。
