# 第5章 第10話 ミドルウェア、シェル、API

通販アプリ、予約アプリ、会計アプリは目的が違っても、データ保存、通信、認証、ログ、取引管理など似た機能を必要とします。

すべてのアプリが一から作れば、時間が掛かり、異なる不具合を抱えます。
OSとアプリの中間で、複数アプリに共通機能を提供するソフトウェアが**ミドルウェア**です。
共通機能を任せれば開発量は減りますが、アプリはその部品の障害、版、設定にも依存します。

```text
業務アプリ
────────────
ミドルウェア
────────────
OS
────────────
ハードウェア
```

## 共通の保存、通信、取引を任せる

### 1 OSとの違い

OSはCPU、メモリ、装置、ファイルなど低い水準の資源を管理します。

ミドルウェアはOSの機能を使い、データベース、Web処理、メッセージ、取引など、アプリに近い共通機能を提供します。

境界は絶対ではなく、OSに組み込まれる機能もあります。
選択時は提供機能、性能、互換性、運用、費用、サポートを見ます。

### 2 DBMS

通販アプリが注文を探すには、保存場所そのものより、データの構造と検索方法が必要です。
データベースを管理するミドルウェアが、**DBMS**、Database Management Systemです。
データ構造を定義し、検索、追加、更新、削除を行います。

複数の処理による同時更新を制御し、故障から回復し、権限を管理します。
索引で検索を速めることも機能です。
アプリは保存装置の物理番地を直接操作せず、SQLなどで「条件に合う注文を探す」と依頼します。
詳しくは第6章で学びます。

### 3 Webサーバとアプリケーションサーバ

**Webサーバ**はHTTP要求を受け、静的ファイルを返し、動的処理に要求を渡します。

**アプリケーションサーバ**は、業務アプリの実行環境、DB接続プール、セッション、トランザクション、認証などを提供します。

製品によって機能が重なり、同じプロセスで動く場合もあります。
名称より、どの役割を持つかを確認します。

### 4 通信管理システム

通信接続、相手識別、プロトコル変換、再送、経路、セッションなどを管理し、アプリ間通信を支えるミドルウェアが**通信管理システム**です。

異なる機種、OS、データ形式のアプリをつなぐ**アプリケーションプログラム間連携ソフトウェア**もあります。

共通の通信基盤が止まると多数のアプリに影響するため、容量、冗長化、変更管理が重要です。

### 5 メッセージ指向ミドルウェア

送信側が受信側の完了まで待つ構成は単純ですが、受信側の停止が送信側へ伝わります。
メッセージを一度キューへ預ければ送受信の時点を分けられる代わりに、重複、順序、滞留を管理しなければなりません。

送信側がメッセージをキューに置き、受信側が後で取り出す仕組みです。

```text
注文受付 → [通知キュー] → メール送信
```

受信側が一時停止してもキューに保持し、送受信の速度差を吸収します。

キューを使うなら、1回だけか、少なくとも1回の配送かを決めます。
重複時の扱い、順序を保証する範囲、再試行の回数も指定します。
永久失敗を隔離する場所と、キュー満杯時の対応も決めます。

### 6 TPモニター

多数の利用者から来る取引処理を管理するミドルウェアが、**TPモニター**です。
TPはTransaction Processingを表します。
要求の受付と振分け、プロセスとスレッドの共有、DB接続の共有を行います。

トランザクションの開始、確定、取消、負荷と障害の監視、複数の資源の更新調整も扱います。
銀行や予約などの大量オンライン取引で、アプリごとに資源を持つ無駄を減らし、一貫した制御を行います。

### 7 運用管理・開発支援ミドルウェア

監視、ジョブ、自動配備、ログ収集などを行う**運用管理ツール**も、共通基盤として使われます。

アプリ作成、試験、版管理などを助ける**ソフトウェア開発支援ツール**も広いミドルウェアの用語例に含まれます。

## コマンドの入出力を組み合わせる

### 8 シェル

共通機能はサーバ部品だけにあるわけではありません。
利用者や運用スクリプトがOS機能を組み合わせる入口として、シェルがコマンドの入出力をつなぎます。

利用者から文字の命令、**コマンド**を受け取り、解釈し、プログラム起動やOS機能呼出しを行うソフトウェアが**シェル**です。
shellは殻で、カーネルという核を包む利用者との境界です。

```text
利用者 → シェル → OSカーネル
```

コマンドを解釈するため**コマンドインタプリタ**とも呼びます。

### 9 代表的なシェル

シェルの代表的な系統には、UNIX系の**Bourne Shell**、B Shellと、C言語に似た構文を持つ**C Shell**があります。
公式用語表などでは、空白を入れず**BShell**、**CShell**と書くこともあります。
Windowsの代表的なコマンド処理系は、**cmd.exe**です。

現代にはbash、zsh、PowerShellなどもあります。
同じ名前のコマンドでも、構文と機能が違う場合があります。

### 10 コマンドの基本構造

コマンドの行では、行う仕事、動作方法、対象を分けて指定します。

```text
command option argument
```

commandはすること、optionは動作方法の指定、argumentは対象です。
例えば「一覧を詳しく表示」「このファイルをコピー」のように読みます。
空白、引用符、特殊文字の扱いは、シェルごとに決まります。

### 11 標準入力・出力・エラー

多くのコマンドは、入力、通常の結果、エラーや診断という3つの流れを持ちます。
標準入力では通常キーボードなどから読み、標準出力では通常の結果を画面などへ出します。
標準エラー出力では、エラーや診断を別の流れへ出します。

出力をファイルへ向ける**リダイレクト**、一方の出力を次の入力へつなぐ**パイプ**で、小さなコマンドを組み合わせます。

```text
コマンドA | コマンドB
```

### 12 シェルスクリプト

複数コマンド、条件分岐、繰返しなどをファイルに書き、自動実行するものが**シェルスクリプト**です。

バックアップ、ログ整理、配備などを自動化できます。
入力の引用漏れ、途中失敗、二重実行、強い権限、秘密情報の表示に注意します。

## プログラムから共通機能を呼ぶ

### 13 API

コマンドを組み合わせる方法とは別に、プログラムから共通機能を呼び出す境界が必要です。
呼出し方を固定すれば実装を交換しやすくなりますが、引数、戻り値、失敗時の約束を守る必要があります。

ソフトウェアから別ソフトウェアの機能を呼ぶための約束が**API**、Application Programming Interfaceです。

関数APIなら、名前、引数、戻り値、エラー、呼ぶ順序などを定めます。

```text
open(ファイル名, 読取モード) → 成功ならハンドル、失敗ならエラー
```

API仕様は、利用者向け画面ではなく、プログラム同士の契約書です。

### 14 Web API

ネットワーク越しにHTTPなどで呼び出すAPIが**Web API**です。

```text
GET /weather?city=Tokyo
→ 状態コード200とJSONの天気
```

URL、操作、入力形式、認証、応答形式、エラー、回数制限、版を仕様化します。
遠隔通信なので、遅延、切断、重複、相手変更を扱います。

### 15 ライブラリ

APIで呼び出す機能は、再利用する部品としてまとめられます。
再利用できるプログラム部品を整理して格納したものが、**ライブラリ**です。
人が読めるソース部品をまとめたものは**ソースライブラリ**、翻訳済みの目的コード部品をまとめたものは**オブジェクトライブラリ**です。

実行時に読み込める実行部品をまとめたものが、**ロードライブラリ**です。
動的に結合する共有ライブラリは**DLL**、Dynamic Link Library、オブジェクト指向のクラス群は**クラスライブラリ**です。
ライブラリは呼ばれた機能を提供し、通常はアプリ全体の流れを支配しません。

### 16 フレームワーク

アプリの標準構造、処理の流れ、拡張箇所を用意するクラスやライブラリの群が**開発フレームワーク**です。

ライブラリではアプリが部品を呼ぶのに対し、フレームワークでは枠組みがアプリの書いた部品を呼ぶ、**制御の反転**がよくあります。

代表的な用語例はApache Struts、CakePHP、Spring Framework、Ruby on Railsです。
製品名を暗記するだけでなく、標準構造と共通機能を再利用する目的を理解します。

### 17 コンポーネントウェア

明確なインタフェースを持つ交換や再利用が可能なソフトウェア部品を**コンポーネント**と呼び、その部品を組み合わせて開発する考えが**コンポーネントウェア**です。

Java BeansはJavaの部品規約、CORBAは異なる言語や機種の分散オブジェクトを呼ぶ仕組みです。
OSGiは、Java部品の動的追加、版、依存関係を管理する仕組みです。

部品化しても、インタフェース、版、依存、障害伝播、性能を管理します。

## 接続資源と依存する製品を選ぶ

### 18 接続プール

DB接続の作成や認証には時間が掛かります。
あらかじめ複数の接続を作り、要求ごとに貸し借りするものが**接続プール**です。

作成費用を減らせますが、数が少なければ待ち、多すぎればDBを圧迫します。
返却漏れ、切断済み接続の検査、最大待ちを管理します。

### 19 選択の観点

必要な機能と標準への対応、性能と拡張性、障害時の動作を確かめます。
安全な更新とサポート期間、既存のアプリや言語との互換性、運用監視のしやすさも選択条件です。
ライセンスとTCO、他の製品へ移る難しさも比べます。

高機能なミドルウェアでは、設定、依存する部品、障害点も増えます。
必要な機能を明確にします。

通販、予約、会計が同じ保存や通信の機能を使うなら、共通部品へ任せる方が合理的です。
ただし、作らなくて済んだ機能が消えるわけではなく、障害時の動作、互換性、ライセンスを含む依存関係へ移ります。
再利用の利益は、どの境界を誰が保守するかまで引き受けて初めて得られます。
