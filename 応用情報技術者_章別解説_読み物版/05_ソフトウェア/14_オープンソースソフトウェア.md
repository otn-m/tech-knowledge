# 第5章・第14話　オープンソースソフトウェア――読めるコードにも利用条件がある


## 1 「見える」だけではOSSとは限らない

Web上でソースを読めても、複製・改変・再配布を許すライセンスがなければ、OSSとは限りません。

反対に、OSSを有料で販売・サポートすることもできます。

```text
オープンソース ≠ 必ず無料
ソース閲覧可能 ≠ 必ず自由に利用可能
```

権利はライセンスという許諾条件から得ます。

## 2 OSSライセンス

著作権者は、利用者へ何を許し、何を条件とするかを**ライセンス**で示します。

確認する代表項目は次です。

- 商用利用できるか。
- 改変できるか。
- 再配布できるか。
- 著作権・ライセンス表示が必要か。
- 改変物・結合物のソース提供が必要か。
- 特許に関する条項があるか。
- 無保証であること。
- ライセンスの版。

「有名なライセンス名」だけでなく、対象ファイル、版、配布方法を確認します。

## 3 コピーレフト

改変・再配布する自由を後の利用者にも保つため、一定の派生物を配布するとき同じ自由を与える条件を求める考えが**コピーレフト**です。

著作権、copyrightを否定するのではなく、著作権に基づくライセンス条件で自由を継承させます。

どこまでが派生物か、動的リンク・ネットワーク利用をどう扱うかはライセンスごとに違います。実製品では法務・専門家と確認します。

## 4 GPL

**GPL**、GNU General Public Licenseは、代表的なコピーレフト型ライセンスです。

GPL対象プログラム・派生物を配布する場合、対応するソースコードの提供などの条件があります。私的利用やサーバ内利用だけの場合と、外部へ実行物を配布する場合では義務が違うことがあります。

版によって条項も違います。「GPL」とだけ記録せずGPLv2、GPLv3など版を残します。

## 5 BSDL

**BSDL**、BSD Licenseは、著作権表示・免責表示などを守れば、改変物を比較的広く利用・再配布できる寛容型ライセンス群です。

「BSDライセンス」にも条項の違う版があります。改変物を非公開製品へ組み込める場合が多い一方、表示条件などは残ります。

## 6 Apache License

**Apacheライセンス**は寛容型ライセンスの一つで、著作権・ライセンス・NOTICE表示、変更表示などの条件を持ち、特許許諾・特許訴訟に関する条項も含みます。

寛容型は「条件なし」ではありません。

## 7 MPL

**MPL**、Mozilla Public Licenseは、対象ファイル単位で改変ソースの公開を求める特徴を持つ、弱いコピーレフト型と説明されます。

MPLファイルの改変と、別ファイルとして組み合わせた独自コードを区別しやすい設計です。具体的な適用はライセンス本文を確認します。

## 8 デュアルライセンス

同じソフトウェアを二種類以上のライセンス条件から選べる形が**デュアルライセンス**です。

例えば、OSS条件を守る利用は無償ライセンス、ソース公開などを避けたい商用組込みは有償ライセンスを選ぶ形があります。

どちらを選んだか、購入した権利、対象版を記録します。

## 9 無保証とサポート

多くのOSSライセンスは、ソフトウェアを無保証で提供する旨を定めます。

しかしOSSだからサポートがないとは限りません。

- コミュニティの文書・掲示板。
- 提供企業の有償サポート。
- 自社技術者による保守。
- 外部保守会社。

導入費0でも、調査、更新、障害対応、教育、24時間支援に費用が掛かります。

## 10 LAMPとLAPP

Webアプリ基盤の代表的なOSS組合せを頭文字で表します。

```text
LAMP = Linux + Apache + MySQL + PHP〔Perl/Pythonを含める説明もある〕
LAPP = Linux + Apache + PostgreSQL + PHP
```

- LinuxはOSカーネル・環境。
- ApacheはWebサーバ。
- MySQL/PostgreSQLはDBMS。
- PHP等はアプリを記述・実行する言語環境。

四つ入れれば自動的に安全・高速になるわけではなく、版、設定、構成、アプリ設計が必要です。

## 11 UNIX系OSS

- **Linux**――Linuxカーネルを中心に多数の配布物がある。
- **FreeBSD**――BSD系のOS。
- **NetBSD**――多様な機種への移植性を重視するBSD系OS。
- **OpenBSD**――安全性・正しさを重視するBSD系OS。

**The Open Group**はUNIX商標・標準などを管理します。UNIX認証とUNIX系OSSは同義ではありません。

## 12 言語・ライブラリのOSS

Perl、Python、Rubyなどの言語処理系、多数のオープンソースライブラリがあります。

- **CPAN**――Perlのモジュールを配布する仕組み・保管場所。
- **PEAR**――PHPの再利用部品の配布体系。
- **jQuery**――Webブラウザ上のJavaScript処理を助けるライブラリ。

一つのアプリが数百・数千の間接依存を持つ場合があります。直接選んだ部品だけでなく依存の版・ライセンス・安全性を管理します。

## 13 仮想化・クラウドのOSS

公式シラバスの代表例を役割で整理します。

- **Xen**――ハイパーバイザ。
- **Docker**――コンテナイメージ作成・実行環境。
- **Kubernetes**――多数コンテナの配備・回復・拡縮を調整。
- **Terraform**――インフラ構成をコードで定義・適用。Terraform 1.5.7以前はMPL 2.0のOSSですが、1.6以降はBUSL 1.1へ変更され、ソースを読めてもOSIの定義によるOSSとは区別します。同系統の**OpenTofu**はOSSとして開発されています。製品名だけでなく、利用する版とそのライセンスを確認します。
- **OpenStack**――クラウド基盤を構築するソフトウェア群。
- **Istio**――サービス間通信の制御・観測を支えるサービスメッシュ。

名前の分類は代表的な用途です。複数部品・商用サービスと組み合わせて使います。

## 14 AI・画像処理のOSS

- TensorFlow、PyTorch、Keras、Deeplearning4j――機械学習・深層学習の構築・学習を支援。
- OpenCV――画像・映像処理。
- Chainer――深層学習フレームワークの歴史的な代表例。

モデル、学習データ、重み、コードはそれぞれ別のライセンス・利用条件を持つ場合があります。フレームワークがOSSでも、学習済みモデルを自由に使えるとは限りません。

## 15 開発・運用支援のOSS

役割ごとに分類します。

- Eclipse――統合開発環境。
- Git、Subversion――バージョン管理。
- SonarQube――コード品質・静的解析。
- Jenkins――ビルド・試験・配備などの自動化。
- Redmine――課題・プロジェクト管理。
- Selenium――Webブラウザ操作試験。
- Ansible、Chef、Puppet――構成管理・自動設定。
- Prometheus、Zabbix――監視・時系列収集。
- Grafana――測定値の可視化。

同じ分類内でも仕組み・得意範囲は違います。ここでは製品選定ではなく、OSSが開発全工程で利用されることを理解します。

## 16 オープンソースコミュニティ

OSSは、一社の社員だけでなく、世界の個人・企業・団体が協力して開発する場合があります。

代表的な団体には、

- **OSI**、Open Source Initiative――オープンソース定義・ライセンス承認。
- **FSF**、Free Software Foundation――ソフトウェアの自由を推進。
- Linux Foundation――Linuxを含む共同開発を支援。
- Apache Software Foundation――多数のOSSプロジェクトを支援。
- OpenSSF、Open Source Software Security Foundation――OSSの安全性向上を支援。

があります。

## 17 開発の進み方

典型的には、

1. 課題を報告する。
2. 修正案を公開する。
3. 自動試験と人のレビューを行う。
4. 管理者が統合する。
5. 版として公開する。

という流れです。

誰でも変更案を出せることと、誰でも公式版へ直接書けることは違います。管理権限、レビュー、署名、公開手順があります。

## 18 フォーク

ソースを複製し、別方針で開発を続けることを**フォーク**と呼びます。

元へ改良を提案するための一時コピーを指す場合と、プロジェクトが恒久的に分かれる場合があります。

自由な改変を可能にする一方、利用者・開発者が分散し、互換性が分かれる可能性があります。

## 19 安全性と信頼性

ソース公開だけで安全になるわけでも、危険になるわけでもありません。

確認するものは、

- 更新頻度と最終更新日。
- 脆弱性報告・修正版の速さ。
- レビュー・自動試験。
- 管理者の人数と権限保護。
- 署名・配布経路。
- 利用組織で更新できる体制。
- サポート終了。

です。

有名OSSでも設定ミス、古い版、危険な拡張で事故は起きます。

## 20 SBOMと依存管理

ソフトウェアを構成する部品、版、提供者、ライセンスなどの一覧が**SBOM**、Software Bill of Materialsです。材料表という意味です。

脆弱性が発表されたとき、「自社製品のどこでその版を使うか」を探せます。

一覧を作るだけでなく、

1. 脆弱性情報と照合する。
2. 影響を判断する。
3. 更新・緩和する。
4. 互換性を試験する。
5. 本番へ安全に展開する。

必要があります。

## 21 採用前の確認表

- 目的に合うか。
- ライセンスと版は何か。
- 配布・改変・ネットワーク提供で何が必要か。
- 依存部品は何か。
- 安全な入手元・署名はあるか。
- 更新・サポートを誰が行うか。
- 終了・移行できるか。
- 障害時の責任と連絡先は誰か。

「無償だから試す」は入口にはなっても、本番採用判断の全部ではありません。
