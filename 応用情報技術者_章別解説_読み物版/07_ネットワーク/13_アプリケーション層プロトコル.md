# 第7章 第13話 アプリケーション層プロトコル

IPとTCP/UDPは、データを相手のアプリへ運びます。
「どのページが欲しいか」「このメールを誰に送るか」という業務上の意味は、利用目的ごとのアプリケーション層プロトコルで伝えます。

ブラウザへURLを入力すると、まずDNSが名前をIPアドレスへ変え、TCPまたはQUICが通信路を作ります。
HTTPSではTLSによる相手確認も行い、HTTPで要求と応答を交わします。
画面に「接続できません」と出た場合は、DNS、接続確立、TLS、HTTPのどこまで成功したかを調べます。

## 名前を分散管理して宛先を調べる

### 1 DNS

人に読みやすい名前とIPアドレスなどを対応付ける仕組みが**DNS**、Domain Name Systemです。

```text
www.example.com → 192.0.2.20
```

IPアドレスが変わっても名前を保ち、階層的に分散管理できます。

### 2 ドメイン名

DNSで管理する階層的な名前が**ドメイン名**です。

```text
www.example.com.
```

右から左に大きな階層から読みます。

```text
.       ルート
com     TLD
example 登録されたドメイン
www     その中のホスト名やサービス名
```

末尾のルートを表す点は通常省略します。

### 3 TLD

ルート直下の`com`、`jp`などが**TLD**、Top-Level Domainです。

国や地域に対応するもの、用途を限定しない一般的なものなどがあります。
TLDだけでは、サイトが実際に存在する場所や安全性を保証できません。

### 4 DNSの分散管理

世界中のすべての名前を1台のサーバでは管理しません。

```text
ルートDNS
  ↓ comを管理する場所を示す
TLD DNS
  ↓ example.comを管理する場所を示す
権威DNS
  ↓ www.example.comの答えを返す
```

各管理者に権限を委任します。

### 5 再帰問い合わせ

端末は通常、近くのDNSリゾルバに「最終答えを得てください」と依頼します。
依頼された側が最終結果まで調べて返すものが再帰問い合わせです。

### 6 反復問い合わせ

DNSサーバが、ルート、TLD、権威サーバに順に尋ね、「次はここに」と紹介を受けて進むものが反復問い合わせです。

### 7 DNSレコード

DNSには、目的に応じた種類のレコードがあります。
名前からIPアドレスを得る場合、IPv4には`A`、IPv6には`AAAA`を使います。
メール配送先は`MX`、別名から正式名への対応は`CNAME`、その範囲の権威DNSは`NS`で表します。
`TXT`は文字情報を保持し、メール認証などにも利用します。

1つの名前に複数のIPアドレスを返し、負荷分散や冗長化に使う場合があります。

### 8 DNSキャッシュとTTL

一度得た答えをリゾルバや端末などが一時保存します。
答えを再利用してよい時間が**TTL**です。

これはDNSレコードの**TTL**〔Time To Live〕で、単位は秒、目的はキャッシュ保持期限です。
IPヘッダーのTTLはルータを1台通るごとに減る整数のホップ制限で、0になると破棄して転送ループを止めます。
同じ略語でも「秒のキャッシュ寿命」と「ホップごとの転送上限」で別物です。

長いTTLは問い合わせ負荷を減らしますが、IP変更後も古い答えが残ります。
変更前にTTLを短くし、浸透後に戻す運用があります。

存在しないという答えも一定時間キャッシュされる場合があります。

DNSで宛先IPアドレスが分かっても、利用者がどの情報を求め、サーバがどの結果を返したかは表せません。
Webでは、資源への操作と応答の意味をHTTPで伝えます。

## Webの操作と安全性を伝える

### 9 HTTP

Webでクライアントが要求し、サーバが応答する規則が**HTTP**、Hypertext Transfer Protocolです。

```text
要求: GET /news HTTP/1.1
応答: HTTP/1.1 200 OK
```

ヘッダーに対象ホスト、内容形式、長さ、キャッシュ条件などを置き、本文を運びます。

### 10 HTTPメソッド

HTTPメソッドは、資源に対して行う操作を表します。
`GET`は資源の取得、`POST`はデータを送って処理を依頼する操作です。
`PUT`は指定資源の作成や置換、`PATCH`は部分変更、`DELETE`は削除を表します。
`HEAD`では、本文を受け取らずにヘッダーを取得します。

メソッド名だけで安全性は保証されません。
サーバの実装が、それぞれの意味に従って処理する必要があります。

### 11 状態コード

```text
2xx 成功
3xx 別の場所への転送やキャッシュなど
4xx クライアント要求側の問題
5xx サーバ処理側の問題
```

代表例は、成功を示す200、転送を示す301と302、不正な要求を示す400、認証が必要な401、禁止を示す403、資源がないことを示す404、サーバ内部のエラーを示す500です。

404が返れば通信全体が切れているのではなく、HTTPでサーバまで会話できています。

### 12 HTTPS

HTTPをTLSで保護するものが**HTTPS**、HTTP over TLSです。
通常443番を使います。
TLSはサーバ証明書による相手確認と鍵合意を行い、暗号化で盗聴を防ぎ、改ざんを検出します。
接続時にはURL、証明書名、有効期間、信頼の連鎖を検証します。

HTTPSでも、サーバが提供する内容の正しさ、詐欺サイトではないこと、アプリに欠陥がないことまでは保証しません。

### 13 HTTP/1.1、HTTP/2、HTTP/3

**HTTP/1.1**では接続を再利用し、テキスト形式のヘッダーなどを使います。
**HTTP/2**は、1つのTCP接続上で複数のストリームを多重化し、ヘッダー圧縮などを行います。
**HTTP/3**はUDP上のQUICを使い、接続確立や、損失が各ストリームに与える影響を改善します。

アプリ上でのHTTPの意味と、下位でデータを運ぶ方式を分けて考えます。

### 14 QUIC

**QUIC**は頭字語の展開を持たないプロトコル名です。
UDP上で、暗号化された接続、信頼性、輻輳制御、複数ストリームを備えたトランスポートを提供します。
HTTP/3はこのQUICを利用します。

UDPを使っても信頼性を捨てるのではありません。
OSのTCP実装が更新されるのを待たず、アプリやライブラリで改良しやすい面があります。

Web以外の用途では、同じIP到達性の上へ別の会話を載せます。
遠隔操作、時刻同期、ファイル転送、メール、監視は、必要な信頼性と相手の役割がそれぞれ異なります。

## 用途ごとの通信規則を選ぶ

### 15 TELNETとSSH

**TELNET**は遠隔端末操作の古典的なプロトコルです。
通常は認証情報や通信内容を平文で運ぶため、信頼できないネットワークでは使いません。

**SSH**は遠隔操作、ファイル転送、トンネルを暗号化と認証によって保護します。
サーバ鍵の確認、利用者鍵、権限、更新を管理します。

### 16 NTP

ネットワーク越しに時刻を合わせるプロトコルが**NTP**、Network Time Protocolです。

単に時刻の値を写すだけでなく、通信の往復遅延や時計のずれを見ながら徐々に調整します。

正しい時刻は、ログ照合、証明書有効期間、認証、分散処理に重要です。
信頼する時刻源と改ざん対策を持ちます。

### 17 FTP

**FTP**〔File Transfer Protocol〕はファイル転送用プロトコルです。
制御接続でログインや`RETR report.csv`〔取得〕などの命令と応答を交わし、別のデータ接続で内容を運びます。

データ接続をサーバからクライアントへ開始するのがアクティブモードです。
パッシブモードでは、クライアントがサーバの指定したポートへデータ接続を開始します。

NATやファイアウォールを越える場合には、パッシブモードが扱いやすいことがあります。
通常のFTPでは認証情報や内容が平文になるため、目的に応じてFTPS、SFTP、HTTPSなどを使います。

### 18 TFTP

**TFTP**、Trivial File Transfer Protocolは、UDP上の単純なファイル転送です。

認証や一覧取得などの機能が乏しく、機器の起動や設定の転送など、管理された範囲で使われます。
外部に無防備に公開しません。

### 19 SMTP、POP、IMAP

**SMTP**〔Simple Mail Transfer Protocol〕は、クライアントから送信サーバへの投稿と、メールサーバ間の中継を行います。
`MAIL FROM`、`RCPT TO`、`DATA`のような要求と応答を使います。

受信側では、**POP3**〔Post Office Protocol version 3〕が、`RETR`などでサーバのメールを端末へ取り出します。
端末側で保存する単純な利用に向く方式です。
**IMAP4**〔Internet Message Access Protocol version 4〕は、`SELECT INBOX`や`FETCH`などで、サーバ上のフォルダや既読状態を操作します。
複数の端末で同じ状態を同期する利用に向きます。

メール配送は次の話で詳しく扱います。

### 20 SNMP

ネットワーク機器の状態の取得、設定、通知に使う**SNMP**、Simple Network Management Protocolがあります。
管理情報MIBとともに第16話で学びます。

## サービスやオブジェクトを呼び出す

### 21 SOAP

**SOAP**はXML形式のエンベロープでWebサービス呼出しを定めるメッセージ方式です。
現在は略語の展開より固有名として扱われますが、歴史的にSimple Object Access Protocolと展開されました。

ヘッダー、本文、エラーなどを構造化し、厳密な契約、機能の拡張、企業間の連携に使われます。
HTTP以外を下位にできる設計もあります。

### 22 Web API

**API**〔Application Programming Interface〕は、プログラムから別の機能を呼ぶための取決めです。
そのうちHTTPなどを通じてネットワーク越しに呼ぶものがWeb APIです。
例えば`GET /users/42`に認証情報を添え、JSONの利用者表現または`404 Not Found`を受け取ります。

URL、HTTPメソッド、入出力の形式、認証、エラー、バージョン、回数制限、タイムアウトを契約として決めます。

### 23 REST

**REST**〔Representational State Transfer〕は、Webの資源をURIで識別し、HTTPの統一された操作、状態を持たない要求などを生かすアーキテクチャ上の考えです。

JSONを返せば自動的にRESTになるわけではありません。
資源、メソッドの意味、キャッシュ、表現を設計します。

### 24 CORBA

**CORBA**〔Common Object Request Broker Architecture〕は、異なる言語や機種から成る分散環境で、ネットワーク越しのオブジェクトを共通の方式で呼び出す基盤です。

```text
クライアント
  ↓ 呼出し
IDLから生成したstub
  ↓
ORB ＝＝＝＝ ネットワーク ＝＝＝＝ ORB
                                  ↓
                         skeleton／POA
                                  ↓
                           オブジェクト実装
```

まず、**IDL**〔Interface Definition Language〕で、言語に依存しない操作と型を定義します。
クライアント側のstubは言語内の呼出しを要求メッセージに変換し、**ORB**〔Object Request Broker〕が対象の場所と言語の違いを仲介します。
サーバ側では、skeleton／POAが要求をオブジェクトの実装へ渡します。
必要に応じてNaming Service、Event Serviceなどの共通オブジェクトサービスも利用します。

このような考えを**分散オブジェクト技術**と呼びます。
相手停止、タイムアウト、部分失敗は局所関数呼出しと違います。

公開Web APIで軽量なHTTPによる資源操作を行うならREST系、厳密なXMLの契約や企業連携の機能が必要ならSOAP、異なる言語からオブジェクトを呼び出す基盤を既存環境で使うならCORBA、単純なファイル配送ならFTP系というように、目的、契約、障害モデル、安全要件で選びます。

### 25 名前からWeb表示まで

```text
URLを読む
 ↓
DNSで名前→IP
 ↓
TCPまたはQUICで接続
 ↓
TLSで相手確認・暗号化
 ↓
HTTP要求
 ↓
HTTP応答を解釈
```

どの段階が失敗したかで調査します。

URLを入力してからページが表示されるまで、DNS、トランスポート、TLS、HTTPは順に前の結果を受け取ります。
DNSが失敗すればHTTP要求はまだ作れず、TLSの証明書検証が失敗すればIP到達性があっても安全な接続を続けられません。
同じ画面上の失敗を、どのプロトコルの会話まで成立したかで切り分けます。
