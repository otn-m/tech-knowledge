# 第7章 第18話 Web、電子メール、ファイル転送

Webブラウザ上で1つのWebページを開く操作は、利用者の目には単一の通信で瞬時に完了したように映ります。
しかし実際には、最初に取得したHTML文書内に記述された画像、CSSスタイルシート、JavaScriptプログラム、外部フォントなどのリソースごとに、ブラウザは背後で無数のHTTPリクエストを並行して発行している構造です。
電子メールの世界に目を向けても、送信者の端末から受信者の手元へメッセージが直接届く通信は存在しません。
複数のメール中継サーバがバケツリレー式にメッセージを蓄積・転送し、受信者が都合の良いタイミングでメールボックスから取得する非同期通信が成立しています。
Web、電子メール、ファイル転送の各プロトコルは、下位のTCPやUDPという共通のトランスポート層プロトコルを利用しながらも、要求と応答の対話方式、データの蓄積と中継モデル、コネクションの維持管理において、それぞれ固有の設計思想を宿しているのです。

## Web文書の場所と構造を読む

### 1 Webとは何か

世界規模のインターネット網を舞台に、ハイパーテキストと呼ばれる文書群を相互に結び付け、画像やマルチメディアを含む情報を有機的に閲覧・操作可能とした情報システムが**Web**（World Wide Web：WWW）です。

```text
WebページA ──ハイパーリンク──> WebページB
     │
     └──ハイパーリンク──> 画像や動画
```

文書内の特定キーワードや画像をクリックすることで別の情報へと即座にジャンプできる参照構造をハイパーリンクと呼びます。
ここで注意すべき点として、物理的な地球規模の通信インフラであるインターネットと、その通信基盤の上で動作するアプリケーションサービスであるWebは別次元の概念です。
インターネット上ではWeb以外にも電子メール、DNS、ファイル転送、オンラインゲームなど多彩なサービスが稼働しています。

### 2 ブラウザとWebサーバ

Webの利用環境は、情報を要求して閲覧するクライアントソフトウェアと、情報を蓄積して提供するサーバソフトウェアの協調関係によって成り立ちます。

利用者がURLを入力し、HTMLを解釈してグラフィカルな画面として描画するクライアントプログラムが**Webブラウザ**です。
これに対し、クライアントからの閲覧要求を受け取り、対応するWebページや画像データを送り返すサーバプログラムが**Webサーバ**にあたります。

```text
利用者
  ↓ ブラウザへURLを入力
Webブラウザ ──HTTPリクエスト──> Webサーバ
Webブラウザ <──HTTPレスポンス── Webサーバ
  ↓
HTML・CSSを解釈して画面を描画
```

### 3 URLで情報の場所を表す

インターネット上に散らばる膨大なWebリソースの所在と取得方法を一意に特定するための統一表記形式が**URL**（Uniform Resource Locator）です。

```text
https://www.example.jp:443/shop/item?id=25#detail
└─┬─┘ └──────┬──────┘ └┬┘└────┬────┘└─┬─┘└─┬──┘
スキーム   ホスト名     ポート   パス    クエリ 断片
```

先頭の`https`は利用するプロトコルを示すスキームであり、それに続いて接続先のドメイン名（ホスト名）が指定されます。
ポート番号はWebサーバが待受を行う通信窓口であり、HTTPSの標準である443番やHTTPの80番であれば通常は省略可能です。
スラッシュ以降のパス名はサーバ内部での論理的な配置場所を示し、クエリ文字列はサーバプログラムへ渡す検索引数、末尾のフラグメント（断片識別子）は取得文書内のスクロール位置を表します。

### 4 HTMLでページの構造を表す

Webページの骨格となる見出し、段落、箇条書き、表、ハイパーリンクなどの論理構造を記述するためのマークアップ言語が**HTML**（HyperText Markup Language）です。

```html
<h1>商品の説明</h1>
<p>これは説明文です。</p>
<a href="/order">注文画面へ</a>
```

`<p>`や`<a>`のように山カッコで囲まれた構成要素をタグと呼びます。
HTMLは手順を順次実行するプログラミング言語というより、文書のどこがタイトルでどこが本文であるかという「情報の意味構造」を宣言する言語です。
文字の装飾やレイアウト設計はCSSが担い、動的な画面制御はJavaScriptが担当するという明確な役割分担が確立されています。

### 5 XMLで意味のある項目を表す

タグを用いてデータ項目の意味や階層構造を自在に定義できる汎用的なマークアップ言語として**XML**（Extensible Markup Language）が広く普及しました。

```xml
<product>
  <name>入門書</name>
  <price>2000</price>
</product>
```

HTMLがWebブラウザによる画面表示を主目的にあらかじめ決められた固定タグを用いるのに対し、XMLでは利用者が業務要件に合わせて任意のタグ名を自由に定義できる仕様です。
OSやプログラミング言語の差異を超えて構造化データを正確に伝達できるため、企業間の電子データ交換（EDI）や各種設定ファイルの記述形式として長年にわたり活用されてきた歴史を持ちます。

## 要求と応答から状態を管理する

### 6 HTTPでWebの要求と応答を交わす

WebブラウザとWebサーバが通信を行う際の共通プロトコルが**HTTP**（Hypertext Transfer Protocol）です。

```text
ブラウザ: GET /news HTTP/1.1
サーバ  : HTTP/1.1 200 OK
```

クライアントから送信されるHTTPリクエストは、操作内容を宣言するHTTPメソッド、取得対象のリソースパス、プロトコルバージョン、各種制御情報を格納するリクエストヘッダー、そして必要に応じて付加されるメッセージボディから構成されます。

- `GET`：指定されたリソースの取得を要求します。
- `POST`：送信フォームの入力データなどをサーバへ渡し、新たなリソースの作成や処理の実行を依頼する命令です。
- `PUT`：指定したURIのリソースを完全に置き換えるか、新規作成します。
- `DELETE`：指定されたリソースの削除を要求する命令です。

### 7 ステータスコード

HTTPリクエストを受け取ったWebサーバが、その処理結果の成否や理由をクライアントへ通知するための3桁の数字がステータスコードと呼ばれます。

- `200 OK`：要求が正常に受理され、処理が成功したことを示します。
- `301 Moved Permanently`：要求されたリソースが恒久的に別のURLへ移転したことを示すコードです。
- `400 Bad Request`：クライアントのリクエスト構文が不正でサーバが解釈できない状態を表します。
- `401 Unauthorized`：対象リソースの閲覧に適切なユーザ認証が必須であることを示します。
- `403 Forbidden`：リクエストは理解されたものの、管理者によってアクセス権限が拒絶された状態です。
- `404 Not Found`：指定されたリソースがサーバ上に存在しないことを告げます。
- `500 Internal Server Error`：サーバ側プログラムの例外や設定不備により内部処理が破綻した状態です。
- `503 Service Unavailable`：アクセス集中やメンテナンスにより一時的にサービスを提供できない旨を通知します。

百の位の数値が処理結果の大分類（2xx成功、3xxリダイレクト、4xxクライアント起因エラー、5xxサーバ起因エラー）を明快に表現する体系です。

### 8 HTTPS

平文でやり取りされるHTTP通信を暗号化プロトコル（TLS）で保護し、安全な対話を実現する仕組みが**HTTPS**（HTTP over TLS）です。

HTTPSは、通信路を暗号化して盗聴を退ける機密性、パケットの改ざんを確実に検知する完全性、そして認証局（CA）が署名したサーバ証明書によって接続先サーバが本物であることを確認する真正性を提供します。
ただし、HTTPSが保証するのは「通信相手のサーバとの通信路が暗号化されている事実」に留まる仕様です。
接続先のWebサイト自体の運営者が詐欺グループである可能性や、Webアプリケーション内にSQLインジェクションなどの脆弱性が潜んでいるリスクまでは防ぎきれません。

### 9 静的なページと動的なページ

Webサーバが返却するコンテンツには、生成形態の違いによって静的コンテンツと動的コンテンツの2種類が存在します。

ストレージ上に事前配置されたHTMLファイルや画像ファイルをそのまま読み出して返却するコンテンツが静的コンテンツです。
これに対し、クライアントからの要求を受け取ったWebサーバが背後のプログラムを実行し、データベースの検索結果やログインユーザの情報に基づいてその場でHTMLを組み立てて返却するコンテンツが動的コンテンツにあたります。

```text
ブラウザ → Webサーバ → Webアプリケーション → データベース
                                                ↓
ブラウザ ←────── 検索条件に合致するHTMLを動的に生成 ────┘
```

### 10 CGI

Webサーバがクライアントからの要求に応じて外部の実行可能プログラムを起動し、その標準出力をHTTPレスポンスとしてクライアントへ返送するための標準インターフェース仕様が**CGI**（Common Gateway Interface）です。

CGIは特定のプログラミング言語に依存せず、Webサーバと外部プログラムの間で環境変数や標準入出力を介してデータをやり取りする連携規約を意味します。
リクエストごとにプロセスを新規生成するCGIはサーバ負荷が高いため、現代のWebシステムではアプリケーションサーバプロセスを常駐させてリクエストを高速処理するアーキテクチャが主流です。

### 11 HTTPは前の会話を自動では覚えない

HTTPというプロトコルの最も根本的な性質として、過去の通信履歴を保持しないステートレス性が挙げられます。

Webサーバは個々のHTTPリクエストを完全に独立したイベントとして処理するため、1秒前にログイン認証を完了した端末から次のリクエストが届いても、同一のユーザからの通信であるかをプロトコル単体では判別できません。
しかし、ショッピングサイトの買い物かごや会員専用ページの閲覧には、過去の対話履歴を記憶する状態（ステート）の維持が不可欠となります。
このステートレスなHTTPの上で状態管理を実現するために導入された技術がCookieとセッションです。

### 12 Cookie

Webサーバからの指示に基づき、Webブラウザ側のストレージに小さなテキスト情報を保存させ、次回以降のアクセス時に自動でサーバへ送り返させる仕組みが**Cookie**です。

```text
初回訪問: Webサーバ ──「Set-Cookie: session_id=xyz789」──> ブラウザ（ローカル保存）
再訪問時: Webサーバ <──「Cookie: session_id=xyz789」────── ブラウザ（自動添付）
```

Cookieには有効期限、送信対象ドメイン、送信対象パス、さらにはJavaScriptからのアクセスを禁止する`HttpOnly`属性や、HTTPS通信でのみ送信を許可する`Secure`属性などの安全制御フラグを付与できます。

### 13 セッションID

ユーザの個人情報、ログイン状態、カートの中身といった機密性の高い実データをすべてWebサーバ側で集中管理する手法が広く採用されています。
このときブラウザに預けられる一意な識別キーが**セッションID**という識別キーです。

もしセッションIDが第三者に盗聴されたり推測されたりすると、悪意ある攻撃者がそのユーザになりすまして不正操作を実行できてしまいます。
したがって、セッションIDには十分な桁数の暗号学的に安全な擬似乱数を用い、HTTPSによる通信路暗号化を徹底するとともに、ログイン成功時には古いセッションIDを破棄して新規再発行する対策が不可欠な防衛策です。

## Webの機能を共有し通信を減らす

### 14 Web APIとREST

異なるソフトウェア同士がインターネットを通じて機能を相互利用するためのインターフェースがWeb APIです。
そのWeb APIを設計する際のデファクトスタンダードとなっている設計思想が**REST**（Representational State Transfer）にあたります。

```text
GET    /api/v1/products/25   商品番号25の詳細情報を取得
POST   /api/v1/products      新しい商品を登録
PUT    /api/v1/products/25   商品番号25の情報を全体更新
DELETE /api/v1/products/25   商品番号25を削除
```

操作対象となるデータをURIという名詞で一意に識別し、それに対する操作内容をHTTP標準のメソッドという動詞に厳格に対応付ける規律あるアーキテクチャです。
ステートレス性を堅持し、データ交換形式として軽量なJSONを採用することで、高スループットで保守性の高いシステム連携基盤を実現します。

### 15 WebDAV

HTTPプロトコルを拡張し、Webサーバ上のファイルやディレクトリを遠隔から直接作成・編集・削除できるようにした仕様がWebDAVです。

通常のHTTPメソッドに加え、ディレクトリ一覧を取得する`PROPFIND`、リソースを複製する`COPY`、別名に変更する`MOVE`、そして複数ユーザによる同時編集の衝突を防ぐ`LOCK`や`UNLOCK`といった拡張メソッドを提供します。
クライアントOSのファイル管理機能と統合することで、ネットワーク越しに存在するリモート共有フォルダのように直感的に操作できる利便性を備えた仕組みです。

### 16 HTTP/2、HTTP/3、QUIC

リッチなWebサイトが数百個もの画像やスクリプトを読み込む現代において、従来のHTTP/1.1が抱える通信遅延を克服するために新世代規格が登場しました。

- `HTTP/2`：単一のTCPコネクション内で複数のリクエストとレスポンスを細かなフレームに分割し、並行して送受信するストリーム多重化を実現しました。ヘッダー圧縮（HPACK）の導入と合わせて往復遅延を大幅に削減します。
- `HTTP/3`：下位トランスポート層にUDPベースの次世代プロトコルである**QUIC**を採用した最新規格です。TCP特有のヘッドオブラインブロッキングを根絶し、暗号鍵交換とコネクション確立を一体化することで、モバイル通信などの不安定な環境でも驚異的な高速化を達成しました。

QUICはUDPを採用しながらも、パケット順序制御、再送保証、輻輳制御のすべてをプロトコル自身が内蔵して実行する設計となっています。

### 17 検索エンジン

世界中に公開されている膨大なWebページの中から、利用者が入力した検索キーワードに関連する情報を瞬時に探し出して提示するシステムが**検索エンジン**です。

```text
クローラがWeb上を巡回 ──> HTML文書を収集 ──> 形態素解析してインデックス（索引）を作成
                                                            │
利用者がキーワードを入力 ─────── インデックスを高速照合して適合順にランキング表示 ────┘
```

Webサイト間を結ぶハイパーリンクを自動的に辿って世界中のページを巡回・収集するプログラムを**クローラ**と呼びます。
収集したテキストから単語を抽出し、どの単語がどの文書に含まれているかを逆引き辞書形式で整理したインデックスを作成しておくことで、億単位の文書群に対する瞬時の全文検索を可能にする基盤技術です。

## メールを蓄積しながら配送する

### 18 電子メールの登場人物

電子メールシステムは、即時応答を前提とするWebとは対照的に、ストア・アンド・フォワード（蓄積交換）モデルに基づいて動作します。

システムを構成する主な要素は、利用者がメールの作成や閲覧を行うクライアントソフト、メールの送信受付と宛先サーバへの中継を司る送信メールサーバ、受信したメールを私書箱に保管する配送サーバ、そして宛先ドメインのメールサーバを特定するDNSサーバです。

```text
alice@example.jp
└─┬─┘ └────┬────┘
ユーザ名   宛先ドメイン名
```

メールアドレスの`@`以降に示されたドメイン宛てにメールを配送するため、送信サーバはDNSに対して**MXレコード**の問い合わせを実行し、宛先メールサーバのホスト名とIPアドレスを取得します。

### 19 メールを送るSMTP

電子メールの送信およびサーバ間の中継を担当する標準プロトコルが**SMTP**（Simple Mail Transfer Protocol）です。
TCPポート番号25（サーバ間配送用）や587（クライアントからの投稿用サブミッションポート）を使用します。

```text
送信クライアント
  │ SMTP（TCP:587 / SMTP認証）
  ▼
送信側メールサーバ
  │ DNSのMXレコードを参照
  ▼ SMTP（TCP:25 / STARTTLS暗号化）
受信側メールサーバ
  │ ローカル配送
  ▼
受信者のメールボックス（私書箱）
```

送信側は`HELO`、`MAIL FROM`、`RCPT TO`、`DATA`といったシンプルなテキストコマンドを順次発行して配送を進行する手順です。
送信元の成りすましを排除するため、投稿時にはユーザ認証を行うSMTP-AUTHが義務付けられており、近年ではSPF、DKIM、DMARCといった送信ドメイン認証技術の併用が世界的な標準要件となりました。

### 20 POP3

メールサーバの私書箱に届いた電子メールを、手元のクライアント端末へ一括ダウンロードして閲覧するためのプロトコルが**POP3**（Post Office Protocol version 3）です。
通常はTCPポート番号110または995（TLS暗号化）を用いて接続します。

端末側にメールの実データを保存し、サーバ側からは削除する運用スタイルが古典的な基本形です。
単一のパソコンでメールを管理する形態には適しているものの、スマートフォンやノートPCなど複数の異なる端末から同一の受信メールを閲覧したり、既読状態やフォルダ分けを同期させたりする用途には不向きな構造となっています。

### 21 IMAP4

電子メールの実体をメールサーバ上で集中管理し、クライアント端末はサーバ上のフォルダ構成や既読・未読フラグなどの状態情報のみを同期して閲覧するプロトコルが**IMAP4**（Internet Message Access Protocol version 4）です。
通常はTCPポート番号143または993（TLS暗号化）を使用します。

```text
サーバ上のメールボックス
   ├─ 受信トレイ
   ├─ 業務プロジェクト
   └─ 送信済みトレイ
       ▲▼ フラグ・フォルダ状態のリアルタイム同期
複数端末（PC、スマートフォン、タブレット）
```

複数の端末からアクセスしても閲覧状態が完全に一致する絶大な利便性を誇る一方、全メールがサーバ上に蓄積されるため、メールサーバ側のストレージ容量管理やバックアップ体制の整備が重要な運用課題にあたる要素です。

### 22 Webメール

専用のメールソフトを端末にインストールすることなく、Webブラウザ上で電子メールの作成、送受信、管理を完結できるサービス形態が**Webメール**です。

ブラウザとWebメールサーバの間はHTTPSプロトコルを用いて暗号化通信を行い、Webメールサーバ自身が背後でSMTPによるメール送信やIMAP4によるメールボックス操作を代行します。
利用者の視点からはWebアプリケーションの操作に見えても、背後では標準的な電子メールプロトコルの連鎖が忠実に稼働している構造です。

## 本文と添付を表現して失敗を調べる

### 23 MIME

黎明期の電子メールは7ビットのASCII英数字テキストのみを伝送対象として設計されており、日本語などの多言語文字や画像ファイルを取り扱う能力を持ちませんでした。
この制約を突破し、多言語テキスト、HTML、画像、音声、添付ファイルなどを電子メールで自在に送受信できるように拡張した仕様が**MIME**（Multipurpose Internet Mail Extensions）です。

MIMEは電子メールのヘッダー部に以下の制御フィールドを追加することで、メッセージの構造を厳密に定義します。

```text
Content-Type: multipart/mixed; boundary="frontier"
Content-Transfer-Encoding: 7bit

--frontier
Content-Type: text/plain; charset=UTF-8
本日の会議議事録を添付します。

--frontier
Content-Type: application/pdf; name="report.pdf"
Content-Disposition: attachment; filename="report.pdf"
Content-Transfer-Encoding: base64
...（Base64エンコードされたバイナリ列）...
--frontier--
```

受信側のメールソフトはこのMIMEヘッダーを解析することで、どの部分が本文テキストであり、どの部分が添付ファイルであるかを正確に分離して処理する段取りです。

### 24 base64

電子メールのように7ビット文字列しか通過できない伝送路上で、8ビットのバイナリデータを破損することなく安全に転送するための符号化方式が**Base64**です。

Base64は、任意のバイナリデータを6ビット単位に分割し、英大文字、英小文字、数字、記号の計64種類の印刷可能文字へとマッピングします。
元のデータ3バイトが4文字のテキストへと変換されるため、データ量は元のサイズに対して厳密に4/3倍（約1.33倍、約33%増）へと肥大化する計算です。
例えば3MBの添付ファイルは、Base64エンコードを施した時点で本文データだけで約4MB相当へと膨張する点に留意しなければなりません。
Base64は文字種を制限する符号化処理であり、暗号化とは異なり誰でも即座に元のバイナリへと復元できる性質を持ちます。

### 25 HTMLメールとMHTML

電子メールの本文をHTML形式で記述し、文字のフォントや配色、表組み、画像のインライン埋め込みを可能にした形式がHTMLメールです。

Webページと同等の豊かな表現力を享受できる一方、本文を開いた瞬間に外部サーバから画像を読み込ませるWebビーコンによる開封確認や、悪質なフィッシングサイトへの偽装リンクといったセキュリティ上の脅威を伴います。
なお、HTMLファイルとそれに付随する画像やCSSファイルを単一のファイルとしてMIME形式で統合パッケージ化した規格が**MHTML**という規格です。

### 26 メール配送の失敗を読む

電子メールが宛先に届かないトラブルが発生した際、エラーの発生箇所を特定するにはバウンスメールの内容を論理的に読み解く姿勢が不可欠です。

- **Host or domain name not found**：宛先アドレスのドメイン名が存在しないか、送信側のDNSサーバでMXレコードの名前解決に失敗した状態を示します。
- **Connection timed out**：宛先メールサーバのIPアドレスは判明したものの、ファイアウォールによるポート25の遮断や相手サーバの停止によりTCP接続が成立しなかったエラーです。
- **User unknown / No such user here**：相手メールサーバへの接続には成功したものの、指定されたアカウントが受信サーバ上に存在しないと拒絶された状態を表します。
- **Mailbox quota exceeded**：受信者のメールボックスが容量制限の上限に達しており、新たなメッセージを受け入れられない状態です。
- **Message size exceeds fixed limit**：添付ファイルを含むメールの総容量が、中継サーバや受信サーバの許容上限を超過したため差し戻された状態を示します。

届かないという結果だけにとらわれず、送信ログ、DNSレコード、SMTPエラー応答コードを時系列で照合することが確実な原因究明へと繋がります。

## ファイル転送の接続を選ぶ

### 27 アップロードとダウンロード

ネットワークに接続された2台のコンピュータ間で、ファイルの実データを送受信する処理がファイル転送です。

利用者の手元にあるクライアント端末からリモートサーバへファイルを転送して配置する操作をアップロードと呼び、逆にリモートサーバ上に存在するファイルを取得して手元端末へ保存する操作をダウンロードと呼びます。
通信の方向性は常に利用者の手元の端末を主語にして定義されるのが普遍的なルールです。

### 28 FTP

インターネットの黎明期からファイル転送の標準として広く利用されてきた専用プロトコルが**FTP**（File Transfer Protocol）です。

FTPの最大の特徴は、ログイン認証や転送コマンドをやり取りする制御用接続（TCPポート21）と、ファイルの実データやディレクトリ一覧を伝送するデータ用接続（TCPポート20等）という2本の独立したTCPコネクションを分離して運用する点に特徴があります。
ただし、従来の標準FTPはユーザ名、パスワード、ファイル内容のすべてを平文のままネットワークへ流す致命的な脆弱性を抱えていました。
そのため現代の実務では、SSL/TLSで通信全体を暗号化するFTPSや、SSHプロトコルをベースとした安全なファイル転送プロトコルであるSFTPへの移行が定着しているのが実情です。

### 29 FTPのアクティブモード

FTPにおいて、データ用接続をサーバ側からクライアント側へ向けて能動的に開始する古典的な動作モードとしてアクティブモードが知られています。

```text
制御接続: クライアント (Port: 1025) ─────> FTPサーバ (Port: 21)   コマンド送信
データ接続: クライアント (Port: 1026) <───── FTPサーバ (Port: 20)   ファイルデータ転送
```

クライアントが自身の待受ポート番号をサーバへ通知し、サーバ側のポート20からクライアントへ向けて新規接続を仕掛けてくる手順です。
しかし、一般的な企業のファイアウォールや家庭用ルータのNAT環境では、外部から内部へ向けて突然開始される新規TCP接続は不正侵入とみなされて遮断されてしまいます。
このファイアウォール遮断問題を回避するために考案されたのがパッシブモードです。

### 30 FTPのパッシブモード

データ用接続も制御用接続と同様に、クライアント側からサーバ側へ向けて開始するように改良されたモードとしてパッシブモードが開発されました。

```text
制御接続: クライアント (Port: 1025) ─────> FTPサーバ (Port: 21)     PASVコマンド送信
データ接続: クライアント (Port: 1026) ─────> FTPサーバ (Port: 50001) ファイルデータ転送
```

クライアントから送られた`PASV`コマンドに対し、サーバ側がデータ転送用の一時的な待受ポート番号を返答する段取りです。
クライアントはサーバから指定されたそのポートへ向けて自発的にデータ接続を開設するため、内側から外側への接続を許可する一般的なNATやファイアウォール環境でも問題なくファイル転送を完結できる利点があります。

### 31 TFTP

機能を極限まで削ぎ落とし、UDPプロトコル（ポート69）を用いてシンプルにファイルを転送する仕組みが**TFTP**（Trivial File Transfer Protocol）です。

ユーザ認証機構やディレクトリ一覧の表示機能を持たず、エラー発生時のパケット再送ロジックも極めて簡易的なアルゴリズムで動作します。
プログラムサイズを極めて小さく抑えられる利点から、ルータやL2スイッチのファームウェア更新、あるいはOSを持たないディスクレス端末がネットワーク経由でブートイメージを読み込むPXEブートなどの閉じた管理環境に特化して利用されるプロトコルです。

### 32 サービスを比べる

インターネット上で日常的に利用される主要な上位アプリケーションサービスの通信モデルと役割の違いを以下の対比表に整理します。

| アプリケーション種別 | 代表プロトコル | 主な通信モデル | 典型的な利用用途 |
|---|---|---|---|
| Webアクセス・API連携 | HTTP、HTTPS | クライアント／サーバ（即時同期対話型） | Web閲覧、クラウドサービス、RESTful API |
| メール送信・中継 | SMTP | ストア・アンド・フォワード（非同期中継型） | メール投稿、サーバ間バケツリレー配送 |
| メール受信・同期 | POP3、IMAP4 | メールボックス取得／状態同期型 | 端末への保存、複数端末間でのフォルダ同期 |
| ファイル転送 | FTP、SFTP、TFTP | 制御／データ分離型、UDP転送型 | 大容量ファイル配送、ファームウェア更新 |

1つのWebページを表示する処理では、最初のHTML取得が成功しても、付随する画像や外部スクリプトのURL解決や追加要求が途絶すれば画面は欠落してしまう構造です。
電子メールはSMTPによって複数のサーバを経由し、受信者がメールソフトを開くまでサーバ上に安全に保持され続けます。
同じデータを相手へ送り届けるという目的であっても、対話の同期性、データの永続化モデル、接続の確立手順はサービスごとに異なり、それぞれの設計思想がインターネットの豊かな発展を支える礎です。
