# 第7章 第22話 1つの通信を端から端までたどる

WebブラウザのアドレスバーにURLを入力したものの、画面が白いまま停止してエラーが表示される現象に直面したとき、原因を直感だけで特定することは不可能です。
「通信が繋がらない」という同一の事象であっても、背後で起きているトラブルの所在は実に多岐にわたるのが実態です。
DHCPによるIPアドレス取得の失敗、DNSの名前解決エラー、同一セグメント内でのARP解決不能、デフォルトゲートウェイの経路喪失、ファイアウォールによるTCPポート遮断、TLS証明書の不一致、そしてWebアプリケーション自体の内部エラーに至るまで、あらゆる階層が障害の容疑者に挙げられるでしょう。

Webページを1枚開くという日常的な操作の裏側では、OSI基本参照モデルの最下層から最上位層に至る無数のプロトコルがバトンを繋ぎ合っています。
端末のキーボードが押された段階から、世界中を駆け巡って遠隔のサーバへ到達し、再び手元の画面にコンテンツが組み上がるまでの一連のパケットの旅を順を追って精密にトレースしてみましょう。
各プロトコルが直前の階層から何を受け取り、自身のヘッダを付与してどこへ送り出したのかを把握できれば、複雑なネットワーク障害に直面しても、成功した境界と失敗した境界を論理的に切り分けられるはずです。

## 接続設定と名前解決を確かめる

### 1 出発前に必要な設定

端末がインターネットとの通信を開始するためには、自身のネットワークインタフェースに正しいTCP/IPパラメータが事前に組み込まれていなければなりません。
具体的には、自分自身を識別するIPアドレス、所属するサブネットの範囲を定義するサブネットマスク、異なるネットワークへパケットを送り出す出口となるデフォルトゲートウェイ、そしてドメイン名をIPアドレスへ変換するDNSサーバのIPアドレスの4点です。

現代のオフィスや家庭環境では、これらのパラメータを管理者が1台ずつ手動設定する代わりに、**DHCP**（Dynamic Host Configuration Protocol）を用いて自動取得する運用が定着しています。

```text
端末 ──DHCP Discover──>「設定を配布してくれるサーバはいますか（ブロードキャスト）」
端末 <──DHCP Offer────「このIPアドレスとネットワーク設定を提案します」
端末 ──DHCP Request───>「提示された設定を使用させてください」
端末 <──DHCP Ack──────「使用を正式に承認しました（リース完了）」
```

Wi-Fi接続を利用している環境であれば、このDHCPシーケンスが始まる前に、周囲の電波をスキャンしてSSIDを特定し、WPA2やWPA3による認証プロトコルと暗号化キーの共有ハンドシェイクを完了させておく物理・データリンク層の準備が欠かせない前提となります。

### 2 URLを入力する

すべての通信基盤が整った状態で、利用者がブラウザのアドレスバーに次のURLを入力した場面を想定してみましょう。

```text
https://www.example.jp/products/25
```

ブラウザは入力された文字列を構文解析し、通信方式（スキーム）が暗号化通信である`HTTPS`、接続先のFQDNが`www.example.jp`、接続先のポート番号が標準のTCP 443、そして取得対象となるリソースのパスが`/products/25`であることを瞬時に解釈する動作に入ります。
しかし、この段階で手元にあるのは人間に理解しやすいドメイン名にすぎないのが実情です。
IPパケットを組み立てるためには、相手のコンピュータを一意に特定する32ビット（または128ビット）のIPアドレスを突き止めねばなりません。

### 3 DNSキャッシュを調べる

ドメイン名が出現するたびに世界中のネームサーバへ問い合わせを発行していては、無駄なトラフィックがネットワークを圧迫し、Web閲覧のレスポンスが著しく悪化するのは自明です。
そのため、ブラウザ、オペレーティングシステムのリゾルバ機能、さらには社内ルータに至る各階層が、過去の名前解決結果をメモリ上に一定期間保持するキャッシュ機構を標準装備しています。

```text
ローカルキャッシュに有効なレコードが存在するか
  ├─ 存在する ──> キャッシュされたIPアドレスを即座に採用
  └─ 存在しない ─> ネットワーク上のDNSサーバへ問い合わせを発行
```

レコードをキャッシュに保持してよい制限時間は**TTL**（Time To Live）と呼ばれ、ドメインの管理者が権威DNSサーバ上で秒単位で明示的に指定する値です。
サーバ移転時に「一部の端末だけが古いサーバへ繋がってしまう」というトラブルが発生した際は、まさにこのTTLが切れるまで古いキャッシュが各所に残留している状況を疑うべきでしょう。

### 4 DNSで名前を解決する

ローカルキャッシュに対象のレコードが見当たらない場合、端末のスタブリゾルバは設定されたDNSキャッシュサーバ（フルサービスリゾルバ）へ再帰的な問い合わせパケットを送出する流れとなります。
キャッシュサーバは自前でキャッシュを持っていなければ、インターネットの頂点に君臨するルートDNSサーバから順に階層構造をたどる段取りです。

```text
端末 ──> キャッシュサーバ ──> ルートDNS ──> .jpのTLD DNS ──> example.jpの権威DNS
端末 <── キャッシュサーバ <──────────────── wwwのIPアドレス ──────────┘
```

問い合わせと回答の伝送には、接続確立オーバーヘッドのない軽量なUDPポート53が主として利用されます。
ただし応答サイズが512バイトを超える場合やゾーン転送時には、TCPポート53へと切り替わる仕様が一般的です。
もしDNSサーバの設定誤りや障害によって名前解決が失敗すると、物理回線やルーティングが健全であってもブラウザは「サーバが見つかりません」というエラー画面を出力して立ち往生してしまいます。

## 最終宛先と次の転送先を決める

### 5 宛先が近いか遠いかを判断する

名前解決によって相手のIPアドレス（例: `203.0.113.20`）が判明すると、端末のOSは自身のIPアドレス（例: `192.168.1.25`）とサブネットマスク（例: `255.255.255.0`）を用いて論理積（AND演算）を実行します。
宛先のIPアドレスが自身と同じネットワークセグメント（LAN内）に属しているか、それとも外部のネットワークに属しているかを判定するためです。

```text
同一サブネットに所属 ──> LAN内の宛先機器へ直接Ethernetフレームを届ける
外部サブネットに所属 ──> デフォルトゲートウェイ（ルータ）へフレームを届ける
```

今回の宛先は外部のパブリックIPアドレスであるため、OSはパケットを「デフォルトゲートウェイへ託す」というルーティング判断を下します。
ここで注意すべきは、IPパケットのヘッダに記される最終宛先はWebサーバのIPアドレスですが、そのIPパケットを包み込むEthernetフレームの宛先MACアドレスは、同じLAN上に存在するデフォルトゲートウェイのMACアドレスになるという事実です。

### 6 ARPでMACアドレスを知る

OSはデフォルトゲートウェイのIPアドレス（`192.168.1.1`）を把握していますが、LAN内でフレームを送出するためには、そのルータが持つ物理的なMACアドレスを知る必要があります。
自身のARPテーブルに対象のエントリが存在しない場合、**ARP**（Address Resolution Protocol）要求をブロードキャストで発信します。

```text
端末 ──ブロードキャスト（FF:FF:FF:FF:FF:FF）──>「192.168.1.1を持つ機器はMACを教えてください」
端末 <──ユニキャスト───────────────────────── ルータ「私のMACアドレスは AA:BB:CC:DD:EE:01 です」
```

回答を受け取った端末は、IPアドレスとMACアドレスの対応関係を自身のARPキャッシュに記録し、送信フレームの組み立てを完了させる段取りです。
なお、IPv6環境ではARPに代わり、ICMPv6を用いる近隣探索（Neighbor Discovery）がMACアドレス解決の役割を担っています。

### 7 TCP接続を作る

相手がWebサーバである場合、上位のHTTP/1.1やHTTP/2は高信頼なストリーム伝送を前提とするため、事前のTCPコネクション確立が欠かせません。
ブラウザはOSのTCPスタックを呼び出し、WebサーバのTCPポート443に向けてSYNパケットを送信します。

```text
ブラウザ ── [SYN] seq=1000 ─────────────────────> Webサーバ
ブラウザ <── [SYN, ACK] seq=5000, ack=1001 ────── Webサーバ
ブラウザ ── [ACK] seq=1001, ack=5001 ───────────> Webサーバ
```

これが有名な**3ウェイハンドシェイク**です。
双方が双方向のデータ送受信を開始できる健全な状態にあるかを確認し、送信データのバイト位置を追跡するための初期シーケンス番号（ISN）を互いにすり合わせます。
クライアント側の送信元ポート番号には、OSによってエフェメラルポートと呼ばれる49152〜65535の範囲から未使用の番号（例: `52140`）が自動的に割り当てられます。

```text
送信元ソケット: 192.168.1.25:52140
宛先ソケット  : 203.0.113.20:443
```

OSはこの送信元IP、送信元ポート、宛先IP、宛先ポート、プロトコル番号の5つの組（5タプル）によって、同時に走る無数の通信コネクションを一切混同することなく独立に管理するのです。
なお、最新のHTTP/3を採用する環境であれば、TCPハンドシェイクを排し、UDP上で動作するQUICプロトコルを用いてより迅速な暗号化接続確立を推進します。

### 8 LAN内をフレームが進む

TCPの制御セグメントは、OS内部でIPヘッダが付与されてIPパケットとなり、さらにネットワークインタフェースカード（NIC）でEthernetヘッダとFCS（誤り検出符号）が付加されて物理的なEthernetフレームへとカプセル化される流れです。

```text
┌────────────────────────────────────────────────────────┐
│ Ethernetヘッダ: 宛先MAC（ルータ）, 送信元MAC（端末）     │
│   ┌────────────────────────────────────────────────────┐│
│   │ IPヘッダ: 宛先IP（サーバ）, 送信元IP（端末）        ││
│   │   ┌────────────────────────────────────────────────┐││
│   │   │ TCPヘッダ: 宛先ポート443, 送信元ポート52140    │││
│   │   │   ┌────────────────────────────────────────────┐│││
│   │   │   │ アプリケーションデータ（TLS/HTTP）          ││││
│   │   │   └────────────────────────────────────────────┘│││
│   │   └────────────────────────────────────────────────┘││
│   └────────────────────────────────────────────────────┘│
│ FCS（フレームチェックシーケンス）                       │
└────────────────────────────────────────────────────────┘
```

LANケーブルを電気信号として流れたフレームは、まずフロアのレイヤ2スイッチへと物理的に届きます。
スイッチはフレームの宛先MACアドレスを読み取り、自身のMACアドレステーブルを参照して、デフォルトゲートウェイのルータが接続されているポートだけにフレームを高速転送する仕組みです。
スイッチはL2機器であるため、内部のIPアドレスやTCPポート番号に干渉することなくフレームを中継する設計です。

### 9 ルータを一段ずつ進む

フレームを受け取ったデフォルトゲートウェイ（ルータ）は、Ethernetヘッダを剥離して中身のIPパケットを取り出す動作に移ります。
ルータはパケットの宛先IPアドレスを読み取り、自身のルーティングテーブルと最長一致（ロンゲストマッチ）で照合して、パケットを送り出すべきネクストホップ（次のルータ）を決定しなければならない立場です。

```text
端末 ──> 社内ルータ ──> ISPエッジルータ ──> バックボーンルータ群 ──> サーバ側ルータ ──> Webサーバ
```

ルータはパケットを次の伝送路へ送り出す際、IPヘッダ内の**TTL**（Time To Live）フィールドの値を1だけ減算する処理を行います。
ネットワークの誤設定によってルーティングループが発生した際に、パケットが永久に回り続けて帯域を食いつぶす破局を防ぐための安全弁です。
TTLが0に達したパケットはその場で破棄され、送信元へICMP Time Exceededメッセージが返送されます。
また、パケットがルータを通過するたびに、L2のフレームヘッダ（送信元MACと宛先MAC）は次のホップに合わせて完全に作り直される一方、IPヘッダの送信元・宛先IPアドレスは基本的に終点まで不変のまま保持される構造となっています。

### 10 NAT/NAPTを通る

家庭や企業のLAN環境では、端末にプライベートIPアドレスが割り当てられているため、インターネットへパケットを直接送り出すことは不可能です。
そこで、組織の境界に設置されたブロードバンドルータやファイアウォールが、IPアドレスとポート番号の変換処理（NAPT/IPマスカレード）を実行します。

```text
LAN側パケット: 192.168.1.25:52140 ──> 203.0.113.20:443
                    │
              [ NAPT変換テーブルにマッピングを記録 ]
                    ↓
WAN側パケット: 198.51.100.8:40001 ──> 203.0.113.20:443
```

ルータは変換テーブルに「内部IP:ポート」と「外部グローバルIP:ポート」の対応関係を厳密に書き留めます。
相手サーバから返信パケットが届いた際には、このテーブルを逆引きして宛先を端末のプライベートアドレスへと書き戻し、LAN内へ安全に中継する仕組みです。
もし変換テーブルの保持期限が切れてエントリが消滅したり、事業所の同時接続数が多すぎてNATポートが枯渇したりすると、パケットはルータで無言で破棄され、通信が突如として途絶えることになります。

### 11 経路は行きと帰りで同じとは限らない

インターネットは自律システム（AS）と呼ばれる多数の独立したネットワーク組織が網の目のように相互接続された分散システムです。
各事業者のルータはBGPなどの経路制御プロトコルに基づき、自社の回線コストやトラフィックポリシーを反映してパケットの転送経路を自律的に決定します。

したがって、端末からサーバへ向かう「往路」と、サーバから端末へ戻る「復路」が全く異なる物理経路を通る**非対称ルーティング**は日常茶飯事の現象です。

```text
往路: 端末 ──> ルータA ──> ルータB ──> ルータC ──> サーバ
復路: 端末 <── ルータF <── ルータE <── ルータD <── サーバ
```

IPプロトコル自体は非対称ルーティングを完全に許容する仕様ですが、通信の行き帰りを厳密に監視するステートフルインスペクション型ファイアウォールが経路の途中に介在している場合、往路を通っていない戻りパケットを不正な通信と見なして破棄してしまう障害を引き起こす恐れがあります。

## 相手を確認してWebの応答を受け取る

### 12 TLSで相手を確認し暗号鍵を作る

TCPコネクションの3ウェイハンドシェイクが完了すると、HTTPS通信の核心である**TLS**（Transport Layer Security）ハンドシェイクへと移行します。
まずクライアントがサポートする暗号スイートの一覧を提示し、サーバが採用する暗号方式を選択した上で、自身の身元を証明するデジタル証明書をクライアントへ返す段取りです。

```text
クライアント ── ClientHello ──────────────────────────> サーバ
クライアント <── ServerHello, Server Certificate ───── サーバ
クライアント ── [鍵交換パラメータ送付, 暗号化開始] ────> サーバ
クライアント <── [暗号化開始, Finished] ────────────── サーバ
```

ブラウザはOSに組み込まれた信頼できる認証局（CA）のルート証明書を用いて、サーバ証明書のデジタル署名を数学的に検証する流れです。
証明書の有効期限が切れていないか、失効リスト（CRL/OCSP）に含まれていないか、そして何より証明書に記載されたコモンネーム（CN）やサブジェクト別名（SAN）がURLのホスト名`www.example.jp`と寸分違わず一致しているかを厳密に照合しなければなりません。
身元の正当性が確認されると、双方はDiffie-Hellman鍵交換などを通じて安全に共通鍵（セッション鍵）を生成し、以降の全通信データを強力に暗号化して盗聴と改ざんを完全に封じ込めるのです。

### 13 HTTP要求を送る

強固に暗号化されたTLSトンネルが確立された段階で、ブラウザはようやく本来の目的であるHTTPリクエストメッセージの生成と送信に踏み切るのです。

```http
GET /products/25 HTTP/1.1
Host: www.example.jp
User-Agent: Mozilla/5.0 ...
Accept: text/html,application/xhtml+xml
Cookie: session_id=a1b2c3d4e5f6
Connection: keep-alive
```

リクエスト行には対象リソースを取得する`GET`メソッドとパス`/products/25`が記され、続く`Host`ヘッダによって同一のIPアドレス上で複数のWebサイトを同居させるバーチャルホストの識別が行われます。
以前のアクセスでサーバから発行されたCookieが存在すれば、認証状態やショッピングカートの状態を維持するために`Cookie`ヘッダとして添えて送信される仕組みです。

### 14 サーバ側で処理する

Webサーバの物理拠点に到達したHTTPリクエストは、巨大なWebサービスであれば単一のコンピュータで処理されることは稀であり、多層化されたシステム基盤を順に通過していきます。

```text
インターネット
     ↓
ロードバランサ（L7負荷分散・TLS終端）
     ↓
リバースプロキシ / Webサーバ（静的コンテンツ配信・振り分け）
     ↓
アプリケーションサーバ（ビジネスロジック実行）
     ↓
データベース / 分散キャッシュ / 外部決済API
```

ロードバランサは膨大なアクセスを複数のサーバへ均等に振り分け、背後のアプリケーションサーバはセッションIDを検証して利用者のアクセス権限を確認します。
続いてSQLクエリを発行してデータベースから商品番号25の名称や価格、在庫情報を取得し、HTMLテンプレートへそれらのデータを流し込んで動的なWebページを組み立てる段取りです。
もしここでプログラムのバグによる未処理例外が発生したり、データベースへの接続がタイムアウトしたりすると、サーバはクライアントに対して内部エラーを示す`500 Internal Server Error`を返送することになります。

### 15 HTTP応答が戻る

アプリケーションの処理が無事に完了すると、WebサーバはHTTPレスポンスメッセージを組み立ててクライアントへと返送する運びとなります。

```http
HTTP/1.1 200 OK
Date: Wed, 21 Oct 2026 07:28:00 GMT
Content-Type: text/html; charset=UTF-8
Content-Length: 48212
Cache-Control: max-age=3600

<!DOCTYPE html>
<html lang="ja">
<head>...
```

ステータスコード`200 OK`は、要求が正常に受理されてコンテンツが返却された事実を宣言するものです。
HTMLのデータサイズが数万バイトにおよぶ場合、下位のTCP層はそのデータを複数のMSS（最大セグメントサイズ、通常は約1,460バイト）に細かく分割してパケット化する方針を採ります。
受信側のブラウザOSは、バラバラに届いたTCPセグメントのシーケンス番号を照合して元の正しい並び順へ再構築し、途中で消失したパケットがあればACKの不達を検知して再送を要求することで、1ビットの欠落もない完全なHTMLストリームとしてブラウザへ引き渡すのです。

### 16 ブラウザが画面を組み立てる

HTMLデータを受け取ったブラウザのレンダリングエンジンは、構文解析を行ってDOM（Document Object Model）ツリーをメモリ上に構築し始める段取りです。
しかし、HTMLの本文中には外部のCSSスタイルシート、JavaScriptファイル、商品画像、Webフォントへの参照リンクが多数埋め込まれています。

```text
HTMLの解析開始
  ├─ style.css の外部参照を発見 ────> 追加のHTTP GET要求を発行
  ├─ app.js の外部参照を発見 ───────> 追加のHTTP GET要求を発行
  ├─ item25.jpg の外部参照を発見 ───> 追加のHTTP GET要求を発行
  └─ Webフォントの参照を発見 ────────> 追加のHTTP GET要求を発行
              ↓
  すべての素材を合成してレンダリングツリーを構築
              ↓
  画面への描画（ペイント処理）完了
```

現代のWebページでは、1つの画面を表示するために数十から数百回におよぶ追加のHTTPリクエストが発生するのが普通です。
リクエストごとにTCP接続とTLSハンドシェイクを繰り返していては画面表示が著しく遅延するため、同一コネクション上で複数のリクエストを並列処理できるHTTP/2やHTTP/3のマルチプレキシング技術が極めて重要な威力を発揮するわけです。

## 転送量と往復回数から待ちを考える

### 17 通信時間を足し合わせる

利用者がブラウザのリンクをクリックしてから画面全体の描画が完了するまでに体感する総所要時間は、単純な通信速度の割り算だけでは決まりません。
経路上の各ステップで発生する処理時間と遅延の総和として捉える視点が不可欠です。

```text
Webページの総表示時間
= DNS名前解決の所要時間
+ TCP 3ウェイハンドシェイクの往復時間（RTT）
+ TLSハンドシェイクの往復時間（1〜2 RTT）
+ HTTPリクエストがサーバへ届く片道遅延
+ サーバ内部での処理・DB問い合わせ時間
+ HTTPレスポンスの伝送時間（帯域幅に依存）
+ 追加アセット（CSS/画像/JS）の取得時間
+ ブラウザによる構文解析とレンダリング描画時間
```

例えば、物理的に遠く離れた海外サーバとの通信で往復遅延時間（RTT）が80ミリ秒かかるネットワーク回線を想定してみましょう。
TCPハンドシェイクで1往復（80ms）、TLSハンドシェイクで2往復（160ms）、HTTPリクエストとレスポンスの往復で1往復（80ms）を順番に消費するだけで、データ本体の転送時間をカウントする前の段階ですでに320ミリ秒（0.32秒）の待機時間が確定してしまいます。
帯域幅をどれほど太く増強したとしても、プロトコルの往復回数が多ければレスポンスの鈍重さは解消されないというネットワークの基本原則が浮き彫りになります。

### 18 転送時間を計算する

データサイズが10メガバイト（MB）の高精細画像ファイルを、実効通信速度40メガビット毎秒（Mbit/s）のブロードバンド回線を用いてダウンロードするケースを計算してみましょう。
計算にあたっては、1バイトが8ビットである点に留意し、単位をビットに統一して処理を進めます。

```text
総データ量 = 10 MB × 8 ビット/バイト
           = 80 Mbit

所要転送時間 = 総データ量 ÷ 実効通信速度
             = 80 Mbit ÷ 40 Mbit/s
             = 2.0 秒
```

理論計算上の転送時間はちょうど2秒となります。
ただし、現実の通信環境ではTCP/IPやEthernetのヘッダオーバーヘッド、パケット欠落に伴う輻輳制御での転送速度の一時低下、相手サーバのディスク読み出し遅延などが上乗せされるため、実測値は計算値よりやや長くなるのが通例です。
ネットワークの計算問題を解く際には、大文字の`B`（バイト）と小文字の`b`（ビット）の換算ミスを犯さない細心の注意が求められます。

### 19 帯域と遅延は別

ネットワークの性能を評価する際、通信事業者や利用者が最も混同しやすい概念が「帯域幅（スループット）」と「遅延（レイテンシ）」の違いです。

```text
帯域幅（Bandwidth）: 高速道路の車線数（単位時間あたりに通過できる車両の最大総数）
遅延（Latency）    : 車両が道路の始点から終点まで走り抜けるのに要する所要時間
```

車線数を10車線に拡張したとしても、自動車の制限速度が変わらなければ、1台の車が目的地へ到着するまでの時間は1秒たりとも短縮されません。
巨大な動画ファイルを一括ダウンロードするようなユースケースでは帯域幅の広さが支配的な影響を与えますが、Webページの閲覧やオンライントレード、オンラインゲームのように小さなパケットを数百回も往復させる用途では、遅延の短さこそが体感速度を決定づける生命線となります。

## 成功した段階から障害範囲を絞る

### 20 層ごとの障害の見え方

トラブルシューティングの現場において最も重要な鉄則は、「どこまで通信が成功し、どの境界から先で失敗しているか」を階層構造に沿って特定することです。

| 観察された具体的な症状 | 想定される主な障害原因と調査領域 |
|---|---|
| PCやネットワーク機器の電源ランプが点灯しない | 電源ケーブル抜け、ACアダプタ故障、PDUのブレーカー断 |
| LANポートのLink LEDが完全に消灯している | 物理ケーブルの断線、ポート不良、対向スイッチの停止 |
| Wi-FiのSSIDが表示されない、接続が拒絶される | 電波干渉、WPA認証パスワード相違、MACアドレス制限 |
| IPアドレスが`169.254.x.x`（APIPA）になっている | DHCPサーバの停止、スコープ内のIPアドレス枯渇、VLAN設定ミス |
| 同一LAN内のルータへpingが届かない | ARP解決失敗、サブネットマスク設定誤り、スイッチのポート障害 |
| ルータには届くがインターネット上のIPへ届かない | デフォルトゲートウェイのルーティング異常、WAN回線断、NAT不具合 |
| IP直打ちではWebが開くがURLのドメイン名では開かない | DNSサーバのアドレス設定誤り、DNSキャッシュ破損、DNS障害 |
| TCP 80は開くがTCP 443（HTTPS）だけ接続が拒否される | ファイアウォールのフィルタリング規則、Webサーバの443未リッスン |
| ブラウザに「安全な接続ではありません」と警告される | SSL/TLS証明書の有効期限切れ、ホスト名不一致、オレオレ証明書 |
| HTTPステータス`500 Internal Server Error`が返る | バックエンドプログラムの例外、データベースダウン、外部API遅延 |
| HTMLは届くがデザインが崩れて画像が一切表示されない | CDN障害、CSS/画像リソースへのパス誤り、CORS制約違反 |

表にまとめた症状は、あくまで調査の糸口を掴むための初期指標にすぎません。
先入観にとらわれて特定の原因を早合点することなく、パケットの通る経路を一段ずつテストして容疑範囲を絞り込む姿勢が不可欠です。

### 21 切分けの順序

障害対応において最も避けるべき愚行は、原因の仮説を立てないまま手当たり次第にルータを再起動し、状況を混迷させる対応です。
論理的で再現性のある障害切り分けを行うためには、規律ある手順を遵守しなければなりません。

```text
手順1: 現象の具体化（いつ、どの拠点の、誰の端末で、どのプロトコルが失敗したか）
手順2: 影響範囲の比較（1台だけの問題か、フロア全体か、全社的か）
手順3: 直近の変更点の洗い出し（機器のファームウェア更新、設定投入、物理工事の有無）
手順4: レイヤ順のテスト（L1の物理結線から順にL7のアプリケーションまで積み上げ試験）
手順5: ログの時系列照合（端末、スイッチ、ルータ、サーバのタイムスタンプを突き合わせ）
手順6: 暫定回避と恒久対策の分離（まずは業務復旧を最優先し、原因究明を別途進める）
手順7: 変更内容と結果の詳細記録（再発防止策の策定とドキュメントの更新）
```

「ネットが重い」「繋がらない」といった曖昧な報告を鵜呑みにせず、「社内LANから外部WebサーバへのHTTP GETに対して、どのルータまでパケットが届いているか」という観点へ具体性を高めて特定する取り組みが、プロの切り分け手法といえるでしょう。

### 22 1台と全台を比べる

影響範囲の広さを比較観察することは、障害箇所の物理的・論理的なレイヤを一撃で特定するための強力なアプローチとなります。

トラブルを訴えているのが社内で「特定の1台のPCだけ」であるならば、背後の共通インフラを疑う前に、その端末自身のLANケーブル、無線NICの不調、IP設定の手動誤入力、ローカルのOSファイアウォール、あるいはブラウザのキャッシュを調査するのが最短ルートです。
これに対し、「同じフロアの全端末」が一斉に通信不能に陥ったのであれば、そのフロアの島ハブ、アクセスポイント、フロア集約L2スイッチ、あるいは所属するVLANのDHCPスコープに原因がある可能性が極めて濃厚となります。
全社規模のトラブルであれば、対外WAN回線、コアルータ、全社共通DNS、あるいはクラウド側の認証プロバイダを調査対象に据えるべきです。

### 23 IP直指定と名前指定を比べる

ネットワークの疎通確認において、DNSに起因するトラブルを瞬時にあぶり出す古典的かつ強力な手法が「名前指定」と「IPアドレス直指定」の比較実験です。

例えば、ブラウザで`https://www.example.jp/`へアクセスするとエラーになるものの、ターミナルから`ping 203.0.113.20`を実行したりブラウザのアドレスバーに直接IPアドレスを打ち込んだりすると応答が返ってくるケースを想定します。
この比較が成立した段階で、物理ケーブル、L2スイッチ、ルータのルーティングテーブル、WAN回線、そして相手先サーバの物理生存に至るまでの全インフラが正常に稼働している事実が確定します。
疑うべき領域はDNSクライアントの設定、指定されたDNSリゾルバの稼働状況、あるいはドメインのゾーン設定だけに絞り込まれるのです。

### 24 pingだけで正常とはいえない

ネットワークエンジニアが最初に実行しがちなコマンドが`ping`ですが、pingの成功をもってシステム全体の健全性を証明できたと過信することは極めて危険です。

pingはネットワーク層のプロトコルである**ICMP**（Internet Control Message Protocol）のエコー要求とエコー応答を往復させているにすぎません。
相手のルータやサーバからpingの応答があったとしても、それは「IPパケットが往復できた」という事実を示しているだけであり、Webサーバのプロセス（nginxやApache）がポート443でリッスンしているか、TLS証明書が正しくインストールされているか、背後のデータベースが生きているかについては何一つ保証してくれません。
さらに、企業の公開サーバではセキュリティ上の理由からICMPの応答を意図的に遮断しているケースも多いため、pingが通らないからといってサーバがダウンしていると決めつけることも誤りです。

### 25 パケット損失の影響

ネットワーク回線上でパケットが何らかの原因（バッファあふれ、ノイズ、電波微弱）で廃棄される現象が**パケット損失**（パケットロス）です。

TCP通信においてパケット損失が発生すると、送信側はACKの不達や重複ACKの受信によってパケット消失を検知し、消失したセグメントの再送処理を実行します。
その間、受信側のアプリケーションはデータを受け取れずに待たされるだけでなく、TCPの輻輳制御アルゴリズムが発動して送信ウィンドウサイズが強制的に縮小され、通信速度の急激な低下を招く仕組みです。
わずか1%程度のパケット損失であっても、Webブラウジングの体感速度が数倍遅くなるのはこの理由に起因します。
音声通話やライブ配信のようなリアルタイムUDP通信では、失われたパケットの再送を待つ余裕がないため、即座に音声の途切れや映像の激しいブロックノイズとして顕在化するのです。

### 26 MTUの問題

ネットワークインタフェースが一度に送信できるIPパケットの最大バイト長を**MTU**（Maximum Transmission Unit）と呼び、一般的なEthernet環境では1,500バイトが規定値となっています。

ここで、社内LANとクラウドの間をIPsecやGREなどのVPNトンネルで相互接続している環境を想定してみましょう。
VPNは元のIPパケットの外側にさらに新しい暗号化ヘッダやIPヘッダ（カプセル化ヘッダ）を包み込んで送信するため、その分だけ内部パケットに使える実効サイズが目減りします。
もしパケットヘッダに「パケット分割禁止（DFビット）」がセットされた状態でルータの許容MTUを超える巨大パケットが届くと、ルータはそのパケットを中継できずに破棄し、送信元へICMP Fragmentation Neededを返送する仕様です。
このICMPがファイアウォールでブロックされていると、小さなpingは通るのに大きなWeb通信だけが途中で固まるという「パケットブラックホール」現象が発生するため、ルータでのMSSクランプ設定によるTCPセグメントサイズの自動縮小調整が極めて重要な対策となります。

### 27 セキュリティ装置の正常な拒否

ファイアウォールやUTMが通信パケットを遮断した際、運用現場ではしばしば「セキュリティ機器が故障した」と早合点される場面が散見されます。
しかし、大半の事象は機器の故障というよりも、管理者が定義したセキュリティポリシーに従って未許可の不正なトラフィックを忠実に破棄した正常動作にほかなりません。

トラブルシューティングを行う際は、遮断された通信が真に正当な業務トラフィックであるかを確認した上で、送信元IP、宛先IP、宛先ポート番号、プロトコル種別を正確に特定し、セキュリティ機器のドロップログと突き合わせる作業が不可欠です。
障害を急いで解決したい一心で「一時的に全ポートを開放する（Any Any Permit）」といった短絡的な設定変更を行うことは、組織全体を即座に破滅的なサイバー攻撃の危機に晒す行為であり、厳に慎むべきでしょう。

## 用途と冗長化の設計へ広げる

### 28 メールも同じ層を通る

Web閲覧だけでなく、電子メールの送受信もまた、まったく同一のTCP/IP階層アーキテクチャの上で成り立っています。

```text
メールソフトで送信ボタンを押下
  ↓ SMTP over TLS（TCP 465 / 587）で自社の送信メールサーバへ転送
送信メールサーバがDNSへ問い合わせ
  ↓ DNSのMXレコードを参照して宛先ドメインの受信メールサーバを特定
送信メールサーバから相手先メールサーバへ
  ↓ インターネット経由でSMTP配送（TCP 25）
宛先メールサーバのローカルスプールへ格納
  ↓ 受信者のメールボックスへ安全に保存
受信者がスマートフォンやPCで閲覧
  ↓ IMAP4 over TLS（TCP 993）またはPOP3 over TLS（TCP 995）で同期取得
```

メーラーの画面に「送信完了」と表示されたとしても、それは単に「手元のPCから自社の送信メールサーバへの受け渡しが完了した」ことを意味しているにすぎません。
宛先サーバのDNS名前解決の失敗、相手先ファイアウォールによるブロック、あるいは迷惑メールフィルタによる自動隔離など、相手の手元に届くまでの間には多重の関門が存在します。

### 29 IoTも同じ層を通る

山間部の土壌センサや工場の温度計といったIoTデバイスであっても、基本となる階層的な考え方はWebやメールと何ら変わりません。

```text
温度センサ素子による物理量サンプリング
  ↓ マイコンによるA/D変換
LPWA / Wi-Fi HaLowなどの省電力無線送信
  ↓ 現場のIoTゲートウェイで電波を受信
IPパケット化とLTE閉域網経由の中継
  ↓ クラウド上のMQTTブローカへPublish（TCP 8883 / TLS）
時系列データベースへの書き込み
  ↓ 監視ダッシュボードへのリアルタイム反映・異常アラート発報
```

「工場の監視ダッシュボードに温度が表示されない」という障害が発生した際、センサの電池切れ、現場の電波障害、ゲートウェイのハングアップ、クラウドのDNS名前解決エラー、MQTTの認証トークン期限切れ、データベースのディスクフルなど、切り分けるべきポイントはWebシステムと完全に地続きの構造を持っています。

### 30 冗長化は経路図だけで確かめない

システムの高可用性を実現するために、ネットワーク構成図の上で回線を2系統引き、ルータを2台並べて冗長化したつもりになっていても、物理的な実態を精査すると単一障害点（SPOF）が残存しているケースが後を絶ちません。

```text
【論理設計図の見かけ】
社内ネットワーク ──┬── 回線キャリアA（メイン回線） ──┬── クラウド
                    └── 回線キャリアB（バックアップ回線） ──┘

【物理的な現場の実態】
社内ネットワーク ──┬── 引き込み電柱（同一の電柱） ──┬── 局舎（同一のNTT収容ビル） ──> クラウド
                    └── 地下配管（同一の管路） ───┘
```

異なる通信事業者と契約していたとしても、電柱から建物内へ入る物理的な地下配管が同一であったり、ビルの電源系統や受電盤を共有していたりすれば、道路工事によるショベルカーの配管誤切断や局舎の停電によって両回線が同時に壊滅します。
真の冗長性を確保するためには、論理的なルーティング設計にとどまらず、物理的な敷設ルート、電源設備、保守ベンダーの体制に至るまで依存関係を徹底的に洗い出し、実際に主回線を物理的に引っこ抜いて通信が数秒以内に切り替わるかを実地検証する入念な確認が不可欠です。

### 31 設計問題を解く視点

応用情報技術者試験や実務の要件定義においてネットワーク設計の課題に直面した際は、最新のバズワードや特定の製品名に目を奪われる前に、要求仕様を冷静に因果関係へと分解する思考が求められます。

```text
・通信の主体と客体: 誰が、どこから、どこへ向かってデータを送受信するのか
・トラフィックの量と質: 1回のデータサイズ、発生頻度、ピーク時のスループット
・要求される通信品質: 許容できる往復遅延時間、ジッタ、パケット損失への耐性
・セキュリティと機密性: データの暗号化、端末の相互認証、通信経路の閉域性
・障害耐性と稼働率: 許容できるダウンタイム（RTO）、目標復旧時点（RPO）
・制約条件とコスト: 導入予算、月額回線費用、現場の給電環境、運用管理者のスキル
```

「高速だからとりあえず5G」「最新だからとりあえずクラウド」といった思考停止を排し、個々のビジネス要件に対してなぜそのプロトコルや伝送媒体を選択するのかを1対1の論理で説明できる能力こそが、アーキテクトに求められる最大の資質です。

### 32 第7章の全体地図

本章で学んできた膨大なネットワーク技術は、すべて「人間の目的」を「物理世界の伝送媒体」へと変換し、再び目的へと復元するための壮大な階層構造の中に美しく位置づけられます。

```text
【人間の目的】
Web閲覧、オンライン会議、メール送受信、ファイル共有、IoT機器の遠隔監視
                            │
                            ▼
【アプリケーション層】 HTTP, HTTPS, SMTP, POP3, IMAP4, DNS, DHCP, MQTT, CoAP
利用者の目的に応じたメッセージフォーマットを規定し、サービスを提供する
                            │
                            ▼
【トランスポート層】   TCP, UDP, ポート番号
プロセス間の論理通信路を識別し、信頼性の高い再送制御やリアルタイム伝送を担う
                            │
                            ▼
【ネットワーク層】     IP（IPv4/IPv6）, ICMP, ARP, ルーティングプロトコル（OSPF/BGP）
異種ネットワークを相互接続し、IPアドレスに基づいてパケットを世界中へ届ける
                            │
                            ▼
【データリンク層】     Ethernet, 無線LAN（Wi-Fi）, VLAN, MACアドレス
同一通信媒体で直結された隣接機器間でフレームを確実に受け渡す
                            │
                            ▼
【物理層】             ツイストペアケーブル, 光ファイバ, 電波, 電圧・光・位相変調
デジタルデータを物理的な電気信号、光パルス、電磁波へと変換して空間を伝搬させる
```

pingが成功したとしても、それが証明するのは主にネットワーク層までの片道・往復疎通の一部にすぎず、DNSの名前解決、TCPポートの開放、TLS証明書の正当性、そしてWebアプリケーションの正常動作までは何一つ保証しません。
逆に、ブラウザに「404 Not Found」というエラー画面が返ってきたならば、最下層の物理ケーブルから最上位のWebサーバプロセスに至るまでの膨大な通信ステップが見事に成立し、ただ目的のファイルがサーバ上に存在しなかったことだけを示しています。

画面が白いまま固まるというたった1つのトラブルを前にしたとき、この全体地図を脳内に展開し、最後に成功した境界から一歩ずつパケットの足跡をたどっていく姿勢こそが、ネットワークという巨大な世界を完全に掌握するための最も確実な道標となるのです。
