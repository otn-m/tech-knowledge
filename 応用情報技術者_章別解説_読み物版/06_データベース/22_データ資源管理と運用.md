# 第6章 第22話 データ資源管理と運用

高性能なDBMSを導入しても、「売上」という項目の意味が部署ごとに違い、誰が直すか分からなければ、正しい判断には使えません。

データを組織の資源として、意味、品質、所在、権限、寿命まで管理することが**データ資源管理**です。

データ辞書へ売上の定義を1回登録すれば、意味の食い違いはなくなるように思えるかもしれません。
しかし、返品の扱いが変わったとき、誰が定義を承認し、どの帳票を再計算するか決まっていなければ、説明は古いまま残ります。
定義、責任者、変換経路、変更手順を一緒に管理します。

## 意味と技術情報を結び付ける

### 1 データ管理の対象

管理するのはデータそのものだけではありません。
表、列、ファイルなどの構造と、業務上の意味や計算式を管理します。
作成元と変換経路、所有者と管理責任者、品質と更新時刻も対象です。

機密区分と権限、保存場所、バックアップ、期限を把握し、そのデータを使う画面、帳票、プログラムも管理します。

### 2 メタデータを三種類で見る

#### 2.1 業務メタデータ

項目の意味、目的、責任部門、同義語、機密区分が業務メタデータです。

#### 2.2 技術メタデータ

意味を実装へ結び付けるDB名、表名、列型、主キー、ファイル形式、API、ジョブが技術メタデータです。

#### 2.3 運用メタデータ

利用中の状態を示す更新時刻、件数、失敗記録、品質結果、利用頻度が運用メタデータです。

3つを結び付けると、「この売上列を変えるとどの報告に影響するか」を調べられます。

### 3 データディクショナリ

データ項目、型、意味、制約、関係を体系的に記録した辞書が**データディクショナリ**、データ辞書です。

DBMSがシステムカタログとして持つ定義情報と、人が合意する業務用語辞書があります。

```text
項目標準名: 税込請求額
定義:       商品・送料の税込確定請求額。取消分を除く
型・単位:   DECIMAL、円
作成元:     請求確定処理
責任者:     経理部
```

## 辞書と成果物を組織で共有する

### 4 IRDS

情報資源に関する辞書情報を体系的に管理する仕組みが**IRDS**、Information Resource Dictionary System、情報資源辞書システムです。

データの名称だけでなく、処理、システム、組織との関係を管理し、開発、保守、影響調査を支えます。

### 5 リポジトリ

ソフトウェアの開発や保守に関する、さまざまな成果物や情報を一元管理するものが**リポジトリ**です。

要求と設計モデル、データ定義、プログラム構成、テスト情報、変更履歴などを集めます。
画面や帳票との対応も管理します。

単にファイルを置くフォルダではなく、版、関係、検索、権限、変更を管理します。

### 6 データカタログ

組織内にどのデータがあり、誰が所有し、どう利用できるかを検索する仕組みがデータカタログです。

辞書、技術メタデータ、品質、利用例、注意事項をまとめます。
カタログに載っていても、利用権限や目的の承認が自動で得られるわけではありません。

## データの出所と品質に責任を持つ

### 7 データリネージ

項目の意味が分かっても、その値がどの元データから、どの変換を経て届いたか分からなければ誤りの影響範囲を追えません。
入力から帳票までの流れを記録します。

データがどこから来て、どの変換を通り、どの報告に出たかという系譜が**データリネージ**です。

```text
販売システム.amount
  → 税・通貨変換
  → DWH.sales_amount_yen
  → 月次売上ダッシュボード
```

数字の説明、誤りの影響範囲、変更前の調査に使います。

### 8 データ品質

データ品質は、複数の観点に分けて確かめます。
現実や正しい元データと一致することが**正確性**、必要な項目や件数が欠けないことが**完全性**です。
システム間や項目間で矛盾しない性質は、**一貫性**と呼びます。

必要な時点までに新しい状態であることが**適時性**、重複した実体がないことが**一意性**です。
型、範囲、規則を満たすことは**妥当性**として確認します。

100%を漠然と求めず、重要項目ごとに測定式と許容値を決めます。

例えば顧客表1,000行について、必須メールアドレスが950行に入り、そのうち形式規則を満たすものが930行、重複を除いた顧客実体が980件なら、分母を明示して次のように測ります。

```text
完全性 = 必須値あり行数 / 対象行数 = 950 / 1,000 = 95%
妥当性 = 形式妥当行数 / 値あり行数 = 930 / 950 ≈ 97.9%
一意性 = 一意な実体数 / 対象行数 = 980 / 1,000 = 98%
```

妥当性の分母を全行にする定義もあり得ます。
指標名だけを比較せず、対象、分子、分母、測定時刻をデータ品質規則として固定します。
正確性は信頼できる外部の正解データと一致した件数を分子にし、正解が得られた標本数を分母にします。

### 9 マスターデータとリファレンスデータ

品質と意味をそろえる対象には、複数の業務で共有する基本データもあります。
顧客、商品、組織などの基本対象がマスターデータです。

国コード、通貨コード、区分一覧など、値の意味を統一する参照用データが**リファレンスデータ**です。
これを集めたものを**リファレンスデータベース**と呼びます。

信頼できる事実や関係を知識として蓄えるものを**ファクトデータベース**と呼ぶ文脈もあります。

### 10 データオーナーとスチュワード

品質指標を測るだけでは、異常値を誰が判断し修正するかは決まりません。
業務上の責任と日々の管理作業を役割として割り当てます。

データの利用方針、品質、権限に最終責任を持つ役割をデータオーナーと呼びます。

定義調整、品質監視、問い合わせ対応を日常的に行う役割をデータスチュワードと呼びます。

IT部門だけでは、売上、顧客、医療記録の業務上の意味を決められません。
業務部門と協力します。

## サービスと保存層の保証を確認する

### 11 データベースサービス

組織内やクラウドで、DBの作成、バックアップ、監視、更新などを共通サービスとして提供するものを**データベースサービス**と呼びます。

利用開始を速め、標準化できます。
一方で、提供者がどこまで管理するか、利用者がバックアップの復元を試せるかを確認します。
地域、暗号鍵、監査を選べるか、障害時の責任と退出や移行の方法は何かも確認します。
「管理サービスだから運用責任がゼロ」ではありません。

### 12 分散ファイルシステム

大量ファイルを複数装置へ分割し複製できても、関係表の主キーやトランザクションまで自動的に得られるわけではありません。
保存層が提供する保証と、その上のDBや処理エンジンが提供する保証を分けます。

多数のコンピュータの保存装置を協力させ、大きなファイルや大量データを保存するものが**分散ファイルシステム**です。

公式シラバスでは、**HDFS**、Hadoop Distributed File System、**Ceph**、**GlusterFS**が例に挙げられています。

データを複数ノードに分割して複製し、障害に対応します。
小さなファイルが大量にある場合、メタデータ、整合性、再複製、ネットワークが課題になります。

DBMSのトランザクション、索引、SQLを自動で提供するものとは限りません。
その上に処理エンジンを置きます。

### 13 HDFSの基本像

大きなファイルをブロックに分け、複数データノードに複製して保存します。
メタデータを管理する役割が、ファイル名とブロック位置を把握します。

大きな連続読取りや分散処理に向けた設計で、低遅延の小さなランダム更新をRDBのように行う目的とは違います。

## 定義と変更を管理する

### 14 データベース作成時の定義

DBの作成時には、方式に応じて保存する記録とアクセス方法を定義します。
1件のレコードが持つ項目、型、長さを**レコード形式**と呼びます。
どのキーで配置や索引を行うかを示すのが**キー順**です。

階層型や網型でどの記録を結ぶかは、**親子関係**として定めます。
親が存在しなければ子を持てないなどの規則が、**存在制約**です。
索引やインバーテッドファイル、権限、保存領域、ログも定義します。

### 15 階層型と網型での物理的な用語

階層型や網型のDBでは、親子の集合や、記録を置く順序と方式を明示してたどる設計があります。
親とそれに属する子のまとまりが**親子集合**です。
子をどのキー順などで並べるかを示すのが**親子集合順序**、記録を保存領域へどの方式で配置するかを示すのが**配置モード**です。

関係DBでは物理的な経路を利用者から隠す考え方が強いものの、物理設計が不要になるわけではありません。

### 16 変更管理

表の列を変更すると、その表以外にも次のような影響が及びます。

```text
表定義
ビュー
API
ETL
帳票
分析指標
バックアップ・移行
権限
```

リポジトリやリネージで影響を調べ、版、適用順、戻し方を管理します。

### 17 スキーマ変更を安全に行う

稼働中のアプリと新旧の定義が一時的に共存できるよう、段階的に移行する場合があります。
まず互換性のある新列を追加し、新旧の両方へ書き込みながら、過去の行も埋めます。
その後、読取りを新列へ切り替え、古い列への書込みを止めます。
動作を観測してから古い列を削除します。

一度に変更すると、旧アプリが停止する危険があります。

## 利用中の状態とデータの寿命を管理する

### 18 運用監視

利用可能性と接続数、応答時間、処理量、失敗率を監視します。
CPU、主記憶、物理I/Oに加え、ロック待ち、デッドロック、長時間トランザクションも調べます。

ログと保存容量、複製遅延、バックアップの成否と復元試験も監視対象です。
データ品質とETLの遅延、強い権限と異常操作も確認します。
1つの閾値だけで判断せず、通常値、増加傾向、業務時刻と合わせて見ます。

### 19 再編成と保守

データが増減すると、索引やページが断片化し、統計が古くなります。
必要に応じて統計を更新し、索引の再構築や再編成を行います。
古いデータのアーカイブ、表分割の追加、ソフトウェアの更新、不要な権限やアカウントの削除も行います。

保守処理自体も負荷、ログ、複製遅延、ロックを生むため、時間帯、中断方法、戻し方を準備します。

### 20 容量の傾向を監視する

現在70%だから安全とは限りません。

```text
現在空き: 300GB
一日増加: 20GB
保持可能日数 = 300GB ÷ (20GB/日)
             = (300÷20) 日
             = 15日
```

GBが約分され、分母の「/日」が逆数になって結果の単位が日になります。
実運用では急増と安全余裕を見込み、15日になる前に増設、削除、アーカイブを完了させます。

ログの急増、異常な一時領域、バックアップ失敗も見ます。
必要日までに装置の増設やデータの分割、削除の方針を準備します。

### 21 保存と廃棄

長く保存するほど、データを分析や監査に使える一方、漏えいの影響、費用、古いデータの誤った利用も増えます。
法律や契約で必要な期間、業務上の再現期間、本人からの削除要求を、データ分類ごとに確認します。
バックアップや複製からの削除、集計や匿名化後の利用も、分類ごとに決めます。

### 22 構造化、半構造化、非構造化データを一緒に管理する

注文表、JSONイベント、PDF契約書、音声記録が同じ顧客に関係することがあります。

保存方式が違っても、共通ID、メタデータ、権限、保存期限、リネージで関連付けます。
ファイルをDBに入れただけでは、検索や管理が可能になるわけではありません。

### 23 データを使う前の確認

カタログでデータセットを見つけても、表名だけでは判断に使えません。
粒度、単位、欠損、更新時刻、変換方法を確認して、目的に合う値かを判定します。

分析者は1行の粒度と、項目の定義や単位、対象期間と更新時刻を確認します。
欠損、重複、除外条件、元システムからの変換も調べます。
利用目的と権限、結果を公開してよい範囲も確認します。

表名と列名だけで意味を推測しません。

「売上」という列が見つかっても、受注額か入金額か、返品と税を含むか、いつ更新されたかが分からなければ比較できません。
データ辞書で意味を定め、オーナーとスチュワードが変更を管理し、リネージで影響先を追える状態にします。
DBMSの性能ではなく、この責任と履歴までそろって初めて、同じ売上を組織で再利用できます。
