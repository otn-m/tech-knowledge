# 第6章 第10話 SELECTと検索条件

検索条件を増やせば、欲しい行を正確に絞り込めるように思えます。
しかし、`AND`と`OR`の優先順を誤れば別の集合になり、NULLを普通の値として比較すれば、条件に合うとも合わないとも確定しない行が生まれます。
条件の数より、論理的な評価結果を追う必要があります。

以降の例では、次の表を使います。

```text
books
book_id | title          | category | price | stock | published_on
1       | はじめての星   | 科学     | 1200  | 3     | 2025-04-01
2       | 海辺の地図     | 小説     | 1800  | 0     | 2024-09-10
3       | 雲のしくみ     | 科学     | 1500  | 2     | NULL
4       | 小さな料理     | 料理     | 900   | 5     | 2026-01-20
```

## 取り出す行と列を決める

### 1 すべての列を読む

```sql
SELECT *
FROM books;
```

`*`はすべての列を表します。
学習や確認には便利ですが、アプリでは必要な列を明示します。
列が追加されると取得結果が変わるほか、容量の大きな列まで読むと通信量が増えます。
不要な個人情報まで取得したり、同名の列があって扱いにくくなったりする点にも注意が必要です。

### 2 列を選ぶ

すべての列を取得する代わりに、必要な列の名前を並べます。

```sql
SELECT book_id, title, price
FROM books;
```

列を取り出すこの考え方は、関係代数の射影に対応します。

### 3 WHEREで行を絞る

列を選ぶだけでは、表のどの行を読むかは変わりません。
`WHERE`に条件を指定すると、その条件が真になる行だけを残せます。

```sql
SELECT book_id, title
FROM books
WHERE stock > 0;
```

これは関係代数の選択に対応します。

### 4 比較演算子

価格の大小などを条件にするには、比較演算子を使います。

```text
=   等しい
<>  等しくない
<   より小さい
<=  以下
>   より大きい
>=  以上
```

製品によっては`!=`も使えますが、標準的な`<>`を読めるようにします。

```sql
WHERE price >= 1000
```

この条件は価格が1000以上の行を残し、1000も含みます。

## 条件の組合せと範囲を表す

### 5 AND、OR、NOT

カテゴリが科学で、かつ在庫がある行を求めるなら、`AND`で条件を結びます。

```sql
WHERE category = '科学'
  AND stock > 0
```

科学と料理のいずれかを求めるなら、`OR`を使います。

```sql
WHERE category = '科学'
   OR category = '料理'
```

`AND`では両方の条件、`OR`では少なくとも一方の条件を満たす行が対象です。
`NOT`は条件を否定します。

### 6 括弧で優先順を明示する

`AND`と`OR`を組み合わせるときには、条件のまとまりに注意します。

```sql
WHERE category = '科学'
   OR category = '料理'
  AND stock > 0
```

この式では、人が意図したまとまりと評価結果が異なる可能性があります。
演算の優先順位に頼らず、括弧でまとまりを明示します。

```sql
WHERE (category = '科学' OR category = '料理')
  AND stock > 0
```

### 7 BETWEEN

価格などの範囲は、`BETWEEN`で表せます。

```sql
WHERE price BETWEEN 1000 AND 1600
```

一般に両端を含み、`price >= 1000 AND price <= 1600`と同じ考え方です。

日時の範囲では、上端にどの時刻を指定するかに注意します。
「7月14日の全時刻」を表すつもりで、日付時刻列に`BETWEEN '2026-07-14 00:00' AND '2026-07-14 23:59'`を指定すると、秒以下の部分を落とす危険があります。
翌日の開始時刻未満とする方法を検討します。

### 8 IN

複数の候補のいずれかと等しい条件は、`IN`で表せます。

```sql
WHERE category IN ('科学', '料理')
```

同じ列を比較する多数の`OR`を、読みやすくまとめられます。

### 9 LIKEとパターン文字列

書名の一部で検索するなど、文字列のパターンを調べるには`LIKE`を使います。

```sql
WHERE title LIKE 'はじめて%'
```

多くのSQLでは、`%`が0文字以上の任意の文字列、`_`が任意の1文字を表します。

`%星%`のように先頭も不定のパターンでは、通常の先頭順の索引を効率よく使いにくい場合があります。
全文検索用の転置インデックスなどを検討します。

## NULLを含む条件を評価する

### 10 NULLを調べる

価格やカテゴリが分かっている行なら、比較結果は真か偽になります。
値が不明であるNULLを含むと、比較結果にUNKNOWNが加わります。
普通の値と同じように比較しても、条件に合うかどうかを確定できません。

```sql
-- 意図どおりにならない
WHERE published_on = NULL
```

NULLであることを調べるには、`IS NULL`を使います。

```sql
WHERE published_on IS NULL
```

NULLでない行を調べるには、`IS NOT NULL`を使います。

### 11 三値論理

SQLの条件結果には、真、偽に加えて**不明**があります。
`published_on`がNULLの行で、次の条件を評価する場合を考えます。

```sql
published_on < DATE '2025-01-01'
```

出版日が分からなければ、指定日より早いとも遅いとも判断できません。
結果は不明です。
`WHERE`は真の行だけを残し、偽と不明の行は残しません。

`NOT (published_on < ...)`としても、不明を否定した結果は不明のままです。
NULLの行が自動的に検索結果へ入るわけではありません。

### 12 NOT INとNULL

候補に含まれない行を求める`NOT IN`でも、NULLが結果に影響します。

```sql
WHERE book_id NOT IN (2, 3)
```

この例のように候補が明示されていれば分かりやすい条件です。
しかし、候補を副問合せから取り出し、その中にNULLがあると、「どの候補とも違う」と確定できません。
予想外に行が出なくなることがあります。
NULLが含まれる可能性を除くか、`NOT EXISTS`を使う設計を検討します。

## 結果の値と並びを整える

### 13 DISTINCT

検索結果の重複する行を1つにまとめるには、`DISTINCT`を使います。

```sql
SELECT DISTINCT category
FROM books;
```

カテゴリの結果は科学、小説、料理です。

ただし、`DISTINCT`を付けると「なぜ重複したか」が見えなくなることもあります。
結合条件の誤りや表設計の問題がないかを先に確認します。
重複除去には、並べ替えやハッシュなどの処理費用もかかります。

### 14 列に別名を付ける

取得する列には、`AS`で別名を付けられます。

```sql
SELECT title AS book_title,
       price * stock AS inventory_value
FROM books;
```

表に付ける別名は、相関名とも呼びます。
この例の計算列`inventory_value`は保存列とは限らず、問合せ時に計算した結果です。

### 15 四則演算とNULL

数値列を使って、検索時に計算することもできます。

```sql
SELECT price * stock
FROM books;
```

一般に、計算する値にNULLが1つ混ざると、結果もNULLです。
「分からない値を足しても結果は分からない」と考えます。
NULLを0に置き換える関数もありますが、0と不明を同じものとして扱ってよい業務かを確認します。

### 16 CASE式

条件によって返す値を変えるには、`CASE`式を使います。

```sql
SELECT title,
       CASE
         WHEN stock = 0 THEN '在庫なし'
         WHEN stock <= 2 THEN '残りわずか'
         ELSE '在庫あり'
       END AS stock_status
FROM books;
```

上から順に調べ、最初に当てはまった結果を使うため、条件の順番が重要です。

### 17 ORDER BY

返す値が決まっても、そのままでは行の順序は保証されません。
結果の並びは`ORDER BY`で指定します。

```sql
SELECT title, price
FROM books
ORDER BY price ASC, title ASC;
```

`ASC`は小さい方からの昇順、`DESC`は大きい方からの降順です。
この例で価格が同じ行は、書名順に並びます。
完全に再現できる順番が必要なら、最後に主キーなど一意になる列を加えます。

`ORDER BY`がなければ、保存順や主キー順に見える結果でも、その順序は保証されません。

### 18 結果件数を制限する

上位10件や次の20件など、返す件数を制限する構文もあります。
標準的な`FETCH FIRST`や製品ごとの`LIMIT`など、表記は異なります。

ページ番号が深くなるほど多くの行を読み飛ばす方式は、遅くなる場合があります。
最後に見た一意のキーより後を取得する方式もあります。

## 行集合が作られる順に条件を確かめる

### 19 論理的な評価順

SQL文は`SELECT`から書き始めますが、結果を考える順序は記述順と異なります。
元の行集合を作り、条件で絞り、集団に分けた後で、表示する列や集約結果が決まります。

```text
FROM       元になる行集合を作る
WHERE      行を絞る
GROUP BY   集団へ分ける
HAVING     集団を絞る
SELECT     出す列・式を作る
ORDER BY   並べる
```

まずは`FROM → WHERE → SELECT → ORDER BY`の順で結果をたどります。
集計を加える場合の考え方は第12話で扱います。

### 20 条件式で列へ関数をかける費用

条件の意味が同じでも、書き方によって処理費用が変わる場合があります。

```sql
WHERE EXTRACT(YEAR FROM published_on) = 2026
```

この式では各行の列を計算してから比較するため、普通の`published_on`索引を使いにくい場合があります。

```sql
WHERE published_on >= DATE '2026-01-01'
  AND published_on <  DATE '2027-01-01'
```

このような範囲条件なら、索引を使いやすい場合があります。
結果の正しさを保ち、実行計画で確認します。

科学または料理という条件に価格範囲を加えるときは、括弧を省くと意図しないカテゴリまで残る場合があります。
出版日がNULLの行は、通常の比較結果がUNKNOWNとなり、真の行だけを残す`WHERE`から除かれます。
条件を日本語で確認し、括弧、NULL、論理的な評価順を、求める行集合と対応させます。
