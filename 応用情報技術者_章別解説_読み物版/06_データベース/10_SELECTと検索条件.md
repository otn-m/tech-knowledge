# 第6章 第10話 SELECTと検索条件

検索条件の記述を増やせば、目的の行を的確に絞り込めるように感じられます。
しかし`AND`と`OR`の優先順位を取り違えれば意図しない集合が返され、NULLを通常の値と同様に比較すれば、合致とも不一致とも断定できない行が生じてしまうのがデータベースの現実です。
条件式の数を機械的に増やすにとどまらず、背後で成立する論理的な評価結果を厳密に追尾しなければなりません。

以降の例では、次の表を使います。

```text
books
book_id | title          | category | price | stock | published_on
1       | はじめての星   | 科学     | 1200  | 3     | 2025-04-01
2       | 海辺の地図     | 小説     | 1800  | 0     | 2024-09-10
3       | 雲のしくみ     | 科学     | 1500  | 2     | NULL
4       | 小さな料理     | 料理     | 900   | 5     | 2026-01-20
```

## 取り出す行と列を決める

### 1 すべての列を読む

```sql
SELECT *
FROM books;
```

アスタリスク`*`はすべての列を一括取得する指定です。
動作確認や学習の場面では手軽ですが、本番アプリケーションの実装では取得する列名を明示的に列挙すべきです。
将来的に表へ新しい列が追加された際に取得データ構造が狂うリスクがあり、大容量列の無駄な転送によってネットワーク帯域を浪費しかねません。
業務上不要な機密情報を不用意に読み出してしまう事故を防ぐためにも、列の明示指定が基本となります。

### 2 列を選ぶ

すべての列を取得する代わりに、必要な列の名前をカンマ区切りで並べます。

```sql
SELECT book_id, title, price
FROM books;
```

必要な列のみを垂直方向に切り出すこの操作は、関係代数における射影演算に対応する考え方です。

### 3 WHEREで行を絞る

列を選択しただけでは、表に含まれる全レコードが読み出されてしまいます。
`WHERE`句に条件式を指定すると、その条件が真（TRUE）と評価される行のみを抽出できます。

```sql
SELECT book_id, title
FROM books
WHERE stock > 0;
```

この行の絞り込み処理が、関係代数における選択演算に対応する操作です。

### 4 比較演算子

価格の大小や一致判定を記述する際は、各種の比較演算子を活用します。

```text
=   等しい
<>  等しくない
<   より小さい
<=  以下
>   より大きい
>=  以上
```

DBMS製品によっては`!=`もサポートされますが、標準SQLに準拠した`<>`の記法を確実に理解しておくべきです。

```sql
WHERE price >= 1000
```

この条件式は価格が1000以上の行を抽出対象とし、境界値である1000自身も含める判定となります。

## 条件の組合せと範囲を表す

### 5 AND、OR、NOT

カテゴリが科学で、かつ在庫が存在する行を求めるなら、`AND`演算子で2つの条件を結ぶ設計です。

```sql
WHERE category = '科学'
  AND stock > 0
```

科学または料理のいずれかに該当する書籍を求めるなら、`OR`演算子を使用します。

```sql
WHERE category = '科学'
   OR category = '料理'
```

`AND`は双方の条件を満たす論理積を、`OR`は少なくとも一方を満たす論理和を表す演算子です。
一方で`NOT`演算子は、条件式の真偽判定を論理反転させる役割を担います。

### 6 括弧で優先順を明示する

`AND`と`OR`を混在させるときは、論理式の結合優先順位に細心の注意を払わなければなりません。

```sql
WHERE category = '科学'
   OR category = '料理'
  AND stock > 0
```

この記述では、人間が頭の中で意図した条件のまとまりと、構文解析器による評価結果が食い違う危険を孕んでいます。
演算子の優先順位に過度に依存せず、丸括弧を用いて評価のグループを明示的に括る設計が不可欠です。

```sql
WHERE (category = '科学' OR category = '料理')
  AND stock > 0
```

### 7 BETWEEN

数値や日時の範囲を指定したい場合は、`BETWEEN`述語を利用できます。

```sql
WHERE price BETWEEN 1000 AND 1600
```

これは`price >= 1000 AND price <= 1600`と論理的に同等であり、両端の境界値を含みます。

日時データの範囲検索を行う際は、終了日時の境界をどのように指定するかに配慮が必要です。
「7月14日の全時間帯」を抽出する目的で、日時列に`BETWEEN '2026-07-14 00:00' AND '2026-07-14 23:59'`を指定すると、23時59分以降の秒やミリ秒を含むデータを取りこぼす恐れがあります。
こうした不整合を防ぐには、翌日の開始時刻（2026-07-15 00:00）を上限とし、「未満（<）」で比較する方式が安全です。

### 8 IN

複数の候補値のいずれかに合致する条件は、`IN`述語を用いることで簡潔に記述できます。

```sql
WHERE category IN ('科学', '料理')
```

同一列に対する複数の`OR`条件を、見通しの良い単一の述語として整理できるわけです。

### 9 LIKEとパターン文字列

書名の一部に含まれる文字列を照合するなど、パターンマッチングを行う場合は`LIKE`演算子を用います。

```sql
WHERE title LIKE 'はじめて%'
```

多くのSQL環境において、`%`は0文字以上の任意の文字列を表し、`_`は任意の一文字に合致するワイルドカードです。

`%星%`のように中間一致や後方一致を指定した場合、通常のBツリー索引を先頭から効率的に走査することが困難になります。
検索性能が要求される場面では、全文検索専用の転置インデックスなどの導入を検討すべきです。

## NULLを含む条件を評価する

### 10 NULLを調べる

価格やカテゴリのように具体的な値が確定している列であれば、比較演算の判定結果は常に真（TRUE）または偽（FALSE）の二値に定まります。
しかし、値が未確定または不在であることを示すNULLが演算に紛れ込むと、判定結果に第三の状態であるUNKNOWN（不明）が介入してくるわけです。
通常の値と同様に等号演算子（=）で比較しても、合致するかどうかを論理的に判定できません。

```sql
-- 意図どおりにならない誤った例
WHERE published_on = NULL
```

列の値がNULLであるかを判定するには、専用の`IS NULL`述語を使用します。

```sql
WHERE published_on IS NULL
```

逆にNULLでない有効な行のみを抽出したい場合は、`IS NOT NULL`と記述する構文規則です。

### 11 三値論理

SQLにおける条件評価は、真と偽に加えて**不明**（UNKNOWN）を含む**三値論理**（Three-Valued Logic）の体系に基づいています。
例として、`published_on`がNULLである行に対して、次の不等式を評価する場面を考えてみましょう。

```sql
published_on < DATE '2025-01-01'
```

出版日自体が存在しない以上、指定日より過去であるとも未来であるとも断定できません。
したがって比較演算の評価結果はUNKNOWNとなります。
`WHERE`句は評価結果が真となった行のみを抽出し、偽および不明となった行は容赦なく除外します。

条件式を`NOT (published_on < ...)`のように反転させたとしても、UNKNOWNを否定した結果は依然としてUNKNOWNのままです。
否定形にしたからといって、NULLを持つ行が検索結果に浮上してくるわけではありません。

### 12 NOT INとNULL

候補リストに含まれない行を検索する`NOT IN`句では、NULLの存在が極めて重大な落とし穴となります。

```sql
WHERE book_id NOT IN (2, 3)
```

このように具体的な数値のみが並んでいれば、意図どおりに動作します。
しかし副問合せから取得した候補リストの中にNULLが1件でも含まれていると、「どの候補とも一致しない」という条件が真と判定されず、意図しない全件空振りを引き起こしかねません。
したがって、候補集合からNULLを確実に排除するか、あるいは後述の`NOT EXISTS`述語による相関副問合せへ書き換える設計が安全です。

## 結果の値と並びを整える

### 13 DISTINCT

出力結果から重複する行を取り除いて一意にまとめるには、`DISTINCT`キーワードを指定します。

```sql
SELECT DISTINCT category
FROM books;
```

重複が排除された結果、得られるカテゴリの一覧は科学、小説、料理の3行です。

ただし問合せに`DISTINCT`を無批判に付与すると、「なぜそこで行の重複が発生したのか」という設計上の問題が覆い隠されてしまいます。
結合条件の指定漏れやテーブル設計の不備が存在しないかを事前に精査する手順を怠ってはなりません。
重複排除の内部処理にはソートやハッシュテーブル構築が伴うため、相応の実行コストを消費する点にも留意が必要です。

### 14 列に別名を付ける

取得する列や計算式に対しては、`AS`句を用いて別名を付与できます。

```sql
SELECT title AS book_title,
       price * stock AS inventory_value
FROM books;
```

表に対して指定する別名は相関名とも呼ばれます。
この例における計算列`inventory_value`のように、元表に存在しない動的な算出値を結果セットに含めることが可能です。

### 15 四則演算とNULL

数値列同士を演算子で組み合わせて、検索時に動的な計算を行わせることも可能です。

```sql
SELECT price * stock
FROM books;
```

一般に、計算対象の式のなかにNULLが1つでも含まれると、演算結果全体もNULLへと帰着します。
「不明な値に数値を加減乗除しても、結果は不明のままにとどまる」という論理的な帰結です。
NULLを既定の数値へ置き換える`COALESCE`関数なども用意されていますが、未設定を数値のゼロと同一視してよい業務仕様であるかを慎重に見極めなければなりません。

### 16 CASE式

条件分岐に応じて動的に戻り値を切り替えたい場合は、`CASE`式を活用します。

```sql
SELECT title,
       CASE
         WHEN stock = 0 THEN '在庫なし'
         WHEN stock <= 2 THEN '残りわずか'
         ELSE '在庫あり'
       END AS stock_status
FROM books;
```

上から順に条件式を評価し、最初に真となったWHEN節の結果を返す仕組みであるため、記述する条件の並び順が極めて重要です。

### 17 ORDER BY

検索条件に合致した行が特定されても、それだけでは出力される行の並び順は保証されません。
結果セットの表示順序を確定させるには、明示的に`ORDER BY`句を指定します。

```sql
SELECT title, price
FROM books
ORDER BY price ASC, title ASC;
```

`ASC`は昇順を、`DESC`は降順を表すキーワードです。
この指定により、同一価格の書籍群は書名の昇順に整列されます。
完全に一意で再現可能な並び順を担保したい場合は、ソートキーの末尾に主キーなどの一意列を必ず追加しておくべきです。

`ORDER BY`を明示しない問合せでは、たとえ物理配置や主キー順に見える結果が返されたとしても、DBMSはその順序性を一切保証しません。

### 18 結果件数を制限する

先頭10件や指定ページ分の行のみを取得する目的で、結果件数を制限する構文が広く使われています。
標準SQLの`FETCH FIRST`句をはじめ、各製品が備える`LIMIT`句など、構文の表現形式は環境によって様々です。

オフセットを用いたページネーションでは、ページが深くなるほど大量の先行行を読み飛ばす負荷が生じ、応答が急激に悪化しかねません。
直前に取得した一意キーを境界として後続行を引くキーセット方式（シーク法）の採用が有力な選択肢となります。

## 行集合が作られる順に条件を確かめる

### 19 論理的な評価順

SQL文は`SELECT`句から書き始めますが、DBMSが内部で論理的に処理を進める順序は記述順と大きく異なります。
元となる行集合を同定し、検索条件で絞り込み、グループ化を施した後に、ようやく出力列の評価や並べ替えが行われるのです。

```text
FROM       元になる行集合を準備する
WHERE      行単位の条件で絞り込む
GROUP BY   集約のグループに分割する
HAVING     グループ単位の条件で絞り込む
SELECT     出力する列や計算式を決定する
ORDER BY   最終的な行の並び順を整える
```

まずは`FROM → WHERE → SELECT → ORDER BY`の基本順序に沿って思考を組み立てることが肝要です。

### 20 条件式で列へ関数をかける費用

条件式の論理的な意味が同一であっても、式の記述形態によって内部の実行性能が大きく左右される場合があります。

```sql
WHERE EXTRACT(YEAR FROM published_on) = 2026
```

このように列に対して関数を適用してしまうと、全行について関数演算を行わなければ比較できず、列に張られた標準索引を走査に利用できなくなります。

```sql
WHERE published_on >= DATE '2026-01-01'
  AND published_on <  DATE '2027-01-01'
```

列を生のまま残した範囲条件に書き直せば、Bツリー索引をそのまま活用して目的の行を高速に特定可能です。
構文の見かけ上の簡潔さだけでなく、オプティマイザが索引を活用できる記述になっているかを常に意識しなければなりません。

科学または料理という条件に価格範囲を組み合わせる際は、括弧の記述を怠ると意図しないカテゴリの行まで混入してしまいます。
出版日がNULLの書籍は、通常の比較において判定結果がUNKNOWNとなり、真の行のみを要求する`WHERE`句によって自然に除外される仕組みです。
日本語の要件定義を安易に直訳せず、括弧による結合順序、NULLの三値論理、そしてDBMSにおける論理的な評価順序を的確に意識しながら、目的の行集合を導き出していく姿勢が求められます。
