# 第6章 第11話 結合と副問合せ

利用者表と貸出表をキーで結合すれば、氏名と借用資料の一覧を1つの検索結果に統合できます。
2つの表を繋ぎ合わせただけなのだから、出力行数も利用者数と同じ1人1行にとどまると思いがちです。
しかし1人の利用者が3件の貸出履歴を持っていれば、その利用者のレコードは3行に増殖して出力されます。

結合後の行数は表の連結数にとどまらず、結合キーが結ぶ多重度の対応関係によって決まるわけです。

## 結合条件と対応する件数を確かめる

### 1 使用する表

ここでは利用者、蔵書、貸出の3つの表を具体例として話を進めましょう。

```text
users
user_id | name
1       | 青木
2       | 伊藤
3       | 上田

loans
loan_id | user_id | book_id | loaned_on
101     | 1       | 10      | 2026-07-01
102     | 1       | 20      | 2026-07-02
103     | 2       | 10      | 2026-07-03

books
book_id | title
10      | 星の図鑑
20      | 海の物語
30      | 山の料理
```

### 2 内部結合

利用者名、書名、貸出日を1つの行に集約するため、共通するキー列を手掛かりに表同士を結びつけます。

```sql
SELECT u.name, b.title, l.loaned_on
FROM loans AS l
JOIN users AS u
  ON l.user_id = u.user_id
JOIN books AS b
  ON l.book_id = b.book_id;
```

`AS l`は表に付与した別名（相関名）です。
`l.user_id`は`loans`表に属する`user_id`列であることを明示しています。

`ON`句で指定した条件式が結合条件です。
条件に合致した行のみを抽出するため、貸出履歴のない上田や、一度も借りられていない「山の料理」は結果に含まれません。

### 3 列名を修飾する

複数の表に同一名称の`user_id`列が存在するため、列の指定には表名や別名を前置して修飾します。

```sql
l.user_id
u.user_id
```

同名の列が存在しない場合であっても、複雑なSQLでは各列の所属テーブルを明確にしておく配慮が保守性を高めます。

### 4 結合条件を忘れる

単に表の名前をカンマで並べただけでは、意図した行同士の対応関係は成立しません。

```sql
FROM users AS u, loans AS l
```

結合条件を指定せずに2つの表を並べると、数学的な直積が生成されてしまいます。
利用者3行と貸出3行のすべての組合せが展開され、3×3=9行の巨大な行集合が出現するわけです。

旧来のSQL構文では`WHERE`句に結合条件を記述する形式もありましたが、結合条件の記述漏れを防止するため、現代では`JOIN ... ON`構文の利用が強く推奨されます。

### 5 一対多で行が増える

青木は貸出を2件保持しているため、結合結果において青木のレコードは2行にわたって出力されます。
これは重複の不具合ではありません。
それぞれが独立した異なる貸出事実に対応している証拠です。

```text
青木 | 星の図鑑 | 2026-07-01
青木 | 海の物語 | 2026-07-02
```

氏名列のみを射影すると一見重複行に見えますが、背後にある貸出レコードの実体は別個の存在です。

## 対応のない行を残す

### 6 左外部結合

内部結合を実行した場合、対応する貸出履歴が存在しない利用者は結果セットから自動的に脱落してしまいます。
「貸出件数がゼロ件の利用者」も含めて網羅的に一覧化したい場合は、未対応の事実をNULLとして保持する外部結合の適用が欠かせません。

```sql
SELECT u.name, l.loan_id
FROM users AS u
LEFT JOIN loans AS l
  ON u.user_id = l.user_id;
```

この問合せを実行すると、次のような未対応行も確実に取得できます。

```text
上田 | NULL
```

左側に指定した`users`表の全行を保持し、一致する相手が存在しない右側テーブルの列にはNULLが補完される仕組みです。

### 7 外部結合とWHEREの落とし穴

外部結合によってせっかく残した未対応行が、後続の`WHERE`句によって誤って排除されてしまうトラブルが多発します。

```sql
SELECT u.name, l.loaned_on
FROM users AS u
LEFT JOIN loans AS l
  ON u.user_id = l.user_id
WHERE l.loaned_on >= DATE '2026-07-01';
```

貸出のない利用者の行では`l.loaned_on`がNULLであるため、`WHERE`条件の評価結果がUNKNOWNとなり抽出対象から除外されます。
未貸出の上田が結果から脱落し、意図せず内部結合と同じ挙動に陥ってしまうわけです。

外部結合において相手表との対応付けを制限する条件は、`WHERE`句を避け、`JOIN`の`ON`句内に直接記述しなければなりません。

```sql
LEFT JOIN loans AS l
  ON u.user_id = l.user_id
 AND l.loaned_on >= DATE '2026-07-01'
```

外部結合における`ON`句と`WHERE`句の配置の差異は、出力結果を根本から左右する重要ポイントです。

### 8 右外部結合と完全外部結合

`RIGHT JOIN`は右表の全行を保持し、`FULL OUTER JOIN`は左右双方の未対応行を網羅して結果を生成します。
表の記述順序を左右入れ替えれば、右外部結合は左外部結合の構文で自然に書き換え可能です。
完全外部結合の実装状況はDBMS製品によって差が存在します。

### 9 自己結合

上司と部下の関係のように同一階層のデータをたどる場合は、単一の社員表に2つの別名を与えて自己結合を適用する設計が有効です。

```text
employees
employee_id | name | manager_id
1           | 青木 | NULL
2           | 伊藤 | 1
3           | 上田 | 1
```

```sql
SELECT e.name AS employee_name,
       m.name AS manager_name
FROM employees AS e
LEFT JOIN employees AS m
  ON e.manager_id = m.employee_id;
```

同一の物理テーブルを、部下役の`e`と上司役の`m`という2つの異なる役割として参照するわけです。

## 問合せの結果を別の条件へ使う

### 10 副問合せ

複数表にまたがるデータを処理する手段は、表同士の結合構文にとどまりません。
平均値より高い点数を抽出する場合のように、ある問合せの結果を別の検索条件として再利用する構文設計が可能です。

SQL文の内部に埋め込んで実行する別の問合せを**副問合せ**（サブクエリ）と呼びます。

```sql
SELECT title
FROM books
WHERE book_id IN (
  SELECT book_id
  FROM loans
  WHERE user_id = 1
);
```

内側の問合せが青木の借りた本番号の集合を動的に生成し、外側の問合せが該当する書名を抽出します。

### 11 単一行副問合せ

戻り値が確実に単一のスカラ値（1行1列）となる副問合せであれば、通常の比較演算にそのまま組み込める仕様です。

```sql
SELECT title, price
FROM books
WHERE price > (
  SELECT AVG(price)
  FROM books
);
```

平均価格を動的に算出し、それより高額な書籍を抽出します。
単一の値を期待する演算子に対して副問合せが複数行を返却してしまうと、実行時エラーを引き起こしかねません。
期待される結果セットの形状（スカラか複数行か）を事前に確認しておく必要があります。

### 12 EXISTS

値の一覧をメモリ上に展開する必要がなく、条件に合致する行が存在するか否かのみを判定したい場合は、`EXISTS`述語を採用するのが定石です。
副問合せが1件でも合致行を返せば、その時点で評価を打ち切って真と判定します。

```sql
SELECT u.user_id, u.name
FROM users AS u
WHERE EXISTS (
  SELECT 1
  FROM loans AS l
  WHERE l.user_id = u.user_id
);
```

貸出履歴が1件以上存在する利用者のみを効率的に割り出すことが可能です。
`SELECT 1`と記述しているとおり、取得する値の内容自体は破棄され、行が存在するという事実のみが評価対象です。

### 13 NOT EXISTS

逆に、条件に一致するレコードが存在しないことを確認したい場合は、`NOT EXISTS`述語を用います。

```sql
SELECT u.user_id, u.name
FROM users AS u
WHERE NOT EXISTS (
  SELECT 1
  FROM loans AS l
  WHERE l.user_id = u.user_id
);
```

貸出履歴が1件も存在しない利用者を正確に抽出する結果となります。
候補リストにNULLが混入するリスクを伴う`NOT IN`句と比較して、二重否定を明快に表現できる利点を備えているわけです。

## 行ごとの参照と途中結果を整理する

### 14 相関副問合せ

内側の副問合せが外側の親問合せの現在行を参照する構文が**相関副問合せ**です。

先ほどの`EXISTS`の例でも、内側の条件式で外側の`u.user_id`を参照していました。

```text
外側の利用者を1行取得する
  ↓
その利用者番号を持つ貸出が存在するか内側で検査する
  ↓
判定結果を反映して次の利用者へ進む
```

論理モデル上は、外側のテーブルを1行走査するたびに内側の副問合せが再評価されるループ構造です。
ただし現代のDBMSオプティマイザは、論理的に等価な内部結合やセミ結合へと内部で自動変換する高度な最適化を施します。
「相関副問合せだから一律に遅い」という先入観を排し、実行計画を取得して実際の処理費用を検証する姿勢が肝要です。

### 15 すべてを満たす二重NOT EXISTS

「すべての必須科目を修了した社員」という命題は、「未修了の必須科目が1件も存在しない社員」と言い換えることができます。

```sql
SELECT e.employee_id
FROM employees AS e
WHERE NOT EXISTS (
  SELECT 1
  FROM required_courses AS r
  WHERE NOT EXISTS (
    SELECT 1
    FROM completions AS c
    WHERE c.employee_id = e.employee_id
      AND c.course_id = r.course_id
  )
);
```

外側の`NOT EXISTS`は、「未修了の必須科目が存在しない社員」を厳密に抽出する条件を表現しています。
これは関係代数における商演算の論理をSQL上で体現したアプローチにほかなりません。

### 16 共通表式、CTE

複雑にネストした問合せの途中結果に識別名を付与し、SQL文の先頭で定義可能にする機能が**共通表式**（CTE：Common Table Expression）です。

```sql
WITH active_users AS (
  SELECT DISTINCT user_id
  FROM loans
  WHERE loaned_on >= DATE '2026-01-01'
)
SELECT u.name
FROM users AS u
JOIN active_users AS a
  ON a.user_id = u.user_id;
```

SQL全体の可読性向上、再帰問合せの実装、複雑な集計の段階化に威力を発揮します。
DBMSが物理的な一時テーブルを実体化するかインライン展開するかは、オプティマイザの判断や製品仕様に委ねられる領域です。

## 求める答えに合わせて書き方を選ぶ

### 17 結合か副問合せか

同一の検索結果を導くにあたり、結合構文と副問合せの双方が選択肢となるケースは頻繁に生じます。
結合相手の表に含まれる複数列も同時に出力したいのであれば、結合構文を用いるのが素直な設計です。
単に対象データの存在有無を検証したいだけであれば`EXISTS`が適しており、単一の集計値との比較であれば単一行副問合せが自然な可読性を提供します。

構文の短さのみで安易に判断せず、重複行の発生有無、NULLの挙動、業務意図の明瞭さ、そして実行計画の効率性を総合的に点検しなければなりません。

### 18 N+1問題

利用者100人を検索した後、アプリケーション側のループ処理で1人ずつ貸出履歴を逐次検索した場合、データベースとの往復回数は次のように跳ね上がります。

```text
利用者一覧の取得 1回
各利用者の貸出履歴 100回
合計往復回数 101回
```

このような無駄な往復問合せの多発は、**N+1問題**として知られる代表的な性能アンチパターンです。

適切な結合構文、一括IN検索、あるいはO/Rマッパーの事前読込み（Eager Loading）設定によって往復回数を劇的に削減できます。
ただし一度に巨大な結合結果をメモリ上に展開すると、転送負荷や消費リソースが跳ね上がるトレードオフも無視できません。
ネットワークの往復回数と転送データ量のバランスを定量的に測定しながら最適な結合粒度を見極めるべきです。

### 19 結合前後の件数を調べる

意図しない重複行が発生した際、安易に`DISTINCT`で結果を取り繕うことを戒め、各テーブルの主キー構成と結合キーの一意性を原点に戻って検証します。
データの多重度が1対1、1対多、多対多のいずれであるかを再確認し、結合条件の不足や外部キー列へのNULL混入を漏れなく洗い出す作業が不可欠です。

1対多の関係性によって生じた複数行は、それぞれが個別の貸出事実を正確に表した正当なデータである可能性を忘れてはなりません。
結合の前段階で期待されるキー構造と件数の変化を論理的に予測し、求めている分析粒度と合致しているかを厳格に検証する姿勢が大切です。
