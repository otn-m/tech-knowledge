# 第6章 第12話 集約とグループ化、ウィンドウ関数

売上明細が何万行あっても、経営者が見たいのは「商品別の合計」「月別の平均」「売上順位」かもしれません。
ここでは行を集団としてまとめて計算する視点が求められます。

商品別合計だけなら、明細を商品ごとの1行へ縮めれば十分です。
ところが、各明細を残したまま商品内の順位や累計を付けたい場合、同じ集約処理では元の行が消えてしまうわけです。
したがって、行を減らす計算と、行を残したまま集団を参照する計算をきちんと切り分けなければなりません。

## 何を数え、どの値を計算するか

### 1 集約関数

複数行から1つの値を求める関数を「**集約関数**」や集合関数と呼びます。
代表例として、件数を求める`COUNT`、合計を求める`SUM`、平均を求める`AVG`などがあります。
最小値の取得には`MIN`、最大値の取得には`MAX`を指定する形です。

```sql
SELECT COUNT(*) AS book_count,
       SUM(stock) AS total_stock,
       AVG(price) AS average_price,
       MIN(price) AS minimum_price,
       MAX(price) AS maximum_price
FROM books;
```

### 2 COUNTの違い

同じ`COUNT`であっても、引数の指定方法によって数える対象が変わります。

```sql
COUNT(*)
```

この書き方は表全体の行数をそのまま数えます。

```sql
COUNT(published_on)
```

この指定では、`published_on`がNULLでない行だけをカウントする仕組みです。

```sql
COUNT(DISTINCT category)
```

この形では、NULLを除いた異なるカテゴリの重複を排除して数えます。
同じ表を対象にしても得られる値が異なるため、何を数えたいのかを明確に意識しなければなりません。

### 3 NULLと集約

多くの集約関数は、NULLを計算対象から除外して処理を進める仕様です。

```text
点数: 80, 100, NULL
AVG(score) = (80+100)÷2 = 90
```

この計算結果は、NULLを0点とみなして平均した値60とは一致しません。
「未受験」を0点として扱うか、それとも平均の母数から外すかは業務規則次第です。
また、全行がNULLの場合や対象行が1行も存在しないとき、`SUM`や`AVG`の結果はNULLを返します。
値が存在しないNULLと数値の0は、明確に区別して捉えなければなりません。

## 集団を作り、集団に条件を付ける

### 4 GROUP BY

カテゴリ別に売上を集計したい場合は、同じ値を持つ行を`GROUP BY`でグループに分類し、集団ごとに集約関数を適用します。

```sql
SELECT category,
       COUNT(*) AS book_count,
       AVG(price) AS average_price
FROM books
GROUP BY category;
```

```text
科学 | 2 | 1350
小説 | 1 | 1800
料理 | 1 | 900
```

### 5 SELECTへ書ける列

グループ化した問合せでは、通常、`SELECT`に`GROUP BY`で指定した列と、集約関数で計算した値を置きます。

```sql
-- titleはカテゴリ内で一つに決まらない
SELECT category, title, AVG(price)
FROM books
GROUP BY category;
```

カテゴリ「科学」には複数書名があるため、どの書名を出すか決まりません。
エラーにするDBMSが一般的です。
制約の緩い設定で1値が返っても、その値に意味を持たせてはいけません。

### 6 複数列でグループ化

集団は1列だけでなく、複数列の組合せでも作れます。

```sql
SELECT category, publisher_id, COUNT(*)
FROM books
GROUP BY category, publisher_id;
```

カテゴリと出版社の組ごとに1集団です。

### 7 WHEREとHAVING

集団を作る前に不要な行を除く条件と、集団を作った後に合計や平均で除く条件は、同じ場所へ書けません。
どの時点の値を判定するかで、`WHERE`と`HAVING`を使い分ける必要があります。

`WHERE`はグループ化前の個々の行を絞り込みます。
一方で、`HAVING`はグループ化後の集団に対して条件を適用する構文です。

```sql
SELECT category, AVG(price) AS average_price
FROM books
WHERE stock > 0
GROUP BY category
HAVING AVG(price) >= 1000;
```

この問合せは、まず在庫のある書籍だけを対象にしてカテゴリごとに分類し、それぞれの平均価格を計算します。
そのうえで、平均価格が1000以上のカテゴリのみを最終結果として抽出する流れです。

### 8 WHEREへ書ける条件は先に絞る

次のように書ける製品や状況でも、集約前に判定できる個別の条件をあえて`HAVING`まで残しておく利点はありません。

```sql
HAVING category = '科学'
```

集約前に判定できる行条件を`WHERE`に記述すれば、処理の初期段階で行数を減らせるため性能面でも有利ですし、問合せの意図も明確になります。
集約関数を通した結果に対する絞り込みに限り、`HAVING`を使う必要があるわけです。

### 9 条件付き集計

条件に合致する特定の行だけをカウントしたいときは、集約関数の中で`CASE`式を組み合わせます。

```sql
SELECT
  COUNT(*) AS all_books,
  SUM(CASE WHEN stock > 0 THEN 1 ELSE 0 END) AS available_books
FROM books;
```

この書き方を使えば、テーブルを1回走査するだけで複数の条件に応じた件数を同時に算出できます。
条件が真なら1、偽なら0を返すことで、合計値として件数が求まる仕組みです。

## 行を減らす計算と残す計算を使い分ける

### 10 集約で行が減る

`GROUP BY category`を実行すると、出力される1行はカテゴリ1つを表す単位へと集約されます。

元の個々の書名や個別価格といった明細情報は、この集約によって結果から失われます。
一度グループ化された集約結果から、元の個別行を復元することは不可能です。
明細行の詳細を残したまま集計値を扱いたい場合は、別の問合せを発行するか、後述するウィンドウ関数を活用する必要があります。

### 11 ウィンドウ関数

集約関数で商品別合計を求めると、複数の明細は商品ごとの1行にまとまります。
各明細を残して順位や累計を付けるには、結果行を減らさずに集団を参照する計算が必要です。

元の各行の姿をそのまま残しながら、関連する行の集合に対して計算を実行する仕組みが「**ウィンドウ関数**」です。

```sql
SELECT title,
       category,
       price,
       AVG(price) OVER (PARTITION BY category) AS category_average
FROM books;
```

個々の書籍の行を保持したまま、同一カテゴリの平均価格を各行の横に並べて出力できます。

### 12 PARTITION BY

カテゴリごとの平均のように、ウィンドウ計算の対象を集団に分ける指定が`PARTITION BY`です。

```sql
OVER (PARTITION BY category)
```

`GROUP BY`と似ていますが、結果を1集団1行へまとめません。

## 順位と前後関係を求める

### 13 順位

順位を求める関数は、同じ値を持つ行の扱い方によって複数の種類が用意されています。

```sql
SELECT title,
       price,
       ROW_NUMBER() OVER (ORDER BY price DESC) AS row_no,
       RANK()       OVER (ORDER BY price DESC) AS price_rank,
       DENSE_RANK() OVER (ORDER BY price DESC) AS dense_rank
FROM books;
```

`ROW_NUMBER`は、値が同一であっても行ごとに一意の連番（1, 2, 3...）を割り振る関数です。
一方、`RANK`は同順位の後の番号を飛ばすため、1位、2位、2位の次は4位となります。
これに対して`DENSE_RANK`は番号を飛ばさず、1位、2位、2位の次を3位とする仕様です。
同着の行に対しても完全に一意な順序を保証したい場合は、`ORDER BY`句に主キーなどの列を追加してソート順を確定させなければなりません。

### 14 累計

集団内に順序と計算範囲を指定すれば、累計も求められます。

```sql
SELECT sold_on,
       amount,
       SUM(amount) OVER (
         ORDER BY sold_on, sale_id
         ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
       ) AS running_total
FROM sales;
```

最初の行から現在行までの合計です。

同じ日付が複数存在する場合、同値処理の仕様や`ROWS`と`RANGE`の解釈の違いによって予期せぬ結果が生じかねません。
意図通りの累計を得るには、一意な並び順を指定し、計算対象となるフレーム範囲を明示的に定義しておく必要があります。

### 15 前後の行を見る

前回の計測値と比較したいケースなどでは、前後の行の値を参照する関数が重宝します。

```sql
SELECT measured_at,
       temperature,
       LAG(temperature) OVER (ORDER BY measured_at) AS previous_temperature
FROM measurements;
```

`LAG`は指定した並び順における直前の行を取得し、`LEAD`は直後の行の値を取得する関数です。
売上の前回比の計算や、次回予約日時の表示といった要件で頻繁に利用されます。

### 16 上位N件を集団ごとに取る

ここでは、カテゴリごとに価格上位2冊を抽出する処理を考えてみましょう。

```sql
WITH ranked AS (
  SELECT b.*,
         ROW_NUMBER() OVER (
           PARTITION BY category
           ORDER BY price DESC, book_id
         ) AS rn
  FROM books AS b
)
SELECT *
FROM ranked
WHERE rn <= 2;
```

まず共通表式（CTE）の中で各行にカテゴリ内順位を割り当てておき、外側の主問合せで順位が2以下の行を抽出する形をとります。

## 結合と集計の粒度をそろえる

### 17 結合による集計の水増し

どれほど正確に集約関数を記述していても、結合操作の段階で行が重複して複製されていれば合計値は水増しされてしまいます。
したがって、集計対象の列の指定だけでなく、集約直前の時点で1行が何を表しているかを把握することが欠かせません。

たとえば、注文1件に対して明細が3行、支払情報が2行ぶら下がっている状況を考えてみます。
この注文に対して明細テーブルと支払テーブルを安易に同時結合すると、直積によって行数が3×2=6行へと膨らみ、明細金額や支払額を何重にも合算してしまう危険が生じます。
こうした不整合を防ぐには、多側の各テーブルをあらかじめ注文単位で集約してから結合するなど、データの粒度を適切に揃える工夫が必要です。

### 18 粒度

結合によるデータの重複や誤計算を避ける鍵は、テーブルの1行が表す対象を正確に見極めることです。
データが保持するこの最小の単位を「**粒度**」と呼びます。

```text
売上明細表: 1件の商品明細が1行
日別売上表: 1日が1行
月別商品売上: 1か月、1商品が1行
```

集計や結合を組み立てる前に、各テーブルの粒度を言葉で整理しておけば、意図しない行の増殖を未然に防ぐ助けとなります。

### 19 論理順序をもう一度

集計とウィンドウ計算を含めると、論理的な評価順は以下の通りです。

```text
FROM/JOIN  行の候補を作る
WHERE      行を絞る
GROUP BY   集団へ分ける
HAVING     集団を絞る
SELECT     集約・列・ウィンドウ結果を作る
ORDER BY   並べる
```

ウィンドウ関数の計算結果を同じクエリ内の`WHERE`句で直接絞り込めないときは、共通表式や副問合せを利用して一段階外側のクエリで条件判定を行わなければなりません。

商品別合計では明細行を商品ごとの1行へと集約するのに対し、商品内順位の算出では明細行を保持したまま同一商品をグループとして参照する形をとります。
どちらも同じように集団を扱っているものの、出力されるデータの粒度は根本から異なるわけです。
結合処理によって変化する行数、NULLをスキップする集約の挙動、そして`WHERE`と`HAVING`が実行されるタイミングの違いを整理しておけば、SQLの構文自体は正しく見えても結果が食い違う原因を論理的に説明できるようになります。
