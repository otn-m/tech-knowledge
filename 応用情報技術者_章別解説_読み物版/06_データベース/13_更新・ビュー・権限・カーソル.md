# 第6章 第13話 更新とビュー、権限、カーソル

検索処理は既存のデータを参照するだけですが、追加、変更、削除といった更新操作は共有されている事実そのものを書き換えます。
条件の指定を1つ誤っただけでテーブル全体の行に影響が及ぶため、対象件数、制約、トランザクション、そして実行権限を合わせて検討しなければなりません。

正しい`WHERE`句さえ書けば安全に更新できるように思えるかもしれません。
しかし、データを検索してから実際に更新するまでのわずかな間に別のトランザクションが値を書き換えてしまえば、前提条件が実行時には崩れている可能性もあります。
更新条件、実行権限、そして影響を受ける変更件数を、DBMSが変更を実際に適用するタイミングで確実に確かめる姿勢が求められるわけです。

## 追加と更新の対象を確かめる

### 1 INSERTで1行を追加する

テーブルに1行を新規追加するには、`INSERT`文で対象の列名と値を明示的に指定します。

```sql
INSERT INTO users (user_id, name, registered_on, member_type)
VALUES (1025, '山田花子', DATE '2026-07-14', '一般');
```

列名を省略せずに記述しておけば、将来テーブルに列が追加されたり並び順が変わったりしてもクエリが破綻しません。
さらに、渡している値がどの項目に対応するのかを一目で把握できる利点もあります。

もし主キーの重複、必須値の欠落、検査制約違反、外部キー違反などが生じた場合は、DBMSが自動的に登録を拒否する仕組みです。

### 2 複数行や検索結果を追加する

SQLでは複数行を一度に挿入する構文のほか、`SELECT`文の検索結果をそのまま別テーブルへ追加する手法も用意されています。

```sql
INSERT INTO archived_loans (loan_id, user_id, book_id, loaned_on)
SELECT loan_id, user_id, book_id, loaned_on
FROM loans
WHERE loaned_on < DATE '2021-01-01';
```

履歴テーブルへ追加した後に元のテーブルから該当行を削除する場合は、途中で処理が失敗した際に重複や欠落が生じないよう、一連の手順をトランザクションとして設計しなければなりません。

### 3 UPDATEで変更する

すでにテーブルに存在する行を書き換えるには、`UPDATE`文を使用します。

```sql
UPDATE books
SET price = 1200
WHERE book_id = 10;
```

`WHERE`句の条件によって、実際に値を更新したい特定の行を正確に指定する形です。
本番環境で実行する前には、同一の条件を付与した`SELECT`文を実行して更新対象の行を事前に確認する運用が広く行われています。

### 4 WHEREを忘れたUPDATE

`WHERE`句をうっかり書き忘れてしまった場合でも、SQL構文としては文法的に成立してしまうケースが少なくありません。

```sql
UPDATE books
SET price = 1200;
```

このクエリを実行すると、テーブル内に存在する全行の価格が一律で1200へと書き換わってしまいます。
文法上は正常なクエリであっても、業務の観点からは致命的な事故につながりかねないわけです。

こうした惨劇を防ぐには、変更件数に上限を設定したり、トランザクション内で影響行数を確認してからコミットしたり、本番データへ直接更新をかけられる権限を厳密に絞ったりする防御策が欠かせません。
更新直前のバックアップや監査ログを確実に取得し、事前に検証された手順書に沿って実行することも不可欠な対策といえます。

## 条件の判定と変更を一体で行う

### 5 条件付きの原子的更新

在庫が残っている場合に限って1冊だけ減らす処理を考えてみます。

```sql
UPDATE books
SET stock = stock - 1
WHERE book_id = 10
  AND stock > 0;
```

このクエリでは、更新された行数が1件であれば処理成功、0件であれば在庫切れだったと判定できる設計です。

アプリケーション側で「まず在庫数を読み込み、問題なければ数値を更新する」という2段階の手順を踏むと、読取りと書込みの隙間に別の処理が割り込む隙が生まれてしまいます。
判定と更新を1文にまとめた条件付き更新としてDBMSへ委ねれば、並行処理による割込みを根本から排除しやすくなるわけです。
貸出履歴の登録まで含めて一連の処理とするならば、それら全体を同一トランザクションで囲まなければなりません。

### 6 DELETEで行を削除する

テーブルから特定の行を削除する際には、`DELETE`文を用います。

```sql
DELETE FROM loans
WHERE loan_id = 101;
```

テーブルの構造そのものは維持したまま、指定した条件に合致するデータ行だけを切り取って削除する構文です。
ここでも`WHERE`句を省略してしまうと、テーブル内の全行が一括で消去されてしまうため細心の注意を払わなければなりません。

外部キーによって他のテーブルから参照されている行を削除しようとした場合の挙動は、削除の拒否、連鎖削除（CASCADE）、あるいはNULLの自動設定など、テーブル定義時に指定された参照整合性制約に従って制御されます。

### 7 論理削除

物理的なデータ削除を行わず、状態フラグや削除日時を記録して「削除扱い」にとどめる手法も広く使われています。

```text
deleted_at = 2026-07-14 15:00
```

過去の変更履歴の追跡や誤操作時の復元には便利な半面、以降のあらゆる検索クエリで削除済みフラグを除外する条件を書き続けなければなりません。
また、一意制約の設計が格段に複雑化するうえ、データベース上に個人情報がそのまま残留し続ける問題も生じます。
さらに、不要になったデータが蓄積されてテーブルやインデックスの容量が増大し続ける運用コストも見逃せません。
法令に基づく完全なデータ消去が求められる場面では、単に削除フラグを立てるだけでは要件を満たせない場合もあるわけです。

### 8 MERGEなどの更新

対象データが存在すれば更新を行い、存在しなければ新規追加を行う処理を1文で表現する構文として`MERGE`文などが提供されています。
ただし、競合が発生した際の細かい挙動はデータベース製品ごとに異なるため、事前の仕様確認が欠かせません。

アプリケーション側で「存在確認のSELECTを行ってからINSERTする」と処理を分けてしまうと、並行して走る2つのトランザクションが同時に「データなし」と誤認して主キーの重複エラーを引き起こす競合が生じます。
最終的にはデータベースの一意制約によって重複登録が阻止される形です。

## 公開する範囲とDB側の処理を定める

### 9 ビューを作る

実表を直接参照させず、業務に必要な特定の行や列だけを限定して公開したい局面があります。
検索結果の問合せに名前を付けて仮想的なテーブルとして定義したものが「**ビュー**」です。

```sql
CREATE VIEW active_loans AS
SELECT l.loan_id, u.name, b.title, l.loaned_on
FROM loans AS l
JOIN users AS u ON u.user_id = l.user_id
JOIN books AS b ON b.book_id = l.book_id
WHERE l.returned_on IS NULL;
```

利用者は、実表の複雑な結合構造を意識することなく、通常のテーブルと同じ感覚で検索を行えます。

```sql
SELECT * FROM active_loans;
```

### 10 ビューと安全性

ビューは関係データベースにおける外部スキーマを実装する有力な手段であり、機密情報や個人情報の列を隠蔽した状態で安全にデータを公開できます。
ただし、ビューを定義しただけで背後にある基表への直接アクセスが自動的に遮断されるわけではありません。
利用者のアカウントに対して基表への直接参照権限を付与せず、ビューに対する権限のみを与えるといった適切なアクセス制御を並行して設計する必要があります。

また、副問合せや集計関数、あるいはエラーメッセージの内容から隠されたデータを間接的に推測されないかという観点も考慮しなければなりません。
ビューの定義変更によって公開範囲が意図せず拡大しないよう、スキーマの変更管理を徹底することも肝要です。

### 11 更新可能なビュー

単一の実表と1対1で対応している単純なビューであれば、ビュー経由で`UPDATE`や`INSERT`を実行できるケースがあります。

しかし、集約関数、`DISTINCT`、集合演算、あるいは複数テーブルの複雑な結合を含むビューの場合、ビューへの変更を基表のどの行へどのように反映すべきかが一意に定まりません。
そのため、多くのDBMSにおいてこのような複雑なビューは更新不可能として扱われます。
どのビューが更新可能とみなされるかは、採用しているデータベース製品の仕様を個別に確認しなければなりません。

### 12 TRIGGER

テーブルに対する行の追加、更新、削除などのイベントを検知して、事前に定義した処理を自動的に実行する仕組みを「**トリガ**」（TRIGGER）と呼びます。

更新履歴を記録する監査ログの生成、複雑な業務整合性制約の強制、あるいは別テーブルの派生値の自動再計算といった用途で重宝される仕組みです。
その一方で、アプリケーション側のSQL文からは見えないところで勝手に処理が走るため、予期せぬ副作用や連鎖的な動作、性能低下、トリガ同士の再帰呼び出しなどが深刻なトラブルを引き起こしかねません。
ビジネスロジックをどこまでトリガに担わせるかという配置基準と、網羅的なテスト方法を開発初期に明確化しておく必要があります。

### 13 ストアドプロシージャ

データベース管理システム内部に一連の処理手順をあらかじめ保存しておき、クライアントから呼び出して実行する仕組みがストアドプロシージャです。

クライアントとデータベース間のネットワーク往復回数を大幅に削減できるほか、権限を業務単位でカプセル化したり、共通ロジックをデータのごく近傍で集中的に実行できたりする大きなメリットがあります。
ただし、記述構文が各DBMS製品固有の方言に強く依存するため、バージョン管理、単体テスト、保守の責任分担などを組織的に管理する運用が欠かせません。

## 仕事に必要な権限を割り当てる

### 14 GRANT

データベースの利用者や業務上の役割に対して操作権限を付与する命令が`GRANT`です。

```sql
GRANT SELECT ON books TO librarian_reader;
GRANT SELECT, INSERT, UPDATE ON loans TO loan_operator;
```

データベースへの接続権限に加えて、`SELECT`による参照権限、`INSERT`による追加権限、`UPDATE`による更新権限、`DELETE`による削除権限など、操作の種別ごとに細かく権限を切り分けられます。
テーブルやビューの新規定義を行える管理権限も含めて、セキュリティの基本方針は「業務遂行に必要な最小限の権限のみを付与すること」に尽きるわけです。

### 15 REVOKE

すでに付与した権限を剥奪して取り消す際には、`REVOKE`文を発行します。

```sql
REVOKE UPDATE ON loans FROM loan_operator;
```

ただし、対象のユーザーが別のロールやグループを経由して同一の権限を多重に継承している場合、1つの権限を剥奪しただけでは依然として操作を実行できてしまうケースが珍しくありません。
ロールの階層関係や継承ツリー全体を把握したうえで、意図通りに権限が遮断されているかを慎重に検証する必要があります。

### 16 ロールによる権限管理

個々の利用者に個別で権限を設定していくと、管理コストが爆発して設定ミスを誘発します。
そこで、業務上の役割ごとに権限をひとまとめにした「**ロール**」を定義し、ユーザーをそのロールに所属させる運用が標準的です。

```text
貸出担当ロール → 貸出の参照・追加・更新
監査担当ロール → 監査ビューの参照
```

この仕組みを導入すれば、人事異動や退職が発生した際にもロールの所属を変更するだけで権限の付け替えが完了します。
特権を持つ管理者アカウントの兼務を避け、相互牽制が効くようにロールを適切に分離して運用することが組織防衛の観点からも欠かせません。

## アプリから値と処理を安全に渡す

### 17 アプリからSQLを使う

対話型ツール上で正しく動作するSQLであっても、アプリケーションコード内で文字列連結を使って組み立てると、利用者の入力値がSQL命令の一部として解釈されてしまう重大な脆弱性を招きます。
SQLの構文構造と入力パラメータの値を明確に分離し、コネクションやトランザクションの生存期間を適切に管理しなければなりません。

ユーザー入力をそのまま文字列結合してSQLを組み立てる行為は絶対に避けるべき悪手です。

```text
危険な考え方:
"SELECT ... WHERE name = '" + 入力 + "'"
```

悪意ある入力によってクエリの構造が書き換えられ、データベース全体が破壊されるSQLインジェクション攻撃を招く危険性があります。
値が入るべき位置を特殊な記号で示しておき、後からパラメータとして安全に流し込む「**プレースホルダ**」や準備済み文（Prepared Statement）の利用が必須となるわけです。

```sql
SELECT user_id, name
FROM users
WHERE name = ?;
```

なお、プレースホルダの記号`?`にはテーブル名やソート対象の列名をパラメータとしてバインドできません。
動的なテーブル指定などが必要な場合は、あらかじめ許可した安全なホワイトリストとの突合によって安全性を担保する形をとります。

### 18 埋込みSQL

C言語などの汎用プログラミング言語（親言語）のソースコード内に直接SQL文を記述し、専用のプリコンパイラを通して実行形式を生成する方式を埋込みSQLと呼びます。
親言語側の変数とデータベースの列とのデータ型の整合性、NULL値の表現方法、エラーハンドリング、そしてトランザクションの境界設定などを厳密に対応付ける仕組みです。
また、SQL文を独立したモジュールとして切り離して呼び出すモジュール言語という設計思想も存在します。

現代のデータベースドライバやO/Rマッパーを用いる開発においても、言語側のオブジェクトとデータベースのレコードの間で型やNULL、例外をどのように対応付けるかという共通の課題はそのまま引き継がれているわけです。

### 19 カーソル

SQLの問合せ結果として返された複数行のデータセットに対して、1行ずつ順番に取り出して処理を進める走査機構を「**カーソル**」と呼びます。

カーソルを利用する際の一連の標準的な処理フローは以下の通りです。

```text
DECLARE  カーソルを宣言
OPEN     問合せを開始
FETCH    現在行を変数へ読む
FETCH    次の行を読む
...
CLOSE    終了
```

具体的な宣言構文やエラー時の検知方法は、利用するDBMSや埋込み方式によって細部が異なります。

### 20 カーソルと集合処理

外部APIの呼び出しなど、1行ごとに外部システムとの複雑な連携を行う要件であればカーソルによる順次処理が妥当な選択肢となります。
しかし、100万行に及ぶデータをカーソルで1行ずつループ更新するアプローチは、集合として1本のSQLで一括更新する場合に比べて極端な処理遅延を招きがちです。

```sql
UPDATE books
SET price = price * 1.05
WHERE category = '科学';
```

DBMSのクエリオプティマイザは、集合処理のSQLに対してテーブル全体を俯瞰した最適な実行計画を構築できます。
まずは集合演算として1つのクエリで表現できないかを優先して検討し、どうしても個別制御が避けられない場合に限ってカーソルを採用するのが定石です。

### 21 非カーソル操作

1行だけをピンポイントで取得する検索や、条件に合う行の集合を一括で更新・削除する操作のように、カーソルを用いた逐次読取りを行わない処理を非カーソル操作と呼びます。
膨大なレコード群をアプリ側に丸ごと転送して選別するのを避け、データベース側で必要な行や列、集約結果に絞り込んでから取得する設計が鉄則です。

## 接続と変更結果を管理する

### 22 接続プール

アプリケーションがデータベースとの接続を新しく確立するたび、ネットワーク通信、暗号化ハンドシェイク、ユーザー認証、内部メモリの確保といった重い処理負荷が発生します。
あらかじめ確立した複数の接続をプールしておき、要求に応じて貸し出して再利用する仕組みが「**接続プール**」（コネクションプール）です。

ただし、プールサイズをむやみに拡大しすぎると、DBMS側の同時接続数上限の圧迫、メモリの枯渇、激しいロック競合などを引き起こしかねません。
アプリケーション側の待機キューの長さ、平均処理時間、データベースのハードウェア容量などを総合的に勘案して最適な接続数を決定する必要があります。
また、使用後のコネクション返却漏れや、トランザクションのコミット漏れが接続内部に残存して次の処理へ汚染を広げないよう、厳格な接続ライフサイクル管理が求められます。

### 23 変更件数を確認する

`UPDATE`や`DELETE`の実行後には、その操作によって実際に影響を受けた行数を必ずプログラム側で確認しなければなりません。

```text
予定1行、実績0行 → 対象なし・競合・条件誤り
予定1行、実績5000行 → 条件誤りの疑い
```

影響行数の一致だけで処理の完全な正しさを証明できるわけではありませんが、想定外の大規模障害を検知するための極めて強力な防壁として機能します。

たとえば在庫を1点減らす更新処理を行う場合、事前に在庫数を読み出して計算するよりも、`在庫 >= 注文数`を更新条件に組み込んだ1本のクエリで判定と変更を同時に完結させる方が同時実行制御の観点から格段に堅牢です。
それでも、実際の影響行数が0件であれば在庫不足や直前の競合を即座に認識できますし、もし想定外の5000件が更新されていれば即座に異常を検知してロールバックを試みなければなりません。
更新用SQLの適切な記述、最小権限の徹底、トランザクション境界の保護、そして影響件数の機械的検証という多層的な防御策が揃って初めて、安全なデータ変更が成立するわけです。
