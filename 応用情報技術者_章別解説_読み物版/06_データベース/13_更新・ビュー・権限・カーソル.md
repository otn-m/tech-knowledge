# 第6章・第13話　更新・ビュー・権限・カーソル――値を変え、見せ方を制御する

検索はデータを読むだけですが、追加・変更・削除は共有する事実を変えます。条件を一つ誤ると全行へ影響するため、対象件数、制約、トランザクション、権限を一緒に考えます。

## 1 INSERTで一行を追加する

```sql
INSERT INTO users (user_id, name, registered_on, member_type)
VALUES (1025, '山田花子', DATE '2026-07-14', '一般');
```

列名を明示します。表の列追加・並び変更に強く、値の意味を読みやすくします。

主キー重複、必須値欠落、検査制約違反、外部キー違反ならDBMSが拒否します。

## 2 複数行・検索結果を追加する

複数行の構文や、`SELECT`の結果を別表へ追加する方法があります。

```sql
INSERT INTO archived_loans (loan_id, user_id, book_id, loaned_on)
SELECT loan_id, user_id, book_id, loaned_on
FROM loans
WHERE loaned_on < DATE '2021-01-01';
```

追加後に元を削除するなら、途中失敗で重複・欠落しないよう一連の処理を設計します。

## 3 UPDATEで変更する

```sql
UPDATE books
SET price = 1200
WHERE book_id = 10;
```

`WHERE`が対象行です。実行前に同じ条件の`SELECT`で対象を確認することがあります。

## 4 WHEREを忘れたUPDATE

```sql
UPDATE books
SET price = 1200;
```

全行を1200へします。文法上正しくても業務上は事故かもしれません。

- 変更件数の上限を設ける。
- トランザクション内で確認する。
- 本番の直接更新権限を絞る。
- 変更前バックアップ・監査記録を持つ。
- 検証済み手順を使う。

で守ります。

## 5 条件付きの原子的更新

在庫が残るときだけ一冊減らします。

```sql
UPDATE books
SET stock = stock - 1
WHERE book_id = 10
  AND stock > 0;
```

更新件数が1なら成功、0なら在庫なしです。

アプリが先に在庫を読み、後で書く二段階より、一文の条件付き更新としてDBMSへ任せると、間への割込みを防ぎやすくなります。貸出行の追加まで同じトランザクションにします。

## 6 DELETEで行を削除する

```sql
DELETE FROM loans
WHERE loan_id = 101;
```

表構造は残し、条件に合う行を削除します。`WHERE`なしなら全行です。

外部キーが参照する行の削除は拒否、連鎖削除、NULL設定など定義に従います。

## 7 論理削除

物理的に行を消さず、状態や削除日時を付ける方法があります。

```text
deleted_at = 2026-07-14 15:00
```

履歴・復元に使えますが、

- 全検索で削除済み除外が必要。
- 一意制約が複雑になる。
- 個人情報が消えず残る。
- 表・索引が増え続ける。

という費用があります。法的な削除要求にも、印を付けるだけでは足りない場合があります。

## 8 MERGEなどの更新

存在すれば更新、なければ追加する処理を表す`MERGE`などがあります。製品ごとの競合時の振舞いを確認します。

アプリで「存在確認→INSERT」と分けると、同時に二処理が存在なしと判断し、主キー重複する競合があります。DBの一意制約を最後の防波堤にします。

## 9 ビューを作る

```sql
CREATE VIEW active_loans AS
SELECT l.loan_id, u.name, b.title, l.loaned_on
FROM loans AS l
JOIN users AS u ON u.user_id = l.user_id
JOIN books AS b ON b.book_id = l.book_id
WHERE l.returned_on IS NULL;
```

利用者は、

```sql
SELECT * FROM active_loans;
```

と一表のように読めます。

## 10 ビューと安全性

個人情報列を含めず公開できます。しかしビューだけで常に安全とは限りません。

- 元表への直接権限を与えない。
- 行ごとの制御も必要なら設計する。
- 副問合せ・エラー・集計から秘密を推測できないか考える。
- ビュー定義変更を管理する。

外部スキーマの実装手段の一つです。

## 11 更新可能なビュー

一つの実表の行へ一意に対応する単純なビューは更新できる場合があります。

集約、`DISTINCT`、集合演算、複雑な結合を含むビューは、変更をどの元行へ反映するか決められず、更新不可能になりやすいです。

製品の条件を確認します。

## 12 TRIGGER

表への追加・更新・削除などをきっかけに自動実行する仕組みが**TRIGGER**、トリガです。

監査行の作成、複雑な制約、派生値更新などに使えます。

一方、アプリのSQLから見えない副作用、連鎖、性能、実行順、再帰が問題になります。規則の置き場所と試験方法を明確にします。

## 13 ストアドプロシージャ

DB側へ保存して呼び出す一連の処理がストアドプロシージャです。

通信往復を減らす、権限を処理単位にする、共通手順をDB近くへ置く利点があります。製品依存、版管理、テスト、責任分担を管理します。

## 14 GRANT

利用者・役割へ権限を与えます。

```sql
GRANT SELECT ON books TO librarian_reader;
GRANT SELECT, INSERT, UPDATE ON loans TO loan_operator;
```

- 接続する権限。
- `SELECT`の**参照権限**。
- `INSERT`の**挿入権限**。
- `UPDATE`の更新権限。
- `DELETE`の**削除権限**。
- 表・ビューを定義する権限。

必要な仕事に必要な最小限だけ与えます。

## 15 REVOKE

```sql
REVOKE UPDATE ON loans FROM loan_operator;
```

権限を取り消します。別の役割経由でも同じ権限を持つなら、完全には失わない場合があります。継承関係を確認します。

## 16 役割、ロール

個人一人ずつへ権限を設定する代わりに、仕事ごとの**ロール**へ権限を付け、人を所属させます。

```text
貸出担当ロール → 貸出の参照・追加・更新
監査担当ロール → 監査ビューの参照
```

異動・退職時に所属を外しやすくなります。強い権限の兼務・相互牽制も見直します。

## 17 アプリからSQLを使う

入力を文字列連結してはいけません。

```text
危険な考え:
"SELECT ... WHERE name = '" + 入力 + "'"
```

入力がSQLの構造へ混ざり、SQLインジェクションを起こします。

値の場所を印で示し、値を別に渡す**プレースホルダ**、準備済み文を使います。

```sql
SELECT user_id, name
FROM users
WHERE name = ?;
```

`?`へ値として渡せない表名・並べ替え列は、許可した候補との対応表から選びます。

## 18 埋込みSQL

Cなどの親言語の中へSQL文を書き、事前処理して利用する方式が**埋込みSQL**です。

親言語の変数とDB列の型、NULL表示、エラー、トランザクション境界を対応付けます。SQLを別モジュールとして呼ぶ**モジュール言語**の考えもあります。

現代のドライバ・ORMでも、言語とDBの型・NULL・例外の橋渡しという問題は同じです。

## 19 カーソル

問い合わせ結果の行を一件ずつ指す位置・仕組みが**カーソル**です。

典型的な流れは次です。

```text
DECLARE  カーソルを宣言
OPEN     問合せを開始
FETCH    現在行を変数へ読む
FETCH    次の行を読む
...
CLOSE    終了
```

製品・埋込み方式で構文は違います。

## 20 カーソルと集合処理

一行ずつ複雑な外部処理をするならカーソルが必要な場合があります。しかし、100万行を一行ずつ更新すると、集合として一文で更新するより遅くなりやすいです。

```sql
UPDATE books
SET price = price * 1.05
WHERE category = '科学';
```

DBMSは全体を最適化できます。まず集合処理で表せないか考え、必要な場合にカーソルを使います。

## 21 非カーソル操作

一行だけ返す検索、集合を一括更新する処理など、カーソルで逐次読取りをしない操作が**非カーソル操作**です。

大量データをすべてアプリへ運んでから絞るより、DB側で必要な行・列・集計へ減らします。

## 22 接続プール

アプリがDBへ接続するたび、通信・認証・状態準備に費用がかかります。既存接続を再利用する**接続プール**があります。

大きくしすぎるとDBMSの同時接続・主記憶・ロック競合を増やします。待ち行列、処理時間、DB容量に合わせます。返却漏れや、接続に残ったトランザクション状態へ注意します。

## 23 変更件数を確認する

更新・削除後、影響行数を確認します。

```text
予定1行、実績0行 → 対象なし・競合・条件誤り
予定1行、実績5000行 → 条件誤りの疑い
```

件数だけで正しさは保証できませんが、重要な異常検知です。


## 応用情報技術者試験での扱われ方

- **典型設問:** 「`INSERT`で列名を明示する利点を答えてください。」
- **条件語:** `INSERT`を本文の定義と対応させます。
- **最初の着眼点:** 問われた語の上位概念、対象、役割、成立条件を分けて思い出します。
- **途中の組立て・式:** 『何であるか』に加え、『何へ何をするか』と、似た語との境界を一文にします。 対象→入力→処理→出力の流れと、成立条件・限界を対応させます。選択問題でも不採用案が条件へ反する箇所を示します。
- **典型誤答と理由:** 略語展開や日常語の印象だけでは、対象・役割・成立条件のいずれかが抜け、近い用語と区別できません。
