# 第6章 第13話 更新とビュー、権限、カーソル

検索はデータを読むだけですが、追加、変更、削除は共有する事実を変えます。
条件を1つ誤ると全行に影響するため、対象件数、制約、トランザクション、権限を一緒に考えます。

正しい`WHERE`を書けば安全に更新できるように見えます。
しかし、検索してから更新する間に別の処理が値を変えれば、条件は実行時には成り立たないかもしれません。
更新条件、権限、変更件数を、DBMSが変更を適用する時点で確かめます。

## 追加と更新の対象を確かめる

### 1 INSERTで1行を追加する

1行を追加するには、`INSERT`で列名と値を指定します。

```sql
INSERT INTO users (user_id, name, registered_on, member_type)
VALUES (1025, '山田花子', DATE '2026-07-14', '一般');
```

列名を明示します。
表の列追加や並びの変更に強く、値の意味を読みやすくします。

主キー重複、必須値欠落、検査制約違反、外部キー違反ならDBMSが拒否します。

### 2 複数行や検索結果を追加する

複数行の構文や、`SELECT`の結果を別表に追加する方法があります。

```sql
INSERT INTO archived_loans (loan_id, user_id, book_id, loaned_on)
SELECT loan_id, user_id, book_id, loaned_on
FROM loans
WHERE loaned_on < DATE '2021-01-01';
```

追加後に元を削除するなら、途中の失敗で重複や欠落が起きないよう一連の処理を設計します。

### 3 UPDATEで変更する

既存の行を変更するには、`UPDATE`を使います。

```sql
UPDATE books
SET price = 1200
WHERE book_id = 10;
```

`WHERE`の条件で、変更する行を指定します。
実行前に同じ条件の`SELECT`で対象を確認することがあります。

### 4 WHEREを忘れたUPDATE

`WHERE`を書き忘れても、SQLの文法上は正しいことがあります。

```sql
UPDATE books
SET price = 1200;
```

この文は全行の価格を1200にします。
文法上正しくても、業務上は事故かもしれません。

変更件数に上限を設け、トランザクション内で確認し、本番で直接更新できる権限を絞って防ぎます。
変更前のバックアップと監査記録を持ち、検証済みの手順を使うことも対策です。

## 条件の判定と変更を一体で行う

### 5 条件付きの原子的更新

在庫が残るときだけ1冊減らします。

```sql
UPDATE books
SET stock = stock - 1
WHERE book_id = 10
  AND stock > 0;
```

更新件数が1なら成功、0なら在庫なしです。

アプリが先に在庫を読み、後で書く2段階より、1文の条件付き更新としてDBMSに任せると、間への割込みを防ぎやすくなります。
貸出行の追加まで同じトランザクションにします。

### 6 DELETEで行を削除する

行を削除するには、`DELETE`を使います。

```sql
DELETE FROM loans
WHERE loan_id = 101;
```

表構造は残し、条件に合う行を削除します。
`WHERE`なしなら全行です。

外部キーが参照する行の削除は拒否、連鎖削除、NULL設定など定義に従います。

### 7 論理削除

物理的に行を消さず、状態や削除日時を付ける方法があります。

```text
deleted_at = 2026-07-14 15:00
```

履歴や復元に使えますが、すべての検索で削除済みの行を除外する必要があります。
一意制約も複雑になり、個人情報が消えずに残ります。
表や索引が増え続ける費用もあります。
法的な削除要求にも、印を付けるだけでは足りない場合があります。

### 8 MERGEなどの更新

存在すれば更新、なければ追加する処理を表す`MERGE`などがあります。
製品ごとの競合時の動作を確認します。

アプリで「存在確認→INSERT」と分けると、同時に2処理が存在なしと判断し、主キー重複する競合があります。
最後にはDBの一意制約で、重複を拒否します。

## 公開する範囲とDB側の処理を定める

### 9 ビューを作る

元の表を直接見せず、必要な行と列だけを公開したい場合があります。
検索結果へ名前を付ければ見せ方を固定できますが、ビューを作っただけで基表への権限まで自動的に安全になるとは限りません。

```sql
CREATE VIEW active_loans AS
SELECT l.loan_id, u.name, b.title, l.loaned_on
FROM loans AS l
JOIN users AS u ON u.user_id = l.user_id
JOIN books AS b ON b.book_id = l.book_id
WHERE l.returned_on IS NULL;
```

利用者は、次のように1つの表として読めます。

```sql
SELECT * FROM active_loans;
```

### 10 ビューと安全性

ビューは外部スキーマを実装する手段の1つであり、個人情報の列を含めずに公開できます。
ただし、ビューを作るだけで常に安全になるとは限りません。
元の表への直接権限を与えず、必要なら行ごとの制御も設計します。

副問合せ、エラー、集計から秘密を推測できないかも考えます。
公開範囲を変えるビュー定義の変更も管理します。

### 11 更新可能なビュー

1つの実表の行に一意に対応する単純なビューは更新できる場合があります。

集約、`DISTINCT`、集合演算、複雑な結合を含むビューは、変更をどの元行に反映するか決められず、更新不可能になりやすいです。

製品の条件を確認します。

### 12 TRIGGER

表への追加、更新、削除などをきっかけに自動実行する仕組みが**TRIGGER**、トリガです。

監査行の作成、複雑な制約、派生値更新などに使えます。

一方、アプリのSQLから見えない副作用、連鎖、性能、実行順、再帰が問題になります。
規則の置き場所と試験方法を明確にします。

### 13 ストアドプロシージャ

DB側に保存して呼び出す一連の処理がストアドプロシージャです。

通信往復を減らす、権限を処理単位にする、共通手順をDB近くに置く利点があります。
製品依存、版管理、テスト、責任分担を管理します。

## 仕事に必要な権限を割り当てる

### 14 GRANT

利用者や役割に権限を与える命令が`GRANT`です。

```sql
GRANT SELECT ON books TO librarian_reader;
GRANT SELECT, INSERT, UPDATE ON loans TO loan_operator;
```

接続する権限に加えて、`SELECT`の**参照権限**、`INSERT`の**挿入権限**、`UPDATE`の更新権限、`DELETE`の**削除権限**などがあります。
表やビューを定義する権限も管理対象です。

仕事に必要な権限を、最小限だけ与えます。

### 15 REVOKE

与えた権限を取り消すには、`REVOKE`を使います。

```sql
REVOKE UPDATE ON loans FROM loan_operator;
```

別の役割経由でも同じ権限を持つなら、完全には失わない場合があります。
継承関係を確認します。

### 16 役割、ロール

個人1人ずつに権限を設定する代わりに、仕事ごとの**ロール**に権限を付け、人を所属させます。

```text
貸出担当ロール → 貸出の参照・追加・更新
監査担当ロール → 監査ビューの参照
```

異動や退職の際に所属を外しやすくなります。
強い権限を持つ人の兼務や相互牽制も見直します。

## アプリから値と処理を安全に渡す

### 17 アプリからSQLを使う

対話ツールで正しく動くSQLも、アプリから文字列連結すれば入力値が命令として解釈される危険があります。
SQLの構造と値を分け、接続とトランザクションの寿命も管理します。

入力を文字列連結してはいけません。

```text
危険な考え:
"SELECT ... WHERE name = '" + 入力 + "'"
```

入力がSQLの構造に混ざり、SQLインジェクションを起こします。

値の場所を印で示し、値を別に渡す**プレースホルダ**、準備済み文を使います。

```sql
SELECT user_id, name
FROM users
WHERE name = ?;
```

`?`に値として渡せない表名や並べ替え列は、許可した候補との対応表から選びます。

### 18 埋込みSQL

Cなどの親言語の中にSQL文を書き、事前処理して利用する方式が**埋込みSQL**です。

親言語の変数とDB列の型、NULL表示、エラー、トランザクション境界を対応付けます。
SQLを別モジュールとして呼ぶ**モジュール言語**の考えもあります。

現代のドライバやORMでも、言語とDBの間で型、NULL、例外を対応付ける問題は同じです。

### 19 カーソル

問合せ結果を1件ずつ処理する場合に、その行を指す位置や仕組みが**カーソル**です。

典型的な流れは次です。

```text
DECLARE  カーソルを宣言
OPEN     問合せを開始
FETCH    現在行を変数へ読む
FETCH    次の行を読む
...
CLOSE    終了
```

製品や埋込み方式で構文は違います。

### 20 カーソルと集合処理

1行ずつ複雑な外部処理をするならカーソルが必要な場合があります。
しかし、100万行を1行ずつ更新すると、集合として1文で更新するより遅くなりやすいです。

```sql
UPDATE books
SET price = price * 1.05
WHERE category = '科学';
```

DBMSは全体を最適化できます。
まず集合処理で表せないか考え、必要な場合にカーソルを使います。

### 21 非カーソル操作

1行だけ返す検索、集合を一括更新する処理など、カーソルで逐次読取りをしない操作が**非カーソル操作**です。

大量データをすべてアプリに運んでから絞るより、DB側で必要な行や列、集計結果に絞ります。

## 接続と変更結果を管理する

### 22 接続プール

アプリがDBに接続するたび、通信、認証、状態の準備に費用がかかります。
既存接続を再利用する**接続プール**があります。

大きくしすぎるとDBMSの同時接続数、主記憶の使用量、ロック競合が増えます。
待ち行列、処理時間、DB容量に合わせます。
返却漏れや、接続に残ったトランザクション状態に注意します。

### 23 変更件数を確認する

更新や削除の後には、影響を受けた行数を確認します。

```text
予定1行、実績0行 → 対象なし・競合・条件誤り
予定1行、実績5000行 → 条件誤りの疑い
```

件数だけで正しさは保証できませんが、重要な異常検知です。

在庫1件を減らす更新では、読取り後に値を計算するより、`在庫 >= 注文数`を更新条件へ含めた1文で判定と変更を行う方が競合に強くなります。
それでも、影響行数が0件なら在庫不足か競合かをアプリが判断し、5000件なら条件誤りを疑わなければなりません。
更新文、権限、トランザクション、変更件数は、同じ変更を安全に確定するための、役割の異なる仕組みです。
