# 第6章 第9話 SQLと表の定義

利用者番号1025の行を探すために、保存装置の番地や探索順まで指定する必要はありません。
アプリは欲しい結果を示し、DBMSが索引や表走査を選びます。
ただし、値を検索できるだけでは、重複番号や存在しない利用者への貸出を防げません。

関係DBに、「利用者という表を作ってほしい」「番号1025の利用者を探してほしい」と伝えるための代表的な言語が**SQL**です。

SQLは一般にStructured Query Languageに由来する名前として扱われます。
製品ごとに拡張や細かな違いがありますが、標準化された共通の仕様があります。

## DBMSへ伝える要求をSQLで表す

### 1 SQLは何を伝えるか

多くのSQLでは、保存装置のどの位置から何バイト読むかという手順を書きません。
欲しい結果や行う変更を宣言します。

```sql
SELECT name
FROM users
WHERE user_id = 1025;
```

これはおおまかに、

```text
users表から
user_idが1025の行について
name列を取り出す
```

という意味です。

### 2 SQL文の見た目

```sql
SELECT name
FROM users
WHERE user_id = 1025;
```

`SELECT`、`FROM`、`WHERE`はSQLの予約語です。
`users`、`name`、`user_id`は設計者が付けた名前で、`1025`は数値です。
最後の`;`が1文の終わりを表します。

予約語の大文字と小文字を区別しない製品が多く、読みやすさのために予約語を大文字で書く慣習があります。
名前の大文字と小文字、引用規則は製品ごとに確認します。

### 3 コメント

処理意図を人に説明する文字がコメントです。

```sql
-- 返却されていない貸出を調べる
SELECT loan_id
FROM loans
WHERE returned_at IS NULL;
```

コメントは実行結果を変えません。
ただし古い説明を残すと誤解を生むため、コードと一緒に更新します。

## 構造の定義とデータの操作を分ける

### 4 SQLの大きな分類

#### 4.1 DDL

表、ビュー、スキーマなどの構造を定義する言語が**DDL**、Data Definition Language、データ定義言語です。

代表は`CREATE`、`ALTER`、`DROP`です。

#### 4.2 DML

定義した構造に対して、データの検索、追加、変更、削除を行う言語が**DML**、Data Manipulation Language、データ操作言語です。

代表は`SELECT`、`INSERT`、`UPDATE`、`DELETE`です。

#### 4.3 権限とトランザクション

`GRANT`、`REVOKE`で権限を扱い、`COMMIT`、`ROLLBACK`で一連の変更を確定したり取り消したりします。
分類名は教材や製品で細分されることがあります。
命令の役割を理解します。

### 5 独立言語方式と親言語方式

SQLを対話用画面やコマンドから単独で実行する使い方が**独立言語方式**、会話型SQL、コマンド方式です。

プログラム言語のコードからSQLを利用する使い方が**親言語方式**です。
SQLをコード中に書く**埋込みSQL**、ライブラリやドライバから呼ぶ方式などがあります。

画面フォームに条件を入力すると、内部で問合せを組み立てる道具もあります。

## 表へ保存できる値を定義する

### 6 表を作るCREATE TABLE

SQLの分類を覚えるだけでは、無効な値をどこで止めるかは決まりません。
表の定義時に型、主キー、NULLの可否、参照関係を宣言すれば、どのアプリから更新しても同じ規則を適用できます。

利用者表を定義します。

```sql
CREATE TABLE users (
  user_id       INTEGER      NOT NULL,
  name          VARCHAR(100) NOT NULL,
  registered_on DATE         NOT NULL,
  member_type   VARCHAR(20)  NOT NULL,
  PRIMARY KEY (user_id)
);
```

この文は、`users`という表を作る定義です。
`user_id`を必須の整数、`name`を最大長を持つ必須の文字列とします。
`registered_on`は必須の日付、`member_type`は必須の文字列です。
最後に、`user_id`を主キーと定めています。

### 7 データ型

列に入れる値の種類が**データ型**です。

#### 7.1 数値型

整数には`INTEGER`、十進の固定小数点には`DECIMAL(p,s)`を使います。
後者は合計p桁、小数部s桁などと指定します。
浮動小数点型は、非常に広い範囲を近似で扱います。

金額を二進浮動小数点で近似すると端数問題が起こるため、必要な十進桁を正確に扱う型を検討します。

#### 7.2 文字型

固定長の文字列には`CHAR(n)`、可変長の文字列には`VARCHAR(n)`を使います。

文字数とバイト数、末尾空白、照合順序、大小文字の扱いは製品や設定によって異なります。

#### 7.3 日付型と時刻型

日付を扱う**日付型**が`DATE`、時刻を扱う型が`TIME`です。
`TIMESTAMP`は日付と時刻を扱います。

時刻帯を持つか、夏時間をどう扱うかを確認します。
日時を単なる文字列にすると、存在しない日付や並べ替えの問題が起きます。

#### 7.4 真偽値、二進データ、大きな値

真偽値、バイト列、大きな文字や画像を扱う型があります。
製品差があります。
巨大なデータをDB内に置くか、外部保存して参照だけ持つかは、整合性、バックアップ、配信性能で決めます。

### 8 列制約

列のすぐ後ろに規則を書けます。

```sql
score INTEGER NOT NULL CHECK (score BETWEEN 0 AND 100)
```

`NOT NULL`はNULLを許さない**非NULL制約**です。
`UNIQUE`は重複を許さない一意性制約、`CHECK`は条件を満たさせる検査制約です。
`DEFAULT`には、値を省略したときの既定値を指定します。

`DEFAULT`は「分からない値」を勝手に0にする機能ではありません。
業務上本当に既定値が決まる場合に使います。

## 表全体の制約と参照先を定める

### 9 表制約

複数列をまとめる制約は、表の要素として書くと読みやすくなります。

```sql
CREATE TABLE results (
  student_id INTEGER NOT NULL,
  subject_id INTEGER NOT NULL,
  score      INTEGER CHECK (score BETWEEN 0 AND 100),
  PRIMARY KEY (student_id, subject_id)
);
```

主キーが2列の組であることが明確です。

### 10 外部キー制約

別の表との対応関係は、外部キー制約で定義します。

```sql
CREATE TABLE loans (
  loan_id  INTEGER PRIMARY KEY,
  user_id  INTEGER NOT NULL,
  book_id  INTEGER NOT NULL,
  loaned_on DATE NOT NULL,
  FOREIGN KEY (user_id) REFERENCES users(user_id),
  FOREIGN KEY (book_id) REFERENCES books(book_id)
);
```

`REFERENCES`は参照先を示します。
存在しない利用者や本についての貸出を防ぎます。

### 11 CASCADE

参照先の更新や削除に合わせ、参照側に処理を連鎖させる指定が`CASCADE`です。

```sql
FOREIGN KEY (user_id) REFERENCES users(user_id)
  ON DELETE CASCADE
```

利用者を削除すると、その利用者の貸出も消える指定です。
貸出履歴を残す業務なら不適切です。
便利な構文ではなく、業務上の削除方針として選びます。

## 定義の変更と製品差を扱う

### 12 ALTER TABLE

作成した表の定義を変更するには、`ALTER TABLE`を使います。

```sql
ALTER TABLE users
ADD COLUMN email VARCHAR(254);
```

巨大な表に列や制約を追加すると、長いロック、全行の検査、保存容量の増加を伴う場合があります。
本番では製品の実行方法、退避、戻し方を確認します。

### 13 DROP

定義ごと削除する命令が`DROP`です。

```sql
DROP TABLE users;
```

行だけでなく表構造を削除します。
`DELETE`とは違います。
関連するビューや外部キーへの影響と、バックアップを確認します。

### 14 名前と予約語

表名や列名に予約語、空白、特殊文字を使うと、引用符が必要になり移植や入力が難しくなります。
意味が明確で一貫した命名規則を決めます。

```text
悪い例: data1, item, value
改善例: loaned_on, returned_on, member_type
```

ただし長すぎる名前も読みにくくなります。
略語辞書を整えます。

### 15 スキーマという名前空間

SQLでは、表などをまとめる名前空間も**スキーマ**と呼びます。

```text
library.users
library.loans
accounting.payments
```

3層スキーマの一般概念と、SQL製品の名前空間としてのスキーマは関連しますが、完全に同じ意味ではありません。
どの意味で使っているかを文脈から確認します。

### 16 方言と標準

自動採番、文字列結合、日付計算、ページ分割、真偽型などは製品差があります。

```text
標準で共通する考えを学ぶ
使用製品の仕様を確認する
移植が必要な箇所を分離する
```

SQLが動いたことと、他製品でも同じ結果や性能になることは別です。

### 17 文字列と数値を区別する

表の型を定義しても、SQL文中の値を誤った型として渡せば、暗黙変換や比較の違いが生じます。
値の見た目ではなく、文字列、数値、日付として何を渡しているかを区別します。

文字列は引用符で囲みます。

```sql
'山田花子'
'2026-07-14'
```

数値は通常囲みません。

```sql
1025
80.5
```

日付リテラルの標準的な書き方や暗黙変換は製品差があります。
値を文字列連結せず、後に学ぶプレースホルダで型と値を渡します。

利用者番号1025を探すSQLは、結果の条件をDBMSへ伝えます。
一方、主キーや外部キーを表定義へ置けば、別のアプリが更新しても番号の重複と不正な参照を拒否できます。
SQLは検索手順を細かく命令する言語ではなく、欲しい結果と守る構造をDBMSへ宣言する言語です。
