# 第6章 第9話 SQLと表の定義

利用者番号1025の行を探すために、物理的な記憶位置や探索順まで指定する必要はありません。
アプリは欲しい結果を示し、DBMSが索引や表走査を選びます。
ただし、値を検索できるだけでは、重複番号や存在しない利用者への貸出を防げません。

関係DBに、「利用者という表を作ってほしい」「番号1025の利用者を探してほしい」と伝えるための代表的な言語が**SQL**です。

SQLは一般にStructured Query Languageに由来する名称として親しまれています。
製品ごとに拡張や細かな違いがありますが、国際標準化された共通の仕様が存在します。

## DBMSへ伝える要求をSQLで表す

### 1 SQLは何を伝えるか

多くのSQLでは、ディスクのどの位置から何バイト読むかという物理的な手順を書きません。
欲しい結果や行う変更を宣言的に記述します。

```sql
SELECT name
FROM users
WHERE user_id = 1025;
```

これをおおまかに読み解くと、次の内容になります。

```text
users表から
user_idが1025の行について
name列を取り出す
```

### 2 SQL文の見た目

```sql
SELECT name
FROM users
WHERE user_id = 1025;
```

`SELECT`、`FROM`、`WHERE`はSQLの予約語です。
`users`、`name`、`user_id`は設計者が付けた識別名で、`1025`は具体的な数値を表しています。
文末のセミコロン「;」がSQL文の終端を示す記号です。

予約語の大文字と小文字を区別しない製品が多いものの、可読性のために予約語を大文字で統一する慣習が広く定着しています。
識別名の大文字小文字の扱い、引用符の規則については製品ごとの仕様確認が欠かせません。

### 3 コメント

処理意図を人に説明する文章がコメントです。

```sql
-- 返却されていない貸出を調べる
SELECT loan_id
FROM loans
WHERE returned_at IS NULL;
```

コメントを記述しても実行結果は変わりません。
ただし古い説明を残すと誤解を生むため、コードの修正と歩調を合わせて更新します。

## 構造の定義とデータの操作を分ける

### 4 SQLの大きな分類

#### 4.1 DDL

表、ビュー、スキーマなどの論理構造を定義する分類が**DDL**（Data Definition Language、データ定義言語）です。

代表的な命令として`CREATE`、`ALTER`、`DROP`が挙げられます。

#### 4.2 DML

定義された構造に対して、データの検索、追加、更新、削除を実行する分類が**DML**（Data Manipulation Language、データ操作言語）です。

こちらは`SELECT`、`INSERT`、`UPDATE`、`DELETE`が中心的な命令を構成します。

#### 4.3 権限とトランザクション

`GRANT`や`REVOKE`で権限を制御し、`COMMIT`や`ROLLBACK`で一連のデータ更新を確定または破棄します。
命令の分類名は教材や製品によって細分化される場面も少なくありません。
まずは各命令が担う役割の区別を確実に押さえておく必要があります。

### 5 独立言語方式と親言語方式

SQLを対話用画面や端末コマンドから単独で実行する使い方が**独立言語方式**（会話型SQL、コマンド方式）です。

汎用プログラミング言語のコード内からSQLを呼び出す使い方が**親言語方式**です。
SQL文をソースコード中に直接記述する埋込みSQLや、ライブラリ・ドライバを経由して発行する方式などが含まれます。

画面フォームに条件を入力すると、背後で問合せを自動生成するツールも普及しています。

## 表へ保存できる値を定義する

### 6 表を作るCREATE TABLE

SQLの構文分類を暗記しただけでは、無効なデータの混入を阻止できません。
表の定義時にデータ型、主キー、NULLの可否、外部参照関係を宣言することで、あらゆるアプリケーションからの更新に対して厳密な整合性を保てます。

利用者表の定義例を見てみましょう。

```sql
CREATE TABLE users (
  user_id       INTEGER      NOT NULL,
  name          VARCHAR(100) NOT NULL,
  registered_on DATE         NOT NULL,
  member_type   VARCHAR(20)  NOT NULL,
  PRIMARY KEY (user_id)
);
```

このDDL文は、`users`という新しい表を構築する定義です。
`user_id`を必須の整数型、`name`を最大100文字の必須文字列型として指定します。
`registered_on`は必須の日付型、`member_type`は必須の文字列型です。
最後に`user_id`を主キーとして確定させています。

### 7 データ型

列に格納可能な値の種類や性質を定めたものが**データ型**です。

#### 7.1 数値型

整数には`INTEGER`、十進の固定小数点数には`DECIMAL(p,s)`を用います。
後者は全体の有効桁数をp桁、小数部をs桁といった形式で厳密に指定する仕組みです。
一方で浮動小数点型は、極めて広大な数値範囲を近似値として表現します。

金額計算を二進浮動小数点で近似すると丸め誤差が生じるため、所定の十進桁数を正確に保持できるデータ型の選択が不可欠です。

#### 7.2 文字型

固定長の文字列には`CHAR(n)`、可変長の文字列には`VARCHAR(n)`を使用します。

指定長がバイト数か文字数か、末尾の空白をどう扱うか、照合順序（Collation）や大文字小文字の区別基準は、DBMS製品の設定に依存します。

#### 7.3 日付型と時刻型

暦日を扱う日付型が`DATE`、時刻を扱う型が`TIME`です。
`TIMESTAMP`は日付と時刻を統合して管理する型です。

タイムゾーン情報の有無や、夏時間の補正規則を事前に確認しておく必要があります。
日時を単なる文字列型で代用してしまうと、不正日付の混入や時系列の並べ替え異常を招きかねません。

#### 7.4 真偽値、二進データ、大きな値

論理値を扱う真偽型、バイナリ列を扱う型、長文テキストや画像などの巨大オブジェクトを扱う型も存在します。
製品ごとの仕様差異が顕著な領域です。
巨大データをデータベース内に直接格納するか、外部ストレージに保存して参照パスのみを保持するかは、保全性、バックアップ容量、配信性能を総合して決定します。

### 8 列制約

列定義の直後に続けて、制約ルールを付加できます。

```sql
score INTEGER NOT NULL CHECK (score BETWEEN 0 AND 100)
```

`NOT NULL`はNULLの格納を拒絶する非NULL制約です。
`UNIQUE`は値の重複を許さない一意性制約、`CHECK`は指定した条件式の成立を強制する検査制約です。
`DEFAULT`句を用いれば、値が省略された際の既定値を設定できます。

`DEFAULT`は「不明な値」を安易にゼロで埋める道具ではありません。
業務ルールとして正当な初期値が確定している場合に限って指定します。

## 表全体の制約と参照先を定める

### 9 表制約

複数列を組み合わせた制約や明確な主キー宣言は、表全体の要素として記述すると見通しが良くなる設計です。

```sql
CREATE TABLE results (
  student_id INTEGER NOT NULL,
  subject_id INTEGER NOT NULL,
  score      INTEGER CHECK (score BETWEEN 0 AND 100),
  PRIMARY KEY (student_id, subject_id)
);
```

主キーが2列の複合キーで構成されている事実が一目で分かります。

### 10 外部キー制約

他の表との論理的な参照関係を保証するのが外部キー制約です。

```sql
CREATE TABLE loans (
  loan_id  INTEGER PRIMARY KEY,
  user_id  INTEGER NOT NULL,
  book_id  INTEGER NOT NULL,
  loaned_on DATE NOT NULL,
  FOREIGN KEY (user_id) REFERENCES users(user_id),
  FOREIGN KEY (book_id) REFERENCES books(book_id)
);
```

`REFERENCES`句は参照先となる親表とキー列を明示する構文です。
親表に実在しない利用者や蔵書に対する不正な貸出登録をデータベース側で確実に遮断します。

### 11 CASCADE

親レコードの更新や削除に連動させ、子レコード側も自動追従させる指定が`CASCADE`です。

```sql
FOREIGN KEY (user_id) REFERENCES users(user_id)
  ON DELETE CASCADE
```

親である利用者を削除すると、紐づく貸出履歴も自動的に削除されます。
過去の貸出履歴を監査用として永続保持すべき業務要件であれば、安易なCASCADEの適用は危険を伴います。
構文の手軽さだけで判断せず、業務要件に合致した正当な削除方針に基づいて採用の可否を判断しなければなりません。

## 定義の変更と製品差を扱う

### 12 ALTER TABLE

既存の表定義を変更する際には`ALTER TABLE`文を実行します。

```sql
ALTER TABLE users
ADD COLUMN email VARCHAR(254);
```

巨大な表に対して列や制約の追加を行うと、長時間の排他ロックや全件スキャン、記憶領域の急増を招くケースがあります。
本番環境での変更作業では、DBMSの実行方式やロールバック手順を事前に検証しておくべきです。

### 13 DROP

表や索引などのオブジェクトを定義ごと消去する命令が`DROP`です。

```sql
DROP TABLE users;
```

レコードの中身のみならず、表の構造定義そのものを辞書から抹消します。
行データのみを消去する`DELETE`文とは目的が根本から異なるわけです。
依存するビューや外部キーへの連鎖的な影響を精査し、バックアップの確保を徹底します。

### 14 名前と予約語

表名や列名に予約語、空白、特殊文字を用いると、特殊な引用符による囲みが必要となり移植性や保守性が損なわれます。
業務意図が明確で統一された命名基準を設けるべきです。

```text
悪い例: data1, item, value
改善例: loaned_on, returned_on, member_type
```

ただし極端に冗長な名称も可読性を低下させます。
プロジェクト内で用語辞書を整備し、適切な略語ルールを共有することが有効です。

### 15 スキーマという名前空間

SQLの世界では、表やビューを束ねる名前空間の単位をスキーマと呼びます。

```text
library.users
library.loans
accounting.payments
```

ANSI/SPARCの3層スキーマという理論概念と、DBMS製品が備える名前空間としてのスキーマは、関連を持ちつつも対象範囲が一致しません。
議論の文脈が理論モデルを指すのか、具体的な製品機能を指すのかを見極めて理解を深めます。

### 16 方言と標準

自動採番、文字列結合演算子、日付の計算関数、ページネーション構文などは、DBMS各社の方言が色濃く残る分野です。

```text
標準SQLの共通基盤を習得する
使用する特定DBMSの独自仕様を把握する
移植が必要なモジュールを適切に分離する
```

あるDBMSで動作したSQLが、別製品でも同一の結果や性能を発揮するとは限りません。

### 17 文字列と数値を区別する

表の列型を適切に宣言していても、SQL文へ渡すリテラルの型指定を誤れば、暗黙の型変換や意図しない比較の不整合が生じます。
値の表面的な表記にとらわれず、文字列、数値、日付といった各データ型の本質を意識した記述が必要です。

文字列リテラルは常に単一引用符（シングルクォート）で囲んで表現します。

```sql
'山田花子'
'2026-07-14'
```

数値リテラルは引用符を付けずに記述するのが原則です。

```sql
1025
80.5
```

日付リテラルの解釈や暗黙の変換規則には製品ごとの癖が存在します。
アプリケーションから動的に値を渡す際は、文字列連結を避け、後述するプレースホルダ（バインド機構）を活用するのが定石です。

利用者番号1025を検索するSQL文は、求める結果の条件をDBMSへ宣言的に伝えます。
一方で主キーや外部キーを表定義に組み込んでおけば、どの外部アプリから更新要求が飛んできても、重複や不正参照をデータベース自身が断固として拒絶できるわけです。
SQLは検索手順を逐一命令する手続き言語を超えて、求める結果の条件と守るべきデータの整合構造をDBMSへ明確に宣言する言語なのです。
