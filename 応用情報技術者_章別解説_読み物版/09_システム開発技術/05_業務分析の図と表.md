# 第9章 第5話 業務分析の図と表

長い文章だけで業務を説明すると、読み手ごとに異なる場面を想像します。
図や表では、見たい関係を限定して表します。
漏れや矛盾を見つけ、関係者が同じ対象について話すために使うもので、文章を飾ることが目的ではありません。

## 利用者の目的と、システムとのやり取りを表す

### 1 図法を名前から選ばない

図法の名前を選ぶ前に、「何を知りたいか」を決めます。
目的と表現方法の対応は、次のように整理できます。

| 知りたいこと | 主な表現 |
|---|---|
| 誰が何の目的で使うか | ユースケース |
| 1件の利用場面 | シナリオ |
| 小さな価値要求 | ユーザーストーリー |
| データがどこからどこに流れるか | DFD |
| 情報の種類と関係 | E-R図 |
| 条件の組合せと行動 | 決定表 |
| 状態と出来事による変化 | 状態遷移図・表 |
| 見た目・操作 | モックアップ・プロトタイプ |

どの図も、同じシステムを異なる角度から見ています。
一つの図で、すべてを表そうとはしません。

### 2 ユースケース

利用者や外部システムが、一つの目的を達成するためにシステムとやり取りするまとまりが**ユースケース**です。
欠席連絡なら、欠席を登録する、登録を訂正する、学級の連絡を確認する、電話連絡を代理入力するといったものがあります。

「登録ボタンを押す」という1回の操作より広く、利用者にとって意味のある目標を表します。

### 3 アクター

そのユースケースに関わる役割を**アクター**といいます。

```text
保護者 ── 欠席を登録する
担任   ── 学級の連絡を確認する
職員   ── 電話連絡を代理入力する
認証サービス ── 利用者を認証する
```

アクターは特定の個人を指すものではありません。
1人が保護者と学校職員の2役を持つこともあります。
人以外の時刻装置や外部システムも、アクターになり得ます。

### 4 ユースケース図

アクターとユースケースの関係を図示したものが**ユースケース図**です。

```text
        ┌──── 欠席連絡システム ────┐
保護者 ── (欠席を登録する)          │
保護者 ── (登録を訂正する)          │
担任   ── (学級一覧を確認する)      │
        └──────────────────────┘
```

図だけでは、入力、順番、例外、業務規則を十分に表せません。
詳しいユースケース記述を添えます。

### 5 ユースケース記述

図に表した目的を、操作の流れや条件として具体化します。
欠席登録のユースケース記述は、次のようになります。

```text
名称：欠席を登録する
主アクター：保護者
目的：当日の欠席を学校へ伝える
事前条件：保護者が認証済み、児童との関係が有効
きっかけ：保護者が欠席登録を選ぶ

基本フロー：
1 対象児童を選ぶ
2 区分・理由を入力する
3 システムが権限、締切、入力を確認する
4 システムが保存し、受付番号を示す

代替・例外：
3a 締切後なら代理電話を案内する
3b 既登録なら訂正・取消しを案内する
4a 保存失敗なら未受付と明示し、再試行方法を示す

事後条件：一件だけ記録され、担任一覧へ反映可能
```

正常な基本フローだけでなく、代替・例外のフローと事後条件も書きます。

### 6 振舞いとシナリオ

システムやアクターが見せる動作を**振舞い**といいます。
ユースケースで起こり得る一つの具体的な経路が**シナリオ**です。

```text
ユースケース：欠席を登録する
シナリオA：通常登録に成功
シナリオB：締切後で電話を案内
シナリオC：通信切断後に再送し、二重登録を防ぐ
```

ユースケースは経路の集まりで、シナリオはその中の1つの経路だと考えます。

## 利用者の価値を、小さく確かめられる単位にする

### 7 ユーザーストーリー

利用者の立場、欲しいこと、価値を短く表す形式が**ユーザーストーリー**です。

```text
保護者として、当日の欠席をスマートフォンから登録したい。
そうすれば、混雑する電話を待たず学校へ伝えられる。
```

よく使われる形式は、次のようになります。

```text
＜役割＞として、＜機能・能力＞が欲しい。
それは＜価値・目的＞のためである。
```

短い文だけでは、完全な仕様にはなりません。
会話、受入れ条件、例、設計、テストが必要です。

### 8 エピック

1回の短い開発期間で実現するには大きすぎるストーリーを**エピック**と呼びます。

```text
エピック：学校への全連絡をオンライン化する
  ├─ 欠席を登録する
  ├─ 遅刻・早退を登録する
  ├─ 学校から一斉連絡する
  └─ 保護者が受領確認する
```

エピックは、利用者の価値を保った小さなストーリーへ分けます。
画面層だけ、DB層だけに分けると、1回の開発期間で利用できる価値が完成しません。

### 9 良いストーリーのINVEST

分けたストーリーを点検する観点として、**INVEST**があります。

- Independentは、できるだけ独立していることです。
- Negotiableは、詳細を対話で調整できることです。
- Valuableは、利用者や事業に価値があることです。
- Estimableは、おおよその大きさを見積もれることです。
- Smallは、短い期間で完成できる大きさです。
- Testableは、受入れ条件を試験できることです。

完全な独立が無理な場合は、依存関係を見えるようにします。

### 10 受入れ条件

ストーリーが完成したと判断する、具体的な条件が**受入れ条件**です。
欠席登録なら、締切直前の送信がどう扱われるかも条件にします。

```text
前提：認証済み保護者が本人の児童を選んでいる
もし：8時29分59秒に有効な欠席内容を送る
なら：一件登録され、受付番号が表示される

前提：同じ登録が既に受理済み
もし：同じ要求IDで再送する
なら：二件目を作らず、最初の受付番号を返す
```

正常、境界、例外を含めて定めます。

### 11 ストーリーポイント

ストーリー同士の相対的な大きさを表す数値が**ストーリーポイント**です。
作業量、複雑さ、不確実性などをチームで比較します。
「1点=1日」と固定する時間単位ではありません。

異なるチームの点数を成績のように比較せず、同じチームが計画と学習に使います。

## データの流れから処理を分析する

### 12 DFD

利用者の目的とは別に、業務をデータの流れから捉える方法もあります。
データがどこから来て、どの処理で変わり、どこへ保存・出力されるかを表す図が**DFD**、Data Flow Diagramです。
基本要素は4つあります。

境界外でデータを出したり受けたりする人やシステムが**外部実体**で、源泉と吸収ともいいます。
データを変換する処理が**プロセス**、流れるデータが**データフロー**、データを保存する場所が**データストア**です。

### 13 DFDの例

欠席連絡をDFDで表すと、次のようになります。

```text
[保護者]
   │ 欠席内容
   ▼
(欠席を受け付ける) ── 欠席記録 ──> ||欠席データ||
   │ 受付結果                         │
   ▼                                  │ 当日一覧
[保護者]                              ▼
                               (一覧を作る) → [担任]
```

矢印には「欠席内容」「受付結果」のように、データ名を書きます。
「電話する」のような制御や動作だけを、データフローとして表すことはしません。

### 14 コンテキストダイアグラム

対象システム全体を一つのプロセスとして描き、外部実体との出入りを示す最上位のDFDが**コンテキストダイアグラム**です。

```text
保護者 ──欠席内容──> (欠席連絡システム) ──当日一覧──> 担任
保護者 <─受付結果──  (                 ) <─児童名簿── 名簿システム
```

内部の詳細へ進む前に、境界と外部接点の確認に使います。

### 15 段階的詳細化

大きなプロセスを、内部の小さなプロセスへ順に分けることが**段階的詳細化**です。

```text
(欠席を受け付ける)
  ├─ (利用者と児童の関係を確認する)
  ├─ (入力と締切を確認する)
  ├─ (欠席を記録する)
  └─ (通知を予約する)
```

分ける際は、上位プロセスに入出力するデータと、下位図全体に入出力するデータを一致させます。
これを、DFDのバランスといいます。

### 16 ミニスペック

DFDでは、データの流れを表せても、細かな判断手順は表しにくくなります。
最下位のプロセスについて、処理規則を文章、決定表、構造化された記述などで詳しく補ったものが**ミニスペック**です。

### 17 構造化分析法

DFD、データ辞書、ミニスペックなどを使い、複雑な業務やシステムを上位から段階的に分析する考えが**構造化分析法**です。
処理とデータの流れを中心に、境界から内部へと分析を詳しくしていきます。
後の構造化設計とも関連します。

## 管理する情報と、その関係を表す

### 18 E-R図

データが流れる経路に加え、情報そのものの関係も捉えます。
業務で扱う情報を、実体と関連として表す図が**E-R図**、Entity-Relationship Diagramです。

識別して管理したい対象を**実体、エンティティ**、実体が持つ性質を**属性**といいます。
実体同士の結び付きを**関連、リレーションシップ**といいます。

```text
保護者(保護者ID, 氏名)
   1
   │
   │ 0..*  保護する
   ▼
児童(児童ID, 氏名, 学級)
   1
   │ 0..*
   ▼
欠席連絡(連絡ID, 日付, 区分, 理由)
```

### 19 多重度

一つの実体が、相手側のいくつの実体と関係できるかを**多重度**、カーディナリティといいます。

- `1`は、必ず1つです。
- `0..1`は、なくてもよく、最大1つです。
- `0..*`は、0個以上です。
- `1..*`は、1個以上です。

多重度は、現実の規則を確認して定めます。
1人の児童に複数の保護者がいることや、保護者に兄弟である複数の子がいることなど、単純な1対多で表せない場合には、中間の関係実体を設けます。

### 20 データ中心設計

処理手順は変わりやすい一方、業務で管理する情報と関係は比較的安定する場合があります。
データの構造と整合性を中心にシステムを設計する考えを**データ中心設計**といいます。

ただし、データだけを見て、利用者の操作、時間、障害を無視してよいという意味ではありません。
処理、状態、責任と組み合わせて考えます。

## 条件と状態に応じた動作を確かめる

### 21 決定表

複数条件の組合せと、そのとき行う処理を表すものが**決定表**、デシジョンテーブルです。

| 条件・処理 | 規則1 | 規則2 | 規則3 | 規則4 |
|---|---:|---:|---:|---:|
| 正規保護者か | Y | Y | N | Y |
| 締切前か | Y | N | － | Y |
| 既登録か | N | － | － | Y |
| 新規登録 | X |  |  |  |
| 電話を案内 |  | X |  |  |
| 権限拒否 |  |  | X |  |
| 訂正を案内 |  |  |  | X |

`－`は、結果に影響しない条件です。
全組合せを調べ、同じ条件なのに処理が異なる箇所や、どの規則にも当てはまらない組合せを見つけます。

### 22 状態

条件の組合せだけでは、動作を決められないこともあります。
同じ操作でも、対象が現在どの段階にあるかによって結果が変わります。
この段階を**状態**といいます。

欠席連絡なら、下書き、受付済み、担任確認済み、取消済みなどです。
状態は単なる画面の表示名ではなく、許される操作と業務上の意味を持ちます。

### 23 状態遷移図

出来事によって状態がどう変わるかを表すものが**状態遷移図**です。

```text
[下書き] --送信・条件OK--> [受付済み]
   │                         │
   └--破棄--> [終了]         ├--担任確認--> [確認済み]
                             └--取消し--> [取消済み]
```

矢印に出来事、条件、行動を書きます。
許される遷移だけでなく、禁止される遷移も確認します。

### 24 状態遷移表

状態と出来事の組合せを表にしたものが**状態遷移表**です。

| 現在状態＼出来事 | 送信 | 担任確認 | 取消し |
|---|---|---|---|
| 下書き | 受付済み | 不可 | 終了 |
| 受付済み | 二重防止 | 確認済み | 取消済み |
| 確認済み | 二重防止 | 変化なし | 条件付き取消済み |
| 取消済み | 不可 | 不可 | 変化なし |

図よりも全組合せを点検しやすく、未定義の動作を見つけられます。

## 試作品で操作と実現可能性を確かめる

### 25 モックアップ

図や表に加え、操作を試せるモデルも使います。
画面の配置、文字、操作の流れなどを確認するモデルが**モックアップ**です。
紙に描いたものでも構いません。

データ保存や外部接続が動かなくても、早い段階で使用性、項目の漏れ、用語の違いを確認できます。

### 26 水平型プロトタイプ

多数の画面や機能について、外観と画面間の移動を浅く作るものが**水平型プロトタイプ**です。

```text
ログイン → 児童選択 → 欠席入力 → 確認 → 完了
```

全体の操作や情報構成を確認しやすい一方、DB、性能、安全性など、内部の実現可能性は分かりにくい方式です。

### 27 垂直型プロトタイプ

一つの機能を、画面からDBや外部接続まで深く作るものが**垂直型プロトタイプ**です。
欠席登録1件だけを本番に近い技術で通し、認証、性能、データ、外部APIの実現可能性を確かめます。

全機能の使いやすさは分かりにくいため、水平型とは目的を分けます。

### 28 プロトタイプ版評価

試作品を作る前に、何の疑問に答えるために作るのかを定めます。
その目的に沿って、**プロトタイプ版評価**を行います。

```text
疑問：高齢の保護者が児童切替えを理解できるか
方法：対象利用者5人に課題を行ってもらう
観測：成功、時間、迷った箇所、発言
判断：配置を変更して再評価
```

「好評だった」という感想だけで判断せず、決めたいことについて証拠を集めます。

### 29 捨てる試作品と発展させる試作品

学習後に捨てる前提の試作品を、そのまま本番に使うと危険です。
簡易コード、仮データ、弱い認証、エラー処理不足が残るからです。

本番に発展させるなら、保守性、安全性、性能、試験、文書を最初から段階的に整えます。
どちらかを関係者に明示します。

## モデルを現実の業務と照合する

### 30 図と現実を照合する

図がきれいでも、現実の業務に合っているとは限りません。
現場の利用者が読める用語か、例外、障害、取消しを含むかを確かめます。
図同士の名前と境界が一致し、要件と追跡できるかも確認します。

版と承認を管理し、実際のデータや操作で試します。
図は合意と発見の道具であり、作成自体が目的ではありません。

### 31 モデルという言葉を整理する

**モデル**は、現実の全部ではなく、考えたい部分を選んで簡単に表したものです。
学校そのものを教室に持ち込めなくても、校内図なら部屋の位置を考えられるのと同じです。

仕事の人、手順、判断、情報を表す活動を**業務モデリング**といいます。
その結果の1つが**システム業務フロー**です。
業務フローには、誰が、何を受け取り、何を判断し、次に誰に渡すかを書きます。

データの種類と関係を表す活動が**データモデリング**です。
名前、生徒番号、欠席日など、個々の項目を**データ要素**と呼びます。
要素をどのまとまりにし、どう結び付けるかを表す抽象的な姿が**論理モデル**、実際の製品や保存場所に合わせた姿が**物理モデル**です。

**データベース又はデータ維持の要件**には、保存期間、正しさ、更新できる人、バックアップ、削除方法などを書きます。
「データを保存する」だけでは、必要な管理方法が決まりません。

業務を1枚の図へ押し込めると、見やすさと引き換えに別の関係が見えにくくなります。
目的、流れ、データ、規則、状態を異なる図や表で確かめ、同じ欠席連絡を重ねて見たときに、文章だけでは隠れていた漏れと矛盾が現れます。
