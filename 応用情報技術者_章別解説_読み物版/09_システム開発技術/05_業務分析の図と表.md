# 第9章・第5話　業務分析の図と表――目的、データ、規則、状態を別の角度から見る

長い文章だけで業務を説明すると、読み手ごとに異なる場面を想像します。

図や表は、文章を飾るためではありません。見たい関係を限定し、漏れ・矛盾を見つけ、関係者が同じ対象を話すために使います。

## 1 図法を名前から選ばない

最初に「何を知りたいか」を決めます。

| 知りたいこと | 主な表現 |
|---|---|
| 誰が何の目的で使うか | ユースケース |
| 一件の利用場面 | シナリオ |
| 小さな価値要求 | ユーザーストーリー |
| データがどこからどこへ流れるか | DFD |
| 情報の種類と関係 | E-R図 |
| 条件の組合せと行動 | 決定表 |
| 状態と出来事による変化 | 状態遷移図・表 |
| 見た目・操作 | モックアップ・プロトタイプ |

同じシステムを違う角度から見ます。一つの図で全部を表そうとしません。

## 2 ユースケース

利用者・外部システムが、一つの目的を達成するためにシステムとやり取りするまとまりを**ユースケース**といいます。

欠席連絡なら、次があります。

- 欠席を登録する。
- 登録を訂正する。
- 学級の連絡を確認する。
- 電話連絡を代理入力する。

「登録ボタンを押す」のような一操作より広く、利用者にとって意味ある目標を表します。

## 3 アクター

ユースケースに関わる役割を**アクター**といいます。

```text
保護者 ── 欠席を登録する
担任   ── 学級の連絡を確認する
職員   ── 電話連絡を代理入力する
認証サービス ── 利用者を認証する
```

アクターは特定個人でなく役割です。一人が保護者と学校職員の二役を持つこともあります。人だけでなく、時刻装置や外部システムもアクターになり得ます。

## 4 ユースケース図

アクターとユースケースの関係を図示したものが**ユースケース図**です。

```text
        ┌──── 欠席連絡システム ────┐
保護者 ── (欠席を登録する)          │
保護者 ── (登録を訂正する)          │
担任   ── (学級一覧を確認する)      │
        └──────────────────────┘
```

図だけでは、入力、順番、例外、業務規則までは十分に表せません。詳しいユースケース記述を添えます。

## 5 ユースケース記述

```text
名称：欠席を登録する
主アクター：保護者
目的：当日の欠席を学校へ伝える
事前条件：保護者が認証済み、児童との関係が有効
きっかけ：保護者が欠席登録を選ぶ

基本フロー：
1 対象児童を選ぶ
2 区分・理由を入力する
3 システムが権限、締切、入力を確認する
4 システムが保存し、受付番号を示す

代替・例外：
3a 締切後なら代理電話を案内する
3b 既登録なら訂正・取消しを案内する
4a 保存失敗なら未受付と明示し、再試行方法を示す

事後条件：一件だけ記録され、担任一覧へ反映可能
```

正常な基本フローだけでなく、代替・例外と事後条件を書きます。

## 6 振舞いとシナリオ

システム・アクターが見せる動作を**振舞い**といいます。

ユースケースにあり得る一つの具体的な経路が**シナリオ**です。

```text
ユースケース：欠席を登録する
シナリオA：通常登録に成功
シナリオB：締切後で電話を案内
シナリオC：通信切断後に再送し、二重登録を防ぐ
```

ユースケースは経路の集まり、シナリオはその中の一経路と考えます。

## 7 ユーザーストーリー

利用者の立場、欲しいこと、価値を短く表す形式が**ユーザーストーリー**です。

```text
保護者として、当日の欠席をスマートフォンから登録したい。
そうすれば、混雑する電話を待たず学校へ伝えられる。
```

よく使われる形です。

```text
＜役割＞として、＜機能・能力＞が欲しい。
それは＜価値・目的＞のためである。
```

短い文だけで完全な仕様にはなりません。会話、受入れ条件、例、設計・テストが必要です。

## 8 エピック

一回の短い開発期間では大きすぎるストーリーを**エピック**と呼びます。

```text
エピック：学校への全連絡をオンライン化する
  ├─ 欠席を登録する
  ├─ 遅刻・早退を登録する
  ├─ 学校から一斉連絡する
  └─ 保護者が受領確認する
```

利用者価値を保つ小さなストーリーへ分けます。画面層だけ、DB層だけに分けると、一期間で利用可能な価値が完成しません。

## 9 良いストーリーのINVEST

ストーリーを点検する観点として**INVEST**があります。

- Independent――できるだけ独立している。
- Negotiable――詳細を対話で調整できる。
- Valuable――利用者・事業に価値がある。
- Estimable――おおよその大きさを見積もれる。
- Small――短い期間で完成できる大きさ。
- Testable――受入れ条件を試験できる。

完全独立が無理な場合は、依存関係を見えるようにします。

## 10 受入れ条件

ストーリーが完成したと判断する具体的な条件が**受入れ条件**です。

```text
前提：認証済み保護者が本人の児童を選んでいる
もし：8時29分59秒に有効な欠席内容を送る
なら：一件登録され、受付番号が表示される

前提：同じ登録が既に受理済み
もし：同じ要求IDで再送する
なら：二件目を作らず、最初の受付番号を返す
```

正常・境界・例外を含めます。

## 11 ストーリーポイント

ストーリー同士の相対的な大きさを表す数値が**ストーリーポイント**です。

作業量、複雑さ、不確実性などをチームで比較します。「1点=1日」と固定する時間単位ではありません。

異なるチームの点数を成績のように比較しません。同じチームが計画と学習に使います。

## 12 DFD

業務・システム内でデータがどこから来て、どの処理で変わり、どこへ保存・出力されるかを表す図が**DFD**、Data Flow Diagramです。

基本要素は四つです。

- **外部実体**――境界外でデータを出す・受ける人やシステム。源泉と吸収ともいう。
- **プロセス**――データを変換する処理。
- **データフロー**――流れるデータ。
- **データストア**――データを保存する場所。

## 13 DFDの例

```text
[保護者]
   │ 欠席内容
   ▼
(欠席を受け付ける) ── 欠席記録 ──> ||欠席データ||
   │ 受付結果                         │
   ▼                                  │ 当日一覧
[保護者]                              ▼
                               (一覧を作る) → [担任]
```

矢印には「欠席内容」「受付結果」のようにデータ名を書きます。「電話する」のような制御・動作だけをデータフローにしません。

## 14 コンテキストダイアグラム

対象システム全体を一つのプロセスとして描き、外部実体との出入りを示す最上位DFDを**コンテキストダイアグラム**といいます。

```text
保護者 ──欠席内容──> (欠席連絡システム) ──当日一覧──> 担任
保護者 <─受付結果──  (                 ) <─児童名簿── 名簿システム
```

境界と外部接点の確認に使います。

## 15 段階的詳細化

大きなプロセスを、内部の小さなプロセスへ順に分けることが**段階的詳細化**です。

```text
(欠席を受け付ける)
  ├─ (利用者と児童の関係を確認する)
  ├─ (入力と締切を確認する)
  ├─ (欠席を記録する)
  └─ (通知を予約する)
```

上位プロセスへ入出力するデータと、下位図全体へ入出力するデータを一致させます。これをDFDのバランスといいます。

## 16 ミニスペック

DFDの最下位プロセスについて、処理規則を文章、決定表、構造化された記述などで詳しくしたものを**ミニスペック**といいます。

DFDはデータの流れを表し、細かな判断手順までは表しにくいため補います。

## 17 構造化分析法

DFD、データ辞書、ミニスペックなどを用い、複雑な業務・システムを上位から段階的に分析する考えが**構造化分析法**です。

処理とデータの流れを中心に、境界から内部へ詳しくします。後の構造化設計と関連します。

## 18 E-R図

業務で扱う情報を、実体と関連として表す図が**E-R図**、Entity-Relationship Diagramです。

- **実体、エンティティ**――識別して管理したい対象。
- **属性**――実体が持つ性質。
- **関連、リレーションシップ**――実体同士の結び付き。

```text
保護者(保護者ID, 氏名)
   1       
   │
   │ 0..*  保護する
   ▼
児童(児童ID, 氏名, 学級)
   1
   │ 0..*
   ▼
欠席連絡(連絡ID, 日付, 区分, 理由)
```

## 19 多重度

一つの実体が、相手の何個と関係できるかを**多重度**、カーディナリティといいます。

- `1`――必ず一つ。
- `0..1`――なくてもよく、最大一つ。
- `0..*`――0個以上。
- `1..*`――1個以上。

現実の規則を確認します。一児童に複数保護者がいる、保護者が兄弟を持つなど、単純な一対多で表せない場合は中間の関係実体を設けます。

## 20 データ中心設計

処理手順は変わりやすい一方、業務で管理する情報と関係は比較的安定する場合があります。

データの構造・整合性を中心にシステムを設計する考えを**データ中心設計**といいます。

データだけを見て利用者操作・時間・障害を無視してよいという意味ではありません。処理・状態・責任と組み合わせます。

## 21 決定表

複数条件の組合せと、そのとき行う処理を表すものが**決定表**、デシジョンテーブルです。

| 条件・処理 | 規則1 | 規則2 | 規則3 | 規則4 |
|---|---:|---:|---:|---:|
| 正規保護者か | Y | Y | N | Y |
| 締切前か | Y | N | － | Y |
| 既登録か | N | － | － | Y |
| 新規登録 | X |  |  |  |
| 電話を案内 |  | X |  |  |
| 権限拒否 |  |  | X |  |
| 訂正を案内 |  |  |  | X |

`－`は結果に影響しない条件です。全組合せを調べ、同じ条件で異なる処理、どの規則にも当てはまらない組合せを見つけます。

## 22 状態

同じ操作でも、対象が現在どの段階にあるかで結果が変わります。この段階を**状態**といいます。

欠席連絡なら、下書き、受付済み、担任確認済み、取消済みなどです。

状態は単なる画面表示名ではなく、許される操作と業務上の意味を持ちます。

## 23 状態遷移図

出来事により状態がどう変わるかを表すものが**状態遷移図**です。

```text
[下書き] --送信・条件OK--> [受付済み]
   │                         │
   └--破棄--> [終了]         ├--担任確認--> [確認済み]
                             └--取消し--> [取消済み]
```

矢印へ、出来事、条件、行動を書きます。禁止される遷移も確認します。

## 24 状態遷移表

状態と出来事の組合せを表にしたものが**状態遷移表**です。

| 現在状態＼出来事 | 送信 | 担任確認 | 取消し |
|---|---|---|---|
| 下書き | 受付済み | 不可 | 終了 |
| 受付済み | 二重防止 | 確認済み | 取消済み |
| 確認済み | 二重防止 | 変化なし | 条件付き取消済み |
| 取消済み | 不可 | 不可 | 変化なし |

図より全組合せを点検しやすく、未定義動作を見つけられます。

## 25 モックアップ

画面の配置、文字、操作の流れなどを確認する模型が**モックアップ**です。紙に描いたものでも構いません。

データ保存や外部接続が動かなくても、早い段階で使用性、項目漏れ、用語の違いを確認できます。

## 26 水平型プロトタイプ

多数の画面・機能の外観と移動を浅く作るものが**水平型プロトタイプ**です。

```text
ログイン → 児童選択 → 欠席入力 → 確認 → 完了
```

全体の操作・情報構成を確認しやすい一方、DB、性能、安全性など内部実現可能性は分かりにくい方式です。

## 27 垂直型プロトタイプ

一つの機能を、画面からDB・外部接続まで深く作るものが**垂直型プロトタイプ**です。

欠席登録一件だけを本番に近い技術で通し、認証、性能、データ、外部APIの実現可能性を確かめます。

全機能の使いやすさは分かりにくいため、水平型と目的を分けます。

## 28 プロトタイプ版評価

試作品を何の疑問に答えるため作ったかを先に定め、**プロトタイプ版評価**を行います。

```text
疑問：高齢の保護者が児童切替えを理解できるか
方法：対象利用者5人に課題を行ってもらう
観測：成功、時間、迷った箇所、発言
判断：配置を変更して再評価
```

「好評だった」という感想だけでなく、決めたいことへ証拠を集めます。

## 29 捨てる試作品と発展させる試作品

学習後に捨てる前提の試作品を、そのまま本番へ使うと危険です。簡易コード、仮データ、弱い認証、エラー処理不足が残るからです。

本番へ発展させるなら、保守性、安全性、性能、試験、文書を最初から段階的に整えます。どちらかを関係者へ明示します。

## 30 図と現実を照合する

図がきれいでも、現実の業務に合うとは限りません。

- 現場利用者が読める用語か。
- 例外・障害・取消しがあるか。
- 図同士で名前・境界が一致するか。
- 要件と追跡できるか。
- 版と承認が管理されているか。
- 実際のデータ・操作で試したか。

図は合意と発見の道具であり、作成自体が目的ではありません。

## 31 モデルという言葉を整理する

**モデル**は、現実の全部ではなく、考えたい部分を選んで簡単に表したものです。学校そのものを教室へ持ち込めなくても、校内図なら部屋の位置を考えられるのと同じです。

仕事の人、手順、判断、情報を表す活動を**業務モデリング**といいます。その結果の一つが**システム業務フロー**です。業務フローには、誰が、何を受け取り、何を判断し、次に誰へ渡すかを書きます。

データの種類と関係を表す活動が**データモデリング**です。名前、生徒番号、欠席日など、一つ一つの項目を**データ要素**と呼びます。要素をどのまとまりにし、どう結び付けるかを表す抽象的な姿が**論理モデル**、実際の製品や保存場所に合わせた姿が**物理モデル**です。

**データベース又はデータ維持の要件**には、保存期間、正しさ、更新できる人、バックアップ、削除方法などを書きます。「データを保存する」だけでは、必要な管理方法が決まりません。


## 応用情報技術者試験での扱われ方

- **典型設問:** 「ユースケースとシナリオの違いを説明してください。」
- **条件語:** `ユースケース`、`シナリオ`を本文の定義と対応させます。
- **最初の着眼点:** 二つの語を、対象・目的・成立条件・失敗時の四列に置いて比べます。
- **途中の組立て・式:** 共通点を一つ、相違点を一つ示し、問題の条件へ合う側を選びます。 対象、目的、入力と出力、処理時点、成立条件、障害時を表にし、問題文で差が付く列を根拠にします。
- **典型誤答と理由:** 名称や長所だけで選ぶと、守る対象・処理時点・前提条件が違う方式を交換可能だと誤認します。

### 問1

## 解答

### 問1の解答

- **解法の入口:** 二つの語を、対象・目的・成立条件・失敗時の四列に置いて比べます。 問題は「ユースケースとシナリオの違いを説明してください。」です。
- **途中手順:** 共通点を一つ、相違点を一つ示し、問題の条件へ合う側を選びます。 結論「ユースケースは利用者が一つの目標を達成する一連のやり取りと、あり得る経路の集まりです。シナリオは、その中の通常成功・締切後など一つの具体的経」の比較軸を確認します。
- **結論の確認:** 直後の解説冒頭「ユースケースは利用者が一つの目標を達成する一連のやり取りと、あり得る経路の集まりです。シナリオは、その中の通常成功・締切後など一つの具体的経路です。」から、条件を満たす根拠まで追います。
- **この誤答が起きる理由:** 名称や長所だけで選ぶと、守る対象・処理時点・前提条件が違う方式を交換可能だと誤認します。
- **戻る本文:** [2 ユースケース](#2 ユースケース)で、定義・条件・例を再確認します。


ユースケースは利用者が一つの目標を達成する一連のやり取りと、あり得る経路の集まりです。シナリオは、その中の通常成功・締切後など一つの具体的経路です。

### 問2の解答

- **解法の入口:** 問われた語の上位概念、対象、役割、成立条件を分けて思い出します。 問題は「アクターは特定の個人ですか。外部システムもアクターになれますか。」です。
