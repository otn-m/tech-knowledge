# 第9章 第5話 業務分析の図と表

長い文章だけで業務を説明すると、読み手ごとに異なる場面を想像します。
図や表では、見たい関係を限定して表します。
漏れや矛盾を見つけ、関係者が同じ対象について話すために使うもので、文章を飾ることが目的ではありません。

## 利用者の目的と、システムとのやり取りを表す

### 1 図法を名前から選ばない

図法の名前を選ぶ前に、「何を知りたいか」を決めます。
目的と表現方法の対応は、次のように整理できます。

| 知りたいこと | 主な表現 |
|---|---|
| 誰が何の目的で使うか | ユースケース |
| 1件の利用場面 | シナリオ |
| 小さな価値要求 | ユーザーストーリー |
| データがどこからどこに流れるか | DFD |
| 情報の種類と関係 | E-R図 |
| 条件の組合せと行動 | 決定表 |
| 状態と出来事による変化 | 状態遷移図・表 |
| 見た目・操作 | モックアップ・プロトタイプ |

これらの図法はすべて、対象とする同一のシステムを異なる切り口から観察するための道具です。
単一の図面の中にあらゆる関心事を詰め込もうと試みる姿勢は、かえって混乱を招くだけにすぎません。

### 2 ユースケース

利用者や外部システムが、一つの目的を達成するためにシステムとやり取りするまとまりが**ユースケース**です。
欠席連絡なら、欠席を登録する、登録を訂正する、学級の連絡を確認する、電話連絡を代理入力するといったものがあります。

「登録ボタンを押下する」という単発の物理操作にとどまらず、利用者の視座において完結した意味のあるゴールを表すのが特徴です。

### 3 アクター

そのユースケースと直接・間接に対話する外部の役割主体をアクターと呼びます。

```text
保護者 ── 欠席を登録する
担任   ── 学級の連絡を確認する
職員   ── 電話連絡を代理入力する
認証サービス ── 利用者を認証する
```

アクターは特定の個人を指すものではありません。
1人が保護者と学校職員の2役を持つこともあります。
人間に限らず、定時起動を担うシステムタイマーや連携先の外部システムも立派なアクターとなり得ます。

### 4 ユースケース図

アクターとユースケースの関係を図示したものがユースケース図です。

```text
        ┌──── 欠席連絡システム ────┐
保護者 ── (欠席を登録する)          │
保護者 ── (登録を訂正する)          │
担任   ── (学級一覧を確認する)      │
        └──────────────────────┘
```

ただし、図面の視覚情報だけでは、入力パラメータ、実行順序、例外分岐、詳細な業務ルールを表現しきれません。
そのため、補足文書として精緻なユースケース記述を併記する運用が不可欠です。

### 5 ユースケース記述

ユースケース図で定義した大枠の目的を、具体的な操作手順や分岐条件の連鎖へと落とし込みます。
欠席登録を題材にした典型的なユースケース記述の構成例を見てみましょう。

```text
名称：欠席を登録する
主アクター：保護者
目的：当日の欠席を学校へ伝える
事前条件：保護者が認証済み、児童との関係が有効
きっかけ：保護者が欠席登録を選ぶ

基本フロー：
1 対象児童を選ぶ
2 区分・理由を入力する
3 システムが権限、締切、入力を確認する
4 システムが保存し、受付番号を示す

代替・例外：
3a 締切後なら代理電話を案内する
3b 既登録なら訂正・取消しを案内する
4a 保存失敗なら未受付と明示し、再試行方法を示す

事後条件：一件だけ記録され、担任一覧へ反映可能
```

正常な基本フローだけでなく、代替・例外のフローと事後条件も書きます。

### 6 振舞いとシナリオ

システムやアクターが見せる動作を振舞いといいます。
ユースケースで起こり得る一つの具体的な経路がシナリオです。

```text
ユースケース：欠席を登録する
シナリオA：通常登録に成功
シナリオB：締切後で電話を案内
シナリオC：通信切断後に再送し、二重登録を防ぐ
```

ユースケースは経路の集まりで、シナリオはその中の1つの経路だと考えます。

## 利用者の価値を、小さく確かめられる単位にする

### 7 ユーザーストーリー

利用者の立場、欲しいこと、価値を短く表す形式が**ユーザーストーリー**です。

```text
保護者として、当日の欠席をスマートフォンから登録したい。
そうすれば、混雑する電話を待たず学校へ伝えられる。
```

よく使われる形式は、次のようになります。

```text
＜役割＞として、＜機能・能力＞が欲しい。
それは＜価値・目的＞のためである。
```

短い文だけでは、完全な仕様にはなりません。
会話、受入れ条件、例、設計、テストが必要です。

### 8 エピック

1回の短い開発期間で実現するには大きすぎるストーリーをエピックと呼びます。

```text
エピック：学校への全連絡をオンライン化する
  ├─ 欠席を登録する
  ├─ 遅刻・早退を登録する
  ├─ 学校から一斉連絡する
  └─ 保護者が受領確認する
```

エピックは、利用者の価値を保った小さなストーリーへ分けます。
画面層だけ、DB層だけに分けると、1回の開発期間で利用できる価値が完成しません。

### 9 良いストーリーのINVEST

分けたストーリーを点検する観点として、INVESTがあります。

- Independentは、できるだけ独立していることです。
- Negotiableは、詳細を対話で調整できることです。
- Valuableは、利用者や事業に価値があることです。
- Estimableは、おおよその大きさを見積もれることです。
- Smallは、短い期間で完成できる大きさです。
- Testableは、受入れ条件を試験できることです。

完全な独立が無理な場合は、依存関係を見えるようにします。

### 10 受入れ条件

ストーリーが完成したと判断する、具体的な条件が受入れ条件です。
欠席登録なら、締切直前の送信がどう扱われるかも条件にします。

```text
前提：認証済み保護者が本人の児童を選んでいる
もし：8時29分59秒に有効な欠席内容を送る
なら：一件登録され、受付番号が表示される

前提：同じ登録が既に受理済み
もし：同じ要求IDで再送する
なら：二件目を作らず、最初の受付番号を返す
```

正常、境界、例外を含めて定めます。

### 11 ストーリーポイント

ストーリー同士の相対的な大きさを表す数値がストーリーポイントです。
作業量、複雑さ、不確実性などをチームで比較します。
「1点=1日」と固定する時間単位ではありません。

異なるチームの点数を成績のように比較せず、同じチームが計画と学習に使います。

## データの流れから処理を分析する

### 12 DFD

利用者の目的とは別に、業務をデータの流れから捉える方法もあります。
データがどこから来て、どの処理で変わり、どこへ保存・出力されるかを表す図が**DFD**、Data Flow Diagramです。
基本要素は4つあります。

境界外でデータを出したり受けたりする人やシステムが外部実体で、源泉と吸収ともいいます。
データを変換する処理がプロセス、流れるデータがデータフロー、データを保存する場所がデータストアです。

### 13 DFDの例

欠席連絡をDFDで表すと、次のようになります。

```text
[保護者]
   │ 欠席内容
   ▼
(欠席を受け付ける) ── 欠席記録 ──> ||欠席データ||
   │ 受付結果                         │
   ▼                                  │ 当日一覧
[保護者]                              ▼
                               (一覧を作る) → [担任]
```

矢印には「欠席内容」「受付結果」のように、データ名を書きます。
「電話する」のような制御や動作だけを、データフローとして表すことはしません。

### 14 コンテキストダイアグラム

対象システム全体を一つのプロセスとして描き、外部実体との出入りを示す最上位のDFDがコンテキストダイアグラムです。

```text
保護者 ──欠席内容──> (欠席連絡システム) ──当日一覧──> 担任
保護者 <─受付結果──  (                 ) <─児童名簿── 名簿システム
```

内部の詳細へ進む前に、境界と外部接点の確認に使います。

### 15 段階的詳細化

大きなプロセスを、内部の小さなプロセスへ順に分けることが段階的詳細化です。

```text
(欠席を受け付ける)
  ├─ (利用者と児童の関係を確認する)
  ├─ (入力と締切を確認する)
  ├─ (欠席を記録する)
  └─ (通知を予約する)
```

分ける際は、上位プロセスに入出力するデータと、下位図全体に入出力するデータを一致させます。
これを、DFDのバランスといいます。

### 16 ミニスペック

DFDはデータの流通経路を鳥瞰するのに長けている半面、内部で行われる細かな分岐判断や計算式までは表現できません。
そこで、これ以上分割できない最下位プロセスに対し、処理ロジックを平易な自然言語や決定表、構造化英語などで補足定義した文書がミニスペックです。

### 17 構造化分析法

DFD、データ辞書、ミニスペックなどを使い、複雑な業務やシステムを上位から段階的に分析する考えが構造化分析法です。
処理とデータの流れを中心に、境界から内部へと分析を詳しくしていきます。
後の構造化設計とも関連します。

## 管理する情報と、その関係を表す

### 18 E-R図

データの流れる経路だけでなく、情報資産そのものが持つ構造的な関連性も把握しなければなりません。
業務上で永続管理すべき情報を、実体とその相互関係としてモデル化した図が**E-R図**（Entity-Relationship Diagram）です。

システム内で一意に識別して管理すべき対象を実体（エンティティ）、各実体が保持する具体的な項目を属性と定義します。
そして、実体同士の間に存在する業務上の結び付きを関連（リレーションシップ）と呼ぶわけです。

```text
保護者(保護者ID, 氏名)
   1
   │
   │ 0..*  保護する
   ▼
児童(児童ID, 氏名, 学級)
   1
   │ 0..*
   ▼
欠席連絡(連絡ID, 日付, 区分, 理由)
```

### 19 多重度

1つの実体が、相手方の実体と最大・最小でいくつのインスタンスと結び付き得るかを表す数値制約を、多重度（カーディナリティ）と呼びます。

- `1`: 必ず1つ存在する関係
- `0..1`: 存在しないか、最大で1つ存在する関係
- `0..*`: 0個以上の任意の数で存在する関係
- `1..*`: 最低1つ以上存在する関係

多重度の定義にあたっては、業務規則や現場の制約を忠実に反映させる姿勢が不可欠です。
1人の児童に複数の保護者が紐付くケースや、1人の保護者が複数の兄弟姉妹を抱える実態など、単純な1対多で表現しきれない関係性に対しては、関連実体（交差テーブル）を中間に設けます。

### 20 データ中心設計

業務の処理手順や画面構成は頻繁に変更される半面、組織が永続管理する中核エンティティとその関係性は長期にわたり安定する傾向があります。
この特性に着目し、データの論理構造と整合性の保持を軸にシステム全体のアーキテクチャを組み立てる思想が、データ中心設計（DOA）です。

ただし、データだけを見て、利用者の操作、時間、障害を無視してよいという意味ではありません。
処理、状態、責任と組み合わせて考えます。

## 条件と状態に応じた動作を確かめる

### 21 決定表

複数条件の組合せと、そのとき行う処理を表すものが**決定表**、デシジョンテーブルです。

| 条件・処理 | 規則1 | 規則2 | 規則3 | 規則4 |
|---|---:|---:|---:|---:|
| 正規保護者か | Y | Y | N | Y |
| 締切前か | Y | N | － | Y |
| 既登録か | N | － | － | Y |
| 新規登録 | X |  |  |  |
| 電話を案内 |  | X |  |  |
| 権限拒否 |  |  | X |  |
| 訂正を案内 |  |  |  | X |

`－`は、結果に影響しない条件です。
全組合せを調べ、同じ条件なのに処理が異なる箇所や、どの規則にも当てはまらない組合せを見つけます。

### 22 状態

条件の組み合わせを網羅するだけでは、システムの振る舞いを一意に確定できない場面も少なくありません。
ユーザーがまったく同じボタンを押したとしても、対象データが現在どのようなライフサイクル段階にあるかによって、期待される挙動は根本から異なる結果となります。
この時間的な経過に伴う履歴や段階の区別を表す概念が、状態です。

欠席連絡の例でいえば、下書き、受付済み、担任確認済み、取消済みといった区分が該当します。
状態とは単なる画面の表示ラベルにとどまらず、その時点で実行可能な操作と業務上の意味論を内包する概念にほかなりません。

### 23 状態遷移図

外部からのイベント（出来事）によって状態がどう変化するかを視覚化したダイアグラムが**状態遷移図**です。

```text
[下書き] --送信・条件OK--> [受付済み]
   │                         │
   └--破棄--> [終了]         ├--担任確認--> [確認済み]
                             └--取消し--> [取消済み]
```

矢印に出来事、条件、行動を書きます。
許される遷移だけでなく、禁止される遷移も確認します。

### 24 状態遷移表

状態と出来事の組合せを表にしたものが状態遷移表です。

| 現在状態＼出来事 | 送信 | 担任確認 | 取消し |
|---|---|---|---|
| 下書き | 受付済み | 不可 | 終了 |
| 受付済み | 二重防止 | 確認済み | 取消済み |
| 確認済み | 二重防止 | 変化なし | 条件付き取消済み |
| 取消済み | 不可 | 不可 | 変化なし |

図よりも全組合せを点検しやすく、未定義の動作を見つけられます。

## 試作品で操作と実現可能性を確かめる

### 25 モックアップ

図や表に加え、操作を試せるモデルも使います。
画面の配置、文字、操作の流れなどを確認するモデルが**モックアップ**です。
紙に描いたものでも構いません。

データ保存や外部接続が動かなくても、早い段階で使用性、項目の漏れ、用語の違いを確認できます。

### 26 水平型プロトタイプ

多数の画面や機能について、外観と画面間の画面遷移を浅く広く作成する手法を、水平型プロトタイプと呼びます。

```text
ログイン → 児童選択 → 欠席入力 → 確認 → 完了
```

全体の操作動線や情報構造を俯瞰して確認しやすい半面、バックエンドのDB処理、負荷耐性、データ保護といった非機能面の実現可能性までは見通せません。

### 27 垂直型プロトタイプ

これに対し、特定の重要機能に絞り込み、ユーザーインターフェースからデータベースアクセス、外部API連携に至るまで縦断的に実装する手法が垂直型プロトタイプです。
欠席登録という中核機能1件だけを本番相当のアーキテクチャで貫通させ、認証、スループット、トランザクション整合性、外部依存性の実現可能性を技術的に検証します。

業務全体の網羅的な操作性を確認する目的には適さないため、水平型プロトタイプとは適用フェーズと評価目的を明確に切り分ける運用が肝要です。

### 28 プロトタイプ版評価

試作品のコーディングに着手する前に、「今回の検証によって解消すべき不確実性は何か」という評価の問いを明確に設定しなければなりません。
その検証目的にフォーカスして実施される体系的なテスト活動がプロトタイプ版評価です。

```text
疑問：高齢の保護者が児童切替えを理解できるか
方法：対象利用者5人に課題を行ってもらう
観測：成功、時間、迷った箇所、発言
判断：配置を変更して再評価
```

「好評だった」という感想だけで判断せず、決めたいことについて証拠を集めます。

### 29 捨てる試作品と発展させる試作品

学習後に捨てる前提の試作品を、そのまま本番に使うと危険です。
簡易コード、仮データ、弱い認証、エラー処理不足が残るからです。

本番に発展させるなら、保守性、安全性、性能、試験、文書を最初から段階的に整えます。
どちらかを関係者に明示します。

## モデルを現実の業務と照合する

### 30 図と現実を照合する

図がきれいでも、現実の業務に合っているとは限りません。
現場の利用者が読める用語か、例外、障害、取消しを含むかを確かめます。
図同士の名前と境界が一致し、要件と追跡できるかを確認する作業も欠かせません。

ドキュメントの版数管理と変更承認プロセスを徹底し、実環境に近いサンプルデータや操作シナリオを用いて有効性を検証します。
図面やダイアグラムは関係者間の合意形成と潜在的リスクの発見を促す対話ツールであり、美しい図を描くこと自体が開発の目的ではないのです。

### 31 モデルという言葉を整理する

**モデル**とは、複雑な現実世界から着目したい特定の側面に焦点を絞り込み、中核となる要素を抽出して抽象化した表現形式を指します。
学校の校舎そのものを会議室へ持ち込めなくても、簡略化された校内見取り図があれば教室の配置関係を議論できるのと同様の理屈です。

業務に携わる人員、作業手順、判断分岐、流通する情報資産を可視化する活動を、業務モデリングと呼びます。
その代表的な分析成果物が、システム業務フローです。
業務フローには、誰が、何を受け取り、何を判断し、次に誰に渡すかを書きます。

データの種類と関係を表す活動がデータモデリングです。
名前、生徒番号、欠席日など、個々の項目をデータ要素と呼びます。
要素をどのまとまりにし、どう結び付けるかを表す抽象的な姿が論理モデル、実際の製品や保存場所に合わせた姿が物理モデルです。

データベース又はデータ維持の要件には、保存期間、正しさ、更新できる人、バックアップ、削除方法などを書きます。
「データを保存する」だけでは、必要な管理方法が決まりません。

業務を1枚の図へ押し込めると、見やすさと引き換えに別の関係が見えにくくなります。
目的、流れ、データ、規則、状態を異なる図や表で確かめ、同じ欠席連絡を重ねて見たときに、文章だけでは隠れていた漏れと矛盾が現れます。
