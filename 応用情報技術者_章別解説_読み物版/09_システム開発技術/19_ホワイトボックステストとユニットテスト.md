# 第9章 第19話 ホワイトボックステストとユニットテスト

プログラム内のすべての命令を1度は実行できれば、十分に調べたように見えます。
それでも、判定の別の結果、条件の組合せ、そもそも実装されなかった要求は残り得ます。

## 内部構造から通す道筋を選ぶ

### 1 ホワイトボックスというたとえ

**ホワイトボックステスト**は、箱の内部が透けて見えるものと仮定し、ソースコードの論理構造や制御の流れに基づいてテストケースを設計する手法です。

```text
入力 → [命令A → 条件X ┬→ 命令B] → 出力
                       └→ 命令C
```

どの命令文を実行し、どの条件分岐を通過させたのかを内部視点から厳密に確認します。

### 2 ブラックボックスとの違い

外部視点と内部視点の相違は次のように対比されます。

```text
ブラックボックス：要求・仕様から、入力と期待結果を選ぶ
ホワイトボックス：コード・制御構造から、通す経路を選ぶ
```

ソフトウェアの品質を真に担保するためには、双方のアプローチが不可欠です。

内部構造のすべての命令を実行し尽くしたとしても、要求仕様書に定義されていた機能そのものが実装から抜け落ちていた事実に気付くことはできません。
他方で、仕様書に基づくテストをいくら重ねても、コードの奥深くに埋もれた特殊な例外分岐を一度も通過していない事態が起こり得ます。

### 3 制御フロー

プログラムの実行が1つの命令から次の命令へと順を追って進んでいく道筋を制御フローと呼びます。

条件分岐、繰り返しループ、例外の送出、早期リターンによって実行経路は多彩に分岐していくわけです。

```text
開始
  ↓
入力検査 ─不正→ エラー終了
  │正常
  ↓
保存 ─失敗→ 再試行またはエラー
  │成功
  ↓
完了
```

### 4 制御フローグラフ

プログラムの基本処理ブロックを節点（ノード）、処理の遷移関係を有向辺（エッジ）として図式化した構造モデルが**制御フローグラフ**です。

```text
      [1 開始]
           |
      [2 条件?]
       /       \
    真/         \偽
 [3 保存]     [4 エラー]
       \       /
        [5 終了]
```

このグラフを用いることで、どの分岐パスが実行され、どの経路が未実行のまま残されているのかを視覚的かつ論理的に把握しやすくなります。

## 何を網羅した割合なのかを区別する

### 5 カバレージ

テスト対象となるプログラム要素のうち、テスト実行によって実際に通過した要素の割合を示す指標がカバレージ（テスト網羅率）です。

```text
カバレージ = 実行した対象数 ÷ 全対象数 × 100%
```

分母に設定する要素の種類によってカバレージの意味合いは劇的に変化します。
単に「網羅率100%を達成した」という報告だけでは、何をどこまで検証したのか客観的に判断できません。

### 6 命令網羅

プログラム内に存在するすべての実行可能な命令文を、少なくとも1回は実行させるカバレージ基準が**命令網羅**（ステートメントカバレージ、C0）です。

```text
if (age < 18) {
    discount = 100;
}
print(discount);
```

このコードに対して `age = 17` というテストデータを1件投入すれば、if文ブロックの内部もprint文も実行されるため、命令網羅としては100%が達成されます。

### 7 命令網羅の限界

しかし、先ほどの例で `age = 17` しか実行していない場合、条件が偽となる `age = 18` 以上のケースが一度も検証されていません。

すべての命令文を通過したからといって、分岐の逆側の振る舞いに欠陥がないことまで確認できたわけではないのです。

```text
命令網羅100% ≠ 全ての条件結果を確認済み
```

### 8 判定網羅・分岐網羅

すべての判定条件（if文やwhile文など）の結果が、真（True）と偽（False）の両方の分岐を少なくとも1回ずつ通過するようにテストする基準が**判定網羅**（分岐網羅、デシジョンカバレージ、C1）です。

```text
if (age < 18)
```

この判定に対しては、`age = 17` で真の分岐を通し、`age = 18` で偽の分岐を通すテストケースを設計します。

判定網羅を100%満たせば、通常はすべての命令文を通過するため命令網羅（C0）も同時に達成されます。
ただし、構文規則の特殊性や到達不能コードの存在には留意しなければなりません。

### 9 条件と判定

複合的な論理条件を扱う場合、判定全体の真偽と、その内側に含まれる個別の条件式の真偽を明確に区別して捉える視点が求められます。

```text
if (本人確認済み AND 日付が有効) {
    登録する
}
```

この例において、「本人確認済み」が個別条件A、「日付が有効」が個別条件Bに該当します。
判定式全体は `A AND B` であり、判定式全体の真偽を真と偽の2通り試しただけでは、個別条件のそれぞれが真偽の両方を網羅したとは限りません。

### 10 真理値表

2つのブール条件AおよびBが取り得るすべての真偽値の組み合わせは、次の4パターンに整理されます。

| A | B | A AND B | A OR B |
|---|---|---|---|
| 真 | 真 | 真 | 真 |
| 真 | 偽 | 偽 | 真 |
| 偽 | 真 | 偽 | 真 |
| 偽 | 偽 | 偽 | 偽 |

この論理値表を活用することで、どのパターンの組み合わせをテストし、どの組み合わせが未消化であるかを整然と可視化できます。

### 11 条件網羅

判定式を構成する個々の条件式（個別条件）のそれぞれが、真と偽の両方の値を少なくとも1回ずつ取るようにテストケースを設計する基準が**条件網羅**（コンディションカバレージ、C2）です。

`A AND B` という判定式に対して、次の2つのテストケースを実行した場合を考えてみましょう。

```text
ケース1：A=真、B=偽 → 判定は偽
ケース2：A=偽、B=真 → 判定は偽
```

個別条件Aも個別条件Bも真と偽をそれぞれ1回ずつ経験しているため、条件網羅の基準は完全に満たされます。
しかし、判定式全体の結果はいずれのケースでも「偽」となっており、「真」となる実行パス（登録処理）を一度も通過していません。
このように、条件網羅を満たしていても判定網羅を満たせない逆転現象が発生する点に注意が必要です。

### 12 判定条件網羅

判定式全体が真と偽の両方の結果を取り、かつ判定式に含まれるすべての個別条件も真と偽の両方の値を取るように設計する基準が判定条件網羅です。

`A AND B` に対しては、次のようなテストケースのペアが該当します。

```text
ケース1：A=真、B=真 → 判定は真
ケース2：A=偽、B=偽 → 判定は偽
```

判定網羅と条件網羅を同時にクリアできますが、Aが真でBが偽、あるいはAが偽でBが真という混在した組み合わせまでは検証されません。

### 13 複数条件網羅

判定式に含まれるすべての個別条件について、取り得る真偽値のあらゆる組み合わせパターンを全数テストする最も厳格な基準が**複数条件網羅**（複合条件網羅）です。

個別条件の数が2個なら4通り、3個なら8通り、4個なら16通りのテストケースが必要となります。

```text
組合せ数 = 2の条件数乗
```

条件式の数が増加するにつれてテストケース数が指数関数的に跳ね上がるわけです。
プログラミング言語の短絡評価の挙動や、業務仕様上あり得ない組み合わせの除外を考慮して適用範囲を慎重に検討しなければなりません。

## 経路の増加と、実行できない道を扱う

### 14 経路組合せ網羅

プログラムの開始点から終了点に至るまでに存在する、あらゆる独立した実行経路の組み合わせを完全に網羅しようとする理想的な基準を経路組合せ網羅と呼びます。

連続する分岐が増えるほど経路数は爆発的に増加し、さらに内部にループ処理が含まれている場合、ループ回数の組み合わせは理論上無限に発散してしまいます。
そのため、一般的なソフトウェア開発において完全な全経路網羅を達成することは非現実的と見なされるのが実情です。

### 15 ループのテスト

繰り返し処理をホワイトボックスで検証する際は、ループ本体を一度も実行せずスキップする0回のケースと、境界となる1回実行のケースを確実にテストします。
さらに2回の実行を検証することで、初回から2回目へのループ変数や内部状態の引き継ぎが正常に行われるかを確認できます。

典型的な複数回の実行に加え、仕様上許容される最大反復回数、およびその直前・直後の境界条件も網羅しなければなりません。
空のコレクション、要素数が1件のリスト、複数件のデータ、上限容量の配列をそれぞれテストするアプローチも同じ思想に基づいています。

### 16 短絡評価

多くの近代プログラミング言語では、論理積（AND）の左辺が偽であれば全体の偽が確定するため右辺の評価をスキップし、論理和（OR）の左辺が真であれば全体の真が確定するため右辺を評価しません。
この言語仕様を短絡評価（ショートサーキット評価）と呼びます。

```text
A AND B：Aが偽ならBを評価しない
A OR B ：Aが真ならBを評価しない
```

右辺の式に関数呼び出しや副作用を伴う代入処理が含まれている場合、左辺の値によってその処理が実行されたりされなかったりする挙動が生じます。
条件式の記述順序と副作用の有無には細心の注意を払わなければなりません。

### 17 MC/DC

判定式内の各個別条件が、他のすべての個別条件を一定の値に固定した状態で、判定式全体の結果を単独で真から偽（または偽から真）へと反転させられることを実証する厳格な基準が**MC/DC**（修正条件・判定網羅）です。

`A AND B` という判定式であれば、次の組み合わせによって各条件の独立した影響力を証明できます。

```text
Aの影響：A=真,B=真 → 真 ／ A=偽,B=真 → 偽
Bの影響：A=真,B=真 → 真 ／ A=真,B=偽 → 偽
```

航空宇宙産業や自動車制御（ISO 26262）など、人命に関わる極めて高い安全水準が求められる分野で国際標準として義務付けられている評価基準です。
全組み合わせを試す複数条件網羅に比べてテストケース数を大幅に抑えつつ、単なる条件網羅を遥かに凌駕する検出精度を叩き出すわけです。

### 18 到達不能コード

いかなる入力データを与えても物理的に実行されることのない無駄なコードブロックを到達不能コード（デッドコード）と呼びます。

```text
return result;
log("ここには来ない");
```

カバレッジの数値を100%に近づけたいがために無理やり不正なテストケースを捏造する本末転倒な対応を避け、不要コードとして安全に削除するか、前提となる分岐論理の矛盾を修正しなければなりません。

### 19 防御的な例外経路

メモリ割り当て失敗やハードウェア通信途絶など、通常のテスト環境では意図的に引き起こすことが極めて困難な例外ハンドリング経路が存在します。

外部依存モジュールをモックやスタブに差し替えて意図的にエラーコードを返却させたり、障害注入（フォルトインジェクション）の手法を適用したりして例外処理の堅牢性を確かめます。
実環境の物理設備を危険に晒すことを避け、安全に隔離された試験環境と障害注入手順によって検証を進めるのがプロフェッショナルの鉄則です。

## 実行したことと、正しさを確認したことを分ける

### 20 カバレージ100%の意味

命令網羅100%が意味する客観的な事実は、「測定ツールに認識された実行可能コードの行を、少なくとも1度は通過した」という事象にすぎません。
要求された仕様がすべて正しく実装されていることや、あらゆる入力パターンに対して正しい計算結果を返せることまでを保証するものではない点に留意すべきです。

出力値の妥当性が検証されているか、処理性能や耐障害性に問題がないか、あるいはテストコードのアサーション自体が正しく記述されているかは、カバレージの数値だけでは一切分かりません。
カバレージは、テストがまだ不足している未検証領域を発見するための道標として捉えるべきです。

### 21 カバレージを上げるだけのテスト

対象の関数を単に呼び出すだけで、戻り値やデータベースの更新結果を一切アサート（検証）しない無意味なテストコードであっても、カバレージの数値自体は上昇してしまいます。

```text
悪い例：calculateFee(100)を呼ぶだけ
良い例：calculateFee(100)の結果が定めた120円であると比較する
```

プログラムの行を「実行した」という事実と、その処理結果が「正しいと判定した」という検証行為は厳格に峻別しなければなりません。

## 小さな単位で、条件と結果を比較する

### 22 ユニットテスト

関数、メソッド、クラス、単一モジュールといったソフトウェアの最小構成単位を対象として、隔離された環境下でその振る舞いを検証する活動が**ユニットテスト**（単体テスト）です。

不具合が混入した箇所を狭いスコープ内で即座に特定でき、修正後の再検証をミリ秒単位で高速に繰り返せる絶大な機動性を誇ります。

### 23 良いユニットテストの性質

優れたユニットテストは、瞬時に実行が完了し、外部環境に左右されず何度実行しても完全に同一の結果を再現できる決定論的な性質を備えています。
テストケース同士が互いに依存せず独立して実行可能であり、成否の判定が機械的かつ客観的に自動判定される構造を保たなければなりません。

モジュールの重要な仕様を過不足なく表現し、テストが失敗した際にはどの論理が破綻したのかが一目で判別できるように記述します。
実行速度を求めるあまり、重要なモジュール間結合の検証までをすべて代役に置き換えてしまっては本末転倒です。

### 24 Arrange、Act、Assert

ユニットテストのコード構造を可読性高く整理する世界的な標準パターンとして「AAA（トリプルエー）」の記述様式が定着しています。

```text
Arrange：前提データと対象を用意する
Act    ：対象の操作を一度実行する
Assert ：実際結果を期待結果と比較する
```

テストの事前準備（Arrange）、検証対象の実行（Act）、結果の検証（Assert）の3段階を明確に視覚分離することで、テストが何を検証しようとしているのかが誰の目にも明瞭になる仕組みです。

### 25 アサーション

テストコードの実行結果が、あらかじめ定義された期待値と論理的に合致しているかを判定する検証構文をアサーションと呼びます。

```text
assertEqual(actualStatus, "受付済み")
assertEqual(savedCount, 1)
```

1つのテストメソッドの中で密接に関連する一連の出力値を検証することは自然ですが、無関係な複数の関心事を1つのテストに詰め込みすぎて可読性を損なわない配慮が欠かせません。

### 26 正常系、異常系、境界

ユニットテストを網羅的に組み立てる際は、正常系、異常系、境界条件の3つの軸をバランスよく配置します。
正常系では正しい入力値に対して期待通りの業務処理が成功することを確かめ、異常系では不正な引数やリソース枯渇に対して安全に例外処理が作動することを検証します。
境界条件では、不等号の境界線上で処理の分岐が狂いなく切り替わるかを確かめるわけです。

単に「エラーが出ずに動いた」という正常系の自己満足にとどまらず、異常発生時にデータを破損させることなく、原因が明確に追跡できる形式で安全に失敗することを担保します。

## 依存を制御し、再現可能なテストにする

### 27 ドライバ

テスト対象となるモジュールを呼び出す上位のコンポーネントが未完成である場合に、テスト対象へ擬似的な引数を渡して呼び出しを実行する代役プログラムがドライバです。

JUnitやpytestといった現代の自動テストフレームワークにおけるテストランナー自体も、広義のテストドライバとして機能しています。

### 28 スタブ

テスト対象のモジュールが処理の過程で呼び出す下位の依存コンポーネントの代役を務めるテスト用部品がスタブです。

```text
通知スタブ
  呼ばれたら常に成功を返す版
  呼ばれたら通信失敗を返す版
```

外部のメール送信サーバや課金決済APIを実際に呼び出すことなく、ネットワーク切断やタイムアウトといった異常系の応答を自在に再現できます。

### 29 テストダブルの使いすぎ

すべての外部依存をスタブやモックといった代役（テストダブル）に置き換えてしまうと、単体テスト上では完璧にパスしていても、本物のデータベースや外部APIと結合した段階で接続エラーに直面して破綻する事態を招きます。

ユニットテストによってモジュール内部の複雑なドメインロジックを高速に検証し、後続の統合テストによって本物のデータベース接続やネットワーク通信の互換性を検証するという適切な責務分担が欠かせません。

### 30 時刻・乱数・外部環境を制御する

現在時刻の取得関数や乱数生成器をビジネスロジックの内部に直接ハードコードすると、テストを実行した日時やミリ秒によって合否がブレる不安定なテストに陥りかねません。

```text
業務処理 → Clockという時刻取得の契約
テスト   → 2026-07-14 08:00を返す偽物
本番     → 実際の現在時刻を返す実装
```

時刻取得インターフェースを外部から注入（依存性の注入、DI）できるように設計し、月末やうるう年といった特定の境界時刻をいつでも寸分違わず再現できるように環境を整えます。

### 31 テストの独立性

先行するテストケースがデータベースに書き残したレコードを、後続のテストケースが暗黙の前提として利用するような密結合を作ると、実行順序によって合否が変動するトラブルを招いてしまいます。

各テストケースが自前で必要な初期データをセットアップし、テスト終了時に確実にロールバックやクリーンアップを行う自己完結型の設計を徹底しなければなりません。
テストスイートをランダムな順序で並び替えて並列実行しても、すべてのテストが安定して成功する独立性を担保することが大切です。

### 32 フレーキーテスト

ソースコードに一切変更を加えていないにもかかわらず、ある時はパスし、ある時は不意に失敗する不安定なテストをフレーキーテストと呼びます。
固定秒数のスリープ処理（`sleep`）によるタイミング待ちや、非同期スレッドの完了順序に対する暗黙の依存が主な原因として挙げられます。

外部インターネットへの無制御なアクセスや、現在時刻の変動、テスト間での静的メモリの共有もフレーキーテストを生み出す温床となりかねません。
テストがたまに落ちた際に「再実行したら通ったから問題ない」と見過ごす悪習を排し、不安定さの根本原因を突き止めて排除しなければなりません。

## テストが誤りを検出できるかを調べる

### 33 テスト駆動開発

短い開発サイクルの中で、まず失敗するテストコードを書き、そのテストをパスさせる最小限の実装を行い、最後にコードの構造を美しく整理する反復手法が**テスト駆動開発**（TDD）です。

```text
Red      ：期待を表す失敗テストを書く
Green    ：最小限の実装で成功させる
Refactor ：動作を保って設計を改善する
```

テストを先行して記述すること自体が優れたアーキテクチャを自動保証するわけではないため、結合テストや性能測定、ユーザビリティ評価など多面的なテスト活動を組み合わせなければなりません。

### 34 ミューテーションテスト

対象プログラムのソースコードにあえて意図的な微小変異（ミュータント）を注入し、既存のテストコード群がその不具合を正しく検知して失敗できるかを検証する高度な品質測定手法が**ミューテーションテスト**です。

```text
元のコード：age < 18
変異コード：age <= 18
```

変異コードに対してテストが正しく失敗した状態を「変異を殺した（Killed）」と呼び、テストが誤りを検知できずパスしてしまった状態を「変異が生き残った（Survived）」と判定します。

### 35 ミューテーションスコア

注入された変異体の総数のうち、テストスイートによって正しく撃墜（検出）された変異の割合を示す指標がミューテーションスコアです。

```text
ミューテーションスコア
= 殺した変異数 ÷ 対象となる変異数 × 100%
```

コードの記述は変わったものの論理的な実行結果が全く同一である等価変異については、手作業または高度な解析によって分母から除外する配慮を行います。
ミューテーション解析は膨大なコンパイルとテスト実行を伴うため、システムの重要中核モジュールや変更差分に絞り込んで適用するのが一般的です。

### 36 カバレージとミューテーションの違い

コードカバレージは、テスト実行中に特定の行を「通過したか否か」という動線の通過実績だけを測定します。
これに対してミューテーションテストは、コード内部に潜む微細な論理エラーに対してテストコードのアサーションが「正しく反応できるか否か」というテストの検知力を測定するわけです。

```text
コードを通るが結果をassertしない
→ カバレージは上がる
→ 変異を検出できず、生き残りやすい
```

中身の伴わない見せかけのテストコードを炙り出し、テストスイート自体の真の頑健性を評価するための決定打となります。

## 網羅率を要求と期待結果へ結び付ける

### 37 デッドコードとテスト不足

カバレージ測定によって未実行として検出されたコード領域に直面した際は、2つの可能性を冷静に見極めます。

1. 仕様上必要な処理であるが、単にテストケースの作成が漏れている。
2. そもそもいかなる条件でも到達できない不要なデッドコードである。

後者のデッドコードに対して無理に数値を稼ぐテストケースを急造することを避け、設計仕様を再確認した上で不要コードをきれいに削除するのが健全な対応です。

### 38 単純な網羅例

次の割引判定ロジックを例に、ホワイトボックスの各網羅基準を比較してみましょう。

```text
if (isMember AND amount >= 1000) {
    discount = 100;
} else {
    discount = 0;
}
```

| ケース | isMember | amount | 判定 | discount |
|---|---:|---:|---:|---:|
| 1 | 真 | 1000 | 真 | 100 |
| 2 | 偽 | 1000 | 偽 | 0 |
| 3 | 真 | 999 | 偽 | 0 |
| 4 | 偽 | 999 | 偽 | 0 |

ケース1とケース4の2件だけを実行すれば、判定条件網羅（判定全体の真偽、個別条件の真偽）を一見クリアできますが、個別条件が単独で結果に与える影響までは検証できません。
複数条件網羅を達成するためには、表に示した4パターンすべてを実行する必要があります。
さらに限界値分析の観点を組み入れ、amountの値として999、1000、1001をテストケースに配置する工夫が求められます。

### 39 ホワイトボックスでも期待結果が必要

内部の実行パスを通過させたという実績だけでは、テストとしての責務を果たしたことにはなりません。

通過した各実行経路において、関数の返却値、データベースの状態推移、外部呼び出しの引数、送出された例外オブジェクトが仕様通りであるかを厳格にアサートします。
テストデータを導き出す根拠として内部コードの制御構造を活用しつつ、合否を判定する真実の基準は常に上位の要求仕様書に置かなければならないのです。

### 40 主な概念の区別

- 命令網羅（C0）は、すべての実行可能命令を少なくとも1回実行する。
- 判定網羅（C1）は、各判定文の真と偽の分岐を少なくとも1回ずつ通過させる。
- 条件網羅（C2）は、判定式内のすべての個別条件が真と偽を1回ずつ取るようにする。
- 判定条件網羅は、判定全体の真偽と個別条件の真偽を同時に満たす。
- 複数条件網羅は、個別条件のすべての真偽組み合わせパターンを全数網羅する。
- MC/DCは、各個別条件が判定結果を独立して反転させられることを実証する。
- ユニットテストは、最小のソフトウェア部品を高速・隔離して検証する。
- ミューテーションテストは、人工的な変異を検出できるかによってテスト自体の品質を測る。

### 41 この話のまとめ

ホワイトボックステストは、ソースコードの制御フローやデータ構造を直視し、命令文、判定分岐、個別条件、実行パスをどこまで網羅的に通過させたかを客観的に検証する手法です。

カバレージ指標はテストの盲点を発見するための有力な手掛かりですが、それ単体で機能の正しさや仕様の完全性を保証するものではありません。
ユニットテストによって最小単位のロジックを高速かつ決定論的に検証し、ブラックボックステストや統合テストと有機的に連携させることで、真に堅牢なソフトウェアを構築できます。

すべての命令文を通過させたとしても、それは実装されたコードの範囲をなぞったにすぎない可能性があります。
コード内部の未検証パスをカバレージによってあぶり出しながら、外部から期待される真の要求仕様と照らし合わせて合否を判定することこそが、ホワイトボックステストの到達点です。
