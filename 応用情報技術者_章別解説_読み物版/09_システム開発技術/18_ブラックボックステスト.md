# 第9章 第18話 ブラックボックステスト

1から40までを受け付ける入力欄なら、40個の値を全部試せば十分に見えます。
ところが実際には、範囲外の値、未入力、文字列、条件の組合せ、状態の違いまであり、入力を総当たりすることはできません。

## 外から観察できる振舞いを対象にする

### 1 ブラックボックスというたとえ

**ブラックボックステスト**は、テスト対象の内部構造を不可視の黒い箱として扱い、外部から観測できる入出力の振る舞いだけに着目して検証を進める手法です。

```text
入力・事前条件 → [ 内部は見ない箱 ] → 出力・状態変化
```

ここで「内部の実装を絶対に知ってはならない」という制約を課すわけではありません。
テストデータを選定する根拠として、内部のソースコードに依存せず外部の要求仕様書を最優先に位置づけます。

### 2 何を入力・出力と考えるか

入力には、画面から直接入力される文字列や数値にとどまらず、利用者のクリック操作、APIへ送信されるHTTPリクエスト、バッチ処理に投入されるファイル群が含まれます。
システム内クロックの経過時間、IoTセンサーの検知値、外部連携サービスからの通知イベントも立派な入力情報です。
ログインユーザーの権限ロール、環境設定パラメータ、データベースに蓄積された初期データも、振る舞いを左右する前提条件として機能します。

出力についても、画面上の描画メッセージやAPIの戻り値、HTTPステータスコードだけに限定されません。
データベース内のレコード更新、生成された帳票PDF、他システムへ送信された連携電文、監査ログの追記、さらには物理機器の作動に至るまで、仕様書で要求されたあらゆる外部変化を検証対象とします。

### 3 ブラックボックステストの利点

ブラックボックステストを実施することで、利用者の視点や呼び出し元の立場に立った真の振る舞いを評価できます。
プログラムの実装者以外のエンジニアであっても仕様書さえあればテストケースを設計でき、内部実装の言語やアルゴリズムを刷新してもテスト資産をそのまま再利用できる点が強みです。

要求仕様書から演繹的にテストケースを導出するため、実装者が設計書から作り忘れて抜け落ちた機能の欠落にも迅速に気付ける利点があります。
反面、内部のどの制御パスを実行したのかを追跡することはできず、仕様書そのものに潜む考慮漏れをそのまま引き継いでしまうリスクを孕んでいる点に注意が必要です。

## 値を分類し、振舞いが変わる境界を選ぶ

### 4 全ての値は試せない

入力値が「0から150までの整数」という単純な仕様であれば151通りの網羅で済みますが、姓名の文字種、日付、権限、操作手順が重なると組み合わせの総数は爆発的に跳ね上がります。

そこで、同一の処理ロジックが適用されると論理的に推測できる入力値群をグループ化し、不具合の混入しやすい境界値をピンポイントで選び抜く戦略が求められるわけです。

### 5 同値分割法

入力データや出力データの取り得る範囲を、同一の処理や結果をもたらすグループごとに分類し、各グループから代表値を抽出してテストケースを構成する技法が**同値分割法**（同値分析法）です。

すべての値を総当たりで試す代わりに、同じ結果をもたらす代表値を選んでテスト工数を最適化する方針をとります。

たとえば、受け入れ可能な人数が1人以上40人以下と定義されている場面を想定してみましょう。

```text
無効同値クラス：0以下
有効同値クラス：1～40
無効同値クラス：41以上
```

この仕様に対しては、代表値として0、20、41をテストケースに採用する選択が合理的です。

### 6 同値クラス

同一の振る舞いを示すと仮定してグループ化されたデータの集合を同値クラスと定義されます。

システムが正しく受け入れるべき入力の集合を「有効同値クラス」、エラーとして正しく拒絶すべき入力の集合を「無効同値クラス」と区別しなければなりません。
1つのテストデータに複数の無効同値クラスの値を同時に混入させると、どのエラー要因によって処理が弾かれたのか原因を特定しづらくなるため、原則として1つのテストケースにつき1つの無効値を含めるのが鉄則です。

### 7 同値分割の具体例

欠席日の指定可能範囲が「当日から30日後まで（両端を含む）」と定められた仕様を考えてみましょう。

```text
クラスA：昨日以前               → 無効
クラスB：今日～30日後           → 有効
クラスC：31日後以降             → 無効
クラスD：日付として読めない文字 → 無効
クラスE：空欄                   → 無効
```

単なる日付の数値範囲だけでなく、日付フォーマットの不正や未入力といったデータ形式の観点も独立した無効同値クラスとして切り分けます。

### 8 限界値分析法

同値クラスの境界となる値、およびその境界の直前・直後に位置する隣接値は、不等号の比較演算子ミスや添字のオフバイワンエラーが極めて集中しやすい危険地帯です。

この境界線付近の値に着目してテストケースを設計する技法が**限界値分析法**（境界値分析）です。

人数の指定範囲が1から40である場合、次のような値のセットを候補として選定します。

```text
0, 1, 2, 39, 40, 41
```

最小値と最大値そのものだけでなく、境界の外側と内側に隣接する直前・直後の値を確実に網羅しなければなりません。

### 9 なぜ境界で誤りやすいのか

「40以下（<= 40）」と書くべき実装条件を誤って「40未満（< 40）」と記述したり、0始まりの配列インデックスと1始まりの業務番号を混同したりするミスは日常的に発生します。

```text
正しい条件：人数 >= 1 かつ 人数 <= 40
誤りの例  ：人数 > 1  かつ 人数 < 40
```

同値クラスの中央値である「20」だけをいくら入念にテストしても、このような境界判定のバグを見つけ出すことは不可能です。

### 10 数値以外の境界

境界の概念は、単純な数値の大小関係だけに留まりません。
文字列長であれば0文字（空文字）、1文字、システム許容上限の最大長、最大長+1文字が境界となり、日付であれば月末・月初やうるう年の2月29日が境界となります。
受付締切時刻の1秒前、ちょうど、1秒後という時刻境界や、一般ユーザーと管理者権限が切り替わるロール定義も立派な境界条件です。

ファイル取り込み時の0レコード、1レコード、上限レコード数、空リストと先頭・末尾の要素も検証対象となります。
業務ルールが劇的に切り替わる境界ポイントを逃さず洗い出さなければなりません。

### 11 複数境界の組合せ

開始日と終了日のように、2つ以上の入力パラメータが相互に関連し合う仕様も頻出します。

```text
開始日 < 終了日
開始日 = 終了日
開始日 > 終了日
```

個々の入力値単体としては完全に有効な日付であっても、二者の順序関係が破綻している組み合わせを確実にテストして不正な登録を阻止します。

## 条件の組合せを規則として整理する

### 12 デシジョンテーブル

複数の入力条件の組み合わせパターンと、それぞれの状況下で実行されるべき出力動作の対応関係を論理的なマトリクス表として表現したものが**デシジョンテーブル**（決定表）です。

例として、新規登録の可否が本人確認、日付範囲、既存データの有無という3つの論理条件によって分岐するケースを整理してみましょう。

| 条件・動作 | 規則1 | 規則2 | 規則3 | 規則4 |
|---|---:|---:|---:|---:|
| 本人確認済み | 真 | 偽 | 真 | 真 |
| 日付が範囲内 | 真 | ― | 偽 | 真 |
| 既存登録あり | 偽 | ― | ― | 真 |
| 新規登録する | ○ |  |  |  |
| 認証エラー |  | ○ |  |  |
| 日付エラー |  |  | ○ |  |
| 更新確認を出す |  |  |  | ○ |

表内の「―」（ドントケア）記号は、先行する条件によって結果が一意に確定するため、その条件の真偽が判定結果に何ら影響を与えないことを示しているわけです。

### 13 決定表からテストを作る

整理された決定表の各規則列（ルール）を、そのまま1件ずつの独立したテストケースへとマッピングします。

条件数が増大すると組み合わせの総数は `2のn乗` で指数関数的に膨れ上がるため、業務上あり得ない組み合わせや結果に影響しない冗長な条件を論理的に圧縮・整理しなければなりません。
ただし、都合よく行を省略しすぎて重要な複合バグの検出機会を失わないよう、論理圧縮の根拠を明確に残しておかなければなりません。

### 14 原因結果グラフ法

要求仕様書に記述された入力条件を「原因」、出力やシステム動作を「結果」と定義し、それらの因果関係をブール論理記号で可視化する技法が**原因結果グラフ法**です。

```text
原因C1：本人確認済み ─┐
原因C2：日付が有効   ─┼─ AND → 結果E1：登録成功
原因C3：権限あり     ─┘
```

文章だけでは把握しづらい複雑な論理関係をグラフ図として整理し、そこから機械的にデシジョンテーブルを生成してテストケースへ落とし込む流れです。

### 15 AND、OR、NOT

原因結果グラフの骨格をなす論理演算子として、AND、OR、NOTの3要素が活用されます。
ANDはすべての入力原因が真のときのみ結果が真となり、ORはいずれか1つ以上の原因が真であれば結果が真となる演算です。
NOTは入力された条件の真偽値を論理反転させる演算です。

```text
登録可能 = 本人確認済み AND 日付有効 AND NOT 利用停止中
```

仕様書の自然言語に頻出する「〜または〜」という曖昧な表現が、両立を許す論理和なのか、いずれか一方に限定する排他的論理和なのかを厳密に区別しなければなりません。

### 16 制約を表す

入力原因の間には、物理的・業務的な制約によって同時に成立し得ない関係性が存在します。

たとえば連絡区分であれば、「欠席」「遅刻」「早退」のうち同時に選択できるのは厳密に1つだけという排他制約（One and Only One）が課されるわけです。
業務上起こり得ない無意味な組み合わせを制約によって除外し、検証すべき必須の論理パターンを漏れなく網羅します。

## 状態と操作の順序を確かめる

### 17 状態遷移テスト

システムが保持する内部の「状態」と、外部からのイベント入力によって引き起こされる「状態遷移」に着目して振る舞いを検証する技法が**状態遷移テスト**です。

```text
[下書き] --送信--> [受付済み] --担任確認--> [確認済み]
   |                    |
   └--削除--> [削除]    └--取消--> [取消済み]
```

全く同一の「取消ボタンを押す」という操作イベントであっても、システムが現在「下書き」にあるのか、「受付済み」にあるのか、「確認済み」にあるのかによって期待される結果は劇的に変化します。

### 18 状態遷移表

取り得るすべての状態を縦軸に、発生し得るすべてのイベントを横軸に配置し、交点に遷移先状態や発生アクションを網羅した一覧表が状態遷移表です。

| 現在状態＼イベント | 送信 | 確認 | 取消 |
|---|---|---|---|
| 下書き | 受付済み | エラー | 削除 |
| 受付済み | エラー | 確認済み | 取消済み |
| 確認済み | エラー | そのまま | 要承認 |

仕様書に明記された正当な遷移パターンだけでなく、特定の状態において禁止されている不正なイベントが入力された際に、適切にエラー処理が行われるかも検証しなければなりません。

### 19 遷移列

単発の状態変化だけでなく、複数の操作イベントを連続して実行した際の一連のシナリオ（遷移シーケンス）をテストケースとして組み立てます。

```text
下書き → 送信 → 取消 → 再送信
```

操作履歴のスタック破綻、回数制限の誤作動、ブラウザの「戻る」ボタンによる不整合など、操作順序に依存して発生する厄介なバグを摘出できるわけです。
遷移パスの組み合わせは無限に発散するため、中核となる業務フローや利用頻度の高いシナリオを優先してテスト対象に選定します。

### 20 ユースケーステスト

エンドユーザーが特定の業務目標を達成するためにシステムと対話する一連のシナリオ（ユースケース）に基づいてテストケースを導出するアプローチが有効です。

最も典型的な成功ルートである「基本フロー」に加え、途中で発生する例外処理や代替ルートである「代替フロー」を網羅します。

```text
目的：保護者が欠席を連絡する
正常：ログイン→児童選択→入力→確認→送信→受付確認
例外：送信中に通信切断→再送→二重登録を防止
```

個々の入力フォームが単体で正常に動作していても、業務の一連のライフサイクル全体を通したときにデータ不整合が発生しないかを確かめられるわけです。

## 多変数の境界と相互作用を選ぶ

### 21 ドメイン分析テスト

複数の入力パラメータが組み合わさることで形成される多次元の領域（ドメイン）境界に着目し、境界線上およびその近傍の値を体系的に検証する技法がドメイン分析テストです。

たとえば特別割引の適用条件が「年齢18歳未満、かつ会員期間12か月以上」と規定されている場合、年齢の境界（17歳/18歳）と会員期間の境界（11か月/12か月）が交差する平面上の境界ポイントを多角的に検証します。

単一変数の限界値分析を多次元空間へと発展させた高度なテスト設計手法にほかなりません。

### 22 境界上・内側・外側

多次元領域を区切る境界線や境界面に対して、境界線上の点（オンポイント）、有効領域のわずかに内側にある点（インポイント）、無効領域のわずかに外側にある点（アウトポイント）を精緻にサンプリングします。
境界から遠く離れた代表値だけをテストしていては、不等号の傾きやオフセット値の微細な計算ミスをあぶり出すことは困難です。

### 23 組合せ爆発

テスト対象の動作環境として、OS 4種、ブラウザ 5種、言語 3種、ユーザー権限 4種が存在する場合、全組み合わせを単純計算すると `4 × 5 × 3 × 4 = 240` 通りものマトリクスになります。

入力パラメータや設定項目の数が増加するにつれて、全パターンの網羅的実行は工数的に不可能となる「組合せ爆発」の壁に直面するわけです。
そこで、パラメータ間の相互作用リスクを科学的に見極め、最小限のテストケース数で最大の欠陥検出率を達成する工学的アプローチが欠かせません。

### 24 ペアワイズ法

任意の2つのパラメータ（因子）の値の組み合わせが、テストスイート全体のどこかで少なくとも1回は必ず網羅されるように組み合わせを最適化する技法が**ペアワイズ法**（オールペア法）です。

ソフトウェアの欠陥の大半は単一因子の不具合か、あるいは2因子の相互作用によって引き起こされるという工学的な知見に基づいており、全組み合わせテストに比べてテストケース数を大幅に圧縮できます。

ただし、3因子以上が同時に重なり合った時だけに発火する特殊なバグはすり抜けてしまうため、過去に重大障害を起こした危険な組み合わせは個別に追加しなければなりません。

### 25 実験計画法

多数の要因が実験結果に及ぼす影響を、統計的な計画に基づいて最小限の試行回数で効率的に評価する手法が実験計画法です。

```text
要因：サーバ台数、DB索引、同時利用者数
結果：応答時間
```

どの要因がシステムの性能に対して決定的な影響を及ぼしているのか、要因間にどのような交互作用が存在するのかを分散分析によって明らかにします。
単に組み合わせ数を削減する道具にとどまらず、測定誤差の分散や反復実験、無作為化の統計的規律を体系化した手法です。

### 26 直交表

すべての因子の水準の組み合わせが均等な頻度で現れるように数学的に配置された特殊なマトリクスが直交表です。

全組み合わせを実行することなく、主効果や一部の二因子間相互作用を効率的に推定できる利点を持ちます。
ただし、どの直交表がどの相互作用の交絡を許容しているかを正しく理解せずに適用すると、検証すべき重要な相互作用を見落とす危険性があるため注意が必要です。

## 仕様から選びにくい欠陥を探す

### 27 エラー推測

テスターの過去の経験、直感、過去の欠陥ナレッジベースに基づいて、開発者が誤りを犯しやすい弱点や盲点を推測してテストケースを立案する手法がエラー推測です。
ゼロ値、未入力、空ファイル、SQL予約語を含む特殊文字列、許容桁数を大幅に超える極端な長文などを直感的に投入します。

送信ボタンの連続連打、ブラウザの「戻る」操作による二重処理、通信タイムアウト直前の再送といった意地悪な操作パターンも有力な候補です。
体系的な仕様ベース技法を補完する強力なアプローチですが、テスター個人の勘だけに依存して基本要件の確認をおろそかにしてはなりません。

### 28 探索的テスト

テスト対象のソフトウェアを実際に操作しながら学習し、テスト設計、テスト実行、結果の評価を短いサイクルで同時に進行させる動的なテスト手法が**探索的テスト**です。

行き当たりばったりの無計画な操作とは明確に区別されます。
明確な検証テーマを掲げたチャーター、タイムボックス（制限時間）、観察メモ、発見された振る舞いのログを体系的に残しながら進める規律ある活動です。

既知の仕様に対する退行確認は自動テストに委ね、ツールの網羅をすり抜ける予期せぬ不整合の探索は人間の知性に任せるという住み分けが威力を発揮します。

### 29 エラー埋込法

あらかじめ既知の人工的な欠陥（バグ）をプログラム内部に意図的に埋め込んでおき、テストチームがその埋め込みバグをどれだけの割合で発見できたかをもとに、システム全体の潜在バグ総数を統計的に推定する手法がエラー埋込法です。

たとえば、意図的に埋め込んだ20件の欠陥のうち16件がテストで摘出され、同時に本来の未知の欠陥が40件発見されたとします。
埋め込み欠陥の検出率と同じ割合で本来の欠陥も発見できていると仮定し、残存するバグの件数を数理モデルから推計するわけです。

ただし、人工的なバグと本物のバグが同等の難易度で検出されるという強い仮定が成立しなければならず、埋め込んだバグをリリース前に確実に除去する厳格な管理が不可欠となります。

### 30 推定の考え方

埋め込み欠陥の発見率が `16 ÷ 20 = 0.8`（80%）であり、本来の欠陥も同様に80%の確率で発見されたと仮定した場合、潜在していた真の欠陥総数は `40 ÷ 0.8 = 50` 件と推計されます。
したがって、現在発見された40件を差し引いた約10件のバグが、いまだシステム内部に潜伏していると計算される仕組みです。

これはあくまで統計的な推定値であり、絶対的な確定値ではありません。
埋め込んだバグの性質や混入箇所が実際の開発欠陥を正しく代表しているかどうかに結論が大きく左右される点に留意すべきです。

### 31 ファジング

予測不能なランダムデータや、不正に加工・変形させた大量のテストデータ（ファズ）を外部から自動的かつ連続的に流し込み、システムの異常クラッシュやメモリ破壊、例外処理のハングアップを検出する自動化セキュリティテスト手法をファジングと呼びます。

独自のファイルフォーマット解析部、ネットワークプロトコルのハンドシェイク処理、外部APIのエンドポイントなどで未知の脆弱性を洗い出すために広く活用される手法です。

クラッシュを誘発した入力データを保存・最小化して再現テストケースを構築します。
正常系の業務シナリオを網羅的に保証する手法とは目的が異なるため、他の仕様ベーステストと相互補完的に運用しなければなりません。

### 32 ランダムテストとの違い

現代のインテリジェントなファジングツールは、単なる完全なランダムノイズを垂れ流すわけではありません。

正常な構造を持つ入力ファイルをベースに少しずつ変異を加えたり、ソースコードの新しい実行パスを通過した入力を優先的に次世代の変異元として採用したりするフィードバック制御を備えています。
これにより、表層的な構文チェックをすり抜けてコアロジックの奥深くに潜む脆弱性へ効率的に到達できるのです。

## 技法を組み合わせ、仕様の曖昧さも見つける

### 33 ブラックボックス法の組合せ

どれか1つのテスト技法だけで、システムのあらゆる欠陥を網羅することはできません。

```text
同値分割     → 代表的な有効・無効値
限界値分析   → 境界とその両側
決定表       → 条件の組合せ
状態遷移     → 状態と操作順
ユースケース → 業務の一連の流れ
探索・推測   → 予想外の使われ方
```

対象モジュールの特性やリスクプロファイルに応じて、複数のテスト技法を戦略的に組み合わせてテストスイートを編成します。

### 34 仕様の欠陥を見つけたら

テストケースの設計を進めている最中に、仕様書の記述が曖昧で期待結果を1つに確定できない状況に直面することがあります。

```text
締切「17時まで」
17:00:00ちょうどは受け付けるのか
```

このような曖昧さを発見した際、テスト担当者が独断で解釈を決めてテストを進めてはなりません。
要件定義や設計の担当者へ直ちに確認を求め、仕様書の記述と要求トレーサビリティの定義を正式に修正させます。
テスト設計というプロセスは、コードが書かれる前の段階で仕様書自体の欠陥を早期検出する強力な品質ゲートとしても機能するわけです。

### 35 小さな総合例

暗証番号は4桁の半角数字とし、5回連続で入力を誤るとアカウントが自動ロックされるというセキュリティ仕様を総合的にテストする例を見てみましょう。

```text
同値分割：4桁数字／3桁／5桁／文字を含む／空
限界値：0000、9999、長さ3・4・5
状態遷移：誤り0回→1回→…→5回→ロック
決定表：番号一致、ロック状態、有効期限の組合せ
エラー推測：同時送信、5回目直前の正解、日付変更
```

単一の短い仕様文であっても、多面的なブラックボックス技法を適用することで、強固な網羅性を持つテストケース群を導出できます。

### 36 主な概念の区別

- 同値分割は、同一の振る舞いを示すと想定される集合から代表値を抽出する。
- 限界値分析は、同値クラスの境界となる値とその直前・直後の隣接値を検証する。
- 決定表は、複数の条件分岐の論理的な組み合わせと実行動作をマトリクスで整理する。
- 原因結果グラフは、入力条件と出力動作の因果関係をブール論理記号でモデル化する。
- 状態遷移テストは、システムの内部状態とイベントに伴う状態推移の正しさを検証する。
- ドメイン分析は、複数パラメータの組み合わせによって形成される境界領域を扱う。
- エラー埋込法は、人工的に埋め込んだ欠陥の検出率から残存する潜在バグ総数を統計推定する。

### 37 この話のまとめ

ブラックボックステストとは、ソフトウェアの内部コードに立ち入ることなく、要求仕様書に基づいて外部から観測可能な入出力や状態変化を検証する体系的技法です。

あらゆる入力値の全網羅は不可能なため、同値分割法、限界値分析法、デシジョンテーブル、状態遷移テスト、ペアワイズ法、エラー推測などの技法を駆使して、不具合の潜みやすい高リスクな条件を戦略的に選別します。

総当たりを断念することは、決して品質検証の妥協を意味しません。
同一の振る舞いを示す領域を見極め、振る舞いが切り替わる境界を射抜き、状態とルールの組み合わせを整理することによって、限られたリソースの中で最大の欠陥検出力を発揮する体系的なアプローチこそがブラックボックステストの真髄といえます。
