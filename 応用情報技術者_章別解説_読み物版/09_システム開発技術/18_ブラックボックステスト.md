# 第9章・第18話　ブラックボックステスト――中身を見ず、入力と出力から確かめる

1から40までを受け付ける入力欄なら、40個の値を全部試せば十分に見えます。
ところが実際には、範囲外の値、未入力、文字列、条件の組合せ、状態の違いまであり、入力を総当たりすることはできません。

## 1 ブラックボックスというたとえ

**ブラックボックステスト**は、テスト対象の内部を黒い箱として扱い、外から見える振舞いを確認する方法です。

```text
入力・事前条件 → [ 内部は見ない箱 ] → 出力・状態変化
```

ここで「内部を絶対に知ってはいけない」という意味ではありません。
テストデータを選ぶ主な根拠を、内部コードではなく要求・仕様に置きます。

## 2 何を入力・出力と考えるか

入力は、画面に打つ文字だけではありません。

- 利用者の操作
- APIへの要求
- ファイル
- 時刻の経過
- センサー値
- 他システムからの通知
- 権限・設定・既存データ

出力も、画面表示だけではありません。

- 返却値や応答コード
- DBの状態変化
- ファイルや帳票
- 外部サービスへの送信
- ログ・監査記録
- 機器の動作

要求された外部振舞いを広く確認します。

## 3 ブラックボックステストの利点

- 利用者・呼出し側から見た振舞いを確認できる。
- コードを書いた人以外でも仕様から設計できる。
- 実装方法が変わっても、外部仕様が同じなら再利用しやすい。
- 実装者が作り忘れた機能も、要求からテストを作れば気付ける。

一方、内部のどの経路を通ったかは分からず、仕様自体の抜けをそのまま引き継ぐ恐れがあります。

## 4 全ての値は試せない

年齢が0から150の整数なら151通りですが、名前、日付、権限、操作順まで含めると組合せは急増します。

そこで、同じように扱われると考えられる値をまとめ、間違いが起きやすい境界を重点的に選びます。

## 5 同値分割法

入力・出力の範囲を、同じ処理・結果になると考えられるグループに分け、各グループから代表値を選ぶ方法が**同値分割法**です。

この技法は**同値分析法**とも呼ばれます。
「全部の値を試さず、同じ結果になると考えられる組から代表を選ぶ」という意味は同じです。

たとえば、人数は1人以上40人以下とします。

```text
無効同値クラス：0以下
有効同値クラス：1～40
無効同値クラス：41以上
```

代表として0、20、41を試す、といった選び方をします。

## 6 同値クラス

同じ振舞いになると仮定してまとめた集合を**同値クラス**といいます。

有効な入力の集まりを有効同値クラス、拒否されるべき入力の集まりを無効同値クラスと呼びます。

1つの無効テストに複数の誤りを同時に入れると、どの誤りを検出したか分かりにくいため、目的に応じ1つずつ試します。

## 7 同値分割の具体例

欠席日の指定範囲が「今日から30日後まで、両端を含む」とします。

```text
クラスA：昨日以前               → 無効
クラスB：今日～30日後           → 有効
クラスC：31日後以降             → 無効
クラスD：日付として読めない文字 → 無効
クラスE：空欄                   → 無効
```

数値範囲だけでなく、形式と未入力も別のクラスです。

## 8 限界値分析法

範囲の端と、そのすぐ両側は、比較演算子や数え方の誤りが起きやすい場所です。

この境界付近を選ぶ方法が**限界値分析法**、境界値分析です。

人数1～40なら、次を候補にします。

```text
0, 1, 2, 39, 40, 41
```

最小値・最大値だけでなく、その直前・直後を確認します。

## 9 なぜ境界で誤りやすいのか

「40以下」を書くつもりで「40未満」とする、0から数える内部値と1から数える表示を混同する、といった誤りがあります。

```text
正しい条件：人数 >= 1 かつ 人数 <= 40
誤りの例  ：人数 > 1  かつ 人数 < 40
```

中間の20だけを試しても、この誤りは見つかりません。

## 10 数値以外の境界

境界は数値だけではありません。

- 文字列の0文字、1文字、最大長、最大長+1
- 月末と月初
- うるう年の2月29日
- 締切時刻の直前、ちょうど、直後
- 権限が切り替わる役割
- ファイル0件、1件、最大件数
- 空の一覧と最初の要素、最後の要素

業務規則が切り替わる地点を探します。

## 11 複数境界の組合せ

開始日と終了日のように2つの値が関係する場合があります。

```text
開始日 < 終了日
開始日 = 終了日
開始日 > 終了日
```

個別には有効な日付でも、関係が無効になる組合せを試します。

## 12 デシジョンテーブル

複数の条件の組合せと、そのとき行う処理を表にしたものが**デシジョンテーブル**、決定表です。

例として、登録可否が本人確認、日付範囲、既存登録の3条件で決まるとします。

| 条件・動作 | 規則1 | 規則2 | 規則3 | 規則4 |
|---|---:|---:|---:|---:|
| 本人確認済み | 真 | 偽 | 真 | 真 |
| 日付が範囲内 | 真 | ― | 偽 | 真 |
| 既存登録あり | 偽 | ― | ― | 真 |
| 新規登録する | ○ |  |  |  |
| 認証エラー |  | ○ |  |  |
| 日付エラー |  |  | ○ |  |
| 更新確認を出す |  |  |  | ○ |

「―」は、その規則では結果に影響しない条件です。

## 13 決定表からテストを作る

各規則を少なくとも1つのテストケースにします。

条件が多いと組合せが`2の条件数乗`で増えるため、業務上あり得ない組合せ、結果に影響しない条件を整理します。
ただし、都合よく省いて重要な相互作用を失わないようにします。

## 14 原因結果グラフ法

入力条件を**原因**、出力・動作を**結果**とし、AND、OR、NOTなどの論理関係で結ぶ方法が**原因結果グラフ法**です。

```text
原因C1：本人確認済み ─┐
原因C2：日付が有効   ─┼─ AND → 結果E1：登録成功
原因C3：権限あり     ─┘
```

複雑な条件を図で整理し、決定表とテストケースに変換します。

## 15 AND、OR、NOT

- **AND**――すべてが真なら結果が真。
- **OR**――1つ以上が真なら結果が真。
- **NOT**――真偽を反転する。

```text
登録可能 = 本人確認済み AND 日付有効 AND NOT 利用停止中
```

日常語の「または」が排他的か、両方でもよいかを明確にします。

## 16 制約を表す

原因同士に、同時には成り立たない、少なくとも1つ必要などの制約があります。

たとえば、連絡区分は「欠席」「遅刻」「早退」のちょうど1つです。
あり得ない組合せを除き、必要な組合せを網羅します。

## 17 状態遷移テスト

システムが持つ現在の**状態**と、出来事による**遷移**に注目する方法です。

```text
[下書き] --送信--> [受付済み] --担任確認--> [確認済み]
   |                    |
   └--削除--> [削除]    └--取消--> [取消済み]
```

同じ「取消」操作でも、下書き、受付済み、確認済みのどこから行うかで結果が違います。

## 18 状態遷移表

現在状態とイベントの組合せを表にします。

| 現在状態＼イベント | 送信 | 確認 | 取消 |
|---|---|---|---|
| 下書き | 受付済み | エラー | 削除 |
| 受付済み | エラー | 確認済み | 取消済み |
| 確認済み | エラー | そのまま | 要承認 |

有効な遷移だけでなく、禁止された遷移もテストします。

## 19 遷移列

1回の状態変化だけでなく、複数操作の順序を試します。

```text
下書き → 送信 → 取消 → 再送信
```

履歴、回数制限、戻り操作など、順序依存の欠陥を探せます。
すべての長い列は無限に近くなるため、重要な業務シナリオとリスクで選びます。

## 20 ユースケーステスト

利用者が目的を達成する一連の流れに沿って確認します。

正常シナリオだけでなく、代替・例外シナリオも含めます。

```text
目的：保護者が欠席を連絡する
正常：ログイン→児童選択→入力→確認→送信→受付確認
例外：送信中に通信切断→再送→二重登録を防止
```

個々の欄が正しくても、一連の仕事が完了できない問題を見つけます。

## 21 ドメイン分析テスト

複数の入力変数で決まる領域の境界を分析し、境界上とその両側を試す方法が**ドメイン分析テスト**です。

たとえば、割引条件が「年齢18歳未満、かつ会員期間12か月以上」なら、年齢17/18、期間11/12という境界の組合せを調べます。

1変数ずつの限界値分析を、多変数の領域に広げた考えです。

## 22 境界上・内側・外側

領域を分ける線・面について、次の点を選びます。

- 境界の上
- 有効側に少し内側
- 無効側に少し外側

離れた代表値だけでは、境界条件の演算子誤りを見つけにくいからです。

## 23 組合せ爆発

OS 4種、ブラウザ5種、言語3種、権限4種なら、これだけで`4 × 5 × 3 × 4 = 240`通りです。

入力項目が増えると、全組合せは現実的でなくなります。
そこで、相互作用のリスクを考え、少ない組合せで重要な組を含める方法を使います。

## 24 ペアワイズ法

任意の二因子の値の組が、少なくとも一度は現れるようにテスト組合せを選ぶ方法が**ペアワイズ法**です。

多くの欠陥が少数因子の相互作用で起きるという経験を利用し、全組合せより件数を減らします。

3つ以上の因子が同時にそろったときだけ起きる重要な欠陥は逃すため、危険な組合せは別途追加します。

## 25 実験計画法

複数の要因が結果に与える影響を、計画的な実験で効率よく調べる統計的な考えが**実験計画法**です。

```text
要因：サーバ台数、DB索引、同時利用者数
結果：応答時間
```

どの要因が強く効くか、要因同士の相互作用があるかを調べます。
単に組合せを減らす道具ではなく、測定のばらつき、反復、無作為化なども考える方法です。

## 26 直交表

要因と水準の組合せを均衡よく配置した表を**直交表**といい、実験計画や組合せテストに使います。

全組合せより少ない実験で主効果などを分析できます。
ただし、どの相互作用を調べられる設計かを理解せず使うと、必要な問題を見逃します。

## 27 エラー推測

過去の経験や知識から、誤りが起きそうな条件を推測して試す方法が**エラー推測**です。

例は次のとおりです。

- 0件、空欄、空ファイル
- 同じボタンを素早く二度押す
- 戻るボタンを使う
- 期限直前・直後
- 通信を途中で切る
- 特殊文字や非常に長い文字列
- 同じデータを2人が同時更新する

体系的な手法を補います。
経験だけに頼り、基本範囲を欠かさないようにします。

## 28 探索的テスト

テスト対象を学びながら、設計・実行・評価を短い周期で繰り返す方法が**探索的テスト**です。

自由に触るだけではありません。
目的を示すチャーター、時間枠、観察メモ、発見事項を残します。

既知の回帰確認は自動テスト、予想外の振舞いの探索は人、というように組み合わせます。

## 29 エラー埋込法

意図的に既知の欠陥を埋め込み、テストでどの程度見つけられるかから、残る欠陥を推定する考えが**エラー埋込法**です。

たとえば、埋め込んだ20件のうち16件、元からあった欠陥40件を発見したなら、同程度の検出割合を仮定して残存欠陥を推測します。

本物の欠陥と同じ見つかりやすさという仮定が難しく、埋込欠陥を本番に残さない厳格な管理が必要です。

## 30 推定の考え方

埋込欠陥の発見割合が`16 ÷ 20 = 0.8`、元の欠陥も80%見つけたと仮定すると、元の総欠陥は`40 ÷ 0.8 = 50`件、残りは約10件と推定します。

これは確定値ではありません。
埋め込んだ欠陥の種類・位置・難しさが実際の欠陥を代表するという強い仮定があります。

## 31 ファジング

大量の予想外・不正・変形した入力を自動的に与え、異常終了、停止、情報漏えいなどを探す方法が**ファジング**です。

ファイル形式、通信プロトコル、API入力などに使われます。

クラッシュした入力を保存・最小化し、再現テストにします。
正常な業務結果を広く保証する手法ではなく、他のテストと組み合わせます。

## 32 ランダムテストとの違い

ファジングは単なる完全な乱数とは限りません。

有効な入力を少し変形する、コードの新しい経路を通る入力を優先する、既知の危険値を混ぜるなど、欠陥発見を高める仕組みを使います。

## 33 ブラックボックス法の組合せ

1つの方法だけで十分ではありません。

```text
同値分割     → 代表的な有効・無効値
限界値分析   → 境界とその両側
決定表       → 条件の組合せ
状態遷移     → 状態と操作順
ユースケース → 業務の一連の流れ
探索・推測   → 予想外の使われ方
```

対象の特徴に合わせて選びます。

## 34 仕様の欠陥を見つけたら

テスト設計中に、期待結果を1つに決められないことがあります。

```text
締切「17時まで」
17:00:00ちょうどは受け付けるのか
```

テスト担当者が勝手に決めず、要求・仕様の担当者に確認し、文書と追跡関係を修正します。
テスト設計は、仕様の曖昧さを早く見つける活動でもあります。

## 35 小さな総合例

暗証番号は4桁の数字、5回連続で誤るとロックするとします。

```text
同値分割：4桁数字／3桁／5桁／文字を含む／空
限界値：0000、9999、長さ3・4・5
状態遷移：誤り0回→1回→…→5回→ロック
決定表：番号一致、ロック状態、有効期限の組合せ
エラー推測：同時送信、5回目直前の正解、日付変更
```

1つの仕様から複数の観点を導けます。

## 36 試験で区別する要点

- 同値分割は、同じ振舞いと考える集合から代表を選ぶ。
- 限界値分析は、境界とその直前・直後を選ぶ。
- 決定表は、条件の組合せと動作を表す。
- 原因結果グラフは、入力条件と結果を論理関係で結ぶ。
- 状態遷移テストは、現在状態とイベントに注目する。
- ドメイン分析は、複数変数でできる領域の境界を扱う。
- エラー埋込法は、既知の欠陥の検出率から残存欠陥を推定する。

## 37 この話のまとめ

ブラックボックステストは、要求・仕様に基づき、外から見える入力、出力、状態変化を確かめます。

すべての値を試せないため、同値分割、限界値分析、決定表、原因結果グラフ、状態遷移、ドメイン分析、組合せ手法、エラー推測などで、欠陥を見つけやすい条件を選びます。

総当たりを諦めることは、テストを粗くすることではありません。
同じ振舞いをすると考えられる範囲、振舞いが変わる境界、規則や状態の組合せを選ぶことで、限られた入力から欠陥を見つけやすい条件を狙えます。

## 解答と解説

### 問1の解答

主に要求や外部仕様に基づいて選びます。
内部コードの経路ではなく、利用者・呼出し側から見える入力、出力、状態変化に注目します。

### 問2の解答

同じ処理・結果になると考えられる入力範囲を同値クラスに分け、それぞれから代表値を選ぶ方法です。
有効なクラスだけでなく無効なクラスも作ります。

### 問3の解答

0、1、2、39、40、41などです。
最小・最大だけでなく、その直前、境界そのもの、直後を選びます。

### 問4の解答

複数の入力条件の真偽・値の組合せと、その組合せで行う処理・出力を規則ごとに整理します。
組合せの抜けや矛盾を見つけ、テストケースに変換できます。

### 問5の解答

原因は入力条件や事前条件、結果は出力や実行される動作です。
AND、OR、NOTなどで論理関係を結び、条件組合せを整理します。

### 問6の解答

注文、申請、認証失敗回数など、過去の操作により現在状態が変わり、同じイベントでも現在状態によって結果が変わる対象に有効です。
有効な遷移と禁止された遷移の両方を試します。

### 問7の解答

全組合せより少ない件数で、任意の二因子の値の組を含められる利点があります。
一方、三因子以上が同時にそろったときだけ起きる欠陥は保証しないため、高リスクの組合せを別に追加します。

### 問8の解答

エラー推測は、過去に起きた問題や現場知識を生かせますが、経験にない基本範囲を漏らす恐れがあります。
同値分割や限界値分析などで体系的な範囲を確保し、推測で補います。

### 問9の解答

埋め込んだ欠陥と本物の欠陥の種類、位置、見つけやすさが似ているという仮定が必要です。
推定値は確定値ではありません。
また、意図的な欠陥を製品に残さない厳格な管理が必要です。

### 問10の解答

テスト担当者が都合よく決めず、要求・仕様の担当者に確認します。
業務上の意味を決定し、要求・仕様書とテストの期待結果を共に更新し、変更を追跡可能にします。
