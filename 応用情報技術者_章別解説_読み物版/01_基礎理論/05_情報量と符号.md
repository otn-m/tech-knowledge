# 第1章5 情報量と符号――「分かったことの大きさ」を測る

## 珍しい知らせほど、なぜ情報量が大きいのか

8枚のカードから当たりを探す場面を思い浮かべてみてください。
「当たりは左半分にある」という知らせと、「当たりは7番だ」という知らせは、どちらも文字数としては短い一文にすぎません。
しかし、前者を聞いたあとにはまだ4枚の候補が残るのに対し、後者を聞けば候補は即座に1枚へ絞り込まれます。
同じ「知らせ」であっても、受け取った側が知る内容の重みはまったく異なります。
言葉の長さや文字数だけでは、「どれだけ分かったか」という大きさは測れません。

コンピュータ科学において「情報量」とは、知らせを受け取ったときに不確かさがどれだけ減ったかを表す尺度です。
この不確かさの減り方を丁寧に測っていくと、結果を区別するために最低限必要な「ビット数」と自然に結びつきます。
この関係をうまく利用すれば、よく現れるデータを短いビット列で表す「データ圧縮」が実現できます。
その一方で、現実の通信路にはノイズがつきものです。
通信中のビット化けや消失といった誤りに備えるには、一度削ぎ落とした冗長性を、今度は「誤りを検知・訂正するための足場」として意図的に付け足さなければなりません。

小さく削る技術と、安全のためにあえて足す技術。
どちらも「情報をビット列へどう対応づけるか」という符号化の設計思想から生まれています。

## 候補が減る量をビットで測る

### 1 知らせを聞く前と後を比べる

裏返しのカードが8枚あり、そのうちの1枚だけが当たりだとします。
カードをめくる前は、どれが当たりかまったく見当がつきません。

```text
候補: 1 2 3 4 5 6 7 8       8通り
```

ここで「当たりは左半分の4枚の中にある」と教えられたとしましょう。

```text
候補: 1 2 3 4               4通り
```

候補は8通りから4通りへと半減しました。
この知らせには、全体を2分割して「分からない度合い」を1段階減らす働きがあります。

さらに続けて「当たりはその4枚の左半分にある」と教えられたとしましょう。

```text
候補: 1 2                   2通り
```

そして最後にもう一度「左側だ」と告げられた瞬間、候補は1番のカード1枚に決まります。

```text
8候補 → 4候補 → 2候補 → 1候補
         1回目    2回目    3回目
```

8つの候補を完全に1つへ絞り込むまでに、「候補を半分にする二者択一の質問」がちょうど3回必要となりました。
この「二者択一を何回行ったか」という回数こそが、まさに3ビットの情報量です。

1ビットとは、0か1かという2通りの状態を区別する尺度に他なりません。
3ビットあれば、`2³ = 8` 通りの状態をすべて漏れなく区別できます。
裏を返せば、8通りの候補から1つを特定する知らせは、ちょうど3ビット分の価値を持つわけです。

### 2 「2を何回掛けると元の数になるか」

候補が16通りある場合はどうでしょうか。
半分に絞る知らせを繰り返してみます。

```text
16 → 8 → 4 → 2 → 1
```

今度は1枚に絞り込むまでに4回の知らせが必要です。
この「4回」という数値は、16が「2を4回掛けた数（2の4乗）」であることと正確に対応しています。

```text
2⁴ = 16
```

数学では、「2を何乗すると16になるか」を逆向きに求める計算を **対数（logarithm）** と呼びます。

```text
log₂ 16 = 4
```

読み方は「ログ、底（てい）2の16」です。
右下に小さく書かれた2を底と呼びます。

```text
2³ = 8   と   log₂ 8 = 3   は、同じ関係を表裏から見ている
```

候補の数と、完全に1つに絞り込むために必要な二者択一の回数（対数）を並べてみると、次のようになります。

| 候補数 | 必要な二者択一の回数 | 対数 |
|---:|---:|---:|
| 2 | 1 | `log₂2 = 1` |
| 4 | 2 | `log₂4 = 2` |
| 8 | 3 | `log₂8 = 3` |
| 16 | 4 | `log₂16 = 4` |
| 1024 | 10 | `log₂1024 = 10` |

候補数が2の累乗でない場合はどう考えればよいでしょうか。
たとえば候補が5つある場合、2ビット（4通り）では足りず、1つ余ってしまいます。
そのため、すべての候補を均一な固定長のビット列で表すなら、切り上げて3ビット（8通り）を割り当てなければなりません。
しかし、後述するように工夫次第で、平均ビット数をさらに削る余地が生まれます。

### 3 珍しい知らせほど情報量が大きい

ここまでは、8枚のカードのように「どの候補も同じ確率で起こる」状況を前提にしていました。
しかし現実の出来事は、すべてが等確率で起こるわけではありません。

たとえば、連日晴天が続いている砂漠の町で「明日も晴れです」という予報を聞いても、驚く人はほとんどいないでしょう。
一方、「明日は観測史上初の大雪になる」という予報を聞けば、街中が大騒ぎになります。
前者の知らせは当たり前すぎて不確かさをほとんど減らしませんが、めったに起きない後者の知らせは、人々の予想を大きく覆し、多くの曖昧さを一挙に解消します。

すなわち、めったに起きない珍しい知らせほど、受け取った側の「情報量」は大きいのです。

ある出来事の起こる確率を `p` とするとき、その出来事が実際に起きたと知ったときの情報量 `I`（選択情報量）は、次のように定義されます。

```text
I = -log₂ p
```

ここで `I` は information（情報）、`p` は probability（確率）の頭文字です。
単位はビット（bit）で表します。

#### 確率が 1/8 の出来事

8枚のカードから1枚が当たる確率は `p = 1/8` です。
`1/8 = 2⁻³` ですから、公式に当てはめると次のようになります。

```text
I = -log₂(1/8)
  = -log₂(2⁻³)
  = -(-3)
  = 3ビット
```

8通りの候補から1つに絞り込むために3ビット必要だったカードの例と、まったく同じ値が導かれました。

#### 必ず起きる出来事

「明日太陽が東から昇る」のように、確率が1（100%）で必ず起きる出来事の情報量はどうなるでしょうか。

```text
I = -log₂ 1 = 0ビット
```

最初から起きることが分かりきっている出来事を聞いても、新しく減る不確かさはありません。
したがって、情報量はゼロです。

#### なぜ先頭にマイナスが付くのか

確率 `p` は常に0より大きく1以下の値をとります。
そのため、底が2の対数 `log₂ p` は必ず0以下の負の数になります。

```text
log₂(1/2) = -1
log₂(1/4) = -2
```

情報量を「得られた知識の量」として直感的な正の数値で扱うため、定義式の先頭にマイナス記号を付けて正の値へ反転させているのです。
あるいは、分数の逆数を取って `log₂(1/p)` と書いても同じことです。

### 4 なぜ対数を使うのか

情報量の定義になぜわざわざ対数を使うのか、疑問に思うかもしれません。
その最大の理由は、独立した出来事の情報量を「足し算」で扱えるようにするためです。

表と裏が等確率（1/2）で出る硬貨を2回投げる場面を考えます。
「1回目が表になり、かつ2回目も表になる」という複合的な出来事の確率は、確率の積として計算されます。

```text
1/2 × 1/2 = 1/4
```

一方で、私たちが直感的に感じる情報量はどうでしょうか。
1回目に表が出た知らせ（1ビット）を受け取り、さらに2回目も表が出た知らせ（1ビット）を受け取ったのですから、合計で「1 + 1 = 2ビット」の情報を受け取ったと数えるのが自然です。

確率の世界では出来事を組み合わせると掛け算になります。
しかし、情報量の世界では出来事を組み合わせたとき足し算になってほしいのです。
対数にはまさに、「掛け算を足し算に変換する」という代数的な性質があります。

```text
log₂(x × y) = log₂ x + log₂ y
```

情報量を `-log₂ p` と定義しておけば、確率の積がそのまま情報量の和へ綺麗に変換されます。

```text
-log₂(1/2 × 1/2)
= -log₂(1/2) + -log₂(1/2)
= 1 + 1
= 2ビット
```

そして底に2を選ぶのは、コンピュータが拠って立つ「0か1かの二者択一」を情報量の基本単位「1ビット」に据えるためです。

## 1回の情報量から平均の情報量へ

### 5 平均すると、情報源全体の不確かさになる

珍しい出来事1つひとつの情報量がどれほど大きくても、それがめったに起きないなら、普段やり取りするデータの大部分を占めるわけではありません。
通信やデータ保存の効率を考えるには、個別の出来事の大きさだけでなく、「長期的に平均して1回あたり何ビットの情報が送られてくるのか」を捉える必要があります。

ここで、ある情報源から3つのメッセージ A、B、C のいずれかが送信される状況を考えてみましょう。
それぞれの出現確率は次のとおりです。

```text
A: 1/2 （50%）
B: 1/4 （25%）
C: 1/4 （25%）
```

各メッセージが単独で届いたときの情報量を計算してみます。

```text
A: -log₂(1/2) = 1ビット
B: -log₂(1/4) = 2ビット
C: -log₂(1/4) = 2ビット
```

もしこの情報源からメッセージが100回送られてきたらどうなるでしょうか。
確率どおりなら、Aはおよそ50回、BとCはおよそ25回ずつ届きます。

```text
100回分の合計情報量
= 50回 × 1ビット + 25回 × 2ビット + 25回 × 2ビット
= 50 + 50 + 50
= 150ビット
```

100回で合計150ビットですから、1回あたりの平均情報量は次の値になります。

```text
150ビット ÷ 100回 = 1.5ビット/回
```

この計算を確率を使って直接書くと、それぞれの情報量にその発生確率を掛けて足し合わせる「期待値の計算」そのものです。

```text
(1/2 × 1ビット) + (1/4 × 2ビット) + (1/4 × 2ビット) = 1.5ビット
```

このように、各出来事の情報量をそれぞれの出現確率で重み付けして平均した値を、情報理論では **エントロピー（平均情報量）** と呼び、通常記号 `H` で表します。

```text
H = - Σ pᵢ log₂ pᵢ
```

数式の各記号を丁寧に読み解いてみましょう。

- `H`: エントロピー（平均情報量）を表す記号。
- `Σ`（シグマ）: すべての出来事について足し合わせる。
- `i`: どの出来事かを指すインデックス番号。
- `pᵢ`: i番目の出来事が起きる確率。
- `-log₂ pᵢ`: i番目の出来事が持っている個別の情報量。
- `pᵢ` を掛ける: よく出る出来事ほど平均値に強く反映させるための重み付け。

エントロピーが大きいほど、次に何が起きるか事前に予測しにくく、情報源全体の「不確かさ」が高いことを意味します。
そしてこのエントロピーこそが、後述する「これ以上は縮められない圧縮の理論的限界」を表す数値となります。

### 6 同じ4種類でも確率でエントロピーが変わる

エントロピーの直感を掴むために、同じ4つの記号（A, B, C, D）を出力する2つのシステムを比較してみましょう。

もし4種類の記号がすべて `1/4` の等確率で出現するなら、次に何が出るかは完全に五里霧中です。

```text
H = 4 × (1/4 × -log₂(1/4))
  = 4 × (1/4 × 2)
  = 2ビット
```

このときエントロピーは最大値の2ビットになり、4通りを固定長ビットで表す長さ（2ビット）と一致します。

一方、Aの確率が97%で、B、C、Dはそれぞれ1%ずつしか出ない極端なシステムを想像してみてください。
BやCが出たときの単独の情報量は約6.64ビットと非常に大きいですが、普段はほぼ毎回Aが出ます。
計算してみると、エントロピーは約0.24ビットまで激減します。
「ほぼ毎回Aに決まっている」という強い偏りがあるため、システム全体としての不確かさはほとんど存在しないのです。

つまり、データの「種類の多さ」だけで必要なビット数が決まるわけではありません。
「それぞれの種類がどれほどの割合で現れるか」という出現確率の偏りこそが、データをどれだけ小さく圧縮できるかを決定づけるのです。

## 短く、区切りを失わずに符号化する

### 7 符号化――対象をビット列へ対応づける

文字や記号をコンピュータで扱うには、それぞれの対象に一意のビット列を割り当てる必要があります。
この対応関係を定義することを **符号化（エンコード）** と呼び、個々の対象に割り当てられたビット列を**符号語**と呼びます。
逆に、受信したビット列から元の文字を復元する処理が **復号（デコード）** です。

たとえば4文字 A、B、C、D をすべて同じ長さのビット列で表すなら、2ビットずつ割り当てれば十分です。

```text
A → 00
B → 01
C → 10
D → 11
```

この対応表を使えば、文字列 `ABCD` は `00011011` という8ビットの列へと変換されます。
固定長符号は構造が単純で扱いやすい反面、どの文字も同じ長さとして扱うため、文字ごとの出現頻度の違いを活かせません。

### 8 よく出る文字を短くする圧縮

先ほどエントロピーを計算した A、B、C（確率は Aが 1/2、BとCが 1/4 ずつ）を例に取ります。
文字ごとにビット列の長さを変える「可変長符号」を導入してみましょう。
頻繁に現れるAには短い1ビットを、たまにしか現れないBとCには2ビットを割り当ててみます。

```text
A → 0
B → 10
C → 11
```

このとき、1文字あたりの平均ビット長の計算は次の通りです。

```text
(1/2 × 1ビット) + (1/4 × 2ビット) + (1/4 × 2ビット)
= 0.5 + 0.5 + 0.5
= 1.5ビット/文字
```

すべてを2ビットで表していた固定長符号と比べ、データ全体の長さを25%も削減できました。
しかも、この平均1.5ビットという数値は、先ほど求めたエントロピーの値と完全に一致する理論値に他なりません。

出現確率の偏りを利用して全体のデータ量を減らすこのアプローチを**情報源符号化**、日常的な言葉でいえば**データ圧縮**と呼びます。

### 9 どこで1文字が終わるか

可変長符号には大きなメリットがある反面、重大な落とし穴も潜んでいます。
文字ごとに長さが異なるため、ビット列を受信した側が「どこからどこまでが1文字なのか」を見失ってしまう危険があるのです。

失敗する例を見てみましょう。

```text
A → 0
B → 01
```

いま、ビット列 `01` が届いたとします。
受信側は、先頭の `0` を見て「Aだ」と判断すべきでしょうか。
それとも、次の `1` まで合わせて「Bだ」と判断すべきでしょうか。
`0` のあとに続くデータを見なければ判断が定まらず、曖昧さが生じてしまいます。

この混乱を防ぐための鉄則が、 **接頭語条件（プレフィックス条件）** です。
接頭語条件とは、「ある符号語が、別の符号語の先頭部分（プレフィックス）になってはならない」という規則を指します。
この条件を満たす符号を **接頭語符号（瞬時復号可能符号）** と呼びます。

先ほどの成功例を改めて確認してみましょう。

```text
A → 0
B → 10
C → 11
```

`0` で始まる符号語はAしかありません。
したがって、`0` を読み取った瞬間に「これは絶対にAだ」と即座に確定できます。
もし `1` から始まったなら、まだ確定はできませんが、次のビットをもう1つ読めば `10` でBか、`11` でCかが確実に判別できます。
後ろのデータを先読みして迷うことなく、ビット列を左から順に読み進めるだけで一意に復元できるのです。

### 10 ハフマン符号

接頭語条件を満たしながら、出現頻度に応じて最適な符号語を自動的に組み立てる代表的なアルゴリズムが**ハフマン符号**です。

ハフマン符号の構築手順は、非常に明快なロジックに基づいています。
出現頻度の低い2つの要素を順次ペアにして木構造（二分木）をボトムアップに構築し、よく出る要素を木の「根（ルート）」の近くへ、めったに出ない要素を「葉（先端）」の遠くへ配置します。

具体的な例で手順を追ってみましょう。
A、B、C、D の出現回数が次のように与えられたとします。

```text
A: 50回
B: 25回
C: 15回
D: 10回
```

#### 手順1: 最も頻度の低い2つをまとめる
最も回数の少ない C（15）と D（10）を選び、両者を合算した新しい親ノード「CD（25）」を作ります。

```text
C 15 + D 10 = 25
```

#### 手順2: 残った候補の中で最も低い2つをまとめる
現在の候補は A（50）、B（25）、CD（25）です。
最も低いのは B（25）と CD（25）なので、この2つを合算して親ノード「BCD（50）」を作ります。

#### 手順3: 最後の2つをまとめる
残ったのは A（50）と BCD（50）です。
この2つを合算して根ノード（100）を作れば、木が完成します。

```text
          [100]
         /     \
      A (50)   [50]
              /    \
           B (25)  [25]
                  /    \
               C (15)  D (10)
```

#### 手順4: 枝に 0 と 1 を割り振る
根から各文字へ向かう枝について、たとえば「左に進むなら0、右に進むなら1」と割り当ててみましょう。

- A へ進むパス: 左 → 0
- B へ進むパス: 右 → 左 → 10
- C へ進むパス: 右 → 右 → 左 → 110
- D へ進むパス: 右 → 右 → 右 → 111

できあがった符号語は次のようになります。

```text
A → 0     (1ビット)
B → 10    (2ビット)
C → 110   (3ビット)
D → 111   (3ビット)
```

出現頻度が最も高いAには最短の1ビットが割り当てられ、頻度の低いCとDには3ビットが割り当てられました。
すべての文字が木の「葉」に位置しているため、ある符号語が別の符号語の先頭になることは構造上あり得ません。
ハフマン木から生成した符号は、自動的に接頭語条件を満たします。

なお、左右の枝に0と1のどちらを割り振るかは流儀の違いにすぎず、平均の符号長はどちらでもまったく変わりません。
最も重要なのは、出現頻度に応じて木が作る深さの構造です。

### 11 可逆圧縮と非可逆圧縮

ハフマン符号のように、圧縮したデータから元の完全なデータを1ビットの狂いもなく復元できる方式を **可逆圧縮（ロスレス圧縮）** と呼びます。
プログラムの実行ファイル、テキスト文書、データベースの帳簿記録など、1文字や1ビットの食い違いも許されない用途では、必ず可逆圧縮を用います。ZIPやPNGなどがその代表例です。

一方、人間の知覚の限界を利用して、元のデータから知覚しにくい微細な成分を大胆に間引く方式を **非可逆圧縮（ロッシー圧縮）** と呼びます。
写真（JPEG）、音楽（MP3, AAC）、動画（MP4, H.264/HEVC）などが代表例です。

非可逆圧縮は、データを適当に壊して小さくしているわけではありません。
人間の目が色の細かな変化よりも明暗の変化に敏感であることや、人間の耳が大きな音の直後にある小さな音を聞き取りにくいといった生理学的な性質（心理音響・心理視覚モデル）を計算に取り入れ、影響の極めて小さい情報を選んで削ぎ落としています。
その結果、可逆圧縮とは桁違いの圧縮率を達成できますが、一度失われた情報は二度と元には戻りません。
編集や保存を何度も繰り返すと劣化が蓄積していく点に注意が必要です。

## 誤りを見つけるために冗長性を持たせる

### 12 通信では、あえて余分な情報を加える

データ圧縮の目的は、データの冗長性（無駄な偏り）を限界まで削ぎ落とし、最小限のビット列に詰め込むことでした。
しかし、極限まで圧縮されたビット列をノイズ混じりの現実のネットワークに流すと、新たな困難に直面します。

すべてのビットが重要な情報で満ちているため、通信中のノイズでたった1ビットが `0` から `1` に反転しただけでも、受信側はそれが誤りであることに気付けません。
気付けないまま復号を試みれば、まったく別の文字に化けたり、以降のすべてのデータがずれて崩壊してしまいます。

そこで通信の世界では、圧縮とは正反対のアプローチを取ります。
誤りを検知したり、自力で元の正しい値へと修復したりするために、あらかじめ計算された検査用の余分なビット（冗長ビット）を意図的に付け足して送信するのです。
この仕組みを**通信路符号化**と呼びます。

```text
情報源符号化（圧縮）: 余分な冗長性を削り、ビット列を極力短くする
通信路符号化（誤り制御）: 誤りに備えて、計算された冗長ビットをあえて付け足す
```

一見すると矛盾する操作のように思えますが、どちらも「情報の性質を理解し、ビット列の対応関係を精密に設計する」という根底の思想は同じです。

### 13 パリティビット――1の個数で誤りを見つける

最も身近でシンプルな誤り検出の仕組みが**パリティビット**です。

いま、送信したい元データが `1011001` であるケースを考えてみましょう。
このデータの中に含まれる「1」の個数を数えると、4個（偶数個）並んでいます。
パリティ方式では、データ全体の「1」の個数が常に偶数（または奇数）になるよう、末尾に検査用の1ビットを付加する設計です。
1の個数を偶数に揃える方式が偶数パリティ、奇数に揃える方式が奇数パリティと呼ばれます。

ここでは偶数パリティを採用してみましょう。
元データに含まれる1の個数はすでに4個（偶数）ですから、偶数パリティビットには `0` を設定します。

```text
元データ         : 1011001   (1が4個)
パリティビット   : 0
送信するビット列 : 10110010  (1が4個)
```

このビット列が通信路を通り、途中でノイズによって1ビットだけ反転したとします。

```text
受信したビット列 : 10100010  (1が3個)
```

受信側で1の個数を数えた結果は3個（奇数）です。
「偶数パリティのはずなのに奇数になっている」ことから、通信のどこかでビット化けが発生した事実を確実に検知できます。

しかし、パリティビットには明確な限界が存在します。
もし偶然にも2つのビットが同時に反転してしまうと、1の個数は再び偶数に戻るため、誤りを見逃してしまうのです。
また、「どこかのビットが誤っている」ことは分かっても、「何番目のビットが化けたのか」までは特定できないため、受信側が自力で値を修正することはできません。

### 14 CRC――多項式の割り算でバースト誤りを捕まえる

パリティビットよりも遥かに強力な誤り検出方式として、イーサネットやストレージ機器などで広く使われているのが **CRC（Cyclic Redundancy Check: 巡回冗長検査）** です。

CRCでは、送信するビット列を数学の「多項式の係数」と見なし、規格であらかじめ定められた共通の生成多項式で割り算を行います。
この割り算（ビットごとの排他的論理和を用いた二進演算）を行って得られた「余り（剰余）」を検査用コードとしてデータ末尾に付加して送信します。

受信側でも全く同じ生成多項式で割り算を行い、余りがゼロになるかを照合する仕組みです。
CRCの優れた点は、ノイズによって連続した複数のビットがまとめて反転するバースト誤りに対しても、極めて高い確率で検出できることにあります。

ただし、CRCを扱う上で混同してはならない重要な注意点があります。
CRCはあくまで偶然発生した通信エラーや物理的な媒体劣化を検出するための技術です。
もし悪意を持った攻撃者がデータを改ざんした場合、攻撃者は改ざん後のデータに合わせてCRCの値も正しく再計算して偽装できてしまいます。
人為的な改ざんを防ぐ用途には、暗号学的ハッシュ関数（SHA-256など）やデジタル署名を用いなければなりません。

### 15 ハミング距離――符号語同士が何ビット離れているか

「誤りを見つける能力（検出）」と「誤りを自力で直す能力（訂正）」の間には、どのような数学的境界があるのでしょうか。
この境界を解き明かす鍵となるのが、**ハミング距離**という概念です。

ハミング距離とは、同じ長さの2つのビット列を比べたとき、値が異なっている桁の個数を指します。

```text
1 0 1 1 0 1
1 0 0 0 0 1
    ↑ ↑       2箇所が異なる

ハミング距離 = 2
```

もし私たちが使う正規の符号語同士の距離が近すぎると、わずか1ビット化けただけで「別の正規の符号語」にすり替わってしまい、誤りを見つけることすらできません。
逆に、正規の符号語同士を互いに遠く離しておけば、途中でビット化けが起きても「正規の符号語から外れた不正な値」として検出できます。
さらに十分な距離が確保されていれば、「変化したビット列に最も近い正規の符号語はどれか」を探すことで、化けたビットを特定して元の値へ修復（訂正）することまで可能です。

数学的には、すべての正規符号語の間で最も小さいハミング距離を**最小ハミング距離 `d`** とするとき、次の関係が成り立ちます。

- `d - 1` ビットまでの誤りを検出できる
- `floor((d - 1) / 2)` ビットまでの誤りを訂正できる

ここで `floor` は小数点以下を切り捨てる演算です。

| 最小ハミング距離 `d` | 検出できる誤り数 | 訂正できる誤り数 |
|:---:|:---:|:---:|
| 1 | 0ビット | 0ビット |
| 2 | 1ビット | 0ビット（パリティビットなど） |
| 3 | 2ビット | 1ビット（ハミング符号など） |
| 4 | 3ビット | 1ビット（1ビット訂正・2ビット検出） |

たとえば最小ハミング距離が 3 の符号体系を用意すれば、途中で1ビットが化けても元の符号語へ正しく訂正でき、訂正はできずとも2ビットまでの誤りなら検出できます。

### 16 ハミング符号――誤りの位置を特定して直す

このハミング距離の原理を鮮やかに具現化したのが**ハミング符号**です。
ハミング符号は、コンピュータのメインメモリ（ECCメモリ）などで広く使われており、1ビットの誤りを自動的に訂正できる能力を持っています。

その仕掛けは「複数のパリティ検査を重ね合わせる」点に他なりません。
ハミング符号では、データビットの隙間に複数の検査ビットを戦略的に配置する構成をとります。
それぞれの検査ビットは、特定のビット位置を組み合わせたグループごとに分担してパリティを照合する仕組みです。

通信中にどこか1ビットが反転した際、そのビットが含まれるグループのパリティ検査だけが一斉にエラーを起こします。
受信側は「どの検査が失敗し、どの検査が成功したか」というエラー結果の組み合わせ（シンドローム）を並べるだけで、まるで二分探索のように、何ビット目が狂っているのかという座標を一意に特定できるのです。

場所さえ分かれば、訂正は簡単です。
二進数の世界では値は0か1しかありませんから、特定された位置のビットを反転させるだけで、完全に元のデータへと復元されます。

誤りの検出や訂正の能力を高めれば高めるほど、付加する冗長ビットが増え、計算量や通信のオーバーヘッドも大きくなります。
ネットワークの品質、再送が可能かどうか、リアルタイム性などの制約を天秤にかけながら、システムに最適な符号化方式を選定することが重要です。

### 17 符号化の目的を混同しない

「符号化（エンコード）」という言葉は、ITの様々な場面で登場します。
しかし、その目的や要求される性質は文脈によってまったく異なります。

| 目的 | 何をするか | 代表例 |
|---|---|---|
| 文字表現 | 文字をコンピュータで扱うため一意のビット列に対応づける | ASCII, UTF-8, Shift_JIS |
| データ圧縮 | 出現頻度の偏りを利用して全体の平均データ量を減らす | ハフマン符号, ランレングス符号, ZIP |
| 誤り検出 | 通信や保存の途中でビット化けが起きた事実を見つける | パリティビット, CRC, チェックサム |
| 誤り訂正 | 誤りが発生した位置を特定し、自力で元の値へ修復する | ハミング符号, リード・ソロモン符号 |
| 暗号化 | 正当な鍵を持たない第三者に内容を解読されないよう秘匿する | AES, RSA（第8章で詳述） |

これらを混同してはいけません。
データを圧縮しても、決して情報が秘密になったわけではありません。
CRCで検査値を付けても、悪意ある改ざんを防ぐ盾にはなりません。

それぞれの仕組みが「何を目的として、どのような前提のもとで作られているのか」を正しく見極めることが、堅牢なシステムを設計するための第一歩となります。
