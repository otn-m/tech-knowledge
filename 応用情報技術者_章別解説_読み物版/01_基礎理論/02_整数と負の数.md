# 第1章2 整数と負の数――同じビット列をどう読むか

## 同じビット列が255にもマイナス1にもなる

8ビットの`11111111`というデータには、プラスやマイナスの符号も、どこが境目かを示す小数点も記録されていません。
これを「符号なし整数」として読めば255になりますが、「二の補数を使った符号付き整数」として読めば-1になります。
物理的なメモリから0と1のビット列を取り出しただけでは、それが255なのか-1なのかは誰にも判断できないのです。

8ビットで作れる256通りの組み合わせを、現実世界のどの数値に割り当てるか。
負の数を扱いたいなら、その割当てルールをあらかじめ決めておかなければなりません。
さらに、ルールを決めて正しく計算したとしても、計算結果が同じ8ビットの器の中に収まりきるとは限りません。
コンピュータが整数を扱うときに直面する「符号の割り当て」と「器の限界（オーバフロー）」の仕組みを解き明かしていきましょう。

## 負数を含めた値の割当て

### 1 256枚の番号札を何へ割り当てるか

8ビットの箱を使うと、256通りの異なる並びを作ることができます。

```text
00000000
00000001
00000010
   …
11111111
```

この256通りのビット列に、0から255までの整数を小さい順に1つずつ割り当てていくのが最も素直な方法です。

```text
00000000 →   0
00000001 →   1
   …
11111111 → 255
```

正か負かを示す目印のことを**符号**と呼びます。
この方式ではマイナスの値を一切使わないため、**符号なし整数**（unsigned integer）というわけです。

しかし、現実のシステムでは、氷点下の気温、銀行口座の引き落としによる残高不足、ビルの地下階など、マイナスの数（負数）を扱いたい場面が無数に存在します。
もしビットの桁数（8ビット＝256通り）を増やせないとすれば、限られた256枚の番号札を、正の数と負の数で分け合って割り当てるしかありません。
この読み方を**符号付き整数**（signed integer）と呼びます。

手元にあるビット列がまったく同じ`11111111`であっても、どちらのルールで解釈するかによって得られる数値は激変するのです。

```text
ビット列: 11111111

符号なし整数として解釈する         →  255
二の補数の符号付き整数として解釈する →   -1
```

この「ビット列をどう解釈するか」という取り決めこそが、プログラミング言語における**データ型**（整数型）の正体に他なりません。

### 2 先頭を正負の印にする素朴な案（符号絶対値表現）

負数を表現しようと考えたとき、誰もが最初に思いつくのが「一番左端の1ビットをプラス・マイナスの目印（符号ビット）にする」というアイデアです。

```text
先頭が 0 → 正の数（+）
先頭が 1 → 負の数（-）
残りの7ビット → 数値の絶対値（大きさ）
```

この方式を**符号絶対値表現**と呼びます。

```text
00000101 → +5
10000101 → -5
```

直感的で人間にはとても分かりやすい方式ですが、コンピュータにとっては2つの深刻な欠点がありました。

第一に、「`+0`」と「`-0`」という2種類のゼロが生まれてしまう点です。

```text
00000000 → +0
10000000 → -0
```

数学的にはまったく同一の「0」に対して、貴重な256通りのビット列のうち2つを無駄に消費してしまいます。プログラムで「`x == 0`」を判定するたびに、わざわざ2通りのゼロをチェックしなければなりません。

第二の、より致命的な欠点は、通常の加算回路で計算ができない点です。
たとえば`5 + (-5)`を計算しようとして、`00000101`と`10000101`をそのまま足し算すると、`10001010`（-10）というわけのわからない結果になってしまいます。
加算回路とは別に専用の減算回路を用意し、「正と負を足すときは絶対値を比べて大きい方から引き算して……」といった複雑な条件分岐回路をハードウェア上に組まなければならなくなります。

回路を複雑にすることなく、足し算の回路だけで引き算まで自動的に片づけられる、もっとスマートな割当てルールはないものか。
そうして生み出されたのが「二の補数」です。

## 加算回路をそのまま使い回す「二の補数」

### 3 二の補数――反転して1を足す魔法

現在ほぼすべてのコンピュータで採用されている負数の表現形式が**二の補数**（two's complement）です。
二の補数では、負の数を作る手順が次のように決まっています。

「0と1をすべて反転させ、最後に1を足す」

例として、8ビットの器の中で`-5`を作ってみましょう。

#### 手順1 正の数（+5）を二進数で書く

```text
+5 = 00000101
```

#### 手順2 すべてのビットを反転させる（ビット反転）

0を1に、1を0にひっくり返します。

```text
00000101
   ↓ 反転
11111010
```

#### 手順3 最後に1を足す

```text
  11111010
+ 00000001
----------
  11111011
```

こうして完成した`11111011`が、8ビット二の補数における「`-5`」のビット列です。

### 4 なぜ反転して1を足すと負数になるのか

なぜこんな奇妙な操作でマイナスの数が作れるのでしょうか。
その答えは、元の`+5`と、いま作った`-5`を、普通の足し算の手順で足してみると一瞬で氷解します。

```text
  00000101   （+5）
+ 11111011   （-5）
----------
1 00000000
```

答えは9桁の`100000000₂`になりました。
しかし、この世界は「8ビット」の器しかありません。左端にあふれ出た9桁目の「1」は、器に入り切らずにそのままポロリと捨てられます。
その結果、器の中に残った数値を見てください。

```text
00000000 （= 0）
```

見事に「`5 + (-5) = 0`」が成立しています！
引き算のための専用回路を一切使わず、第1節で学んだ「普通の二進数の足し算」を実行しただけで、完全に正しい計算結果が得られたのです。

#### 時計の針で考える補数の原理

この仕組みは、アナログ時計の文字盤を思い浮かべると直感的に理解できます。
時計の針を「5時間戻したい（-5）」とき、針を反時計回りに5時間戻してもいいですが、「時計回りに7時間進める（+7）」ことでも、まったく同じ時刻を指すことができます。なぜなら、時計は「12時間」でちょうど1周して元の位置に戻るからです。

8ビットの世界もこれとまったく同じです。
8ビットは256進むとちょうど1周して`00000000`に戻ります。
したがって、「5を引く（-5）」という操作は、「1周の256から5を引いた数、つまり251を足す」ことと完全に等価です。

```text
256 - 5 = 251
251₁₀ = 11111011₂
```

そして、「全ビットを反転して1を足す」という操作は、二進数において「`256 - 元の数`」を素早く計算するための天才的なショートカットだったのです。

### 5 8ビット二の補数が表現できる範囲

8ビットで作れる256通りの組み合わせを、二の補数では次のように半分ずつ山分けします。

- 0以上のグループ（先頭ビットが0）：0から127までの128個
- 負の数のグループ（先頭ビットが1）：-1から-128までの128個

```text
00000000 =    0
00000001 =    1
   …
01111111 =  127  （正の最大値）
10000000 = -128  （負の最小値）
10000001 = -127
   …
11111110 =   -2
11111111 =   -1
```

ここで重要な特徴に気づきます。
表現できる範囲は「-128から+127まで」であり、プラス側とマイナス側で対称になっていません。マイナス側のほうが1つだけ余分に広くなっています。
なぜなら、非負のグループ（128個）の中に「0」が含まれているため、正の整数に使える枠が127個分しかないからです。

符号絶対値表現のような「`+0`」と「`-0`」の重複がなく、256通りの組み合わせが無駄なくすべて有効な数値に割り当てられています。

#### 一般のnビットにおける表現範囲

この規則を一般的な`n`ビットに拡張すると、表現できる範囲は次の公式で表されます。

```text
最小値 = -2ⁿ⁻¹
最大値 =  2ⁿ⁻¹ - 1
```

たとえば、8ビット（`n = 8`）における計算は次の通りです。

```text
最小値 = -2⁷     = -128
最大値 =  2⁷ - 1 = 127
```

基本情報や応用情報技術者試験で頻出の公式ですが、丸暗記する必要はありません。「最上位の1ビットを正負の境界に使っているため、残りの`n - 1`ビットで大きさを表している。そしてプラス側は0に枠を1つ譲っているから-1される」と理解しておけば、試験会場でいつでも自力で導き出せるはずです。

### 6 負のビット列を十進数へ戻す

先頭が「1」で始まっている二の補数のビット列を見かけたとき、それが十進数でマイナスいくつなのかを調べるには、負数を作ったときの手順を逆にたどります。

例として、`11110110`を十進数に戻してみましょう。先頭が1なので負数であることは明白です。

1. 1を引く: `11110110 - 1 = 11110101`
2. ビット反転する: `00001010`
3. 十進数に直す: `00001010₂ = 10`

絶対値が10だと判明したので、元の値は「-10」です。

あるいは、先ほどの「時計の針の理屈」を使って、符号なし整数としての値（246）から1周分の256を引き算しても同じ答えにたどり着けます。

```text
246 - 256 = -10
```

## 表現範囲と演算の限界

### 7 オーバフロー――器の限界を越えたとき

二の補数によって引き算が加算回路で扱えるようになったとしても、8ビットという「器のサイズ」そのものが広がったわけではありません。
8ビット符号付き整数の限界である「127」に、うっかり1を足してしまったら何が起きるでしょうか。

数学的な正しい答えはもちろん「128」です。しかし、筆算をしてみると予期せぬ結果になります。

```text
  01111111   （ 127）
+ 00000001   （   1）
----------
  10000000   （-128 ！？）
```

最上位ビットに繰り上がりが起きて、先頭が「1」になってしまいました。
この`10000000`を8ビット二の補数として読むと、なんと「-128」です。最大の正の数に1を足した結果、最上位ビットが反転して負の数へと切り替わってしまったのです。

このように、計算結果がデータ型の表現可能な限界値を上（または下）に越えてしまい、まったくデタラメな数値になってしまう現象を**オーバフロー**（桁あふれ）と呼びます。

```text
期待される正しい計算結果:   128
8ビット符号付き整数の上限:  127
実際に保存されたビット列:   10000000
そのビット列の解釈結果:    -128
```

オーバフローが起きたときのコンピュータの振る舞いは、システムや言語によって様々です。何食わぬ顔で計算を続けてしまう言語もあれば、例外エラー（OverflowException）を発生させてプログラムを強制停止させる言語も存在します。
ゲームの得点、銀行の預金残高、宇宙ロケットの軌道制御などでオーバフローを放置すれば、莫大な金銭被害や重大な事故へと直結しかねないのです。

#### オーバフローを検知する論理

二の補数の足し算でオーバフローが発生したかどうかは、足し合わせる2つの数の符号と、結果の符号を見比べることで瞬時に見抜けます。

```text
正の数 ＋ 正の数 ＝ 負の数   → 明らかにオーバフロー！
負の数 ＋ 負の数 ＝ 正の数   → 明らかにオーバフロー！
```

正の数と負の数を足し合わせた場合は、結果の絶対値が必ず元の数より小さくなるため、加算によるオーバフローは原理的に絶対に起きません。

### 8 ビットを左右にずらすシフト演算

二進数の桁の位置関係を利用して、ビット列全体を丸ごと左右にずらす操作を**シフト演算**と呼びます。
十進数で数値を左に1桁ずらして末尾に0を付けると値が10倍になるのと同様に、二進数ではビット列を左に1桁ずらすと値が2倍になる仕組みです。

正の数`00101100₂`（十進数の44）を左へ1ビットずらし、空いた右端に0を入れてみましょう。

```text
元のビット列:   00101100  （44）
左へ1ビット:    01011000  （88 ＝ 44 × 2）
```

各桁の「1」がそれぞれ重みの2倍大きな左隣の桁へ引っ越すため、値が見事に2倍になりました。この操作が**左シフト**です。
掛け算の回路を動かすよりも、配線をずらすだけのシフト演算のほうが圧倒的に高速に処理できるため、プログラムの高速化テクニックとして多用されています。
ただし、左端から「1」が器の外へはみ出してこぼれ落ちてしまうと、当然ながら2倍の計算は成り立ちません。

逆に、ビット列を右へ1ビットずらすと、各桁の重みが半分になるため、正の数であれば2分の1（半分）の計算結果が得られます。

```text
元のビット列:   00101100  （44）
右へ1ビット:    00010110  （22 ＝ 44 ÷ 2）
```

右端からはみ出た端数はそのまま切り捨てられる仕様です。

#### 論理シフトと算術シフトの使い分け

シフト演算には、符号をどう扱うかによって2つの方式が存在します。

1. **論理シフト**：空いた隙間に無条件で「0」を詰め込む方式。単なるビットの並び（データ列やフラグ）を操作したいときに使います。
2. **算術シフト**：数値としての正負の符号を維持しながらシフトする方式。数値を2倍や2分の1にする計算用途で使います。

特に注意が必要なのが、負の数を半分にしたいときの「算術右シフト」です。
二の補数の負数は、先頭ビットが「1」になっています。もし右シフトしたときに空いた左端へ「0」を詰めてしまうと、負の数だったものが突然プラスの正数に化けてしまうわけです。
そこで算術右シフトでは、元の先頭ビット（符号ビット）の値をそのままコピーして左端を埋めるルールです。

```text
元の値:        11111000  （-8）
算術右シフト:  11111100  （-4 ＝ -8 ÷ 2）
               ↑ 先頭の「1」を引き継いで埋める！
```

この工夫のおかげで、負の数であっても符号を壊すことなく、正しく2分の1の計算を行えます。

## 用途に合わせた整数の表現形式

### 9 BCD（二進化十進数）――1円のズレも許さない表現

整数の量をまるごと純粋な二進数に変換する形式のほかに、「十進数の各桁の数字を、4ビットずつ独立して二進数で持つ」という特殊な表現形式も存在します。
たとえば「59」という数値を表現するときは、5と9を別々の4ビットに割り当てる設計です。

```text
十進数の「5」 → 0101
十進数の「9」 → 1001

合成したBCD:    0101 1001
```

この表し方を**BCD**（Binary Coded Decimal、二進化十進数）と呼びます。
通常の二進数と並べて見比べると、その構造の差異は一目瞭然です。

```text
通常の二進数としての 59:  0011 1011
BCDとしての 59:          0101 1001
```

BCDは4ビット（16通り）の器を使いながら、0から9までの10通りしか使わず、残りの`1010`〜`1111`（10〜15）の6パターンを丸ごと捨てています。
そのため、メモリの保存効率という観点では無駄が多く、一見不利に映るかもしれません。

それでもなおBCDが銀行の勘定系システムやPOSレジなどで使われ続けているのは、「人間が使う十進数との間で、一切の変換誤差が出ない」という絶対的な信頼性があるからです。
1バイトに十進数2桁を詰め込む形式を**パック十進数**と呼び、金融や会計の基幹システムを支える重要な技術となっています。

### 10 整数の型を選ぶ判断基準

同じ`11111111`という8ビットのデータであっても、それを255と読むか、-1と読むか、あるいはBCDとして読もうとしてエラーになるかは、プログラマが選択した「データ型」によってすべてが決まるのです。

システムを設計するときは、次の観点から最適な整数の型を選定します。

- 負の値を扱う可能性があるか（符号付きか符号なしか）
- 想定される最小値と最大値はいくらか
- 将来データ量が増加したとき、オーバフローを起こす危険はないか
- 計算の途中で一時的に桁あふれが発生しないか
- 連携する外部システムやデータベースと、ビット幅や解釈のルールが一致しているか

1人の年齢を記録するだけなら8ビット（0〜255）で十分ですが、全利用者のアクセスログの通算秒数をカウントするような変数に小さな型を割り当ててしまうと、数年後に必ずオーバフローを起こして大惨事を招く恐れがあります。
入力される値の範囲だけでなく、「計算の途中経過」と「将来の拡張性」まで見通して適切な器を選ぶこと。
それが、堅牢なシステムを築くための第一歩です。
