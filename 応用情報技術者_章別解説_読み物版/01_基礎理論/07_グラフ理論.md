# 第1章7 グラフ理論――つながりを点と線へ置き換える

## 地図の細部を捨てると、経路が見える

スマートフォンで乗り換え案内やカーナビを使うとき、画面の地図を思い浮かべてみてください。
道路沿いにある建物の形状、コンビニの看板の色、街路樹の並びといった細かな風景は、目的地までの道順を計算する上では一切不要です。
そうした詳細を思い切って削ぎ落とし、「交差点」と「道路」のつながりだけを抜き出すことで、コンピュータは迷うことなく最短ルートを計算できます。

しかし、何でもかんでも捨ててよいわけではありません。
もし「一方通行の矢印」まで消し去ってしまえば、現実には逆走になって通れない道を最短ルートとして案内してしまうでしょう。
あるいは「右折禁止」や「時間帯別の通行規制」といった制約を無視すれば、現場で立ち往生することになります。

現実の細部をすべて抱え込むと計算がパンクし、必要な条件まで捨ててしまうと全く別の問題に変質してしまいます。
現実世界の対象を「点（ノード）」と「線（エッジ）」へと大胆に置き換え、問題の核心だけを美しく抽出する数学的道具。
それが **グラフ理論** です。

## 目的に必要なつながりを残す

### 1 抽象化――必要な関係だけを残す

3つの駅 A、B、C が線路で結ばれている場面を考えてみましょう。
現実の駅には壮大な駅舎があり、改札機が並び、売店や待合室が存在します。
しかし、「どの駅からどの駅へ直接行けるのか」という接続関係だけを知りたいとき、駅舎の見取り図を眺めても意味がありません。

そこで、駅を丸い「点」で表し、それらを結ぶ線路を「線」で表してみます。

```text
A ─────── B ─────── C
```

このように、現実の対象から目的に無関係な情報を削ぎ落とし、必要な特徴や関係性だけを抜き出す思考法を **抽象化** と呼びます。
対象を点、対象同士の関係を線で表した数学的なデータ構造が **グラフ（graph）** です。
統計で使う棒グラフや円グラフとは同音異義語であり、情報科学では「つながりのネットワーク構造」そのものを指します。

グラフを構成する要素には、明確な名前が付いています。

- 点: 頂点（vertex）またはノード（node）
- 線: 辺（edge）またはエッジ

グラフの考え方は交通網にとどまりません。
インターネットの世界ではWebページを頂点、ページ間のハイパーリンクを辺と見なせます。
SNSではユーザーを頂点、友人関係やフォロー関係を辺と対応づけることが可能です。
プロジェクト管理では各作業タスクを頂点、作業の前後関係を辺と見なしてクリティカルパスを導き出します。
一見まったく異なる現実の課題が、「点と線のネットワーク」という共通の土俵の上で統一的に扱えるようになるのです。

### 2 向きがある辺と、ない辺

2つの頂点が線で結ばれているとき、そのつながりに「方向」があるかどうかは極めて重要です。

たとえば友人関係を考えてみましょう。
「お互いに友人として認めている」という双方向の合意を前提にするなら、AさんとBさんの結びつきに向きはありません。
このように、向きを持たない辺で構成されたグラフを **無向グラフ** と呼びます。

```text
A ─────── B
```

一方、Twitter（X）などのフォロー関係や、Webページのリンクはどうでしょうか。
AさんがBさんをフォローしていても、BさんがAさんをフォローし返しているとは限りません。
このような一方通行の関係を表すには、矢印を使って向きを明示する必要があります。
向きを持つ辺（有向辺）で構成されたグラフが **有向グラフ** です。

```text
A ───────> B
```

道路交通網でも、対面通行ができる広い国道なら無向辺、狭い路地の一方通行なら有向辺としてモデル化するのが自然です。
現実のルールが双方向なのか一方通行なのかを見極め、適切なグラフの種類を選択することが設計の第一歩となります。

### 3 辺に距離やコストを付加する

辺の向きを正しく設定しても、複数の迂回路がある場合、どのルートが最適かを決めるにはまだ情報が足りません。

そこで、各辺に「移動にかかるコスト」を表す数値を書き込んでみます。
駅間の所要時間を辺に割り当ててみましょう。

```text
A ──(5分)── B ──(3分)── C
 │                       ^
 └─────────(12分)────────┘
```

このように、辺に割り当てられた数値を **重み（コスト）** と呼び、重みを持つグラフを重み付きグラフ（ネットワーク）と呼びます。

重みに設定する数値は、物理的な距離だけに限りません。
移動時間、電車の運賃、通信ネットワークの遅延時間（レイテンシ）、配管の敷設費用、道路の渋滞度や危険度など、用途に応じて様々な数値を重みとして扱えます。

ここでエンジニアが常に意識すべき原則があります。
「最短経路」を計算する前に、「自分は何を最小化したいのか」という評価基準を定義しなければならないという点です。
物理的な距離が最短のルートと、所要時間が最も短い高速道路ルート、そして運賃が最も安い鈍行ルートは、それぞれまったく別の経路になるケースが日常茶飯事だからです。

## 経路と木の性質を調べる

### 4 経路、閉路、連結

グラフの構造を分析するための基本的な概念を整理しておきましょう。

ある頂点を出発し、辺を順にたどって別の頂点へと進む一連の道筋を **経路（パス）** と呼びます。

```text
A ──> B ──> C
```

経路の中には、出発した頂点と同じ頂点へと一周して戻ってくるループが存在する場合があります。
出発点と終点が一致するこのような経路が **閉路（サイクル）** です。

```text
A ──> B ──> C ──> A   (閉路)
```

無向グラフにおいて、どの2つの頂点を選んでも、辺をたどって互いに行き来できる道筋が存在するとき、そのグラフは **連結（connected）** であるといいます。
もし孤立した頂点や、線路が途切れて行き来できない島が存在するなら、そのグラフは「非連結」です。

有向グラフの場合は向きの制約が加わるため、すべての頂点同士が互いに矢印をたどって行き来できる状態を特に強連結と呼んで区別します。

### 5 次数――1つの頂点に何本の線が集まるか

各頂点に何本の辺が接続しているかという数値も、グラフの特性を測る重要な指標です。
無向グラフにおいて、1つの頂点に接続している辺の本数を **次数（degree）** と呼びます。

```text
    B
    │
C ─ A ─ D
```

上図の中央にある頂点 A には3本の辺が集まっているため、Aの次数は 3 です。
一方、端にある B、C、D の次数はそれぞれ 1 となります。

有向グラフでは矢印の向きがあるため、入ってくる辺の本数を入次数、出ていく辺の本数を出次数と呼び分けて区別します。

ここで、グラフ理論における基本的で美しい定理を1つ紹介しましょう。
「すべての頂点の次数を足し合わせると、グラフ全体の辺の本数のちょうど2倍になる」という性質です。

```text
全頂点の次数の合計 = 2 × 辺の本数
```

理由は極めて明快です。
1本の辺には必ず「両端」の2つの端点があります。
各頂点の次数を数える操作は、すべての辺を両端から1回ずつ、合計2回カウントしていることに他ならないからです。
この定理から、「奇数の次数を持つ頂点の個数は、どんなグラフでも必ず偶数個になる」という面白い法則（握手補題）も導かれます。

### 6 木――閉路を持たない連結グラフ

通信網や道路網を設計するとき、「すべての頂点を互いに行き来できるように繋ぎたいが、無駄なループ（閉路）を作ってコストを浪費したくない」という状況が頻繁に現れます。
このように、連結でありながら閉路を一切持たない無向グラフが、数学における **木（ツリー）** です。

```text
    A
   / \
  B   C
     / \
    D   E
```

木構造には、極めて実用的で強力な特徴が備わっています。

1. 任意の2頂点間を結ぶ経路が、ちょうど1つだけ存在する（もし2通りの迂回路があれば、それらを繋ぐと閉路ができてしまうため）
2. 頂点の数を `n` とすると、辺の本数は必ず `n - 1` 本になる

たとえば上図の木は、頂点が5個（A, B, C, D, E）あり、辺の本数はちょうど `5 - 1 = 4本` になっています。

なぜ必ず `n - 1` 本になるのでしょうか。
最初の頂点が1個だけポツンとある状態では、辺は0本です。
そこへ新しい頂点を木に仲間入りさせるには、既存の頂点のどこか1箇所と新しい辺1本で繋ぐしかありません。
頂点が1つ増えるたびに、辺がちょうど1本ずつ増えていくため、頂点が `n` 個になれば辺の総数は必ず `n - 1` 本になるのです。
もし1本でも余分に辺を足せばループ（閉路）が生まれ、1本でも削ればグラフがバラバラに分裂して非連結になってしまいます。

### 7 根付き木

木構造の頂点の中から、特別な「出発点（頂点）」を1つ選び出して一番上に配置したものが根付き木です。
最上位に置かれた頂点を根（ルート）、その直下にぶら下がる頂点を子、子の視点から見た上の頂点を親、子を持たない末端の頂点を葉（リーフ）と呼びます。

```text
       [ 根: A ]
        /     \
    [ 子: B ] [ 子: C ]
               /     \
           [ 葉: D ] [ 葉: E ]
```

根付き木は、コンピュータの世界の至る所で階層構造を表現するために使われています。
ファイルシステムのフォルダ階層、会社の組織図、HTMLのDOMツリー、JSONデータの構造などが代表例です。

ただし、現実世界の関係を木構造でモデル化する際には注意が必要です。
たとえば会社組織において「1人の社員が複数の部署を兼務している」ような場合、親が2人存在することになるため、厳密な木構造の前提が崩れてしまいます。
現実の制約が本当に木の定義に収まっているかを検証する姿勢が大切です。

## 個別の移動と全体の接続を最適化する

### 8 最短経路問題――2点間の移動コストを最小化する

重み付きグラフ上で最も代表的な応用問題が、**最短経路問題**です。
指定された出発点から目的地まで、経由する辺の重みの合計が最小となるルートを見つけ出す課題を指します。

```text
A ──(2)── B ──(3)── D
 │                   ^
 └──(4)── C ──(2)────┘
```

AからDへ向かう2つのルートを比較してみましょう。

- ルート1（上回り）: A → B → D （コスト: 2 + 3 = 5）
- ルート2（下回り）: A → C → D （コスト: 4 + 2 = 6）

合計コストを比べると、ルート1のほうが小さいため、AからDへの最短経路は A → B → D と求まります。

辺の重みがすべて0以上（マイナスの重みがない）という条件下では、ダイクストラ法（Dijkstra's Algorithm）と呼ばれるアルゴリズムが極めて効率的です。
出発点に近い頂点から順に最短距離を確定させていく手法であり、カーナビのルート探索やインターネットのルーティングプロトコル（OSPFなど）の心臓部として日常を支えています。

### 9 最小全域木――ネットワーク全体の敷設コストを最小化する

最短経路問題と並んで重要なのが、**最小全域木（Minimum Spanning Tree: MST）** の問題です。

たとえば、点在する複数の集落すべてに光ファイバー網を敷設する工事を想像してください。
どの集落からも他のすべての集落と通信できるようにケーブルを張り巡らせたいが、工事費用は全体として極力安く抑えたい、という状況です。

グラフに含まれるすべての頂点を網羅しながらループを作らない木を全域木（全域ツリー）と呼びます。
そして、無数に描ける全域木の中で、使われるすべての辺の重み（工事費）の合計が最小になるものが最小全域木です。

ここで初心者が最も陥りやすい誤解を解いておきましょう。
「最短経路」と「最小全域木」は、目的が根本から異なります。

```text
最短経路問題:
  「特定の2地点間」の移動コストを最小化する（自分ひとりの移動時間の最適化）

最小全域木問題:
  「ネットワーク全体を維持する辺の総コスト」を最小化する（インフラ工事全体の最適化）
```

最小全域木はインフラ全体の合計費用を最小化するため、特定の2つの集落の間を行き来しようとすると、わざわざ遠回りさせられる経路になることが珍しくありません。
個別の利便性を最大化するのか、それともシステム全体の維持コストを最小化するのかという目的の違いを明確に区別して解法を選ぶ必要があります。

最小全域木を求める代表的なアルゴリズムには、コストの安い辺から閉路を作らないように順次採用していくクラスカル法や、接続済みのグループから最も安く伸びる辺を順次追加していくプリム法が代表的です。

## グラフの保存とモデルの妥当性

### 10 隣接行列で保存する

数学的なグラフの構造をプログラムで表現するアプローチには、主に2つの方式が存在します。
1つ目が、二次元配列（表）の形式で接続関係を保持する **隣接行列** です。

頂点 A、B、C があり、A-B間、A-C間に辺があるグラフを考えてみましょう。
縦軸と横軸に全頂点を並べ、辺が存在するマスに1、存在しないマスに0を書き込む形式をとります。

```text
      A   B   C
  ┌─────────────
A │   0   1   1
B │   1   0   0
C │   1   0   0
```

無向グラフの場合、「AからBへ行けるならBからAへも行ける」ため、対角線を中心にして対称な行列になります。
自分自身へ戻る辺（自己ループ）がなければ、対角線上の値はすべて0です。

隣接行列の最大の利点は、「頂点Xと頂点Yが直接繋がっているか」を調べる処理が、行列の座標を1箇所参照するだけ（計算量 `O(1)`）で瞬時に判定できる点にあります。
一方で、頂点の数が `n` 個あると、たとえ辺が1本も存在しなくても `n × n = n²` 個のメモリ領域を消費してしまいます。
頂点の数が数万、数百万に達する巨大なグラフでは、メモリの浪費が激しく実用になりません。

### 11 隣接リストで保存する

辺の数が少なくスカスカなグラフ（疎グラフ）を扱う際に威力を発揮するのが、2つ目の表現形式である **隣接リスト** です。

隣接リストでは、全頂点の組み合わせを総当たりで保持する代わりに、各頂点に対して「自分から直接繋がっている相手の頂点だけを並べたリスト」を管理します。

```text
A: [ B, C ]
B: [ A ]
C: [ A ]
```

隣接リストの強みは、メモリ消費量を「頂点の数 + 実際の辺の数」だけに最小限に抑えられる点です。
また、「頂点Aから伸びている隣の駅をすべて走査する」といった処理も、リストを先頭から順に辿るだけで無駄なく完了します。
現実の道路網やSNSの人間関係は、頂点数に比べて辺の数がごくわずかな疎グラフであることが大半であるため、実務の多くの場面では隣接リストが第一選択となるわけです。

| 比較項目 | 隣接行列 | 隣接リスト |
|---|---|---|
| メモリ使用量 | `O(V²)` （頂点数の2乗） | `O(V + E)` （頂点数 + 辺の数） |
| 2頂点間の接続確認 | 極めて高速（`O(1)`） | リストの探索が必要（`O(次数)`） |
| 隣接する全頂点の走査 | 遅い（全頂点をチェック） | 高速（実際の接続先だけ走査） |
| 適したグラフの性質 | 辺が密集した密グラフ | 辺がまばらな疎グラフ（現実の多く） |

### 12 現実をグラフへ落とし込むときの設計判断

アルゴリズムの計算がどれほど高速で正確であっても、現実世界をグラフに落とし込むモデル化の前提が間違っていれば、得られる答えはまったく役に立ちません。

たとえばカーナビの経路探索システムを設計する場合、次のような現実の制約をどうモデルへ反映させるべきでしょうか。

- 一方通行の標識を正しく有向辺として反映できているか
- 交差点の「右折禁止」や「Uターン禁止」は、単なる頂点と辺だけで表現できるか（進入元の道路と脱出先の道路の組み合わせ制約が必要ではないか）
- 朝夕の通勤ラッシュによる所要時間の変動を、固定の重みとして扱ってよいか
- 事故や大雪による通行止めの情報を、リアルタイムに辺のコストへ反映できるか

SNSの分析でも、双方向の「友達承認」と一方通行の「フォロー」を混同して同じ無向グラフとして扱ってしまえば、正確な人間関係のネットワークは浮かび上がりません。

道路地図から建物の形状を省いても問題なかったのは、それが「経路の計算結果」に影響を与えない無関係な情報だったからです。
一方で、一方通行の向きを省くことが許されないのは、それが「経路の正しさ」そのものを根本から左右する決定的な条件だからです。

現実をグラフへと抽象化するときは、「何を削ぎ落とし、何を残したのか」を、解くべき問題の目的に照らして常に厳しく吟味しなければなりません。
この取捨選択の洞察力こそが、グラフ理論を道具として使いこなすエンジニアの真の武器となります。
