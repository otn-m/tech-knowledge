# 第1章9 数値計算と最適化――ぴったり解けない問題へ近づく

## 正しい式があっても、正確な答えは出ない

学生時代に習った数学の世界では、方程式には必ず「解の公式」や「因数分解」が用意され、ノートの上に綺麗な分数や根号で答えを書き出すのが当たり前でした。
しかし、コンピュータが現実の社会やビジネスで解かされる問題の多くは、紙と鉛筆では綺麗に解けない方程式や、厳密に解こうとすれば宇宙の寿命よりも長い時間がかかる巨大な問題ばかりです。

たとえば、`x² = 2` を満たす正の数 `x`（すなわち `√2`）を求めてみましょう。
`1.4² = 1.96`、`1.42² = 2.0164` ですから、真の解は 1.4 と 1.42 の間にあることが分かります。
どれほど計算桁数を増やしていっても、`1.41421356...` と無限に不規則な数字が続くだけで、有限桁しか扱えないコンピュータのメモリの中に「真の `√2`」がぴったり収まる瞬間は永遠に訪れません。

このように、現実のエンジニアリングでは「寸分違わぬ真の解」を求めることは諦め、目的を達成するのに十分な精度を持った「近似解」をいかに素早く、安全に導き出すかが勝負となります。
近似計算を行う際には、単に計算結果の数値を眺めるだけでは不十分です。
「真の値とどれほどのズレ（誤差）が残っているか」「これ以上計算を続けても意味がないと判断する停止基準は何か」を論理的に見極めなければなりません。
完璧な正解が存在しない不確実な世界で、実用的な最適解へと少しずつ歩み寄っていくための技術体系。
それが、数値計算と最適化の世界です。

## 変化と蓄積を関数で表す

### 1 関数は「入力から出力を決める規則」

あらゆる数値シミュレーションや最適化の出発点となるのが「関数」という概念です。
難しく考える必要はありません。
1個120円の缶コーヒーを `x` 個買う場面を想像してみましょう。
支払うべき代金 `y` 円は、次のシンプルな規則によって決まります。

```text
y = 120x
```

個数 `x` に具体的な値を1つ指定すれば、代金 `y` もただ1つの値として確定するわけです。

```text
x = 1 → y = 120
x = 2 → y = 240
x = 3 → y = 360
```

このように、入力を1つ決めると出力がただ1つに決まる対応関係を **関数** と呼び、一般に次のように書き表します。

```text
y = f(x)
```

ここで記号 `f` は Function（機能・関数）の頭文字をとった関数の名前にすぎません。
`f(x)` は「入力 `x` を関数 `f` のルールに従って処理した結果の値」を意味しており、決して `f` と `x` を掛け算しているわけではない点に注意してください。
プログラミング言語における「引数を受け取って戻り値を返す関数」と、数学の関数はまったく同じ考え方で成り立っています。

### 2 変化の速さを見る微分

日常の現象をモデル化するとき、現在の値そのものだけでなく、「値がどれほどの勢いで変化しているか」という変化の速さを捉えたい場面が頻繁に訪れます。
静止した状態から走り出した自動車の走行距離を、ストップウォッチで計測してみましょう。

```text
時刻 0秒: 走行距離  0m
時刻 2秒: 走行距離 10m
```

この最初の2秒間における平均の速さは、小学校で習ったとおり次の計算で求まります。

```text
距離の変化量 ÷ 時間の変化量
= (10 - 0)m ÷ (2 - 0)秒
= 5m/秒
```

グラフの上にプロットすれば、時刻0秒の点と時刻2秒の点を結んだ直線の「傾き」に他なりません。

しかし、自動車の速度メーターは2秒間の平均値を示しているわけではありません。
アクセルを踏み込んだ「まさに今、この瞬間」のスピードを表示しているはずです。
この瞬間の速度を知るにはどうすればよいでしょうか。

時間の幅を2秒から1秒、0.1秒、0.01秒、0.0001秒……と極限までゼロに近づけていけば、測定される平均速度は「その瞬間の変化の速さ」へと限りなく近づいていきます。
このように、ある関数の「ごくわずかな入力の変化に対する、出力の瞬間の変化率」を求める数学的操作が **微分** です。

関数 `y = f(x)` を微分して得られる新しい関数を導関数と呼び、`f'(x)`（エフプライムエックス）や `dy/dx`（ディーワイ・ディーエックス）と表記します。

#### 具体例: y = x² の変化率を求める

微分がどのような計算を行っているのかを実感するために、放物線 `y = x²` の瞬間の傾きを手計算で導いてみましょう。
ある入力 `x` から、ごくわずかな幅 `h` だけ右に進んだ点 `x + h` までの平均変化率を組み立てます。

```text
((x + h)² - x²) / h
```

ここで分母の幅 `h` をゼロに近づけていくわけですが、いきなり `h = 0` を代入すると「0除算」になって計算が破綻してしまいます。
そこで、代入に先立って分子の括弧を展開し、式を整理してみましょう。

```text
((x + h)² - x²) / h
= (x² + 2xh + h² - x²) / h    分子を展開
= (2xh + h²) / h              x² と -x² が打ち消し合う
= h(2x + h) / h               分子を共通因数 h でくくる
= 2x + h                      h ≠ 0 なので分母・分子の h を約分
```

綺麗に約分された式 `2x + h` が手元に残りました。
この段階になって初めて、幅 `h` を限りなく 0 へと近づける極限操作（`h → 0`）を実行します。
すると、末尾の `h` が消え去り、次のシンプルな結果が得られます。

```text
2x
```

したがって、関数 `y = x²` の任意の地点 `x` における瞬間の傾きは、常に `2x` で計算できることが分かりました。
たとえば `x = 3` の地点であれば傾きは `2 × 3 = 6` ですし、原点 `x = 0` であれば傾きは `0`（水平）となります。

微分は単なる机上の計算にとどまりません。
走行する乗り物の加速度の算出、ロケットの弾道軌道計算、そして後述する「AIの機械学習において、損失関数が最小になる方向へとパラメータを更新する勾配降下法」の心臓部として、現代のIT社会を根底から支えています。

### 3 小さな面積を足す積分

瞬間の変化率を割り出す「微分」に対して、まったく逆向きの視点を持つのが「積分」です。
刻一刻と変化する自動車のスピードメーターの数値を眺めながら、「これまで走行してきた全体の移動距離」を復元したい場面を考えてみましょう。

車の速度はアクセルやブレーキの踏み込みによって常に変動していますが、もし時間を「0.1秒ごと」という極めて短い区間に細かく刻めば、そのごく短い区間内だけは「一定のスピードで走っていた」とみなすことができます。
短い区間の移動距離は、「その区間の速度 × 経過時間（0.1秒）」という単純な掛け算で近似できるはずです。

```text
各微小区間の移動距離 ≈ 区間の速度 × 微小時間
全体の移動距離 ≈ 各区間の微小な移動距離をすべて足し合わせる
```

時間を細かく刻めば刻むほど、長方形で近似した面積の段差は消え去り、真の移動距離へと収束していきます。
このように、細かく刻んだ微小な量を足し合わせ、その極限として全体の蓄積量（グラフと横軸で囲まれた面積）を求める操作が **積分** です。

微分が「細かな変化の勢いを調べる虫眼鏡」であるなら、積分は「バラバラに散らばった細かな変化をかき集めて全体像を復元する望遠鏡」といえます。
微分と積分は、一定の滑らかな条件下において互いに表裏一体の逆演算関係（微分積分学の基本定理）で結ばれています。

## 方程式と積分を数値で近似する

### 4 数値計算が必要になる理由

高校までの数学では、微分や積分の公式を駆使して、数式変形だけで答え（数式としての解）を導き出す訓練を重ねてきました。
しかし、現実の工学問題に登場する複雑な方程式や微分方程式のほとんどは、人間が手作業で解の公式を導き出すことが数学的に不可能（解析解が存在しない）であることが証明されています。

また、理論上は厳密解が存在する問題であっても、10万行×10万列の巨大な連立一次方程式を解の公式（クラメルの公式など）で解こうとすれば、天文学的な計算回数を要して現実的な時間内には絶対に終わりません。

そこでエンジニアは発想を転換します。
「綺麗な数式で一発で解くことは諦め、コンピュータの圧倒的な計算速度を活かして、反復計算（ループ処理）によって実用上十分な精度の近似解へ少しずつ近づけていこう」
このアプローチこそが **数値計算（数値解析）** です。

ただし、コンピュータによる近似計算には、常に次のシビアな問いがつきまといます。

- 繰り返しの計算によって、本当に正しい答えへ近づいているのか（発散していないか）
- 得られた値と真の解との間に、どれほどの誤差が残っているのか
- 計算の精度と計算速度のトレードオフをどこで切り上げるべきか
- コンピュータ特有の「浮動小数点の丸め誤差」が蓄積して、答えが狂っていないか

これらの疑問に答えるための代表的なアルゴリズムを見ていきましょう。

### 5 二分法で方程式の解を探す

方程式 `f(x) = 0` の解（グラフが横軸と交差する点）を数値的に見つけ出す最も頑健で分かりやすいアルゴリズムが「二分法」です。

例として、冒頭で触れた `x² - 2 = 0`（すなわち `x = √2`）の正の解を探す手順を追いかけてみましょう。
関数 `f(x) = x² - 2` に、手始めに `x = 1` と `x = 2` を代入してみます。

```text
f(1) = 1² - 2 = -1  （負の値）
f(2) = 2² - 2 = +2  （正の値）
```

`x = 1` ではグラフは横軸より下にあり、`x = 2` では横軸より上にあります。
この関数が途中で途切れることなく滑らかにつながっている（連続である）以上、1 と 2 の間のどこかで必ず横軸（値が 0 になる点）を横切っているはずです（中間値の定理）。

そこで、区間 `[1, 2]` のちょうど真ん中にある中点 `x = 1.5` を調べてみます。

```text
f(1.5) = 1.5² - 2 = 2.25 - 2 = +0.25  （正の値）
```

中点での値は正でした。
もともと負だったのは `x = 1` ですから、真の解は「負と正が切り替わる区間」、すなわち `[1, 1.5]` の中に存在することが確定します。
探索すべき範囲が、最初の半分の広さに絞り込まれました。

```text
探索区間: [1, 2] → [1, 1.5]
```

続いて、新しい区間の中点である `x = 1.25` を調べます。

```text
f(1.25) = 1.25² - 2 = 1.5625 - 2 = -0.4375  （負の値）
```

今度は中点の値が負になりました。
直近で正だったのは `x = 1.5` ですから、解が含まれる範囲は `[1.25, 1.5]` へとさらに半分に絞り込まれます。

```text
探索区間: [1, 1.5] → [1.25, 1.5]
```

このように、「解を挟み込む2点の中点を計算し、符号をチェックして探索区間を半分に縮める」操作をひたすら繰り返すアルゴリズムが **二分法** です。

二分法の最大の強みは、その絶対的な安定性といえるでしょう。
初期区間の両端で符号が異なってさえいれば、ステップを踏むごとに探索区間の幅が `1/2, 1/4, 1/8, 1/16...` と機械的に確実に狭まり、必ず解へと収束していきます。
10回繰り返せば誤差の幅は約 1/1,000 に、20回繰り返せば約 100万分の1 にまで絞り込めます。

反面、収束のスピードは一歩一歩が一定の歩幅（線形収束）であるため、後述するニュートン法のような爆発的な高速性はありません。
また、グラフが横軸に接して跳ね返るような重解（符号が反転しない解）を見つけることは苦手です。

### 6 ニュートン法

二分法が「確実に両側から解を挟み込んでジワジワ追い詰める亀」だとすれば、関数の傾きを利用して解に向かって猛スピードで跳躍する兎が「ニュートン法（ニュートン・ラフソン法）」です。

ニュートン法のアイデアは、実に直感的といえます。
現在いる地点において、関数の接線を引き、その接線が横軸（y = 0）とぶつかった交点を「次の探索候補地点」とするアプローチです。

方程式 `f(x) = 0` に対するニュートン法の更新公式は、次のように定義されます。

```text
次の x = 現在の x - (f(x) / f'(x))
```

ここで `f'(x)` は現在の地点における関数の傾き（微分）です。
現在の高さ `f(x)` を傾きで割ることで、接線が横軸に到達するまでに進むべき補正量を直接計算できるわけです。

実際に `f(x) = x² - 2`、傾き `f'(x) = 2x` を用いて、初期値 `x₀ = 2` からスタートしてみましょう。

```text
1回目の更新:
x₁ = 2 - (2² - 2) / (2 × 2)
   = 2 - 2 / 4
   = 1.5
```

たった1回の計算で、二分法で数ステップ要した `1.5` に到達しました。
得られた `1.5` を使って、2回目の更新を行います。

```text
2回目の更新:
x₂ = 1.5 - (1.5² - 2) / (2 × 1.5)
   = 1.5 - 0.25 / 3
   ≈ 1.5 - 0.08333
   ≈ 1.4167
```

なんと、わずか2回の反復計算で、真の値 `√2 ≈ 1.41421...` に対して小数第2位まで正確な値が叩き出されました。
さらに3回目の計算を行えば `x₃ ≈ 1.41421568` となり、瞬く間に有効桁数が倍々ゲームで倍増していくのが大きな特徴です（2次収束）。

しかし、この圧倒的な速さには相応のリスクも潜んでいます。
もし探索の途中で傾きが水平に近い点（`f'(x) ≈ 0`）に遭遇すると、0除算に近い状態となって候補点が大きく吹き飛んで発散しかねません。
また、初期値の選び方が悪いと、目的の解とは全く異なる別の根へ迷い込んだり、複数の候補点の間を無限に往復して振動し続けたりする危険があります。

実務のライブラリでは、「まずは二分法で解の近くまで大雑把に安全に絞り込み、最後の数桁の追い込みにニュートン法を適用する」といったハイブリッドな手法が広く採用されています。

### 7 台形則で面積を近似する

方程式の解法だけでなく、定積分の計算（グラフの下の面積）も数値計算の独壇場です。
複雑な関数や、実験によって離散的に得られた観測データ（毎秒のセンサログなど）の積分値を求める手法として最も基本となるのが「台形則」です。

区間 `[0, 2]` における曲線 `y = x²` の面積を近似してみましょう。
区間を幅 1 で2分割し、3つの境界点を用意します。

```text
x = 0 → y = 0
x = 1 → y = 1
x = 2 → y = 4
```

各区間において、曲線の両端を直線で結び、できた「台形」の面積を計算して合算します。
台形の面積公式は「幅 × (上底 + 下底) ÷ 2」です。

```text
区間 [0, 1] の台形面積: 1 × (0 + 1) ÷ 2 = 0.5
区間 [1, 2] の台形面積: 1 × (1 + 4) ÷ 2 = 2.5
合計面積: 0.5 + 2.5 = 3.0
```

数学の積分公式を使って求めた厳密な理論値は、`[x³/3]₀² = 8/3 ≈ 2.667` です。
粗い2分割の台形近似であっても、真値 2.667 に対して `3.0` という近い値が得られました。

分割数をもっと増やして幅を 0.1 や 0.01 へと細かくしていけば、曲線と台形の斜辺との隙間は急速に埋まり、近似精度は飛躍的に向上します。
ただし、分割数を極端に増やせば計算時間が増大するだけでなく、後述する浮動小数点の足し算による「丸め誤差」が何百万回も蓄積してしまうため、分割の細かさには最適なバランスが存在します。

## 誤差と停止条件を判断する

### 8 誤差を分けて考える

数値計算を行うエンジニアにとって、誤差は単に排除すべき対象にとどまらず「性質を理解して正しく制御すべき要素」です。
コンピュータの計算結果に生じるズレは、その発生原因によって明確に分類されます。

#### 打切り誤差
アルゴリズムの都合上、本来であれば無限に続けるべき計算を有限回で途中で打ち切ったり、曲線を直線で近似したりすることによって生じる構造的な誤差です。
二分法やニュートン法を一定回数でストップしたときの残差や、台形則で曲線を直線で結んだときの隙間がこれに該当します。
計算回数（反復回数や分割数）を増やすことで小さく抑えることができます。

#### 丸め誤差
コンピュータのメモリが有限桁（64ビットのIEEE 754浮動小数点数など）しかないために、表現しきれない最下位ビットを四捨五入（丸め処理）することによって不可避に生じる微小な誤差です。
打切り誤差を減らそうとして分割数を何千万回にも増やしすぎると、逆にこの微小な丸め誤差が膨大に積み重なり、計算結果が崩壊する逆転現象が生じます。

#### 入力誤差
シミュレーションの前提として外部から入力されたセンサの測定値や、観測データそのものに最初から含まれていたノイズや測定精度の限界です。
どれほど完璧な数値計算アルゴリズムを用意しても、入力された初期データ以上の確かさを後から作り出すことは原理的に不可能です（Garbage In, Garbage Out）。

#### 絶対誤差と相対誤差

誤差の大きさを測る物差しには、2つの表現形式があります。

```text
絶対誤差 = |近似値 - 真値|
相対誤差 = 絶対誤差 ÷ |真値|
```

たとえば、測定値に「1メートル」の絶対誤差が含まれていたとします。
もし東京から福岡までの距離（約1,000キロメートル）を測定しているなら、1メートルのズレなど皆無に等しい極微な誤差（相対誤差 0.0001%）です。
しかし、机の横幅（2メートル）を測定しているときに生じた1メートルのズレは、致命的な欠陥（相対誤差 50%）となります。

数値計算の精度を議論する際は、単なる絶対誤差の数値だけでなく、「対象の大きさに対してどれほどの比率のズレなのか」を表す相対誤差を常に意識しなければなりません。
なお、真値がゼロである場合は相対誤差を定義できないため、絶対誤差を用いるか、業務ドメインで定めた基準値で正規化して評価します。

### 9 収束と停止条件

反復計算によって得られる値が、計算ステップを重ねるにつれてある一定の値へと落ち着いていく現象を **収束** と呼びます。
逆に、値が無限に増大したり、激しく振動して定まらない状態が「発散」です。

プログラムが無限ループに陥ることなく、適切なタイミングで安全に計算を完了させるためには、信頼できる「停止条件」をあらかじめ設計しておかなければなりません。
実務で用いられる代表的な停止判定には、次の4種類があります。

1. 前回と今回の候補値の差が、許容値 `ε`（エプシロン）を下回ったとき（`|xₙ₊₁ - xₙ| < ε`）
2. 方程式の関数値（残差）の絶対値が、十分にゼロに近づいたとき（`|f(x)| < ε`）
3. 二分法などの探索区間の幅が、許容幅より狭くなったとき（`|b - a| < ε`）
4. 計算ステップ数が、あらかじめ設定した「最大反復回数（Max Iterations）」に到達したとき

ここで陥りやすい重大な落とし穴があります。
「前回と今回の値の差が小さくなったからといって、必ずしも正しい解に到達したとは限らない」という点です。
極めて平坦な関数の谷底の近くでは、解から遠く離れているにもかかわらず、アルゴリズムの歩幅だけが極端に縮小して計算が停滞してしまう現象（偽の収束）が起こり得ます。

したがって、実務の堅牢なコードでは、候補値の変化量だけでなく「残差 `|f(x)|` が実際にゼロに近いか」を併せて検証し、万が一の暴走を防ぐために最大反復回数の上限ガードを必ず設ける多重防御が鉄則となります。

## 制約の中でよい解を選ぶ

### 10 最適化――制約の中で目的を最善にする

方程式の解を探す技術と並び、工学やビジネスの意思決定で極めて重要な役割を果たすのが「最適化」です。
方程式を解くのが「条件をぴったり満たす1点を探す作業」だとすれば、最適化は「無数に存在する選択肢の中から、限られた制約を守りつつ、最も都合のよい最高の選択肢を選び出す作業」といえます。

たとえば、工場で2種類の製品Aと製品Bを製造している場面を考えてみましょう。
倉庫にある原料の在庫量や工場の稼働時間には、物理的な上限（制約）が存在します。
その縛りの中で、会社の合計利益を極限まで大きくすることを目指すわけです。

この問題を数学的に定式化する際、中核となる2つの概念を整理しておきましょう。

- **目的関数**: 最大化（または最小化）したいターゲットを数値で表した数式（例: 合計利益、輸送コスト、電力消費量）
- **制約条件**: 守らなければならない現実の制約やルールの壁（例: 原料の在庫量、納期、労働時間、予算）

```text
目的関数: 利益 = 300x + 200y を最大化する
制約条件: 2x + y ≤ 8   （原料の制約）
          x + 2y ≤ 8   （作業時間の制約）
          x ≥ 0, y ≥ 0 （生産数はマイナスにならない非負条件）
```

すべての制約条件をクリアした「製造可能な組み合わせ `(x, y)`」全体の集合を **実行可能領域** と呼びます。
この実行可能領域の海の中から、目的関数の値を最も大きくしてくれる最高の1点を見つけ出すこと。
それが最適化問題のゴールといえます。

### 11 線形計画法

目的関数も制約条件も、すべて変数の1次式（直線や平面の式）で表現できる最適化問題を「線形計画問題」と呼び、それを解く数学的手法を **線形計画法（LP: Linear Programming）** といいます。

先ほどの工場の例を、2次元のグラフ（x軸を製品Aの個数、y軸を製品Bの個数）の上に図示してみましょう。
それぞれの制約不等式を描き出すと、原点を含む多角形のエリア（実行可能領域）が浮かび上がります。

この実行可能領域の角（頂点）を整理したのが、次の4点です。

```text
頂点1: (0, 0)  何も作らない
頂点2: (4, 0)  Aだけを4個作る
頂点3: (0, 4)  Bだけを4個作る
頂点4: (8/3, 8/3)  2つの制約直線の交点
```

線形計画問題には、美しく強力な基本定理が存在します。
「もし実行可能領域が存在し、有限の最適解があるならば、最適解は必ず領域の境界の頂点（角）のいずれかに存在する」という性質です。

なぜなら、利益を表す目的関数の等高線（傾きが決まった直線）を実行可能領域の中で平行移動させていくと、領域から最後に離れていく点は必ず「多角形の尖った頂点」になるからです。
したがって、無数にある領域内の点すべてを調べる必要はなく、数個の頂点における利益を計算して比較するだけで勝負がつきます。

| 実行可能領域の頂点 `(x, y)` | 利益 `Z = 300x + 200y` の計算 | 合計利益 |
|:---:|:---:|:---:|
| `(0, 0)` | `300×0 + 200×0` | 0円 |
| `(4, 0)` | `300×4 + 200×0` | 1,200円 |
| `(0, 4)` | `300×0 + 200×4` | 800円 |
| `(8/3, 8/3)` | `300×(8/3) + 200×(8/3)` | 1,333.3円 |

表を比較すれば、頂点 `(8/3, 8/3)` を選んだときに最大利益 1,333.3円 が得られることが一目瞭然です。

変数が数十万個にも及ぶ実務の大規模な物流計画やサプライチェーン最適化では、多面体の頂点を効率よく辿っていく「シンプレックス法（単体法）」や、領域の内部を突っ切って最適解に迫る「内点法」といった高度なアルゴリズムが活躍しています。

ただし、現実の製品は「8/3個（約2.67個）」のように小数の個数で作ることはできません。
解を整数に限定する条件が加わった問題を「整数計画問題」と呼びます。
小数の解を単に四捨五入するだけでは制約を違反してしまう恐れがあり、計算の難易度が爆発的に跳ね上がる（NP困難な問題になる）点に注意が必要です。

### 12 局所最適と大域最適

関数の形状が直線から離れ、複雑に波打つ曲線や曲面になったとき、最適化の難度は一気に跳ね上がります。
霧が深く立ち込めた山脈の中で、最も標高の高い頂上（最高峰）を目指して歩いている登山者を想像してください。

足元の地面の傾斜（勾配）を調べ、上り坂の方向へと一歩ずつ歩みを進めていけば、確実に周囲より高い場所へと到達できます。
しかし、ようやく辿り着いたそのピークは、山脈全体の中では小さな前衛峰にすぎず、谷を隔てた遠くの場所に遥かに高い真の最高峰がそびえ立っているかもしれません。

最適化の用語では、この2つの頂上を次のように区別します。

- **局所最適解（ローカルオプティマム）**: 周囲のごく近い範囲の中だけで見れば最も優れているが、全体で見ると最高とは限らない解
- **大域最適解（グローバルオプティマム）**: 探索可能な全領域の中で、名実ともに最も優れている真の最善解

微分の傾き情報だけを頼りに進むシンプルなアルゴリズム（勾配降下法や山登り法）は、最初に足を踏み入れたスタート地点（初期値）の近くにある局所最適解の窪みに一度ハマってしまうと、自力ではそこから抜け出せなくなる弱点を抱えています。

もし問題の形状がお椀のような形（凸関数）をしているならば、「局所最適解 ＝ 大域最適解」となるため、安心して勾配法を適用できるのが大きな強みです。
しかし、ニューラルネットワークの学習のように無数の峰と谷が入り組んだ非凸な問題では、あえて坂を下るランダムな動きを許容する「焼きなまし法（シミュレーテッド・アニーリング）」や、生物の進化を模倣して複数の候補を同時に探索させる「遺伝的アルゴリズム」といったメタヒューリスティクスが動員されます。

エンジニアの実務においては、途方もない計算時間をかけて真の大域最適解を100%の保証付きで追い求めることよりも、「現実的な締め切り時間の中で、実用上95点といえる十分によい解を確実に手に入れる」という妥協のバランス感覚が極めて重要といえるでしょう。

## 複数の量と変換を一度に計算する

### 13 ベクトル――複数の数を一組として扱う

ここまでは1つの変数 `x` を中心に扱ってきましたが、現実のシステムでは数十から数百万個のパラメータが同時に相互作用しながら変化します。
このような多次元のデータを整然と処理するための共通言語が「線形代数（ベクトルと行列）」です。

平面上の地図における位置座標や、画面上のキャラクターの移動量を表す場面を考えてみましょう。
位置を表すには、「横方向（x軸）に3」「縦方向（y軸）に2」という2つの数値がセットで必要になります。

```text
(3, 2)
```

このように、複数の数値を特定の順序でひとまとめに並べた数学的オブジェクトが **ベクトル** です。
プログラミングにおける「配列」や「リスト」に数学的な演算規則を与えたものと解釈できるでしょう。

ベクトル同士の足し算は、対応する同じ位置の成分同士を足し合わせるだけで完了します。
位置 `(3, 2)` にいるキャラクターが、移動ベクトル `(1, -1)` に沿って歩いた後の新しい位置を求めてみましょう。

```text
(3, 2) + (1, -1)
= (3 + 1,  2 + (-1))
= (4, 1)
```

数式の上では単なる数字の足し算ですが、幾何学的には「矢印と矢印を連結して合成する」という直感的な物理現象をそのまま表現しています。

### 14 行列――数を長方形に並べる

ベクトルが「数字を1列に並べたもの」であるなら、数字を縦横の長方形の格子状に並べたものが **行列** です。
行列は単なるデータの保管庫にとどまらず、空間上のベクトルを受け取って別のベクトルへと変形・回転させる「変換マシン」としての強力な役割を担っています。

2行2列の正方行列の例を見てみましょう。

```text
┌  0  -1 ┐
└  1   0 ┘
```

この行列を、先ほどのベクトル `(3, 2)` に掛け算してみます。
行列の「上の行」とベクトルを掛けて足し合わせることで新しい横成分を求め、「下の行」とベクトルを掛けて足し合わせることで新しい縦成分を算出します。

```text
新しい x成分 = (0 × 3) + (-1 × 2) = -2
新しい y成分 = (1 × 3) + ( 0 × 2) =  3
```

計算結果として、新しいベクトル `(-2, 3)` が得られました。
方眼紙の上に元の点 `(3, 2)` と新しい点 `(-2, 3)` を描いてみると、原点を中心にして反時計回りに「きっかり90度だけ回転」していることが分かります。
つまり、この行列は「あらゆる2次元座標を90度回転させる変換規則」だったわけです。

行列を用いれば、3DゲームのCGレンダリングにおけるカメラ視点の回転や拡大縮小、画像処理のフィルタリング、巨大な連立一次方程式の解法、そして大規模言語モデル（LLM）における数千億個の重みパラメータの並列計算に至るまで、すべてを極めて高速かつエレガントに一括処理できるようになります。

#### 行列の掛け算における最大の鉄則: 順序を変えてはならない

通常の数値の掛け算では、掛ける順番を入れ替えても結果は変わりません（`3 × 5 = 5 × 3 = 15`）。
しかし、行列の掛け算においては、この常識は完全に通用しません。

```text
行列 A × 行列 B ≠ 行列 B × 行列 A  （一般には一致しない）
```

幾何学的な直感で考えれば、この非可換性は当たり前の事実です。
「右に5メートル移動してから、反時計回りに90度回転する」という操作と、
「反時計回りに90度回転してから、右に5メートル移動する」という操作では、
最終的に立っている場所が全く異なるはずです。

数式の上で行列を扱う際も、「どの変換を、どのような順番でデータに作用させているのか」という因果の順序を常に正確に意識しなければなりません。

完璧な解を求めることが不可能な現実世界において、微分と積分で現象のダイナミクスを捉え、二分法やニュートン法で実用的な近似解を手繰り寄せ、制約の中で最適な意思決定を下し、行列とベクトルで多次元の空間を自在に操る。
この数値計算と最適化の技術基盤こそが、不完全なコンピュータを地上最強の知的ツールへと押し上げるための翼なのです。
