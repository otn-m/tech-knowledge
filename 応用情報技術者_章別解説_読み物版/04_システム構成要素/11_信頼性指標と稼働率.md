# 第4章 第11話 信頼性指標と稼働率

稼働率99.9%という数値は、一見するとほとんど停止しない極めて健全なシステムのように感じられます。
しかし、これを1年間の累積時間に換算した場合、許容される年間ダウンタイムは約8時間46分にも及ぶ計算です。
同じ8時間半の停止であっても、深夜のメンテナンス時間帯に分散して生じる場合と、月末決算の締切直前に一括して発生する場合とでは、ビジネスに及ぼす打撃の深刻さが大きく異なります。

システムが「止まりにくい」という抽象的な信頼性を定量的に測るためには、故障の発生頻度、復旧に要する時間、およびコンポーネント同士の接続形態を業務要件へ関連づけることが不可欠です。

## 信頼性の評価軸を分ける

### 1 RASIS

情報システムの総合的な信頼性を客観的に評価する際、単なるハードウェアの壊れにくさだけでなく、可用性、修復の容易さ、データの完全性、セキュリティといった複数の側面を明確に区別して評価します。
これら5つの代表的な評価基準の英頭文字を組み合わせた古典的な評価指標が**RASIS**です。

### 2 Reliability（信頼性）

所定の動作環境と運用条件の下で、指定された期間にわたってシステムが故障することなく正常に機能し続ける能力がReliability（信頼性）です。
「どれだけ故障を起こしにくいか」を評価する尺度であり、平均故障間隔（MTBF）や故障率を用いて定量的に測定されます。

### 3 Availability（可用性）

故障の少なさを表す信頼性に対し、エンドユーザーが必要とした際にいつでもシステムが利用可能な状態にある性質をAvailability（可用性）と呼びます。
仮に故障が発生したとしても、わずか数十秒で予備系へフェイルオーバーできれば、業務上の利用不能時間を極小化することが可能です。
障害の発生頻度そのものに加えて、障害検知から修復・切り替え完了までの初動の迅速さが可用性の高低を大きく左右します。

### 4 Serviceability（保守性）

障害発生時の迅速な復旧を支える基盤がServiceability（保守性）です。
障害の早期検知、原因究明の迅速化、および部品交換やリストア手順の簡易性を備えている度合いを指します。

活線挿抜（ホットスワップ）への対応、詳細なログ出力による問題個所の迅速な切り分け、標準化された復旧マニュアルの存在などがその具体例です。
保守用の交換部品と専門技術者をオンサイトへ迅速に手配できるサポート体制も、保守性の実効性を担保する重要な要素といえます。

### 5 Integrity（完全性）

システムがどれほど無停止で稼働し続けていても、データベースが誤った数値を記録したり、残高の計算ミスを頻発させたりするようでは信頼に値しません。
格納されたデータや処理結果に矛盾や欠落がなく、権限のない不正な改ざんから正しく保護されている状態がIntegrity（完全性）です。
いつでもアクセスできる可用性と、データの内容が正しいことを保証する完全性の2軸を混同してはなりません。

### 6 Security（安全性・機密性）

悪意ある第三者による不正アクセス、情報漏えい、データの改ざん、サービス妨害攻撃からシステムリソースを堅牢に防護する能力がSecurity（安全性）です。
古典的なRASISでは災害対策や事故防止の意味合いも含めて語られましたが、現代のIT環境においては情報セキュリティの基本要件（機密性・完全性・可用性）と密接に連動した防護能力として位置づけられます。

RASISはこれら5つの特性を足し合わせて単一の得点を算出するための計算式ではありません。
多角的な視点からアーキテクチャの潜在的な弱点やボトルネックを洗い出すための網羅的なチェックリストとして活用されます。

## 正常に動く時間と復旧時間を測る

### 7 MTBF

「壊れにくさ」と「直しやすさ」を定量的なメトリクスへ変換するためには、正常稼働と故障発生のタイムラインを客観的に記録することが第一歩です。
修理を行いながら反復して稼働させ続ける機器やシステムにおいて、故障から次の故障が発生するまでの平均連続稼働時間を**MTBF**（Mean Time Between Failures、平均故障間動作時間）と呼びます。

あるサーバの連続稼働時間が3回の観測でそれぞれ100時間、140時間、120時間であった場合、平均稼働時間は次のように算出されます。

```text
MTBF = (100+140+120)÷3
     = 360÷3
     = 120時間
```

これは120時間が経過するごとに必ず故障するという確定的な予測ではありません。
同一環境における多数回の運用実績や、同型マシンを大規模に並列稼働させた際の統計的な平均値を示しています。

### 8 MTTF

修理を行わずに新品へ丸ごと交換して使い捨てる部品やコンポーネントでは、運用開始から最初の故障に至るまでの単一期間を測定対象とします。
稼働開始から寿命によって故障に至るまでの平均動作時間がMTTF（Mean Time To Failure、平均故障時間）です。

実務の現場ではMTBFとMTTFという用語が厳密に区別されずに混用されるケースも見受けられます。
修理を前提として繰り返し稼働させるシステムなのか、それとも故障時に新品へ丸ごと交換する部品なのかという前提の確認が重要です。

### 9 MTTR

システムの信頼性を評価するためには、正常に動いていた時間だけでなく、障害発生からサービスが完全に再開するまでの所要時間も正確に測定しなければなりません。
故障が発生した時点から、原因調査、部品交換、データリストアを完了して正常稼働へ復帰するまでの平均所要時間を**MTTR**（Mean Time To Repair、平均修復時間）と呼びます。
3回の障害復旧にそれぞれ1時間、3時間、2時間を要した場合の平均値は次の通りです。

```text
MTTR = (1+3+2)÷3 = 2時間
```

障害の物理的発生、アラート検知、保守要員の駆けつけ、切り替え完了のどのタイムスタンプを測定の起点と終点にするかによって数値は大きく変動します。
実務の運用監視においては、計測の起点と終点に関する共通ルールの統一が不可欠です。

## 稼働率を利用可能な時間から求める

### 10 稼働率

MTBFが十分に長く、MTTRが極めて短ければ、ユーザーがシステムをいつでも利用できる時間の割合は100%に近づきます。
修理を繰り返しながら稼働するシステムの基本サイクルを、正常稼働と修復の交互の連続としてモデル化してみましょう。

```text
正常に動く MTBF時間 → 故障 → 修理する MTTR時間 → 再開
```

1サイクルの全所要時間は`MTBF+MTTR`であり、そのうち実際に業務へ供された時間はMTBFであるため、システムの**稼働率**（アベイラビリティ）は次の公式で導出されます。

```text
稼働率 = MTBF ÷ (MTBF + MTTR)
```

#### 例

MTBFが1,000時間、MTTRが10時間であるシステムの稼働率は次の試算の通りです。

```text
1,000÷(1,000+10)
= 1,000÷1,010
≈ 0.990099
≈ 99.01%
```

MTBFを延長するか、あるいはMTTRを短縮することで、システムの稼働率は確実に向上します。

### 11 MTTR短縮の効果

故障の発生頻度そのものを変えずに、復旧の初動と作業時間を短縮させた場合の可用性向上効果を検証してみましょう。
MTBFを1,000時間に固定したまま、MTTRを10時間から1時間へと劇的に圧縮したシナリオを計算します。

```text
1,000÷(1,000+1)
≈ 99.9001%
```

ハードウェアの故障率を下げることは容易ではありませんが、待機系への自動フェイルオーバー、ホットスワップ機構、手順書の整備によってMTTRを削り込むアプローチは、可用性向上において極めて強力な手段です。

### 12 停止率と年間停止時間

パーセンテージの数値上はわずかな差に見えても、年間の許容停止時間へと換算し直すことで、ビジネスへの許容度をリアルに判定できます。
稼働率が99.9%である場合、システムが停止している時間の割合（停止率）は次の通りです。

```text
100%-99.9%=0.1%=0.001
```

年間日数を365日（8,760時間）として、稼働率99.9%における年間許容ダウンタイムを算出した結果が次の計算です。

```text
365×24 = 8,760時間
8,760×0.001 = 8.76時間
```

冒頭で触れた約8時間46分という停止時間は、この数式から導出されます。
代表的な数値を比較すると、「9」の桁数（ナインの数）が1つ増えるごとに、年間で許容されるダウンタイムはおおむね10分の1に激減する計算です。

| 稼働率 | 年間停止時間の概算 |
|---:|---:|
| 99% | 87.6時間、約3日15時間36分 |
| 99.9% | 8.76時間、約8時間46分 |
| 99.99% | 0.876時間、約52.6分 |
| 99.999% | 0.0876時間、約5.26分 |

## 要素のつながりと故障の独立性

### 13 直列システムの稼働率

単一コンポーネントの稼働率と、複数のコンポーネントが連結されたシステム全体の稼働率は異なります。
処理の成立に双方の要素の正常稼働が必須であり、互いの故障が確率論的に独立である場合、システム全体の稼働率は各要素の稼働率の積（掛け算）で求まります。
「Aが健全に稼働している」かつ「Bも健全に稼働している」という同時確率を計算するためです。

```text
A 0.99 ─ B 0.98

全体 = 0.99×0.98
     = 0.9702
     = 97.02%
```

直列に連結されるコンポーネントの数が増えるほど、システム全体の総合稼働率は個々の構成要素の稼働率よりも確実に低下していきます。

### 14 並列システムの稼働率

いずれか一方が健全であれば処理を継続できる並列構成では、「全系統が同時に故障する確率」を1から差し引く余事象の考え方を用いて計算します。
「少なくとも一方が稼働している確率」を直接足し合わせるよりも、背反事象を引く方が計算手順をシンプルに整理できるためです。
各系統の稼働率が99%（停止率が1%=0.01）である並列システムの稼働率は、次のように求まります。

```text
両方停止 = 0.01×0.01 = 0.0001
全体稼働 = 1-0.0001 = 0.9999 = 99.99%
```

独立した2系統の稼働率をAおよびBとおいた場合の並列稼働率の一般公式が次の式です。

```text
並列稼働率 = 1 - (1-A)(1-B)
```

### 15 直列と並列が混ざる計算

直列接続と並列接続が混在した複合システムでは、部分的な並列ブロックを先に解きほぐして単一の仮想ブロックへ集約していく手順を踏みます。
稼働率99%のWebサーバ2台が並列化され、その背後に稼働率98%のDBサーバ1台が直列に連結された構成を想定してみましょう。
第1ステップとして、二重化されたWeb層の並列稼働率を求めます。

```text
1-(1-0.99)²
= 1-0.0001
= 0.9999
```

第2ステップとして、算出したWeb層の稼働率とDBサーバの稼働率を直列に掛け合わせます。

```text
0.9999×0.98
= 0.979902
≈ 97.99%
```

Web層をどれほど手厚く二重化してもDB層が単一障害点（SPOF）であれば、システム全体の可用性はDBの稼働率によって厳しく制約される道理です。

### 16 独立という前提

並列構成によって飛躍的な可用性向上が得られるという数理モデルは、各コンポーネントの故障が互いに完全に独立しているという厳格な前提に立脚しています。
二重化された2台のサーバが同一の電源ライン、同一のラックスイッチ、同一の建物を共有していた場合、共通のインフラ障害によって両系統が一網打尽に停止する共倒れリスクが高まります。
同一のOSやミドルウェアの未知のバグ、設定ファイルの配布ミス、共通管理者権限の誤操作もまた、二重化を無効化する共通原因故障の典型例です。

共通原因の存在を無視して独立性を仮定した計算式を無批判に適用すると、机上の稼働率を危険なレベルで過大評価してしまいます。
物理的なハードウェアを2台並べたという外形的事実だけでは、真の耐障害性を達成したことの証明にはなりません。

## 故障率と寿命の関係

### 17 故障率とFIT

単位稼働時間あたりにコンポーネントが故障する比率を故障率と呼び、数理モデル上は記号λで表されるのが通例です。
待ち行列理論における到着率と同じ記号が使われますが、工学的な文脈は明確に区別されます。
偶発故障期のように故障率が時間経過に対してほぼ一定であると仮定できる環境下では、MTBFと故障率の間に成立する逆数関係が次の数式です。

```text
MTBF ≈ 1÷故障率
```

半導体集積回路などの高信頼性デバイスでは、10億時間（10の9乗時間）あたりの故障回数を示す指標としてFIT（Failures In Time）が広く利用されます。
ある集積回路の故障率が100FITである場合の具体的な換算手順を確認してみましょう。

```text
故障率 = 100÷1,000,000,000
         = 0.0000001 /時間
MTBF ≈ 1÷0.0000001
     = 10,000,000時間
```

これは単一の半導体チップが1,000万時間にわたって生き続けるという意味ではありません。
数万個以上のサンプルを加速試験などで観測し、統計的な故障頻度を標準化した理論値です。

### 18 バスタブ曲線

工業製品の稼働時間と故障率の推移をグラフにプロットすると、洋式浴槽の断面に酷似したU字型のカーブを描くのが特徴です。
この代表的な故障特性グラフを**バスタブ曲線**と呼びます。

```text
故障率
高 |＼                 ／
   |  ＼_____________／
低 +--------------------→ 時間
    初期   偶発故障期   摩耗期
```

#### 初期故障期

製造工程の潜在的欠陥や部品の初期不良が稼働直後に一気に表面化し、エージング（慣らし運転）の進行とともに故障率が急速に低下していく期間です。

#### 偶発故障期

初期不良が取り除かれ、突発的かつランダムな外乱によって一定の低い故障率で安定稼働を継続する期間です。
指数分布や一定故障率に基づく理論計算を適用できる期間に該当します。

#### 摩耗故障期

部品の物理的摩耗、熱ストレス、経年劣化によって故障率が加速度的に跳ね上がる期間です。
この段階に突入する前に計画的な予防保守と部品リプレースを実行しなければなりません。
MTBFを静的な固定値として捉え、製品寿命の全期間にわたって一律に適用することは重大な誤謬です。

## 復旧とデータ損失の目標を決める

### 19 RTOとRPO

稼働率は年間の累積ダウンタイムを大所高所から測る指標であるため、個別のインシデントにおける事業継続計画（BCP）の目標値は別途定義しなければなりません。
大規模障害が発生した時点から、業務を許容可能な水準まで再開させるまでの目標復旧時間を**RTO**（Recovery Time Objective）と定義します。
一方、障害発生時に過去どの時点までのデータ損失を許容するかという目標指標を**RPO**（Recovery Point Objective、目標復旧時点）と呼びます。

```text
最後の復旧可能時点 ----- 障害 ----- 再開
        ← RPO →            ← RTO →
```

仮に要件が「RTO 1時間、RPO 5分」と定められている場合、障害発生から1時間以内にシステムを再稼働させ、失われるデータの巻き戻しを最大でも過去5分以内に封じ込めるアーキテクチャが必要です。
日次1回の深夜バッチバックアップ運用では最大24時間分のデータが欠損するため、RPO 5分の要件を到底達成できません。
バックアップからのリストアとデータ整合性検証に3時間を要するのであれば、RTO 1時間の合意も未達に終わります。

### 20 数字を業務へ戻す

稼働率99.9%を達成しているシステムであっても、年間許容停止の全8時間半が年度末の決済締め切り直前に発生した場合、企業活動に致命的な破滅をもたらします。
たとえ合計停止時間が同一であっても、1分間の小規模な瞬断が年間526回頻発する環境では、ユーザーからの信頼失墜は避けられません。
同じ稼働率という単一の数字であっても、停止が発生する業務領域、時間帯、機能の重要度によってビジネスへの影響は天と地ほど変化します。

計画停止を計算母数に含めるか否か、部分的な機能縮退を何割の稼働率としてカウントするか、夜間帯を除外するかといった合意形成を関係者間で事前に確立しておくことが不可欠です。
許容不可能な高レイテンシやデータの不整合をシステム停止とみなすかどうかも運用基準の分かれ目となります。
数理モデルは設計を支援する強力な道具ですが、ビジネスへの許容限度を定義する最終判断は常に人間側の要件定義に委ねられているわけです。
