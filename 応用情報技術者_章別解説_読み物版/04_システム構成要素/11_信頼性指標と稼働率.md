# 第4章 第11話 信頼性指標と稼働率

稼働率99.9%は、ほとんど止まらない数字に見えます。
1年間へ換算すると、許される停止は約8時間46分です。
同じ停止時間でも、深夜の数分停止と締切直前の8時間停止では、業務への影響が違います。

「止まりにくい」を数字で表すには、故障の間隔、復旧の速さ、構成要素のつながりを、対象業務へ結び付けます。

## 信頼性の評価軸を分ける

### 1 RASIS

システムの評価では、壊れにくさだけでなく、利用できること、直しやすいこと、正しい結果とデータ、安全性を分けます。
5つの観点の頭文字を並べたものが、**RASIS**です。

### 2 Reliability（信頼性）

決められた条件の下で、一定期間にわたり故障せず正しく働く性質が、Reliability、信頼性です。
「どれだけ壊れにくいか」を、平均故障間隔や故障率などで見ます。

### 3 Availability（可用性）

壊れにくさに対し、必要なときに利用できる性質が、Availability、可用性です。
故障しても1分で直れば、利用不能時間は短くなります。
故障の少なさに加えて、修理や切替えの速さが影響します。

### 4 Serviceability（保守性）

修理や切替えを支えるのが、Serviceability、保守性です。
故障を見つけ、原因を特定し、修理、交換、復旧をしやすい性質を指します。

動作中に部品を交換できること、ログから原因箇所を絞れること、交換手順が簡単なことが該当します。
保守部品と担当者をすぐに用意できることも、復旧のしやすさにつながります。

### 5 Integrity（完全性）

止まらず動いていても、預金残高を誤って返せば、良いシステムとはいえません。
データや処理結果が正しく、欠けず、許可なく変更されていない性質が、Integrity、完全性です。
利用できることを表す可用性と、正しいことを表す完全性を区別します。

### 6 Security（安全性）

不正利用、情報漏えい、改ざん、破壊などから守られる性質が、Security、安全性です。
「事故を起こさない安全性」と訳す古い説明もありますが、現代の試験では、情報セキュリティの機密性、完全性、可用性などとの関係も意識します。

RASISは、これらを1つの点数へまとめるものではありません。
5つの観点から弱点を探す確認表です。

## 正常に動く時間と復旧時間を測る

### 7 MTBF

「壊れにくい」「直しやすい」を測れる量へ変えるため、まず故障と故障の間にどれだけ正常動作を続けたかを見ます。
修理して使い続ける装置で、故障から次の故障まで平均して正常に動く時間が、**MTBF**、Mean Time Between Failuresです。
**平均故障間動作時間**、平均故障間隔などと呼びます。

3回の正常動作時間が100時間、140時間、120時間なら、平均は120時間です。

```text
MTBF = (100+140+120)÷3
     = 360÷3
     = 120時間
```

120時間ごとに必ず故障するという予言ではありません。
多数回、または多数台を観測した平均です。

### 8 MTTF

修理せず、寿命で交換する部品では、故障までの1回を測ります。
故障するまで平均して動く時間が、**MTTF**、Mean Time To Failureです。

MTBFとMTTFは文脈で混用されることがあります。
修理して繰り返す系か、故障までの1回を測るかを区別します。

### 9 MTTR

故障の間隔に加えて、復旧までの時間も測ります。
故障してから修理して復旧するまでの平均時間が、**MTTR**、Mean Time To Repairです。
復旧時間が1時間、3時間、2時間なら、平均は2時間です。

```text
MTTR = (1+3+2)÷3 = 2時間
```

障害の発生、検知、担当者到着のどこを測定開始とするかによって、値は変わります。
運用では定義をそろえます。

## 稼働率を利用可能な時間から求める

### 10 稼働率

故障の間隔が長く、復旧が短ければ、利用できる時間の割合は大きくなります。
修理可能な単純モデルで、正常動作と修理を合わせた1周期を考えます。

```text
正常に動く MTBF時間 → 故障 → 修理する MTTR時間 → 再開
```

全時間は`MTBF+MTTR`、利用できる時間はMTBFなので、**稼働率**は次の式で求めます。

```text
稼働率 = MTBF ÷ (MTBF + MTTR)
```

#### 例

MTBFが1,000時間、MTTRが10時間なら、次のようになります。

```text
1,000÷(1,000+10)
= 1,000÷1,010
≈ 0.990099
≈ 99.01%
```

MTBFを長くするか、MTTRを短くすると、稼働率は上がります。

### 11 MTTR短縮の効果

故障頻度を変えず、復旧だけを速くする効果を見ます。
MTBFを1,000時間のまま、MTTRを10時間から1時間へ短くします。

```text
1,000÷(1,000+1)
≈ 99.9001%
```

自動切替え、交換しやすい設計、監視、手順の改善でも、可用性を大きく上げられます。

### 12 停止率と年間停止時間

稼働率では小さく見える差も、停止時間に戻すと、業務に許せる長さかを判断できます。
稼働率99.9%なら、停止率は次のとおりです。

```text
100%-99.9%=0.1%=0.001
```

1年を365日として、年間停止時間へ換算します。

```text
365×24 = 8,760時間
8,760×0.001 = 8.76時間
```

冒頭の約8時間46分は、この計算から得られます。
代表値を比べると、9が1つ増えるごとに、許される停止時間はおおむね10分の1になります。

| 稼働率 | 年間停止時間の概算 |
|---:|---:|
| 99% | 87.6時間、約3日15時間36分 |
| 99.9% | 8.76時間、約8時間46分 |
| 99.99% | 0.876時間、約52.6分 |
| 99.999% | 0.0876時間、約5.26分 |

## 要素のつながりと故障の独立性

### 13 直列システムの稼働率

1台の稼働率と、利用者が通るサービス全体の稼働率は異なります。
2つの要素が両方動く必要があり、互いの故障が独立なら、全体稼働率は掛け算です。
「Aが動く、かつ、Bも動く」という2条件が同時に成立する確率だからです。

```text
A 0.99 ─ B 0.98

全体 = 0.99×0.98
     = 0.9702
     = 97.02%
```

要素を直列に増やすほど、全体稼働率は各部品より低くなります。

### 14 並列システムの稼働率

AかBのどちらか一方が動けばよい構成では、反対の「両方止まる」確率を1から引きます。
直接「少なくとも一方が動く」を数えるより、計算を整理できます。
各稼働率が99%、停止率が1%=0.01なら、次のようになります。

```text
両方停止 = 0.01×0.01 = 0.0001
全体稼働 = 1-0.0001 = 0.9999 = 99.99%
```

一般に、独立な2台の稼働率がA、Bなら、こちらの式です。

```text
並列稼働率 = 1 - (1-A)(1-B)
```

### 15 直列と並列が混ざる計算

直列と並列が混ざる場合は、部分ごとに計算します。
各稼働率99%のWebサーバ2台が並列で、その先に98%のDBが1台だけあるとします。
まずWebの並列部分を求めます。

```text
1-(1-0.99)²
= 1-0.0001
= 0.9999
```

次に、DBとは直列なので掛け合わせます。

```text
0.9999×0.98
= 0.979902
≈ 97.99%
```

Webを二重化してもDBが1台なら、全体はDBの稼働率に強く制限されます。

### 16 独立という前提

並列構成の大きな改善は、故障が独立しているという前提に支えられます。
2台が同じ電源、建物、通信回線を共有すると、同時停止が増えます。
同じソフトウェアの欠陥、誤設定、管理権限も、共通の故障原因になります。

共通原因故障があるのに単純式だけを使うと、稼働率を過大評価します。
2台を並べたという事実だけでは、独立性を確かめたことになりません。

## 故障率と寿命の関係

### 17 故障率とFIT

単位時間当たりに故障する割合を**故障率**と呼び、`λ`で表すことがあります。
待ち行列の到着率にもλを使いますが、文脈は異なります。
故障率が一定という単純モデルでは、次の関係です。

```text
MTBF ≈ 1÷故障率
```

**FIT**、Failures In Timeは、10億時間当たりの故障数を表します。
100FITなら、次のように換算します。

```text
故障率 = 100÷1,000,000,000
         = 0.0000001 /時間
MTBF ≈ 1÷0.0000001
     = 10,000,000時間
```

1個が1000万時間動くまで実際に試すという意味ではありません。
多数の部品の観測と統計から表します。

### 18 バスタブ曲線

機器の寿命に伴う故障率を時間順に描くと、浴槽の断面に似ることがあります。
この形を**バスタブ曲線**と呼びます。

```text
故障率
高 |＼                 ／
   |  ＼_____________／
低 +--------------------→ 時間
    初期   偶発故障期   摩耗期
```

#### 初期故障期

製造不良や接続不良などが早期に現れ、時間とともに減ります。

#### 偶発故障期

比較的一定の低い故障率が続くと見なします。
一定故障率の計算を適用しやすい期間です。

#### 摩耗故障期

劣化や消耗で故障率が上がるため、寿命前の交換が必要です。
MTBFの一定値を、全寿命へ無条件に当てはめません。

## 復旧とデータ損失の目標を決める

### 19 RTOとRPO

稼働率は長い期間で利用できた割合なので、個々の障害の復旧目標は別に決めます。
障害後に何時間以内でサービスを再開するかという目標が、**RTO**、Recovery Time Objective、目標復旧時間です。
障害時点から過去何分までのデータ損失を許すかという目標が、**RPO**、Recovery Point Objective、目標復旧時点です。

```text
最後の復旧可能時点 ----- 障害 ----- 再開
        ← RPO →            ← RTO →
```

RTOが1時間、RPOが5分なら、障害から1時間以内に再開し、失うデータを原則5分以内へ抑える仕組みが必要です。
毎日1回のバックアップでは最大約24時間分を失うため、RPO 5分を満たしません。
復元に3時間掛かれば、RTO 1時間も満たしません。

### 20 数字を業務へ戻す

稼働率99.9%でも、重要な締切の10分前に8時間止まれば、大きな損害になります。
1分の停止が年間526回ある場合も、利用者体験は悪くなります。
同じ割合でも、止まる業務、時間帯、使えなくなる範囲によって影響が変わります。

計画停止を含めるか、一部機能や一部地域の停止をどう数えるか、何時から何時までを対象にするかを決めます。
応答が遅すぎる状態や、データの誤りを停止と見なすかも、定義する条件です。
数式は設計を助けますが、業務影響の定義は人が決めます。

稼働率の小数点以下に9を増やすこと自体が目的ではありません。
故障間隔、復旧時間、共通原因、RTO、RPOを業務の許容範囲へ結び付け、その数字が必要な信頼性を表すかを判断します。
