# 第4章 第2話 クライアントサーバとWeb

通販サイトで商品名を入力すると、画面にはすぐ結果が現れます。
利用者には1回の操作に見えますが、その裏では画面、業務処理、データベースが順に仕事を受け渡しています。
どこかが返事をしなければ、利用者から見えるのは同じ「待ち」です。

そこで、機械の大きさではなく、誰が何を頼み、誰が応えるかという役割から構成を捉えます。

## 1 要求と応答

クライアントサーバシステムの基本は、**要求**と**応答**です。

```text
クライアント                     サーバ
   | 「商品123を見せて」  要求 →   |
   | ← 応答 「価格は500円」         |
```

要求には、何をしてほしいか、対象、必要なデータ、利用者を確かめる情報などが入ります。
応答には、結果、成功したか失敗したか、失敗した場合の理由などが入ります。

ネットワークでは、要求が届かない、処理は終わったが応答だけ届かない、途中で時間切れになることがあります。
「返事がない」と「相手が何もしなかった」は同じではありません。

## 2 機能を分ける三つの層

要求と応答だけでは、サーバの内部で何が起きたかまでは分かりません。
見せる仕事、判断する仕事、保存する仕事に分けると、変更や障害の影響を追えるようになります。

業務システムの仕事を、次の3種類に分けて考えます。

### 2.1 プレゼンテーション層

利用者に画面を見せ、入力を受け取る役割です。
presentationは「見せ方」です。

### 2.2 ファンクション層

業務の規則に従って判断し、計算する役割です。
例えば、割引条件、在庫確認、注文可能かの判断です。
**業務処理層**、**アプリケーション層**とも呼ばれます。

### 2.3 データベースアクセス層

データベースに読取りや書込みを頼む役割です。
保存方法の違いを、上の業務処理から隠します。

```text
プレゼンテーション層 → ファンクション層 → データベースアクセス層
       見せる               判断する                 保存する
```

ここでいう**層**は、役割の段階です。
3層だから必ず3台の機械が必要、という意味ではありません。
1台に3層を置くことも、1層を100台に広げることもあります。

## 3 二層クライアントサーバ

役割を分けても、必ず別々の機械へ置く必要はありません。
まず、画面と業務処理をクライアントにまとめる構成から見ます。

クライアントが画面と多くの業務処理を持ち、データベースサーバに直接接続する構成を考えます。

```text
クライアント                 DBサーバ
画面＋業務処理 ─────────→ データ保存
```

これが代表的な**2層クライアントサーバ**です。

### 長所

- 小規模なら構造が分かりやすい。
- クライアント側で処理するため、ローカル処理の応答を速くできる。
- 専用画面を豊かに作れる。

### 短所

- 各端末にプログラムを配り、更新する必要がある。
- 多数端末がDBに直接接続し、接続数や負荷が集中する。
- DBの構造変更が端末プログラムに広く影響する。
- 端末にDB接続情報や大きな権限を置く危険がある。

## 4 三層クライアントサーバ

利用者が少ないうちは、クライアントからDBへ直接つなぐ単純さが利点になります。
利用者や変更が増えると、その単純さが、端末更新とDB接続の集中として効いてきます。

画面、業務処理、データ保存を3つの役割に分けます。

```text
クライアント      アプリケーションサーバ       DBサーバ
   画面      →          業務処理          →      保存
```

### 長所

- 業務ルールを中央のアプリケーションサーバで更新しやすい。
- クライアントにDBの詳細を見せずに済む。
- 各層を必要に応じて別々に増やせる。
- 責任の境界を決めやすい。

### 短所

- 通信する段階が増える。
- どの層で遅延や障害が生じたか調べる必要がある。
- アプリケーションサーバが新しい集中点になる。
- 設計、監視、配備が複雑になる。

## 5 ストアドプロシージャ

データベース側に保存し、そこで実行する一まとまりの手続を**ストアドプロシージャ**と呼びます。
storedは保存された、procedureは手続です。

例えば、送金で次を1つの手続にします。

1. 送金元の残高を減らす。
2. 送金先の残高を増やす。
3. 履歴を記録する。

DBの近くでまとめて実行すれば、通信の往復を減らし、データ整合性を保ちやすくなります。
一方、処理が特定DB製品に強く結び付く、業務ルールがアプリとDBに分散する、DBに負荷が集中するという注意があります。

## 6 RPCで離れた処理を関数のように呼ぶ

層を分ければ、離れた相手へ処理を頼む場面が増えます。
呼出し方を関数に似せることはできても、通信の不確かさまでは消せません。

**RPC**、Remote Procedure Callは、別のコンピュータにある手続を、近くの関数を呼ぶような形で依頼する仕組みです。

```text
合計を求める(商品123, 2個)
        ↓ 通信へ変換
遠隔サーバで計算
        ↓ 応答
結果1000円
```

見た目を単純にできますが、本当のローカル関数とは違います。

- 通信で時間が掛かる。
- 相手や回線が止まる。
- 同じ要求が重複する。
- 送れるデータ形式に変換する必要がある。
- 相手だけ処理済みで、返事を失う場合がある。

遠隔呼出しを「絶対に成功する普通の関数」と考えないことが重要です。

## 7 Webシステム

ブラウザで開くWebシステムも、要求する側と応える側を分けた構成です。
画面の手軽さの裏側に、これまで見た層と遠隔呼出しがあります。

WebページやWebアプリを提供する構成が**Webシステム**です。

- **Webブラウザ**は、利用者の端末でWebの文書や画面を表示し、操作を受けます。
- **Webサーバ**は、ブラウザからのHTTP要求を受け、文書や結果を返します。

```text
Webブラウザ → Webサーバ → アプリケーション → DB
             HTTP
```

URLで場所を指定し、HTTPで要求と応答をやり取りする基本は、[第2章のWebプログラミング](../02_アルゴリズムとプログラミング/19_Webプログラミング.md)で扱いました。

## 8 静的なページと動的なページ

保存済みのHTMLや画像をそのまま返すものを、**静的コンテンツ**と呼びます。

利用者、時刻、データベースの内容に応じて作る結果を、**動的コンテンツ**と呼びます。

```text
静的: 会社案内.html を読む → そのまま返す
動的: 注文履歴を要求 → DB検索 → その人用HTMLを作る
```

動的処理は便利ですが、アプリやDBの負荷、入力の安全確認、障害点が増えます。

## 9 状態をどこへ置くか

Webサーバを増やせば、要求を多くさばけそうです。
ところが、買物かごを特定の1台だけが覚えていると、要求を別のサーバへ振り分けた瞬間に内容が消えて見えます。

HTTPの1回1回の要求は、基本的に別の要求として扱えます。
しかし、ログイン済みか、買物かごに何が入っているかという**状態**は、要求をまたいで覚える必要があります。

状態を各Webサーバだけに置くと、次の要求が別サーバに送られたときに失われます。

対策には次があります。

- 同じ利用者を同じサーバに送る。
- 共有の状態保存先に置く。
- 状態を安全な印付きデータとしてクライアントに持たせる。
- どのサーバでも再現できるよう設計する。

共有保存先を使えば引き継げますが、その保存先が新しい性能ボトルネックや単一障害点になり得ます。

## 10 シンクライアント

端末側の保存や処理を少なくし、主な処理や管理をサーバ側に寄せる仕組みが**シンクライアント**です。
thinは薄い、つまり端末の役割が軽いという意味です。

### 長所

- 端末に重要データを残しにくい。
- 更新と管理を中央に集めやすい。
- 端末の交換を簡単にしやすい。

### 短所

- サーバと通信への依存が大きい。
- サーバに利用が集中する。
- 映像、音声、特殊機器で使い勝手が落ちる場合がある。

「端末が安い」だけでなく、サーバ、回線、ライセンス、運用を含むコスト性能比とTCOで比べます。

## 11 ピアツーピア

固定した1台だけがサーバになるのではなく、参加する機器同士が対等に機能やデータを提供し合う形が**ピアツーピア**、P2Pです。
peerは同等の仲間です。

```text
端末A ↔ 端末B
  ↕       ↕
端末C ↔ 端末D
```

中央への集中を減らし、参加台数の資源を利用できます。
一方、参加と離脱、データの所在、信頼、著作権、安全性、全体管理が難しくなります。

## 12 サーバへの利用集中

仕事を中央へ寄せる構成は、更新と管理をそろえやすくします。
同時に、利用が増えたときの待ちも中央へ寄せます。

クライアントを増やしても、サーバの処理能力が変わらなければ待ちが増えます。

1台が毎秒100件処理でき、毎秒120件来続ければ、差の20件が毎秒列にたまります。

```text
到着 120件/秒 - 完了 100件/秒 = 毎秒20件増加
```

一時的な集中なら列で吸収できます。
しかし永遠に能力を上回るなら、列は永遠に伸びます。
サーバ増設、処理削減、キャッシュ、受付制限、後回し処理などが必要です。

クライアントサーバ構成を読むときは、箱の台数だけを数えません。
要求の経路、役割の境界、状態の置き場所、集中する負荷を追うと、1回の操作の裏にある設計判断が見えてきます。

## 確認問題

1. クライアントとサーバは機械の大きさで決まりますか。
2. プレゼンテーション、ファンクション、DBアクセスの3層を説明してください。
3. 2層構成で多数端末がDBに直接接続する問題を2つ答えてください。
4. ストアドプロシージャの長所と注意を1つずつ答えてください。
5. RPCを普通の関数と同じだと考えてはいけない理由を2つ答えてください。
6. Webサーバ2台の各メモリにログイン状態を置くと何が起きますか。
7. 毎秒80件処理できるサーバに、毎秒95件が継続到着します。
   列は毎秒何件増えますか。

## 解答と解説

1. **解答**：いいえ。
   要求する側か、提供する側かという役割で決まります。
2. **解答**：画面と入力、業務判断、データ保存へのアクセスという役割です。
3. **解答**：接続、負荷集中、端末更新の手間、DB変更の影響、接続情報、権限の危険などです。
4. **解答**：通信を減らし整合性を保ちやすい一方、DB製品依存やDBへの負荷集中などがあります。
5. **解答**：通信遅延、切断、相手の停止、重複、応答だけの消失があるためです。
6. **解答**：別サーバに振り分けられたとき状態を読めず、ログアウトしたように見えるなどの問題が起きます。
7. **解答**：`95-80=15`なので毎秒15件増えます。
